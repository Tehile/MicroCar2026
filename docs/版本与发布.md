| `RemoteControl/code_competition - V6+/` | 前一步 | 5 个 | 远程档刚移植完，保留作对照 |

`code_competition - V6++` 是单工程五 Target：

| Target | Define | 产物 | 用途 |
|---|---|---|---|
| `V6_0mm` | `GOAL_DEPARTURE_EXTRA_MM=0` | `USER/Build/V6_0mm/TEST_V6_0mm.hex` | 终点掉头起步附加 0 mm |
| `V6_2mm` | `=2` | `.../V6_2mm/...` | 2 mm |
| `V6_4mm` | `=4` | `.../V6_4mm/...` | **默认**，4 mm |
| `V6_6mm` | `=6` | `.../V6_6mm/...` | 6 mm |
| `Target_Remote` | `MOUSE_REMOTE,REMOTE_FULL,EN_USART1_RX`（**不定义** mm 宏） | `USER/Remote/TEST.hex` | 上位机接管，跑真正的 V6 算法 |

四个比赛档的源码**完全相同**，只有宏不同；远程档额外开 `REMOTE_FULL`
（`#if !defined(MOUSE_REMOTE) || defined(REMOTE_FULL)`），其中 **3 处刻意不改**——
那 3 处包着 `#define FLASHSAVE`，一开吃 ~9.5 KB RAM。

资源占用：比赛档 ROM 90 672 B / RAM 20 360 B（**RAM 本就近满，余 120 B**）；
远程档 ROM 106 536 B / RAM 14 200 B。

### 2.2 怎么"证明没动比赛代码"

**只比 hex 的 sha256**，不比源码 diff、不比 ROM 大小。

```bash
cd RemoteControl
python build_v6pp_modes.py                 # 五档全量重编 + 自动比 REDLINE
python build_v6pp_modes.py --only Target_Remote
python build_v6pp_modes.py --no-redline    # 只有在你**打算**改基线时才用
```

三条纪律：

1. **比 hex 前必须"改动前源码同机重编"做对照。** 文档里记的 hash 天生会过期——
   2026-11-05 就踩过：文档记的四个 hash 早因"改了源码没重编"而失效，看着像改造把比赛档改了，其实不是。
2. **UV4 的 exit code 不可信**（0=无错 / 1=仅有告警 / 2=有错），一律看日志里的 `N Error(s)`。
3. `build_competition_modes.py` **没有 `--help`**，误传参数会直接跑全量重编；全量会触发批量删除护栏，
   日常用 `--incremental`。

### 3.1 已知失败（发布时复核过，**不是本次整理引入**）

`RemoteControl/host/selftest.py --e2e` 会在连续拉取之后卡在 `client.get_all()`，
抛 `CommandError: timeout waiting for: GET ALL`。同一份代码在 `pre-release-20261114` 快照上
用独立 worktree 复跑，**现象一致** ⇒ 既有缺陷，不是清理导致。

- `selftest.py`（纯协议断言）**45/45 通过**，说明协议层没问题；
- 失败点在"取流还在跑的时候下发 `GET ALL`"，与已知的"取流期间下行被打坏"是同一类
  （见 `RemoteControl/docs/工具与校验.md` 的真机铁律）。
- 规避：先停流再 `GET ALL`；或用 `link_pull_evt.py`（事件触发、在途恒 ≤1）替代连续拉取。

## 4. 归档流程

```
跑绿（所有判据）→ 重编（确认 hex 基线与 REDLINE 一致）→ 审计（git status 干净）
  → 写文档 / 归档说明 → 打包（git archive，不是打包工作区）→ 抽查 → sha256sum -c → 提交
```

关键点：

- **从 git 导出，不从工作区打包**。工作区有未跟踪产物，打进去就不是"这一版源码"了。
- 每个 `release/` 目录三件套：`<包>.zip` + `SHA256SUMS.txt`（含包内源码文件各自的哈希）+ `归档说明.md`（版本、日期、提交号、这一版验过什么）。
- `make_archive.py` / `verify_archive.py` 是打包与校验脚本，改归档规则时一起改。

## 5. 什么不入库

`.gitignore` 的判定原则：**跑一次就能再生的东西不入库**。

| 类别 | 例子 | 原因 |
|---|---|---|
| Python 缓存 | `__pycache__/`、`*.pyc` | 再生 |
| Keil 中间件 | `USER/Build/`、`USER/Remote/`、`*.o/.d/.crf/.axf/.hex/.map` | Rebuild 就有 |
| Keil 每用户状态 | `*.uvgui.*`、`*.uvguix.*`、`JLinkLog.txt` | 只对这台机器有意义 |
| 运行现场 | `Control/sessions/`、`Control/.tmp/`、`RemoteControl/host/sessions/` | 跑一次就产生 |
| 采集落盘 | `PhoneCamera/pc/data/` | 6 G 级，随跑随涨 |
| 实验产物 | `Auto Locate/out/`、`Auto Locate/experiments/` 下的大件 | 可复现 |
| 大素材 | `Auto Locate/samples/*.mp4`、`video/` | 体积 |
| 数据本体 | `Control/records/` | 不是产物而是**跑车记录**，本地保留 |

**例外（必须入库）**：`固件_V*/*.hex`、`*.axf`、`SHA256SUMS.txt`、`USER/TEST.uvoptx`。
判断方法：`git check-ignore -v <path>`——被匹配到的规则决定去留。
