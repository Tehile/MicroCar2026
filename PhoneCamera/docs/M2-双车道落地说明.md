# M2 双车道落地说明（监视道 + 交付道）

> 里程碑：**M2 双车道与会话** —— 目标从 M1 的"端到端跑通一张图"提升到
> **"一次会话几百张可靠交付，且现场随时看得见取景"**。
> 状态：**控制道 / 交付道已在 M1 打通，本轮补齐监视道（D6）**。

---

## 1. 两条车道各是什么

| 车道 | 载荷 | 协议 | 时效 | 本轮状态 |
|---|---|---|---|---|
| **监视道** | 缩略图（20–40 KB）+ 帧元数据 | WS 文本帧（base64 JPEG） | 秒级（1 Hz） | ✅ **本轮实现**（v1.10.0） |
| **交付道** | 全质量 Y 平面（2.76 MB/帧）+ 元数据 | HTTP 分片 + 续传 + SHA-256 终检 | 批量（实测 ≈2 fps） | ✅ M1 已通（455 帧 verified） |

**为什么必须分开**（D6）：混在一条链路上会同时牺牲两件事 —— 为实时而压画质，或为画质而牺牲响应；
且大文件上传与触发指令共用连接时，**队头阻塞会让远程触发变成摆设**。

## 2. 本轮做了什么

### App（v1.10.0）
- 从**已经采到的那一帧**现算 480 宽灰度 JPEG（q70），中心十字准线保留（现场对位用），
  **1 Hz** 经 WS 发 `thumb`。复用既有的预览降采样结果 ⇒ 不额外读一遍图像。
- **发送走独立线程 + 2 格队列（满则丢最旧）**：`WsClient.send` 是阻塞式写 socket，
  在相机回调线程上直发会把帧回调堵住，进而扰动"哪一帧被抽中"。
- 未连接/编码失败一律**静默丢弃并计数**（`thumbs_sent` / `thumbs_dropped` 进 `status`）。
- 监视道**不排队、不落盘、不重传** —— 丢了只影响"看不见画面"，不影响任何交付数据的完整性。

### PC（`pc/server.py`）
- `thumb` 接收：落 `thumbs/thumb_<seq>.jpg` + **旁挂 `thumb_<seq>.json`**（记帧时间戳、路径标识、
  App 当时的状态）⇒ 监视道也能回答"这张缩略图对应哪一帧"。
- **只留最新 200 张**（`MAX_THUMBS`，设计上这类数据"可随时清理"）：避免与 R29 同类的"悄悄吃磁盘"。
- `GET /api/v1/sessions/{sid}/thumb/latest`：返回最新一张 JPEG（`Cache-Control: no-store`）。
- 会话摘要与 `manifest.json` 都带 `thumbs` / `thumb_latest` —— 监视道也有记录，不只是"画在屏幕上"。
- **面板新增监视道区块**：实时显示最新缩略图 + 张数 + seq + 字节数 + 帧时间戳 + 收到时间。

## 3. 三条硬约束（都是"看起来能省事、实际会出事"的地方）

1. **缩略图不进交付队列**：一旦共用队列，交付道堵住时监视道就会一起卡死 —— 那就等于回到单车道，
   而"交付积压时仍能看画面"正是分车道的**唯一理由**。
2. **绝不在相机线程上发**：手写 WS 的 `send` 是阻塞写。链路越差越需要监视道，而恰恰在链路差的时候
   这个阻塞会把帧回调拖住 → 抽帧节奏被扰动（"哪一帧被抽中"是元数据的一部分）。
3. **PC 端处理缩略图永不抛异常**：坏 base64、未知会话都只记一笔日志。
   **未知会话的缩略图不能顺手建会话** —— 否则监视道会在 PC 上凭空造出一堆空会话目录，
   把"哪次是真采集"搞乱（`pc/test_server.py` 13b 就是这条的判据）。

### 第 ④ 条硬约束（v1.11.0 追加）

4. **面板推送绝不允许阻塞控制道**：推送在 App 的控制道循环里被触发（收到 `thumb` 转发），
   所以投递只做非阻塞 `put_nowait`（每面板一个 2 格队列 + 独立发送任务）。
   **在别人的消息循环里 `await`，等于把那条循环的生死交给被 await 的一方。**

## 5. 怎么用（现场流程）

```bash
# ① PC：起服务（打印 URL + 二维码）
C:\Users\liuru\.conda\envs\general_env\python.exe pc\server.py --token abcd1234
# ② 手机：装 v1.10.0 → 粘整行 URL → 连接 PC → 开流交付
# ③ 浏览器打开 http://<PC-IP>:8765/?token=abcd1234
```

面板上会同时看到：**监视道画面**（1 Hz 刷新，交付积压时照样刷新）、会话表（帧数/字节/缩略图数/断言）、
最近 `status`（含 `upload_mbps` / `backlog_fps` / `eta_full_min` / `thumbs_sent`）。
调位置时用手机屏幕上的预览（快，8 Hz）或面板上的监视道（能远程看，1 Hz）。

## 6. 与"参数选择"的关系（回应"双流实现后再综合选参数"）

监视道**不影响交付带宽的账**：1 Hz × 约 40 KB = **0.4 Mbps**，相对实测 44–93 Mbps 的量级可以忽略。
所以：

- 它不改变 R29 的结论（抽帧率仍须 ≤ 实测交付率）；
- 但它**改变了现场可用性**：即使交付道在慢慢补传，人也随时看得见取景是否符合要求 ——
  这正是"先实现、再定档"的意义：定档最终要服务的是"能不能拍对"，
  而不是"链路能跑多少"。

## 7. 已知限制（下一步）

## 4.5 会话确认：由控制道声明，不让监视道去猜（v1.10.5）

**现场现象**：v1.10.3 上机后 PC 控制台又出现 `[ws] thumb 忽略：未知会话 2026-09-25_1354_e079`，
而同一时刻 App 报的是 `thumbs_gated: 0` —— 闸门**没拦住**。

**根因（用落盘时序坐实）**：闸门只看"**有没有任何一帧** verified"，而交付队列是
**跨会话**补传的。该次连接后 16 秒内补传的全是**上一个会话** `1331_6f68` 的积压帧
（13:54:31–13:54:46 共 7 帧），它们的 verified 把闸门打开了；
而当前会话 `1354_e079` 在 PC 端直到 **13:54:47**（它自己的首帧 init）才存在
⇒ 中间那两张缩略图必然被拒。

| 旧 | 新 |
|---|---|
| 闸门 = "任何一帧 verified"（**全局**） | 闸门 = "**本会话**的帧 verified" 或 "收到 `session_ack`" |
| 会话的存在由交付道**间接**证明（首帧 init），而首帧可能排在几十帧积压之后 | 会话由控制道**显式声明**：`session_begin` → PC 建会话 → `session_ack` |
| 被拒时 App 无从知晓（只在 PC 控制台打一行） | PC 回一次 `thumb_rejected`（每个未知会话一次，防刷屏）⇒ App **自己关闸** |
| PC 重启后会话表丢失 ⇒ 永久黑屏 | App 收到拒绝后**重新声明**（上限 3 次，防空转）⇒ 自愈 |

协议新增三条（§7.1）：

| 方向 | 消息 | 载荷 |
|---|---|---|
| App→PC | `session_begin` | `{session_id, app_version, model, calib_id, delivery, capture_path_id, capture_path_rev, zoom_choice, zoom_effective, zoom_source}` |
| PC→App | `session_ack` | `{session_id}` |
| PC→App | `thumb_rejected` | `{session_id, reason:"unknown_session", message}` |

**为什么不干脆让 PC 见到缩略图就建会话**：那样陈旧/伪造的缩略图会凭空造出会话目录，
把"哪次是真采集"搞乱。会话的创建权归**控制道**（`start` 或 `session_begin`），
监视道永远只是"显示" —— 这条边界不放松。

判据：`pc/test_server.py` **16a–16e**（声明建会话 / 幂等 / 幂等后可直接收帧 / 非法 id 报 400 而非 500）
与 **17a–17b**（未知会话缩略图拒收、只回话一次、不建会话）。
