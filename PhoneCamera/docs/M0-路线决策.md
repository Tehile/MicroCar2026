# M0 路线决策：采集与交付走哪条路（第 9 轮）

> 用户指令原文：**「拍照还是流式都可以，只需要满足一开始设计方案中的要求。这一轮对话先确定路线。」**
>
> 本轮**不新增任何真机测量**，只做两件事：① 用**已有实测证据**在「拍照」与「连续流」之间做出判决；② 把判决同步进方案、规程、判据与代码。
>
> ---
>
> ## 结论先行
>
> **路线 = 连续流（按需开流）+ 按 `sensor_timestamp` 抽帧交付单张图像。**
> **不使用 `TEMPLATE_STILL_CAPTURE`。**
>
> ⑥ 拍照路径降级为**备选**、不再阻塞交付（`--delivery stream` 下 G26 = INFO）。
> 总判定随之从第 8 轮的 `INCOMPLETE` 回到一个**确定值**：`WARN`（PASS=20 WARN=1 FAIL=0 INFO=12）。
> 剩下的那个 WARN 是 G18「60 fps 档不可达」—— 按 §5.3 已认定的**能力边界**，且 §9 允许 WARN 进入 M1。

## 1. 判「路线是否合格」的标准，必须来自最初的设计要求

标准不能由本轮临时拟定。回到设计方案的 §1。

### 1.1 §1.2 的三条真实需求（**本轮的判据**）

| # | 原文要点 | 对路线的裁判含义 |
|---|---|---|
| **N1** | 「内参可复现性 —— 标定之后，相机参数**必须可证明地**没有漂移」 | 交付物必须落在**已被取证的那条路径**上。关键词是「**可证明**」，不是「应该没问题」 |
| **N2** | 「保证每一张交付的图像**都能被判定**属于哪一次标定、当时的参数是什么」 | 交付物必须带 `calib_id` + 完整帧级 `CaptureResult` |
| **N3** | 「在参数漂移时**主动报警**，而不是静默失准」 | 需要**逐帧（时序）**证据，而不是单次快照 |

### 1.2 题面的口径（§1.1）

题面写的是「拍照回传」。而设计方案 §1.2 对它做过再解释：

> 「题面写的是'拍照回传'，但项目的真实目标是**定位**，所以核心矛盾不是传输效率，而是内参可复现性。」

⇒ 题面约束的是**交付物形态**（回传的是图像，不是录像），**不是**采集 API 的选择。
这一条在下面 §4 会用到 —— 它决定了「连续流 + 抽帧」**并不违反题面**。

### 1.3 「路线」的精确含义

一条路线 = 三元组 **{采集模板, 调度方式, HAL 输出格式}**，再叠加**交付形态**。

这个三元组正是 `(capture_path_id, capture_path_rev)` 想表达的东西 —— 它是「**这个时间戳的语义属于哪一套**」的唯一凭据
（R22：ZSL 旧帧、多帧合成都会在不同路径上改写时间戳的含义）。

| 路线 | 采集模板 | 调度方式 | HAL 输出格式 | 交付形态 | 现有证据 |
|---|---|---|---|---|---|
| **A 拍照** | `TEMPLATE_STILL_CAPTURE` | 单张下发 | JPEG | 单张 | **零** |
| **B 连续流** | `TEMPLATE_MANUAL` | `setRepeatingRequest` | `YUV_420_888` | 抽帧单张（可多张） | **①–⑤ 全跑过，19 项 PASS** |
| C 混合（旧 D3+D23） | 连拍取证 / 拍照交付 | 两种都有 | 两种都有 | 单张 | 取证有一套、**交付那套没有** |

## 2. 判决

| 原始要求 | A 拍照 | B 连续流 | 说明 |
|---|---|---|---|
| **N1 可证明的内参可复现性** | ✗ | ✓ | A 的证据为零，且需先证明 HAL 肯关 ZSL/多帧合成 —— **可能证明不了**；B 已有逐帧回读（见 §3） |
| **N2 交付物可判定归属** | ✓ | ✓ | 两者都可带 `calib_id` + 帧级元数据；B 的归属凭据已经在手 |
| **N3 漂移主动报警** | △ | ✓ | A 单张无时序，只能靠「事后两次标定比对」；B 有逐帧序列（G20 零漂移 + G21 跨会话重复性） |
| **时间戳准确** | △ | ✓ | A 独有 **ZSL 旧帧**与**多帧合成**两个机制，二者**只污染时间戳、不改画面**；B 实测 `edge_mode`/`noise_reduction_mode` 全 OFF（§3） |
| **交付物是单张图像（题面口径）** | ✓ | ✓ | B 抽帧交付的产物**就是单张图像**，不是视频 |
| **精度上限 `fx`** | ✓ 可用全幅 | ✓ 同样可用全幅 | 4096×3072 对拍照与对抽帧交付都成立；差别只在**带宽**，而带宽可用 `SENSOR_FRAME_DURATION` 与抽帧控制（§5） |
| **发热 / 功耗** | ✓ 最低 | △ | B 连续采集更热（R6）。但「**按需开流**」而非常开，且降帧率已证生效 ⇒ 差距被压缩 |

**⇒ 连续流在三条核心要求上全部占优，且在交付形态与精度上限上不落后。判决：路线 B。**

## 3. 判决所依赖的实测证据（本轮从 4 份原始 JSON 逐帧重算）

不采信任何报告汇总结论，直接从 `m0_out/m0_locked_capture*.json` 重算。

### 3.1 锁定字段是否真的被锁住（145 个有效取样点 / 份）

| 字段 | 4 份的取值 | `distinct_count` |
|---|---|---|
| `edge_mode` | `OFF` | **1** |
| `noise_reduction_mode` | `OFF` | **1** |
| `distortion_correction_mode` | `OFF` | 1 |
| `ois_mode` / `video_stab_mode` | `OFF` | 1 |
| `zoom_ratio` | `1.0` | 1 |
| `lens_focus_distance_diopter` | `1.001001` | 1 |
| `sensor_exposure_time_ns` / `sensor_sensitivity_iso` | `10000000` / `200` | 1 |
| `sensor_frame_duration_ns` | `33287995` | 1 |
| `rolling_shutter_skew_ns` | `9212928` | 1 |
| `active_physical_id` | `2` | 1 |
| `sensor_pixel_mode` | `0` | 1 |

**两行加粗的字段是本轮判决的直接证据**：`EDGE_MODE` 与 `NOISE_REDUCTION_MODE` 是 HAL 用来塞
**多帧降噪 / HDR** 的开关。它们在连续流里全程为 `OFF` 且逐帧回读一致 ⇒
**「连续流不含多帧合成」这句话是测出来的，不是推出来的**，多帧合成会破坏的时间戳单值性因此不成立。

### 3.2 时间戳结构与参考行偏置

| 项 | 4 份的实测 |
|---|---|
| 帧数 | 150 / 份（有效 145，预热 5） |
| 单调性 | 全部严格递增 |
| 间隔取值 | 只有 3 个：`33 287 916` / `33 287 917` / `33 288 125 ns` |
| `crop_region` | 每份每帧恒为 `(0,0,4096,3072)` ⇒ **`crop.top = 0`，参考行偏置 = 0** |
| 采集路径三元组 | `TEMPLATE_MANUAL` + `setRepeatingRequest` + `YUV_420_888`（`config_fingerprint` 主体四份一致） |

主报告 `m0_locked_capture.json` 的周期结构（G20 消费的那一份）：144 个有效间隔，
`d[i] == d[i+5]` 在 **139/139** 处成立，对齐的 **28 个 5 帧组和全部 = 166 440 000 ns，极差 0**
⇒ 名义间隔 **33 288 000.0 ns**，与回读帧时长 `33 287 995` 一致到 **0.150 ppm**。

> ⚠️ **本轮重算翻出一个此前没被记录的事实（已知边界，不影响判决）**：
> `d[i] == d[i+5]` 在 **r1 上是 111/139**（28 处不等），另外三份是 139/139。
> r1 的对齐 5 帧组和取 3 个值 `{166 439 792, 166 440 000, 166 440 208}`，**极差 416 ns = 2.5 ppm**。
> 两点含义：① 量级远低于 `TS_DRIFT_OK_PPM = 20 ppm`，**不改变任何结论**；
> ② 「严格周期 5」是**某一次运行的相位性质，不是机型不变量** —— 而 G20 **只跑主报告**。
> ⇒ 已记为待办：把周期结构判据扩展到逐轮（r1 的 r1/r2/r3 目前只被 G21/G23 消费）。

### 3.3 定档证据（⑤ 尺寸扫描，第 7 轮实测）

| 档位 | 预测 `fx` | 每帧 YUV | 实测帧率 | `skew` | 带宽 @30 fps |
|---|---|---|---|---|---|
| 1920×1440 | ≈1283 px | 4.1 MB | 30.04 fps | 9.21 ms | ≈125 MB/s |
| 2880×2160 | ≈1924 px | 9.3 MB | 30.04 fps | 9.21 ms | ≈280 MB/s |
| **4096×3072（全幅）** | **≈2736 px** | 18.9 MB | 30.04 fps | 9.21 ms | ≈567 MB/s |
| 3840×2160（16:9） | ≈2565 px | 12.4 MB | 30.04 fps | 6.91 ms | ≈374 MB/s |

三条与本轮判决相关的事实：

1. **五档帧率全是 30.04 fps** ⇒ 30 fps 是**该 session 模式的上限**，与 ISP 缩放无关。
2. **判别档证明 `skew` 与 crop 高度无关**（同 16:9 输出、crop 2304 行 vs 3072 行，`skew` 一模一样）
   ⇒ **`skew` 绑定输出纵横比**。交付档取 4:3 全幅即 9.21 ms。
3. **16:9 档不可用作交付档**：`crop.top = 384` ⇒ 1.15 ms **静默**参考行偏置，且白扔 25% 垂直视场（R23）。

### 3.4 「时间戳准确」的主战场不在时间基

| 误差源 | 量级 | 类别 |
|---|---|---|
| 帧率 / 时间基漂移 | 3.06 ppm × 33.288 ms ≈ **101.9 ns** | 累积型，多帧可压掉 |
| **卷帘读出（单帧）** | **9.21 ms**（±4.61 ms） | 固有型，**多张平均消不掉** |
| 参考行偏置（仅 16:9 档） | 1.15 ms | 静默常量，交付档为 0 |

差**四个数量级**。⇒ 时间基做到 ns 级毫无收益；真正决定上限的是「一帧跨了 9.21 ms，目标在这段时间里动了多少」。
**这是交付形态的代价，与走哪条路线无关** —— 单张交付（无论怎么来的）都只有这一个 9.21 ms 的窗。

## 4. 为什么不是拍照（三条硬理由）

### 4.1 它让 N1「可证明」变成一句无法兑现的话

第 8 轮已用源码核实：改造前的 App 里**完全没有** `takePicture` / `TEMPLATE_STILL_CAPTURE` / JPEG。
7 份报告全部来自连续流。交付走拍照 ⇒ **三元组三样都不同** ⇒ 19 个 PASS **一条也覆盖不到交付物**。
这就是 R22。选路线 B 则**从结构上消掉 R22**：交付物就是连续流里的某一帧，与证据同源同格式。

### 4.2 它独有的两个风险，恰好都只污染时间戳

| 风险 | 后果 | 为什么危险 |
|---|---|---|
| **ZSL 交出旧帧** | `SENSOR_TIMESTAMP` 指向更早时刻，偏差随机 | 画面与通知**完全正常** |
| **多帧合成（MFNR/HDR）** | 时间戳**不再对应单一时刻** | 同上，且直接毁掉 N1 |

两者都需要**先证明 HAL 肯关**（`CONTROL_ENABLE_ZSL=false` 生效、`EDGE_MODE`/`NOISE_REDUCTION_MODE` 未被改写）。
**而这个证明至今不存在**：⑥ 已实现并编译通过（APK 911 603 B），但**没上机跑过**。

### 4.3 它让 N3「主动报警」退化成「事后发现」

单张没有时序结构，判不了周期、判不了跨会话重复性，只能在下次标定时**回溯**发现漂移 ——
而 R12 已经指出：连「焦点回读值」都只能证明**请求落点可复现**，不能证明镜片物理位置相同。

## 5. 代价与残留（诚实的部分）

| # | 代价 / 残留 | 量级 | 处置 |
|---|---|---|---|
| C1 | **发热高于单张**（R6） | 未实测 | ① 用「按需开流」而非常开；② 用 `SENSOR_FRAME_DURATION` 降帧率（**已证生效**：12/15/24 fps 全部跟随请求，偏差 +0.12%~+0.14%）；③ 温度监控 + 轮次切分。⇒ **≥5 min 长时热漂移测试的必要性上升**（仍是唯一没仪器的漂移源） |
| C2 | **带宽未实测** | 估算 | 表里的 `MB/s` 是「每帧字节 × 30 fps」**算出来的**，不是链路实测吞吐。⇒ 定档（R19）需要一个实测值 |
| C3 | **交付采集格式是新的证据边界** | — | 现有证据的 HAL 输出格式是 `YUV_420_888`。若交付让 HAL 直接出 JPEG，**采集路径就变了** —— 这正是 R22 同一类错误下沉一层。⇒ 新增判据 **G27** 把它变成可判的量（见 §7） |
| C4 | **题面字面风险** | — | 题面写「拍照回传」。本判决交付的**是单张图像**（满足交付物形态），但采集用的是连续流 API。⇒ 见 §6 可逆性 |
| C5 | **周期性只在主报告上验过** | 2.5 ppm | 见 §3.2 的已知边界；记为待办 |

## 6. 可逆性：若必须走拍照，成本是多少

**路线 A 已经实现好了**（⑥ 的两条受控路径 + 判据 G26），切换只需一条声明：

```bash
python tools\m0_evaluate.py --pull --delivery still     # 交付走拍照
```

代价是：**必须先上机跑 ⑥**，且若 HAL 不认 `CONTROL_ENABLE_ZSL=false` 或把
`EDGE_MODE`/`NOISE_REDUCTION_MODE` 改写为 `ZERO_SHUTTER_LAG`/`HIGH_QUALITY`，**该机型拍照路径不可用**，
只能回到本路线。⇒ 本判决可逆，且逆向后立刻知道可不可行。

## 7. 对判据与后续阶段的影响

### 7.1 判据

| 判据 | 变化 |
|---|---|
| **G18**（帧率权威性） | `--delivery stream` 下**恢复阻塞**（WARN）：流式路线的带宽直接由帧率决定，帧率不再是可忽略项 |
| **G26**（拍照路径证据） | `--delivery stream` 下给 **INFO「不适用」**；仍保留完整判定逻辑，供逆向后使用 |
| **G27**（**新增**：交付采集格式一致性） | 把 C3 变成可判的量：声明的 HAL 输出格式必须与**证据实际使用的格式**一致，否则 **WARN「交付采集格式未被取证」**。缺字段判「不可判定」（fail closed） |
| `--delivery` 默认值 | `still` → **`stream`**（与路线一致），并打印明确声明。**它仍是调用方声明的输入，不是测出来的事实** |
| `--capture-format`（新增参数） | 声明交给 HAL 的输出格式（`yuv` / `jpeg` / `raw`），默认 `yuv`。**由 YUV 软件编码成 JPEG 不算换路径**（编码在采集之后，不碰时间戳） |

### 7.2 定档建议（R19，仍未收口）

链路已定为连续流抽帧 ⇒ 不再是「拍照档 vs 流式档」的二选一，而是**档位 × 帧率**的组合：

| 方案 | `fx` | 每帧 YUV | 交付带宽 | 评价 |
|---|---|---|---|---|
| **4096×3072 + 降帧率 2–5 fps** | **2736 px** | 18.9 MB | 38–95 MB/s | **推荐**：精度最高、`crop.top=0`；带宽靠降帧率压 |
| 2880×2160 + 2–5 fps | 1924 px | 9.3 MB | 19–47 MB/s | 若实测链路吞吐偏低，退到这一档 |
| 1920×1440 @30 fps | 1283 px | 4.1 MB | 125 MB/s | 不推荐：精度损失一半，带宽反而更高 |

⚠ **定档仍需一个实测的链路吞吐**（C2）。在此之前，档位建议是**在估算带宽上做的**。

### 7.3 M0 剩余工作

| # | 事项 | 为什么还必需 |
|---|---|---|
| 1 | **重跑 ②（当前 APK）** | 让连续流也带上 `control_enable_zsl` / `sensor_ts_minus_request_ns`（1.8.0 新增字段）⇒「连续流无 ZSL 结构」从推理变成实测 |
| 2 | **实测链路吞吐**（PC 服务起来后） | 定档的唯一缺口（C2） |
| 3 | **≥5 min 长时热漂移** | 唯一没仪器的漂移源；路线改连续流后权重上升（C1） |
| 4 | **M1 两次独立标定比 `fx`** | R12 的最终裁判 —— 直接对应 N1 |
| 5 | 待办：G20 的周期结构扩展到逐轮 | §3.2 的已知边界（C5） |

**可不再做**：⑥ 拍照路径（除非逆向后）。
