# M1 落地说明（连续流 + 抽帧交付，端到端跑通一张图）

> 目标（§10 实施阶段 M1）：**aiohttp 服务 + 二维码 + 手输 IP；App 按需开流 →
> 按 `sensor_timestamp` 抽帧交付 + 帧级元数据上传；PC 落盘 + manifest → 端到端跑通一张图（走 D24）**
>
> 本轮交付：`pc/server.py`（+ 23 条端到端测试）、App 的 `DeliverySession`（v1.9.0）、
> 采集路径登记（`stream_deliver_yuv/1`）。**App 侧尚未上机**，PC 侧已在真 HTTP/WS 上自测通过。

## 1. 这一版做了什么（对照 §10 M1 的四项）

| M1 要求 | 落地 | 证据 |
|---|---|---|
| aiohttp 服务 + 二维码 + 手输 IP | `pc/server.py`：单进程提供 HTTP 分片 + WS 控制 + 面板；启动枚举网卡并打印 `http://<ip>:<port>/?token=…` + 终端二维码 | `pc/README.md`；服务启动即打印 |
| App 按需开流 | 「开流交付」按钮 / PC 面板「开始采集」下发 `start`（含 `plan.interval_ms`） | `DeliverySession.startCapture()` |
| 按 `sensor_timestamp` 抽帧交付 | 抽帧判据是**传感器时间差** `ts - lastSampledTs ≥ interval`（不是回调计数）；预热丢前 5 帧（② 的丢弃规则） | `onResult()`；元数据含 `warmup_frames_dropped`/`sample_rule` |
| 帧级元数据上传 + PC 落盘 + manifest | 帧级 JSON 与 §6.3 对齐；PC 写 `frames/frame_%06d.{yuv,json}` + 会话 `manifest.json`（含断言） | `pc/test_server.py` 的 1b/1c/1d |

另外两条按 §5.6/§7 落地：**本地持久化队列 + 只有服务端 verified 才删**；**分片 + 断点续传 + 幂等键**。

## 3. 与设计的一处**必须写明**的判断：交付路径是**新的采集路径**

`stream_deliver_yuv`（rev=1）与 M0 取证的 `burst_yuv_manual`（rev=1）**不是同一条**：

| 维度 | `burst_yuv_manual`（② 取证） | `stream_deliver_yuv`（交付） |
|---|---|---|
| 模板 / 格式 / 调度 | `TEMPLATE_MANUAL` / `YUV_420_888` / `setRepeatingRequest` | **相同** |
| 几何（默认） | 1920×1440 输出 + 4096×3072 crop | **相同**（profile 可改） |
| 锁定项 | 对焦/变焦/曝光/ISO/OIS/EIS/edge/nr/aberration/distortion 全手动 | **相同** |
| `CONTROL_ENABLE_ZSL` | **不设**（靠 HAL 默认；回读 false） | **显式设 false** |
| `SENSOR_FRAME_DURATION` | 恒发 30 fps 对应值 | 由 `profile.frame_interval_ms` 决定，**默认不发** |
| 丢弃规则 | 丢前 5 帧 | 丢前 5 帧 **+ 按间隔抽帧** |

⇒ 请求层差两个键、丢弃规则不同 ⇒ **登记为新路径**，且既有 ②③⑥ 的 `rev` **一个都没动**
（这正是 R20/R21 用两轮代价换来的规则：新增路径不得让其它路径的证据作废）。

**它的意义与边界：**
- ✅ "交付物落在已取证路径上"这条（G27）问的是**输出格式**是否一致 —— 一致（`YUV_420_888`），成立；
- ✅ 由**格式与几何**决定的量可与之比对（`crop.top=0`、`skew = 2999 ns/读出窗口行`）；
- ❌ 但**不能**说"交付路径已被 M0 取证"：M0 取证的是 ② 的行为（锁定项逐帧恒定、跨会话可复现），
  而那条证据只覆盖 ②。要取证交付路径，得把 ②③ 那套逐帧验证在交付路径上重跑一遍
  （`tools/m0_evaluate.py` 可以直接吃它的报告 —— 判据按 `(capture_path_id, rev)` 成对比较）。

## 4. 代码里几处"因为有坑所以这么写"的地方

| 位置 | 坑 | 处置 |
|---|---|---|
| `DeliverySession.onResult/onImage` | **图与结果是两条回调，先后不保证**（R28 的教训） | 结果侧决定抽帧 → 若图未到则记入 `pendingSample`；图侧到了再补 | 
| `DeliverySession.extractY` | `rowStride` 可能大于宽度（补齐行） | 按 stride 逐行取并**重排成紧密排布**，元数据记 `source_row_stride`/`repacked` |
| `DeliverySession` 写盘 | 写一帧 2.7 MB 会阻塞**相机回调线程**（图回调与它同线程） | 元数据在相机线程组好，**文件 I/O 交给 writer 线程** |
| `DeliverySession` 元数据 | 连续流里"每帧的请求时刻"**没有定义** | 不伪造 `sensor_ts_minus_request_ns`（置 null 并说明），改记 `sensor_ts_minus_stream_start_ns` |
| `DeliverySession.nextSeq` | 序号从头开始会撞旧幂等键 → 服务端 409 拒收 | 序号**持久化**在队列目录 |
| `pc/server.py` 错误响应 | 错误走 `text/plain` 会让 App 拿到解析异常而不是错误码 | 统一 JSON：`{"error": code, "message": …}` |
| `pc/server.py` 校验失败 | 删分片会强迫客户端从头传 | **保留分片**，只把真实偏移告诉它 |
| 采集路径登记 | 复用别人的 `rev` 会让"交付路径已取证"变成一句没有证据的话 | 登记新路径 + 在登记表里写明差异与边界 |

## 4.5 首次真机联调（11:30）暴露并修掉的 4 处缺陷

第一次真机跑通后（PC 收到 67 帧 verified，每帧 2 764 800 B = 1920×1440 纯 Y 平面，
与 profile 完全吻合 ⇒ 提取/重排/元数据/分片/SHA-256 整条链正确），
从"日志与落盘的差异"里揪出四个**都会静默丢数据**的问题：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | **上一轮一帧都没传**（queue 只涨不降、PC 端零 init） | `disconnect()` 没有把 `uploader` 置 null，而上传线程以 `while(connected)` 为循环条件、断开即退出 ⇒ **重连不再建线程**。现场日志有三次 hello（连了三次），界面完全看不出异常 | `disconnect()` 置空 `uploader`/`statusThread`，重连即重建 |
| 2 | 旧队列永久滞留（51 帧） | 队列按 `sessionId` 切目录，而 PC 每次 `start` 都生成新会话 ⇒ 旧目录再也不会被扫描（**违反 §5.6 的补传要求**） | 队列改为**全局一个** `delivery/queue/`；上传用**帧自己的 `session_id`**（写在元数据里）⇒ 跨会话补传并正确归位；连接时自动迁移旧目录 |
| 3 | 有概率丢帧（静默） | 写盘序为「先 yuv 后 json」，上传侧遇到"有图无元数据"直接 `delete` | 原子序：`.part` → rename `.yuv` → `.json`；上传侧缺元数据**只跳过不删** |
| 4 | 抽帧率只有 ~2 fps（期望 5） | `acquireLatestImage()` 会**丢弃队列里更旧的图像**，而交付路径每帧都要与 `SENSOR_TIMESTAMP` 配对 ⇒ 被丢掉的帧永远等不到图 | 改 `acquireNextImage()`（FIFO），`MAX_IMAGES` 3→4 留余量 |

另外两处小噪声：`hello` 不再带 `session_id`（否则每连一次就在 PC 端留一个空会话目录）；
`status` 增加 `queue_bytes` / `queue_sessions`（积压与跨会话残留要看得见）。

## 4.6 App 端画面预览（现场调整位置）

交付区顶部的画面 = **用已采到的 Y 平面**降采样成灰度位图 + 中心十字准线，
节流 ~8 fps，叠加采集尺寸/队列/温度/已抽帧数。

**为什么不是加一个预览 Surface**：多一个 Surface 就改变了**会话配置** ——
按本项目规则那是采集行为变更（要动 `rev`、作废既有证据）。而"把已经在手的帧画出来"是**纯显示**：
不进 HAL 请求、不进元数据、不进指纹 ⇒ **零 rev 影响**。
代价只是每帧几毫秒 CPU；收益是现场不必盲拍。



## 4.7 界面重构（v1.9.1）

现场反馈：「预览框把连接电脑、开流、断开这几个按钮都盖住或者看不到了」。

根因（是我的布局问题，不是"小屏适配"的运气问题）：预览固定 240dp，且插在**地址栏与连接按钮之间**；
上面还平铺着 ①③④⑤⑥ 六个探针按钮。整屏内容超出后，**被裁掉的正是最下面那几行 —— 恰好是现场唯一
要用的操作按钮**。（root 是纵向 LinearLayout、日志带 weight=1：非权重子项超屏时，越靠后的越先被挤掉。）

| 项 | 旧 | 新 |
|---|---|---|
| 预览位置/高度 | 地址栏之后、固定 240dp | **置顶**（状态栏下方）、`≤ min(260dp, 屏高 30%)` |
| M0 探针 ①③④⑤⑥ | 平铺在首屏（约占 290dp） | **默认折叠**，点「▸ 展开 M0 探针」才出现 |
| 连接 / 断开 | 一个按钮改文字 —— 而成功分支只改了状态栏、没改文字 ⇒ **连上之后断开入口从未出现** | **两个独立按钮**，可用状态由状态机决定（未连接：只有"连接"；连接中：可"断开"取消；已连接：可断开/开流/停流） |
| 日志 | 无上限（5 fps × 两条/帧 ⇒ 一小时几万行，越用越卡） | 只保留最近 400 行 |

**没有删掉探针代码**：①③④⑤⑥ 是 M0 证据链的采集入口，M0 的每条结论都挂在
"哪份报告对应哪条采集路径 `(id, rev)`"上（`tools/capture_path_versions.json`）。删了就再也采不出
等价证据 —— 将来只要动一次采集行为、或要给第二台机器复测，就得把这套探针重写。折叠后界面同样干净。

**这轮不改任何采集行为**：四条采集路径的 `rev` 一个都没动（纯 UI + 版本串统一），
见 `tools/capture_path_versions.json` 的 `m0probe-1.9.1` 条目；M0 判据回归全绿。

顺带修一处隐患：同一个 APK 里探针报 `m0probe-1.8.3`、交付报 `m0probe-1.9.0`（两个出口两个版本号，
采集路径登记表对不上号）⇒ 1.9.1 起共用 `LockedCaptureProbe.APP_VERSION`。

## 4.8 连接状态与按钮可用性（v1.9.2）

现场反馈：「连接时 App 显示连接中，电脑有输出信息，但无法点击开流交付」。

**根因**：上一轮给连接失败加了 `onConnectResult`，但**只加了失败路径** ——
成功时没有任何人通知界面 ⇒ 按钮一直停在「连接中…」，开流/停流永远 disabled。
而 PC 端其实一切正常（hello、status、上传都在跑，日志里能看到 `queue_len` 在下降），
所以现象是"两边都对、就是点不动"。

同时发现两个同源缺陷：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 连上后按钮仍然灰 | 成功路径没有回调 | WsClient 增加 `onOpen`（`HTTP/1.1 101` 后立刻回调），`onConnectResult(true, …)` 由它发出 |
| 2 | PC 端显示 `[ws] disconnected` 后 App 仍显示已连接 | WS 读到 EOF / close 帧 / 读写异常时**没人通知界面** | WsClient 增加 `onClosed(reason)`；DeliverySession 增加幂等的 `onConnectionLost()`：停采集、清 `uploader`/`statusThread`（否则重连不重建线程）、状态栏写明原因 |
| 3 | `queue_sessions` 报 151（211 帧） | 旧命名文件（`frame_000123.yuv`，无 `__`）被逐个当成"不同会话" | 只统计含 `__` 的；旧命名单独记 `queue_legacy_names` |

另外两处一致性修正：

- **用户主动断开 ≠ 连接丢失**：`disconnect()` 先把 `connected=false`（它同时是
  `onConnectionLost` 的幂等闸门），并且 WsClient 用 `userClosed` 标记 ——
  否则点「断开」也会弹一次"连接已断开"，把正常操作说成故障。
- **本地开流不复用 PC 的会话号**：PC 每次 `start` 新建会话号，App 采纳它；
  若之后在 App 上直接点「开流交付」，帧会带着**上一次的会话号**上传进 PC 那边
  已经结束的会话目录 —— 两轮数据混进同一份 `manifest`，断言（`calib_id` 一致 /
  参数漂移 / 温度区间）被静默污染。⇒ 新增 `startCaptureLocal()`：检测到会话号来自
  PC 时先换一个新的。

**路径影响**：四条采集路径的 `rev` 一个都没动（控制道与界面变化不进 HAL 请求），
见登记表 `m0probe-1.9.2` 条目。

## 4.9 吞吐实测：链路通了，但交付跟不上采集（v1.9.3）

用户报告"测试似乎正常"。逐帧重算后确认**数据一个字节没错**（4 个会话 455 帧
`verified`，每帧 2 764 800 B 与 profile 逐字吻合），但控制台里 `queue_len`
**从 162 涨到 249** ⇒ 采集速率高于交付速率。

| 环节 | 实测 |
|---|---|
| 现场交付（1920×1440） | **≈5.5 MB/s ≈2.0 帧/s**（App 队列斜率与 PC `VERIFIED` 时间戳两处独立吻合） |
| 回环协议天花板 | **39 MB/s**（4 帧并行 51 MB/s）⇒ **瓶颈在链路或手机端，不在协议** |

附带发现：旧的限速实现（每请求固定 sleep）把 40 MB/s 档实测压到 **17.6 MB/s**，
启动横幅上的数字是误导的（已改真令牌桶，长跑复测 39.5 MB/s）。新增两个仪器：

- **App**：`status` 增 `upload_mbps` / `backlog_fps` / `eta_full_min`；开流中积压即告警
  （含"约 N 分钟后写满剩余空间"）；新增「链路测速」按钮（相机不开，纯上传 20 MB）。
- **PC**：`/api/v1/linktest`、`manifest.verify_rate_mbps`、`upload.log` 每帧记交付速率、
  新增 `pc/probe_throughput.py`。

⇒ 完整数据与定档推演见 **`docs/M1-吞吐实测与诊断.md`**。
**新增 R29**：采集率高于交付率 ⇒ 本地队列无界增长（本机约 40 分钟写满 21 GB）⇒
抽帧率必须 ≤ 实测交付率，或改善链路/减小输出尺寸。
