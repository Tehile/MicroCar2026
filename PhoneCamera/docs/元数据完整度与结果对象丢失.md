# 元数据完整度：结果对象丢失导致 64% 的帧缺一组字段

> 第 18 轮（v1.10.5）。**这是本项目迄今最"像没事"的一个缺陷** ——
> 送达的帧画面正常、时间戳正常、字节数正常、计数器正常，只是元数据里少了一整组字段。

---

## 1. 发现过程（从落盘数据回算，不看汇总）

用户报告"日志检测应当正常"。逐项核对 PC 端落盘（会话 `2026-09-25_1354_e079`，44 帧 verified）时，
顺手数了一遍每帧的字段完整度：

```
共 44 帧
  缺 rolling_shutter_skew_ns     28/44  (64%)
  缺 active_physical_id          28/44  (64%)
  缺 zoom_ratio                  28/44  (64%)
  缺 crop_region                 28/44  (64%)
  缺 exposure_time_ns            28/44  (64%)
  缺 iso                         28/44  (64%)
```

**恰好都是同一组**：`buildMeta` 里 `result?.let { … }` 包起来的那一段 —— 即所有
**来自 `CaptureResult` 的派生字段**。

## 2. 根因：配对时把"结果对象"丢了

交付的每一帧要凑齐三样东西：**图**（`ImageReader.OnImageAvailable` 回调）、
**结果**（`CameraCaptureSession.CaptureCallback`）、**时间戳**（`SENSOR_TIMESTAMP`，两者共用）。
两条回调**顺序不保证**，所以实现里有两条配对路径：

| 到达顺序 | 原实现 | 后果 |
|---|---|---|
| 图先到、结果后到 | `recentY[ts] = y`；结果到达时 `recentY.remove(ts)` 取出图 ⇒ `enqueue(ts, y, result)` | ✅ 元数据完整 |
| **结果先到、图后到** | 记 `pendingSample.add(ts)` 后**把 result 丢掉**；图到达时 `enqueue(ts, y, **null**)` | ❌ **整组 CaptureResult 字段缺席** |

而"结果先到"恰恰是**常态**（回调链上结果通常早于图像可用），于是 64% 的帧中招。

### 为什么它是"静默"的

- 帧照样落盘、`size_bytes` 正常、`sensor_timestamp_ns` 正常、`seq` 连续；
- `manifest` 的帧计数、`bytes_verified`、`frames_verified` 全都正常；
- 只有把每帧 JSON 逐个打开数字段，才看得出少了东西。

**下游的真实危害**（不是"少个字段"而已）：

1. `rolling_shutter_skew_ns` 是 **G25 单帧固有不确定度**的载体（9.213 ms）。缺它的帧无法参与
   任何时序精度讨论；若被当成 0 参与"平均 skew"，结论直接错。
2. `active_physical_id` 是**换镜检测**的唯一依据（0.6× 是否切到超广角）。缺它的帧在
   `lens_info` 里是"没出现过的镜头"，会让"整段同一颗镜头"这个判断**基于部分样本**成立
   ——本例 `active_physical_id_unique=true` 其实只有 16/44 帧参与，**看起来干净，实则证据不足**。
3. `crop_region` 缺 ⇒ 无法验证"参考行偏置为 0"（G25 的前提）。
4. `exposure_time_ns` / `iso` 缺 ⇒ 无法做曝光一致性核对。

## 3. 修法（v1.10.5）

三件事，**缺一不可**：

1. **保留结果对象**：新增 `recentResult: LinkedHashMap<Long, TotalCaptureResult>`（上限 30），
   "结果先到"时存起来，图到达时取出补齐 ⇒ 这一条修的是**成因**。
2. **缺失要自描述**：确实缺席（结果回调真的丢了）的帧写 `result_missing: true`，
   status 报 `meta_missing_result` ⇒ 这一条保证"没有"和"没测"分得开。
3. **判据自己算**：PC 端 `manifest.meta_quality` 逐项计数（`missing` 六项 +
   `flagged_result_missing` + `ok`），并进 `/api/v1/sessions` 摘要 ⇒ 这一条让缺陷
   **可回查历史会话**，而不是等下次上机。

## 4. 复验方法（不需要真机）

```bash
# 回查任意会话：缺了哪些字段、缺多少帧
python - <<'EOF'
import json, glob, os
KEYS = ("rolling_shutter_skew_ns","active_physical_id","zoom_ratio",
        "crop_region","exposure_time_ns","iso")
for sid in sorted(os.listdir('pc/data/sessions')):
    d = f'pc/data/sessions/{sid}/frames'
    js = sorted(glob.glob(d + '/*.json'))
    if not js: continue
    miss = {k: sum(1 for f in js if json.load(open(f, encoding='utf-8')).get(k) is None)
            for k in KEYS}
    bad = max(miss.values())
    print(f"{sid}  {len(js):>4} 帧  最多缺 {bad:>3} 项 " + ("⚠" if bad else "✅"))
EOF
```

真机验收（装 v1.10.5 后开流 20 秒）：

- `status.meta_missing_result` 应为 **0**；
- 该会话 `manifest.meta_quality.ok` 应为 **true**、六项 `missing` 全 0；
- 若 `flagged_result_missing > 0` ⇒ 说明结果回调真的丢了（那是另一个问题，会记在日志里）。

## 5. 口径：为什么这不是"采集路径变更"

判定口径（本项目一直是这一条）：**请求参数 / 会话配置 / 模板 / 输出格式 / 调度方式 /
丢弃规则 / 锁定字段集合**任一变化才算采集行为变更。本次只改"配对后写进元数据的字段是否齐全"，
与 1.9.3（加 status 字段）、1.10.2（加 lens 字段）同一先例 ⇒ **四条路径 rev 全不变**。

但要明确说清代价：**1.10.5 之前采的交付数据里约 2/3 的帧缺这组字段**，
涉及 skew 或换镜的结论应只用 `meta_quality.missing` 为 0 的会话。

## 6. 教训（已写进技能）

**跨回调配对时，待配对的两个对象都必须留着** —— 只缓存一个，等于另一个的一半字段被丢掉。
"结果先到就丢结果对象"这种写法在功能上完全说得通（毕竟等的是图），
但它把"这一帧的元数据"降级成了"可有可无"。

配套的两条纪律：

- **每个"可能缺席"的字段都要能被判据说出来**（自描述 + 计数），否则静默缺陷永远是"发现了才存在"；
- **判据要能回查已落盘的数据**（`meta_quality` 直接算 manifest 里的帧元数据），
  这样修一个缺陷的同时就获得了对历史数据的解释力。
