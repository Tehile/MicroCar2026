# M0 第 5 轮复算结论（改档后首轮）

> ⚠️ **本文的 skew 结论已被第 6 轮推翻，请勿直接采信 —— 见 `M0-第6轮复算结论.md`。**
>
> 本文第 2 节写的"`skew` 是输出帧的读出时间、随**输出高度**成正比（`6397.8667 ns/行`）"**是错的**。
> 它只用了 `1920×1080 → 1920×1440` **一对**数据，而那一对里"输出高度""输出纵横比""crop 高度"
> **三个量同时按 4/3 变化**，一对观测在数学上分不出因果。第 6 轮的 ⑤ 尺寸扫描
> （固定纵横比与 crop、只动输出高度）把它证伪：三档 4:3 尺寸的 `skew` **完全相同**。
>
> **正确口径**：`读出窗口行数 = crop_w × outH / outW`；`skew = 2999.0 ns/行 × 该行数`。
> 本文其余部分（G21 证据过期、G20 的同义反复与相位污染、恒等式不可当证据、
> 判据双向路径测试的做法）**仍然成立**，只有 skew 归属这一条要替换。
>
> 留痕的理由：同一条规则连续两轮错在**同一类推理**上（把"看起来成比例"当因果），
> 所以本文与第 6 轮一起保留 —— 错误的过程本身比错误更值得记。

> 输入：用户提供的 `m0_evaluate.py --pull` 报告（总判定 WARN，PASS=16 WARN=2 FAIL=0 INFO=10）。
> 按前几轮的做法，**不采信报告里的汇总结论，一律从逐帧原始 JSON 重算**，
> 并对本轮新增/修改的判据做 PASS/FAIL 双向路径测试。
> 结论：**报告漏了一件比它自己报的两个 WARN 都更严重的事。**

## 0. 一句话结论

改档（`1920×1080` → `1920×1440`）**确实生效且已修好各向异性问题**（G22 PASS）；
但**手上 6 份报告里有 4 份是旧配置/旧版本的产出**（16.5 小时前、`1920×1080`、旧版 App），
而 G21 报的"输出尺寸 = 1 种"只在那 3 轮**内部**比较 ——
**"一次标定覆盖多次采集"的证据证明的是另一套配置。** 已立判据 G23 堵住这个洞。

同时本轮实测**推翻了自己上轮写进技能与文档的一条规则**：`skew` 不需要按 `N/H` 缩放，
HAL 已经缩过一次；照旧规则做会把卷帘补偿量算成真值的一半。

## 1. 报告与原始数据的三处不一致

### 1.1 六份报告分属两个批次与两套配置（报告完全没提）

| 文件 | 报告内墙钟 | 输出尺寸 | `crop_region` 字段 | App 版本 |
|---|---|---|---|---|
| `m0_capability.json` | 2026-09-24 15:17:34 | — | — | 新 |
| `m0_locked_capture.json` | 2026-09-24 15:18:01 | **1920×1440** | 有 | 新 |
| `m0_rate_sweep.json` | 2026-09-24 15:18:19 | 1920×1440（推测） | — | 新 |
| `m0_locked_capture_r1.json` | **2026-09-23 22:44:28** | **1920×1080** | **无** | 旧 |
| `m0_locked_capture_r2.json` | **2026-09-23 22:44:36** | **1920×1080** | **无** | 旧 |
| `m0_locked_capture_r3.json` | **2026-09-23 22:44:43** | **1920×1080** | **无** | 旧 |

`r1..r3` 比主连拍早 **59 613 s ≈ 16.55 h**。它们是新版 App 上线**之前**那批老文件，
`--pull` 只是把它们又拉了一遍 —— 意味着今天只重跑了 ①②④，**③ 从未在 `1920×1440` 上跑过**。

**为什么这比报告里那两个 WARN 更严重**：G21 的判定是
"焦点回读 ['1.001001','1.001001','1.001001']，极差 0；生效物理镜头 ['2']；**输出尺寸=1 种**；
回读帧时长 [33287995]" —— 这些全部只在 `r1..r3` **内部**一致，与主连拍的 `1920×1440` 无关。
"1 种"这个数让人以为配置统一，实际是"整批都过期"。

### 1.2 G14 的 skew 从一个值变成另一个值，报告没解释

| 报告 | 输出 | `skew` |
|---|---|---|
| 主连拍 | 1920×1440 | **9 212 928 ns** |
| r1 / r2 / r3 | 1920×1080 | **6 909 696 ns** |

只看这两个数会以为 `skew` 在漂。实测**不是漂，是按输出高度缩放**：

```
9212928 / 1440 = 6397.866666...  ns/行
6909696 / 1080 = 6397.866666...  ns/行      ← 8 位有效数字完全一致
9212928 / 6909696 = 1.333333333 = 1440/1080 精确
```

⇒ **`skew` 是"输出帧"的读出时间，随输出行数成正比。** 详见第 3 节。

### 1.3 G20 打印的"累积偏离终值 = +0"是恒等式，不是证据

`cum[i] = Σ_{k≤i}(d_k − mean)`，而 `mean = Σd / n`，所以 `cum[n−1] ≡ 0` 恒成立。
它**永远**是 0，与数据有没有漂移无关。这是我第 3 轮自己写进判据、并在第 4 轮当成
"无漂移"证据引用过的一行字。已删除并换成"每周期之和是否恒定"。

## 2. 两个核心要求的现状

### 2.1 时间戳准确 —— 站得住，而且这轮的表述比前几轮更硬

从逐帧 `sensor_timestamp_ns` 重算（有效帧 145，即 144 个间隔）：

| 量 | 实测 |
|---|---|
| 单调性 | 144 个间隔全严格递增 |
| 取值 | 只有 3 个：`33287916 / 33287917 / 33288125` ns |
| 结构 | `d[i] == d[i+5]` 在 **139/139** 处成立 ⇒ **严格周期 5 的确定性拍频** |
| **每 5 帧一组之和** | **28 个完整个周期全部 = 166 440 000 ns，极差 0** ⇒ **零漂移（精确）** |
| **由周期和推出的名义间隔** | **33 288 000.0 ns**（整数精确） |
| 与回读帧时长 | 33 288 000 vs 33 287 995 ⇒ 差 **5 ns = 0.150 ppm** |
| 累积偏离极值 | −82 / +165 ns（有界，不累积） |

前几轮报的"抖动 3.06 ppm"和第 4 轮的"累积偏离终值 = 0"两个说法都作废：
前者把确定性图案说成噪声，后者是同义反复。**真正的证据是"每个周期的和恒定"** ——
这是精确整数比较，不受窗口长度是不是周期整数倍的相位污染。

### 2.2 内参不变 —— 单会话干净、跨会话"落点可复现"，但**证据对应的不是交付配置**

- **单会话干净**：`active_physical_id` 恒为 2（150 帧）；13 项锁定字段 `distinct_count` 全为 1；
  `crop_region = (0,0,4096,3072)` = 整个活动阵列；`lens_state` 仅第 0 帧 MOVING。
- **跨会话（旧配置）**：3 轮焦点回读极差 0、会话新鲜度 3/3（每轮首帧回到掉电默认超焦距并重新移动
  ⇒ 确为独立 `openCamera`）。
- **两组配置之间，13 项锁定字段有 12 项完全一致**（含 `sensor_pixel_mode = 0`，说明传感器读出模式没变），
  **唯一变化的是 `skew`** —— 因为它是输出几何的派生量。
- **仍未证**：HAL 的距离量化单位实测 = **1 mm**（`1.001001` diopt ⟺ `999.0000 mm`），
  回读值很可能只是"请求量化后回显"。所以 G21 只能证明**请求落点可复现**。
  **"内参是否真的不变"最终只能靠 M1 做两次独立标定比较 `fx`。**

## 3. 本轮最重要的一条技术修正：`skew` 不要自己乘 `N/H`

**旧规则（本仓库早期版本、技能说明、M0 文档都写过）**：
> AOSP：`SENSOR_ROLLING_SHUTTER_SKEW` 按整个活动阵列报告，
> 若输出只覆盖 `N` 行（活动阵列高 `H`），须按 `N/H` 缩放。

**第 5 轮实测把它否掉了。** 同一台机、**同一次 crop**（都 = 全活动阵列 `4096×3072`），
只把输出高度 1080 → 1440：

| 输出 | `skew` | `skew / 输出高` | 占帧周期 |
|---|---|---|---|
| 1920×1080 | 6 909 696 ns | **6397.8667 ns/行** | 20.76% |
| 1920×1440 | 9 212 928 ns | **6397.8667 ns/行** | 27.68% |

两者比值精确 = 4/3，`ns/行` 完全一致（差 0.0 ppm）。
**HAL 已经按输出行数缩放过 `skew`。**

若照旧规则在 1440 高这档再乘一次 `N/H = 1440/3072 = 0.46875`：
`9212928 × 0.46875 = 4 318 560 ns ≈ 4.32 ms` —— **不到真值（9.21 ms）的一半**。
这会让卷帘补偿量系统性偏小一半，而**没有任何判据会报错**（画面正常、标定照常收敛）。

**现行规则**：
1. `skew` 与输出尺寸**绑定记录、绑定冻结**；
2. **换档必须重测**，不得跨档复用、不得自行缩放；
3. 报告打印 `ns/输出行` 便于比对；G23 在多档并存时自动校验该规则。

**副作用（有用的）**：这条比例关系同时是"新输出尺寸确实在 HAL 层生效"的**独立证据** ——
否则 `skew` 不会变。而其余 12 项锁定字段一项没变，说明**只**改了输出几何。

> 一个方法论教训：第 4 轮曾试图用 `skew` 反推"传感器读了哪些行"
> （`6397.87 ns/行` 与 `2249 ns/行` 两套口径并存）。方向搞反了 ——
> `skew` 是输出几何的**派生量**，不能用它反推源量。

## 4. 本轮新增/修改的判据（都做了双向路径测试）

| 判据 | 变化 | 由来 |
|---|---|---|
| **G20** | 主判据从"回归斜率 / 累积偏离"改为**"每周期之和是否恒定"**；删除恒等式"终值"；与回读帧时长的比较改用**周期推出的名义间隔**（无偏） | 周期性序列 + 窗口非周期整数倍 ⇒ 回归斜率会被**残段相位**污染，报出 −0.10 ppm 的假漂移 |
| **G14** | 输出 `ns/输出行`；结论里写明"随输出尺寸变化、勿自行乘 `N/H`" | 见第 3 节 |
| **G16** | 景深改用**回读**对焦距离（原来用请求值），与别处"回读值才是唯一事实"保持一致 | 报告里 `requested = 1.0` 而回读 = `1.001001`（999.0 mm）。本机差 0.1% 无所谓，但超焦距档差 0.36%，而 1 m 处景深只有十几厘米宽 |
| **G23（新）** | **报告集自洽性**：配置指纹（或退回 `output_size`+`format`）+ 批次时间跨度；顺带实测并校验 `skew` 缩放规则 | 见 1.1、第 3 节 |
| **G24（新）** | **输出尺寸定档依据**：有 ⑤ 数据就汇总候选表（帧率 / `skew` / 每帧字节数 / `fx`），没数据就明确提示"档位缺实测依据" | 见第 5 节 |

**双向测试五条路径**（都通过）：
G23 PASS（同配置同批次）/ G23 WARN（跨批次）/ G23 INFO（只有 1 份）/
G20 WARN（注入 30 ppm 线性漂移，周期性被破坏 ⇒ 走回归路径，判出漂移）/
G24 INFO（注入合成 ⑤ 数据，正确汇总出 `1920×1440 → 30.04 fps / 9.21 ms / 4.1 MB / fx 1283 px`）。

## 5. 我不同意"其余已经符合"的一处：输出尺寸档位

G22 转 PASS 说明**改档生效了**，但**没有把 `fx` 提上去**：

| 档位 | 预测 fx | 每帧 YUV |
|---|---|---|
| **1920×1440（当前）** | **1282.5 px** | 4.1 MB |
| 2880×2160 | 1923.8 px | 9.3 MB |
| 4096×3072 | 2736 px | 18.9 MB |

`fx` 与输出**宽度**成正比，而改档只改了高度（1080 → 1440）。现行档位之所以是 1920 宽，
是因为 App 的选档规则里有一个**我上轮设的、没有实测依据的**面积上限：

```kotlin
const val CAPTURE_AREA_CAP_PX = 2048L * 1536L   // ≈ 3.15 MP，当初只是为了避开 16:9
```

它把 `2880×2160` 与 `4096×3072` 都排除了。也就是说：
**这个随手定的常数正在决定方案的精度上限，却没有一条证据链支撑它。**

所以本轮加了 App 的 **⑤ 尺寸扫描**（`m0_size_sweep.json`）：按宽度阶梯
`1920 / 2880 / 4096` 各取一个同纵横比候选，量出各档的实际帧间隔、回读帧时长与 `skew`。
定档时把这张表与带宽预算一起看（宽度翻倍 ⇒ `fx` 翻倍、每帧字节数约翻 4 倍）。
