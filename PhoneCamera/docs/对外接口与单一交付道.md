# 对外接口与单一交付道（被整体架构调用 · 每一帧都留）

> 需求（用户）：本项目作为整体架构的一部分，**负责从手机摄像头采集数据**，会涉及跨程序通信
> 与广播。要求：① 对现有程序打包封装；② 在现有调试基础上**预留被调用的接口**；
> ③ **实时视频流可跨程序通信**；④ **保留原始数据供分析**。
>
> **第 24 轮的用户口径（本轮唯一的验收标准）**：
>
> > "我只想要确保**实际记录的内容能够原封不动地传到电脑上**，如果你所谓的"交付道"已经能完成
> > 这个任务了，就不需要归档道了。"
>
> 追问确认：**"每一帧都留。交付道的目标就是这个，把归档和交付两个合并。"**
>
> ⇒ 第 23 轮设计的"交付道（抽帧）+ 归档道（每一帧）"**合并成一条道**。
> 归档道的一切（`kind=archive`、`archive/` 目录、`s.archives` 表、归档端点、App 归档器、
> 面板归档列）**全部删除**，它的三个增量（**不抽帧** / **配额熔断** / **缺口账本**）
> 并入交付道。
>
> **第 27 轮的用户口径（本轮新增的可选项）**：
>
> > "监视道添加可选项，此时只实时回传数据，不储存也不在事后回传额外的数据。
> > 这一过程允许使用彩色传输"
> > "阻塞发送但是要保证实时性，甚至发送完再拍摄，发送都可以。确认最终方案"
>
> ⇒ 新增 **`capture_mode=live`**：整条会话切成"**只看不留**"，**交付道整体关闭**、
> 允许**彩色**。它与既有的 `deliver` 是**互斥的两种会话性质**，不是"多开一条道"
> （见 **§1.1**、判据 **A9** / **P13**）。默认仍是 `deliver`（**每一帧都留**）。

## 0. 先纠正一句话：为什么"实时把每一帧都传过去"不成立

这条必须先写，因为它是整个方案的**量化地基**，而且它解释了"为什么要先落本地"。

**（a）"实时回传每一帧"确实不可行**（不是保守估计，是 15 倍差距）：

| 量 | 值 | 来源 |
|---|---|---|
| 单帧（1920×1440 纯 Y 平面） | **2 764 800 B = 2.765 MB** | 与 profile 逐字吻合（M1 真机 455 帧） |
| 相机出帧率 | **30.04 fps**（帧周期 33.288 ms） | M0 第 5~9 轮逐帧重算 |
| ⇒ 全帧率数据率 | **83.0 MB/s** | 30.04 × 2.765 MB |
| 手机→PC 实测链路 | **5.5 MB/s** | M1 吞吐实测（App 队列斜率 + PC `upload.log` 两处独立吻合） |
| 回环协议天花板 | 39.0 MB/s（4 帧并行 50.6） | `pc/probe_throughput.py` |

⇒ 83.0 / 5.5 = **15.1 倍**。提高并发、改协议都没用（回环上并发只多 30%）。

**（b）"采集期间写手机本地、边采边传、停采后排空"可行**，但有一条**硬边界**必须写在最前面：

```
可录时长 = 手机可用空间 ÷ 83.0 MB/s
         = 21 GB ÷ 83.0 MB/s  ≈ 4.2 分钟        ← 全帧率 1920×1440
```

**这不是软件能绕过的**：手机写满之后，不只是留存停了 —— **交付和 App 自己也会一起挂**
（元数据、队列、日志全都写不下去）。所以本地留存必须自带**配额 + 熔断**，见 §4.4。

要更长的时长只有三条路（都不改"每一帧都留"的语义）：

| 手段 | 效果 | 代价 |
|---|---|---|
| 降 `SENSOR_FRAME_DURATION`（让相机就出 5 fps，"每一帧"= 5 fps 全留、**零丢弃**） | 13.8 MB/s ⇒ **约 25 分钟** | 需要新的**采集路径**取证（M0 扫过 12/15/24/60 fps，**没有 5 fps**） |
| 降输出尺寸（960×720） | 3.46 MB/s @5 fps ⇒ 约 100 分钟 | `fx` 腰斩，亚像素精度下降约一半 |
| 接 USB（`adb reverse`）代替 WiFi | 上限待实测（USB2 约 30+ MB/s） | 需要连线；**未取证** |
| **用降载旋钮**（`plan.interval_ms > 0`） | 按比例 | ⚠ **语义被改成"只留一部分"** ⇒ 账本里 `every_frame` 变 false |

⚠ **本轮的诚实边界**：无真机连接（`adb devices` = 空），所以
**"手机能否以 83 MB/s 持续写盘"没有实测证据**。判据是"整段留存的
`frames_expected == frames_verified_on_pc`"，但**能不能达到 83 MB/s 只能现场跑一次才知道**。
App 侧因此必须把这件事**做成可读的数**（`store_write_mbps` / `store_bytes`），而不是假设它成立。

## 1. 三条道 + 一个接口面

需求里的四件事落到两个**载荷性质完全不同**的通道上。把它们混成一条是这类系统最常见的失败：

| 道 | 载荷 | 时机 | 可靠性 | 谁消费 |
|---|---|---|---|---|
| **监视道** | 480 宽灰度 JPEG（20–40 KB） | 实时 | **可丢**（不排队、不落盘） | 本机上位机（MJPEG）+ 浏览器面板 |
| **交付道** | **每一帧**的原始 Y 平面（2.765 MB/帧）+ 逐帧元数据 | 先落手机本地 → 边采边传 → 停采后排空 | **一帧不落**（`verified` 才算，且有完整性账本） | 在线算法 + **离线分析** |
| **实时道**（`capture_mode=live`） | **彩色 JPEG**（默认 960×720 q70，可调） | 实时、**串行闭环**（发送完再拍摄） | **可丢**（不排队、**零留存**、允许彩色） | 只想"看得清"的现场查看 |

> ⚠ **实时道不是监视道的替代，而是"整条会话性质的切换"**：`capture_mode=live` 时
> **交付道整体关闭**（不落盘、不起 writer、不排空、连 WS 的 `thumb` 也关），
> 这时**唯一的道就是实时道**，并且它**允许彩色**——这是用户明确要的那个可选项
> （第 27 轮口径：「监视道添加可选项，此时只实时回传数据，不储存也不在事后回传额外的数据。
> 这一过程允许使用彩色传输」）。
> 载荷性质与其它两条道都不同 ⇒ **必须是独立的路径 id**（`live_stream_color`，见 §6.1）。

> **第 23 轮的"归档道"为什么可以被删掉**：逐行核实过它唯一比交付道多做的事就是
> **不抽帧**。原始数据的保真链本来就已经在交付道上：
> 送的是**原始 Y 平面**（`lossy: false`）、**逐帧 sha256** 校验后才算 `verified`、
> `extractY` 只去掉行尾填充（**像素值不变**）。
> ⇒ "传输环节动数据"的担心不成立；真正没做到"每一帧都留"的，是**抽帧**。
> 抽帧一取消，两条道就重合了 —— 于是合并。

三条道的仲裁规则（**不许互相借道**，M2 已确立）：

1. **可丢的绝不进可靠队列**：监视道与交付道共队列 ⇒ 交付积压时实时画面一起卡死
   ⇒ 等于没分道。
2. **监视道提速不得改采集行为**：`thumb_interval_ms` 是**纯显示通道的节奏**，
   不进 HAL 请求、不进元数据、不进配置指纹（M1 §4.6：把已经在手的帧画出来是纯显示）。
   ⇒ **默认值保持 1000 ms 不变**，实时档（100 ms ≈ 10 fps）需显式开启。
3. **不回传"看不见的进度"**：留存进度必须**常驻可见**（`store` 段 + `delivery_progress` 事件），
   否则"边采边传"会退化成"采完了才发现没传出去"。
4. **两条道不许共用同一个取图回调**（第 27 轮新增，这是本轮最关键的架构约束）：
   `deliver` 必须 `acquireNextImage()`（FIFO 逐帧，才能与 `SENSOR_TIMESTAMP` 配对）；
   `live` 必须 `acquireLatestImage()`（要的是"此刻最新"）。
   **两者对取图语义的要求正好相反** ⇒ `live` 下**不注册** `onImage` 回调，
   改由实时线程自己循环取图。理由见 §1.1。

### 1.1 实时道：`capture_mode=live`（"只看不留"）

**它存在的理由**：现场有一类需求是"我只要现在**看得清**，不要留档"——
联网看取景、对焦、找目标。这类场景下"每一帧都落本地再回传"是纯负担
（2.765 MB/帧 ≈ 83 MB/s 的写盘负载 + 21 GB 空间 4.2 分钟写满）。
于是给一个**整条会话性质切换**的开关。

**"实时"的可验证定义 = 延迟不累积**（不是高 fps）：

| 做法 | 第 N 帧的延迟 | 含义 |
|---|---|---|
| 有队列（边采边发） | `队列长 × 单帧时间`，**随运行时长线性增长** | 越跑越迟钝 ⇒ 其实是"慢半拍的录像" |
| **串行闭环**（本方案） | 恒为"编码 + 单帧传输"，**与运行时长无关** | 永远只差"发送这一帧"的时间 |

这就是用户那句「**发送完再拍摄**」的真正含义。所以实时线程是严格串行的：

```
acquireLatestImage() → 编码彩色 JPEG → **阻塞** POST /api/v1/live/frame → 回到 acquire
```

**为什么走独立 HTTP 二进制、而不是复用控制道的 WS**：`live` 是"尽力发"，
必然占满链路 ⇒ 同一条 WS 上会挤 `start` / `stop` 的时延；
且 WS 走文本帧 + base64（**+33% 膨胀**）。HTTP 二进制两者都避开。
⇒ `live` 下 App 侧 **WS `thumb` 通道关闭**，控制道只剩指令与事件。

**为什么用 `acquireLatestImage` 而不是 `acquireNextImage`**：前者会**主动丢掉**
没被及时取走的陈帧（这正是我们要的——发不赢就跳过，而不是排队）。
但它丢的帧数 Android **没有精确 API** ⇒ App 侧只能给**估算值** `skipped_est`
（口径 = 取图间隔 ÷ 帧栅格周期 − 1）。**带 `_est` 后缀是为了让判据不得强于事实**。

⚠ **`skipped` 与 `dropped` 不许合并**：`skipped` = 设计内的跳过（链路不够快）；
`dropped` = 队列满 / 编码失败等**异常**。合并后就分不清"链路不够快"与"实现有 bug"。

**"不储存"这条承诺有三处独立证据**（判据见 §7 的 `A9`）：

| # | 证据 | 为什么必须独立 |
|---|---|---|
| ① | 接口三态：`store.applicable=false`、`delivery_complete=**null**`（**不适用**）、note 含「不适用」 | 消费方靠它显示，但**接口字段是自报的** |
| ② | **磁盘事实**：该会话 `frames/` 里**一个 `.yuv` 都没有** | "落盘才是真相"——只看接口字段不够 |
| ③ | **源码锚定**：`startLiveLoop` 函数体内**不得**出现 `enqueue(` / `startWriter(` | 行为测试抓不住"修没修都不报错"的缺陷 |

⚠ **`delivery_complete` 必须判 `null`（而不是 `false`）**：
`false` 的含义是"有留存机制、但没收全"；live 下**留存这个概念不存在**。
把"不适用"写成 `false`，面板会显示成一个**永远失败的进度条**——
而其实没有失败，是问题问错了。三态必须分清：
**不适用**（live）≠ **判不了**（取证不足，`null`）≠ **0 帧**（有机制但没写成 = 缺陷）。

**保留安全旋钮**：`plan.live_max_mbps`（默认 0 = 不限）——
实时道是"尽力发"，现场若把链路打满影响了别的用途，能一键限速。
它**不进**采集路径登记表（改它不改变"产出物是什么"，只改发多快）。

**版本与登记**：App `1.14.0`、`SERVER_VERSION 1.15.0`（对外行为多了一种 ⇒ minor +1）；
登记表**新增** `live_stream_color`(rev=1)，**既有路径 rev 一个不动**
（`stream_deliver_yuv` 仍为 3）——见 §6.1。

## 2. 对本机上位机的接口面（localhost-only）

**这是"预留被调用的接口"的实体。** 设计的出发点：凡是"另一段程序要接进来"，都应当能靠
**一个 HTTP 地址 + 一份 JSON** 完成，不需要读本项目的源码。

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/v1/capabilities` | 无（只读、不含凭据） | **能力与版本声明**：`lanes.monitor` / `lanes.delivery` / **`lanes.live`**、各道的 `knobs` 与 `ledger` 字段表、**`console.features`（控制台功能映射，见 §2.4）**、`routes`（**从真实路由表导出**的端点清单）。上位机启动时先读它，不要假定接口存在 |
| GET | `/api/v1/host/status` | **需要 token** | 机器可读状态（见 §3），替代"人去浏览器看面板" |
| POST | `/api/v1/control/{action}` | **需要 token** | 启动/停止采集（`action=start\|stop`，复用既有面板接口）。`start` 的 body 可带 **`capture_mode`**（`deliver`（默认）\| `live`），非法值 ⇒ 显式 **400 `bad_capture_mode`**（不许静默退回默认） |
| GET | `/stream/mjpeg` | **需要 token** | **实时视频流**：`multipart/x-mixed-replace`，可直接给 `cv2.VideoCapture` / `ffmpeg` / `<img>`。⚠ **live 的彩色帧也走这条管线**（监视道与实时道在此汇合） |
| POST | `/api/v1/live/frame` | **无** ⚠ 已知开口，见 §9 | **实时道帧入口**（设备面）：body 是**裸 JPEG 字节**，header 带 `X-Session-Id` / `X-Seq` / `X-Sensor-Timestamp-Ns`。**只转 MJPEG，绝不落盘**。会话 `capture_mode != live` ⇒ **400 `mode_conflict`**（模式互斥**由服务端判**，不靠 App 自觉）；未知会话 ⇒ 404 且**不建目录** |
| GET | `/api/v1/host/events` | **需要 token** | **WS 事件广播**（订阅制，见 §3.3） |
| GET | `/api/v1/pair` | **需要 token** | **配对三件套**：网址 + token + 二维码（三种形态）。**唯一要求 token 的读接口** —— 它返回的正是 token 本身（见 §2.5） |
| GET | `/api/v1/sessions` | 无 | 面板用（保留原样，不破坏既有调试入口）；`sessions[].store` 就是该会话的账本 |
| GET | `/api/v1/sessions/{sid}/thumb/latest` | 无 | 监视道最新一张 JPEG（**与面板轮询用的是同一条**）。⚠ 已知开口，见 §9 |

> ⚠ **第 24 轮删掉了 `GET /api/v1/sessions/{sid}/archive`**：账本现在只有两个出口
> ——`host/status` 的 `store` 段与 `sessions[]` 的 `store` 段——**而且必须是同一份**
> （"面板说好、接口说不清"是上一轮专门避免过的坑）。判据 `A6d` 钉住这一点。

> ⚠ **第 25 轮补的欠账：「声明必须为真」。** 上表把 `POST /api/v1/control/{start|stop}`
> 写成"需要 token"，`capabilities.auth.token_required` 里也列了它 —— 而 `h_control`
> **从不校验 token**。名不副实只是表层，真问题是：它**不在 loopback 名单里**
> （名单只有 `/api/v1/host/`、`/stream/`）⇒ **同一局域网里任何一台机器都能启停采集**
> （让手机白录、写满存储、PC 建一堆空会话）。现已真的校验（`SERVER_VERSION` `1.13.0 → 1.13.1`，
> 对"不带 token 调 control"的调用方是不兼容变更，所以版本号必须变），并且加了一条
> **从声明自身推导**的判据 `A1f`：拿 `capabilities.auth.token_required` 里列的每一条路径，
> 不带 token 打过去都必须是 403 —— 以后谁往声明里加一条却没实现，这条判据立刻红，
> 不用再靠人记。`A1g` 还要求**错 token 也 403**（不能只判"有没有"），
> `A1h` 锚定面板的 control 调用自带 token（否则给服务端加鉴权就把**取证入口**打死了）。

### 2.1 为什么必须是 loopback-only（而不是"反正没人知道端口"）

设备侧的接口（`/api/v1/files/*`、`/ws`）**天生必须监听 `0.0.0.0`**（手机要连进来）。
于是本机接口与设备接口**共用同一个端口**，把 `host/status`、`control`、`stream` 暴露给了整个局域网。
处置：**中间件按对端地址判定** —— 非 loopback 访问上表受控的路径一律 `403 not_local`。

> 为什么按**对端地址**判、而不是按 `Host` 头：`Host` 头是客户端可任意伪造的，
> 按它判等于没判。这里要防的恰恰是"同一个局域网里另一台机器来读我们的状态/看我们的画面"。
> ⚠ 一个必须写明的例外：`--host 0.0.0.0` 下若有**反向代理**转发过来，对端会是代理地址 ⇒
> 这种部署方式**不支持**（本项目不做反向代理）。宁可少一种部署，不要留一个静默的绕过口。
> ⚠ 拿不到对端地址时 **fail closed**（不是放行）。

### 2.2 三行接入（`pc/hostlink.py`）

```python
from hostlink import HostLink
h = HostLink("http://127.0.0.1:8765", token="ab12cd34")
h.start()                      # 等价于面板点「开始采集」
print(h.status()["capture"])   # 机器可读状态
print(h.ledger())              # 交付道账本（= host/status 的 store 段）
for ev in h.events():          # 订阅广播（生成器）
    print(ev["type"], ev.get("seq"))
```

面板（控制台）能做的，这个库都能做（§2.4 的映射表由服务端声明、判据自动核对）：

```python
print(h.overview())            # 面板顶部环境行：profile / 数据目录 / WS 客户端数
print(h.sessions()[0])         # 面板会话表那一行（含 store 账本 / 门控 / 镜头）
p = h.pair()                   # 配对三件套：网址 + token + 二维码
print(p["url"], p["token"], [x["adapter"] for x in p["hosts"]])
h.qr_png("pair.png")           # 二维码落成 PNG（⚠ 图里有 token，等同凭据）
print(h.thumb_url())           # 监视道最新一张（与面板轮询用的是同一条 URL）
```

实时流不必用这个库（它是标准 MJPEG）：

```python
import cv2
cap = cv2.VideoCapture("http://127.0.0.1:8765/stream/mjpeg?token=ab12cd34")
```

> ⚠ **MJPEG 是"看得见"，不是"算得准"**：它经 JPEG 有损压缩、来自**可丢**的监视道，
> 分辨率与帧率由监视道档位决定。**任何用于测量/分析的数据都必须取交付道。**

> ⚠ **广播类型名分两条道**，消费者最容易在这里搞错：`start` / `stop` 是**设备道**
> （`/ws`）的消息类型；**本机事件道**（`/api/v1/host/events`）用的是
> `session_started` / `stopped` / `frame_verified` / `delivery_done` / `delivery_progress`
> / `delivery_aborted` / `device_online` / `device_offline`。按 `start` 去过滤本机事件道
> 只会收到握手，不会收到任何业务事件（本轮 P3 就是这么红过一次）。

### 2.3 跨程序验证：为什么另有一份 `pc/test_interop.py`

`pc/test_server.py` 用 aiohttp **在同一个进程里**打服务 —— 它证明的是**协议正确**；
而本节承诺的是"**整体架构里的其它程序**能直接消费"，这是另一件事：
同进程里跑得通的客户端，可能暗地里依赖了只有本项目才有的东西（aiohttp 的 WS / multipart
解析、共享的 Python 对象）。所以另有一份脚本：**起独立进程的服务**，再用**三套互不相关的
技术栈**去读它 —— 本项目反复栽在"测试全绿、现场不 work"上，所以消费端刻意不共用任何代码：

| 判据 | 内容 |
|---|---|
| P1 | `capabilities` 无需 token、**不含凭据**、道声明结构完整且**恰有一条非 lossy 的留存道**（含反例：合成一个含 token 的响应，同一个嗅探器必须判否） |
| P2 | `hostlink.status()` 有 `store` 无 `archive`；账本两个出口**同一口径**；两个缺口分开命名 |
| P3 | `hostlink.events()` 收到 `hello` 与 `session_started`（广播能被第三方程序消费） |
| P4 | `hostlink.start()` 三行接入即闭环；控制指令**真的到了设备**；**默认 plan 不抽帧**（`interval_ms == 0`）+ 源码锚定（旧的 200 ms 默认必须消失） |
| P5 | **`cv2.VideoCapture`** 直读实时流，且解出来的**内容**就是发过去那张（480×360 灰度渐变：左黑右白、均值 ≈127.5）—— 不是"有字节就算" |
| P6 | **`ffmpeg`（另一个操作系统进程、非 Python）** 解出 2 帧，尺寸与像素均值都对 —— 这才是"消费方零依赖"的证据 |
| P7 | 无 token 的 `host/status`、`/stream/mjpeg` 都 403 |
| P8 | control 无 token ⇒ 403、错 token ⇒ 403、对 token ⇒ 200 |
| P9 | **第三方 DX**：连不上时抛的是可读的 `HostLinkError`（不是裸 `URLError`），调用方才有线索排查 |
| P10 | 文档里的接入示例**真的能跑**：README 的每个 `h.xxx` 都真实存在、构造函数关键字都在签名里（含反例：旧的坏示例必须被全部报出来） |
| P11 | 配对**三件套**：`pair()` 给全网址 + token + 二维码；`qr_png()` 落盘；**接口真实产出的 PNG 交给另一个 JVM 进程的 zxing 解出并逐字符比对**（含"换个码必须解出不同"的反例） |
| P12 | 用 hostlink **代替面板**走一遍：`overview` / `sessions` / `start` / `status` / `stop` / `ledger` / `thumb_url` / `mjpeg_url` —— 面板能做的，第三方程序都能做 |
| P13 | **实时道（`capture_mode=live`，只看不留）**：用**标准库**推彩色帧、再用 **cv2** 从 MJPEG 把它**解出来比像素**（左半红 / 右半蓝）⇒ 证明这段画面**真的是彩色**；配反例：同一套判据用在**灰度**帧上必须判否；另含跨进程的模式互斥反例 |
| P14 | **环境里的代理不得影响接入**：注入一个"死代理"（`HTTP_PROXY=http://127.0.0.1:1`）后，`hostlink` 必须照常工作（**行为只该取决于地址，不该取决于这台机器上装了什么软件**）；配反例：同一注入下"按默认方式（读环境）新建的 opener"必须被带偏 ⇒ 必须失败（防"注入根本没生效"而真空通过） |

跑法：`python pc/test_interop.py`（需要 aiohttp + cv2 + ffmpeg；`P11f` 另需 JDK 与
`app/libs/core-3.5.3.jar` —— **缺哪个就判 FAIL 并说明，不静默跳过**，因为本轮要证的正是
"二维码能被扫出来 / 别的程序能用"）。

> 这条判据本轮**真的抓到东西**：`P4b/P4c` 抓出 `hostlink.start()` 的默认 plan 仍停在
> `interval_ms: 200`（合并前的旧语义）—— 本库**显式下发 plan**，服务端默认兜不住它
> ⇒ 任何用这个便利方法的程序都会**静默拿到 1/6 的帧**，而 `status()` 里 `every_frame` 变 false。
> **同一件事在两条实现里各写一遍默认值，就一定会分叉** —— 判据必须是源码锚定的，
> 而且要有反例（"旧写法必须消失"）。

### 2.4 控制台能做的，接口都能做（**这张表由声明驱动，不由文档驱动**）

需求口径：「对外接口要包括**在现有项目控制台的全部功能**」。这句话如果只写在文档里，
就只能靠人定期核对 —— 而"面板加了个控件、声明忘了补"是最容易发生的漂移（第 25 轮在同类
地方一次抓到三处"声明与实现不符"）。所以它写成了 **`capabilities.console`**，
再由判据**从这份声明自身推导**逐项探针。

| 面板上做的事 | 接口 | hostlink |
|---|---|---|
| 顶部环境行（profile / 数据目录 / WS 客户端数 / 启动时刻） | `GET /api/v1/sessions` 的**外层信封** | `overview()` |
| 会话表 11 列（含留存账本、门控、镜头） | `GET /api/v1/sessions` 的 `sessions[]` | `sessions()` |
| ▶ 开始采集 | `POST /api/v1/control/{action}`（`action=start`） | `start()` |
| ■ 停止 | 同上（`action=stop`） | `stop()` |
| **采集模式选择（deliver / live）** | 同上（`start` 的 body 带 `capture_mode`） | `start(capture_mode=…)` |
| 指令回执 / 状态变化的即时刷新（面板 WS） | `WS /api/v1/host/events` | `events()` |
| 监视道缩略图 + **live 模式的彩色画面**（同一条 MJPEG 管线） | `GET /stream/mjpeg` | `mjpeg_url()` |
| 监视道最新一张（轮询兜底的那条 URL） | `GET /api/v1/sessions/{sid}/thumb/latest` | `thumb_url()` |
| 扫码配对（二维码 + 配对码 + 地址 + token） | `GET /api/v1/pair` | `pair()` / `pair_url()` / `qr_png()` |
| （面板无对应控件，接口更全）整机状态 | `GET /api/v1/host/status` | `status()` / `ledger()` |
| （面板**无**对应控件，接口更全）**开 live 会话（只看不留）** | `POST /api/v1/control/start` 带 `capture_mode=live` | `start(capture_mode="live")` |

四条"声明必须为真"的判据（`A8`，每条都配反例）：

| 判据 | 内容 |
|---|---|
| `A8b` | 声明里的每条 `endpoint` **都真的在路由表里** —— 比对 `capabilities.routes`（**从 `app.router.routes()` 导出**），不让判据去猜"404 到底是路由没有、还是业务说会话不存在" |
| `A8d` | 声明要 token 的，**不带 token 与带错 token 都必须 403**（逐条探，不另抄清单） |
| `A8e` | 声明里的 `hostlink` 方法名**都真的定义在 `pc/hostlink.py` 里**（源码锚定；**读不到源文件判 FAIL**，不是 INCOMPLETE —— 锚定失效等于没测） |
| `A8f` | **反向**：面板源码里用到的每个路径都被声明覆盖 —— 面板新增控件而没同步声明 ⇒ 立刻红 |

> ⚠ 反例与正例**成对**：`A8c` 拿两条伪造的声明喂给探针必须判否（否则探针空转），
> `A8c2` 拿真声明喂给同一探针必须全过（否则"恒判否"也能全绿）。
> **只写反例不写正例，反向用例自己就会真空通过**（第 18 轮栽过）。
>
> ⚠ **第 28 轮：`live` 模式从"接口能做、面板做不到"升为面板控件** ——
> 于是它的声明必须**从 `beyond_console` 搬进 `features`**（留在原地那句话就变成假话：
> 那里写着"面板上暂时没有这个开关"）。判据 `A9m3` 钉住这次搬迁。
> **漂移是双向的**：不只"面板加了控件忘了声明"，也有"声明说面板没有、其实已经有了"。
>
> ⚠ `endpoint` 写的是**真实路由模板**（如 `/api/v1/control/{action}`），`probe` 给出
> "能真打到的具体路径"。第一版把 start/stop 写成理想化的 `/api/v1/control/start`，
> **`A8b` 当场红** —— 这正是这张表该起的作用：声明与实现不一致时，**红的是声明，不是人**。

### 2.5 配对三件套：网址 / token / 二维码

`GET /api/v1/pair?token=…` 一次给全（= 面板顶部"扫码配对"那一块的全部内容）：

| 字段 | 内容 |
|---|---|
| `url` | 整行可粘贴：`http://<ip>:<port>/?token=…` |
| `host` / `port` / `token` | 分开的单项（有些程序要自己拼） |
| `hosts[]` | **全部网卡候选**：`{ip, adapter, virtual, recommended, url, pair_uri}`。多网卡机器上首选未必对（VPN / 虚拟网卡 / 双网段），所以候选**都给出来**；`recommended=True` 的那条与 `pair_uri` 一致 |
| `pair_uri` | 配对码 `m0probe://pair?h=…&p=…&t=…`（**格式由 App 侧锚定**，见 `docs/扫码配对.md`） |
| `qr_svg` | 二维码 SVG（面板内联进 DOM；矢量、放大不糊） |
| `qr_matrix` | **`{size, border, bit, rows}`**：每行一个 `0/1` 字符串，**任何语言都能自己画**（C++/Go/嵌入式上位机都能用）。⚠ **必须带 `border`（静区）** —— 只给黑模块边界而不说四周留几格白，画出来**看着完全正常但扫不出来** |
| `qr_png_b64` | PNG（base64）：存盘 / 贴文档 / 丢给别的工具 |
| `qr_formats` | 三形态的**可用性声明** + `missing_deps` + 降级说明。**缺席必须有解释**：`qr_svg: null` 单看只像"没生成"，调用方无从知道该装依赖、该重试、还是该退回手输 |

三者**共用同一个模块矩阵**（`qr_modules()`）。判据 `A8g2` 逐格比对 SVG 与 matrix、
`A8h2` 把 PNG 解码后**按模块中心采样**再逐格比对 —— **只比黑模块个数是不够的**：
把两个模块互换位置，数量一个不差，而码已经废了。

> ⚠ **"给出来了" ≠ "扫得出来"**：`P11f` 把**接口真实产出的 PNG** 交给 **App 里那个
> zxing jar**（另一个 JVM 进程、另一套实现）解码，逐字符比对配对码；
> `P11g` 再拿"换个地址的码"做反例，要求解出来**必须不同** —— 否则 `P11f` 只是在比两个常量。
> ⚠ 夹具必须取**被观测对象的真实产出**（这里是接口当场给的那张 PNG），
> 不是"我们自己另画一张"—— 第 20 轮的教训：夹具写 `"OFF"` 而真机是 `"OFF(0)"`，
> 测试全绿、现场全坏。

> ⚠ **这些内容绝不进 `capabilities`**：那个接口无需 token 就能读，放配对信息等于把凭据
> 广播给同网段。判据 `A8k` 钉住"新增的 console / routes 段不含凭据"。
> `hostlink.pair()` 的返回体**含 token**（等同凭据）⇒ 别写进日志、别贴进 issue、别投屏；
> 要落盘就用 `qr_png()`（只写图，不写整个响应）。

### 3.1 `GET /api/v1/host/status`

```json
{
  "ok": true, "server_version": "1.15.0", "protocol_version": 1,
  "capture": {"running": true, "session_id": "s20260925-1", "state": "running",
              "frames_verified": 67, "deliver_fps": 0, "upload_mbps": 5.5,

  "device":  {"connected": true, "model": "…", "serial": "…", "app_version": "m0probe-1.14.0"},
  "gate":    {"status": "pass", "checked": true, "hard_fail": []},
  "monitor": {"subscribers": 1, "thumbs": 44, "thumb_fps": 1.0, "interval_ms": 1000},
  "store":   {"applicable": true, "mode": "deliver",
              "state": "recording", "every_frame": true, "interval_ms": 0,
              "frames_expected": 412, "frames_stored_on_device": 412, "gaps_on_device": 0,
              "frames_verified_on_pc": 388, "upload_gaps": 24,
              "missing_seqs": [301, 302, "…"], "missing_seqs_note": null,
              "seq_first": 0, "seq_last": 411, "complete": false,
              "self_consistent": true, "aborted_reason": null},
  "live":    {"applicable": false, "mode": "deliver", "frames_received": 0, "bytes_received": 0},
  "storage": {"data_dir": "…", "free_gb": 412.3},
  "sessions": ["s20260925-1"]
}
```

> ⚠ **`capture_mode=live` 时 `store` 那个对象会变样**（三态必须分清）：
> `store.applicable=false`、`store.state="not_applicable"`、`delivery_complete=null`、
> 各计数为 `null`，并附 `note` 明写「**不适用**」；同时 `live.applicable=true`
> 带上实时道账本（`frames_received` / `bytes_received` / `mbps_received` / `fps_actual` /
> `skipped_est` / `dropped` / `rejected`）。
> **两个 `applicable` 是互补的**——消费方不必改取值路径就能显示，
> 且 `null` 与 `0` 在界面上必须能区分（"不适用" ≠ "0 帧" ≠ "判不了"）。

**这个接口的价值在于"把面板上的判断变成机器可读的判断"**——而它的字段含义必须与面板一致
（否则会出现"面板说好、接口说不清"）。特别地：

- `gate.status` 三态（`pass`/`fail`/`incomplete`）必须原样透出：**`incomplete` 不是通过**；
- `store.complete` 可以**是 `null`**（App 还没宣告应有帧数）⇒ **判不了 ≠ 通过**；
- `store.missing_seqs_note` 非空表示**三条证据互相矛盾**（见 §5.3），此时**不要照任何一方去补采**。

### 3.2 `GET /stream/mjpeg`

- `Content-Type: multipart/x-mixed-replace; boundary=…`，每部分 `Content-Type: image/jpeg`
- `Cache-Control: no-store`（否则浏览器/代理缓存会让画面冻住）
- 每帧之间按**最新**原则：订阅者拿到的永远是"当前最新一张"，慢消费者**丢自己的旧帧**，
  **绝不阻塞**投递方（沿用面板推送的教训：在别人的消息循环里 `await` = 把那条循环的生死交出去）
- **接入即得画面**：断开后没有任何新推送时，新订阅者仍须立刻拿到缓存的最新一张
  （否则 1 Hz 档下最长要等 1 秒，现场会以为"流没连上"）
- 订阅者断开不得影响控制道/交付道；订阅数进 `host/status`

### 3.3 `GET /api/v1/host/events`（WS 广播）

| 事件 | 载荷要点 |
|---|---|
| `session_started` | `session_id` / `profile_id` / `capture_path_id` / `rev` |
| `frame_verified` | `session_id` / `seq` / `bytes` / `sensor_timestamp_ns` / `file` |
| `gate` | `session_id` / `status`（pass/fail/incomplete）/ `hard_fail` |
| `stopped` | `session_id` / `stopped_at` / `frames` |
| `delivery_done` | `session_id` / `frames` / 完整账本（见 §5.3） |
| `delivery_progress` | `session_id` / `declared`（账本快照） —— **节流**（默认 2 s） |
| `delivery_aborted` | `session_id` / `reason` / `message` / 账本快照 |
| `device_online` / `device_offline` | `device_serial` |

**每个订阅者一个定长队列**（默认 512 条），满则**丢最旧**并累计 `dropped`；
`delivery_progress` 是**节流**的（默认 2 s 一条）——否则 30 fps × 每帧一条 = 每秒 30 条事件，
订阅者一个慢就积压。事件里带 `dropped` 计数，**慢消费者必须能知道自己漏了**（不许静默）。
⚠ 反过来：`throttle_s=0` 时**必须一条不落地全发** —— 节流不许变成静默丢弃（判据 `A5g`）。

## 4. 交付道：采集期间（手机本地）

> ⚠ **本章只适用于 `capture_mode=deliver`。** `capture_mode=live` 时交付道**整体不存在**
> ——不起 writer、不写 `frames/`、不写 `index.jsonl`、不排空（见 §1.1）。
> App 侧的对应实现是：`startCapture()` 走 `storeState = "not_applicable"` 而**不调 `startStore()`**，
> 且 `onImage` 回调**根本不注册**。判据 `A9e` 直接查"live 会话的 `frames/` 里一个 `.yuv` 都没有"。

### 4.1 采集期间写什么

**每一帧**（不是抽帧后的子集），且**与交付帧同目录、同命名**（因为只有一条道了）：

- `frames/frame_%06d.yuv` —— 原始 Y 平面，**不转码**
- `frames/frame_%06d.json` —— 该帧的相机状态（`sensor_timestamp_ns` / 曝光 / ISO / 镜头 /
  `crop_region` / `rolling_shutter_skew_ns` / `zoom_*` …）
- `index.jsonl` —— **追加式**索引，每帧一行（帧号 → 时间戳 → 文件 → 字节 → sha256）

> **为什么是追加式 `jsonl` 而不是一个大 `manifest.json`**：30 fps 下把 N 条清单重写一遍，
> 写到第 4 分钟就是每帧重写几 MB × 30/s 的额外写。**索引必须 O(1) 追加。**

### 4.2 原子序与"缺口"的定义

沿用交付道的原子序（`.part` → rename → 再写 json），但**多一个必须记账的量**：
**写不过来的时候，缺的是哪几帧**。

```
frames_expected         = 相机实际产出并进入回调的帧数（逐帧 ++，**唯一的分母**）
frames_stored_on_device = 原子序完成落盘的帧数
gaps_on_device          = expected − stored，且**必须记下具体位置**（不是只给个数）
```

⚠ **"写不过来"必须有名字**，而且**四条路径都要进账本**（这是第 24 轮修的核心缺陷，见 §4.5）：

| 丢帧路径 | 记账用的 `why` |
|---|---|
| 写队列满（`writeQueue.offer` 返回 false） | `write_queue_full` |
| 图从未到达（结果先到、图未到，且最终没配上） | `image_never_arrived` |
| 写盘失败（I/O 异常） | `write_failed` |
| 元数据组装失败 | `meta_build_failed` |

- 缺口的**位置**按 `sensor_timestamp_ns` 记（不是序号）——因为**被丢的帧根本没有 seq**
  （seq 是写盘成功时才分配的）；
- `gaps_on_device` 与"抽帧没抽到"**完全无关**（后者一旦发生，`every_frame` 会变成 false，
  语义变化是**可见**的，不许混进缺口计数）；
- 缺口一旦存在，账本的 `complete` 必须是 `false`，并且**不许**用"反正大多数帧都在"含糊过去。

### 4.3 writer 线程（为什么不能写在回调里）

交付道已经踩过一次（M1 §4）：写一帧 2.7 MB 会阻塞**相机回调线程**，而回调线程决定了
"哪一帧被抽中"。**不抽帧之后**，写盘负载是全帧率的（83 MB/s 量级），
写在回调里等于**把采集节奏交给磁盘**。⇒ 元数据在回调线程组好，
**字节与 json 的写盘全部交给独立 writer 线程**；回调只做"取 Y 平面 → 投递 → 返回"。

### 4.4 配额与熔断（**这条是安全阀，不是优化**）

| 规则 | 理由 |
|---|---|
| 留存前检查可用空间，预算 = 剩余空间的 50%（`profile.store_budget_gb` 可覆盖） | 写满手机 ⇒ **交付和 App 一起挂**（元数据/队列/日志都写不下） |
| 剩余空间低于 `profile.store_reserve_gb`（默认 2 GB）⇒ **立即停写盘**并把 `store.state` 置 `aborted_no_space` | 宁可少留，不可失联。**必须显式命名，不许静默停止** |
| **熔断只停写盘、不停回传**：已存下的帧照常传完 | 熔断保的是"已经拿到的数据"（判据 `A7b`） |
| 写入速率与空间占用进 `status`（`store_write_mbps` / `store_bytes` / 剩余空间） | 现场要能回答"还能录多久" |

### 4.5 本轮的命门：静默丢帧（已修）

**症状**：`writeQueue.offer(...)`（容量 **32**）的返回值**从未被检查**。
队列满时那一帧**静默消失**，而：

- App 的 `deliveredCount`（**写盘成功才 `++`**）少一帧；
- App 的 `queue_len`（**数磁盘上的 `.yuv`**）少一帧；
- PC 的 `_delivery_complete`（**就靠这两个数**）因此也认为"一帧不少"。

**三方一致地少一帧，谁都发现不了** —— 这与"每一帧都留"直接冲突。

**修法**：检查返回值 + 把四条丢帧路径**全部**计入账本（§4.2 的表），
并用**源码锚定**判据（`R9a`/`R9b`）钉住"必须检查返回值、且旧写法必须消失"。

> 为什么这类缺陷要用**源码锚定**而不是行为测试：它的特征是**"修没修都不报错"**。
> 只有把"必须长成什么样"钉在源码上，回归才会响。

## 5. 交付道：回传

### 5.1 触发顺序（不许抢带宽）

```
开始采集 → 每一帧先落手机本地（原子序）→ 上传线程持续把已落盘的帧传出去
停止采集 → 本地队列排空（把没传完的补传完）→ delivery_done（App 宣告账本）
```

与第 23 轮的区别：**不再是"采集结束之后才回传"**。
第 23 轮的串行是为了"不让归档抢实时交付的带宽"；合并后只有一条道，
实时与留存是**同一批数据**，抢带宽的问题自动消失 —— 但仍然要
**先落本地再传**（83.0 vs 5.5 MB/s，差 15.1 倍），否则一帧都保不住。

⚠ **"停采集 ≠ 停交付"**（第 21 轮用户诉求的判据化）：控制道完全离线时，
HTTP 交付仍必须照常 `verified` —— "实时联通结束"≠"不能回传"。

### 5.2 复用既有协议的三个硬要求

合并后**这三条都消失了**（第 23 轮为了给归档道腾地方才需要它们）：

| # | 第 23 轮的处置 | 第 24 轮 |
|---|---|---|
| 1 | 幂等键含 `kind`：`(sid, serial, kind, seq)` | **去掉 `kind`**：`(sid, serial, seq)`。`kind` 只剩一个合法值 `"frame"` |
| 2 | 归档落 `archive/` 子目录 + `aframe_*` | **只有一个目录一种命名**：`frames/frame_*` |
| 3 | 归档单独一张表 `s.archives[seq]` | **只有一张表** `s.frames[seq]` |

> ⚠ 但"删除项比新增更容易悄悄复发"，所以每一条删除都有判据钉住：
> `R3a`（落盘只有一个目录）、`R3b`（内存只有一张表）、`R1e`/`R3c`（源码里已无 `archives` /
> `KIND_ARCHIVE`）、`R8d`（面板不再读 `s.archive`）。
> **旧客户端（App ≤ 1.12.0）带的 `kind="archive"` 会被显式 `400 lane_merged` 拒绝** ——
> 因为归档帧与交付帧**共用同一个 seq 空间**，若默默放行，归档 seq=7 会写进交付 seq=7 的位置，
> **后到的静默覆盖先到的，而两边都显示"已 verified"**。宁可显式报错，逼老客户端升级。

### 5.3 账本：三个来源、两个缺口、两条自洽式

**PC 绝不采信 App 自报的"我传完了"**（铁律：不采信被测程序自报的汇总结论）。

| 字段 | 谁算的 | 含义 |
|---|---|---|
| `frames_expected` | App 宣告 | 相机实际产出并进回调的帧数（唯一分母） |
| `frames_stored_on_device` | App 宣告 | 手机本地原子序完成的帧数 |
| `gaps_on_device` + `gap_ts` | App 宣告 | 采集期**确实没写进本地**的帧（位置按 sensor ts） |
| `frames_verified_on_pc` | **PC 自己数** | sha256 通过并落盘的帧数 |
| `upload_gaps` | **PC 自己算** | `stored − verified_on_pc`，即"手机有、PC 没拿到"的**个数差** |
| `missing_seqs` | **PC 自己算** | 宣告区间 `[seq_first, seq_last]` 内 PC 没校验到的**帧号** |
| `complete` | **PC 自己判** | `expected == verified_on_pc` **且** 两个缺口都为空 |

自洽式（判据要**逐条验**，不能只看 `complete`）：

```
frames_expected         == frames_stored_on_device + gaps_on_device
frames_stored_on_device == frames_verified_on_pc    + upload_gaps
```

⚠ **两个缺口必须分开命名**：`gaps_on_device`（采集期没写进本地）与
`upload_gaps`（写进去了但没传到）的**处置完全不同** ——
**前者只能重采，后者可以重传**。合并成一个数就等于把"该重采"和"该重传"混在一起，
现场必然选错。

⚠ **`missing_seqs` 的口径与第 23 轮不同**：seq 由 App 的 `nextSeq()` 逐帧分配，
**写失败的帧也占号** ⇒ 判据是"宣告区间内 PC 没校验到的号"，
而**不是**旧的"从 0 起的连续编号"。

⚠ **第三条独立校验**：`len(missing_seqs)` 应当等于 `gaps_on_device + upload_gaps`。
对不上时**必须显式报警**（`missing_seqs_note`），并且**不许**因此推翻 `self_consistent`
—— 这两条是**独立**的校验，不能用一个代替另一个（判据 `R5b`）。
没有宣告 seq 区间时判"点不出来"并**明说**，**不许硬算一串错的帧号**（判据 `R5c`）。

## 6. 采集路径登记（谁改了行为，谁就 +1）

按既定规则（`tools/capture_path_versions.json` / 教训 13、14、27），判量是**请求参数 / 会话配置 /
模板 / 格式 / 调度方式 / 丢弃规则 / 锁定字段集合**，不看版本号。

### 6.1 第 27 轮：**新增**一条路径 `live_stream_color`（`rev=1`），既有路径**一个不动**

`capture_mode=live` 的产出物与 `stream_deliver_yuv` **根本不是同一种东西**，逐项过：

| 维度 | 与 `stream_deliver_yuv` 相比 |
|---|---|
| **取图语义** | `acquireLatestImage`（要最新，主动丢陈帧）↔ 对方是 `acquireNextImage`（FIFO 逐帧配对） |
| **输出格式** | **彩色** JPEG（U/V 平面参与编码）↔ 对方是**灰度**原始 Y（只取 `planes[0]`） |
| **有损 / 无损** | **有损**（JPEG q70）+ 降采样（960×720）↔ 对方是**无损**原始 Y |
| **逐帧 sha256** | **无**（可丢，不校验）↔ 对方是**每帧校验后才算 `verified`** |
| **存储策略** | **零留存**（不落盘、不排空）↔ 对方是**先落本地 → 边采边传 → 停采后排空** |
| **丢弃规则** | **可丢**（尽力发 + 跳过陈帧）↔ 对方是**一帧不落** |

⇒ **四项（丢弃规则 / 输出格式 / 存储策略 / 取图语义）都变了** ⇒ 必须**新开一个路径 id**，
而**不是**借用 `stream_deliver_yuv` 的 rev。
判定依据（教训 27 的先例）：**产出物的含义变了，两个版本的数据不得互相替代**。

⚠ **同一个 APK 可能按模式走不同路径**（登记表的 `_semantics` 已追加这条）：
`m0probe-1.14.0` 在 `deliver` 下仍产出 `stream_deliver_yuv`(rev=3)，
在 `live` 下产出 `live_stream_color`(rev=1)。⇒ 判据 `G23/G26` 比对时必须 **(id, rev) 成对**比较。

三处必须一致（判据 `A9l` 交叉检查）：**App 常量** `LIVE_PATH_ID/LIVE_PATH_REV` ·
**`capabilities.lanes.live.path_id/path_rev`** · **登记表** `live_stream_color`。

### 6.2 第 24 轮：`stream_deliver_yuv` 的 `rev` 2 → 3（**仍然有效**）

逐项过：

| 维度 | 第 24 轮是否变化 | 说明 |
|---|---|---|
| HAL 请求参数（模板、锁定配方、曝光/ISO/对焦/变焦） | **否** | 一字未动 |
| 会话配置（`OutputConfiguration` / Surface 数） | **否** | **不新增 ImageReader** |
| 输出格式 / 尺寸 | **否** | 仍是 `YUV_420_888` / 1920×1440 |
| 调度方式（`setRepeatingRequest`） | **否** | |
| **丢弃规则** | **是** | **默认由"每 200 ms 抽 1 帧"改成"不抽帧 = 每一帧都留"** |
| 锁定字段集合 | **否** | |

⇒ **`stream_deliver_yuv` 的 `rev` 2 → 3**，理由：**默认配置下产出的数据量差约 6 倍**
（30.04 fps ⇒ 83.0 MB/s），交付内容的含义变了。先例是 1.10.3 把默认变焦 1.0× 改 0.6×
（同为"默认值改变 ⇒ rev +1"）。

两侧默认值同步改：

- App：`plan` 默认 `interval_ms` **200 → 0**；`currentIntervalNs()` 在 fps ≤ 0 时返回 **0**；
- PC：`DEFAULT_PROFILE.deliver_fps` **5 → 0**；`/api/v1/control/start` 不带 plan 时默认 `interval_ms=0`。

⇒ **1.13.0 起的交付数据与 1.10.3~1.12.0 的不得互相替代**（后者是 rev=2：0.6× 默认档 + 抽帧）。
登记表与 App 内的 `PATH_REV` 常量**必须同步为 3**（教训 13：登记表的声明必须为真 ——
1.10.3~1.10.6 就是因为 `PATH_REV` 漏改，导致数据被误判）。

⚠ **事实层的诚实注**：以上是**请求层**的推理。写盘负载会不会拖慢相机回调、降低实际出帧率，
**只能靠同一台设备做开/关的 A/B 实测**来回答（判据已就位：PC 端 `frames_seen` 对
`store.frames_expected`，开/关各跑一次即可看出）。

### 7.2 测试基础设施的六条硬要求

1. **必须挂线程持续排空被测进程的 stdout**。实测代价（第 23 轮）：测试没读管道 →
   服务端 `print` 的缓冲被填满 → **服务端阻塞在 `print` 上**，表现是"客户端某个请求 60 s 超时"，
   而真相是**测试自己**造的假故障。
2. **源码锚定判据必须从真源码切段**（`kslice()` 直接读 `DeliverySession.kt`）。
   本轮修的静默缺陷"修没修都不报错"，只有锚定源码才会响。
   ⚠ 同理：**夹具必须与被观测对象的真实产出格式一致** —— 第 20 轮的教训是
   夹具写 `"OFF"` 而真机是 `"OFF(0)"`，断言全绿而现场坏。
   ⚠ **切段必须真的切到**：`A9j` 要在 `startLiveLoop` 的**函数体内**找 `enqueue(`，
   若函数名改了导致切段落空、返回全文，**全文里必然有**（deliver 那条路就写着 `enqueue(`）
   ⇒ 判据会**恒真**。所以 `A9j2` 是必需的：把 `enqueue(` 塞进那段必须判否。
3. **"画面里的代码"必须真跑一遍才算验过**（第 28 轮新增，代价最直接）：
   面板那段 JS 对本项目而言**只是一个 Python 字符串**。本轮实测踩到
   `const isLive` 声明在它的**使用点之后**（块级作用域 TDZ）⇒
   `ReferenceError: Cannot access 'isLive' before initialization` ⇒
   **整个 `refresh()` 抛异常，会话表一行都不渲染**（页面其它部分照常）。
   ⚠ **三层检查全部放过它**：Python `ast.parse` 过、`node --check` 过
   （语法完全合法）、判据 `A9m` 也过（它只检"某个字符串在不在"）。
   ⇒ 做法：`A9m4` 用 node + 最小 DOM/fetch/WS 桩**真执行 `refresh()`** 并断言渲染结果；
   `A9m5` 把那个 TDZ **真实复现**出来（剪声明块到使用点之后）要求判据判否。
   **"字符串里存在" ≠ "跑得起来"** —— 凡是把代码当字符串存的地方（面板 JS、模板、生成的脚本），
   只有版本 1 是"真的跑"，其余都是"看起来跑"。

4. **"画面是不是彩色"不能只看通道数**（第 27 轮新增）：灰度 JPEG 被 `cv2` 解出来
   **也是 3 通道**（三通道值相等）⇒ `len(shape)==3` 恒真，判据等于没写。
   必须比**通道之间的极差**（`spread`）+ **左右半的色相方向**，
   并用**灰度夹具**做反例（`P13c` / `P13d`）。
   ⚠ 反例夹具要选**互补色相**（左红右蓝）：通道串了 / 只取了一个平面 / YUV 矩阵用错，
   这三种典型缺陷都会让左右半对不上 —— 用同色系的夹具则可能掩盖其中一种。
   ⚠ 顺带一条：`spread` **测不出 B/R 互换**（互换后三通道均值一样）⇒
   **左右半的方向检查才是真正的判据**（判据自身写反过一次，好在它是"响亮地失败"）。

5. **环境里的代理必须被显式绕开**（第 28 轮新增，第 6 次复发"验环境 vs 验行为"）：
   `urllib` 默认读 `HTTP_PROXY`（`urllib.request.getproxies()` 会返回本机代理）⇒
   现场机器上装了 Clash / v2ray / 公司代理时，对 `127.0.0.1:8765` 的请求会被塞进代理，
   拿到 `HTTP 502: upstream connect failed … (os error 10061)` —— **而服务好端端在跑**。
   ⚠ **排查方向会被彻底带偏**（看起来像"服务挂了/端口错了"）。
   本轮代价：`test_interop.py` 从 **42/42 掉到 38/40**，两条 FAIL（P1 / P9 走 hostlink）全指向代理。
   ⇒ ① `hostlink` 用**空代理表 opener**（`build_opener(ProxyHandler({}))`）；
   ② 测试里的 urllib 同理；③ `aiohttp` 显式写 `trust_env=False`
   （⚠ 它的默认**本来就是** `False` —— 写出来是把它变成**声明**，不是"修复"；
   不核实就写注释，就会在文档里留下一句假话）；
   ④ 判据 `P14a/P14b` 用**注入式**钉住（注入死代理 ⇒ 接入必须照常工作；
   同一注入下"按默认方式新建的 opener"必须失败，防注入没生效而真空通过）。
   ⚠ 反向用例**不能用 `urllib.request.urlopen`**：它内部的 opener 是**模块级缓存**的，
   早先调用已把当时的环境烘焙进去 ⇒ 注入不进去，反例会**静默变正例**。

6. **启动竞态要显式等就绪**：`test_interop.py` 的 P1 是第一条判据、上来就打 `capabilities`，
   而服务是刚 fork 的 ⇒ 机器负载高时撞"连接被拒"，看着像"接口坏了"。
   ⇒ 加一条**有上限的轮询就绪门**（服务真起不来就判一条明确 FAIL，不让后续每条跟着红）。
   （`test_server.py` 早有这道门；本轮把 `test_interop.py` 补齐 —— **两侧不一致本身就是隐患**。）
   ⚠ 顺带一条：`spread` **测不出 B/R 互换**（互换后三通道均值一样）⇒
   **左右半的方向检查才是真正的判据**（判据自身写反过一次，好在它是"响亮地失败"）。

## 9. 未验证 / 未做的部分（诚实边界）

1. **全帧率能否持续写盘**：无真机，**未实测**。判据已就位
   （`frames_expected == frames_verified_on_pc`），但数字要现场跑。
   **在拿到这个数之前，"每一帧都留"只能算"设计上成立"。**
2. **默认不抽帧对帧率的影响**：需开/关 A/B 实测（§6 的诚实注）。
3. **USB 链路带宽**：未实测。
4. **5 fps 采集路径**：M0 没扫过这一档，若采用"降帧率换取时长"需新路径 + 取证。
5. **MJPEG 的真实观感帧率**：取决于监视道档位与 WiFi；面板推送已验证 1 Hz 可用，
   **10 fps 实时档未上机**。
6. **排空的暂停/继续**：本轮只做"自动排空 + 可中止"，不做"断点续传的 UI 控制"
   （底层分片续传本来就是幂等的，重连即继续）。
7. **21 GB / 4.2 分钟**这个数是**按 83.0 MB/s 算出来的**，不是实测的写盘速率 ——
   实测速率多半低于它（写盘 + 元数据 + 编码预览同时在跑），所以"能录多久"要现场读
   `store_write_mbps` 反推。
8. ⚠ **第 25 轮查到、但**故意没有当场改**的两处"设备面开口"**（写在这里而不是默默放过）：
   `/api/v1/files/*`（分片上传）与 `/api/v1/linktest`（链路测速）**既不在 loopback 名单里，
   也不校验 token** —— 也就是说，同一局域网里的第三方可以往任意 `session_id` 里塞帧、
   或者用测速端点白耗带宽。它们**没有被声明为"需要 token"**，所以不构成"声明为假"，
   属于**设计上的开口**（历史原因：早期把 token 当"防误连"，只保护了控制道 `/ws`）。
   为什么不当场改：这两条在**设备面**上，改动要同步 App 的 URL 构造并**上真机验证**
   （本轮无真机）。**对"取证"这件事这是实质风险**：交付帧的**来源**可被第三方污染，
   而逐帧 sha256 只保证"传输没坏"，不保证"是这只手机写的"。
   ⇒ 下一轮建议：给这两条加 token（App 侧统一拼 `?token=`），并把它们写进
   `capabilities.auth.token_required`（届时 `A1f` 会自动开始要求它们 403）。
9. ⚠ **第 26 轮查到、但同样**故意保留**的一处开口**：`GET /api/v1/sessions` 与
   `GET /api/v1/sessions/{sid}/thumb/latest` **既不校验 token，也不限本机** ——
   它们不含凭据，但**含画面**（缩略图）与**含项目状态**（会话表）。
   为什么保留：这两个是**面板自己**用的接口，而"用手机浏览器打开 `http://<ip>:<port>/?token=…`
   看面板"是 README 里写明的**现场自检手段**（判断网络是否通、取景对不对）——
   把这两条收紧到 loopback，面板从手机打开就只剩"能打开、没画面"，等于废掉那个手段。
   ⇒ 现已**显式写进 `capabilities.console.note`**，并由判据 `A8` 按声明核对
   （声明的是 `auth: "none"`，哪天有人给它加了 token，`A8d` 会立刻要求"不带 token 必须 403"
   —— 也就是**逼他同步声明**，而不是静默漂移）。
   ⚠ 由此带来的边界：**同一局域网里读得到画面**。现场若不能接受，就用 `--host 127.0.0.1`
   （手机就连不上设备面了，只在本机调试用）。
10. ⚠ **本轮"控制台功能覆盖"的判据边界**：`A8` 证的是"**声明**里的每条都能兑现"
    + "**面板源码里出现的路径**都被声明覆盖"。它**不**等于"人对面板逐个点过一遍"——
   如果某个功能既没出现在面板源码的字符串里、也没进声明，两条判据都不会响
   （现实中很难发生：面板要发请求就得写路径；但**不是数学上的完备**，如实记下）。
11. ⚠ **第 27 轮：`POST /api/v1/live/frame` 不校验 token**（**新开的一条已知开口**）：
    它与 `/api/v1/files/*` 同一条口径 —— 在**设备面**上（手机要连进来），
    **不改**的理由也一样（改动要同步 App 的 URL 构造并**上真机验证**，本轮无真机）。
    它**不落盘、也不返回凭据**（比 `files/*` 温和），但**仍允许同网段往任意 live 会话塞画面**
    ⇒ 对"取证"是实质风险（面板上看到的彩色画面**不保证来自这只手机**）。
    ⇒ 已**显式写进** `capabilities.auth.no_token`（连同其余 8 条一起点名）+ `no_token_note`
