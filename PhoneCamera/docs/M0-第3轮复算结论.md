> 数据：`m0_out/m0_capability.json`、`m0_locked_capture.json`、`m0_rate_sweep.json`
> （Xiaomi 24129PN74C / Android 16 API 36 / 后摄 id=0 LEVEL_3 / 150 帧连拍 + 8 条帧率档位）
>
> 复算命令：
> ```
> python tools\m0_evaluate.py m0_out
> ```

## 1. 对两个核心要求的判定

| 核心要求 | 判定 | 依据 |
|---|---|---|
| **内参不变** | **单会话内：已证**<br>**跨会话：未证（判据从未被满足）** | 已证部分是硬的（见 §2）。跨会话唯一的地基判据 G21 从未跑过 —— 而这不是"缺一项测试"，是"核心要求此前没有任何判据覆盖"（见 §3.3） |
| **时间戳准确** | **帧间相对时间：已证**<br>**绝对时刻：不在范围内（D17）** | 单调 ✓、抖动 3.06 ppm ✓、与回读帧时长自洽到 0.124 ppm ✓。绝对时刻需要与 PC/机器人时钟对齐，设计里已显式排除 |

**总判定：`INCOMPLETE`（退出码 2）。** 不是"可用但有瑕疵"，是"地基判据没跑，不得据此判定机型合格"。

## 2. 从原始 JSON 重算出的证据（不依赖报告里的汇总结论）

### 2.1 内参不变 —— 单会话内是干净的

| 项 | 实测 | 含义 |
|---|---|---|
| `active_physical_id` | **恒为 2**（145 个有效帧样本，唯一值） | 未换镜。整段数据共用同一套焦距/主点/畸变 |
| 13 项锁定字段 `distinct_count` | **全部 = 1** | 对焦距离 `1.001001` diopt、`zoom_ratio 1.0`、OIS/EIS/AE/AWB/EDGE/NR/畸变矫正 全 OFF、曝光 10 000 000 ns、ISO 200、`pixel_mode 0`、帧时长、skew |
| `crop_region` | `0,0,4096,3072` = 全活动阵列 | 无数字裁切，zoom = 1.0 名副其实 |
| `lens_state` | 仅第 0 帧 `MOVING`，其余全部 `STATIONARY` | 起始机械收敛瞬态；按协议丢弃前 5 帧已覆盖 |
| 对焦回读 vs 请求 | 1.001001 vs 1.0 diopt（+0.1%） | 量化为 1 mm 级（对焦 0.999 m），远小于景深（±9 cm） |

### 2.2 时间戳准确 —— 三个数

| 项 | 实测 | 判读 |
|---|---|---|
| 单调性 | 149 个间隔全部严格递增 | ✓ |
| 帧间隔取值 | 只有 3 个：`33 287 916`(×30) / `33 287 917`(×60) / `33 288 125`(×59) ns，跨度 **209 ns** | 量化 + ns 级抖动的叠加，幅度 6.3 ppm |
| 抖动 | std = **101.9 ns = 3.06 ppm** | 远优于任何运动建模需求（1 px 在 1 m 处约 0.78 mm，对应 ~0.8 ms 的运动时间） |
| 与回读帧时长的一致度 | 实测均值 33 287 999.13 ns vs 回读 33 287 995 ns → **0.124 ppm** | **回读的 `SENSOR_FRAME_DURATION` 可当名义节奏用** |
| 帧内读出 | `skew = 6 909 696 ns`（恒定），占帧周期 **20.8%**，≈ 2.25 µs/行 | 卷帘补偿的必需量已逐帧可得 |

> 语义按 AOSP 文档核实：`SENSOR_TIMESTAMP` = **活动阵列首行**曝光起点；
> `REALTIME` = 与 `SystemClock.elapsedRealtimeNanos()` 同基（不是 `CLOCK_MONOTONIC`）；
> `SENSOR_ROLLING_SHUTTER_SKEW` = 首行到「末行之后一行」= **帧读出时间**，
> 且按整阵列报告 —— 输出只覆盖 N 行时须乘 `N/H`。

## 3. 三处纠正

### 3.1 G15 的解读被推翻了：帧时长是「被量化」，不是「未被采纳」

第 3 轮的 4 档扫描给出了决定性证据：

| 请求 | 实测 | 偏差 |
|---|---|---|
| 12 fps | 12.01 fps（83.232 ms） | **+0.12%** |
| 15 fps | 15.02 fps（66.576 ms） | **+0.14%** |
| 24 fps | 24.03 fps（41.616 ms） | **+0.12%** |
| 60 fps | **30.04 fps**（33.288 ms） | −49.9% |

三个慢速档位各自跟随请求、偏差量级完全一致 —— **只有"请求被采纳后按同一个量化网格重新表达"
才会呈现这种形态**（基准帧长 33.288 ms 的四分之一档 ≈ 8.32 ms 一档）。

早期"HAL 从未采纳请求值"的结论只基于两个测试点，而这两个点都紧邻默认值
（`[12,12]` 与 33333333 ns 都算出了 33.29 ms）—— **单点/近默认值比对同样不可证伪**。

后果（对后续设计有实际影响）：
- **"降帧率省带宽"这条路是通的**，不必只依赖 PC 端按时间戳抽帧；
- profile 里记回读值，但可以把它当**名义值**用（自洽到 0.124 ppm）；
- 真正的问题从"控制失效"变成"**上限**"：本机型 1920×1080 上最快 **30.04 fps**。

### 3.2 G18 的判据是恒过判据，已改

旧判据：`多个档位的实测帧间隔互不相同` → 用的是 **ns 级整数去重**。
于是它把同档位内部 **26 ns**（相对 8×10⁻⁸）的测量噪声也当成不同档位，
把 4 档报成了 **"7 种实测帧间隔"**。

两条后果：
1. 只要有一点点噪声，"互不相同"永远成立 → **这条判据永远不会 FAIL**；
2. 它看不见"档位不可达"：请求 60 fps 得 30.04 fps，与其它三档确实都不同 → 判成 PASS，
   而真实含义是该尺寸下**速率上限 30.04 fps**。

已改为：**先按 1% 容差聚类再数簇数**，并要求**每档达标**（实测 vs 请求偏差 ≤ 5%），
各档的 `请求→实测` 对照直接打进结论。现在的结论是
`WARN 帧率可控，但有档位不可达`，理由写得明明白白。

### 3.3 G21：项目核心要求此前没有任何判据覆盖

App 的 ③ 会写出 `m0_locked_capture_r1..r3.json`，但**评估脚本压根不读它们**。
于是"**没跑 ③**"和"**③ 全过**"在报告上完全一样，都是 WARN 或 PASS。

这就是"核心要求没有判据覆盖"的教科书症状：文档里写着"一次标定能否覆盖多次采集是方案的地基"，
但没有任何判据消费它的证据 —— 报告就会永远给它 PASS。

已新增 **G21（跨会话内参重复性）**，从原始轮次报告重算：焦点回读相对极差、
各轮生效物理镜头、各轮输出尺寸、各轮回读帧时长、预热区外 MOVING。
**缺证据 → INCOMPLETE**，这就是本轮总判定降级的原因，也是它应该降级的原因。

## 4. 未测项 → 下一步（都很便宜）

| # | 事项 | 为什么必须做 | 代价 |
|---|---|---|---|
| **1** | **跑 ③ 跨会话重复性**（手机上点③，再 `python tools\m0_evaluate.py --pull`） | 这是"一次标定覆盖多次采集"的唯一证据；不跑，总判定永远是 INCOMPLETE | App 里点一下，约 20 s |
| **2** | **长时热漂移测试**（≥ 5 min 连续连拍，记录回读对焦值/帧时长/skew 随时间变化） | 设计文档自己估计温度可致 fx 漂 0.1%–1%；而 G13 用电池温度在 4.8 s 窗口内 delta = 0，**没有任何信息量**。这是"内参不变"目前唯一完全没仪器的漂移源 —— 只能用**图像本身当温度计**（拍固定靶，看标定残差/特征位置随时间漂移） | 一段脚本 + 5 min |
| **3** | **输出尺寸定档**（4:3 全幅 4096×3072 vs 次高档）并排除"纵向压扁" | 现在 1920×1080 把 `fx` 从 2736 px 砍到 **1282.5 px**，亚像素定位精度大致与 fx 成正比 —— 这是**主动放弃一半精度**，不属于"其余已符合要求"。另外 `scale_x = 0.46875 ≠ scale_y = 0.35156`，若非等比缩放则 `fy ≈ 962 ≠ fx`，标定模型的"方形像元"假设就错了 | 改一行尺寸再跑①②，一帧图即可判 fx/fy |

附带（不阻塞 M1）：若后续需要 > 30 fps，须另试更小输出尺寸或 constrained high-speed 会话
（能力位含 `CONSTRAINED_HIGH_SPEED_VIDEO`），M0 未覆盖该路径。

## 5. 一句话总结

**单会话内的内参锁定与时间戳质量都已经很干净**（换镜、参数漂移、时间戳抖动/自洽这三项证据都是硬的）；
真正卡住的是两件事：**跨会话重复性从没被测过、也没有判据**（已补 G21，总判定因此为 INCOMPLETE），
以及**输出尺寸还停在 1920×1080、白扔一半横向精度**（这是精度问题，不是"其余"问题）。
