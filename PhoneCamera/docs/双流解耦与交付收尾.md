# 双流解耦与交付收尾（第 21 轮）

本轮处理现场反馈的两件事：

1. **"电脑端缩略图帧率小于手机端：接收计数一下子 +3，画面只更新 1 张"** —— 现象是 1:3。
2. **"确保实时联通结束后手机能按双流方案回传全部信息"** —— 这是要求，不是故障报告，
   但它当场暴露了一个**真缺陷**（见 §3）。

---

## 1. 缩略图 1:3：不是丢数据，是观测口径

先把两件事分开问："数据丢了吗？"和"我看到的数字能解释吗？"

**数据一张没丢**，证据链（都能自己复核）：

| 证据 | 事实 |
|---|---|
| `manifest.thumbs` | 逐张累加，等于 `thumbs/thumb_*.jpg` 的文件数 |
| 落盘 | 每张缩略图都写了 `thumbs/thumb_<seq>.jpg` **和**旁挂 `.json`（含 `sensor_timestamp_ns`） |
| 面板计数 | 显示的正是这个落盘数，**它一直在涨，且与手机端的 1 Hz 对得上** |

丢的是**显示**：

```
手机端：THUMB_INTERVAL_MS = 1000  ⇒ 1 Hz 推
面板旧实现：setInterval(refresh, 3000) + thumb/latest ⇒ 3 s 拉一张
                ⇒ 3 秒窗口里"收到 3 张、只画 1 张" —— 比例正好 1:3
```

**这是采样口径，不是丢帧。** 但面板把"收到几张"和"画了几张"写在同一个数字里，
让人无法判断到底是哪种 —— 这本身就是缺陷（本项目的老毛病：**判据/记账的表达方式
比事实更强**）。所以修法不是"把轮询调快"，而是让它**如实**：

| 改法 | 为什么 |
|---|---|
| 面板加 **WS 推送通道** `/ws/panel`，收到 thumb 即内联渲染 | 帧率天然与 App 一致，1:3 消失 |
| 前端**分列** `收到 / 渲染 / 合并` | 差额必须被解释，不能无声出现 |
| 推送断了**退回轮询**并在通道状态里写明 | 降级要看得见（"轮询模式（帧率会被节流）"） |
| App 侧拆分 `thumbs_enqueued / thumbs_sent / thumbs_send_failed / thumbs_dropped` | 旧代码只有一个 `thumbsSent`，且它在**入队**时 `++` ⇒ "手机说发了 30、电脑收到 28"**永远对不上账** |

面板上现在长这样：

```
通道 推送（收到即渲染） ｜ 收到 30 张 ｜ 渲染 28 张 ｜ 合并 2 张 ｜ 渲染帧率 1.0/s（App 侧 1.0/s）
收到 30 张 / 渲染 28 张 / 合并 2 张 —— 差额不是丢帧：每一张都已落盘到 thumbs/
（会话目录里有对应 jpg+json），监视道取"最新帧"语义，丢的只是显示；交付道走 HTTP，与这里完全无关。
```

> **"合并"是什么**：上一张的 JPEG 解码还没完成就被新图顶替。监视道取"最新帧"语义
> （与 App 端 `thumbQueue` 2 格丢最旧是同一条原则），所以这是**设计**，不是缺陷 ——
> 但它必须被计数，否则"收到 30 只看见 28"永远只能靠猜。

## 2. 面板推送必须**非阻塞**（本轮踩到的新坑）

推送是在 **App 的控制道消息循环里**触发的（收到 `thumb` 就转发给面板）。
第一版实现给发送加了 1 秒超时：

```python
await asyncio.wait_for(ws.send_str(msg), timeout=1.0)   # ← 错
```

**测试当场抓住**：面板假死时（连上但从不读），超时产生的取消**顺着 `await` 一层层冒泡**，
把 **App 的控制道连接整个掀掉** —— 现象是手机端莫名显示"连接已断开"，
而服务端什么错都不打。测试报的是 `ConnectionError: Connection lost`。

修法是换机制，不是加 `try`：

```python
self.panel_ws: dict = {}          # ws -> asyncio.Queue(maxsize=2)

def broadcast_panel(self, payload) -> int:      # 同步、非阻塞
    for _ws, q in list(self.panel_ws.items()):
        try: q.put_nowait(msg)
        except asyncio.QueueFull:               # 丢最旧、留最新
            q.get_nowait(); q.put_nowait(msg)
```

每个面板连接一个 **2 格队列 + 独立发送任务**（`_pump`），投递方只做 `put_nowait`。
慢面板只会丢自己的帧，**碰不到控制道**。

> 原则与 App 端完全一致：**监视道可丢，控制道不可堵**。
> 顺带一条更通用的教训：**在别人的消息循环里 `await`，等于把那条循环的生死
> 交给被 await 的一方**。要么别 await，要么把 await 挪到自己的任务里。

## 3. 交付道必须独立于控制道（用户第 2 条要求的真实缺陷）

用户要求："实时联通结束后，手机能按双流方案回传全部信息。"

查代码发现 **`Uploader.run()` 的循环条件是 `while (connected)`**：

```
WS 一断（PC 重启 / WiFi 抖动 / 用户关掉面板 / 对端关闭）
  ⇒ connected = false ⇒ 上传线程**立刻退出**
  ⇒ 队列里已经抽好的帧**停在手机上不动了**
  ⇒ 而 HTTP 明明是通的
```

也就是说：**"实时联通结束"等于"交付结束"，剩下的数据永远留在手机里**。
这正是用户要求里要防的事，只是还没人踩到。

### 修法：把"交付道存活"从"控制道在线"里拆出来

| 概念 | 旧实现 | 现实现 |
|---|---|---|
| 上传线程循环条件 | `while (connected)` | `while (deliveryAlive)` |
| `connected=false` 时 | 线程退出、**不再上传** | 只标记"控制道离线"，**交付道照跑** |
| 用户点「断开」 | 线程退出 | 队列非空 ⇒ 进**收尾模式**（不采了，传完才收工）；队列空 ⇒ 立刻收工 |
| 线程重建判据 | `uploader == null` | **`uploader == null \|\| !uploader.isAlive`** |

最后一行是上一轮踩过的坑换了形状又回来：收尾模式下线程会**正常退出**而引用还在，
`uploader == null` 不成立 ⇒ 重连后**永远不重建新线程**，上传从此静默失效。
判据必须是"线程还活着吗"，不是"引用还在吗"。

### 收尾的**唯一**一手证据：`delivery_done`

`stop_ack` 只回答"停在哪"（抽了多少帧、队列还剩几帧），**回答不了"收全了没有"**。
而 PC 侧没有任何可信办法从"不再有新帧"推断出"传完了"：

- 链路卡顿 ⇒ 帧暂时没来；
- App 被系统冻结 ⇒ 帧暂时没来；
- 旧会话串台 ⇒ 帧还在来。

拿它当"传完了"就是**让判据强于事实**。所以收尾必须由**队列的持有者**显式宣告：

```json
{"type":"delivery_done","session_id":"…","frames":57,"sampled":57,
 "queue_len":0,"drain_seconds":38}
```

App 侧**三条同时成立**才宣告（少任何一条都是过度结论）：

1. 采集已停（`!running`）—— 否则"队列空"只是暂时的；
2. 本地队列已空 —— 没有待传的文件；
3. 本轮**至少成功交付过 1 帧** —— 否则空跑也会"宣告传完了"（真空通过）。

`sampled`（抽帧数）与 `frames`（已回传数）**不等时当场喊出来**：那意味着有帧卡在写盘
或校验失败，是真异常。

## 4. `delivery_complete`：三态，不是布尔

`stop_ack` 是"停的那一刻"的快照，`delivery_done` 是"全传完了"。两者都有用，但**含义不同**，
所以 PC 的断言是**三态**，并且每条都能说出证据是哪几个字段：

| 值 | 依据 | 面板显示 |
|---|---|---|
| `true` | 收到 `delivery_done`；或 `stop_ack` 说"抽了 N 帧、队列 0"且 PC 已 `verified ≥ N` 帧，且**停后无迟到帧** | `交付收尾 ✓` |
| `false` | 有 `stop_ack` 但队列还有余量；或停后仍有迟到帧到达 | `交付未收完` |
| `null` | 既无 `stop_ack` 也无 `delivery_done`（例如控制道从未连上/已断开）⇒ **PC 侧不可区分** | `交付收尾 判不了` |

`null` 必须显式画成"判不了"。空着会被读成"没问题"—— 这个项目里"判不了 ≠ 通过"
是要写在纸上的铁律（第 20 轮门控三态就是这么来的）。

**可复核性**：宣告是一手证据，结论照采信；但注记里同时摆出两侧的计数，
不一致就标出来（实测冒烟时正好触发过一次："PC 侧 verified 0 帧 ≠ 宣告 7 帧"）：

```
App 宣告交付收尾：7 帧全部 verified，队列已清空（⚠ PC 侧 verified 0 帧 ≠ 宣告 7 帧 ——
该会话可能另有来源的帧，或宣告早于最后一帧落盘；不影响「已收全」这个结论，但摆出来供复核）
```

## 5. 停采集后收到的帧 = "迟到帧"，不是串台

`h_init` 不做状态检查（**这是对的**：它要接受收尾期到达的帧）。但必须**计数**：

| 字段 | 含义 |
|---|---|
| `stopped_at` | 采集停止的时刻（以 `stop_ack` 为准 —— **下发的 `stop` 是指令，回执才是事实**） |
| `late_frames_after_stop` | 停采集后仍到达的帧数 |

不计数的话，"明明停了怎么还在收"就只能靠猜 —— 而它有两种完全不同的解释
（收尾的正常产物 / 旧会话串台），猜错的代价是把正常数据当异常扔掉，或者反过来。

`stopped_at` 不取"PC 下发 stop 的时刻"，理由与门控一致：
**下发的配置是意图，回读才是事实**。

## 7. 现场怎么用

**装 v1.11.0**（`android/m0probe/app/build/outputs/apk/debug/app-debug.apk`）后：

1. 面板顶部监视道区块：通道显示 **推送（收到即渲染）**，`收到 / 渲染 / 合并` 三个数
   应当 **同步增长**（渲染 ≈ 收到，差值只有解码中的 1–2 张）。**不再有 1:3**。
2. 点「▶ 开始采集」→ 采一会儿 → 点「停止」：
   - App 状态栏应出现 `收尾=回传中` → 最后变成 **`收尾=已传完✓`**；
   - 面板「断言」列出现 **`交付收尾 ✓`** 与"App 宣告交付收尾：N 帧…"；
   - 若队列还有帧，会出现"**停采集后仍到 N 帧（交付道独立于采集，属预期）**"。
3. **要验证"断开也能传完"**：采集、让队列积一点，然后在手机上点「断开」——
   日志应出现"**已断开控制道；队列还剩 N 帧 ⇒ 交付道继续收尾**"，
   PC 端应继续收到帧直到队列清空。（HTTP 通即可，WS 是否连着不影响。）

面板上"**交付收尾 判不了**"出现时不要当成通过：它表示 PC 侧没有收到任何收尾证据
（典型：控制道断过），此时**只有 App 界面的 `收尾=` 字段能回答"传完了没有"**。
