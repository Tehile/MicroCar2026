# 扫码配对（手机 App 扫 PC 上的二维码连接）

> 本轮（第 22 轮）交付：**手机不再需要手输 IP + token**。PC 端（终端 + 面板）显示一个配对二维码，
> 手机 App 点「扫码配对」扫它，自动填好地址与 token 并连接。
> App 版本 `m0probe-1.11.1`；PC 端需同版本（新增 `/api/v1/pair`）。

## 1. 现场怎么用

1. PC 上照旧跑 `python pc/server.py`（终端会打印配对二维码；**面板顶部也显示同一个码**）。
2. 手机 App → 「扫码配对」→ 对准屏幕上的码。听到提示音即成功。
3. 成功后 App 会自动填入 `ip:port` 与 `token`，**并自动发起连接**（日志里会打印解析结果）。
   - 若扫到的东西**不是配对码**（微信号、文章链接…），App 会明确说"这不是配对码（原因）"，
     不会把无关内容填进地址框。
   - 长按「扫码配对」按钮 = **解析器真机自检**（跑 23 条正反用例，结果进日志）。

三条路并存，任选：**扫码** / **粘贴整行 URL**（终端打印的那行）/ **手输 `ip:port` + token**。
三条路走的是**同一个解析器**（`PairCode.parse`），所以不会出现"扫到的能连、粘同一串连不上"。

## 2. 契约：一种规范写法 + 两种兼容写法 + 明确拒绝

```
规范（PC 生成、App 优先认）：
    m0probe://pair?h=<host>&p=<port>&t=<token>

兼容（历史写法，终端仍打印，认但会提示）：
    http://<host>:<port>/?token=<token>

兼容（手工只填地址）：
    <host>[:<port>]        # 含 [IPv6]:port
```

**为什么要拒绝而不是宽容**：宽容的解析器会把 `https://mp.weixin.qq.com/s/xxx` 当成
"主机 = mp.weixin.qq.com"，然后现场表现为"连接失败"—— 而用户看到的是"扫码没反应"，
排查方向从一开始就错了。所以规则是：

| 扫到的内容 | 行为 |
|---|---|
| `m0probe://pair?...` | 接受（规范） |
| `http(s)://<私网地址或主机名>[:port]/[?token=]` | 接受；无 token 时提示手输 |
| `http(s)://<公网域名>/<有路径>` 且无 token | **拒绝**："这是网页链接，不是配对码" |
| 其它 `xxx://`（`weixin://`、`ftp://`…） | **拒绝**："看起来是一个 xxx:// 链接" |
| `WIFI:` / 名片 / 含空格的一句话 / 非 ASCII | **拒绝**："不像地址（可能扫到了文章/名片码）" |
| 端口越界、主机字符非法、`m0probe://别的动作` | **拒绝**，且说明是哪一项不对 |

判据在 `PairCode.SELFTEST`（23 条：**13 条正例 + 10 条反例**）。反例是必须的 ——
只有正例的表在解析器退化成"什么都接受"时依然全绿（本项目的"真空通过"）。

## 3. 实现

### PC 端（`pc/server.py`）

| 位置 | 内容 |
|---|---|
| `pair_uri(host, port, token)` | 唯一的配对码生成器（终端、面板、接口都用它；**不允许手拼字符串**） |
| `qr_svg(text)` | 把码渲染成**内联 SVG**（零依赖：不需要 Pillow，浏览器里是矢量）。纠错等级 **Q(25%)**，`border=2`，默认 `scale=6` ⇒ 41×41 模块、246×246 px |
| `GET /api/v1/pair?token=…` | `{pair_uri, host, port, token, url, qr_svg, note}`。**唯一要求 token 的读接口**（它返回的正是凭据；`/api/v1/sessions` 那类不返回凭据，维持现状） |
| 终端启动输出 | ①扫码 ②粘贴 ③手输 三种方式并列 + 二维码 + 配对码原文（设备不支持扫码时可手抄） |
| 面板「扫码配对」区块 | 显示二维码 + 配对码 + 地址/token + 手输 URL；`loadPair()` **只拉一次**（配对信息在进程生命周期内不变） |

地址来源钉在 `hub.lan_ip`（启动时由 `lan_addresses()` 的首选填充）⇒ 终端与面板**不会各算一遍**，
现场实测取到的是真实 WLAN（`192.168.1.7`）而不是 VMware 虚拟网卡（`192.168.18.1`）。

### App 端（`android/m0probe`）

| 文件 | 内容 |
|---|---|
| `PairCode.kt` | **唯一解析器**（手输/粘贴/扫码共用）+ 23 条自检向量 + `runSelfTest()`。纯 Kotlin、**不依赖任何 Android 类** |
| `QrScanActivity.kt` | Camera2 后摄预览 + `ImageReader(YUV_420_888)` + zxing 实时解码，扫到即回传原文 |
| `MainActivity.kt` | 「扫码配对」按钮（采集运行中会拦下并说明原因；长按 = 解析自检）；`onActivityResult` 里解析 → 回填 → 自动连接 |
| `DeliverySession.connect()` | 改用 `PairCode.parse`（原 `parseTarget` 已删除），解析失败时把**原因**说出来 |
| `AndroidManifest.xml` | `QrScanActivity` 声明为 `exported=false`（返回值会直接进地址框 ⇒ 不能开放给别的应用） |

扫码界面的三个工程细节（都在代码注释里）：

1. **Y 平面 `rowStride` 可能大于图像宽度** ⇒ 必须逐行搬；直接整体读入会让每行末尾混进 padding，
   图像斜切 ⇒ **永远解不出**（`pixelStride` 也做了防御）。
2. 预览按 `sensorOrientation` 旋转 + center-crop。不做的话画面横躺：码照样能解，
   但"看起来坏了"本身就是可用性问题。
3. 这里用 `acquireLatestImage()` **故意丢旧帧**（与交付道的 `acquireNextImage()` 相反 ——
   那处丢帧会破坏抽帧栅格）。两种用法都对，前提是知道自己在保什么。

另外界面会周期性显示"已看 N 帧 / 解码 M 次" —— 扫不出来时这两个数能立刻把原因分成
"相机没给帧" / "限速或解码线程卡住" / "确实解不出（没对准、反光、码太小）"三种。

## 4. 依赖：zxing core（唯一例外，随仓库入库）

| | |
|---|---|
| 文件 | `android/m0probe/app/libs/core-3.5.3.jar`（**入库**，`git check-ignore` 确认不被忽略） |
| 大小 / sha256 | 607 650 B / `8d8064c1636fdaef7189dd9055c7d59950a8940a12f2293956446ec3c109fd82` |
| 引入方式 | `implementation(files("libs/core-3.5.3.jar"))` ⇒ **仍然 `--offline` 可构建**，不新增仓库依赖 |
| 组成 | 纯 Java，**不含** awt / `client.j2se`（已核对 jar 内容）⇒ Android 可用 |

为什么用库而不是自己写 QR 解码：自研要覆盖定位图形检测、透视采样、格式/版本信息、掩码、
RS 纠错 —— 任何一处出错都表现为"扫不出来"，现场无法自查。**这一条改了工程原有的"零第三方依赖"，
所以单独列出来**：它是全工程唯一的二进制依赖，且带了哈希便于复现。

## 5. 判据

### 5.1 `pc/test_server.py` 第 26 组（14 条，107/107 全绿）

| 编号 | 断言 |
|---|---|
| 26a / 26a2 | `/api/v1/pair` 无 token / 错 token ⇒ **403**（它返回凭据） |
| 26b | 返回的 `pair_uri` **逐字符等于** `pair_uri(host, port, token)`（接口里不许再拼一遍） |
| 26c | 写法严格匹配 `m0probe://pair?h=…&p=…&t=…`（没有第二种写法） |
| 26d | 二维码**逐格位置**与 qrcode 库矩阵一致（不是"非空就算过"，也不只是"数量对") |
| 26d2 | 同时给出可手输的 URL 与说明（码扫不出来时还有出路） |
| 26d3 | **反例注入**：挪走一个模块（数量不变）必须判否 |
| 26e / 26f | `host`/`port` 可覆盖；端口非法 ⇒ 400（不静默回默认值） |
| 26g–26j | **契约锚定**：从 `PairCode.kt` 源码读常量、样本串、反例数量，反算 PC 生成器 |
| 26k / 26l | 面板真的显示二维码；终端与面板用同一个生成器；码上写明"等同凭据" |

### 5.2 `pc/verify_pair_contract.py`：**跨语言真跑**（本轮最有价值的一条）

```
[1/3] PC 生成配对码（服务端生成器）
[2/3] zxing（App 里那个 jar）解码：OK
[3/3] App 的 PairCode.parse()（真 Kotlin 代码）：ok=true host/port/token 全对 | 内建自检 23/23
[3b]  旧写法（整行 URL）：解析正确（source=url + 提示）
[3c]  误扫（公众号链接）：REJECTED-AS-EXPECTED 原因=这是网页链接，不是配对码（…）
```

关键点：**它跑的是 App 的那份 Kotlin class**（`build/tmp/kotlin-classes/debug`）与**同一个 zxing jar**，
不是镜像实现。之所以能这么做，是因为 `PairCode` 刻意不依赖 Android 类 ——
**"纯逻辑与平台解耦"本身就是可验证性的红利**。

### 5.3 App 内建自检（真机）

长按「扫码配对」→ 跑 23 条向量 → 日志打印 `配对码解析自检：23 条用例，失败 0 条`。
它的价值在于**现场的机器自己会证明解析器是好的**，不必回来改代码重编一轮。

## 7. 现场故障对照表

| 现象 | 看什么 | 大概率原因 |
|---|---|---|
| 点「扫码配对」没反应 | 日志有没有"正在采集，后摄被占用" | 采集在跑 ⇒ 先「停流」 |
| 界面一直"正在打开相机…" | 是否被别的 App 占相机 | 关掉相机类 App 重试；或权限被拒（日志有说明） |
| 画面出来了但"解码 0 次" | 状态栏的"已看 N 帧 / 解码 M 次" | 帧在给但解码线程没跑（限速/异常） |
| "解码 60 次仍为 0" | 码是否完整入框、屏亮度是否过低 | 没对准 / 反光 / 码太小：靠近一点、避开反光 |
| 扫到了却说"不是配对码" | 日志里的**扫码内容原文** | 扫到了别的二维码（正确行为，换一个码扫） |
| 提示"码里没带 token" | 配对码文本是否完整 | 扫到的可能是旧 URL 或不完整的码 ⇒ 用面板上的码 |
| 长按自检有失败项 | 日志里的失败明细 | 解析器真的坏了 ⇒ 把明细发回来（这条会指到具体用例） |

## 8. 本轮新踩到的四个坑（已写进技能）

1. **"数量对"不等于"位置对"**：二维码判据第一版只比黑模块数量 ⇒ 把两个模块互换位置照样通过，
   而现场一样扫不出来。改成**从 path 重建模块坐标、逐格比对**，并加了"挪走一格必须判否"的反向注入。
   → **判据要能失败，才算判据。**
2. **"×8"有两种写法**：`"a b c" * 8`（横向平铺 8 份图案）≠ 逐格重复（真正的放大）。
   验证脚本第一版就是这么写错的，被 **cv2 与 zxing 两个独立解码器同时抓住** ⇒ 没有一个解码器会说谎，
   但一个解码器可能是"我自己的错实现"。
3. **CLI 参数下标 off-by-one**：`args.length > 2 && args[2]` 让 `--expect-fail` 永远被忽略 ⇒
   **反向用例静默变成正例**，测试失败在一个与缺陷无关的地方（现象是"期望被拒却报 PARSE-FAIL"）。
4. **编码不能进判据**：命令行传中文参数、JVM 默认按 GBK 写管道 —— 都会让判据因为
   "与被测对象无关的原因"失败。做法：参数只用 ASCII，中文输出统一走 UTF-8 `PrintStream`。
