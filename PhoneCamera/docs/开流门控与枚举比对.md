# 开流门控与枚举比对（第 20 轮）

> 起因：现场点「▶ 开始采集」后**画面只刷新一次就再也不动**，手机与电脑端同时停住。
> 现场日志：
> ```
> [ws] start_ack ok=True session=2026-09-25_2108_d86c
> [gate] session=… FAIL hard_fail=['ois','eis']
>       {"ois":{"want":"OFF","got":"OFF(0)","ok":false}, "eis":{"want":"OFF","got":"OFF(0)","ok":false}, …}
> [ws] stop_ack session=… 队列剩 1
> ```
> 门控判"硬项不一致" ⇒ 按设计**自动停流** ⇒ 现象就是"刷一下就不动了"。

## 1. 结论先说

**这是判据缺陷，不是设备缺陷。** `want="OFF"` 与 `got="OFF(0)"` 语义完全相同：

| 来源 | 写法 | 谁写的 |
|---|---|---|
| profile（PC 下发） | `"OFF"` | `pc/server.py` 的 `DEFAULT_PROFILE` / `--profile` |
| 回读（App 上报） | `"OFF(0)"` | `DeliverySession.name()` → `"$名字($码)"` |

门控当时用 `str(got).upper() == str(want).upper()` 直接比字符串 ⇒ `"OFF(0)" != "OFF"`
⇒ 判硬项不一致 ⇒ 停流。**判据把"写法差异"当成了"事实差异"。**

这类缺陷在本项目的判据体系里出现过多次，性质完全一样（G18 吞掉失败档、G24 假阳性、
G26 把不同路径判成同一路径）：**判据的表达方式比被观测的事实更强**。

### 1.1 用真机落盘数据复算（不采信日志结论）

从 `pc/data/sessions/2026-09-25_2108_d86c/frames/frame_000567.json`（App 原始上报的 meta）逐项核对：

```
ois_mode = 'OFF(0)'      eis_mode = 'OFF(0)'      af_mode = 'OFF(0)'
edge_mode= 'OFF(0)'      noise_reduction_mode = 'OFF(0)'
zoom_ratio = 0.6000000238418579     requested = {'zoom_ratio': 0.6, 'zoom_source': 'app_ui', …}
active_physical_id = '3'            capture_path_rev = 1
```

拿同一批原始 JSON 重跑新门控：

```
门控 status = pass   hard_fail = []   unevaluable = []
注记 = ["ois: 请求 'OFF' ≡ 回读 'OFF(0)'（写法不同，语义相同）",
        "eis: 请求 'OFF' ≡ 回读 'OFF(0)'（写法不同，语义相同）",
        "zoom_ratio 未指定（profile=0 ⇒ 由 App 界面档位决定，门控跳过）", …]
```

⇒ 同一份证据，修复前判 `fail`（并停流），修复后判 `pass`。**差别只在判据，不在数据。**

## 2. 为什么测试一直是绿的

`pc/test_server.py` 的夹具 `default_meta()` 写的是：

```python
"ois_mode": "OFF", "eis_mode": "OFF",     # ← 裸名字，而真机是 "OFF(0)"
```

夹具比现实"干净"，于是 19e「门控 pass」这条断言**从来没验过真机的写法**。
这是**夹具保真度**问题，不是覆盖度问题：断言存在、逻辑正确、就是喂错了输入。

规律（可套用到本项目其它判据）：**夹具必须由"被观测对象的真实产出格式"导出，而不是由
"判据期望的格式"书写**。否则测试会退化成安慰剂 —— 全绿，而现场照旧坏。

⇒ 本轮同时加了三条防线：

| 防线 | 做法 |
|---|---|
| 夹具保真 | `default_meta()` 改成真机写法 `"OFF(0)"`，并在注释里写明原因 |
| 格式锚定 | 测试 20h 直接从 `DeliverySession.kt` 源码读 `name()` 的格式串与 `ois` 表：App 一改写法，测试先炸，而不是等到现场 |
| 规则表驱动 | 测试 20a/20b 把归一规则逐条钉住（相等 5 种 + 不等 4 种，**双向**） |

## 3. 修法：门控的枚举比对

判据侧新增 `enum_eq(want, got)`（`pc/server.py`），认三种写法：
`"OFF"`（裸名字）、`"OFF(0)"`（名字+码，App 的写法）、`0`（裸码，`--profile` 里手写）。

比较顺序：

1. **两边都有名字** ⇒ 比名字（`"OFF(0)"` ≡ `"OFF"`）；
   若**两边都带码**，码也必须相等 ⇒ `"OFF(2)"` vs `"OFF(0)"` 判**不一致**
   （名字与码自相矛盾 = 数据有毛病，应该让人看见，不能就地抹平）；
2. 否则**两边都有码** ⇒ 比码（`0` ≡ `"OFF(0)"`）；
3. 一侧只有名字、另一侧只有码 ⇒ 借 `_ENUM_CODES` 表补齐（仅覆盖 `OFF/ON/AUTO/…` 这几种常见名）；
4. **认不出且对不上 ⇒ 判不一致**（保守：宁可误停，也不放过真的配置偏移）。

### 3.1 归一必须留痕

`want="OFF"`、`got="OFF(0)"` 判一致时，`checks.<键>` 会带 `normalized: true`，
并把 `ois: 请求 'OFF' ≡ 回读 'OFF(0)'（写法不同，语义相同）` 写进 `soft_notes`，
面板显示「N 条注记（含 M 项写法归一）」。

**为什么非要留痕**：不让"归一"变成一个静默步骤。否则日后有人看到 `want="OFF"` 而
`got="OFF(0)"` 又 `ok=true`，会以为判据在放水 —— 相当于把缺陷从"假失败"换成了"说不清"。

## 4. 顺带修掉的三件事

### 4.1 "判不了"不再等于"有问题"（三态）

原实现里回读缺席（`got is None`）也走 `put(..., ok=False)` ⇒ 计入 `hard_fail` ⇒ **停流**。
这与本项目的铁律直接冲突：**判不了 ≠ 有问题**（判不了 ≠ 通过，但也不该升级成停流）。

现在三态分离：

| status | 含义 | 动作 |
|---|---|---|
| `fail` | 值对得上、但**语义不一致** | 自动停流 + 标 `gate_failed` |
| `incomplete` | 值是**没看见**（`unevaluable` 列表）或还没有帧 | 只标记，**不停流** |
| `pass` | 已知的硬项全部一致 | 记档 |

### 4.2 门控不再"只判第一帧就冻结"

取证据的规则从"第 1 帧"改成"**按 seq 升序第一个带完整回读字段的帧**"，
并跳过 `result_missing: true` 的帧（1.10.5 之前约 2/3 的帧整组缺 CaptureResult 派生字段）。
`gate_checked` 只在判出**定论**（pass/fail）时置位；`incomplete` 不冻结，后续帧补齐后自动复判。

否则"一次取证不足"会被永久固定成"看不清" —— 而且第一帧恰好缺字段的概率并不低。

### 4.3 溯源字段被静默丢弃（真机落盘数据里查出来的）

查 `manifest.json` 时发现：`device_serial='unknown'`、`app_version=''`、
`capture_path_id=''`、`capture_path_rev=0`，而 App **每个 `init` 都在如实上报这些值**。

原因：v1.10.5 起会话改由控制道 `session_begin` **先建**，而 `h_init` 是
`hub.session(sid) or create_session(...)` —— 会话已存在时，init 里带的
`model / device_serial / app_version / calib_id / capture_path_id / capture_path_rev`
**整组被丢掉**。又是一次"字段在、值没了"的静默缺失，代价是
"这份证据是哪台机器的哪个构建采的"变成不可回答。

修法：`Session.absorb_declaration()` —— **空则补，非空且不同则记冲突**（`declared_conflicts`，
进 manifest 与面板）。**不覆盖**：中途变化说明这批数据混了两套前提（换了标定、换了机器），
那是要人看见的问题，不是就地抹平的问题。面板对空字段显示"未声明"，避免空值看着像正常。

### 4.4 记账更正：`stream_deliver_yuv` 的 rev 声明错了

真机帧 JSON 里 `capture_path_rev = 1`，而登记表在 1.10.3 就把该路径记为 **rev=2**
（默认档改 0.6×，那是请求参数变更）。即 1.10.3~1.10.6 的帧**宣称 rev=1、实际行为是 rev=2**。

登记表存在的意义就是"声明必须为真" —— 声明错了比没声明更坏（看着有，实际对不上）。
v1.10.7 起 `PATH_REV = 2` 与登记表一致。**已采数据的分段提醒**：判断"两份数据是否同一采集路径"
时，1.10.3~1.10.6 的交付数据要按 **rev=2**（Default 0.6×）看待，不能按帧里写的 1。
