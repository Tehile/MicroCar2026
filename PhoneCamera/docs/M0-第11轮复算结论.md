# M0 第 11 轮复算结论（v1.8.1 全量重跑：一次设备级瞬时故障窗口，与四类"过度结论"）

> 输入：用户装 **v1.8.1** 重跑全部科目，`python tools\m0_evaluate.py --pull` 报告
> （8 份，总判定 `WARN (PASS=20 WARN=1 FAIL=0 INFO=12)`，唯一 WARN 仍是 G18）。
> 按固定做法，**不采信报告汇总结论，从 8 份原始 JSON 逐帧重算**，
> 并对本轮改动的每条判据做 PASS/FAIL 双向路径测试。
>
> 一句话结论：**②④③ 全部成功且结论不变；⑥⑤ 与 ④ 的多数档位在 ② 之后的约 20 秒窗口内
> 成组失败 —— 时间线证明这是设备级瞬时故障（R27），不是路径或档位不支持。**
> 由此暴露并修掉三类**判据过度结论**（G18/G24/G26），App 加**零帧重试**（v1.8.2）；
> 另有测试侧"断言依赖真实数据集"第 4 次复发，一并改为注入式。

## 1. 用时间线定性：这是"时间窗"，不是"不支持"

8 份报告的生成时刻（同一分钟内）：

| 时刻 | 报告 | 结果 |
|---|---|---|
| 23:02:11 | ① 静态探测 | ✅ |
| 23:02:30 | ② 主连拍（150 帧） | ✅ |
| **23:02:48** | **⑥ 拍照（2 档）** | ❌ 2/2 失败 |
| **23:02:51** | **⑤ 尺寸扫描（5 档）** | ❌ 5/5 失败 |
| **23:02:52** | **④ 帧率扫描（8 档）** | ⚠ 5/8 失败 |
| 23:03:04 | ③ 第 1 轮 | ✅ |
| 23:03:12 | ③ 第 2 轮 | ✅ |
| 23:03:19 | ③ 第 3 轮 | ✅ |

失败错误只有两类：`摄像头被断开`（`onDisconnected`）×8 与
`CameraAccessException CAMERA_ERROR (3): createDefaultRequest ... Function not implemented (-38)`×1。

⇒ **三条判据**：
1. **失败与成功交错出现**（④ 内部第 4 档成功、第 5 档失败、第 7/8 档又成功）——
   档位级别的"不支持"不可能这样；只有**服务瞬时劣化**才会。
2. **同一份代码另外跑通了**：⑤ 用的采集路径与 ② 完全相同（`burst_yuv_manual`，`rev=1`），
   ②④③ 共 6 次会话全成功。⇒ 不是 v1.8.1 的代码回归（v1.8.1 只改了拍照路径的取图配对与报告字段）。
3. **自行恢复**：约 20 秒后 ③ 三轮连跑全成功，无需重启 App。

## 2. 正面的复算：v1.8.1 的改动在连拍路径上无副作用

- ② 主连拍 + ③ 三轮：**150 帧 × 4**，时间戳结构、锁定项、几何与第 10 轮逐帧一致；
- **G21 PASS**：3/3 轮首帧回到掉电默认（确为独立 `openCamera`）、焦点回读极差 0、生效物理镜头恒为 2；
- **G23 PASS**：四份报告设备/固件分组唯一、配置分组唯一、采集路径 `(burst_yuv_manual, 1)` 成对相同、
  时间跨度 **49 s**（第 10 轮的"跨批次 WARN"随之自然消失——侧面印证第 10 轮把它降级为注记是对的）；
- **G27 PASS**：交付格式 `yuv` 与证据实际格式一致。

## 3. 修掉的三类"判据过度结论"

### 3.1 G18：失败档被静默吞掉

旧实现只取有数据的档位（`ok`），**一句不提 5/8 档失败**；"慢速档位全部跟随请求变化"这句里
本批实际只剩 24 fps 一个慢档。⇒ 改为：显式列出 `N/M 档未取得数据`，**按错误串分组**，
并明说"只覆盖成功档位"；措辞改为"**成功的**慢速档位均跟随请求变化"。

### 3.2 G24：零有效档却打印批次实测结论（结论超出证据）

旧实现在 **0 个有效档位**时仍打印"本机所有 4:3 档 skew 完全相同（9.21 ms）"与
"本批扫描未记录请求帧率（**各档实测均 ≈30.04 fps**）"——后者在本批**一个实测都没有**时是凭空断言。
⇒ 改为：零有效档时明说"**本批没有取到任何档位的实测**"，既往数据一律标注为**历史证据**（含轮次），
并且该警告只在**有有效档位**时才出现。

### 3.3 G26：error 档继续走字段检查，还报出假阳性

旧实现对"跑了但失败"的档位继续做字段检查：报一堆"缺 `crop_region`/缺 `image_pairing`"的 WARN，
更严重的是**对照档缺指纹时走进 `else` 分支报"指纹一致"**（判不了被当成判过了）。
⇒ 改为：`jpg.error` ⇒ **INCOMPLETE**（交付档是 G26 的全部对象）；`yuv.error`/整体缺席 ⇒
WARN「第 1/2 项对照检查缺席」；指纹取不到 ⇒ 单独一支报"**无法逐段比对**"，绝不再输出"一致"。

## 4. App v1.8.2：零帧时按退避重试打开

| 项 | 内容 |
|---|---|
| 触发条件 | `onDisconnected` / `onError` / `openCamera` 抛 `CameraAccessException`，**且尚未采到任何帧** |
| 退避 | 2 s → 5 s → 10 s（最多 3 次重试）；超时预算同步计入退避时间 |
| 留痕 | 报告新增 `open_attempts`、`open_retry_errors`（可审阅） |
| 为何只在"零帧"重试 | 重试必然重建会话；采到一半重建会把**两个会话拼进一份报告**，证据含义全变。打开阶段失败没有任何数据产生，重试不改变采集语义 |
| 为何不升 rev | 三条路径的会话配置、请求参数、模板、格式、调度方式、丢弃规则与逐帧记录**全部未变**；`rev` 只反映采集行为变化（登记表已写明） |
| 产物 | APK **914 060 B**，编译验证通过（`app_version = m0probe-1.8.2`） |

## 5. 测试侧：同一错误第 4 次复发，已根治

用户重跑后，round7/round10 里 **9 条断言**失效，全部因为"**依赖真实数据集恰好具有某属性**"：
版本恰好不同、⑤ 恰好有有效判别档、③ 恰好缺 `device` 段、跨度恰好 6h53m、1.5.0 期报告恰好在场。

| 原断言依赖 | 现在改为 |
|---|---|
| 真实数据里版本不同 | 注入：把 r1~r3 伪装成 1.5.0 期报告（版本号 + **不自描述路径**） |
| 真实 ⑤ 有判别档 | 合成扫描夹具（三档 4:3 + 16:9 普通档 + 全 crop 判别档，行时间统一 2999 ns） |
| 真实数据缺 `device` | 注入删除 `device` 段 |
| 真实跨度 6h53m | 注入时间戳偏移 |
| 1.5.0 期报告在场 | 注入 `old_style()` |

⚠ 顺带发现一条**真空通过**：反向用例"判别档 skew 按 crop 高度变 ⇒ 不该宣布结论"在
"零有效档"的数据上也会通过 —— 那验的是"没跑"，不是"判据克制"。合成夹具一并解决。
⇒ **通用规则：测试要验的是判据的行为，不是环境的现状。**
