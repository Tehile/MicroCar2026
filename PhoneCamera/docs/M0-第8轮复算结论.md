# M0 第 8 轮复算结论（交付方式定为「拍照」）

> ⚠️ **前向标注（第 9 轮）。** 本轮把交付方式定为拍照（**D23**），据此新增 ⑥ 拍照路径与判据 G26，
> 总判定收紧为 `INCOMPLETE`。**第 9 轮用户改为「拍照还是流式都可以，只需要满足一开始设计方案中的要求」，
> 逐项对照 §1.2 的三条需求后改判为连续流（D24 ⇒ D23 被取代）**：
> 交付物与证据同源同格式 ⇒ **R22 从结构上消解**，G26 降为 INFO，总判定回到 `WARN`。
> 本轮的两条结论仍然成立、且必须保留：① 既有 PASS 一条也覆盖不到**另一条路径**；
> ② **一个判据的价值，恰恰在它能说"我不能给你结论"。**
> 判决过程与代价见 **`docs/M0-路线决策.md`**。
>
> 输入：用户指令 **「回传使用拍照，确保时间戳准确即可」** + 第 7 轮 `python tools\m0_evaluate.py --pull` 报告
> （总判定 WARN，PASS=18 WARN=1 FAIL=0 INFO=11）。
> 按固定做法，**不采信报告里的汇总结论，一律从 7 份逐帧原始 JSON 重算**，

> 但它们一条也覆盖不到交付路径** —— 交付走拍照，而源码里根本没有拍照。
> 于是唯一的新增未验证项 G26 把总判定从 `WARN` 变成 **`INCOMPLETE`**。
> 这不是退步，是**把一条原本被"整体 PASS"盖住的盲区显式化了**。

> 顺带澄清一处**看起来像矛盾、其实是两个指标**的地方：报告写"`d[i]==d[i+5]` 在 139/139 处成立"，

**所以第 8 轮不出任何 FAIL —— 问题不在"哪里错了"，而在"哪些根本没测"。**

## 2. 交付路径零证据（本轮的核心发现）

对源码做 grep：**App 里完全没有** `takePicture` / `TEMPLATE_STILL_CAPTURE` / JPEG。
全部 7 份报告都来自：

```
TEMPLATE_MANUAL  +  setRepeatingRequest  +  YUV_420_888      （连续流）
```

而交付方式一旦是拍照，走的是：

```
TEMPLATE_STILL_CAPTURE  +  单张捕获  +  JPEG                 （拍照路径）
```

**模板 / 输出格式 / 调度方式，三样都不同。**

⇒ **集成路径变了，就是证据基础变了。** ②③④⑤ 的 PASS 是"连续流下参数锁得住、时间戳可信"的实证，
它**没有一行**能说明"拍照路径下时间戳还可信"。

### 拍照路径独有的两个风险（连续流里根本不存在）

| 风险 | 机制 | 为什么危险 |
|---|---|---|
| **ZSL 交出旧帧** | `TEMPLATE_STILL_CAPTURE` 常触发零快门延迟：从环形缓冲里取**已经曝光完的旧帧**，`SENSOR_TIMESTAMP` 随之指向**更早**的时刻 | 画面与通知**完全正常**；偏差随机、逐张不同、不受控。只能靠 `sensor_ts_minus_request_ns < 0` 发现 |
| **多帧合成（MFNR/HDR）** | 拍照时 HAL 把 `EDGE_MODE` / `NOISE_REDUCTION_MODE` 自动切成 `ZERO_SHUTTER_LAG` / `HIGH_QUALITY` | 一帧里合了**不同时刻**的多帧 ⇒ `SENSOR_TIMESTAMP` **不再对应单一时刻**，时间戳失去意义 |

这两类风险**在连续流里不会发生**，所以只有单张模式才测得到。

### 处置：新增 ⑥ 拍照路径 + 判据 G26

App 新增第 ⑥ 项，跑**两条受控路径**：

| 档 | 模板 | 格式 | 尺寸 | 帧时长 | 作用 |
|---|---|---|---|---|---|
| 对照档 | `TEMPLATE_MANUAL` | `YUV_420_888` | 与 ② 同档 | 发 | 只把"重复请求"换成"单张捕获"，构成受控实验 |
| **交付档** | `TEMPLATE_STILL_CAPTURE` | `JPEG` | 强制 `4096×3072` | **不发** | 量交付路径自己的时间戳语义与几何 |

每张**串行**下发（拿到上一张结果才发下一张），各 8 张（预热 1 张）。
串行是必须的：连发多条时 HAL 可以自由重排，"第 k 张时间戳对应我第 k 次下发"这个对应关系就没了。

交付档显式下发 `CONTROL_ENABLE_ZSL = false`，并把 `control_enable_zsl` 与
`EDGE_MODE` / `NOISE_REDUCTION_MODE` / `COLOR_CORRECTION_ABERRATION_MODE` 一起列入**锁定字段回读校验**。

判据 **G26**：缺 `m0_still_shot.json` → `add_unverified` ⇒ **INCOMPLETE**。

## 3. 新的判据维度：时间戳的「参考行」与「单帧固有不确定度」（G25）

用户说"确保时间戳准确即可"。那就必须先把"时间戳准确"这件事**拆成可量的项**。
拆完发现：**之前一直没区分过两个量**。

### (a) 参考行偏置 —— 一个静默的常量

`SENSOR_TIMESTAMP` 的语义是**活动阵列首行**的曝光起点，而它**不等于**图像第 0 行 ——
crop 一旦带纵向偏移，两者差 `crop.top` 行：

| 配置 | `crop.top` | 偏置 = `crop.top × 2999.0 ns` |
|---|---|---|
| 全幅 4:3（`1920×1440` / `2880×2160` / `4096×3072`） | **0** | **0 ns** |
| 16:9 经 `aspectSafeCrop` 收紧 `(0,384,4096,2304)` | **384** | **1 151 616 ns ≈ 1.15 ms** |

**为什么它比"帧率不准"更危险**：它是**静默**的。画面正常、时间戳单调递增、帧间隔抖动为 0 ——
**G10 / G15 / G20 / G22 一个都不报警**，它只是让整幅图统一偏了 1.15 ms。

⇒ **交付档必须 `crop.top == 0`**（本机 `4096×3072` 满足）；否则必须在离线端显式补偿。

### (b) 单帧固有不确定度 = 整幅读出时间

卷帘快门意味着同一张图里不同行是**不同时刻**曝光的。所以**单张**照片给出的时间信息
本质上是一个**时间窗**：

| 量 | 实测 | 说明 |
|---|---|---|
| 整幅读出时间 = `skew` | 9 212 928 ns | 图像内部的时间跨度 |
| 帧周期（回读帧时长） | 33 287 995 ns | |
| 占比 | **27.7%** | |
| 窗中心不确定度 | **± 4.61 ms** | = `skew / 2` |

### (c) 三个误差源差四个数量级 —— 这决定了"准确"的主战场在哪

| 误差源 | 量级 | 类别 |
|---|---|---|
| 帧率 / 时间基漂移 | 3.06 ppm × 33.288 ms ≈ **101.9 ns** | 累积型，多帧可回归压掉 |
| **卷帘读出（单帧）** | **9.21 ms**（±4.61 ms） | 固有型，**多张平均消不掉** |
| 参考行偏置（16:9 档） | **1.15 ms** | 静默常量，可显式补偿 |

⇒ **"确保时间戳准确"的主战场是卷帘读出，不是时间基。** 把时间基做到 ns 级对精度毫无帮助；
真正决定上限的是"这一帧跨越了 9.21 ms，目标在这段时间里动了多少"。

> **这也是"回传使用拍照"这个决定最实质的代价。** ②③④⑤ 的帧与帧读出时刻是**错开**的，
> 离线可以用多帧互相插值补出比帧周期更细的时间分辨；**单张拍照没有这个余量**，它只有一个时间窗。
>
> ⚠ 顺带注意**方向**：用户说"时间戳准确即可"= 放弃**帧率约束**，
> 但帧率不再是门槛，恰恰**让时间戳成了唯一的门槛** —— 要求是被**提高**了，不是降低。

### (d) EXIF 不可作时间源

交付格式是 JPEG，天然带一个"看起来像时间戳"的 `DateTimeOriginal`。
它是**系统墙钟**（`currentTimeMillis` 域），与 sensor 的 REALTIME 时间基之间隔着一个系统维护的偏移量，
精度由厂商决定；`SubSecTimeOriginal` 还**未必给足亚秒位数**。

⇒ 时间只认 `sensor_timestamp_ns`；判据 G26 **实测 EXIF 亚秒位数**，< 3 位即 WARN 并明确拒绝把它当时间源。

## 4. G23：从「一个标量」改成「一对标识」

第 7 轮把"同一采集路径"的判据从**版本号**改成了 `capture_path_rev`（修掉了无限返工）。
本轮新增拍照路径后，它又出了个新问题：**`rev` 是全局计数的 —— 加一条新路径，会把其它路径的证据一起作废。**

（返工循环换个形式又回来了：第 7 轮是"改一行代码就让 ③ 作废"，第 8 轮是"加一条路径就让 ②③ 作废"。）

**根因不是计数规则，是接口形状**：判据返回一个标量 `rev`，而"是哪条路径"这个必要信息被丢掉了。
两条不同路径的第 1 版 `rev` **都是 1**，单看数字分不开。

⇒ 改为 **`(capture_path_id, capture_path_rev)` 成对**：

```json
"capture_path_id": "still_jpeg_template",     // burst_yuv_manual / still_yuv_single / still_jpeg_template
"capture_path_rev": 1                          // 按【路径】计数，不是按 App 版本计数
```

`tools/capture_path_versions.json` 也改成 `paths` 字典（每条路径各自计数），并写进
`_why_id`（为什么不能只用修订号）。**通用教训：判据的返回值要能唯一确定被比较的对象。**

## 5. 判据改动与双向路径测试

### 改动

- **新增 G26**（拍照路径证据）：`delivery != still` → INFO；缺报告 → `add_unverified` INCOMPLETE；
  缺交付档 → INCOMPLETE；四项检查（对照档指纹/几何/`skew` 与 ② 一致、`sensor_ts_minus_request` 全正、
  ISP 档位未被改写为 ZSL/HIGH_QUALITY、EXIF 亚秒）；`fails` → FAIL，`warns` → WARN。
- **新增 G25**（参考行与单帧不确定度）：三出口 —— `crop.top ≠ 0` → WARN 须补偿（给出 `crop.top × 行时间`）；
  `crop.top` 缺失 → WARN「判不了」；`crop.top == 0` → PASS 并量化 `skew`、占比、±半幅。
- **G18 加 delivery 门控**：拍照 → 档位不可达降级为 INFO（帧率不再是阻塞项）；连续流 → WARN。
  三个出口都追加交付方式声明文本。
- **G23 改 `(id, rev)` 成对 + skew 段重写**：**刻意不做 skew 归属判定**
  （见下），只判"同几何配置内 skew 是否唯一"。
- **G16 修静默 bug**：焦点回读改显式 `float()` 转换。
- 新增 `--delivery {still,stream}` 参数（**调用方声明的输入**，不是测出来的事实）。

### 本轮修掉的三个实现级坑（都属"静默失败"）

| 坑 | 症状 | 修法 |
|---|---|---|
| `stats.lock_stability.*.values` 是**字符串**（App 用 `toString()` 写），而判据用 `isinstance(v, (int,float))` 过滤 ⇒ **全被丢掉** | G25 报"取不到 skew"、G23 skew 段静默无数据、G16 焦点回读永远走不到"逐帧值优先"分支 | 新增 `_skew_value()` / `_as_positive_int()`（返回值带"原始类型 str，已显式转换"的来源说明）；G16 改显式转换。**加了回归测试 `skew_only_in_lock_stability`** |
| `_resolve_capture_path()` 判不了时返回 **`(None, None)`** 而不是 `None` | **元组恒为真** ⇒ f-string 里对 `None` 取下标 → TypeError **打崩整个脚本**，G23 整行消失（而"整行消失"看起来和"判据没跑"一样） | 返回 `None`。**教训：判不了要用明确哨兵值，不要用"字段全空的结构"** |
| G23 的 skew 归属段**结论超出证据** | 四份报告只有一种几何 ⇒ 三列归一化**同时**恒为 0 ppm ⇒ `min()` 任意挑一个说"恒定的是它"（第 5 轮已被证伪的口径） | 深层根因：crop 与输出同纵横比时 `read_rows = crop_w·outH/outW = crop_h`，两口径**数值必然相同、结构上不可分离** ⇒ 改为按几何分组只判自洽性，并明说"本段不做归属判定"，归属交给 ⑤ 判别档 |

## 6. 我不同意"其余已符合要求"

用户本轮的原话是 **「回传使用拍照，确保时间戳准确即可」**。
"即可"意味着帧率等其余项不再作为阻塞项 —— 这一点我**同意**（帧率已降级为 INFO）。

但**"其余已符合"这个判断在拍照这条路径上不成立**，我要明确反对：

1. **既有 PASS 一条也覆盖不到交付路径。** 源码 grep 证实 App 里**完全没有**
   `takePicture` / `TEMPLATE_STILL_CAPTURE` / JPEG。模板 / 输出格式 / 调度方式三样都不同 ⇒
   **集成路径变了就是证据基础变了。**
2. **拍照路径有两个独有风险，且都不自报故障。** ZSL 交出旧帧（画面和通知完全正常，
   偏差随机不受控）、多帧合成（时间戳不再是单值）。**连续流里测不到它们。**
3. 所以我把 G26 做成 `add_unverified`：**缺 `m0_still_shot.json` 即 INCOMPLETE，
   不得判定机型合格。**

**总判定：第 7 轮 `WARN` → 第 8 轮 `INCOMPLETE (PASS=19 WARN=0 FAIL=0 INFO=13)`。**
唯一未验证项 = G26。**这是正确的收紧，不是退步。**
一条判据的价值，恰恰在它能说"我不能给你结论"的时候。
