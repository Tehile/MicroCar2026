# 手机相机采集与回传 方案设计

> 定位：手机作为**已标定的测量相机**，在局域网内受控采集，把高质量图像 + 完整相机状态元数据可靠回传到 PC，供离线建模与定位处理。
>
> 版本：v1.0（设计定稿，未实施）

---

## 1. 需求与约束

### 1.1 来自题目的硬约束

| 项 | 内容 |
|---|---|
| 传输范围 | 局域网 |
| PC 端 | Python 桌面端接收程序 |
| 时效 | 初期不要求实时性；准在线只需用于"确认现场情况" |
| 目标 | 手机摄像头用于**定位**，需先做**镜头标定** |

### 1.2 本方案识别的真实需求

题面写的是"拍照回传"，但项目的真实目标是**定位**，所以核心矛盾不是传输效率，而是：

> **内参可复现性 —— 标定之后，相机参数必须可证明地没有漂移。**

因此本方案的第一价值不在"传得快"，而在：
1. 把相机钉在一个**已知、可复现、可验证**的状态；
2. 保证每一张交付的图像**都能被判定"属于哪一次标定、当时的参数是什么"**；
3. 在参数漂移时**主动报警**，而不是静默失准。

**路线与时间戳要求（第 9 轮定案，取代第 8 轮的 D23）：**

| 项 | 结论 | 后果 |
|---|---|---|
| 采集/交付路线 | **连续流（按需开流）+ 按 `sensor_timestamp` 抽帧交付单张** —— `TEMPLATE_MANUAL` + `setRepeatingRequest` + `YUV_420_888`（**D24**） | 交付物与既有证据**同源同格式** ⇒ 19 项 PASS 直接覆盖交付物，R22 从结构上消解；抽帧交付的产物**仍是单张图像**，题面「拍照回传」的交付物口径不变 |
| 时间戳要求 | **准确** | 主战场不是时间基（漂移 101.9 ns），而是**单帧卷帘读出时间 9.21 ms**（±4.61 ms，多张平均消不掉）与**参考行偏置**（见 8.1.1、G25）。⚠ **交付形态改变不了这一点** —— 单张交付（无论怎么来的）都只有这一个 9.21 ms 的窗 |
| 帧率要求 | **在连续流路线下重新成为约束项** | 流式的带宽直接由帧率决定 ⇒ G18 恢复阻塞（WARN）。但 `SENSOR_FRAME_DURATION` 已证生效（12/15/24 fps 全部跟随请求）⇒ 降帧率可控带宽 |

> **第 9 轮判决过程**：用户「拍照还是流式都可以，只需要满足一开始设计方案中的要求」⇒ 回到本节的三条需求
> （N1 可证明的内参可复现性 / N2 可判定归属 / N3 漂移主动报警）逐项对照，**取连续流**。
> 完整判决、证据与代价见 **`docs/M0-路线决策.md`**。⑥ 拍照路径降级为**备选**，不再阻塞交付。

### 1.3 环境事实（已核实）

- 工作区 `PhoneCamera\` 为空，全新项目
- `conda general_env` = Python 3.12.13
- **已装**：`cv2` `PIL` `requests` `numpy` `websockets` `qrcode`
- **未装**：`flask` `fastapi` `uvicorn` `aiohttp` `zeroconf` `netifaces`
- 网络地址会变化，**方案中不硬编码任何 IP**

## 2. 关键设计决策

| # | 决策点 | 结论 | 主要理由 |
|---|---|---|---|
| D1 | 手机端载体 | **Android 原生 App（Kotlin）** | 需要专业模式参数控制，跨平台插件够不着 |
| D2 | 相机 API | **Camera2**（非 CameraX） | 需要手动参数、逐帧 `CaptureResult`、重复请求与连拍 |
| D3 | 采集形态 | **高速连拍（连续流）**，放弃 mp4 录像 | mp4 无 `SENSOR_TIMESTAMP`，逐帧时间戳不可信。**只有连续流能逐帧验证锁定与时间戳**。第 9 轮起**它同时是交付形态**（见 D24）—— 这一点与第 8 轮不同 |
| D4 | 图像格式 | **高质 JPEG(q95–98) 主用 + RAW 开关（标定）**，可选 YUV 原始档 | 兼顾日常与亚像素精度 |
| D5 | 单轮规模 | 几百张 / GB 级 | 必须做分片与续传 |
| D6 | 时效形态 | **准在线监视 + 离线批处理交付**（双车道） | 两个目标诉求相反，必须分离 |
| D7 | 传输通道 | **WebSocket（控制+监视） + HTTP 分片上传（交付）** | 控制指令不能被大文件队头阻塞 |
| D8 | 服务端框架 | **aiohttp 单进程** | 一个进程同时提供 HTTP/WS/静态页，胶水最少 |
| D9 | 发现配对 | **二维码为主 + mDNS 为辅**，手输兜底 | IP 会变；`qrcode` 已装，零额外依赖 |
| D10 | PC 端形态 | **本地 Web 面板** | 复用 aiohttp；满足"实时确认"；电脑手机可同看 |
| D11 | 相机参数 | **Profile 锁定 + 只读 UI**，改动需维护模式 | 防现场手滑；改动自动产生新 `calib_id` |
| D12 | 标定指纹 | **采纳 `calib_id`**，帧级记录 + 会话级断言 | 防止新旧标定数据混算而静默出错 |
| D13 | 手机端存储 | **PC 端 ACK 通过后才删除本地文件** | 宁可复杂，不可丢数据 |
| D14 | 断网行为 | **本地持久化队列 + 恢复后自动补传 + 幂等去重** | 现场 Wi-Fi 抖动是常态 |
| D15 | 触发方式 | **远程 START/STOP（主） + 本地按钮（保命） + 定时间隔（辅）** | 网络故障时仍能采集 |
| D16 | 时间基准 | **以手机 `SENSOR_TIMESTAMP` 为唯一权威** | 触发时刻 ≠ 曝光时刻。**注意它是"活动阵列首行的曝光起点"**：crop 带纵向偏移时与图像第 0 行差 `crop.top × 行时间`（见 8.1、G25）；单张拍照下还必须配 `(capture_path_id, capture_path_rev)` 才说明得了"这个时间戳来自哪条采集路径" |
| D17 | 跨设备时钟同步 | **不做**（降级为可选） | 用户明确"时间戳只以手机为准，用于离线处理"。**并且 JPEG 的 EXIF 时间（`DateTimeOriginal`）不可当时间源** —— 那是系统墙钟、精度由厂商决定，与 sensor 时间基无固定关系（见 R5、8.1） |
| D18 | 卷帘快门 | **可开关，默认关；但必须记录可事后补算的原始量** | 目标"大部分静态、小目标会动" |
| D19 | 现场网络 | **自备便携路由器 / 电脑连手机热点**，写进方案前提 | 规避 AP 隔离 |
| D20 | 交付形态 | 先方案文档，后分阶段落代码 | — |
| D21 | 设备规模 | 单手机单电脑（幂等键已预留设备维度） | — |
| D22 | 界面投入 | 自用，不讲究美观，优先稳定性与信息密度 | — |

## 3. 核心风险与对策

### R1 内参漂移的四个源（已在设计中逐项封堵）

| 漂移源 | 影响的参数 | 对策 |
|---|---|---|
| **自动对焦 AF** | 有效 fx/fy、畸变系数（**最大隐藏杀手**，对焦改变镜组间距） | `CONTROL_AF_MODE_OFF` + 锁 `LENS_FOCUS_DISTANCE` |
| **数码变焦 / 镜头切换** | 等效焦距、主点 cx/cy | 锁 `CONTROL_ZOOM_RATIO = 1.0`，`SCALER_CROP_REGION` 设为全画幅 |
| **光学防抖 OIS** | 主点 cx/cy 随机抖动，逐帧不同 | `LENS_OPTICAL_STABILIZATION_MODE_OFF` |
| **电子防抖 EIS** | 视野被裁切且裁切窗随时间变化 | `CONTROL_VIDEO_STABILIZATION_MODE_OFF` |

**第五个源：温度。** 手机连续工作发热，镜头组与传感器形变可致 fx 漂移 0.1%–1%，足够毁掉定位精度。

对策：逐帧记录**电池温度**作代理（`ACTION_BATTERY_CHANGED` 的 `EXTRA_TEMPERATURE`），并在断言中断言温度区间。

> **已核实的实现限制**：Camera2 公共 API **不提供传感器温度**（`android-34` 的 `android.jar` 里不存在 `SENSOR_TEMPERATURE`）。
> 因此温度只能拿到电池温度这种**滞后代理量**，用于判断"设备是否在持续发热"，不能作为精确的内参漂移自变量。这是本方案的一个已知精度上限。

### R2 未去畸变图像（必须在 M0 阶段确认）

用 Camera2 拿到的图像**大概率是未经几何矫正的原始画面**，而厂商相机 App 给你的是已矫正版本。广角镜头畸变可达百分之几。**若到后期才发现，整个标定要重做。** 对策：M0 阶段明确确认；标定模型必须包含畸变项。

### R3 机型能力参差（**必须在 M0 阶段用真实机型验证**）

- `LENS_INFO_MINIMUM_FOCUS_DISTANCE` 返回 0 → 该机型 HAL **根本不支持手动对焦距离**。你在厂商"专业模式"里能拖的对焦滑杆可能是私有实现。
- `REQUEST_AVAILABLE_CAPABILITIES` 是否含 `MANUAL_SENSOR` / `BURST_CAPTURE` / `RAW` / `PRIVATE`
- `SENSOR_INFO_TIMESTAMP_SOURCE` 是否为 `REALTIME`（若为 `UNKNOWN`，帧间时间关系不可靠）

> **结论：选哪台手机，本身就是方案的一部分。** M0 必须先出能力报告。

### R4 现场网络

- **AP 隔离（Client Isolation）** 会让手机根本访问不到 PC —— 代码无法解决，只能靠方案规避 → **自备网络为方案前提**
- **Windows 防火墙**首次监听会弹窗，现场点错则链路全死 → 固定端口 + 提前放行规则

### R5 与机器人数据的时钟对齐（**显式未决项**）

当前"时间戳只以手机为准"对**纯手机侧离线处理**成立。但若后续要把手机帧与**机器人自身运动/里程计数据**对齐，两套时钟的同步问题会重新出现，且此时补做比现在难得多。

对策：记为显式风险，M3 阶段确认上游是否需要；若需要，预留"补做时间同步"或"靠视觉对应关系对齐"两条路。

**配套禁令：交付路径上的时间必须来自 `SENSOR_TIMESTAMP`，不得来自 JPEG 的 EXIF。**
现行交付格式是 `YUV_420_888`（D24），本就不带 EXIF；但 D4 保留了 JPEG 日常档，而 JPEG 天然带一个"看起来像时间戳"的字段 `DateTimeOriginal`。
它是**系统墙钟**（`System.currentTimeMillis()` 域），与 sensor 的 REALTIME 时间基之间只隔着一个
由系统维护的偏移量，精度由厂商决定；`SubSecTimeOriginal` 还**未必给足亚秒位数**。
即便将来真要做跨设备同步，也应该用 `wall_clock_ns + boot_time_ns` 这套受控换算（见 8.1），
而不是从 EXIF 里读。**判据 G26 会实测 EXIF 亚秒位数并明确拒绝把它当时间源。**

### R13 逻辑多摄暗中换镜（**新增，最隐蔽的一个**）

M0 探测确认本机型后摄**声明了 `LOGICAL_MULTI_CAMERA`**，且 zoom 区间是 `[0.6, 10]`。
区间下界 < 1.0 意味着这颗"逻辑摄像头"由多颗物理镜头融合而成（含超广角）。

**关键认知：请求 `CONTROL_ZOOM_RATIO = 1.0` 只说明"我们要了 1.0 档位"，
并不能阻止 HAL 在内部切换物理镜头。** 参数表面上"锁住了"（`CaptureResult` 里
`zoom_ratio` 恒为 1.0），但生效的**物理镜头**可能变了。

换镜的后果：焦距、主点、畸变系数**同时跳变**。这是内参失效里最隐蔽的一种 ——
画面看着正常、程序不报错、标定也能正常跑完，只有定位结果悄悄偏掉。

对策三条，都要做：

1. **直接证据**：逐帧读 `CaptureResult.LOGICAL_MULTI_CAMERA_ACTIVE_PHYSICAL_ID`，
   断言全程唯一（判据 G19）。已用 `javap` 核实这是 `CaptureResult` 的逐帧 Key。
2. **结构化清单**：`CameraCharacteristics.getPhysicalCameraIds()` 枚举所有物理镜头，
   列出各自的焦距与等效焦距（判据 I9），据此判定 1.0 档位对应哪一颗。
3. **间接交叉校验**：由焦距与像元尺寸推算 `fx` 的期望值，与标定得到的 `fx` 对照
   （判据 I10）。本机型预测 `fx ≈ 1283 px @1920×1440`（现档）、`≈2736 px @4096`；
   若实测偏离接近某颗物理镜头的焦距比（例如 0.656 → ≈1955 px），即可反查出换镜。

### R14 采集输出尺寸未冻结（**新增**）

输出尺寸是内参的一部分，却很容易被当成"无关的传输参数"。同一镜头换尺寸，
`fx, fy, cx, cy` 全变。M0 还查出旧选档（1920×1080，16:9）不只是"亏"，而是**选错了**：
面积上限恰好等于 1920×1080 的面积 ⇒ 必然选中这个 16:9 档，而 App 又把 crop 设成整个
4:3 活动阵列 ⇒ 各向异性映射（`fx ≠ fy`，模型前提被破坏）。第 5 轮已改并验证通过
（`1920×1440`，G22 PASS，`fx == fy == 1282.5 px`）。

对策：`output_size` 写进 profile 并随 `calib_id` 冻结；**并额外要求 crop 与输出同纵横比**。
⚠️ 但**档位本身仍由人为面积上限决定**：第 6/7 轮 ⑤ 尺寸扫描已把证据表跑全（五档的帧率、
`skew`、字节数与带宽，含跨纵横比判别档），差异只剩 `fx` / 带宽 / 垂直视场，
"该定在哪一档"取决于回传链路形态（见 R19 与 5.3）—— 这是"精度上限"层面的欠账。

**第 8 轮补充：交付档另有一条硬约束 —— `crop.top` 必须为 0。**

因为 `SENSOR_TIMESTAMP` 标的是**活动阵列首行**，crop 一旦带纵向偏移，图像第 0 行就与时间戳
差 `crop.top × 行时间`（本机 16:9 档 `crop.top = 384` ⇒ **1.15 ms**）。这个偏差是**静默**的：
画面正常、时间戳单调、抖动为 0，现有四个判据一个都不报警（见 8.1、G25）。
所以交付档必须选**全幅同纵横比**的档位（本机 `4096×3072` 满足，`crop.top = 0`）——
这同时也就顺带满足了"crop 与输出同纵横比"。**16:9 档虽然 `skew` 更短（6.91 vs 9.21 ms），
但带 1.15 ms 静默偏置、且白扔 25% 垂直视场，不应用作交付档。**

### R22 交付路径的证据基础与风险（**第 8 轮新增，这是本轮最重要的一条**）

**第 8 轮把交付方式确定为拍照（D23，已由第 9 轮的 D24 取代）时，既有 M0 证据链整体失效。**

②③④⑤ 全部是 `TEMPLATE_MANUAL` + `setRepeatingRequest` 的连续流（`YUV_420_888`）；
交付走 `TEMPLATE_STILL_CAPTURE` + JPEG 单张。**模板 / 输出格式 / 调度方式三样都不同。**
已用源码核实：第 8 轮之前的 App 里**完全没有** `takePicture` / `TEMPLATE_STILL_CAPTURE` / JPEG ——
也就是说，此前所有"PASS"都没有一行覆盖过交付路径。

**拍照路径独有的两个风险（连续流里根本不存在）：**

1. **ZSL 交出旧帧。** `TEMPLATE_STILL_CAPTURE` 常触发零快门延迟：它从环形缓冲里取**已经曝光完的旧帧**
   交给你，`SENSOR_TIMESTAMP` 随之指向**更早**的时刻。画面与通知**完全正常**，
   偏差随机、逐张不同、不受控。**判法：`sensor_ts_minus_request_ns < 0` 即旧帧。**
   对策：显式下发 `CONTROL_ENABLE_ZSL = false` 并把它列入锁定字段回读校验；若 HAL 不认这个开关，该机型拍照路径不可用。
2. **多帧合成（MFNR/HDR）。** 拍照时 HAL 会把 `EDGE_MODE` / `NOISE_REDUCTION_MODE` 自动切成
   `ZERO_SHUTTER_LAG` / `HIGH_QUALITY`（多帧降噪或 HDR）。多帧合成后 `SENSOR_TIMESTAMP`
   **不再对应单一时刻** —— 一帧里合了不同时刻的多帧，时间戳失去意义。
   对策：同样列入锁定字段回读；被改写即说明时间戳不可用，须换模板或换机型。

对策（已落地）：M0 新增 **⑥ 拍照路径**，跑两条受控路径（对照档 = 同几何同格式但改用单张下发；
交付档 = 真·`TEMPLATE_STILL_CAPTURE`+JPEG），判据 **G26** 消费；缺证据即 **INCOMPLETE**
（**不得判定机型合格**）。**通用教训：集成路径变了就是证据基础变了 ——
"整体 PASS"不能覆盖没测过的那条路径。**

> **第 9 轮处置（D24）：这条风险不再靠"补证据"消解，而是靠"选路线"消解。**
> 交付路径改回连续流后，交付物与证据**同源同格式**，R22 的前提（交付走另一套三元组）不再成立。
> ⑥ 与 G26 **保留**为备选、以及逆向后（`--delivery still`）的判定路径。
> **通用教训一条不改地保留**：只要哪天交付路径再换一次，这条风险立刻重新生效。
> 判据 **G27** 就是为了在**输出格式**这一层拦住同一个错误 —— 见 R24。

## 4. 系统架构

### 4.1 三条道设计（D6 + **D27** + **D28**）

| 车道 | 载荷 | 协议 | 时效 | 用途 |
|---|---|---|---|---|
| **监视道** | 缩略图（几十 KB）+ 帧元数据 | WebSocket 双向 / MJPEG（本机） | 秒级 | 现场确认取景、曝光、参数状态 — **已实现（v1.10.0）**：1 Hz / 480 宽灰度 JPEG（q70，约 20–40 KB）/ 从已采帧现算 / **可丢** / PC 端只留最新 200 张；**v1.12.0 起同时以 MJPEG 提供给本机其它程序**（`/stream/mjpeg`，可丢） |
| **交付道** | **每一帧**的原始 Y 平面（2.765 MB/帧）+ 元数据 | **先落手机本地**（writer 线程）→ HTTP 分片上传（断点续传 + 逐帧 sha256） | 边采边传 + **停采后排空** | 在线算法 + **全帧率离线分析**（逐帧几何/时序）—— **一帧不落**（`verified` 才算，且有完整性账本） |
| **实时道**（v1.15.0 新增，`capture_mode=live`） | **彩色 JPEG**（默认 960×720 q70）+ 帧元数据 | **串行闭环** HTTP 二进制（`POST /api/v1/live/frame`，无 base64 膨胀） | 实时、**延迟不累积**（发完一帧才取下一帧） | 只想"看得清"的现场查看（联网取景 / 对焦 / 找目标）—— **零留存、可丢、允许彩色** |

> ⚠ **实时道不是"第三条并行的道"，而是与交付道互斥的会话性质**：`capture_mode=live` 时
> **交付道整体关闭**（不落盘 / 不起 writer / 不排空 / WS `thumb` 也关），唯一在跑的就是实时道。
> 默认仍是 `deliver`。设计细节（为什么串行、为什么 `acquireLatestImage`、为什么要独立 HTTP）
> 见 **D28**，契约见 **`docs/对外接口与单一交付道.md` §1.1**。

**为什么必须分离**：把两者混在一条链路上，会同时牺牲两件事 —— 为实时而压画质、为画质而牺牲响应。
且大文件上传若与触发指令共用连接，**队头阻塞会让远程触发变成摆设**。

> **第 24 轮：归档道已并入交付道。** 用户口径是"**每一帧都留**，且实际记录的内容要**原封不动**
> 传到电脑上"，并明确"如果交付道已经能完成这个任务，就不需要归档道"。
> 逐行核实后确认：交付道的**保真链本来就成立**（送的是**原始 Y 平面**、`lossy:false`、
> 逐帧 sha256 通过才算 `verified`、`extractY` 只去行尾填充**不改像素值**），
> 它唯一没做到"每一帧都留"的地方就是**抽帧**。抽帧一取消，两条道完全重合 ⇒ 合并。
> 归档道的一切（`kind=archive`、`archive/` 目录、`s.archives` 表、归档端点、面板归档列）**已删除**。

**为什么不能实时回传每一帧（算术，不是感觉）**：单帧 `1920×1440` 纯 Y = **2 764 800 B**；相机 **30.04 fps**
⇒ **83.0 MB/s**；而手机→PC 实测链路只有 **5.5 MB/s** ⇒ **差 15.1 倍**。
⇒ **必须"先落设备本地、边采边传、停采后排空"**。
三条由此而来的硬边界（**是地基，不是脚注**）：

1. **可录时长 = 手机可用空间 ÷ 帧率×单帧字节**：21 GB 可用空间在 83.0 MB/s 下约 **4.2 分钟**写满
   （这是按 83.0 MB/s 算的**上界**，实测写盘速率多半更低 ⇒ "能录多久"要现场读 `store_write_mbps` 反推）；
2. **写满会连带拖死交付与 App**（同一文件系统）⇒ 必须有**配额 + 熔断**，
   熔断状态**显式命名** `aborted_no_space`，且**只停写盘、不停回传**（已存下的帧照传完）。
   最坏的形态不是"中止"而是**静默停止**（状态看着还在录，其实早停了）；
3. **两个缺口必须分开命名**：`gaps_on_device`（采集期没写进本地，**只能重采**）
   vs `upload_gaps`（没传到 PC，**可以重传**）。合并成一个数，现场必然选错处置。

> 完整契约（含 A1–A7 / R1–R9 判据与反例）见 **`docs/对外接口与单一交付道.md`**。

### 4.1.1 对本机其它程序的接口面（D26）

| 接口 | 用途 | 鉴权 / 隔离 |
|---|---|---|
| `GET /api/v1/capabilities` | 先读它，拿清"有哪些接口、**三条道**各是什么（含 `knobs` / `ledger` 字段表）" | **无需 token**，**不含凭据** |

| `WS /api/v1/host/events` | 事件广播（会话开始/每帧 verified/门控/停止/收尾/**留存进度**/熔断） | token + **仅本机** |

**两个出口**（`host/status.store` 与 `sessions[].store`），且**必须是同一份**（判据 `A6d`）。

**隔离按 TCP 对端地址判**（不认 `Host` / `X-Forwarded-For`，它们可伪造）；**拿不到对端地址即判"非本机"（fail closed）**。
**既有调试入口一律不受这层门控影响**（面板、`/api/v1/sessions`、缩略图、`/api/v1/pair`）——
手机浏览器打开面板本身就是排查手册里的"5 秒判定法"。

### 5.2 采集模式：高速连拍而非录像（D3）

> **第 9 轮澄清：采集形态与交付形态合并了（D24）。**
> 第 8 轮曾把它们拆成两件事（连拍取证 / 拍照交付），代价是**交付路径与取证路径不是同一条**，
> 既有 PASS 一条也覆盖不到交付物（R22）。第 9 轮改判：**采集与交付共用同一条连续流路径** ——
> 现场按需开流（PC 触发 START/STOP）。
> ⇒ 交付物与证据**同源同格式**，R22 消解；而交付的产物**仍然是单张图像**，
> 题面「拍照回传」的交付物口径不变。⑥ 拍照路径降级为**备选**（见 D24 与 `docs/M0-路线决策.md`）。
>
> **第 24 轮再改一处**：原"交付时按 `sensor_timestamp` 从流里抽帧"的默认档（200 ms ≈ 1/6 帧）
> 已改为**不抽帧**（D27：归档道并入交付道后，交付道 = 每一帧都留）。
> 抽帧能力**保留为降载旋钮**（`plan.interval_ms > 0`），但一旦启用，账本里 `every_frame` 变 `false`
> —— **语义变化必须可见**。⚠ 因此 `stream_deliver_yuv` 的 `rev` 由 2 改为 3（见 R30/R32）。

用 `setRepeatingRequest` / `TEMPORAL_BURST` 连续采集，**每帧自带 `SENSOR_TIMESTAMP` 与完整 `CaptureResult`**。

- 定时精度**不靠** `Handler.postDelayed` / `Timer`（软定时器抖动达数十毫秒且不均匀）
- 正路：**硬件重复请求连续拍，事后按 `SENSOR_TIMESTAMP` 抽帧**，间隔由 sensor 时钟决定，精确且可知
- 代价：存储与带宽高于 H.264，发热更明显 → 需配合温度监控与轮次切分

> **⚠ 抽帧间隔会被量化到"整数个帧栅格"——请求值 ≠ 实际落点（第 15 轮实测）。**
> 抽帧规则是"取第一个与上次样本相隔 ≥ interval 的帧"，而帧只存在于栅格上，
> 所以**实际落点 = ceil(interval / 帧周期) × 帧周期**。本机帧周期 33.288 ms：
>
> | 请求 `interval_ms` | 帧栅格倍数 | **实际落点** | **实际帧率** | 想要该帧率应设 |
> |---|---|---|---|---|
> | 200（=5.0 fps） | 6.01 → 只能等第 **7** 帧 | **233.0 ms** | **4.29 fps** | **199** |
> | 500（=2.0 fps） | 15.02 → 第 16 帧 | 532.6 ms | 1.88 fps | 499 |
> | 1000（=1.0 fps） | 30.04 → 第 31 帧 | 1031.9 ms | 0.97 fps | 998 |
>
> 200 ms 那一行是关键：**6 个帧周期只有 199.7 ms，差 0.3 ms 没够上，只能等第 7 帧**
> ⇒ 请求 5 fps 实际只有 4.29 fps（少 14%），而**链路上没有任何地方会报错** ——
> 只有把"实际落点"算出来并打出来才看得见。App 现在在开流时打印这条换算
> （`抽帧落点：请求 200 ms ≈ 栅格的 6.01 倍（实测栅格 33.288 ms）⇒ 实际落在第 7 帧后`），
> 并报出 `sample_fps` / `deliver_fps` 以便与"期望值"对账。
> **定档时的取值原则：`interval_ms` 应取"帧周期的整数倍再往下取整"，
> 而不是随手填一个漂亮的十进制数。**

**帧间隔的控制点是 `SENSOR_FRAME_DURATION`，不是帧率档位。** 这一点已被实测证伪过一次：
首轮真机请求 `CONTROL_AE_TARGET_FPS_RANGE=[12,12]`（即 83.33 ms），HAL 实际按 33.29 ms 出帧，
偏差 60%。原因是 **`CONTROL_AE_MODE` 置 `OFF` 后 `CONTROL_AE_TARGET_FPS_RANGE` 会被 HAL 忽略**，
帧间隔只由 `SENSOR_FRAME_DURATION` 决定。所以要慢速拍摄就必须设 `SENSOR_FRAME_DURATION`
（受 `SENSOR_INFO_MAX_FRAME_DURATION` 上限约束，且必须大于曝光时间）。

> **后续的 4 档扫描（12/15/24/60 fps）把结论补全了，并且修正了早期的误判：**
>
> | 请求 | 实测 | 偏差 |
> |---|---|---|
> | 12 fps | 12.01 fps（83.232 ms） | +0.12% |
> | 15 fps | 15.02 fps（66.576 ms） | +0.14% |
> | 24 fps | 24.03 fps（41.616 ms） | +0.12% |
> | 60 fps | **30.04 fps（33.288 ms）** | −49.9%（不可达） |
>
> 两点结论：
> 1. **`SENSOR_FRAME_DURATION` 是生效的**，三个慢速档位全部跟随请求、且偏差量级完全一致
>    （+0.12%~+0.14%）。
>    早期"HAL 从未采纳请求"的说法只基于两个都靠近默认值的测试点，那同样是不可证伪的比对。
>    由此 **"降帧率省带宽"这条路是通的**，不必只依赖 PC 端按时间戳抽帧。
>    > **变焦（zoom）与换镜：`CONTROL_ZOOM_RATIO` 区间本机为 [0.6, 10]，但 0.6× 是切到超广角。**
> 逻辑相机融合 3 颗物理镜头（id=2 主摄 23.1mm / id=3 超广角 14.3mm / id=4 9mm≈59.4mm），
> 所以 **zoom≠1.0 的产出属于另一套内参**（不同传感器/像元/光圈，亚像素角分辨率差约 1.6 倍）。
> ⇒ 处置：**不 bump rev**（profile 是运行时输入，与 deliver_fps/曝光同类），
> 但**必须单独标定与单独取证**；每帧记 `active_physical_id` + zoom 请求/回读，
> manifest 出 `lens` 汇总（`active_physical_id_unique` / `zoom_match` / `lens_changes_peak`），
> 会话内换镜要在 App 日志告警。完整分析见 `docs/变焦（0.6x）与换镜风险.md`。

> ⚠ **"同一个量化基准 / 网格步长约 8.32 ms"这个解释已被第 4 轮否掉**（本节早先版本写的，此处更正）：
>    > 三个可达档的 `回读/请求` 比值 = 0.99878385 / 0.99863986 / 0.99878385，偏差**全部为负**
>    > （同一步长取整应正负随机）、`gcd(回读值)=1`（不存在公共网格步长）、档间差 144 ppm
>    > ⇒ 只能说到"**系统性偏低，机制未定**"。给现象起一个听起来合理的名字，
>    > 会把"未知的固定偏置"包装成"已理解的行为"，从而挡掉后续追问。
> 2. **速率上限不是"这个输出尺寸"造成的 —— 本机型在 1920×1440 / 2880×2160 / 4096×3072
>    三档上都是 30.04 fps**（第 6 轮 ⑤ 尺寸扫描实测）。所以它是该 session 模式／传感器
>    读出模式下的上限，与 ISP 缩放无关（`sensor_pixel_mode` 恒为 0 也印证了这点）。
>    要更高帧率须另试 constrained high-speed 会话（需 `REQUEST_AVAILABLE_CAPABILITIES`
>    含 `CONSTRAINED_HIGH_SPEED_VIDEO`），M0 未覆盖该路径。
>    （④ 的每个 trial 现在会记录自己的输出尺寸 —— 不记尺寸，"该档不可达"就不知道适用于哪一档。）
>
> 采集端仍应**把回读值记进 profile 并按它规划节奏**；而它可以当名义值用 ——
> **名义间隔 33288000.0 ns**（由"每 5 帧一组、28 组和恒为 166440000 ns"推出，整数精确）
> 与回读帧时长 33287995 ns 一致到 **0.150 ppm**。
>
> 顺带两条判据教训：这次 60% 的偏差是抖动判据抓不到的 —— 实测帧间隔抖动 = **0.000%**，
> 纯看离散程度会报"极好"。**"离散程度小"和"值正确"是两件事**；
> 而**"值不等"和"值不对"也是两件事**，判定控制点是否生效只能靠多档扫描。

**预热帧必须丢弃。** session 配置完成后，镜头要从初始位置机械移动到设定的焦点位置，
这期间 `LENS_STATE=MOVING`，**这些帧的几何不可信**。实测该机型是首帧为 `MOVING`、从第 1 帧起
收敛。采集协议固定丢弃前 N 帧（默认 5），逐帧记录 `LENS_STATE` 以便验证"MOVING 只出现在起始连续段"。

> **第 5 轮补充：预热帧数 5 → 10（保险，不是已证结论）。**
> ③ 的第 1 轮掉帧位置恰好落在**预热边界**上（帧 5→6，而 warmup = 5），
> 该轮唯一的缺口就在那。n = 1 不足以断言"首帧边界必然掉帧"，
> 但把预热帧加大到 10 的成本是 0.33 s（采集本就不要求实时），而收益是把这段最可疑的时期整个丢掉。
> 无论预热帧设多少，**采集协议必须逐帧校验间隔**：出现 ≥1.5× 名义值的断口即弃用该轮并重采。

### 5.3 图像格式矩阵（D4）

**先定尺寸，再定格式 —— 输出尺寸本身就是内参的一部分，必须一起冻结。**

同一个镜头，换一个输出尺寸，`fx, fy, cx, cy` 全都变。所以 profile 里必须同时锁定
`output_size`，否则"参数没变"是假的。

M0 实测的本机型尺寸账（f = 6.55 mm，像元 2.394 µm，全幅 4096×3072，
同纵横比候选共 12 个）：

| 档位 | 覆盖全幅宽 | 覆盖全幅高 | 预测 fx | 每帧 YUV | ⑤ 实测帧率 | ⑤ 实测 `skew` | 带宽 @30fps |
|---|---|---|---|---|---|---|---|
| 1920×1080（旧档，已弃用） | 100% | **75%** | ≈ 1283 px | 3.1 MB | — | 6.91 ms | — |
| **1920×1440（当前档，G22 PASS）** | 100% | **100%** | ≈ 1283 px | 4.1 MB | 30.04 fps | 9.21 ms | ≈125 MB/s |
| 2880×2160 | 100% | 100% | ≈ 1924 px | 9.3 MB | 30.04 fps | 9.21 ms | ≈280 MB/s |
| 4096×3072（4:3 全幅） | 100% | 100% | ≈ 2736 px | 18.9 MB | 30.04 fps | 9.21 ms | ≈567 MB/s |

**16:9 档位白扔 25% 垂直视场，并把横向分辨率砍掉一半**（宽度不可能超过 4096，16:9 只能从全宽裁出来）。
目标是 1–3 m 的平面时，垂直视场通常是白给的余量，不该扔；而 subpixel 定位精度大致与 `fx` 成正比。
第 5 轮已改用 **1920×1440**（同纵横比、`fx == fy`），但 **`fx` 仍是 1282.5 px** ——
改档解决的是"各向异性 + 白扔视场"，**没有**提高横向分辨率。

> **⑤ 尺寸扫描已跑完（第 6 轮跑 4:3 阶梯，第 7 轮补判别档）**，四条实测结论：
> 1. **帧率不随档位下降** —— 五档全是 **30.04 fps**。⚠ 但各档**都只请求了默认的 30 fps**，
>    所以这句只说明"各档都**达到**了 30"，**不能**推出"帧率上限与尺寸无关"
>    （第 7 轮才发现 ⑤ 原先没记请求值，现已逐档记 `target_fps`，要测上限就在帧率框填 60 再跑）。
> 2. **四条 4:3 档的 `skew` 完全相同（都是 9.21 ms）** —— 这是第 6 轮推翻"skew 随输出高度变"的
>    **直接证据**，也是"只改输出高度不必重测 skew"的依据（见 8.1）。
> 3. **16:9 档的 `skew` 是 6.91 ms**，且**判别档证明它与 crop 高度无关**（强制全阵列 crop 后不变）
>    —— 代价是白扔 25% 垂直视场，换来更短的读出时间（占帧周期 20.8% 而非 27.7%）。
> 4. **定档差异只剩 `fx`、带宽、垂直视场三项**：宽度翻倍 ⇒ `fx` 翻倍（精度同倍提升），
>    每帧字节数约翻 4 倍。4096 档在 30 fps 下是 **567 MB/s**（对回传不现实），
>    但**交付帧率可以下调** —— `SENSOR_FRAME_DURATION` 已证生效（12/15/24 fps 全部跟随请求）
>    ⇒ 2–5 fps 时降到 38–95 MB/s，落在 Wi-Fi 6 / USB 3 的可接受区。
>    **这是第 9 轮改判为连续流后仍能保 4096 档的关键：带宽的约束是「字节数 × 帧率」，而两个因子都可调。**

> **⚠️ 档位仍悬着（R19，未收口）**：现行档位被一个人为常数卡住 ——
> App 的 `CAPTURE_AREA_CAP_PX = 2048×1536 ≈ 3.15 MP`（当初只是为了避开 16:9 随手定的），
> 它把 `2880×2160` 与 `4096×3072` 都排除了。这个阈值**正在决定方案的精度上限却没有证据链**。
> **证据表现在已经齐了（含判别档）。第 9 轮 D24 定案后，"链路形态"这一维不再悬着** ——
> 链路是连续流抽帧，所以问题从「拍照档 vs 流式档」变成**「档位 × 交付帧率」的组合**：
>
> | 方案 | `fx` | 每帧 YUV | 交付帧率 | 交付带宽 | 评价 |
> |---|---|---|---|---|---|
> | **4096×3072（全幅）** | **2736 px** | 18.9 MB | 2–5 fps | 38–95 MB/s | **推荐**：精度最高、`crop.top = 0`；带宽靠降帧率压 |
> | 2880×2160 | 1923.8 px | 9.3 MB | 2–5 fps | 19–47 MB/s | 实测吞吐偏低时退到这一档；精度约为全幅的 70% |
> | ~~1920×1440 @30 fps~~ | 1282.5 px | 4.1 MB | 30 fps | 125 MB/s | **不推荐**：精度损失一半，带宽反而更高 |
> | ~~3840×2160~~ | 2565 px | 12.4 MB | — | — | **不建议**：白扔 25% 垂直视场，横向收益不如直接用 4096×3072 |
>
> ⚠️ **表中的 `MB/s` 是「每帧字节 × 帧率」算出来的，不是链路实测吞吐** ——
> 定档（R19）在拿到实测值之前**仍不能收口**。
> 判据 G24 因此**保持 INFO**：它只负责把取舍与证据边界摆明，不替方案拍板。

（两个 `fx` 是光学推算的预测值，待标定证实。它同时是免费的换镜探测器 —— 见 R13。）

| 档位 | 格式 | 单帧体量(≈4:3 40MP) | 用途 | 说明 |
|---|---|---|---|---|
| 标定档 | `RAW_SENSOR` / `RAW10` | 20–25 MB | 标定专用 | 无 ISP 处理，最可靠 |
| **原始亮度档** | `YUV_420_888` 取 Y 平面 | ≈12 MB | **高精度定位推荐** | **关键：4:2:0 只下采样色度，Y 通道未经压缩** —— 若定位只用灰度，等于完全避开 JPEG 块效应，且比 RAW 小 |
| 日常档 | `JPEG` q95–98 | 3–8 MB | 常规定位 | 注意 8×8 块效应会污染边缘梯度，影响亚像素拟合 |

> **增益点**：若下游亚像素定位只用灰度图，**YUV 的 Y 平面是比"高质 JPEG"更优的选择** —— 无压缩伪影、体量仅为 RAW 的一半。

> **代价要说清楚**：全幅 YUV 单帧约 18.9 MB（4096×3072×1.5），30 fps 就是 566 MB/s ——
> 不可能长时间落盘。⚠ **第 24 轮起默认不抽帧**，所以这条约束的处置变了：
> 现行交付档是 **1920×1440 纯 Y = 2.765 MB/帧 ⇒ 83.0 MB/s**，仍然远超链路（5.5 MB/s），
> 所以走"**先落手机本地 + 配额熔断 + 边采边传 + 停采后排空**"（D27），
> 而不是靠抽帧把负载降下来。要更长时长就用三条路：**降 `SENSOR_FRAME_DURATION`**（零丢弃，
> 但要新采集路径取证）、**降输出尺寸**（`fx` 腰斩）、**接 USB**（未取证）。
> 速率上限要实测，不能假设（判据已就位：`frames_seen` vs `store.frames_expected`）。

### 5.4 参数 Profile 与冻结（D11）

- 参数以 **profile** 形式存在（**输出尺寸**、对焦距离、变焦、曝光、ISO、格式档位等）
- 选定即**锁定**，UI **只读展示**当前实际生效值（读自 `CaptureResult`，不读自设置值）
- 修改需进入**维护模式**，且任何改动**自动生成新 `calib_id`**
- 目的：现场不会手滑改参数；历史数据不会与旧标定混淆
- **注意 profile 里记的是"回读值"而非"请求值"。** 实测 HAL 会对 `LENS_FOCUS_DISTANCE`
  做量化：请求 `0.09039752` diopt、回读 `0.09071941` diopt（偏差 0.36%）；
  请求 1.0 diopt、回读 `1.001001` diopt（0.1%）。标定与断言都必须以回读值为准，
  否则会引入一个看不见的系统偏差
- **帧时长同理，但它是"被采纳后有系统性偏置"而不是"被忽略"**：请求 33333333 ns、回读 33287995 ns。
  4 档扫描证明 HAL 会按请求变速（12/15/24 fps 全部跟随），偏差全为负、量级一致
  （约 −0.13%，`gcd(回读值)=1` 说明**不存在**公共量化网格 —— 第 4 轮已否掉"量化到达网格"这个说法）。
  **名义间隔 33288000.0 ns（周期和推出，整数精确）与回读帧时长一致到 0.150 ppm，
  所以回读值可以当名义节奏使用**；但仍有档位不可达（本机型 1920×1440 上 60 fps 会回落为 30.04 fps）
- **`rolling_shutter_skew` 必须与「输出纵横比」绑在一起记**：实测
  `skew = 2999.0 ns/行 × (读出宽度 × outH / outW)`，**与输出高度、crop 高度都无关**
  （第 6 轮用 ⑤ 尺寸扫描做受控实验定案：三档 4:3 尺寸的 `skew` 完全相同；
  第 7 轮再用判别档排除 crop 高度 —— 同 16:9 输出下 crop 2304 行 vs 3072 行，`skew` 一模一样）。
  改**输出纵横比**即失效；只改输出高度（纵横比不变）不必重测。
  **不要自己按任何 `N/H` 缩放**（详见 8.1 —— 这条规则前两版都是错的，错因是混淆变量）。
  ⚠ 未分离项：读出的"宽度"取 crop 宽还是阵列宽**没有实验分开过**（迄今两者同值），
  所以 crop 宽 ≠ 阵列宽时该公式**不可外推** —— 但采集侧读的是 HAL 报出的 `skew`，正确性不受影响
- **profile 里还应记录 `active_physical_id`**：它是"这段数据用的是哪颗物理镜头"的凭据，
  换镜即意味着内参全变（详见 R13）
- **profile 里应记录 `config_fingerprint`、`capture_path_id`、`capture_path_rev`、`app_version` 四个量，各管各的事**：
  `config_fingerprint` = "这份数据的**请求参数**是哪一套"；
  `(capture_path_id, capture_path_rev)` = "是不是**同一份采集行为**在采集"
  （`id` 说明是哪条路径：`burst_yuv_manual` / `still_yuv_single` / `still_jpeg_template`；
  `rev` 是这条路径的第几版，只在会改变采集行为的改动时 +1）；
  `app_version` = "由哪版代码产出"，**只作标识，不作判据**。判 G23 只比对前两者。
  第 5 轮把 `app_version` 掺进指纹 ⇒ 判据给出错误处置；第 6/7 轮改成"拿版本号当判据" ⇒
  **每改一行代码就让 ③ 作废、重跑又制造新的版本分裂，无限循环**（详见 R20）。
  **第 8 轮又把 `rev` 从"按 App 版本计数"改成"按路径计数"**：否则新增拍照路径这个动作本身
  就会把**其它路径**的历史证据一起作废（返工循环换个形式再来一遍）。代价是两条不同路径的
  第 1 版 `rev` 都是 1 ⇒ **必须成对比较，单看数字分不开**（详见 R20、R21）
- **profile 里还要记「路线声明」两个量**（D24）：`delivery: still | stream`（D24 定为 `stream`）
  与 `capture_format: yuv | jpeg | raw`（交给 HAL 的输出格式，D24 定为 `yuv`）。
  两者都**不是测出来的量**，而是**调用方声明**：前者决定"帧率是否阻塞交付"（G18）、
  后者决定"交付格式是否已被取证"（G27）。采集侧与判据侧都用它们 ——
  采集侧决定走单张还是重复请求；判据侧决定 G18 是否阻塞、G26/G27 怎么判。
  **声明错会让阻塞性判断整体走错，所以它必须写进结论。**
  注：**由 YUV 再软件编码成 JPEG 不算换采集路径**（编码发生在采集之后，不碰时间戳）；
  只有**让 HAL 直接输出 JPEG** 才是换路径。
- **交付档还应记录 `crop.top`（或整个 `crop_region`）**，因为它是"时间戳对的是哪一行"的唯一凭据：
  `crop.top == 0` 才能说"图像第 0 行的曝光时刻就是 `SENSOR_TIMESTAMP`"（见 8.1、G25）

### 5.5 对焦距离与景深：最容易被忽视的物理约束

"锁死内参"不只是把参数设成常量，还要**让焦平面正好落在目标上**。选错对焦点属于**静默失效**——
程序不报错、标定也能正常做，但目标整体离焦会直接削掉亚像素定位精度。

以 M0 实测的目标机型为例（f = 6.55 mm，f/1.62，像元 2.394 µm）：

| 对焦距离 | 景深范围 | 景深厚度 |
|---|---|---|
| **11.06 m（超焦距）** | 5.53 m ~ ∞ | 5.53 m 以外全清晰，**以内全部虚焦** |
| 1.0 m | 0.975 ~ 1.026 m | 约 5 cm |
| 0.5 m | 0.478 ~ 0.524 m | 约 4.6 cm |
| 0.3 m | 0.292 ~ 0.308 m | 约 1.6 cm |

两条结论：

1. **绝不能用超焦距当默认值。** 手机主摄物理焦距只有 6.5 mm，等效焦距短，超焦距落在十几米处；
   用它等于把 5 m 以内整个虚掉。必须按实际工作距离设 `LENS_FOCUS_DISTANCE = 1 / 工作距离`。
   （首轮实现就踩了这个坑：代码里直接取了 `LENS_INFO_HYPERFOCAL_DISTANCE`。）
2. **近距景深只有毫米到厘米量级。** 这带来两个硬约束：
   - 相机与目标的距离必须**机械固定**，靠手持稳定在 ±1 cm 内不现实；
   - **若工作距离本身会变，必须分档标定**：每个固定的 `LENS_FOCUS_DISTANCE` 档位对应一套内参，
     `calib_id` 与档位绑定——此时 `calib_id` 从一维变成「焦档 × 标定轮次」两维。
     这是"目标在纵深方向移动"这一场景的必然后果，不能靠"锁一个对焦距离"绕过。

> **判据化的意义**：M0 的 G16 会把景深范围算出来，与填写的实际工作距离对照，落在景深外直接判 FAIL。
> 这类问题的特征是"不报错、只失准"，所以必须由判据主动发现，而不能等精度出问题再回溯。

### 5.6 待传队列与断网容错（D13 / D14）

- 拍摄的每一帧先**写入本地持久化队列**（Room/SQLite），再尝试上传
- 网络中断不影响拍摄；恢复后按序自动补传
- **只有收到 PC 端"分片完整 + 整文件校验通过"的 ACK，才删除本地文件**
- 队列项以 `session_id + device_serial + seq` 为幂等键，重传不产生重复

## 6. PC 端服务设计

### 6.1 技术选型（D8）

**aiohttp 单进程**：同时提供 HTTP 分片上传、WebSocket 控制、静态 Web 面板。

备选（不推荐）：纯标准库 `http.server` + `websockets` 硬拼 —— 零安装，但需自行调和线程与事件循环，隐蔽 bug 风险高。**本项目的风险预算应该花在相机参数锁定的正确性上，不该花在 asyncio 共存上。**

### 6.2 发现与配对（D9）

1. 启动时**动态枚举本机网卡**取局域网地址（不硬编码）
2. 生成**规范配对码** `m0probe://pair?h=<ip>&p=<port>&t=<token>`（第 22 轮起；此前是整行 URL），
   用 `qrcode` 在终端绘制二维码，**面板顶部同时显示同一个码**（内联 SVG，零前端依赖）
3. App **扫码**即得 IP + 端口 + **会话 token**（同时充当轻量鉴权，防止同网段误连）
4. mDNS 作为"下次自动连"的便利，**不作为唯一手段**（Windows 上 mDNS 时常不稳）
5. 手输 IP 仅作调试兜底

**配对码的三条纪律**（第 22 轮定，判据见 `pc/test_server.py` 第 26 组）：

| 纪律 | 理由 |
|---|---|
| **只有一个解析器**（`PairCode.parse`）| 扫码与手输各写一份必然漂移出"扫到的能连、粘同一串连不上"，且没法自证 |
| **明确拒绝无关二维码**（`weixin://`、文章链接、`WIFI:`…）| 宽容地把公众号链接填进地址框 ⇒ 现象是"连接失败"，而用户以为"扫码没反应"，排查方向一开始就错 |
| **格式由 App 侧锚定**（PC 测试读 `PairCode.kt` 的常量与自检向量反算）| 两台设备之间的契约，两侧"各自编译通过"毫无意义 |

## 7. 通信协议

### 7.1 WebSocket（控制 + 监视道）

| 方向 | 消息 | 载荷 |
|---|---|---|
| App→PC | `hello` | `{device_serial, model, app_version, camera_caps, calib_id}` |
| PC→App | `config` | `{profile_id, profile, session_dir, token}` |
| PC→App | `start` | `{session_id, plan:{mode:"interval"\|"burst", interval_ms, count, duration_ms}}` |
| PC→App | `stop` | `{session_id, reason?, hard_fail?}` —— `reason:"start_gate_failed"` 表示门控失败被自动停流 |
| App→PC | `status` | `{state, queue_len, storage_free_mb, temperature_c, …, drain_state, delivery_alive, uploaded_frames, thumbs_enqueued, thumbs_sent, thumbs_send_failed}` —— `drain_state` 是交付收尾状态机：`drained`（**已传完**）/ `draining` / `blocked`（有积压且传不动）/ `idle`。⚠ `drained` 与 `idle` 必须分开，否则"全部回传完成"与"什么都没发生"长得一样（第 21 轮）。`delivery_alive` **与 `connected` 无关** —— 控制道断了它照样该为 `true` |
| App→PC | `thumb` | `{session_id, seq, sensor_timestamp_ns, capture_path_id, capture_path_rev, jpeg_bytes, jpeg_b64, meta}` —— **实际线上编码是文本帧 + base64**（本工程是零依赖手写 WS 客户端，只实现文本帧；480 宽 JPEG 的 base64 约 30–50 KB，1 Hz ≈ 0.4 Mbps，对控制道无压力）。语义：**可丢**（不排队、不落盘、断开即丢）、**1 Hz**、**不参与任何交付校验**；PC 端落 `thumbs/thumb_<seq>.jpg` + 旁挂同名 `.json`，只保留最新 200 张（`MAX_THUMBS`） |
| App→PC | `start_ack` | `{session_id, ok, error?, output_size, format, plan_interval_ms, zoom_requested}` —— **启动回执**（第 19 轮新增）。没有它，`start` 就只是"WS 发送成功"：相机被占用/设备瞬时故障时 PC 会一直以为在采。只在 **PC 主控**（App 收到 `start`）时回 |
| App→PC | `stop_ack` | `{session_id, running, frames_delivered, queue_len, pending_frames, will_drain, uploaded_frames, meta_missing_result}` —— **停止回执**，回答"停在哪"；停止**不丢已采数据**，队列继续补传。`will_drain:true` 是 App 的**承诺**："我不再采了，但队列传完才收工"（第 21 轮新增）—— 少了它，PC 分不清"停了＝结束了"与"停了但还在传" |
| App→PC | `delivery_done` | `{session_id, frames, sampled, queue_len, drain_seconds}` —— **交付收尾宣告**（第 21 轮新增）。App 在"采集已停 + 本地队列已空 + 本轮至少成功交付过 1 帧"**三条同时成立**时宣告。这是"收全了没有"的**唯一一手证据**：PC 侧无法从"不再有新帧"推断（链路卡顿、App 被冻结、旧会话串台都能骗过），硬推断就是让判据强于事实。`frames`（已回传）与 `sampled`（已抽帧）不等时 App 当场点名 |
| App→PC | `session_begin` | `{session_id, app_version, model, calib_id, delivery, capture_path_id, capture_path_rev, zoom_choice, zoom_effective, zoom_source}` —— **控制道显式声明"我要开始采这个会话了"**（第 18 轮新增）。会话的创建权归控制道（`start` 或本消息）；**监视道不建会话**（否则陈旧/伪造缩略图会凭空造出会话目录） |
| PC→App | `session_ack` | `{session_id}` —— PC 已建立/已知该会话 ⇒ App 监视道开闸 |
| PC→App | `thumb_rejected` | `{session_id, reason:"unknown_session", message}` —— PC 不认识该会话（典型：服务重启过）。**每个未知会话只回一次**（防刷屏）；App 收到即关闸并按上限重声明（自愈） |
| PC→App | `ack` | `{file_id, state:"partial"\|"verified"\|"failed"}` |
| App→PC | `error` | `{code, message, seq?}` |

### 7.2 HTTP（交付道，分片 + 续传）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/files/init` | 声明文件，返回 `file_id` 与 `resume_offset`（断点续传入口） |
| PUT | `/api/v1/files/{file_id}` | 分片上传，带 `Content-Range`；服务端持久化已收偏移 |
| POST | `/api/v1/files/{file_id}/complete` | 提交整文件 `sha256`，校验通过才置 `verified` 并触发 ACK |
| GET | `/api/v1/sessions` | 面板用，列出会话与进度 |
| GET | `/api/v1/pair` | **扫码配对**（第 22 轮新增）：`{pair_uri, host, port, token, url, qr_svg, note}`，供面板显示二维码、App 扫码取地址与 token。⚠ **唯一要求 `?token=` 的读接口**（它返回的正是凭据）；`/api/v1/sessions` 那类不返回凭据，维持"局域网内不鉴权"现状 |
| GET | `/ws/panel?token=…` | **面板推送通道**（浏览器用，第 21 轮新增）：`thumb` / `start_ack` / `stop_ack` / `delivery_done`。与 App 的 `/ws` **分开且不占用 `ws_clients`**（混在一条里会让"刷新页面"被记成"设备掉线"）。每个连接一个 **2 格队列 + 独立发送任务**：投递方只做非阻塞 `put_nowait`，慢面板只丢自己的帧 —— **监视道可丢，控制道不可堵** |
| GET | `/` | Web 面板页面 |

**校验策略**：分片级 CRC32（快速失败）+ 文件级 SHA-256（终检）。
**幂等键**：`session_id + device_serial + seq`。
**限速**：交付道限速，避免打满 Wi-Fi 影响控制道与监视道。

**开流门控的三态（§5.4 的落地，第 20 轮定稿）**：PC 把 profile（意图）与该会话
**第一帧带完整回读字段的帧**（事实）逐项比对：

| 结论 | 条件 | 动作 |
|---|---|---|
| `fail` | 硬键（zoom / ois / eis / 输出尺寸 / 格式）**语义不一致** | 自动下发 `stop`（`reason:"start_gate_failed"`）+ 会话标 `gate_failed` |
| `incomplete` | 硬键回读**缺席**（`unevaluable`），或还没有帧 | **只标记不停流**；不冻结，后续帧补齐后自动复判 |
| `pass` | 已知硬键全部一致 | 记档 |

两条判据纪律（细则见 `docs/开流门控与枚举比对.md`）：

- **枚举按语义比，不按字符串比**：profile 写 `"OFF"`、App 回读 `"OFF(0)"` ⇒ 判**一致**，
  并在 `checks.<键>.normalized` 与 `soft_notes` 留痕。按字符串比会把写法差异当事实差异
  ⇒ 假失败 ⇒ 停流（第 20 轮现场现象："点开始采集，画面刷一下就再也不动了"）。
- **`ois`/`eis` 是锁定配方的断言，不是可调旋钮**：App 侧请求里恒为 OFF，
  profile 里写它们只是让门控能验"HAL 是否照做"。

**溯源字段的补齐（同轮实测）**：会话由控制道 `session_begin` 先建时，
`init` 里携带的 `model / device_serial / app_version / calib_id / capture_path_*`
必须被**补进**会话档案（空则补）；若非空且与 App 声明不同 ⇒ 记 `declared_conflicts`，
**不覆盖**（中途变化说明混了两套前提，要人看见）。

**双车道的独立性问题（实测口径）**：监视道必须能在**交付道积压时照常刷新** ——
这正是把两条车道分开的理由（§4.1）。因此实现上有三条硬约束：
⓪ **会话的创建权归控制道**（`start` / `session_begin`），监视道只显示 —— 第 18 轮实测：
   闸门曾按"任何一帧 verified"开，而交付队列是**跨会话**补传的 ⇒ 旧会话的 verified 把闸门错开，
   当前会话的缩略图照样被拒；修法是**按会话键控** + 由控制道即时声明（见下方协议表）；
① 缩略图**不进交付队列**、不等待、不重传；② 发送走**独立线程**，绝不阻塞相机线程
（`WsClient.send` 是阻塞写 socket，在相机回调线程上直发会扰动"哪一帧被抽中"）；
③ PC 端处理缩略图**永不抛异常**（坏 base64 / 未知会话都只记一笔）——
监视道的问题绝不允许影响交付道的可靠性。判据见 `pc/test_server.py` 的 12/13 组。

**④ 面板推送绝不允许阻塞控制道（第 21 轮实测教训）**：面板推送是在 **App 的控制道
消息循环里**触发的（收到 `thumb` 就转发）。第一版用 `await asyncio.wait_for(send_str, 1.0)`
给发送加超时 —— **测试当场抓住**：面板假死时，超时的取消顺着 `await` 冒泡，
把 **App 的控制道连接整个掀掉**（手机端莫名"连接已断开"，服务端什么错都不打）。
现改为"每面板一个 2 格队列 + 独立发送任务"，投递方只 `put_nowait`。
更通用的教训：**在别人的消息循环里 `await`，等于把那条循环的生死交给被 await 的一方** ——
要么别 await，要么把 await 挪进自己的任务。

**⑤ 交付道的生命周期独立于控制道（同轮）**：`Uploader` 的循环条件曾经是
`while (connected)` ⇒ WS 一断（PC 重启 / WiFi 抖动 / 用户关面板 / 对端关闭）
上传线程立刻退出，队列里已抽好的帧**停在手机上不动**，而 HTTP 明明是通的
（"实时联通结束"≠"不能回传"）。现改为 `while (deliveryAlive)`：只有**用户显式断开
且队列已清空**才收工；意外掉线只标记"控制道离线"，交付道照跑。
⚠ 线程重建判据必须是 **`!uploader.isAlive`**，不是"引用非空" ——
收尾模式下线程会正常退出而引用还在，判"引用非空"⇒ 重连后永不重建 ⇒ 上传静默失效。

**"停采集 ≠ 停交付"的判据（PC 侧三态 `delivery_complete`）**：

| 值 | 依据 | 面板 |
|---|---|---|
| `true` | 收到 `delivery_done`；或 `stop_ack` 说"抽 N 帧、队列 0"且 PC `verified ≥ N`，且停后无迟到帧 | `交付收尾 ✓` |
| `false` | 有 `stop_ack` 但队列还有余量 / 停后仍有迟到帧到达 | `交付未收完` |
| `null` | 既无 `stop_ack` 也无 `delivery_done` ⇒ **PC 侧不可区分**（判不了 ≠ 已收全） | `交付收尾 判不了` |

停采集后到达的帧是**收尾的正常产物**，不是串台，但要计数（`stopped_at` +
`late_frames_after_stop`）。`stopped_at` 取 **`stop_ack`（回执）**，
不取"PC 下发 `stop` 的时刻" —— **下发的指令是意图，回执才是事实**（与门控同一条原则）。

## 8. 时间戳与精度处理

### 8.1 四个时间字段（D16）

| 字段 | 含义 | 用途 |
|---|---|---|
| `trigger_sent_ns` | PC 下发指令时刻 | 统计触发延迟分布 |
| `sensor_timestamp_ns` | **活动阵列第一行的曝光起点**（唯一权威） | 时间轴基准、帧间隔 |
| `exposure_end_ns` | 曝光结束 | 推曝光中心、卷帘补偿 |
| `wall_clock_ns` + `boot_time_ns` | 墙上时钟 + 开机映射 | 跨会话拼接时间轴 |

**时间戳语义已核对 AOSP 文档（不是推断）：**

| 事实 | 原文要点 | 对本方案的后果 |
|---|---|---|
| `SENSOR_TIMESTAMP` | "Time at start of exposure of **first row of the image sensor active array**" | 指的是**整个活动阵列**的首行，不是输出视场的首行 |
| `SENSOR_INFO_TIMESTAMP_SOURCE = REALTIME` | "in the same timebase as `SystemClock.elapsedRealtimeNanos()`" | 是 `elapsedRealtime`（含休眠），**不是** `CLOCK_MONOTONIC`。AOSP 明确提醒：把缓冲转交其他子系统时**自动补偿不存在**，应用需自行换算 |
| `SENSOR_ROLLING_SHUTTER_SKEW` | "Duration between the start of exposure for the first row ... and the start of exposure for **one past the last row** ... also equivalent to the frame readout time" | 它是**帧读出时间**，不是"末行减首行" |
| 该 skew **是否按整阵列报告** | AOSP 原文："...it's based on the full array even if a partial array is read out... if your output covers N rows of the active array of height H, scale this value by **N/H**" | ⚠️ **本机型实测与这条不符** —— 见下方"第 6/7 轮修正"。**结论：不要自己乘 `N/H`，先测出该机遵守哪条规则** |

**第 6/7 轮修正（本条已改判两次，两次都是被"看起来成比例"骗的）：**

| 版本 | 说法 | 判定 |
|---|---|---|
| 旧 | 按整个活动阵列报告，输出覆盖 `N` 行须乘 `N/H` | ✗ |
| 第 5 轮 | 是输出帧的读出时间，随**输出高度**成正比（`6397.8667 ns/行`） | ✗ |
| **第 6 轮** | 读出窗口行数 = 读出宽度 × `outH / outW`；`skew = 2999.0 ns/行 × 该行数` | ✓ |
| **第 7 轮** | 同上，但**判别档排除 crop 高度**；"读出宽度"取 crop 宽还是阵列宽**仍未分离** | ✓ |

第 5 轮只用了**一对**数据（1080 → 1440），而那一对里**输出高度与输出纵横比同时按 4/3 变化**
（16:9 → 4:3，crop 也从 2304 行放回 3072 行）—— 两个自变量一起动，一对观测分不出因果，
"成比例"被错误地归给了输出高度。第 6 轮用 ⑤ 尺寸扫描做受控实验
（**固定纵横比与 crop、只动输出高度**）才把它证伪：三档 4:3 尺寸的 `skew` **完全相同**。

第六个数据点合起来看，只有最后一列恒定：

| 输出 | crop | `skew` | `skew/输出行` | `skew/crop行` | **`skew/读出窗口行`** |
|---|---|---|---|---|---|
| 1920×1080 | 4096×3072 | 6 909 696 | 6397.87 | 2249.25 | **2999.000** |
| 1920×1440 | 4096×3072 | 9 212 928 | 6397.87 | 2999.00 | **2999.000** |
| 2880×2160 | 4096×3072 | 9 212 928 | 4265.24 | 2999.00 | **2999.000** |
| 4096×3072 | 4096×3072 | 9 212 928 | 2999.00 | 2999.00 | **2999.000** |
| 3840×2160（16:9 常规档） | 4096×2304 | 6 909 696 | 3198.93 | 2999.00 | **2999.000** |
| 3840×2160（**判别档**，强制全阵列 crop） | 4096×**3072** | **6 909 696** | 3198.93 | **2249.25** | **2999.000** |

**末两行是第 7 轮判别档的直接结论**：同一个 16:9 输出，只把 crop 高度从 2304 改成 3072，
`skew` **一模一样** ⇒ **crop 高度不是自变量**（`skew/crop行` 那列随分母变化，正是它被排除的样子）。

物理解释：读出窗口取满读出宽度、纵横比跟输出走 ⇒ 输出比 crop 更"宽"时读的行更少
（16:9 只读 `4096×9/16 = 2304` 行 = 3072 的 3/4 ⇒ 6.91 ms 而非 9.21 ms）。

现行做法：**不要自己缩放**，直接用报出的值；`skew` 与**输出纵横比**绑定记录、绑定冻结；
改**输出纵横比**必须重测，**只改输出高度（纵横比不变）不必**；
`skew/读出窗口行数` 可作为跨档交叉校验的不变量
（本机恒为 **2999.0**；两个配置算出不同行时间 ⇒ 其中一套的记录有问题）。

> **未分离项与它的边界**：这个"读出宽度"取的是 **crop 宽**还是**活动阵列宽**，从未被实验分开过
> —— 迄今所有档位的 crop 宽都等于阵列宽（4096）。要分离需一个 crop 宽 < 全阵列的档
> （4:3 输出 + 居中半宽 crop `2048×1536` ⇒ 按 crop 宽预测 4.61 ms、按阵列宽预测 9.21 ms）。
> **这不影响正确性**：采集侧读的是 HAL 报出的 `skew` 本身，公式只用于交叉校验。
> 判据在 crop 宽 ≠ 阵列宽时会明确提示"该公式不可外推"。

**由此得到的曝光时刻约定（冻结进 profile，不要现场另算）：**

```
曝光起点（读出窗口首行）   = sensor_timestamp_ns
窗口第 r 行的曝光起点      = sensor_timestamp_ns + (r / 读出窗口行数) · skew
曝光中心                  ≈ sensor_timestamp_ns + skew/2 + exposure_time_ns/2
                            // 读出窗口行数 = 读出宽度 × outH/outW；本机交付档 = 3072
```

本机型现行档（`1920×1440`，crop = 全活动阵列）实测 **`skew = 9 212 928 ns`**，占帧周期 **27.7%**，
即 **2999.0 ns/读出窗口行**（旧文档按 1080 档写的 `6 909 696 ns / 20.8%` 属旧档；
`6397.87 ns/行`、`2249 ns/行` 两套旧口径**均已作废**）。
现行 crop 就是整个活动阵列（无行偏移），所以"某一图像行对应什么时刻"这件事不再有未定项 ——
一旦 `aspectSafeCrop` 因纵横比不符而收紧 crop，首行偏移按 `行偏移 × 2999.0 ns` 直接算即可。

### 8.1.1 参考行偏置与单帧固有不确定度（**第 8 轮新增**）

**交付形态是「一次交一张」**（第 9 轮 D24 定为「从连续流抽帧交付单张」，第 8 轮的 D23 定为「拍照」）——
不论哪一种，本节要补的两个量都一样：它们**由「单张交付」这个形态决定，与走哪条采集路线无关**。

**（一）参考行偏置 —— 一个静默的常量。**

`SENSOR_TIMESTAMP` 的语义是**活动阵列首行**的曝光起点（AOSP 原文见上表）。
"活动阵列首行"**不等于**"图像第 0 行"：crop 一旦带纵向偏移，两者差 `crop.top` 行。

| 配置 | `crop.top` | 偏置 = `crop.top × 2999.0 ns` |
|---|---|---|
| 全幅 4:3（`1920×1440`、`2880×2160`、`4096×3072`） | **0** | **0 ns** |
| 16:9 经 `aspectSafeCrop` 收紧（`crop = (0,384,4096,2304)`） | **384** | **1 151 616 ns ≈ 1.15 ms** |

**为什么必须单独记这个量**：它**静默**。画面正常、时间戳单调递增、帧间隔抖动为 0 ——
G10 / G15 / G20 / G22 **一个都不报警**，它只是让整幅图统一偏 1.15 ms。
只要目标在动，这就是和"帧率不准"同量级的误差，却没有任何自检能发现。
⇒ **交付档必须 `crop.top == 0`**（本机 `4096×3072` 满足）；否则必须在离线端显式补偿。

**（二）单帧固有不确定度 —— 多张平均也消不掉。**

卷帘快门意味着同一张图里不同行是**不同时刻**曝光的。所以**单张**照片能给出的时间信息
本质上是一个**时间窗**，而不是一个时刻：

| 量 | 本机实测 | 说明 |
|---|---|---|
| 整幅读出时间 = `skew` | **9 213 ms** | 图像内部的时间跨度（首行到末行） |
| 帧周期（回读帧时长） | 33.288 ms | |
| 占比 | **27.7%** | 一帧里近三成时间在逐行读出 |
| 窗中心的不确定度 | **± 4.61 ms** | = `skew / 2` |

> **这是本方案时间精度上的主导项，而它与"时间基准不准"无关。**
>
> | 误差源 | 量级 | 类别 |
> |---|---|---|
> | 帧率/时间基漂移 | 3.06 ppm × 33.288 ms ≈ **101.9 ns** | 累积型，多帧可回归压掉 |
> | 卷帘读出（单帧） | **9.21 ms**（±4.61 ms） | 固有型，**多张平均消不掉** |
> | 参考行偏置（16:9 档） | 1.15 ms | 静默常量，可显式补偿 |
>
> 三者差**四个数量级**。所以"确保时间戳准确"这件事的**主战场是卷帘读出，不是时间基**：
> 把时间基做到 ns 级对精度毫无帮助，真正决定上限的是"这一帧跨越了 9.21 ms，目标在这段时间里动了多少"。
>
> **第 9 轮更正一处过强的说法："多帧能把 9.21 ms 摊薄"不成立。**
> 帧与帧之间**并不错开相位**：第 k 帧的第 r 行曝光于 `t0 + k·33.288 ms + r·2999 ns`，相位固定。
> 所以多帧给的是**多个时刻的样本**（可用于运动建模与交叉校验），
> 但**不会缩小单帧内部那 9.21 ms 的时间跨度**。
> ⇒ 9.21 ms 是**单帧固有**的，与"交付几张"无关，也**与走哪条路线无关**；
> 第 8 轮把它记成"拍照这个决定最实质的代价"同样不准确 ——
> 它是**「一次只用一张图」这个用法的代价**，而交付张数是可调的产品选择，不是路线的强制后果。

**处置**：`skew` 与 `crop.top`（或整个 crop region）都要**冻结进 profile**；
采集端逐张记录，离线端按 `行号 × 2999.0 ns` 重建行内时刻。
判据 **G25** 只负责**量化**这两项、并把 `crop.top ≠ 0` 标成 WARN（给出偏置量供补偿）——
它**不判** 9.21 ms 是否"够小"：那取决于目标的运动速度，是方案参数，不是机型属性。

**（三）EXIF 不能作时间源 —— 第 10 轮有了实测数字。**

交付格式是 JPEG（若走 R22 那条路），JPEG 天然带一个"看起来像时间戳"的字段 `DateTimeOriginal`。
本机实测（8 张交付档，6 张解析出 EXIF）：

| 量 | 实测 | 说明 |
|---|---|---|
| `SubSecTimeOriginal` 位数 | **6 位** | 分辨率 1 µs，形式上"够细" |
| EXIF 时刻 − `SENSOR_TIMESTAMP` | **+92.8 ~ +135.0 ms** | 系统偏置约 **+95 ms**（写入文件在曝光+读出+编码之后） |
| 上式的抖动 | **极差 42.3 ms**（std 14.1 ms） | 比单帧固有不确定度 9.21 ms **还大 4.5 倍** |

⇒ 两点结论，都要写进交付协议：
1. **EXIF 的父字段是系统墙钟**（`currentTimeMillis` 域），与 `SENSOR_TIMESTAMP`（REALTIME 域）
   之间隔着"墙钟校正 + 管线延迟"。**它的偏差不是常数，抖动 42 ms 比我们要解决的所有时间基问题
   都大 4 个数量级**。EXIF 只作旁证与交叉核对。
2. 亚秒位数"够细"**不等于**时刻准确 —— 这与 G15 那条教训同源（"离散程度完美"≠"值正确"）。

**（四）交付物必须能核验「这张图就是这个时间戳那张」（第 10 轮新增）。**

交付物是**一对**：图像 + 时间戳。而图像走 `ImageReader` 回调、`CaptureResult` 走
`onCaptureCompleted`，这是**两条独立通路，到达顺序不保证**。
第 10 轮之前 App 用的是"回调时刻最后拿到的那张图"（单个变量 + 用完置空），它有两个
**看不出问题的**失败模式：

- **图晚到 → 被记到下一张结果头上。** 图是真的、时间戳也是真的，只是两者错配，
  报告里**任何字段都不会自相矛盾**；
- **图没到位 → 只留一个 `null`**，无法区分"管线根本没给图"与"读字节失败"。

第 10 轮实测正好撞上第二种：**交付档 7 张有效张里有 1 张没有图像字节**（`jpeg=null`），
而当时的报告**说不清原因**。⇒ 交付协议与诊断报告都必须让这件事可判：

| 要求 | 理由 | 落地 |
|---|---|---|
| 逐张记录**图像自带的时间戳**（`Image.timestamp`，与 `SENSOR_TIMESTAMP` 同一时间基） | 它是唯一能把"图"与"结果"钉在一起的量 | 1.8.1 起 `stats.image_pairing`：`images_matched` / `images_missing` / `images_surplus` / `acquire_null` / `read_errors` |
| 配不上要**显式计数**，不能只留 `null` | `null` 是多义的：没图 / 读失败 / 配错都长一样 | 同上；"有多余的图"意味着**有结果拿了别的图**，比少图更严重 |
| 交付链路必须有 **ACK + 重传** | 单张交付丢一张就是丢一张，没有帧间冗余可用 | 见 M2 幂等/ACK 设计 |
| 汇总与逐张数据要**互校** | 两者由同一份代码写出，但一个是累加计数、一个是逐条记录；打架时最容易静默通过 | 判据 G26 交叉核对 `images_matched` 与逐张带字节数 |

### 8.2 四条关键论断

1. **触发时刻 ≠ 曝光时刻。** PC 下发到传感器真正曝光，中间隔着网络往返 + Android 请求管线 + sensor 启动，抖动可达数十毫秒且每次不同。**唯一可信基准是 `SENSOR_TIMESTAMP`**，绝不能拿"PC 发送时刻"当曝光时刻。
2. **跨设备时钟同步本方案不做**（D17）。手机纳秒是自开机单调时钟，与 PC 墙上时钟有未知偏移；因用户明确"时间戳只以手机为准、用于离线处理"，此问题在当前范围内不存在。**但 R5 指出：一旦要与机器人数据对齐，它会回来。** 另外，即便不做同步，`wall_clock_ns` 的换算也应写成 `wall_ns = currentTimeMillis()·10⁶ − elapsedRealtimeNanos()`，且按 AOSP 提示**每次活跃会话测一次偏移**即可（`elapsedRealtimeNanos` 与 `uptimeMillis` 只在休眠期间分歧）。
3. **卷帘快门（D18）。** 手机 CMOS 均为卷帘，一帧内首行与末行曝光时刻差数毫秒至十余毫秒
（本机型现行档 **9.21 ms**，占帧周期 27.7%）。目标"大部分静态、少数小目标会动"，偏差不易察觉。
**单张交付时，这 9.21 ms 就是该帧时间戳的固有不确定度（±4.61 ms），且多张平均消不掉**（见 8.1.1）。
它与交付路线无关，**是「一次只用一张图」这个用法的固有代价**。

4. **时间戳的"来源路径"本身是元数据的一部分。** 每一张交付的图都必须能回答
"这个 `sensor_timestamp_ns` 来自哪条采集路径（模板/格式/调度方式）" ——
因为不同路径的语义**可能不同**（ZSL 旧帧、多帧合成都会改变它的含义，见 R22）。
所以 `(capture_path_id, capture_path_rev)` 与 `sensor_timestamp_ns` **必须一起回传**，
不能只回传时间戳而丢掉路径标识。**没有路径标识的时间戳，事后无法判断它是否可比。**

   第 10 轮补第 5 项、同一条道理再往上一层：

5. **时间戳还要能回答"它来自哪台机器"。** 全部判据都在回答"**这台机器**能不能当测量相机"，
   而配置指纹与采集路径**证明不了**这一点 —— 两台机器的这两项可以完全一致，
   而 `fx` / 读出时间 / 卷帘行为都不同。第 10 轮之前，②③④⑤⑥ 的报告里**没有任何字段**
   记录设备身份（只有①能力报告有），于是"两台机器的报告混在一起"这种错误所有判据都看不见。
   ⇒ 报告自 1.8.1 起自带 `device`（manufacturer / model / device / `build_fingerprint` / sdk）；
   回传的帧级元数据同样要带设备标识。**理由与 §8.2.4 完全相同：没有来源标识的测量，事后无法判断它是否可比。**

### 8.3 卷帘快门的处理原则

**不现在把补偿算进去，而是把补偿所需的原始量全部留下来。**

- 记录 `sensor_timestamp_ns` / `exposure_end_ns` / 帧时长 / 读出时间（`skew`）
  **+ 输出纵横比 + `crop_region`**（`skew` 与这两者绑定，改它们即失效 —— 与输出高度无关；
  `crop_region` 同时给出参考行偏置，见 8.1.1）
- **每条元数据必须带 `(capture_path_id, capture_path_rev)`**：时间戳的语义可能与路径绑定
  （ZSL / 多帧合成会改写它），没有路径标识就无法判断两张图的时间戳是否可比（见 R22）
- **不要从 EXIF 读时间**：现行交付格式是 `YUV_420_888`（D24），本就不带 EXIF；一旦用到 JPEG 档，
  `DateTimeOriginal` 是系统墙钟、亚秒位数由厂商决定 ⇒ **仍不可作时间源**。
  时间只认 `sensor_timestamp_ns`（REALTIME 域）。EXIF 只作旁证，判据 G26 会实测其亚秒位数
- 判据是"**数据够不够重建**"，而非"模型现在完不完整"
- 好处：无需为一个小目标的运动重采整轮实验，离线阶段按需补算

**时间戳质量已实测（M0 G20，逐帧原始序列重算）**：单调递增；间隔只取 3 个值
`33 287 916 / 33 287 917 / 33 288 125 ns`，且 `d[i] == d[i+5]` 在 **139/139** 处成立 ——
它是**严格周期 5 帧的确定性拍频**（相位由启动时刻决定），**不是随机噪声**：
每帧偏差可复现、可精确预测。因此主判据是"**每个完整体周期之和是否恒定**"：
实测 28 个完整个周期全部 = **166 440 000 ns**（极差 0）⇒ **零漂移**；
由此推出的**名义间隔 = 33 288 000.0 ns**（整数精确），与回读帧时长 33 287 995 ns 相差
**5 ns = 0.150 ppm**。

> 上一版写的"抖动 3.06 ppm / 累积偏离终值 = 0"两个说法都已作废：
> 前者把确定性图案说成了噪声；后者是**同义反复**（`mean` 取自同一窗口，`cum[-1] ≡ 0`）。

**结论：帧间相对时间可用于运动建模；绝对时刻不在本方案范围内；
名义节奏可以直接用回读帧时长（一致到 0.150 ppm）。**

## 9. 标定指纹（calib_id）机制

**问题**：流程必然是「标定 → 采集 → 发现漂移 → 重新标定 → 再采集」。若无指纹，新旧数据混算会让**定位静默出错而看不出来**。

**机制**：

1. 每帧记录拍摄时生效的 `calib_id`
2. PC 端按 `calib_id` 取对应内参
3. **会话级强制断言**：同一批数据必须同属一次标定，不满足则**拒绝处理并告警**
4. 任何相机参数改动（含在维护模式下）**自动生成新 `calib_id`**
5. 若工作距离会变（见 5.5），`calib_id` 还需绑定**焦档**：内参表按 `(焦档, calib_id)` 索引

> 这把"参数断言"从**帧级**提升到了**会话级**，是本方案可信度的支柱。
