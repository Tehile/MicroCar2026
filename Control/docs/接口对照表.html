Control 接口对照表（Control 端点 ↔ 上游方法）

这份表的存在意义只有一个：防漂移。

上游三个仓库各有自己的取证体系，我们不碰它们的源码（判据 I9）。代价是：上游哪天把 HostLink.ledger() 改名了，Control 会在运行时才炸，而且只在现场那一页才炸。 所以这里把「每个端点是靠哪个上游方法撑起来的」写成一张能被机器读的表， 并用 python tools/check_iface_table.py 一条命令同时校验三件事：

  1. 表里写到的每个上游符号真的存在（改名/删除立刻现形）；
  2. routes.py 里注册的每个端点都在表里有记录（新增端点忘了登记会报错）；
  3. docs/上位机整合设计方案.md 的附录 A 与这份表一致（只有指向，不重复内容）。

改上游之后先跑它，不要靠眼睛。

上游路径（相对 Control/，见 config.yaml 的 paths）：

B PhoneCamera ../PhoneCamera/pc（模块 hostlink）

「上游调用」列里的名字是可机读的：类.方法 或模块级函数名。 — 表示这一步是 Control 自己的逻辑（读缓存、编会话目录、做统计），不经过上游。

1d. 统一帧遥测与迷宫状态机（模块 A，上游 2.0.0）

⚠️ 本节的形态是 2.0.0「传输模式重构」之后的。它取代了 1.5.0 的「组测发送 SNAP」 与 1.5.5 的「三通道迷宫回传」。上游明确"协议整体替换、不做兼容层"，所以本层 没有 _v2 端点、没有弃用期：旧端点一律 404（判据 I22/I23 负向验证）。

只有一条流：TYPE_UNIFIED（53 B = 8 B 开销 + 45 B 载荷）/ 拉取模式 / 解码后 39 个扁平通道。四路红外ADC 与 mm 双传（非线性映射，上位机不便复算）、 电池给 mV（线性映射且分压标定在设备端，所以不传 ADC）、完整迷宫状态机就在帧里。 ⚠️ 帧率由上位机的拉取节奏决定（真机 4.4~6.5 Hz），UNIFIED_HZ = 217.0 只是 协议常量、不代表实际帧率 —— 见下方 2.1.0 说明。

为什么删除 SNAP / SCOPE（上游设计方案 §6）：两者存在的唯一理由是"物理速率不足" （旧链路 152 B/s，只能"实时看状态 / 停车拉数据"）。改自时钟发送后，每一帧都是全量快照， "实验期间的数据"本来就在主机内存里 ⇒ SNAP 的"静默一问一答"与 SCOPE 的"停车后整块回传" 都不再需要。代价是失去"零常驻带宽地看一个瞬时值"—— 而那个代价只剩一种付费方式了。

迷宫状态机回传（LESSON_Blind8）：观测层整个放在固件 HARDWARE/link.c， 不在 maze/state/lesson/motion 里插一行钩子 —— 只读已公开的 mazeState / wallSns / motionCtrl.task，所以"回传的状态"与"代码里的状态"同源，且关掉本模块行为逐字不变。 状态量全在统一帧里；"它刚才识别到了什么"由主机差分相邻帧得到（MAZE EV 已删除）。

2.1.0 的追加变化（拉取模式）：STREAM ON/STREAM OFF 已删除， 新增 TELEM（no_retry，超时 3 s）—— PC → TELEM，设备回一帧 + 时间锚。 固件不再自时钟发帧（v2.0 那套在真机上把蓝牙模块缓冲灌死了，见设计方案 §11.10）。 上位机侧由 host.api.stream.PullRequester 严格停等驱动：在途恒 1， 收到应答才发下一条 ⇒ 可达帧率 = 1/RTT（真机 4.4~6.5 Hz），不是软件限速。 mc.stream.on/off 的方法名与签名都没变，只换了语义 —— 所以本层几乎零代码改动。 ⚠️ UNIFIED_HZ = 217.0 被上游降级为"只用于环形缓冲容量估算 + 缺省显示"， 不代表实际帧率；实际帧率一律用 TelemetryAPI.hz()（按到达间隔实算）。

2.1.1 / 2.1.2 / 2.2.0 / 2.2.1 的追加变化（真机事故驱动，命令 22 → 24）： 帧格式、39 通道、事件模型零改动；变的都是"能不能把车收回来"（见设计方案 §11.12）。 新增返回状态 ERR_LOWBATT（上位机产生、不来自设备，data.blocked=True，带实测 battMv）。 maze.run 的失败语义因此有三态：ERR_LOWBATT（充电/换电）/ ERR_ESTOP（先解锁急停）/ ERR_BUSY（先收车）—— 处置完全不同，不许混成一句。 ⚠️ resume() 只在"原本在跑"时才恢复 ⇒ 本层 /mouse/stream 的开关语义不受影响 （I22 的负向"关掉拉取后帧不许再涨"仍然成立，已复跑确认）。

7. 明确不映射到上游的端点（本层自研）

这些没有对应的上游方法，理由写在「说明」里 —— 列出来是为了防止有人误以为漏了：

camera/offline/*、camera/import、camera/base 无手机演练与现场改 IP 都需要，上游不提供

8. 校验

python tools/check_iface_table.py          # 校验本表 ↔ 上游 ↔ routes.py 三者一致
