电脑鼠整合上位机（Control）设计方案

目标：把三个既有模块整合成一个界面的上位机，用电脑完成全部控制、数据回传与数据收集。 边界：本文只做接口层整合，不改三个模块的内部实现。 形态：Web 上位机（Python 后端 + 浏览器前端）。 状态：设计方案（未实现）。日期：2026-09-27。

总纲（冻结）：设计宗旨与布局方案

本节是全文的上位约束。用户已确认，此后所有任务不得改变这里的方向。 与本节冲突的改动一律视为方案变更，须先回到本节重新决策，再动代码。 改版记录 2026-10-04（一）：布局由"主区固定两栏并排"改为"子系统子页面" （用户要求"把可调整的子系统分开、点细分按钮进子页面"）。 改版记录 2026-10-04（二）：再由"子系统子页面"改为"单页分段"—— 去掉顶部的子系统选项卡，四个子系统竖排在同一个滚动页里，用 分割线与类别名称隔开（用户要求"大类作为分割线名称排布在同一页面"）。 改版记录 2026-10-04（三）：由"单页分段"定稿为"入口页只做导航 + 模块界面整屏"—— 入口页保留（二）的竖排分组与类别名称，但只放卡片、不放控件与工作区；点卡片 单开一个整屏模块界面做那一个实验，点【← 返回】回入口（用户要求"最开始的界面 只作为子功能的导航入口，点击子功能的卡片后需要单开一个新界面实现功能， 否则会显得特别乱"）。三条宗旨不变；不设选项卡、不切页（换界面 ≠ 换页， 也不开新浏览器标签）。 改版记录 2026-10-04（四）：布局规则不变（仍是"入口页只做导航 + 模块界面整屏"）， 只在「小车控制」下新增两个模块卡片：分组测量（上游 1.5.0 的组测发送 SNAP， 含四路红外与电源）与 实验 8 · 无记忆走迷宫（上游 1.5.5 的迷宫状态机回传）。 用户要求："全体参数获取中新增了组测发送，包括新增的红外和电池相关的数据…… 实验 8 无记忆走迷宫……应该放到小车控制大类下一个新增的小类之中"。 同一次变更里，参数分组由"两套"变为四组（生产标定 / 课程调参 / 红外测量 / 电源监控）， 且 Flash 页号随固件分区调整由 99/100 变为 115/116。

改版记录 2026-10-05（六）：上游 RemoteControl 发布 2.0.0「传输模式重构」—— 这是一次协议整体替换，不做兼容层。对「小车控制」的界面影响有两条： ① 两个取参数的子功能合并：分组测量并入实时参数。理由是上游把 SNAP（组测发送）与 SCOPE（1 kHz 录制）整套删除，测量量只剩一条统一帧 （TYPE_UNIFIED，53 B / ≈217 Hz / 39 个扁平通道，四路红外 ADC+mm 双传、电池 mV、 完整迷宫状态机都在里面）—— 于是"实时参数"与"分组测量"读的东西变成了同一样， 两页并一页（用户要求："功能上两个获取参数的子功能合并"）。 ⇒ 「小车控制」的模块由五张卡片变为四张：实时参数 / 运动控制 / 校准例程 / 实验 8 · 无记忆走迷宫。布局规则不变（仍是"入口页只做导航 + 模块界面整屏"）。 ② 其余功能不变、实现方法变：实验 8 的"事件流"改由主机差分相邻帧取得 （MAZE EV 已删除）、EVQ 改从帧 flags bit7 读；校准例程 的 CAL 由 "开局后续"改为请求-响应；分组测量的 SNAP 点查与 实时参数的 RATE 档位 都没有对应物了（RATE/VER 一并删除，VER 并入 PING）。 协议事实（总纲只记这一句，细节见 §1.2 / §11.9）：上行只剩"持续数据流（统一帧）+ 异常事件（STOPPED <reason> #n / ESTOP TRIP #n）"；下行一律请求-响应； 上位机能算的不传。被删除的旧命令/机制清单：SNAP / SCOPE / RATE / VER 已全部删除 （MAZE EV、MAZE RST 同时删除）。

改版记录 2026-10-05（七）：上游同日再发 2.1.0「拉取模式」，推翻了 v2.0 的自时钟发送。 原因是真机实测把假设证伪了：这条链路（CH340 + 蓝牙透传）端到端只有 ≈100~200 B/s， 而 v2.0 的自时钟全速推 ≈4.3 KB/s（超约 20 倍）⇒ 蓝牙模块内部缓冲被灌满后停止转发、 且不会自行恢复（须断电）。现场现象辨识度极高：PING/ARM/GET ALL/MAP DUMP 这些 小的、一次性的突发全部正常，而一经 STREAM ON 开始持续流就立刻 0 字节，之后连 PING 都不答。 修法：把发送节奏交给上位机 —— 删除 STREAM ON/STREAM OFF，新增 TELEM： PC → TELEM，设备回一帧统一帧 + ACK <seq> OK <upMs>；PC 不发请求，固件一个字节都不发， 于是"停发 → 缓冲自然排空 → 无需断电即可自愈"。 协议主线原则不变（单流 / 请求-响应 / 上位机能算的不传），帧格式零改动 （仍 53 B / TYPE=0x0A / 39 个扁平通道）⇒ 本层的解析面、参数面、迷路面都不用动。 ⇒ 对界面的影响只有一条，但很显眼：帧率不再是 217 Hz。 可达帧率 = 1/RTT， 真机 4.4~6.5 Hz（协议常量 UNIFIED_HZ = 217.0 被上游降级为"只用于环形缓冲容量估算"）。 所以界面上任何 "≈217 Hz" 的说法都必须删掉（那是差约 50 倍的谎）。 布局规则不变（仍是"入口页只做导航 + 模块界面整屏"）；模块清单也不变（仍是四张卡）。 细节见 §11.10。

改版记录 2026-10-05（八）：只改「实验 8 · 无记忆走迷宫」这一个模块的界面与记录能力， 其余模块与布局规则全部不变（仍是"入口页只做导航 + 模块界面整屏"，仍是四张卡）。 起因是现场要"看它怎么想、怎么搜、错在哪"，而旧版只有一堆并列的数字。 ① 三栏：左 = 状态机 + 关键传感器实时读数（转速 / 四路红外 / 陀螺 / 位置）； 中 = 重构示意（按朝向把三路墙位转到绝对方向后累积出来的"它眼里的迷宫"： 搜过哪些格、已知哪里有墙、小车在哪、朝向如何、走过什么轨迹）； 右 = 决策与状态迁移时间线（时间正序、可滚动、可点选）。 ② 记录：点【发车】自动开始，检测到停止（或人工兜底）自动收尾，把 从发车到停止的全量 39 通道每帧 + 迁移序列 + 上行事件 + 完整性统计写成一份 JSON。 ③ 复盘：可导入记录文件，用时间游标驱动三栏联动重放 —— 与实时态用同一套渲染， 只是数据来源从"活帧"换成"游标时刻的帧"。 ⚠️ 两处如实标注的局限：固件没有"迷宫结束"事件 ⇒ 自动收尾是弱判据， 必须有【停止并保存】人工兜底（模拟器上尤其明显，见 §11.9）；记录器订阅的是上游 Event.TELEMETRY（每帧 emit），不依赖浏览器订阅，否则"没人看就一份都记不下来"。 细节见 §11.11。

改版记录 2026-10-05（九）：上游同日连发 2.1.1 / 2.1.2 / 2.2.0 / 2.2.1 四个版本， 全部来自那批真机事故。这一轮的性质与前几轮都不同：它推翻了本层写下的一条结论， 并暴露了本层一个一直没红过的真缺陷。

① 被推翻的结论："没有'停止跑迷宫'"。 以前本层到处写着"MAZE RUN 之后只能复位或重连"（MAZE STOP 不存在）。现在它存在了： 2.1.1 新增 MAZE STOP，停车 + 复位发车状态 + 解锁急停 ⇒ 不必断电即可再次发车。 ⚠️ 但车在运动时它不可靠（只置"请退出"标志，而标志检查在 while(1) 顶部， 主循环有 30 余处非协作式阻塞等待）⇒ 2.2.0 的 MCU RESET（整机软复位）才是可靠收车手段。 界面上因此多了【收车】与【救援】两个按钮。

② 新增的低电硬闸：ERR_LOWBATT。 事故链是"低电 ⇒ 红外发射管变暗 ⇒ 墙检测失效 ⇒ 电机一直转、对红外不敏感 ⇒ 强行断电"， 而固件对低电没有任何保护动作。修法是在登记表层加 precheck（maze.run 上， 阈值 LAUNCH_MIN_MV = 7000 mV）—— 放在那里是因为脚本写 send_cmd("maze.run") 也绕不开。 本层做的事：① 把阈值与三态判定端到端如实转达（附实测电压与可照做清单）； ② 在界面上提前可见（/mouse/launch_precheck，纯读帧）。

③ 修掉本层一个"从没红过的真缺陷"：三个动作端点一直是 404。 /mouse/tare、/mouse/stop、/mouse/estop（急停！） 三个端点把线上文本 （"TARE"/"STOP"/"ESTOP"）当成了上游 send_cmd() 要的登记名（全小写） ⇒ 上游 COMMANDS["ESTOP"] 直接 KeyError ⇒ 三个端点一直是 404。 而没有任何判据调过它们，所以从来没红过 —— 直到这一轮要接"急停锁存中发车回 ERR_ESTOP"这条路径才发现（§11.12）。 ⇒ 纪律推广："一道从没红过的闸不算闸"要用在「按钮」上，不只是用在判据上。 现在每个动作按钮都有一条端到端判据走一遍（I28）。

④ 帧率/协议/帧格式：零改动。 命令数 22 → 24（+maze.stop、+system.reset）， 帧类型仍 2 种，39 通道不变 ⇒ 解析面、参数面、记录与复盘格式都不用动。 布局规则与模块清单也不变（仍是入口页 + 整屏模块，仍是四张卡）。 细节见 §11.12。

改版记录 2026-10-06（十）：只改「实验 8」这一个模块，其余模块与布局规则全不变 （仍是入口页 + 整屏模块，仍是四张卡）。这一轮是用现场视角重做它的右栏：

① 时间线进度条放到右栏最顶上，与"运行状态"同一行。它驱动的不只是下面那条时间线， 还有左/中两栏的"此刻" —— 放在别处（比如整页顶部）会让人以为它只管某一部分。

② 运行状态醒目化，且停车后数据仍实时。 状态胶囊三态：● 运行中（绿）/ ■ 已停止（灰）/ — 判不了（虚边框）。 ⚠️ 判据取 mazeTask >= 2（SEARCH 起）而不是"速度非零" —— 速度在换段瞬间会过零， 拿它当"在跑"会让胶囊一秒闪好几次；任务机是状态，不是瞬时量。 停车后三栏继续跟着帧刷新**（"数据仍实时"），只是胶囊变成"已停止"。

③ 进入 / 退出回放（按键 + 拖进度条两种入口）。 拖进度条自动进入回放：现场看到一屏数据想回看刚才那一刻，第一反应就是去拖它。 数据源优先取正在跑的这段（/maze/record/live，内存快照，不落盘、不打断记录）， 没有才用最近一条已保存的记录。 ⚠️ 进度条的量程是时间（ms）而不是帧下标：帧在时间上不均匀（真机 4.4~6.5 Hz，还会丢帧）， 用帧下标当量程会让"拖到中间"在时间上偏早或偏晚。 回放态下左/中显示那一刻、右栏定位到那一刻（高亮当前条并滚进视野）。

④ 右栏的"决策"从 2 类扩到 8 类（这是本轮最主要的工作）。 以前只有"任务迁移 + 上行事件"，基本就是发车/停止两条。现在有： TASK 任务迁移 / ROAD 路口识别（直道·左弯·右弯·T型·十字·死路）/ TURN 转向 / STRAIGHT 直行 / JUNC 岔路口（栈深度变化）/ CELL 进入新格 / HEAD 朝向改变 / GOAL 到达终点区。 ⚠️ 这些必须由主机差分：上游 v1.5.5 曾有一条 MAZE EV 事件流，v2.0 整条删了 （理由同 SNAP/SCOPE：状态量已全在统一帧里）；上游自己只在 task_changes() 里 补了任务机一种差分，其余要调用方来。判据与上游依据逐条写在 §11.13 / maze_rec.py。

⑤ 顺带修一处"点了没反应"的按钮：右栏原来那个【清空显示】是给"前端自己攒的决策" 用的，而决策改成后端产出后它就没有作用了 ⇒ 改名成【刷新】（它真正做的事）。 一个点了没反应的按钮比没有按钮更坏 —— 现场会以为它坏了，或以为"清空成功了"。

改版记录 2026-10-07（十一）：只改「实验 8」里"回放"这一层，界面布局与其余模块 全不变（仍是入口页 + 整屏模块，仍是四张卡）。这一轮修的是现场一眼就看出的毛病： 回放读到的那份"事件/决策树"，与退出回放后的实时那条对不上。

① 根因：发车只把"时间零点"往前挪，没有换掉"这一段"。 右栏实时那条读的是记录器内存里的常驻决策环；回放那条是从内存快照 （/maze/record/live）或落盘文件里重新差分出来的。发车时旧实现只做了一件事 —— 把环的零点挪到发车时刻 —— 于是上一段与发车前的决策原地留在环里，相对新零点 全成了负时间。实测：段 1 收尾后环 151 条；段 2 发车后环 303 条， 其中 151 条的 t_ms 是负的（从 −14180 起）。快照里没有这些"史前"条目 ⇒ 两条来路必然对不上。

② 修法：发车 = 开新纪元。 start() 改成走 _reset_epoch()： 清两个常驻环 + 换一个全新的差分器 + 零点交给"发车后的第一帧"，并把旧的那一套 （差分器 / 决策环 / 零点 / 零点语义 / 事件环）整体存进 _dec_stash。 发车被拒时 restore_epoch() 再整套放回去 —— 一次没开成的发车 不该把右栏正在看的那一段抹成空的。修完实测：实时环 174 条 ≡ 快照 174 条 ≡ 落盘 174 条，逐条数值相等（不同 0 条）。

③ 回滚的判据从"收到几帧"改成"这一次是不是新开的段"。 start() 的应答多一个 fresh_epoch，路由只在它为真时才收尾 + 回滚。原来写的是"frames == 0 才收掉"， 那是个看运气的判据：start() 之后命令往返要 1~3 s，期间待机帧照样进来 ⇒ 同一段代码有时收有时不收，"收不收"还决定要不要回滚 ⇒ 界面表现时好时坏。

④ 上行事件并进常驻环（_ev_ring，容量 500），与决策共用同一个零点： 时间线上"事件落在第几帧旁边"不再由前端按 t0_pc_ms 自己换算 —— 后端能算的，不要前端自己攒。前端那个模块级 evs 数组随之删掉。 细节、实测数据与判据见 §11.14。

改版记录 2026-10-04（五）：「小车控制」下的 ① 参数回传 改为 ① 实时参数。 内容上把遥测的实时读数并到一处：左/右里程等累加量（mid 段）与四路红外 + 电压 （slow 段）放在同一张读数表里 —— 两段本来就在同一条 WS 消息（mouse.telemetry） 里，所以这次没有新增任何传输，只是同屏呈现（用户要求："红外/电压已同在 telemetry.latest() 中体现，将其集成在参数回传中，和已经在累加量中的那些参数放在一起。 此外，这个栏目改成实时参数"）。参数表本身（38 项 / 四组）不变。 布局规则不变（仍是"入口页只做导航 + 模块界面整屏"）。

布局四条硬规则：

  1. 顶栏四个设备标签即入口：不另设"连接"页面。状态灯与连接/配对/选参窗口是同一个控件的两种形态。
  2. 入口页只做导航：只放子系统分组（分割线 + 类别名称）与模块卡片；功能一律进 单开一个整屏模块界面。不设选项卡、不切页 —— 这样"有哪些子系统、各自能做什么" 一进门就在眼前，而真正动手时屏幕上只有那一个实验的东西。
  3. 模块是"可验证的最小实验"：每个模块能独立跑、独立看结果，不要求别的模块先跑过； 一个模块坏了不牵连别的模块。
  4. 跨子系统的产物进底栏：准备清单、会话、⑨数据、服务日志不属于任何单个子系统。

  • 界面只放四样：状态 / 数值 / 控件 / "下一步点哪"。
  • 门控提示只报条件（未连接电脑鼠），不给动作路径；故障类消息才给可照做的清单。

2. 整合的三个硬约束

全篇设计都从这三条推出来。它们不是"注意事项"，是约束。

2.1 带宽：定位只能 ~2 fps 准实时

算术（取自上游实测，不是估计）：

交付单帧          = 1 920 × 1 440 = 2 764 800 B = 2.765 MB
手机→PC 实测链路  = 5.5 MB/s
⇒ 交付道可持续帧率 ≈ 5.5 / 2.765 ≈ 1.99 fps

而算力侧余量很大：1920×1440 默认档 97 ms ⇒ 算力上限约 10 fps。 ⇒ 瓶颈在链路，不在算法。这一条直接推出三个设计决定：

  1. 在线定位只消费「已经 verified 的交付帧」，绝不额外向手机请求帧（否则和上传抢带宽，且抢不到）。
  2. 监视道（MJPEG）不参与定位 —— 480 宽有损，上游明令禁止用于测量。
  3. 必须有第二条「赛后批量道」：会话停止、排空完成（delivery_done）后，PC 上已经有全量帧，此时批量解算不涉及任何网络，可以按算力满速跑（97 ms/帧 ⇒ 1440 帧约 2.3 分钟）。这才是用于建模的数据。

结果：界面上会出现两条轨迹 ——「在线观测轨迹（稀疏，≈2 fps）」与「离线复算轨迹（全量）」。必须明确标注哪条是权威，否则现场必然拿稀疏的那条去算误差。

2.2 时钟：三套时间基，必须有一个主时钟

源 有什么 能当主时钟吗
PC（Control 进程） time.time() 墙钟 + time.perf_counter() 单调 ✅ 定为主时钟
鼠（固件） 遥测里只有 t_host_ms（PC 收字节的本地毫秒） ❌ 设备侧无绝对时间
手机 sensor_timestamp_ns（elapsedRealtime 基）+ wall_clock_ns（epoch）+ boot_time_ns ⚠️ 只能当第二时钟，需要标定与 PC 的偏移

规则（必须写进代码，不能靠人记）：

  • 落盘的每一条记录都盖 t_pc_ms（epoch 毫秒），作为唯一对齐键。
  • 鼠遥测：t_pc_ms = 收到该帧的墙钟；原 t_host_ms 保留为会话内相对量。
  • 相机帧：t_pc_ms = wall_clock_ns / 1e6（不是 sensor_timestamp_ns，后者是开机基准）；sensor_timestamp_ns 原样保留供帧内定时用。
  • 定位结果：t_pc_ms 继承其所属帧的 t_pc_ms，不是解算完成时刻。⚠️ 这是最容易写错的一处。
  • meta.json 里记录本次会话的 clock_offset_ms 及其来源（见下）。

两级对齐（诚实分级，不假装精度）：

级别 手段 可达精度 用在哪
L1（默认） 直接用手机的 wall_clock_ns，与 PC 墙钟都是系统时间 不确定：两机 NTP 偏差，可能几十 ms ~ 数秒 轨迹形状、事后定性对照
L1+（一次标定） 现场做一次「同步脉冲」：鼠静止时 PC 记 T_pc0，同时手机侧记同一事件的 sensor ts ⇒ 得到偏移常量 约 ±10 ms（受快门与手速限） 默认用这个，偏移量写进 meta
L2（研究级） 事件互相关：用 mouseTask 跳变（固件视角）与视觉轨迹拐点/速度过零（视觉视角）做互相关，反解时间偏移 可达 ±1 帧（约 33 ms 分辨，可插值到更细） 需要严格对齐的建模

⚠️ 上游把这件事列为显式未决项（手机相机采集与回传_方案设计.md §R5）。本方案不掩盖它，而是把它变成一个可测量的量（clock_offset_ms + 其不确定度），并把 L2 作为已设计好的升级路径。

3.2 进程边界的取舍（为什么是这样切）

候选方案 否决理由
三个模块各起进程，Control 只做 HTTP 聚合 ❌ 鼠的串口是独占资源，多一层进程只会让"口被占"的报错更难解释；MouseClient 本来就是 headless 库，套 HTTP 是纯损耗
把相机服务也拉进 Control 进程 ❌ server.py 必须绑 0.0.0.0（手机要连入），它自带 loopback 门控 + token + 197 项取证判据。拉进来等于重写它，风险高、收益零
把定位搬到手机端（Android） ❌ aruco_locator 是 Python + opencv-contrib，手机端是 Kotlin ⇒ 要重写算法。否决
本方案：鼠 + 定位同进程，相机跨进程 ✅ 只保留一个跨程序边界，且这个边界上游已经给了官方客户端 hostlink.py（设计目标就是"三行接入"）

必然的结果：Control 与 RemoteControl/host/run_host.py（Qt GUI）不能同时连同一个口。这是上游明确的约束（"串口独占。服务模式与 GUI 不能同时连同一个口；同进程内应共享同一个 MouseClient 实例"）。设计上：启动时探测，给出可照做的错误信息，而不是静默竞争。

3.3 环境：为什么 Web 反而解决了环境冲突

环境 有什么 缺什么
stmlink pyserial 3.5 / numpy 2.4.6 / PySide6 / pyqtgraph ❌ 无 cv2、无 aiohttp
general_env cv2 4.11.0 / numpy 2.5.1 / yaml / scipy / aiohttp 3.14.3 / pyserial 3.5 / websockets / PIL / qrcode / pandas —

Auto Locate 的纪律是"不要换环境、也不要在该环境外 pip install"，而它的依赖在 general_env；鼠的 GUI 需要 stmlink。

⇒ 走 Web 就不需要 PySide6/pyqtgraph，鼠侧只需要 numpy + pyserial（general_env 都有）。 ⇒ 整个 Control 跑在 general_env 一个环境里，零新增依赖、零环境冲突。

这是本方案的一个隐藏收益：Control 与 PhoneCamera/pc 用同一个解释器，hostlink.py 可以直接 import，不需要任何路径魔法。

4. 定位链路：两段式

4.1 为什么必须两段

见 §2.1。一句话：在线受链路限（≈2 fps），赛后受算力限（≈10 fps，且不占网）。

4.2 在线段（准实时）

camera 事件流（hostlink.events）
   │  frame_verified {seq, file, sensor_timestamp_ns, ...}
   ▼
FrameDecoder（线程池，1 个 worker）
   │  np.fromfile(.yuv, uint8).reshape(H, W)   ← H/W 从同名 .json 读，不硬编码
   │  cv2.cvtColor(gray, COLOR_GRAY2BGR)
   ▼
ArucoLocator（**单实例单线程**，上游明令线程不安全）
   │  loc.locate(bgr, frame_index=seq, timestamp=t_pc_s)
   ▼
结果 → ① 推前端（locate.result） ② 追加写 locate/results.jsonl ③ 存路径点给轨迹视图

硬性要求：

  • 不丢帧但也不阻塞：用有界队列（容量例如 8）。满了就记一笔 locate_dropped（显式计数）并丢最旧，绝不阻塞 hostlink.events() 的消费（上游的教训：在别人的消息循环里 await = 把那条循环的生死交出去）。
  • decoder 与 locator 分开线程：解码（IO + 色彩转换）与解算（CPU）串行会浪费一半重叠机会，但 locator 又不能并发 ⇒ 用 ThreadPoolExecutor(max_workers=1) 串行 + 解码预取。
  • valid=false 也要写进 jsonl（带 reason）—— 否则"哪一帧为什么失败"就永久丢了。上游的规矩是「无效帧不抛异常，返回 valid=False+reason」，我们照做且必须留档。
  • 每帧记 locate_latency_ms（从 frame_verified 到解算完成），进前端显示。这直接回答"我看到的画面延迟多少"。

4.3 赛后批量段（权威数据）

触发：delivery_done 事件，或用户手动点「复算本会话」。

<手机会话>/frames/*.yuv  (全量)
   ▼ 单线程顺序解算（ArucoLocator 一实例一线程）
   ▼ 进度可查、可中止、幂等（已算过的 seq 跳过）
locate/
├── results.jsonl     # 每帧一行，完整 Localization.to_dict()（含 flags/diagnostics）
├── results.csv       # 扁平表（to_row()），可直接 pandas
└── run_meta.json     # 定位器配置指纹 + profile + 耗时统计 + 无效帧分类计数

为什么结果落 Control 侧而不是手机会话目录：手机会话目录是上游交付物的领地，往里写东西会破坏"这个目录就是 App 交付的东西"这个不变量，也会让上游的账本校验（frames_verified_on_pc 等）面对陌生文件。⇒ 只读上游目录，产物写自己的 locate/。

4.4 帧解码的正确姿势（一个容易踩的坑）

meta = json.loads(Path(yuv).with_suffix(".json").read_text("utf-8"))
H, W = meta["height"], meta["width"]
stride = meta["y_stride"]
raw = np.fromfile(yuv, dtype=np.uint8)
if meta.get("repacked") is False and stride == W:
    gray = raw.reshape(H, W)
else:
    gray = raw.reshape(H, stride)[:, :W]      # 行尾有填充，按 stride 切
bgr = cv2.cvtColor(gray, cv2.COLOR_GRAY2BGR)

⚠️ y_stride 与 source_row_stride 都要读（当前交付档都是 1920，无填充），一旦将来 profile 变了，repacked 会变 true —— 硬编码 reshape(H, W) 就会静默出错误的图（形状对、内容错位）。⇒ 写成源码锚定的判据（见 §11）。

POST /api/v1/session/open
  ├─ ① mouse: MouseClient.session.open()          → 得 mouse 目录
  ├─ ② camera: hostlink.start()                    → 得 session_id
  ├─ ③ 建 locate/ thumbs/ 与 timeline.csv 表头
  └─ 任一步失败 ⇒ **回滚已成功的步骤**（关会话 + 停采集），返回可读原因

⚠️ 顺序有讲究：先开鼠会话、再起手机采集。理由：手机采集是"物理动作"（相机开始连拍、往手机写盘），一旦起来就产生了耗存储的副作用；鼠会话只是一个本地目录，失败代价几乎是零。把便宜且可回滚的放前面。

停止则相反：先停手机采集 → 等 delivery_done → 再关鼠会话。理由：delivery_done 之后才触发赛后批量定位，而批量定位的结果要写进 locate/，所以鼠会话（承载 locate/ 的那个会话）必须最后收。

6. Web 上位机设计

6.1 技术选型

层 选型 理由
后端 aiohttp general_env 已有；与 PhoneCamera/pc/server.py 同一技术栈，两边的 asyncio 集成没有意外
前端 原生 JS + Canvas 2D + CSS Grid ① 无 npm/构建链 ② 单目录可扔进 U 盘 ③ 用户"自己用，不讲究界面"，优先级是信息密度不是美观 ④ 波形/迷宫/轨迹都是自绘，不用图表库反而更直接
大数组传输 WS 二进制帧（自定义头 + Float32Array） 250 Hz × 9 通道用 JSON 会直接炸掉；二进制可让前端 new Float32Array(buf) 零解析
WS 客户端 浏览器原生 WebSocket —

6.4 九个页面（"在同一个界面实现其所有功能"的落点）

6.4.0 界面里只放四样东西

状态 / 数值 / 控件 / "下一步点哪里"。 为什么这么设计、某个数怎么读、 某条纪律从哪来 —— 全部留在本目录的文档里，不进界面。

这条不是审美偏好，它是防止界面退化成文档的机械约束：

  • 解释性文字会挤占数值的位置。同一块屏幕上，"为什么"多一行，"是多少"就少一行。
  • 解释性文字不会跟着代码一起改。改了三行逻辑而不改那段说明，界面就开始说谎 —— 而且说得很有道理，最难发现。
  • 现场看界面的人要的是"现在能不能跑、缺什么、点哪"，不是"这个字段的来历"。 来历在这里（本文档）写一次就够。

配套的三条实现约定：

  • 每栏底部的「数据」条只放 KV。 没有数据可放的页面，renderContext() 会把它整条 收起，让该栏视图多吃一段高度（空条目比没有条目更浪费）。
  • "还没准备好"不许用"出错了"的样式。 两者是两个类（.gatehint / .errbox）： 未连接是一条待办，故障才要去找原因。混用会让自动检查把提示数成错误， 真错误就淹在里头了。
  • 日志是文本流，不是界面文案。 三处日志容器（底部控制台、设备文本流、服务日志） 都打了 data-log 标记，自动判据扫界面文案时会跳过它们 —— 否则日志里随便一个字符 就能让"界面没有说明性文字"这条判据连红好几轮（真踩过）。
  • 原样端出的上游文本同理，标记是 data-raw。 目前四处：#d-explain（发车页的 timesync.explain()）、#x-lab-out / #x-lesson-out（实验输出）、相机窗口 KV 的 「最近错误」行（值是上游 HostLinkError 的原文）。上游自己会写破折号与口语措辞， 而那是数据、不是我们写的界面文案 —— 判据只该管后者。 （真踩过：上游 explain 里的一句"样本还太少 …… —— 多等几秒"让 B13 偶发连红， 表现还随"服务跑了多久"变化；上游 HostLinkError 那句"连不上 …（服务在跑吗？）" 又让 B23 命中口语词 —— 而这句子改不得：PhoneCamera 的 test_interop.py 就在断言这句原文，它是上游的契约。）
  • 故障类消息要给"可照做的清单"，不能只把上游原文端出来。 相机窗口的 #dc-fault 只放我们自己写的那几行（camera.py 的 _explain 追加的 · 清单），上游原文留在 KV 的「最近错误」行。只取 detail 的第一行（= 上游原文）会把清单整个丢掉 ⇒ 现场看到的是一串 WinError 10061，从中无从知道要去启动上游服务。 由 B29 守着两个方向：不可达时必须写出 ≥1 条 ·、三个依赖配对内容的按钮 禁用（【刷新】保留，它就是重试那一下）；可达时不许留着陈旧故障、四个按钮全可用。

有自动判据盯着：tools/browser_check.py 的 B13（常驻区域：入口页 + 模块界面 + 底栏） 扫 Markdown 残留、反引号、判据编号这类"写作手感漏进界面"的痕迹，B23（同一套 DOM 走法， 再加设备窗口）扫口语词与图形标记。清理一次容易，保持不回流才是判据存在的意义。

6.4.1 「综合运动台」：两栏 + 底部整合栏

主区是两级（见开篇「总纲（冻结）」）：入口页只做导航，点卡片单开一个整屏 模块界面。本节说的是「综合运动台」那个界面内部的样子 —— 它才是原来的 两栏 + 底部整合栏。

┌─ 场地 · 相机 ────── ① 场地   ② 采集                      ← 左栏
├─ 小车 · 控制 ────── ③ 参数  ④ 标定  ⑤ 发车  ⑥ 实验  ⑦ 波形  ⑧ 调试台   ← 右栏
└─ 整合（可收纳）──── 准备清单 · 会话 · ⑨ 数据              ← 底栏

三条切分理由：

  1. 相机侧与小车控制是并列的两件事，而且经常要同时看着。 它们的数据来源、 故障模式、操作节奏都不一样：相机侧是"架好、配对、录"，小车侧是"连上、标定、发车"。 并排摆让"我现在在调哪一套"一眼可见。
  2. 小车控制内部，「参数标定」与「测试发车」还是两套流程（所以右栏的页签按这个顺序排）。 标定是台面上做的（轮子悬空、静态、一项一项来），发车是场地上做的 （真的跑、要计时）。混在一起最容易出的事就是"以为在台面上、其实车会动"。
  3. ⑨数据不进任何一栏。 它读的是两路合起来的产品（统一时间轴、会话浏览器、 轨迹对比、导出），归到任意一栏都会让那一栏名不副实。

⚠️ 视图数与归属在三处必须一致：index.html 的容器/按钮、app.js 的 RAIL_OF + EXPECTED_VIEWS、tools/browser_check.py 的 TAB_CAM/TAB_MOUSE/DOCK_VIEWS。 写死是有意的 —— 加页面时忘了改任何一处都会当场报出来， 而不是让某一页静默变成空白。

⑤ 发车（Depart）—— 时间同步 + 远程发车 + 链路完整性（新增，跟上游 1.4.0）

这一页是「测试发车」那套系统的入口，它回答发车前的三个前置问题：

  • 现在能不能发车：链路活不活、急停是否锁存、固件是哪一档
  • 时间对齐了没有：上游 mc.timesync 的偏移（min-delay）/ 频差（最小二乘 ppm）/ 单程延迟估计 / TIME 帧样本数 / 1Hz 基准灯电平
  • 链路有没有偷偷丢帧：seq_lost / seq_gap / bad_crc / 各流帧数

外加两个动作：发车（ARM） 与 远程发车跑迷宫（MAZE RUN，仅数据收集档）， 以及急停与解锁急停（锁存语义：不解锁就一切运动命令都被拒）。

为什么这三件事必须在同一个动作之前一起看：它们是同一次发车的前置条件。 发车后再发现"时间没对上、还少了几帧"，那时已经无法补救了 —— 唯一能做的就是重跑。

⚠️ 误差验收线用绝对值：上游的 error_ratio 是带符号的，直接拿它比 3% 会让 "-8.9%" 也判成"通过"。本层取 abs()（实测踩到过）。

② 采集（Capture） —— 相机侧的完整功能 - 采集控制（h.start()/stop()）、profile、降载旋钮 plan.interval_ms（⚠️ 一旦 ≠ 0，every_frame 变 false，界面必须显式提示语义变化） - 会话表：复用面板的 11 列（含 store 留存账本、门控、镜头） - 账本的三个数分开显示：frames_expected / gaps_on_device（=重采）/ upload_gaps（=重传）；complete: null 必须显示为「判不了」，不许显示成通过 - 门控 gate.status 三态原样透出（incomplete 不是通过） - 熔断状态显式命名（aborted_no_space → 显示为「空间不足熔断」），并说明回传不受影响 - 配对：二维码（qr_matrix 前端自己画，或 qr_png_b64）+ 网址 + token。⚠️ 这一页要看 token，别投屏

⑨ 数据（Data） - 统一时间轴（事件带 / 甘特）：三路事件按 t_pc_ms 排列，可缩放 - 会话浏览器：列表 + 打开 + 导出（zip / CSV / JSONL） - 轨迹对比：在线（稀疏）vs 离线（全量）叠加，显式标注权威性 - 无效帧分类计数（把 reason 做条形统计：corner_markers_missing / target_marker_missing / square_check_failed …）

⑧ 调试台（Console） - 设备文本流（Event.TEXT，含 printf） - 原始命令逃生舱：POST /mouse/raw ⇒ mc.send_raw(cmd, wait=True)，直接显示 Result 与回读 - Control 服务日志尾

6.4.2 前端启动链的顺序（不是风格问题，是"会不会整页死掉"）

app.js 的 DOMContentLoaded 里，顺序是按"这一步失败了会不会致命"排的，不是按 "先拿到什么数据"排的：

1. bindTop() / bindDev()                    纯 DOM 绑定，不可能慢
2. setInterval(refreshHealth, 2500)   ← **心跳必须在这里**
3. wsConnect()                              断了会自己重连，不致命
4. await refreshHealth()                    先拿到第一份 health（判据 I12：零网络，11 ms）
5. mountViews()                             再挂载视图 —— 这样各视图一次都不用去问相机
   └─ 末尾 broadcastHealth(S.health)        **补喂一次**：视图是在第 4 步之后才挂上的
6. /api/v1/caps                             旁路，**不 await**（界面里没人读它的结果）

三条理由，每一条都是踩出来的：

  • 第 2 步不能挪到后面。 它曾经写在最后，于是前面任何一步变慢（实测 /caps 把服务端 事件循环占住十几秒）都会升级成"整页静默死掉"：setInterval 永远装不上，顶栏停在 启动那一刻、视图是空壳，而服务端日志干净、浏览器零未捕获异常。心跳不依赖任何一步。
  • 第 5 步末尾必须补喂。 视图挂载晚于第一份 health，它们挂载时来不及听广播； 那些"只在 onHealth 里写"的内容（比如发车页的未连提示）就要等下一次心跳才出现。 让视图依赖"心跳一定会来"，正是上面那条错误的翻版。
  • 第 6 步不 await。 caps 是"这台设备支持什么"，属于可选信息；让它挡在启动链上， 等于给页面加了一个"必须顺利"的前置条件。

有自动判据盯着：tools/browser_check.py 的 B22 —— 3.2 s 内 health.uptime_s 必须上涨。没有它时，这个 bug 的表现是 B.capture / B.depart 报红，把人引到"这一页坏了"， 而真相是"整页都死了"；判据的职责就是能说出这是哪一类坏。

7.3 线程与异步模型

asyncio 主循环（aiohttp）
├── mouse 适配器：独立线程（MouseClient 自带调度线程）
│     └─ 事件 → bus.publish()（线程安全入队）→ asyncio.Queue
├── camera 适配器：独立线程跑 hostlink.events() 生成器（阻塞 socket）
│     └─ 事件 → bus.publish() → asyncio.Queue
├── camera 健康探测：**独立线程**（`cam-probe`），周期性读 status 存成快照
│     └─ /health 只读这个快照 ⇒ 零网络、零阻塞
├── locator 在线：ThreadPoolExecutor(max_workers=1)（ArucoLocator 线程不安全）
│     └─ 结果 → bus.publish() → asyncio.Queue
└── WS 广播：从 asyncio.Queue 取，按订阅分发

为什么 camera 用线程而不是 asyncio：hostlink.py 是同步阻塞实现（socket + urllib，刻意只用标准库）。不要为了"优雅"去改它或用 run_in_executor 包整个生成器 —— 用一个专用线程跑生成器、把事件投进线程安全队列，是最简单且不会踩坑的做法。

⚠️ 必须处理的边界：hostlink.events() 断线后会 yield {"type":"_reconnected"}，并且找不回断开期间的事件。⇒ 收到它时必须主动重新对齐状态（这是上游文档明写的用法），否则界面会显示过期状态。

⚠️ 为什么健康要有独立的探测线程（实现期发现，值得单独记一笔）： 本机对 127.0.0.1:8765 一个"被拒绝"的连接要 2.047 s 才返回。因此

  • /health 绝不能同步去探相机 —— 否则它稳定花 2 s，判据 I12 直接不成立；
  • 探测放后台线程，/health 只读快照，并额外报出 probe_age_ms（快照多旧） 与 probe_ms（那次探测花了多久），让"这个结论是哪一刻的"永远可查；
  • reachable 是三态：true 可达 / false 明确不可达 / null 还没探过。 null 在前端渲染成中性色 + "探测中…"，绝不许涂成红色（判据 I11 的同一条纪律）；
  • 可达性翻转时主动推一条 camera.status 事件 —— 翻转稀疏且语义重，不该等前端轮询。

⚠️ 事件循环上不许同步摸设备、不许扫盘（实现期发现，代价最大的一条）： 上面那条纪律（/health 零网络）原本只写在 /health 上，因为它最容易违反。但同一个 错误在任何端点上都成立，而且症状一模一样：服务端日志干干净净，整个服务却对谁都不答话 （连纯内存的 /health 都超时）。实测发生在四处：

位置 同步做了什么 为什么慢
GET /caps → mouse.caps → params_grouped(refresh=False) 对每一个参数调上游 params.get_raw() 上游是带 3 s 超时的实时设备往返，21 项
GET /caps → mouse.caps → conn.targets() Windows 串口枚举（serial.tools.list_ports） 同步慢调用，且与"能力"无关
GET /camera/offline/sessions iterdir + frames/ 下 glob("frame_*.json") + 递归算占用 成千上万个文件
GET /sessions 每个会话逐行数 timeline.csv + 递归算目录占用 随录制量线性增长

判据：任何同步的设备往返 / 串口枚举 / 目录遍历，一律 run_in_executor。 （同文件的 /camera/frames、/session/export、/mouse/ports 本来就是这么写的， 它们是正确样例。）另外 caps 曾经把"候选端口"和"参数当前值"也塞进去了 —— 那两样都是 现场摸设备才能得到的东西，与"这台设备支持什么"无关，已移出：端口列表归 GET /api/v1/mouse/ports（走线程池、由人点【刷新】，慢一点等得起）。

⚠️ 日志纪律：相机没在跑是常态，而事件订阅是 2 s 一轮的重试。 所以断线日志只报这一次故障的第一条，之后按 2→4→8→15 s 退避并在第 15 次报一条心跳， 恢复时再报一条。实测：改之前 20 s 内日志就被同一条 warn 刷了 10 条，800 行的日志环 半小时内会被它填满、把真正的现场事件全挤出去 —— 对一个"靠日志排查"的工具来说等于没有日志。

7.4 场地标定流程（一次性，交互式）

POST /api/v1/arena/calibrate

11.2 实现期发现的真问题（都已修，记在这里防复发）

这些都是"跑起来才会发现、而服务端日志里一个字都没有"的类型。每一条都写下来， 因为它们的共同特征是：报错信息指向的方向是错的。

  1. 加了前置门控之后，原来的"中途失败"判据会失去着力点。 判据 I5（开会话失败要回滚干净）原本靠"相机不可达 ⇒ 开会话失败 ⇒ 看有没有留半个目录" 来验。加了 I18 的门控之后，"相机不可达"在更早一步就被拦住了，那段回滚代码根本走不到 —— I5 于是变红，但它变红的原因是测试构造的场景已经不成立了，不是回滚坏了。 教训：判据之间会互相遮蔽。加一道新闸之后，要回头检查旧判据的场景是否还走得到。 修法：造一个"门控放行、中途才炸"的替身 —— 一个假相机服务（status 正常答让门控放行、 control/start 回 500 触发回滚）。顺带证明了门控与回滚是两道独立的闸： 门控拦"什么都没连就开"，回滚兜"连了但中途炸了"，谁都替不了谁。

0b. 手动"重探"会被后台探测占闸后静默跳过。 探测闸是"同一时刻只允许一次在途探测"。 后台线程正占着闸时，probe_now() 直接返回 —— 拿回去的是一个还没更新的空快照， 表现就是"点了重探，界面上什么都没变"。而这恰恰是现场排查最需要它管用的时候 （I5 因此拿到"探测中…"、门控误判成没准备好）。 修法：_probe_once(wait_guard=True) —— 用户主动点的那一次等闸再探。 原则：周期任务可以跳过，用户主动点的动作不许跳过。

0c. 回滚不能"嘴上报成功"。 _rmtree_quiet 按设计吞掉所有异常（不让清理失败把服务搞崩）， 但"吞掉异常"不等于"删成功" —— 环境限制（只读、占用、删除守卫）会让目录留在盘上。 以前这里无条件写"会话目录已删除（不留半个会话）"，实测就出现过 "报已回滚、目录却还在"（盘上留着一个 mouse/ + timeline.csv 的半截会话， mouse/meta.json 里还写着 rolled_back: true）。 修法：回滚之后检查目录是否真的消失，没删掉就直说并把路径打出来。 这与判据 I11 是同一条纪律：判不了 / 没做到，都要说出来，不许糊过去。

  1. 前端启动顺序：C.state.views 忘了初始化 ⇒ mountViews() 在第一次赋值就抛 TypeError，forEach 当场中断 ⇒ 视图只挂载了 1 个、页签一个都点不动， 表现是"页面能打开但一切都是死的"。修法有两层：显式初始化 + 给启动流程加 bootFail() 兜底（启动期任何未捕获异常都摆到界面上，不再只留给控制台）。 顺带把顺序改成 先拿第一份 /health 再挂载视图 —— 否则每个视图挂载时都会按 "我还不知道相机怎么样"去问一遍相机端点，在常态（相机没跑）下每次冷启动白等 4×2 s。

  2. 健康探测必须后台化（见 §7.3）：本机对被拒绝的连接要 2.0 s。

  3. 日志不许刷屏（见 §7.3）：断线日志要退避 + 只报首条。

  4. 回滚路径绝不能把整个服务搞崩。 会话回滚要删掉自己刚建的目录，用的是 shutil.rmtree(..., ignore_errors=True) —— 它只吞 OSError。而"删目录"这件事 恰恰容易碰到非 OSError 的干扰（文件被占、环境把 rmtree 换成会 raise SystemExit 的实现）。SystemExit 继承自 BaseException，会穿过 except Exception 一路冒到 aiohttp 的请求处理器外面，整个服务进程当场消失，而客户端看到的只是"连接被重置"。 ⇒ 改用自己的删除器 _rmtree_quiet()：逐项吞掉所有异常（含 BaseException）， 并如实返回是否删干净。收拾自己刚拉下的摊子，不该成为把服务搞崩的那件事。

  5. 子进程的 stdout 不能用 PIPE 然后不读它。 tools/drill.py 起服务时用了 stdout=PIPE，却从不去读。管道缓冲区（~64 KB）写满之后，服务进程会阻塞在自己的 日志输出上 ⇒ 事件循环停摆 ⇒ 所有 HTTP 请求挂住，客户端只看到"请求超时"， 跟日志毫无关系。这个坑让 drill.py 的排查绕了两轮（第一次表现成"服务 9 分钟没起来"， 第二次表现成"mouse/connect 卡 30 秒"）。⇒ 服务的输出落成文件：无界、可随时看、 进程死了也还在。

  6. 一条"能打开但对端不存在"的串口会把整个门面钉死。（上游行为，我们改不了，但必须知道） 看门狗 dump 线程栈看到的现场：

调度线程 link.write → serial.write → win32.GetOverlappedResult(True) ← 无限等 主线程 mc.connect → cmd.send("STREAM ON") → with self._lock ← 等那把锁

上游的 _SerialBackend 没设 write_timeout，写一条没有对端的串口会永久阻塞； 而它握着 CommandClient._lock ⇒ 之后任何 connect 都永不返回。 症状极有迷惑性：HTTP 请求挂住，而 /health 照样 200（那个端点是纯内存读）， 看起来像网络问题或"服务卡了"。

对策（不改上游源码，判据 I9）：

  • MouseAdapter.connect 用一把非阻塞闸把"还在途中的连接"挡住。第一次挂住之后， 所有后续调用立刻返回一行能照做的报错（"重启 Control 服务"），而不是排队一起挂死； health 里额外报 connect_in_flight，界面能一眼看出是这个状态。
  • tools/drill.py 不再去连真实串口。 它原来会逐个串口试连以抓"被占用"的报错 —— 那正是能钉死服务的动作。现在只用不存在的端口（COM199）验证"错误信息可照做"， 那条路径是确定性的。一个验收工具把被测对象搞死，它测出来的东西就没有意义了。
  1. 心跳写在启动链的最后 ⇒ 页面会静默死掉（代价最大的一条，详见 §7.3 与 §6.4.2）。

症状：tools/browser_check.py 在"上一轮 --sim 刚把模拟器收掉"之后跑，稳定红两条 （B.capture、B.depart），隔一轮又自己好了。页面 health 看着正常、C.needMouse() 也答得对，但发车页的未连提示、采集页的账本都是空的 —— 像是"某两个视图没渲染"。

排查过程本身值得记下来（每一步都用证据否掉一个假设）：

  1. 在检查器里手动 C.refreshHealthNow() ⇒ 内容立刻出现。⇒ 页面停在旧的 health 上。
  2. 写一次性探针，用 CDP 的 Page.addScriptToEvaluateOnNewDocument 在 app.js 之前 劫持 setInterval / fetch。读到 iv: [] —— 心跳一次都没装上，而 caps 请求 发出去了却没回来。这是决定性证据，而且是注入器给的，不是推断出来的。
  3. 同一时刻从 Python 侧 curl /health：超时 6 s。⇒ 不是浏览器的事，整服务冻住了。
  4. 给服务挂 faulthandler，每秒 dump 全部线程栈（带时间戳）。事件循环线程明明白白停在 aiohttp 处理器里 —— 四处同步的"摸设备 / 扫盘"（清单见 §7.3）。

因果链：--sim 收尾杀掉模拟器 ⇒ 链路变成"连着但已死" ⇒ 冷启动时 /caps 把事件循环 占住 10~20 s ⇒ 浏览器那边 fetch 排队（连接池被占死，那几条请求连 ResourceTiming 条目都没有，即"根本没发出去"）⇒ await C.api('/api/v1/caps') 不返回 ⇒ setInterval(refreshHealth, 2500) 永远装不上 ⇒ 整页停在启动那一刻。

修法：启动链按"失败了会不会致命"排序（心跳第一）；挂载后补喂一次 health； /caps 移出关键路径；服务端四处同步 IO 全部 run_in_executor。 判据：新增 B22（3.2 s 内 uptime_s 必须上涨），并且两个方向都验过 （把 setInterval 打空后必须不涨）—— 一道从没红过的闸不算闸。

  1. "相机不可达"这条路长期没被跑过 ⇒ 第一次跑就红 11 条。

browser_check.py 的 --fake-cam 默认是开的：8765 空着就起一个假上游相机， 好让"二维码真画出来"（B16）验得到。代价是降级路永远走不到 —— 它藏在 --no-fake-cam 后面，而那个开关一直没被用过。真跑一次，红的是两类：

  • B23 命中上游原文里的口语词（HostLinkError 的"（服务在跑吗？）"）。这句原文 改不得 —— PhoneCamera 的 test_interop.py 就在断言它，它是上游的契约。 ⇒ 原样端出的值打 data-raw；视图层也不再重复端出上游原文（那属于诊断行， 归设备窗口的 KV）。与"改文案"是两回事：这是"别把别人的文字当成自己的文案"。
  • 多条判据把"设备窗口里的故障框"数成了页面错误。 .errbox 的计数口径要写清： 有内容、且不在 #dev-modal 里。某一路设备不通由 B29 专门判， 这几条问的是"页面/模块挂载有没有出错"。

同一条纪律的另一面：用户报的那句"连不上手机 / 二维码不显示"，根因不在界面 —— 是上游 pc/server.py 没起（8765 无人监听）。但界面必须自己把这句说出来， 而它当时把 detail 的第 1 行（原始报错）留下、把第 2 行起（可照做的清单）砍了。

判据：新增 B29，两个方向都判（不可达必须给出可照做的 · 清单 + 禁用三个 配对按钮；可达不许留陈旧故障 + 四个按钮全可用）。 一条判据只要有一种状态从没被跑过，就等于没有。

11.3 上游 1.1.0 → 1.4.0 的跟进记录（最长的一节，所以放最后）

Control 第一版是按 RemoteControl 1.1.0 建的；上游当天连跳到 1.4.0。这次跟进做了三类事：

一、把重复实现删掉，改成委托上游（最重要的一条）

上游 1.4.0 起了自己的时间同步：固件有 linkTimeMs（SysTick 1ms，u32 49 天不绕）， ARM 让它在发车时点灯并回 ARMED <ms>，之后每秒上行一帧 TIME（带完整 u32）， 每个快帧的保留字节也让出时基的低 8 位 —— 于是每个采样点都能被钉到准确时刻； 还有 1Hz 基准方波灯供摄像头/光电/人眼独立校核。

⇒ 这一段（mc.timesync：min-delay 偏移 + 最小二乘 ppm + resolve_ms8）是上游做对的事， 本层不再自己算一遍。分工重新划清：

时间基 谁负责
固件毫秒时基 → 本机单调秒 上游 mc.timesync（本层只透传 + 落盘）
本机单调秒 → PC 墙钟 epoch 本层 WallAnchor（单调推进 + 周期性重锚，不回退）
手机 wall_clock_ns → PC 墙钟 本层 Clock.fit_min_latency（L2 有偏上界）

收益是实的：timeline.csv 的 t_pc_ms 以前只能记"帧到达主机的时刻"（被蓝牙缓冲与 抖动污染），现在记的是帧真正发出的时刻；并新增 t_src 列明确标出"这一行是哪一种时间"， 新增 dev_ms 列用来和上游的 stream_*.csv 直接对齐。

二、把上游新增的安全约束接进来

  • mc.motor_guard()：安全测试固件下 MOVE/CAL 照常回 ACK、电机不转，调用方要傻等 90 s 超时才失败。现在所有需要电机的端点在动手前先过这道闸，把 90 秒的困惑换成一行的明确原因
  • 急停是锁存的：触发后一切运动命令返回 ERR_ESTOP，必须显式解锁。 解锁是重新获得控制权的唯一入口 —— 自动恢复的急停等于没有急停

三、把新增的功能面暴露出来，但不信版本号

上游 host.__version__ 至今仍写着 1.1.0（CHANGELOG 已到 1.4.0）⇒ 本层一律用 能力探测（import 那个类 / hasattr 那个方法）判能力，caps() 里明确标 api_version_trustworthy: false。这比信任一个没人维护的字符串可靠得多。

新增三组端点（/timesync、/lab/*、/lesson/*，共 19 条）与两个页面（⑤ 发车、⑥ 实验）。 mc.lesson 的"由回传数据自动算参"里，数学用上游的纯函数（solve_ratio / error_ratio）， 本层只做编排（收实测真值 → 摆出结论 → 按对通道写回）。

⚠️ error_ratio 不在 host.api 的 __all__ 里（只在 host/api/lesson.py 里）， 从包上 getattr 会 AttributeError —— 而"取不到就当没有"会让报错指向错误的方向 （会报成"上游缺少算参纯函数"）。取这些纯函数必须按子模块取。

11.4 上游 1.5.0 → 1.5.5 的跟进记录（组测发送 / 迷宫状态机）

上游在这一轮做了大规模重构（1.4.0 → 1.5.5，同日五个版本）。对本层的影响有三类： 新增能力要接、旧数字会过期、模拟器的行为变了会让判据链误报。

⚠️ 本节记录的能力在 2.0.0 里有变（见 §11.9），但下面两条界面纪律仍然成立 —— 所以这一节保留原文，只在结论处标注"已变/未变"。

一、新增的两个能力，以及它们各自的"界面纪律"

能力 上游 界面落在 界面必须守住的一条
组测发送 mc.snap 1.5.0 「分组测量」模块（2.0.0 已并入「实时参数」） enabled=0 是"没采"不是"没电"；sat 三态（正常 / 近端饱和 / 远端超量程）不能谎报 249mm —— 2.0.0 里红外只给 mm 与 irAdc*，sat 三态没了（改由主机按 wallThresh 复算 critL/critR）

二、写在界面里的数字会悄悄过期

上游 1.5.4 把运行数据区上移，生产标定页 99 → 115、课程参数页 100 → 116 （旧页号正落在 FLASH_EraseRunData() 的擦除范围内 —— 一次擦除就会把标定连课程参数一起抹掉）。 而本层把页号写死在两处：adapters/mouse.py 的 flash_page 与界面上的 SAVE 生产 · page 99 按钮文案。

⇒ 改法不是"把 99 改成 115"，而是不要再写死：页号随参数分组一起从服务端返回， 界面按数据里的 flash_page 现生成 SAVE 按钮（同页的几组共用一个 —— 生产命名空间本来就是一整表一次写）。FLASH_PAGE_PROD / FLASH_PAGE_LESSON 作为 唯一常量留在适配器里，并把"为什么是这两个数"写在旁边。

同一次变更还把参数分组由两套变四组（生产标定 / 课程调参 / 红外测量 / 电源监控）—— I16 的断言因此跟着改：它的形状（按页与通道分组）不变，具体数字变了。

三、--no-auto：一个"上游的坑"差点被记成"我们的红"

drill.py --sim 里原先起模拟器只带 --port。上游 1.5.x 起，SCOPE START 在 auto_explore=True（默认）下会把模拟器置成自走（move_mode=EXPLORE）， 而 LESSON START 的运动互斥判据（link_MotionBusy()）因此恒为真 ⇒ 必得 ERR_BUSY。 更要命的是这条因果链在上游内部自己闭合：LessonAPI.run() 的实现就是 "先 SCOPE START、再 LESSON START" —— 两条自己撞上。上游自己的三套 smoke （lesson_smoke / maze_smoke / selftest）都传了 --no-auto。

⇒ 修法：_start_sim 加 --no-auto（MAZE RUN 是显式发车命令，不受它约束，I23 照样能跑）。 判据链要能区分"我们的错"与"上游的错"：这次靠一句最小实验分清了 —— 全新模拟器上什么都不做、直接跑课程实验，一样 ERR_BUSY。若只看到"drill 红了"就回去 翻自己的代码，会白翻很久。（这也是一条通用手法：报红时先构造最小复现，再看责任方。）

四、_need_mouse(ctx) 返回的是上游客户端，不是本层适配器

新增端点时最容易犯的一个错：写了 mc = _need_mouse(ctx)，然后调 mc.snap_read(...) —— 那得到 500 与 'MouseClient' object has no attribute 'snap_read'，看着像上游改名了。 实际上是：既有端点都直接打上游 API（mc.params.get_all），所以这个辅助函数返回的是 上游 MouseClient；而新加的方法在本层适配器上。⇒ 闸门用 _need_mouse（统一 409 文案）， 干活用 ctx.mouse。这条已经写进 routes.py 的注释里，免得下一个人再踩。

五、模块界面必须有"挂上没挂上"的判据（B30）

模块卡片是 SYS_DEF 渲染出来的 —— 脚本没加载 / 注册失败时，卡片照样在， 点进去才发现是空的。这跟"这个功能本来就没做"在界面上长得一模一样， 所以它只能靠自动判据守：卡片在 + 视图在 + 关键控件在 + 有内容 + 无未捕获异常。 "有内容"这一条对「分组测量」尤其重要：它未连接时要画域与字段的静态表（来自 GET /mouse/meas/meta，零设备访问），否则准备阶段看到的是一张空页。 B30 同时把它盖到「实时参数」上 —— 那一页的 SAVE 按钮改成按数据里的 flash_page 现生成 之后，属于"现生成的东西最容易在某个分支里整个不出现"（脚本不报错、页面上就是没有）。

六、读数表要判"值来自哪一段"（B34）

「实时参数」把同一条 WS 消息的两个段并排放：mid 段（里程 / 陀螺，50 Hz）与 slow 段（四路红外 / 电压，5 Hz）。只判"行在不在"是不够的：段名读错时行照样在、 值永远显示 —，脚本一声不响 —— 这与 B30 是同一类"静态在、内容是空的"。 所以 B34 逐行比对DOM 里渲染出来的字符串与喂进去的遥测，并要求单位（mm / V）真的画出来。

11.5 让"配对"不再依赖手动启动上游（含三个被它牵出来的坑）

用户要求：配对依赖上游服务时，应当能在设置里给出上游程序，并由本层代启， 不必手动双击 start_service.cmd。实现分两半：设置（写回 config.yaml， 外科式改写保住注释）+ 代启（control/launcher.py：直接起 python server.py， 参数从配置推导，stdout 落文件）。

为什么不去调那个 .cmd：它会开一个控制台窗口、结尾 pause，而且进程树里隔了一层 cmd.exe —— 我们停不掉它。直接起 python server.py 才有干净的父子关系。

代启的三条纪律（都有对应判据）：只由人触发（/health 与后台探测绝不拉起进程， 否则一个 2.5 s 刷新的页面会不停起进程）、幂等（已可达就不起、本层起的还在跑就不重复起）、 只停自己起的那个（别处启动的没有父子关系，杀错就是断人现场）。

这个功能一上来就牵出三个坑，都不是它的"新 bug"，而是被它第一次照到的旧问题：

坑 1：config.py::patch() 会给嵌套键重复缩进 ⇒ 把 config.yaml 写坏（最严重）。

head = body.split(":", 1)[0] 拿到的 head 带着行首缩进，而下面又拼了一次 indent。 顶层键（缩进 0）看不出来 —— 所以它一直没被发现：此前只有 clock.* 这类顶层标量被 patch 过。而场地标定写的是 arena.fw_to_arena.y_flip（嵌套！），一旦有人点过"写回标定"， config.yaml 就会多出 4 个空格，下一次启动直接 ParserError，服务起不来。

  • 修法：head 先 .strip()；
  • 加固：落盘前自己 yaml.safe_load 一遍，过不了就整项标成 bad_render 不写。 config.yaml 是"唯一真相"，宁可这一项不生效并告警，也不留下一个读不动的配置；
  • 判据：I24 在临时副本上改嵌套键，断言"重新 load 得动 + 缩进不变 + 注释还在 + 值生效"。

坑 2：browser_check --no-fake-cam 会把真上游拉起来，并在用户机器上留下进程。

--no-fake-cam 跑的是"相机不可达"那条降级路；而代启一旦生效，那条路当场就没了 （界面自己去启动上游），还会留下一个 server.py 进程 —— 测试不该有这种副作用（真发生了）。

  • 修法：给代启加一个"本次运行内暂停"的开关（POST /camera/service/pause， 不写配置），browser_check 在降级那一轮先暂停、收尾复原。 它与配置项 camera.launcher.enabled 分工：那个是"要不要这个能力"（长期）， 这个是"这一次先别动手"（临时）—— 现场"我自己管进程"也用得上。

坑 3：错误信息的"可照做清单"不该依赖"错误恰好是中文"。

_explain 原先只认 连不上 / ConnectionRefused / URLError。而这台机器上有个 HTTP 代理时， urlopen 会先撞代理，拿回来的是英文的 HTTP 502: upstream connect failed (os error 10061) —— 一个关键字都不命中 ⇒ 故障位里只剩第一行原始报错，"下一步点哪"整个消失（B29 当场红）。

  • 修法：识别集合放宽到 connection refused / refused / 10061 / upstream connect failed / 502 / timeout / unreachable，并补一句"若这台机器走 HTTP 代理，代理会让本机回环连接也失败"。 判据的意义在此：B29 要求"不可达时必须有 ≥1 条 ·"，正是它把"认不出的错误"变成红。

顺带修掉一处一致性问题：配对按钮的可用性原先只看"打开窗口那一刻"的 health， 于是服务刚挂掉时三个按钮还亮着（点了必然失败）。改成跟着 health 走（renderDevCamera 里重算）。

坑 4（真机才暴露，最隐蔽）：代启的子进程继承父进程的编码 ⇒ 上游连启动横幅都打不出来。

上游 pc/server.py 的启动横幅里有 ▶ (U+25B6) / ■ / ① / ② / ⚠ 这类字符。 Windows 下 Python 的 stdout 在重定向到文件时用的是 locale 编码（简体中文机器 = GBK）， 于是 print() 当场抛 UnicodeEncodeError、进程 exit 1 —— 服务根本没起来。 现场看到的是：

启动上游服务：代启了 server.py（PID 26136）但没等到它可用：进程已退出（返回码 1）
UnicodeEncodeError: 'gbk' codec can't encode character '\u25b6' in position 11
  • 为什么我此前测不出来：我的开发 shell 里 CodeBuddy 设了 PYTHONUTF8=1 / PYTHONIOENCODING=utf-8，子进程继承的是 UTF-8 —— 我的环境比用户的干净， 于是"在本地永远绿"。（这类"隐性的环境差异"是自动化判据最大的盲区。）
  • 修法：_spawn() 里显式覆盖子进程环境（不改上游源码，那是它的 banner）： PYTHONIOENCODING=utf-8 + PYTHONUTF8=1 + PYTHONUNBUFFERED=1 （第三个顺手解决"日志是空的"：不缓冲就立刻落盘）。
  • 加固：_tail() 两段解码（先严格 UTF-8，再退 GBK）—— 用户手动 .cmd 起的旧日志是 GBK， 而日志尾巴是失败时唯一的证据，读成 ���� 等于没有证据。
  • 判据：I25 必须"在最坏的环境里跑"：先把父环境临时改成 GBK 风格再代启， 并断言 ①子进程环境含那三个键 ②日志可严格 UTF-8 解码 ③无 Traceback ④负向：把这三个键打掉后必须失败、且失败原因正是 UnicodeEncodeError。 没有 ④ 的话，"删掉那三行"不会有任何症状（在我的机器上永远绿）—— 一道从没红过的闸不算闸。

11.6 "看不到画面"：一个真 bug 与一次判断失误

用户报的现象：相机测试连接拿不到画面，手机端有发送队列，预览窗口也是空的， 服务端日志只有两条 MJPEG 反代中断。

查出来的真 bug：反代把 multipart 的 Content-Type 写死成 multipart/x-mixed-replace; boundary=frame，而上游声明的是 boundary=phonecamera-frame —— 声明与实际不符。boundary 是上游对它的流说了算，本层不该猜。 修法：原样透传上游的 Content-Type（不自己拼）。这类"声明与内容不一致"对 严格解析的消费方是致命的：cv2.VideoCapture、ffmpeg、以及我们的判据都是按声明切的。

但它在 Chrome 上是容错的 —— 这是这次最值得记的一条。我把 boundary 改回写死值做负向 验证时，B32（浏览器 <img> 的 naturalWidth > 0）照样 PASS：Chrome 对 multipart/x-mixed-replace 会按 JPEG 的 SOI/EOI 标记识别帧，不严格依赖 boundary。 ⇒ "浏览器能看见"不等于"流是对的"。所以守这条要用严格解析（I26 在 Python 里按声明切）， 不能只靠浏览器渲染（B32 只能守"到底有没有画面"）。

那么用户看到的空白是什么引起的？ 上游 monitor 段给出了分界： {"subscribers": N, "thumbs": n, "last_thumb": {...}|null} —— last_thumb 是 上游最近推出去的那一张，null 就表示它一次都没推过。而这条流的帧源是 手机 App 上行的缩略图（"帧率 = 缩略图节奏"）⇒ 手机侧不出画面，PC 端自然什么都没有。 用户那句"手机端预览窗口也没有画面"才是根因侧的现象，而 Control 只是受害者。 ⇒ 界面必须把这一点摆出来（否则现场只能对着空白猜）：

  • 相机窗口与「图像回传测试」页都加了一行 「监视道」：已收到 · seq N · xx KB / 上游未推过画面 · 手机端需开启预览 / 未订阅上游 / 判不了（四种都给下一步）；
  • 「图像回传测试」页在等画面时不再永远写着「等待第一帧…」，而是按上游到底推没推改写这句；
  • --no-fake-cam 那一轮：判据 B33 两个方向都验（推过 / 从没推过）。

顺手修的两处（都是"事件归错了类"）：

  1. MJPEG 反代中断：ClientConnectionResetError 记为 warn —— 其实那是浏览器关掉了连接 （切页 / 刷新 / 停止预览），是正常事件。记 warn 的下场：现场切一次页面就多一条"故障"， 真故障被自己的噪声淹掉（用户贴的日志里那两条就是它）。现在分开捕获： 读上游失败记 warn（真故障），写浏览器失败记 info（正常事件）。
  2. <img> 拿到 502（反代如实报"连不上上游"）时，浏览器只会显示破图、一个字都不说 ⇒ 补 onerror，把它变成「画面加载失败 · 到顶栏【相机】看服务是否可达」。

11.7 把红外/电压并进「实时参数」（附：一条判据的假红与一条 flaky 判据）

用户要求把四路红外与电压和已有的累加量（左/右里程等）放在同一张表里， 并把这一栏改名为 实时参数。实现上是改动最小的一处：这几个量本来就随 同一条 WS 消息（mouse.telemetry）送到前端 —— 只是分在 mid（50 Hz）与 slow（5 Hz）两个段里。所以没有新增任何传输、端点、轮询，只是同屏呈现 （并标注两段的频率，否则"红外怎么比里程慢一拍"会被当成故障）。 面板标题由「累加量」改为「实时读数」—— 红外与电压不是累加量，标题不能骗人。

这一处踩到的坑是"判据自己写错了"，值得单列：

第一版 B34 用当前遥测值当期望：先读 DOM，再读 C.state.telemetry，两边比对。 结果红了，但界面其实是对的 —— mid 50 Hz、slow 5 Hz 一直在走， 读完 DOM 再读遥测，两边本来就差几拍（实测 gyroRaw 界面 2048 / 遥测 2045）。 另有我自己的期望值漏了单位（界面「178 mm」比「178」）。 ⇒ 改成喂一份已知的哨兵值进去重渲染，逐行比对，比完立刻还原并用真值重渲一次。 这套写法比"抓当下的活数据"稳得多，值得作为"判实时数据渲染"的通用手法： 不要去追一份一直在走的数据，把它钉住再比。

第二件事：同一次跑动里 I15 红了一次、之后三次都绿。查下来不是功能问题 —— 它写死 sleep(2.5) 就去问"帧发生时刻算出来没有"，而那个值要等第一条 TIME 帧到达、 把主机-设备时基对上才有；慢一拍就拿到 None，于是一次绿一次红。 改成等到算得出为止（有上限）+ 把等了几秒写进报告，上限内没出来才是真失败。 ⇒ 两条通用教训："等一个固定时长再断言"必然 flaky，要等的是条件不是时间； 以及判据红的时候先怀疑判据（这次两回都是判据自己不对，不是功能不对）。

11.9 上游 2.0.0「传输模式重构」的跟进记录（协议整体替换）

上游三份权威文档：RemoteControl/docs/传输模式重构设计方案.md（决策台账 / 统一帧规格 / 命令事件集）、传输模式接口设计.md（逐字段迁移映射）、CHANGELOG.md 的 [2.0.0] 段。 CHANGELOG 明说："2.0.0 是这条约定的一次显式破例：本次是协议的整体替换， 不做 _v2 名称 + 弃用期。" ⇒ 本层不许做兼容层，做了就等于自己造了一份会过期的真相。

总账：帧类型 9 → 2（UNIFIED 0x0A / MAP 0x07）；命令 41 → 18 条（23 个 API 名， 2.1.1/2.2.0 后为 24 条，见 §11.12）；上行事件收敛到 2 条（STOPPED <reason> #n / ESTOP TRIP #n）； 遥测由 fast/mid/slow 三档 → 一条统一帧（53 B / ≈217 Hz / 39 个扁平通道）。

一、两个取参数的子功能合并（本次唯一的界面结构变化）

上游删了 SNAP 与 SCOPE 之后，"实时参数"（读三档流的连续值）与"分组测量" （SNAP 一问一答取瞬时值）读的东西变成了同一样 —— 都是那唯一一条统一帧。 于是两页并一页：分组测量并入实时参数（见总纲改版记录（六））。

  • 模块卡片由五张变四张；views/mod_meas.js 删除，index.html 的 <script> 一并去掉 （少一个静态资源会静默变空，见 §11.2 的 I21）。
  • 读数区改成按语义分组画出统一帧的通道（运动与姿态 / 里程与位置 / 迷宫判定 / 四路红外 / 电源 / 链路），键名照上游原样标在行上（现场对着上游文档查字段时能对得上的只有键名）。
  • 不臆造单位：只写上游明确标过的（speedL/R cm/s、track*/cellOdom/ir* mm、 battMv mV、ms8 ms）。gyroAngle/encAngle/pidErr 上游没标 ⇒ 界面也不给单位 （写错的单位比没有单位更坏：现场会拿它去换算）。
  • 新加的键不许静默藏掉：分组表之外还有一块「其他通道」，把不在任何分组里的通道列出来 —— 上游下次加字段时界面会自动多一行，而不是"这个量不存在"。
  • 三档流时代的"这一段慢"（mid 真机 1 Hz / slow 0.5 Hz）整段解释删掉： 一份帧就是全量，所有字段的节奏一样，只说实测帧率 + 最新一帧年龄。

二、实验 8：三块变两块，且必须交代"这是推出来的"

MAZE EV 与 MAZE RST 删除后，"它刚才识别到了什么"改由主机差分相邻帧得到 （mc.maze.task_changes()）。界面相应改成 状态机 + 任务迁移序列 两块， 并把 SNAP MAZE 才给的 evDrop/cellCnt 拿掉（前者改从帧 flags bit7 的 EVQ 读）。

这里有一条必须守住的新纪律：差分出来的边沿不是设备报的事实。 SEQ 跳变说明中间缺帧，那一段的迁移可能整段丢失、也可能一次跨两级 ⇒ 界面必须写清 "它是推出来的、缺口时那一段的边沿不在"，不许把差分结果说得像设备事件流一样权威。 "当时没收到" ≠ "没发生过" —— 这正是本层一贯的取证纪律在差分场景下的延续。

同类的还有：【清统计】的措辞改成【清本层差分】—— 固件侧 2.0.0 已无统计可清， 说成"清固件统计"是谎。

三、EVQ 换了来源，但纪律不变

旧版 EVQ 来自 MAZE 状态帧；2.0.0 它是统一帧 flags 的 bit7（取代了旧的 RUNLOG）， 含义完全一样：有事件行被丢弃 ⇒ 事件流不完整。 而 2.0.0 又新增了一条相关事实：事件行与遥测帧共用一个 1 字节序号， 所以 step >= 2 就能判"中间丢了"。⇒ 本层把它摆到两个地方： link_stats.event_health（ev_lost/ev_gaps/up_lost…）与读数区的独立故障块 （不是藏在 flags 那一行里 —— 藏起来等于没报）。

四、课程参数的读侧不对称（最容易把成功报成失败的一处）

2.0.0 的固件 GET ALL / GET <name> 只查生产表（PRODUCTION_PARAM_IDS，24 项）， 课程 14 项一律回 ERR_NAME；而写侧（SET/SETQ）是通的。三类后果都已在代码里处理：

  1. params_grouped() 给每项带 readable；课程组的值列显示"—"而不是"0" （显示 0 会被当成"这台机器上它是 0"）。
  2. refresh=True 时只对 readable 的项调 get_raw() —— 否则课程 14 项各白等 3 s 超时， 链路刚断时就是整服务冻结（连纯内存的 /health 都不答）。
  3. set_params_grouped() 对课程侧固定 readback=False（带回读去写会把成功的写入 报成失败）；save_params(group="课程调参") 必须带 values， 否则抛明确错误："值读不回来 ⇒ 没有'当前值'可以落盘"。

⇒ 界面上课程组标注 "值读不到，可写" + 输入框 placeholder="填入新值"， SAVE 时把输入框里的值一并提交。不许因为读不到就把它从界面上拿掉 —— 那等于让"改课程参数"这条路消失。

五、被删方法不能在装载期引用（会变成"连都连不上"）

_load() 里还留着 from host.api import ..., ScopeAPI，_attach() 里还订阅着 Event.DUMP_PROGRESS / Event.DUMP_DONE。上游删掉它们之后： ImportError / AttributeError 被 _load()/_attach() 的 except 吞成"鼠模块不可用"， 表现是"页面上所有鼠功能都灰着"，而原因完全指不到"上游删了三个符号"。

⇒ 两条改法，都是"能力探测、不信版本号"这条老纪律的延伸： - _load() 不再 import 已删符号；_attach() 里所有 Event.XXX 一律 getattr(Event, name, None) 探测 —— 老上游/新上游都能跑。 - _probe_features() 改探统一帧：UNIFIED_CHANNELS 长度 39 且 decode_unified 可调等。

11.10 上游 2.1.0「拉取模式」的跟进记录（v2.0 的自时钟被真机推翻）

权威文档：RemoteControl/docs/CHANGELOG.md [2.1.0]、 传输模式重构设计方案.md §6.1（事故与整改）、传输模式接口设计.md §3.5.1（拉取器）。 一句话：协议主线原则不变（单流 / 请求-响应 / 上位机能算的不传）， 帧格式零改动（仍 53 B / TYPE=0x0A / 39 个扁平通道）， 改的只有"谁控制发送节奏"这一条。

一、事故：自时钟把蓝牙模块的缓冲灌死

v2.0 的规则是"设备自时钟、无 Hz 上限"，它假设"背压会让帧率自动收敛到链路真能力"。 真机证明这个假设是错的：

项 实测值
这条链路的端到端持续吞吐 ≈100~200 B/s
单条命令应答往返（MAP DUMP 120 B） ≈1.21 s（不是早期记录的 230 ms）
v2.0 自时钟压上去的速率 53 B × ≈217 Hz ≈ 4.3 KB/s
超出链路能力 约 20 倍

后果：蓝牙透传模块的内部缓冲被灌满后停止转发，且不会自行恢复（必须给模块重新上电）。 现场表现极有辨识度 —— PING / ARM / GET ALL / MAP DUMP 这些小的、一次性的突发全部正常； 一经 STREAM ON（开始持续流）立刻 0 字节；之后连 PING 都不应答。

根因不在固件，而在"谁能控制发送节奏"：固件把 TX 环当背压信号， 但蓝牙模块的内部缓冲对 MCU 完全不可见 —— MCU 侧 TX 环空不空，与模块灌没灌满毫无关系。 在 MCU 这一侧成立的假设，跨过蓝牙透传就不成立了。

关键证据（历史，也是这次最该记的一条）：v1.5.5 的 link.c 里本来就写着这条约束 ——"其内部缓冲一旦被灌满就会停止转发，且不会自行恢复（需要模块重新上电）"， 并因此用一个分频把常驻速率刻意压到 152 B/s。 v2.0 重写链路时把这条注释连同分频一起删掉了。 ⇒ 教训：上游源码里的"现场约束注释"是取证材料，不是历史包袱。 删掉一条注释不会让约束消失，只会让下一个读代码的人重新踩一遍。 本层因此把这条结论写进了 adapters/mouse.py 的模块 docstring（那里也写了"为什么"）。

二、修法：把发送节奏交给上位机

PC  -> TELEM
设备 <-  一帧统一帧(53 B) + `ACK <seq> OK <upMs>`(带时间锚)
  • 删除 STREAM ON / STREAM OFF；新增 TELEM（no_retry=True, timeout=3.0）。 命令 23 → 22 条。固件删除"开流"状态与自时钟组帧，收到一条 TELEM 才发一帧。
  • 自愈性质：PC 停止请求 → 固件不再发送 → 蓝牙缓冲自然排空 → 无需断电即可恢复。 （真机已验证：停发 10 s 后帧计数不再增长，再发 PING 立刻应答。）

三、为什么是停等而不是流水线（这一层也被真机否决过一次）

最初的 v2.1 把拉取器实现成"滑动窗口 + AIMD"（窗口 1..16 自适应）。真机证明这是错的。

根因：固件每 1 ms tick 只消费一行命令（link.c 的 USART_RX_STA & 0x80 未清时， usart.c 把后续字节直接丢弃）⇒ 同一时刻只能有 1 条命令在飞。

背靠背发 N 条 TELEM 回收率
1 100%
2 50%
3 33%
4 25%
8 12%
间隔 300 ms 逐条发 100%

固定窗口扫描（每档 6 s）：窗口 1 = 6.50 Hz（RTT 153 ms）、窗口 2 = 6.49、 窗口 4/6 = 7.15 —— 窗口 1 已经拿到 1/RTT 的满速，加大窗口只多约 10% 却开始成串丢。

⇒ 改为严格停等（_refill() 只在在途为空时才发下一条）。停等不是软件限速， 而是协议层的物理约束，且比堆在途请求更快（每条请求都真的换回一帧，零浪费、零丢失）。 真机停等复测：12 s → 53 帧 = 4.41 Hz（≈234 B/s 载荷），在途恒 1、丢 0、bad_crc 0， 单帧往返 157~234 ms。

⚠️ 中途有一次误判值得记：曾扫到一个 153 ms 的 RTT，据此以为"可以流水线提速"。 实际 RTT 在 143~527 ms 波动，153 ms 只是链路延迟的波动下限。 ⇒ 判断"能不能流水线"时，不能用一次采样的最小值当基线。

六、对真机操作的三条实务结论

  1. stream.off() 是排障手段，不是省流量开关。v2.1 的 off() 会立刻丢弃在途请求 —— 这是让蓝牙模块缓冲排空的唯一办法。现场遇到"连 PING 都不答"时，第一动作是关掉遥测， 等十几秒，而不是断电。
  2. "提高波特率就能提高帧率"已被证伪。一帧 53 B @115200 在串口上只占 4.60 ms， 而 RTT 是 157~234 ms ⇒ 瓶颈是蓝牙透传模块的转发延迟，与串口速率无关。 要真正提速得换掉蓝牙透传（或改有线）。
  3. 帧率是"涌现"的，不是设的。"没有软件 Hz 上限"这条原则仍然成立， 只是数上限的人从固件换成了上位机：收敛点自然落在 1/RTT。

11.11 「实验 8」改三栏 + 从发车到停止的记录与复盘

需求原话：左侧实时显示状态机与关键传感器；中间显示重构示意位置（搜了哪里、认为哪里有墙）； 右侧按时间线展示状态机与决策的变化历程、可滚动；从发车到停止的所有数据都要记录并保存， 且界面能导入过去的记录做复盘。

一、三栏的数据来源（都在，不用新上游能力）

栏 数据来源 为什么不另找
左：状态机 + 转速/红外/陀螺/位置 统一帧的对应通道（mazeTask/motionTask/speedL,R/ir*/gyroAngle/posX,posY…） 一份帧就是全量快照，不需要任何点查
中：重构示意 GET /mouse/maze/reconstruct —— 从最近一段帧按朝向累积 见下节"墙图不存，重建"

二、墙图为什么不存快照，而是从帧重建

每帧都带 wallLeft / wallFront / wallRight（体坐标）与 dir（朝向）， 所以把三面墙按朝向旋到绝对方向再累积，就是一堵一堵长出来的"它眼里的迷宫"。 这样做有三条直接好处：

  1. 记录文件不必复述墙图 —— 复盘时重放帧序列即可确定性重建，文件里只留一份对账基准。
  2. 实时中栏不用发命令。固件那份墙图要走 MAP DUMP（真机 ≈1.21 s 往返）， 跑动中拉一次就占掉一次拉取机会；而重建走的是上游环形缓冲的纯内存读。
  3. 能看见"什么时候才知道那里有墙" —— 快照只有此刻的样子，重建带时间维度。

⚠️ 朝向旋转是最容易错的一步（把左右墙弄反，图会整体镜像且看着像对的）⇒ 自测里四组朝向逐个验过 front/left/right 的落点，并负向验了"背墙读不到"那一面 （known 只该有 3 面，不是 4 面）。固件那份墙图一并返回，作对账用。

第一版我把记录器的数据源接在了本层的 mouse.telemetry 总线消息上 —— 结果是 recording=True 却 frames=0：因为那条消息由 sampler_loop 发，而它 只在有浏览器订阅二进制帧时才发（if not self.bus._bin_subs: continue）。 ⇒ 记录器会"没有数据，而且一声不响"。

四、自动收尾为什么是弱判据（必须有人工兜底）

固件没有"迷宫结束"事件 —— MAZE RUN 之后就一直处于迷宫态。 所以"从发车到停止"里的"停止"没有权威信号，只能组合弱判据： STOPPED 事件 / 任务机离开 WAIT 后回到 WAIT 持续 N 秒 / 链路断开 / 帧数上限。 ⇒ 界面必须同时给【停止并保存】这个人工兜底按钮。 模拟器上尤其明显：它的 maze_running 压根没有设回 False 的路径， 不点一下根本收不了尾。这条如实写进界面文案，不假装"自动就够"。

⚠️ 2026-10-05 补充（上游 2.1.1 / 2.2.0 起）：上面这段的结论仍然成立 （"设备不宣布跑完"这件事没变），但"收尾"的手段变了 —— 现在有两个正经动作： 【收车】MAZE STOP 与【救援】MCU RESET（见 §11.12）。所以界面上是三个按钮， 各管一件事，不合并：

按钮 干什么 什么时候用
【停止并保存】 存盘（只动文件，不动车） 想把手上的数据先落下来
【收车】 动车：停车 + 复位发车状态 + 解锁急停 跑完了正常收；车在运动时不可靠
【救援】 动车：整机软复位 收不住、卡死、失控

分成三个而不是一个，是为了让"车还在跑时先把已收到的存一份"这件事成立 —— 现场真的需要（跑长盘时想中途存一次快照）。

五、记录文件格式（自包含、可导入）

一份 JSON，字段分五组：元信息（起止/时长/mazetype/why/end_why/auto_end）、 帧（channels 一行列名 + t_ms 一行时刻 + frames 每帧一行的值数组）、 迁移序列（changes）、上行事件（events）、完整性（帧数/evq_seen/drop_seen/tiny）、 外加 wall（重建结果，供快速预览）与可选的 firmware_map（对账基准）。

为什么列名行 + 值数组而不是每帧写一遍键名：一帧 39 个键名重复几千次，文件会大好几倍。 代价是列序依赖 channels ⇒ 导入端必须读文件里的 channels，不许假设固定顺序。 t_ms 用相对起点的整数毫秒（再省一截）。

⚠️ 时基统一：帧时刻与事件/迁移时刻必须同源。第一版帧用"帧发生时刻"、 事件用"回调到达时刻"，两者不同基 ⇒ 复盘时间轴会整体错位（而且图看着还对）。 现已统一到同一单调时基，另有一列 t_dev_ms（帧的设备时刻）只作附加、不参与排序； 且只有每一帧都算得出时才写 —— 部分有部分没有的列，读的人不知道该信哪一半。

六、复盘态：同一套渲染，换数据源

导入记录后进入复盘态：一个时间游标驱动三栏，与实时态用同一套渲染函数， 差别只在"数据来自游标时刻的帧"而不是"活帧"。好处是复盘看到的就是当时看到的， 不会出现"实时和复盘两套画法、结论不一样"。

11.12 上游 2.1.1 / 2.1.2 / 2.2.0 / 2.2.1 的跟进记录（"能不能把车收回来"）

这一批四个版本全部由真机事故驱动。主题只有一个：发出去的车要能收回来。 本层在这轮里被推翻了一条结论，也被抓出一个一直没红过的真缺陷 —— 两件都比 "接口变了"要紧得多。

一、被推翻的结论："没有'停止跑迷宫'"

旧结论（写在 §11.9 / §11.11 / 未实现功能.md / README 里）：MAZE RUN 之后固件主循环 停在 LESSON_Blind8() 的 while(1) 里、linkMazeReq 只有上电才清零 ⇒ 发车状态永不复位 ⇒ 再发车永远 ERR_BUSY，只能断电。

新事实分两层，两层都要记住：

手段 可靠性
2.1.1 MAZE STOP（mc.maze.stop()）：停车 + 复位发车状态 + 解锁急停 ⚠️ 车在运动时不可靠
2.2.0 MCU RESET（mc.conn.soft_reset()）：整机软复位，BSS 清零 ✅ 可靠

为什么 MAZE STOP 运动时不可靠（这是本轮最值得记的一条）：它只置一个"请退出"标志 （linkMazeAbort），而标志的检查在 LESSON_Blind8() 的 while(1) 顶部； 主循环却有 30 余处非协作式阻塞等待（motion.c 的 while (odomStr.cellOdom < dis) ; 等，等的是编码器里程这类物理进度）。车在运动时程序正卡在那些循环内部， 标志根本轮不到 ⇒ 真机实测：MAZE STOP 回 OK，但 mazeTask 仍 SEARCH、 MAZE RUN 仍 ERR_BUSY。

⚠️ 顺带解释了 2.1.1 之前那个"越停越死"的现象：STOP 会把 freemode 置 1 ⇒ MOTOR_LoopControl() 输出恒 0 ⇒ 轮子永不再转 ⇒ 那些"等物理进度"的条件 永远不可能满足。命令通道照常回 OK，但程序卡在函数内部。 而看门狗也救不了：喂狗在 LINK_Tick() 里、由 SysTick 中断调用 ⇒ 主循环卡死对看门狗不可见（rst 仍是 POR）。

二、本层的真缺陷：三个动作端点一直是 404（含急停）

接"急停锁存中发车回 ERR_ESTOP"这条路径时才发现：

POST /api/v1/mouse/estop  →  404  {"type":"KeyError","message":"'ESTOP'"}
POST /api/v1/mouse/stop   →  404  {"type":"KeyError","message":"'STOP'"}
POST /api/v1/mouse/tare   →  404  {"type":"KeyError","message":"'TARE'"}

根因：本层的 _simple_cmd() 把线上文本（"TARE"/"STOP"/"ESTOP"）当成了 上游 mc.send_cmd() 要的登记名（"tare"/"stop"/"estop"，全小写）。 而 send_cmd() 第一件事就是 COMMANDS[name] ⇒ KeyError。

为什么这么久没被发现：没有任何判据调过这三个端点。于是：

  • 顶栏那个急停按钮一直是死的 —— 点了只吃一个 404；
  • 界面上【清零 TARE】也是死的（mod_params.js 的标题里就挂着它）；
  • 而所有判据、所有文档、所有"已实现"的标记都还是绿的。

⇒ 这是"一道从没红过的闸不算闸"的推广，值得当成一条新纪律： 每个"动作按钮"都要有一条端到端判据真的走一遍，不能只判"控件在不在"。 控件在、回调绑对了、接口通、线上文本正确 —— 四件事缺一不可， 而前三件都能过、第四件错了，界面上完全看不出来。 已落成 I28（逐条真调这三个端点并核对回来的 cmd 是线上文本）。

三、低电硬闸：ERR_LOWBATT

事故链（真机）：battMv 一路 7681 → 6747 → 3962 mV（松载回升，典型带载跌落） ⇒ 低电时红外发射管变暗 ⇒ 回波微弱 ⇒ 墙检测失效 ⇒ 电机驱动在跌落电压下行为也不确定 ⇒ 现场"电机一直转、且对红外障碍物不再敏感"，操作者被迫强行断电。 而固件对低电没有任何保护动作（safety.c 只算出 battMon.low 供显示）。

修法：在 CommandSpec 登记表层加 precheck，挂在 maze.run 上， 阈值 registry.LAUNCH_MIN_MV = 7000。

⚠️ "放在登记表层而不是某个 API 方法里"是本轮最值得学的一处设计： 先前 MazeAPI.run() 里也能检查，但只要有人写 mc.send_cmd("maze.run") 就绕过去了 —— 而现场脚本恰恰这么写。放在 send_cmd 里执行，脚本 / CLI / datalog / 将来 JSON-RPC 一律绕不开；明确的绕过通道是 send_raw("MAZE RUN")（逃生舱，一眼可见）。

⇒ 与本层"闸门放在最底层、放在所有入口之下"是同一条思路 （对比：本层的 ctx.session_open 是唯一闸，/health 与后台探测绝不代启进程）。

本层做的事（不重复实现闸，只做"提前可见"与"如实转达"）：

  1. caps.launch_min_mv 从上游取（registry.LAUNCH_MIN_MV），不写死 7000 —— 写死会在上游改阈值后变成谎；取不到就不预判。
  2. GET /mouse/launch_precheck：零设备访问（只读最新帧），三态 ok/warn/unknown。 判据与上游逐条对齐（battMv == 0 是"电池监视未开启"不是没电 ⇒ 不拦； 取不到帧 ⇒ 不拦），否则会出现"界面说没问题、发车却被拒"。
  3. 发车端点把预检结果随应答带回，界面上提前把话说出来（B36 守，含负向）。
  4. ERR_LOWBATT 的文案说清 "这是上位机的保护闸，不是设备拒绝 —— 命令压根没发出去" （它连链路都没碰，所以带得出实测电压）；否则现场会去查固件。

四、"急停按了不停"的真正根因（2.1.2）

用户报告"急停发出去以后电脑鼠没有立即停止"。实测（真机 COM7，原地转圈中发 STOP）：

需要重发 从发命令到实测转速归 0
修复前（拉取器开着） 1/5 3220 ms ← 正好等于 MOVE RUN 的 3000 ms 时间护栏
修复后（先让路） 0/5 594 ms

3220 ms 这个数字是判据：它不是"慢"，而是"根本没生效" —— 车是被 MOVE 自己的 时间护栏停下的。根因是链路层争用：固件每 1 ms tick 只消费一行命令， 而拉取器在持续发 TELEM ⇒ 同时下发的 STOP 只要与某条 TELEM 落进同一个 1 ms 窗口 就被丢掉，上位机只能等 TIMEOUT_S（2.5 s）超时重发。

修法（纯主机侧，固件一行未动）：给 11 条"慢一拍就出事"的命令标 urgent， 发送前 stream.suspend()（等在途 TELEM 收尾即证明固件已消费完那一行）→ 发 → resume()。

对本层的意义（三条，都要记）：

  1. /mouse/stream 的开关不是唯一的刹车了 —— 上游自己会为时间敏感命令让路。 本层不必也不该去手动 suspend（那样反而会和上游的嵌套计数打架）。
  2. resume() 只在"原本在跑"时才恢复 ⇒ 本层 /mouse/stream {"on": false} 的语义 不受影响，I22 的负向（"关掉拉取后帧不许再涨"）仍然成立（已复跑确认）。
  3. ⚠️ send_raw 也会让路 ⇒ 逃生舱不再是"绕过一切"的口子（这是好事，但要写清楚）。

五、maze.run 的失败语义：三种，处置完全不同

以前本层把失败一律翻成"只在数据收集档实现 / 其余回 ERR_VALUE" —— 那句在 ERR_BUSY / ERR_ESTOP / ERR_LOWBATT 三种情形下全是错的，会把现场引到错方向。

status 含义 该做什么
ERR_LOWBATT 上位机的低电闸拦下（data.blocked=True，命令没发出去） 充电/换电；台架强发把车架离地面后走逃生舱
ERR_ESTOP 急停锁存中（固件会收下请求，再被 ISR 每帧清零速度 ⇒ 现场"发了车却不动"） 先【解锁急停】（stop，线上 STOP）
ERR_BUSY 已在跑迷宫（发车状态没复位） 先【收车】；收不住就【救援】
ERR_VALUE 该固件档位没有这条命令 换数据收集档固件

六、界面上的三个按钮（不合并）

按钮 干什么 什么时候用 门控
【停止并保存】 存盘（只动文件、不动车） 想先把手上的数据落下来 不门控（断链时恰恰最需要它）
【收车】 动车：停车 + 复位发车状态 + 解锁急停 正常收；车在运动时不可靠 与【发车】同一门控
【救援】 动车：整机软复位 收不住 / 卡死 / 失控 与【发车】同一门控；设备窗口里也放一个

⚠️ "收车收住没有"要当场看得见：MAZE STOP 回 OK 只说明命令被接受。 所以应答里带 state / fresh / reliable，界面据此分三种说法： 收住了 / 没收住（提示改用【救援】）/ 判不了（没等到新帧）。 ⚠️ 而"立刻读状态"是错的：命令返回时环形缓冲里最新那帧仍是停车前的 （帧 1/RTT≈5 Hz 拉来，命令约 300 ms 返回）⇒ 会把已经成功的收车报成失败。 实测：回 OK 后立刻读 → task=SEARCH（看着没收住），1 s 后再读 → task=WAIT。 ⇒ 修法是等条件（有新帧）而不是等固定时长，并把它做成三态：等不到就报 None（判不了）。

救援的三条后果必须一起说（少一条现场就会踩）：

  1. 成功判据是复核 rst == "SW"，不是"ACK 收到" —— 固件先回 ACK 再延迟 ~150 ms 复位， ACK 可能与复位抢在一起而没出链路 ⇒ accepted=False 不代表失败。
  2. 复位只复位固件、不复位物理位置：mousePos/mapWall/stackIdx 全被清零， 而车还在迷宫原处 ⇒ 此时发车会按"我在起点 (0,0)"的错地图行驶， 既不认路也不认墙（2.2.1 正为此修了它自己的复现脚本）⇒ 发车前必须人工把车放回起点角。
  3. 复位后约 3 s 才有新遥测帧：此前读到的是复位前的旧帧，或 main() 尚未初始化完的 早帧（带 BSS 初值，例如 freemode=False）⇒ 判读状态要等新鲜帧，读一次就下结论会拿错。 （本层的做法：救援后故意等 3.2 s 再去读状态，而不是立刻读。）

11.13 「实验 8」右栏的决策差分：8 类判据与它们的上游依据

一、为什么决策必须由主机差分

上游 v1.5.5 曾有一条 MAZE EV <EVENT> 事件流（TASK/ROAD/JUNC/TURN/GOAL/CELL）， 那是"它识别到了什么"最直接的表达。v2.0 把它整条删了 （RemoteControl/docs/迷宫状态机回传.md §3.1），理由与 SNAP/SCOPE 相同： 状态量已全部在统一帧里。代价是"事件"这一层没了 —— 上游自己只在 MazeAPI.task_changes() 里补了任务机一种差分，其余要调用方自己来。

⇒ 本层的 control/maze_rec.py::MazeDecisions 就是那个"其余"。它把帧序列差分成 与当年事件流同构的决策序列，于是现场重新看得见"它在哪一刻识别到了什么"。

二、8 类判据（每一类都取帧里的返回值，不许凭印象）

kind 判据（帧通道） 上游依据
TASK mazeTask 变化 上游 task_changes() 同判据
ROAD 路口分类变化，仅 task==SEARCH 且连续 2 帧一致 迷宫状态机回传.md §4：固件只在搜索决策态评估（"行驶途中侧向开口会一闪而过，全程评估会大量抖动"）+ 20 ms 去抖（连续 2 个采样一致）
TURN motionTask 进转弯类码 MOTION_TASK_NAMES —— 当年 MAZE EV TURN <MOTION> 报的就是这个
STRAIGHT motionTask 进直行类码 ⚠️ 当年事件流没有这一条，是本层按现场要求（"要看得见直行"）加的
JUNC stackIdx 变化 当年 MAZE EV JUNC <stack>
CELL (posX,posY) 变化 当年 MAZE EV CELL（上游标注"默认关，因为量最大"）
HEAD dir 变化 帧里的 dir。"朝向变了"是事实，"转向动作"是动作 —— 两者不是一回事，所以分开报
GOAL posX==goalX && posY==goalY 首次为真 §4「终点判定」

三处刻意的设计选择（写清楚，免得后人当成疏漏）：

  1. TURN/STRAIGHT 只在"跨越类边界"时报（进转弯报一次、进直行报一次），不是每帧都报。 否则一盘下来几百条"直行"，把真正的决策淹掉。实测：模拟器跑 30 s ≈ 45 条 STRAIGHT、 45 条 TURN、62 条 ROAD —— 与"每个路口一次"的密度一致。
  2. GOAL 的判据比固件窄：固件的判据是"落在两个目标格（起/止）的并集里" （(x==xGoal0||x==xGoal1) && (y==yGoal0||y==yGoal1)），而统一帧只给了一对 goalX/goalY ⇒ 主机这边只能做等值判定。所以它报的是"进入了它认为的那个目标格"， 不是"固件的终点区判定为真"。这处差异如实标注，不假装一致 —— 真机验收时要专门看这一条对不对得上。
  3. 第一帧只播种、不产事件：否则时间轴开头会冒出一条"从 0 变到 X"的假迁移 （from 是结构体的零值，不是真实的前一个状态）。

三、码表从外面注入（本层不复制上游的码表）

maze_rec.py 不 import 上游 —— 这是有意的：记录器要能在"上游不可用"时继续工作 （帧已经收到了，就该能存下来、能画出来）。所以 road / motion 的名字由适配器 （MouseAdapter.maze_codes()）从上游码表构造后注入。

注入不到时 MazeDecisions 如实降级：只产不需要码表的四类 （TASK/CELL/HEAD/GOAL），界面在计数旁标「缺码表」—— 而不是自己编一份码表（编一份必然与上游漂移，且没人会发现）。

⚠️ 注入时机有个坑：ctx 建记录器与本适配器 _load() 完成的先后不确定 （_load() 里有一堆可能失败的步骤：路径注入、能力探测）。只在 ctx 构造时给一次的话， "装载晚于 ctx"这条路上码表永远是空的 ⇒ 右栏只有任务迁移、没有路口/转向， 而且不会有任何报错（降级是"如实"的）。⇒ 所以 _load() 成功后再补一次 （set_codes，它会把常驻环清掉，免得环里混着两类密度不同的数据）。

四、记录文件里的 decisions（以及老文件怎么办）

落盘时 decisions 每条的 t_ms 会减去 t0（第一帧时刻） —— 与 t_ms 列、 changes、events 共用同一个零点。混用两种时基会让复盘时"事件插在帧序列的哪一帧" 系统性偏移几百 ms，而图看着还是对的（这个坑 feed() 的 docstring 里记过）。

⚠️ 老记录没有这个字段（它是本版新增的）⇒ load() 时从帧重放重建 （rebuild_decisions），并标 decisions_rebuilt=true。这不是权宜之计： 帧在，决策就在 —— 差分是纯函数，同一份帧序列必然算出同一份决策。 它还有个额外好处：差分逻辑演进后，旧文件也能享受到新判据。

11.14 「回放和实时的决策树不一样」：两条来路必须同一个纪元

一、现象与第一现场的判断

现场看到的是：进入回放 → 读到的决策/事件，与退出回放后实时那条对不上 （"连接到电脑鼠也有这个问题"）。这一条不是"哪边数据脏了"，而是两条来路本来就不在说同一件事。

先把来路分清（分清之后问题就只剩一处）：

来路 数据从哪来 谁做的差分
实时（右栏时间线） 记录器内存里的常驻决策环 _dec_ring 记录器自己的常驻差分器 self._dec
回放（拖进度条 / 进入回放） /mouse/maze/record/live 内存快照，或 records/maze/*.maze.json 这一段自己的差分器 r["_dec"]（落盘那份由 rebuild_decisions 重放）

回放用的是"从帧序列重新算一遍"（差分是纯函数，所以重放必须得到与实时逐条相同的决策）。 ⇒ 只要两边的起点（纪元）一致，逐条必然相等；对不上 ⇒ 起点不一致。

二、根因：start() 只挪了零点，没换"这一段"

旧 start() 做的是"把常驻环的时间零点挪到发车时刻"（self._dec_t0 = self.start_ms）， 既没有清环，也没有重置差分器。于是发车那一刻环里还留着上一段收尾后与 本段发车之前（待机帧产生的）那些决策，相对新零点全是负时间。

实测复现（模拟器，两段）：

段 1 收尾后            环 151 条（t 8 … 14060）
段 2 发车后            环 303 条，其中 151 条 t_ms < 0（最早 −14180）

回放那条从快照重新差分，不会有这些"史前"条目 ⇒ 两条来路必然对不上。

这里有个更坏的性质：负时间看起来不像错误。时间轴上它们被渲染在开头， 图能画、数能看，只有"和回放一比发现对不上"才会暴露。

三、修法：_reset_epoch() / restore_epoch()

把"开一段"这件事做成原子操作（control/maze_rec.py）：

  • _reset_epoch(kind, stash=True) —— 开新纪元。顺序是： 1. 存：(差分器, 决策环, 零点, 零点语义, 事件环) 整体进 _dec_stash（仅 stash=True）； 2. 换：self._dec = MazeDecisions(...)（全新的差分器 —— 它内部还记着"上一帧"， 不清就等于让新段的第一帧和旧段的最后一帧去比较，照样产出一条假迁移）； 3. 清：self._dec_ring = []、self._ev_ring = []； 4. 零点：self._dec_t0 = None + _dec_t0_kind = kind（默认 "launch"）。
  • restore_epoch() —— 把 _dec_stash 整套放回去，返回是否真的回滚了。 供"发车被拒"这条路上用：一次没开成的发车不该把右栏正在看的那一段抹成空的。

⚠️ 清环用的是重新赋值 = [] 而不是 .clear()：常驻环是列表， 但别处（快照/落盘）可能持有的是同一个列表对象的引用；= [] 把"换一份"的意思写明确。 set_codes() 里也一并同步（码表注入会改变两类决策的密度，环里不能混着两种密度）。

四、零点语义：新段的第一帧说了算

feed() 里零点是这样钉的：

if self._dec_t0 is None:            # 新纪元还没落零点
    self._dec_t0 = now_ms
    if self._dec_t0_kind != "launch":   # 不是发车开的段（纯手动记录）⇒ 如实说"从收帧起"
        self._dec_t0_kind = "rx"

t0_kind 会随 live_decisions() 回给界面，界面照它写"发车后 x s"或"从收帧起 x s"。 零点还没有时给 None（而不是猜一个时刻）—— 判不了就说判不了（纪律 4）。

这套零点与落盘那份的 t0 同源（都是"发车后的第一帧"）⇒ 复盘时"事件插在帧序列的哪一帧" 不会系统性偏移。

五、"收到几帧"是个看运气的判据（被这一轮带出来的）

发车失败（ERR_LOWBATT / ERR_ESTOP / ERR_BUSY …）时该不该把这次记录收掉 + 回滚纪元， 旧代码判的是 if not st.get("frames")。这条判据不确定：start() 之后到命令往返完成 要 1~3 s，这期间待机帧照样在进来 ⇒ 同一段代码有时收、有时不收。

⇒ 改成由 start() 的应答给出 fresh_epoch（"这一次是不是新开的段"）：

fresh_epoch 含义 处置
True 这条记录是本次刚建的，随后发车被拒 它只装着"被拒之后的待机帧"，对复盘无价值 ⇒ 收掉 + restore_epoch()
False 本次是"沿用已在记的那一段"（start() 回 already） 那段可能是真在跑的数据 ⇒ 原样不动（收掉反而把它截断）

六、判据

工具 断言
drill I30 ① 实时环 ≡ 快照（逐条相等，含 t_ms / kind / 详情）；② 落盘那份 ≡ 环；③ 负向：换段不残留（发车后环里不许有负 t_ms）；④ 负向：发车被拒不抹数据（restore_epoch 后环条数 == 发车前，keep_ok=None 表示"没等到新鲜帧 ⇒ 判不了"）

⚠️ 报红时必须带原话：I30 在失败时把 m30 / m31 两条原始应答打出来。 只给一个 code=409 的判据等于没判 —— 它指不到任何方向（纪律 13 的同一条）。

七、前端这一侧：一个数据只允许有一条来路

  • 删掉模块级 evs 数组；renderTimeline() 的实时分支改从 live.events 取（后端同零点给的）。
  • mouse.upevent / mouse.estop 这两条 WS 消息不再往数组里 push，改为催一次重拉 （loadDecisions()）—— 事件由后端登记，前端只负责取。
  • 推论（写进纪律 32）：后端能算的，不要前端自己攒；攒出来的一定是第二条来路， 两条来路就一定会漂。
