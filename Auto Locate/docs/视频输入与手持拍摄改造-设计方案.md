# 视频输入 · 手持拍摄 · 发车对轴 —— 改造设计方案

> 版本定位：**方案设计（未实施）**。目标是先把接口与形状定下来。
> 细节（阈值、t0 语义、亚帧精度等）**等测试视频到位后再定**，本文档一律给出"预留位"。
> 现状基线：`aruco_locator` v1.1.0（对外接口冻结）+ `maze_extract.py`（独立脚本）。

## 0. 一页摘要

| 变更 | 性质 | 对算法核心的冲击 | 结论 |
|---|---|---|---|
| ① 输入：视频流 → 真实视频文件 | **改造已有通道**（`sources.py` 已支持视频，但时基不可信、无区间/跳帧控制） | **零** | 新增时基层 + 前置体检 |
| ② 拍摄：固定机位 → 手持 | **约束放松**（相机位姿逐帧变化） | 定位核心**零冲击**；但有 3 处"全局常量假设"被打破 | 逐帧化 + 强制关时序滤波 |
| ③ 新增：LED 发车对轴 | **全新能力** | 零（旁路模块） | 新增 `led.py`，两遍扫描 |

**不动的东西**（务必保持）：`detector.py` / `corners.py` / `geometry.py` / `parallax.py` / `viz.py`
内部算法一行不改；`Localization` 数据结构与 `CSV_FIELDS` 不改；`config.yaml` 既有字段语义不改。

## 1. 现有架构为什么对"手持"天然友好

这是本次改造最重要的一条判断，先说清楚：

> **管线是逐帧自建坐标系的。** `geometry.build_frame()` 用**当帧**检测到的 4 个角标记现场解出
> `H_img2field`，场地系（原点=离画面左下角最近的角点、+x/+y、[0,1]²）由这一帧自己定义。
> 下一帧相机跑到哪里、转了多少度，对下一帧毫无影响。

推论（决定了整个改造的形态）：

1. **手持不需要任何额外标定，也不需要跨帧配准、不需要特征跟踪、不需要 SLAM。**
   相机运动被"每帧重新定义坐标系"这件事自动吸收了。
2. 手持下输出的 `(x, y, θ)` 仍然是**场地系绝对量**，不是增量 —— 所以逐帧结果直接就是轨迹点。
3. 手持带来的真实退化只有两类，且都是**每帧独立**的：
   * **运动模糊** → 角点精度下降 → 位置/角度噪声变大（不产生系统性偏移）；
   * **视角变化** → 角标记在画面里的尺度/透视变化大 → **检出率下降**（缺角标记 → 该帧无效）。
   → 都落在"有效性 + 质量指标"这一层，不触及几何解算本身。

## 2. 被打破的三处"全局常量假设"

这三处是本次改造的**真正内容**。

### 2.1 视差修正的相机参数是常量（最需要改的一处）

`config.camera.parallax` 现在是标定一次的常量：

```yaml
camera_height_mm: null    # ← 必填：镜头光心离地高度
nadir_xy: [0.5, 0.5]      # ← 相机正下方那块场地位置
from_intrinsics: true     # nadir_xy 为 null 且有内参时，用单应分解自动求天底点
```

手持下这两者**逐帧变化**（人站着拍，手臂晃动 ±20cm；相机还会前后左右移动）。

**影响量级**（不是可忽略项）：
修正量 = `(k−1)·|X − N|`，其中 `k−1 = (h_c − h_t)/(Hc − h_c) = 27/(Hc − 50)`。

| 相机高度 Hc | k−1 | |X−N| 最大 0.5 场（720mm）时的修正量 |
|---|---|---|
| 1000 mm | 2.84% | **20.5 mm** |
| 1500 mm | 1.86% | **13.4 mm** |
| 2000 mm | 1.38% | **10.0 mm** |

**关键结论（好消息）**：`parallax.pose_from_plane_homography()` **已经能算出相机高度**。
它返回的 `C = -Rᵀt` 是光心在**场地系**中的位置，而场地是按**单位正方形**标定的 →
`C[2]` 直接就是"以场地边长为单位"的相机高度。乘以 `field_size_mm` 即为 mm。

于是手持下可以完全自动地逐帧得到 `(Hc, N)`：

> **前提只有一个：提供手机内参 K**（`calibrate_camera.py` 已有）。

* 有 K → 逐帧 `(Hc, N)` 自动，视差修正全自动；**不需要卷尺，不需要固定机位**。
* 无 K → 退回常量 `camera_height_mm` + `nadir_xy`（误差随 Hc 的相对误差等比例传递）。

→ 设计上新增开关 `parallax.per_frame_from_homography`（默认关，视频+手持模式建议开）。
→ 每帧把解出的 `Hc` / `N` 写进 `diagnostics`，便于事后核验（若 Hc 序列抖动异常大，
说明镜头畸变或内参不对 → 这是个免费的自检信号）。

### 2.2 时序滤波会破坏"时间轴"

`output.smooth = none | ema | moving_average`，默认 `none`。手持视频下：

* 帧间差异是**真实运动**，任何跨帧平滑都会平滑掉真实轨迹；
* 跳帧（stride）与平挠互斥 —— 平滑器的状态假设帧间等间隔，跳帧后假设不成立。

→ **设计决定（非存疑项）**：视频输入模式下**强制关闭平滑**，若配置里显式开启则打 flag
`smoothed_in_video_mode` 并仍然执行（把选择权留给调用方，但不静默）。
→ 平滑若确实要用，只在"帧号 = 时间轴且 stride=1"时才允许。

### 2.3 迷宫解算是"单帧"的

现有 `maze_extract.py` 从**一帧**解出 144 条墙段的三态。手持视频下这变成了：

> 场景静止、迷宫固定、相机位姿逐帧变化 → **同一面墙会在很多帧里被测到，而不同帧被遮挡的地方不同**。

这是一次**净收益**：多帧可以互相补盲，把单帧的 `UNKNOWN` 消掉。

→ 新增**会话级迷宫融合**：对 144 条墙段，累积所有有效帧的 `cover` / `conf` 与投票，
输出会话级三态 + **一致性统计**（多少帧说墙、多少帧说开）。
→ 一致性统计顺带成为**系统性错误检测器** —— 这正是 v1.0.1 那次事故的教训所要求的：
内部自洽指标抓不到系统性错误，而"不同机位解出的迷宫应当一致"是一个**外部绝对参照**。

## 3. 目标管线

```
┌─ 阶段 0  视频解码 + 时基 ───────────────────────────────┐
│  打开文件 → 前置体检(元数据/fps/VFR/旋转/编码) → 帧迭代   │
│  输出 FrameItem(frame, index, t_video, source)          │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─ 阶段 1  发车对轴（LED）─ 不需要定位，1/4 分辨率 ────────┐
│  扫全片 → 候选阶跃帧 → 窗口内确认 → t0 (+亚帧估计)        │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─ 阶段 2  逐帧定位 ── 完全复用现有 locate()，零改动 ──────┐
│  Localization × N  →  t_rel = t_video − t0               │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─ 阶段 3  会话级汇总 ────────────────────────────────────┐
│  轨迹表 + 有效率/无效原因 + 迷宫多帧融合 + 一致性报告      │
└─────────────────────────────────────────────────────────┘
```

**为什么阶段 1 放在阶段 2 前面**：对轴只需要蓝斑能量，1/4 分辨率下逐帧成本极低，
可以在几十秒的视频上秒级完成；而全分辨率定位单帧约 270ms（39 帧实测），
60s@30fps = 1800 帧 ≈ 8 分钟。先对轴 → 才能只对关心的窗口做重活。

**但这里有个矛盾（已识别，给出解法）**：手持会让画面平移，静止的蓝色物体也会产生
"逐帧新增像素"，所以纯时域阶跃判据不可靠。解法是**两遍扫描**：

| 遍 | 分辨率 | 目的 | 判据 |
|---|---|---|---|
| 第一遍 | 1/4 | 找候选窗口（宁滥勿缺） | 严格颜色 + 小斑块 + 能量阶跃，阈值放松 |
| 第二遍 | 全分辨率 (+定位辅助) | 确认 | 颜色 + 刚性几何 + 与 0 号标记共位 + 保持 N 帧 |

## 5. 接口契约

### 5.1 输入

| 项 | 说明 |
|---|---|
| 主输入 | **视频文件路径**（`mp4/mov/mkv/avi`…，现有 `VIDEO_EXTS` 已覆盖） |
| 区间 | `start_frame` / `end_frame`，或 `start_time_s` / `end_time_s`（**待加**，现在只有 `start` + `max_frames`） |
| 抽帧 | `stride`（**待加**）—— 长视频降本；与平滑互斥 |
| 配置 | `config.yaml` 新增 `video:` / `sync:` 段（见 §5.4） |
| 可选 | 相机内参文件（`intrinsic_file`）—— 决定视差修正能否逐帧自动 |

### 5.2 输出

**逐帧记录**（`trajectory.csv` / `.jsonl`，**新增文件，不改既有 `results.csv` 的列**）

```
frame, t_video_s, t_rel_s, valid, x, y, theta_deg, dir_x, dir_y,
rms_field, target_rms, marker_scale, origin_id, corner_ids, flags, reason
```

> `t_video_s` = 该帧在视频里的绝对时间；`t_rel_s = t_video_s − t0`（发车为 0）。
> 保留 `Localization` 原样不动，`t_rel` 在会话层计算 → **既有 CSV 契约不破**。

**会话汇总**（`session.json`）

```jsonc
{
  "video":  { "path": "...", "frames": 1800, "fps": 30.0, "size": [1920, 1080],
              "duration_s": 60.0, "timestamp_source": "container_pts",
```

### 5.4 配置新增段（**全部为预留，默认值不改变现有行为**）

```yaml
video:
  timestamp_mode: auto      # auto | container_pts | frame_index_over_fps
  orientation_auto: true    # 手机旋转元数据是否自动应用（横竖屏相关）
  preflight: true           # 打开时做体检并落盘元数据
  stride: 1
  start_frame: 0
  end_frame: null

sync:
  enable: false             # 没有 LED 视频前默认关（行为与现在完全一致）
  mode: two_pass            # two_pass | locate_first
  search_window_s: null     # [t0-2, t0+2] 与 t0 精确值未知不冲突，覆盖窗口即可
  led:
    hsv_low:  [100, 140, 190]    # H/S/V 下界（探针结论：必须比朴素阈值严得多）
    hsv_high: [140, 255, 255]
    min_blue_dominance: 80       # B − max(R,G) ≥ 此值
    expect_count: 4              # 预期 LED 颗数
    min_count: 2                 # 至少看到几颗才认（抗部分遮挡）
    min_blob_area: 4
    max_blob_area: 2000
    square_side_tol: 0.45        # 4 斑块构成刚性正方形的容差
    energy_step_ratio: 1.5       # 阶跃倍数（相对静止段的稳健上界）
    hold_frames: 2               # 持续多少帧才确认（抗单帧噪声）
    t0_mode: first_lit           # first_lit | all_lit | stable   ← 存疑 U1
    subframe: true               # 上升沿线性插值给出亚帧估计
  second_fiducial: false     # 把 4 颗 LED 当第二 fiducial 联合求位姿  ← 存疑 U9

camera:
  parallax:
    per_frame_from_homography: false   # 手持建议开（需 intrinsic_file）
    # camera_height_mm / nadir_xy 保留为回退路径
```

## 6. 已用探针确认的事实（本次实测）

三个探针脚本已放在 `experiments/`（**不进归档**，实测 `make_release.collect()` 仍为 43 文件）。
其中 `_probe_led2.py` 是"等视频到了直接跑"的对抗性测试，已写好待运行。

**事实 1 — 视频文件通道的**管线**是通的，但时间戳没有信息量。**
合成一段 29.97fps 的视频回读：`pos_monotonic=True`，但
`max|POS_MSEC − index/fps| = 1.1e-16` —— **完全等于"帧号 ÷ 元数据 fps"**。
→ 说明在 CFR 文件上 `CAP_PROP_POS_MSEC` 没有独立信息；
→ 手机视频若为 **VFR（可变帧率）**，这条路是否仍正确**必须用真实文件验证**（→ 存疑 U4）。
→ 因此时基必须**显式标注来源**并做**非均匀间隔检测**，不能默认信任。

**事实 2 — 朴素的蓝色判据完全不可用。**

| 判据 | 真实 39 帧像素数（960×540） | 中位最大斑块 | 合成 LED 表现 |
|---|---|---|---|
| `H∈[100,140], S≥110, V≥110` | 中位 **12413**，最大 17180 | 6509 px | 6435 px（淹没） |
| `+ S≥140, V≥200` | 中位 46，最大 494 | 27 px | 344 px |
| `+ B−max(R,G)≥90 且 B≥200` | 中位 14，最大 89 | 14 px | 124 px |

→ 放宽判据时，蓝掩码占全图 **2.4%**，比 LED 本身大三个数量级。
→ 收紧后仍**不可分**：真实画面里存在货真价实的饱和蓝色物体
（实测 `B=248, G=107, R=9`，蓝优势 **141**，单斑 89px），与合成 LED（蓝优势 ~200、单斑 ~124px）
只差 **约 1.4 倍**。
→ **结论：LED 检测不能只靠颜色，必须是"颜色 + 小斑块 + 时域阶跃 + 刚性几何"的组合判据。**
→ 这也意味着 **LED 的实际物理亮度/尺寸/在车上的排布必须现场实测**（→ 存疑 U2、U9）。

**事实 3 — 归档边界与既有接口未受影响。** 探针全部落在 `experiments/`，
`aruco_locator/` 未改一行，归档仍 43 文件、完整性检查通过。

## 7. 存疑与预留清单

原则：**每一条都给出"当前怎么预留"，不留空洞。**

| 编号 | 存疑点 | 影响什么 | 现在怎么预留 | 何时能定 |
|---|---|---|---|---|
| **U1** | LED 点亮时序语义：4 颗是同时亮还是逐个亮？亮多久？中途会熄灭吗？ | `t0` 定义、`hold_frames`、`t0_mode` | `t0_mode: first_lit` 为默认；三档可配 | 看到视频 |
| **U2** | 现场是否有其他蓝光源（蓝灯/蓝标/蓝色地贴/屏幕）与 LED 共存？ | 颜色阈值、几何约束是否必需 | 几何约束作为**独立开关**；阈值走配置 | 看到视频 |
| **U3** | 手机内参 K 有没有？ | 视差修正能否逐帧自动；缺角降级方案是否可行 | `per_frame_from_homography` 默认关；无 K 时自动退回常量路径并打 flag | 你确认（`calibrate_camera.py` 已有） |
| **U4** | 视频编码/帧率/是否 VFR/有没有开防抖(EIS)？ | 时基可信度；**EIS 会让逐帧内参漂移 → 破坏逐帧相机高度** | 加 `preflight` 输出容器元数据；时基来源显式标注；EIS 未定前**不打 flag 只记录** | 看到视频（建议拍时**关防抖**） |
| **U5** | 竖屏还是横屏、分辨率、时长 | 下采样倍率、性能预算、是否需要 stride | stride 与下采样倍率全部可配 | 看到视频 |
| **U6** | 是否需要亚帧精度的发车时刻？ | `subframe` 是否要启用、验收口径 | 默认开，但**明确输出为"估计"**，并给出物理不确定度（受曝光时间限制，非插值能改善） | 你定 |
| **U7** | 手持下是否每帧都能看到全部 4 个角标记？ | 有效率；是否要做"部分角标记"降级 | `require_all_corners` 保持 `true`（现状）；保留 `allow_partial_corners: false` 配置位，**不实现** | 看到视频 |
| **U8** | 期望的处理时间上限 | 是否需要 stride / 是否值得做 ROI | 两遍扫描结构已支持；ROI 留 hook | 你定 |
| **U9** | 4 颗 LED 相对 0 号标记的布局（间距/高度） | 能否把 LED 当**第二 fiducial**（0 号标记模糊/被墙遮挡时仍能出姿态） | `second_fiducial: false`，接口留 hook，不实现 | 现场量 |
| **U10** | 交付形态：进包（v1.2.0）还是保持独立脚本？ | 版本号、文档、归档内容 | 建议**进包**（这是定位主链路的扩展，性质与 `maze_extract.py` 不同）；迷宫融合仍留在脚本里 | 你定 |

**另外两条不算存疑、但需要你知悉的设计决定**：

1. **视频模式下强制关闭时序平滑**（§2.2）——除非帧号即时间轴且 `stride=1`。

## 8. 实施顺序（每步可独立验证）

| 步 | 内容 | 依赖 | 验证方式 |
|---|---|---|---|
| S1 | 时基层：`video.py` + `preflight` + 区间/跳帧 | **只要有一段视频** | 打印时长/帧数/时基来源；与 `ffprobe` 对照 |
| S2 | 会话汇总 + 轨迹输出（暂不含 LED） | S1 | 在一段手持视频上跑通，出轨迹图与有效率统计 |
| S3 | LED 对轴 `led.py` | S1 + **含 LED 的视频** | 先用合成视频验判据（`_probe_led2.py`），再用真视频验 |
| S4 | 迷宫多帧融合 | S2 | 对比单帧 vs 融合的 `UNKNOWN` 数量与一致性 |
| S5 | 视差逐帧化（`parallax` 改动） | S1 + 内参 K（U3） | 对比逐帧 vs 常量修正的位置差；检查 Hc 序列是否合理 |

S4 ✅（`run_session` 内置多帧融合，选帧标准 = 四角齐全帧，见会话级接口规范 §3.5）；

**建议顺序**：S1 → S2 可以**现在就做**（只要有任意一段手持视频就能验证）；
