# 归档说明 —— 电脑鼠蓝牙上位机 + LINK 通信层

> **归档版本**：`v2.2.1`　**日期**：2026-10-05
> **归档包**：`release/RemoteControl-v2.2.1-20261005.zip`
> **上一层归档**：`v2.1.2`（2026-10-05，同日）；更早 `v2.1.1`/`v2.1.0`/`v2.0.0`（2026-10-05）、`v1.5.5`（2026-10-04）
> **v2.2.1 性质**：**安全修正（真机事故响应）** —— ① `MCU RESET` 改为**复位前先停车**；
>   ② 新增**发车前低电硬闸**（`maze.run` 前置校验，`battMv < 7000 mV` 时回 `ERR_LOWBATT`）。
>   `API_VERSION="2.2.1"`，固件 `LINK_FW_VER` 213 → **214**，线格式未变。
>   **比赛固件 [5] ROM 90872 B，与 v2.2.0/v2.1.2 逐字节同尺寸。**
>
> ⚠️ **事故摘要（2026-10-05）**：用 v2.2.0 的 `MCU RESET` 后现场出现"电机持续旋转、
>   且对红外障碍物不再响应"，被迫强行断电。两层根因：复位前没停车（带着动力滑行）；
>   复位只复位**固件**、不复位**物理位置** —— 调用方紧接着发车，探索便按"我在起点"的
>   错误假设行驶（墙检测只更新地图、不是硬停车条件）。诱发因素是电池耗尽（同一现场
>   `battMv` 7681 → 6747 → 3962 → 4270 mV，而固件对低电无任何保护动作）。
> **v2.1.1 性质**：**缺陷修复版** —— 修掉"发过一次车之后 `MAZE RUN` 永久 `ERR_BUSY`、
>   连 `STOP` 也救不回、只能断电"（真机复现 2026-10-05）。新增 `MAZE STOP`（**命令 22 → 23 条**）、
>   固件 `LINK_FW_VER` 210 → **211**（**线格式未变**）。**比赛固件 [5] ROM 与 v2.1.0 逐字节同尺寸**，见 §3.2。
> **上一版性质**：**在 v2.0 上真机后被证伪、随即修正的版本**。
>   v2.0 的"固件自时钟全速流"把蓝牙透传模块的内部缓冲**灌死且不自恢复**（连 `PING` 都不应答、须断电重上）；
>   本版把遥测改为**上位机拉取（请求-响应）** —— 删 `STREAM ON/OFF`、加 `TELEM`，**命令 23 → 22 条**。
>   v2.0 的其余主线（单流统一帧、请求-响应下行、IWDG、标定改造）**不变**。
> **看这一份就够**：本包是什么、怎么用、验过什么、**没验过什么**（§5，别跳过）都在这里。

## 0. v2.1 到底变了什么（一表说清）

> v2.0 是"破坏性替换"，v2.1 是在 v2.0 基础上**又做了一次针对性修正**（详见最右列）。
> 传输主线自 v2.0 起未变，只有"谁控制发送节奏"这一条被真机推翻后重做。

| 维度 | v1.5.5 | v2.0 | **v2.1（本版）** |
|---|---|---|---|
| 上行帧 | 9 种（FAST/MID/SLOW/DUMP_HDR/DUMP_BLK/DUMP_END/MAP/TIME/MAZE） | **2 种**（`UNIFIED` 0x0A、`MAP`） | ≡v2.0（**帧格式未改**，仍 53 B） |
| 上行速率 | 常驻 ≈152 B/s（刻意压低，留 9× 余量） | **自时钟全速 ≈217 Hz**（无 Hz 上限，帧率由链路能力决定） | **上位机拉取**：**停等（一次一条，在途恒 1）**；**仍无软件 Hz 上限**，可达帧率 = 1/RTT（真机停等复测 4.41 Hz ≈234 B/s，见 §5.1） |
| 数据来源 | 双流：运动期间实时流 + 停车后 `SCOPE` 1 kHz 整块 `DUMP` | **唯一统一帧**：45 B payload、每帧都是全量快照 | ≡v2.0，但**改由上位机逐条 `TELEM` 拉取**（收到一条请求才发一帧） |
| 下行命令 | 41 条 | **23 条** | **23 条**（v2.1.0：删 `STREAM ON/OFF`、加 `TELEM` → 22 条；**v2.1.1：加 `MAZE STOP` → 23 条**） |
| 标定 | 发命令即回 ACK | **请求-响应**：这一采集步完成才回 ACK（`CAL` 不重发、超时 10 s） | ≡v2.0 |
| 时间基准 | `SNAP TIME` / 慢帧 | **`STREAM ON` 应答带完整 u32 时基**；每帧只带 `ms8` 低 8 位，主机同余还原 | **每次 `TELEM` 应答都带完整 u32 时基**（**每次拉取刷新锚**，失锁自愈）；每帧仍只带 `ms8` |
| 上行事件 | `STOPPED` / `ESTOP TRIP`，无序号 | **带 `#n` 序号**（与帧 `SEQ` 共用计数器；**不 ACK、不重发**，序号只用于检出丢失） | ≡v2.0 |
| 迷宫状态 | 三通道（`MAZE EV` 事件流 / `MAZE` 1 Hz 状态帧 / `SNAP MAZE` 点查） | 状态量并入统一帧；**路口 8 类改由主机侧 `classify_road()` 复刻** | ≡v2.0 |
| 看门狗 | 无 | **IWDG ≈2.0 s**；`PING` → `PONG ... <rst>` 回报上次复位原因 | ≡v2.0 |
| 命令超时 | — | `CommandClient.TIMEOUT_S = 0.50 s` | **`TIMEOUT_S = 2.5 s`**（真机往返 ≈1.21 s，取两倍余量） |
| 版本号 | `API_VERSION = "1.5.5"` | `API_VERSION = "2.0.0"` | **v2.1.1**：`API_VERSION = "2.1.1"`、固件 `LINK_FW_VER` **211**；v2.1.0 为 `"2.1.0"` / **210**；两者 `LINK_PROTO_VER` 均为 **3** |
| **1 kHz 红外采样** | 有（`doWallDetect()` @ SysTick，比赛依赖） | **保留，一行未动** | ≡v2.0 |

> 设计取舍与逐字段迁移映射见 `docs/传输模式重构设计方案.md`（**§6.1 是 v2.1 的事故与整改**）+ `docs/传输模式接口设计.md`（§3.5.1 拉取器）；
> 逐版本变更见 `docs/CHANGELOG.md [2.2.1]` / `[2.2.0]` / `[2.1.2]` / `[2.1.1]` / `[2.1.0]` / `[2.0.0]`。
> **程序 ROM 反而变小了**：v1.5.5 → v2.0 时 [5] 档由 96728 → 90936 B（双流录制/回传代码的移除抵掉了统一帧与 IWDG）；
> v2.0 → v2.1 又因删掉自时钟代码再省一点，[5] 由 90936 → **90872 B**（详见 §2.3）。

## 2. 版本台账

### 2.1 组件版本

| 组件 | 版本 / 值 |
|---|---|
| 归档版本 | `v2.2.1` |
| 上位机 API 版本 | `registry.API_VERSION = "2.2.1"` |
| 固件协议版本 | `proto = 3`（`PING` → `PONG <proto> ...`；v2.1 因命令集变化（`STREAM ON/OFF` → `TELEM`）由 2 进到 3） |
| 固件内部版本 | `fw = 214`（v2.2.1；213=v2.2.0 首版 `MCU RESET`，212/211=v2.1.1，210=v2.1.0，200=v2.0）。**线格式未变**，命令 24 条，故 `proto` 仍为 3 |
| 迷宫尺寸 | `mazetype = 7`（7×7） |
| TX 环大小 | `LINK_TX_BUF_SIZE = 256`（`PONG` 的 `txbuf` 字段回报；可当"固件指纹"） |

> ⚠️ v2.0 删掉了 `VER` 命令，`PONG` 取而代之（`PING` → `PONG <proto> <fw> <mazetype> <txbuf> <rst>`），
> 并多出第 5 个字段 **`rst` = 上次复位原因**（`POR` / `SW` / `IWDG` / `PIN`）。
> 连上设备后第一条就该发 `PING`：既拿指纹，也拿复位原因。
> `scopedepth` 一项随 `SCOPE` 删除，不再存在。
> **v2.1**：`proto` 由 2 升到 **3**、`fw` 由 200 升到 **210** —— 因为命令集变了（删 `STREAM ON/OFF`、加 `TELEM`）。
> 这是**协议指纹**，上位机据此可区分"对端是 v2.0 还是 v2.1 固件"。

### 2.4 Flash 页布局（v1.5.4 起，v2.0/v2.1 未变）

芯片 STM32F103RB：**Flash 128 KB / RAM 20 KB**。

| 页 | 用途 | 地址常量 |
|---|---|---|
| 0 – 100 | **程序区（101 KB）** | `IROM1 Size = 0x19400` |
| 101 | 运行数据计数 | `FLASH_ADDR_DATA_NUM = 0x08019400` |
| 102 – 114 | 运行数据录制区（实际擦除 13 页） | `FLASH_ADDR_DATA = 0x08019800` |
| 115 | **生产标定参数页**（`SAVE` 落这里） | `link.h: FLASH_ADDR_SYSCALIB` |
| 116 | 课程调参参数页 | `link.h: FLASH_ADDR_LESSONPARAM` |
| 118 – 127 | 迷宫 / 路径 / 红外标定表 / 陀螺零偏（**比赛持久数据，本版未动**） | `flash.h: FLASH_ADDR_BLOCK_STACK` 等 |

> v1.5.4 把运行数据录制区由 page 89 上移到 page 102：它原预留 29 页、实际只用 13 页，**虚设的 16 页还给了程序区**，
> 程序区上限因此由 88 KB 扩到 101 KB。顺带修掉一处真实冲突 —— 链路模块的标定页原先取 page 99，
> **正落在录制区的擦除范围（89..101）内**，触发一次 `FLASH_EraseRunData()` 就会连标定一起擦掉（已上移到 115/116）。
> ⚠️ 因为标定页搬了家，**刷本版固件后板上旧标定读不到、会回落源码默认值**（`TRACKL = 53.2015` 等），重做一次 `SAVE` 即可，这是**预期行为**。
> 迷宫/路径/`IRDATA`/陀螺页地址未变 ⇒ **不需要重新标定那些项**。

## 5. 未验证边界（诚实清单）

### 5.1 已经**测过**的

- 上位机全部 **516 项**（九套）自动化断言（**全部对模拟器**）；
  模拟器与固件在协议层逐字节一致。
- **真机（v2.1 排查期间，2026-10-05，COM7 @115200，CH340 + 蓝牙透传）—— 这是本轮最重要的实测**：
  - 端到端**持续吞吐 ≈100~200 B/s**；单条命令应答往返（`MAP DUMP` 120 B）**≈1.21 s**。
  - `PING` / `ARM` / `GET ALL` / `MAP DUMP` 这些**小的、一次性的突发全部正常**。
  - **v2.0 的 `STREAM ON` 一经触发持续流，链路立刻 0 字节；此后连 `PING` 都不回答，只有给蓝牙模块
    断电重上才恢复。** 已定位为**蓝牙透传模块内部缓冲被灌满且不会自行恢复**（详见设计方案 §6.1.1）。
  - 排查中**已排除**：`link_AckU` 坏（`ARM` 同函数、正常）、TX 环/DMA 坏（`MAP DUMP` 120 B 突发正常）、
    MCU 卡死（IWDG 已启用，卡死应 2 s 内复位，但 20 s 不恢复）、端口掉线
    （`list_ports()` 每 0.25 s 采样、持续 15 s，COM7 始终在）。
  - 这条实测**推翻了 v2.0 的两条推算**：① "链路能持续 1.38 KB/s"（那只是短突发）；② "命令往返 230 ms"（实为 ≈1.21 s）。
  - **背靠背回收率（同一轮真机）**：发 1 条 `TELEM` **100%**、2 条 **50%**、3 条 33%、4 条 25%、8 条 12%；
    **间隔 300 ms 逐条发 100%**。根因是**固件每 1 ms tick 只消费一行命令**
    （`link.c` 的 `USART_RX_STA & 0x80`，bit7 未清时 `usart.c` 直接丢字节）⇒ 拉取器必须**严格停等**
    （在途恒 1，见设计方案 §6.1.5）。
  - **停等版真机复测（修正后的拉取链路）**：12 秒收到 **53 帧 = 4.41 Hz**（≈234 B/s 载荷），
    **在途恒为 1、丢 0、`bad_crc` 0**；随后复拉 5 秒得 4.40 Hz、丢 0。单帧 `TELEM` 往返 **157~234 ms**。
  - **停发自愈验证成功**：停止拉取后静默 10 秒（帧计数不再增长），再发 `PING` **立刻应答 —— 不需要断电**。
    这直接证明"蓝牙模块缓冲只是被灌满、并非永久损坏"，"不再请求 → 设备不再发 → 缓冲自然排空"这条恢复路径成立。
- **真机（v1.5.0/v1.5.1 时期，COM7 @115200）**：参数写+回读、遥控流（`bad_crc=0`、`seq_lost=0`）、
  30 次阻塞轮询 30/30 成功。真机链路特征已固化：偶发 `ERR_CRC`（幂等重发自愈）、连上后第一条命令可能慢到 ~750 ms。
  > ⚠️ 当时记录的"稳态命令往返 ≈230 ms"**在 v2.1 排查中被重测并修正为 ≈1.21 s** —— 230 ms 低估约 5 倍。
- **v1.5.3 的运动互斥修复**：曾在真机验证过一次（第 2 条 `MOVE` 正确回 `ERR_BUSY`、时间护栏不再被重置）。

  **不是**拉取模式能期望的帧率 —— 拉取模式是**严格停等**，帧率 = **1/RTT**（真机实测 4.4~6.5 Hz），与窗口深度无关（窗口机制已删除）。

## 6. 归档纪律（下次照这个来）

### 6.1 顺序（**别搞反**）

1. **先全绿 + 重编译**（跑九套件、五档编译，记录**真实数字**）；
2. **接口一致性审计**（清点子 API/命令/帧/参数，核对 `API_VERSION` 与 CHANGELOG 一致）；
3. **修正过期文档**（尤其"当前状态陈述"里的数字；**历史 CHANGELOG 不动**）；
4. **写归档说明**（必须在打包**之前** —— 否则包里没有说明，打开的人不知道它是什么）；
5. **打包**（`make_archive.py`）→ **抽查**（关键文件在、运行现场不在）；
6. **生成 `SHA256SUMS.txt`** → 真的跑一次 `sha256sum -c`，确认**零告警**；
7. **写工作记忆**。

| **把"待处理请求"与"正在执行"塞进同一个变量**（v2.1.1 踩到） | `linkMazeReq` 置位后**只有上电才清零**，而它和 `linkMazeRun` 一起构成 `MAZE RUN` 的忙判据；`LESSON_Blind8()` 又是 `while(1)` 不返回 ⇒ **发过一次车后 `MAZE RUN` 永久 `ERR_BUSY`，连 `STOP` 也救不回，只能断电**（真机复现 2026-10-05）。两条教训：① **边沿信号（有一次请求）与电平信号（当前是否在跑）必须分开存**；② **"停车"与"退出循环"是两件事** —— 只停电机不退出主循环，发车状态就永远复位不了。见设计方案 §6.1.6 |
| **以为能流水线（用滑动窗口/AIMD 加速拉取）** | 实测**固件每 1 ms tick 只消费一行命令**（`link.c` 的 `USART_RX_STA & 0x80`，bit7 未清时后续字节被直接丢弃），**成串发必丢**（发 2 条回收率就掉到 50%）。**拉取器必须严格停等（在途恒 1）** —— 停等不是限速，是协议层物理约束，且比堆在途请求更快（零浪费、零丢失）。见设计方案 §6.1.5 |

### 6.3 已知的悬留项（留给下一轮）

1. **v2.1 拉取模式上真机**（§5.1 已验一部分）：停等拉取 **4.41 Hz / 丢 0**、**停发自愈（无需断电）**
   均已验；**仅发了非运动命令 `PING`/`TELEM`**，仍待验的是**运动相关**（`MOVE`/`ARM`/迷宫流程）
   与 `ms8` 同余还原在真机抖动下的表现（见 §5.2）。**窗口收敛点 / AIMD 阈值已不再适用 —— 该机制已删除，改为停等。**
2. **Control 前端（本仓库的兄弟项目）未适配 v2.x** —— 用户明确决定"不要动下游程序"。
   Control 依赖 `SNAP` / `SCOPE` / 迷宫三通道；连 v2.x 固件时这些功能会失效，其余（墙图/参数/标定）不受影响。
3. **课程 14 项参数读不回**：固件读侧只有生产参数表（`linkParam[LINK_P_NUM]` 只装 24 项）⇒
   `GET ALL` 不返回课程项，`set_params(..., readback=True)` 对课程参数**必然失败**（只能 write-only）。
   这是**固件的受控不对称**，v2.x 未改；若要修需扩 `linkParam` 表 + 重新处理标定页校验（见下条）。
4. **Flash 扩容陷阱**（用户决定不修）：`link_CalibLoad` 校验 `cnt != LINK_P_NUM` 即判无效 ⇒
   参数表一扩容、旧标定页就作废回默认值。刷固件后要重标。
5. **比赛固件瘦身**：当前 [5] ROM **90872 B**，占程序区上限 103424 B 的绝大部分（口径见 §2.3）；若将来又紧张，
   备选是查表收窄到 1 字节（省 ~8488 B）／仿射去冗余（省 ~7654 B），**未实施**。
6. **未决项**：`fastwayCount90` 等原 `MAZE EV` 统计量随事件流删除后已无上报通道
   （统一帧 payload 45/45 B 已用满，要加就得换字段）。
7. GUI 的迷宫面板与统一帧数据面板：代码已跟上 v2.x，但**未在装了 PySide6 的机器上跑过**。
8. ⚠️ **【待决策】课程实验的波形采样密度不足**：真机停等拉取只有 ≈4.4 Hz，实验三（100 mm）约 200 ms
   ⇒ **只采到约 1 个点**，因此 `LessonAPI._compute` 的阶跃指标（σ%/ts/tp）在真机上**不可信**。
   v2.0 设想的 217 Hz 不成立；**v1.5.5 的 `SCOPE`（1 kHz 本地录制 + 停车后回传）正是为此**。
   出路：① 恢复最小化本地录制+回传（改固件+重烧）；② 拉长实验距离（治标）；③ 接受现状只看趋势。
   **用户当前决定取 ③（"暂不处理，先记着"）**；测试已压到"只验通路不验密度"并打印实测密度。
