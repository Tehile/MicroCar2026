## 0. 文档定位

本方案覆盖两部分交付物：

1. **固件侧新增 `HARDWARE/link.c/h`**——一条走蓝牙串口的双向链路，承担遥测上行、命令下行、标定编排、1kHz 环形缓冲与 Flash 参数持久化。
2. **上位机（Python + PySide6 + pyqtgraph）**——实时波形、参数面板、半自动标定向导、迷宫可视化、数据落盘与分析。

设计的第一原则是**零回归**：不改动任何现有业务逻辑与任何红线数值，所有新能力以"新增模块 + 单行钩子"的方式接入。

| 文件 | 操作 | 内容 |
|---|---|---|
| `HARDWARE/link.c` | **新增** | 链路全部实现（1935 行） |
| `HARDWARE/link.h` | **新增** | 对外仅暴露 `LINK_Init()` / `LINK_Tick()`（123 行） |
| `HARDWARE/usart.h` | 改 | 加 `#define EN_USART1_RX`，激活现成接收通路 |
| `HARDWARE/usart.c` | **改 1 行** | `USART1_IRQChannel` → `USART1_IRQn`（旧库符号名，见下"关键实现点"） |
| `HARDWARE/isr.c` | 改 | `SysTick_Handler` 末尾、`if (sleepmode)/else` **之外**，加 `LINK_Tick();` |

**`usart.c` 那一行是被迫的**：它引用了一个未定义的旧库符号名，且在 `#ifdef EN_USART1_RX` 内从未编译过；一旦启用接收就会暴露。同处还负责在 NVIC 里使能中断，不能删。这是本次唯一一处对既有业务文件的"逻辑外"修改。

**`LINK_Tick()` 必须放在 `if (speedSt.sleepmode == 1)` 之外**，这样休眠与标定死循环期间遥测仍然存活。

### 唯一的例外：`calibrate.c` 的薄壳改造（可选，批次 4 执行）

为使按键菜单与上位机共用同一套标定逻辑（避免两处逻辑漂移），把 `CALIB_MenuXxx()` 的函数体改为：

```c
void CALIB_MenuCalibGyro(void)
{
    CALIB_Service(CALIB_ITEM_GYRO, CALIB_ACT_START, NULL);
    while (1) {                        /* 外层死循环与 LED 提示原样保留 */
        CALIB_Service(CALIB_ITEM_GYRO, CALIB_ACT_STEP, NULL);
        ...原 LED 显示代码不动...
        if (CALIB_Service(CALIB_ITEM_GYRO, CALIB_ACT_DONE, NULL)) break;
    }
    ...

```

按键菜单的**外部行为一字不变**（仍是不返回的死循环），但标定算法只有一份实现。日后想让标定完自动回主流程，只需删掉薄壳里的死循环。

### 关键实现点

**RX 优先级修正**（在 `LINK_Init()` 里直接写寄存器，不依赖 CMSIS 的移位约定）：

```c
SCB->SHP[11]        = 0x40;  /* SysTick: 抢占 1 / 子 0 */
NVIC->IP[USART1_IRQn] = 0x00;  /* USART1 RX: 抢占 0 / 子 0 */
```

**为什么必须这么做——一个实施期才发现的隐情**：

`usart.c` 里 `MY_NVIC_Init(3, 3, ..., 2)` 的实现是

```c
u8 IPRADDR = NVIC_Channel / 4;
u8 IPROFFSET = NVIC_Channel % 4;
IPROFFSET = IPROFFSET * 8 + 4;       /* USART1 时 = 12 */
...
NVIC->IP[IPRADDR] |= temp << IPROOFFSET;   /* 0xF0 << 12 */
```

但 CMSIS 的 `NVIC->IP` 是 **`uint8_t[240]`**（`core_cm3.h:395`，不是旧版标准库的 u32 数组），`0xF0 << 12` 被截断成 `0x00` ——**这段优先级设置其实是空操作**，它只完成了"使能中断"。

后果：USART1 RX 的抢占优先级一直是**复位默认的 0**，与 SysTick 完全相同 → 谁也抢占不了谁 → 1 ms 的 SysTick 期间接收照样成片丢字节。所以 `LINK_Init()` 里把 SysTick 降到抢占 1 **不是优化，而是唯一可行且必需的一步**。

（`SCB->SHP[11]` 的索引依据：CMSIS 的 `NVIC_SetPriority` 用 `SCB->SHP[((IRQn & 0xF) - 4)]`，SysTick 异常号 15 → 索引 11 ✓；`SCB->SHP` 在 CM3 上是 `uint8_t[12]`，逐个异常一字节，所以直接赋 0x40 即抢占 1、子优先级 0。）

**`usart.c` 必须改一行**：`MY_NVIC_Init(3, 3, USART1_IRQChannel, 2)` 里的 `USART1_IRQChannel` 是**旧版标准库的符号名**，V3.x 库中已更名为 `USART1_IRQn`。该行位于 `#ifdef EN_USART1_RX` 内，在使能接收之前**从未被编译过**，所以这个笔误一直潜伏着。改为 `USART1_IRQn` 即可（这行同时负责在 NVIC 里使能中断，不能删）。

**RX 消费**（每毫秒，原子）：

```c
if (USART_RX_STA & 0x80) {
    link_ParseLine(USART_RX_BUF, USART_RX_STA & 0x3F);
    USART_RX_STA = 0;
}
```

`LINK_Tick()` 运行在抢占优先级更高的 SysTick 中，整个读—解析—清空过程不会被 RX ISR 打断，天然原子，无需加锁。**若忘记消费 `USART_RX_STA`，一行收完后 bit7 常置位，后续所有字节被直接丢弃。**

**TX 用 DMA1_Channel4**：每次 `LINK_Tick()` 检查若 DMA 空闲且有数据，就启动一次传输（≤256 B 连续段）。DMA1 全空、无需 NVIC 改动、`usart.c` 零改动。这是 C5 的唯一可行解——若用 TXE 轮询，吞吐上限只有约 1000 B/s。

## 5. 通信协议规格

### 5.1 物理层

| 项 | 值 |
|---|---|
| 接口 | USART1，PA9(TX) / PA10(RX) |
| 格式 | 115200-8-N-1 |
| 理论速率 | 11520 B/s |
| 实际预期 | 经典 SPP 通常低于理论值（RFCOMM 分包 + 模块缓冲） |
| 传输媒介 | 蓝牙 SPP，Windows 呈现为"传出"COM 口 |

### 5.2 帧格式（上行二进制）

```
┌──────┬──────┬────────┬──────┬──────┬────────────┬───────┐
│ 0xAA │ 0x55 │ LEN(2) │ TYPE │ SEQ  │  PAYLOAD   │ CRC16 │
│  1B  │  1B  │  2B LE │  1B  │  1B  │    LEN B   │  2B   │
└──────┴──────┴────────┴──────┴──────┴────────────┴───────┘
  帧开销 = 2 + 2 + 1 + 1 + 2 = 8 字节（不是 7）
  LEN   = PAYLOAD 长度（不含头尾），小端
  CRC16 = Modbus 多项式 0xA001，覆盖 TYPE/SEQ/PAYLOAD，小端
```

**LEN 为什么是 2 字节**：dump 数据块载荷 482 字节，远超单字节 255 的上限。用 1 字节会让大帧的 CRC 高字节发不出去（这是实施时真实踩到的 bug，见 §12）。

**与 `printf` 文本共存的依据**：`fputc` 重定向到 USART1，所以现有全部调试打印都会灌进蓝牙。但 `printf`（`%d`/`%f`/字符串字面量）只产出 `0x09–0x7E` + CR/LF，**永远不可能产出 `0xAA`**。因此：

- 解析器见到 `0xAA` 即尝试按帧解析
- `LEN`/`CRC16` 校验失败 → 回退为文本行处理，并前移一位继续扫描（自恢复）
- 校验通过 → 视为二进制帧

**现有 `printf` 调用一行不改**，文本调试与二进制遥测天然共存。注意：也正因为 `printf` 直接走 `fputc` 而非本模块的环形缓冲，**文本输出无法被软件屏蔽**（因此没有设计 `TEXT ON/OFF` 命令）。

### 5.3 上行帧类型与通道

二进制**只用于设备主动上报的遥测**；命令应答一律走文本行（见 §5.6），这样用串口助手裸连就能看见应答。

| TYPE | 名称 | 载荷 | 帧长 | 速率 | 带宽 | 用途 |
|---|---|---|---|---|---|---|
| `0x01` | FAST 快帧 | 16 B | 24 B | **250 Hz** | 6000 B/s | 转速/角度/pidErr/目标速/任务/flags |
| `0x02` | MID 中帧 | 12 B | 20 B | 50 Hz | 1000 B/s | 里程/编码器角/陀螺原始值 |
| `0x03` | SLOW 慢帧 | 16 B | 24 B | 5 Hz | 120 B/s | 红外/墙/电压/CPU/坐标/丢帧 |
| `0x04` | DUMP_HDR | 8 B | 16 B | 按需 | 突发 | dump 头（总点数/每块点数/已填/写指针） |
| `0x05` | DUMP_BLK | 482 B | 490 B | 按需 | 突发 | dump 数据块（2B 块号 + 60 点 × 8B） |
| `0x06` | DUMP_END | 4 B | 12 B | 按需 | 突发 | dump 结束 + 汇总校验 |
| `0x07` | MAP | 102 B | 110 B | 按需 | 突发 | 墙图整块（7×7 时） |

**快帧速率选 250 Hz 的理由**：1000/250 = 4，是**精确整除** → 预览流就是环形缓冲每 4 点抽 1 点，纯整数移位、相位恒定对齐，不会出现抽取点漂移导致的波形抖动。100/200/500 同样整除，故做成可命令切换，默认 250。

预览的意义是判断"是否正常"；一旦发现异常，用 1 kHz dump 看细节。这是标准示波器工作方式。

### 5.5 1 kHz 环形缓冲协议

**缓冲本体就是 `run_data[1200]`**（`RunData` = `{u8 motionTask; s16 gangle, speedl, speedr;}`，8 B/点），因此：

- 深度 **1200 点 @ 1 kHz = 1.2 秒**
- 新增 RAM **0 字节**
- dump 载荷 = 原结构体的直接拷贝（480 B = 60 点的连续内存，**连 memcpy 都不需要**，DMA 直接从 `run_data[]` 搬）

**每条 dump 记录（8 B，即 `RunData` 原生布局）**

| 偏移 | 字段 | 源 |
|---|---|---|
| 0 | `motionTask` | `motionCtrl.task` |
| 1 | 保留 | — |
| 2 | `gangle` | `gyroStr.angle` |
| 4 | `speedl` | `speedSt.speedL` |
| 6 | `speedr` | `speedSt.speedR` |

**命令序列**

| 命令 | 行为 |
|---|---|
| `SCOPE START [<n>]` | 开始采集，环滚动（默认 1200 点） |
| `SCOPE STOP` | 冻结（停止写环），置就绪标志 |
| `SCOPE DUMP` | 冻结并启动**异步** dump 状态机 |
| `SCOPE ARM <cond>` | 条件触发采集（`TASKCHG` / `WALLCHG` / `CELLZERO`） |

**dump 传输**：20 块 × 490 B + 头 16 B + 尾 12 B = 9828 B → 11520 B/s 下 **0.85 s**。

> **实测修订（2026-09-27，真机 STM32F103RB + CH340 + 蓝牙透传）**：同样的 9828 B，实际耗时
> **~7.1 s（≈1.38 KB/s）**，约为 UART 理论上限的 **12%**。瓶颈在**蓝牙透传模块的突发速率**，
> 不在 UART；且**耗时与采集点数无关**（固件固定回传 20 块，上位机按 `filled` 截断）。
> 这也意味着 §4 里"152 B/s 可持续吞吐"是**常驻预算**、而非突发上限 —— 详见
> `docs/电机远程控制与双流传输.md` §4.1、§7.4。

**dump 头的 `filled` / `start` 是正确性前提**（见 §5.4）。固件固定从块 0 起线性回传 1200 点，上位机收到后按 `filled` 截断、按 `start` 旋转，才能得到时间正序的波形。少了这一步，短采集的波形会有一半是零。

**关键设计：dump 全程零阻塞。** DMA 每次搬 ≤256 B，`LINK_Tick()` 只负责"若 DMA 空闲则续一段"，因此 1 ms 控制周期**完全不受影响，机器人可以边跑边 dump**。唯一的约束是 dump 期间环必须冻结（否则 DMA 读的是正在被写的内存），这由 `SCOPE DUMP` 隐含 `SCOPE STOP` 保证。

**dump 期间自动暂停三类遥测帧**——此时全分辨率数据正在传输，降采样的预览流毫无信息增量，暂停它零损失，并把可用带宽从 6005 B/s 释放到 11520 B/s。

### 5.6 下行文本命令

下行选择 ASCII 文本而非二进制，理由有三：

1. `usart.c` 里现成的 CR/LF 分帧逻辑可直接复用，**一行不用改**
2. 可用任意串口助手裸验证，故障定位时不必依赖上位机
3. 命令是低频事件（人手敲或上位机发），文本的带宽开销无关紧要

**行格式**

```
<CMD> [<arg> ...] *<CRC16-HEX>\r\n
```

`CRC16` 覆盖 `*` 之前的全部字节，采用 Modbus 多项式 0xA001，十六进制大写 4 位。

**命令表**

| 命令 | 说明 |
|---|---|
| `PING` | 心跳，回 `PONG <proto> <fw> <mazetype>` |
| `VER` | 返回协议/固件版本、MAZETYPE、TX 缓冲、环深 |
| `GET <name>` | 回读单个参数（Q16.16），回 `P <id> <q>` |
| `GET ALL` | 回读全部参数（7 行 `P …`） |
| `SET <name> <十进制>` | 写参数（仅 RAM，立即生效）。小数最多 4 位 |
| `SETQ <name> <Q16.16 整数>` | 同上，但直接下发定点原值，**无精度损失，上位机走这条** |
| `SAVE` | 把参数表写入 Flash page 99 |
| `RESET` | 擦除参数页（效果在下次上电体现） |
| `TARE` | 调 `MOTION_SetAngle(0)` 清角度基准 + 复位轮差累计 |
| `CAL <item> <act>` | `item ∈ {GYRO, WALLDIST, IRDATA, GYRORATIO, ENCANGLE}`；`act ∈ {START, SAMPLE, ABORT}` |
| `SCOPE START` / `STOP` / `DUMP` | 1 kHz 环形缓冲采集 / 冻结 / 整块回传 |
| `RATE <hz>` | 快帧速率，取值 100/200/250/500 |
| `MAP DUMP` | 墙图整块回传 |
| `MOVE FWD <pulses> [<speed>]` | 固定脉冲直线（标定用，开环）；完成回 `MOVEDONE FWD <dL> <dR>` |
| `MOVE ROT <pwm> [<ms>]` | 固定 PWM 定长原地转（标定用，开环） |
| `STOP` | 正常停止（清任务、速度归零、电机解锁） |
| `ESTOP` | 急停（额外置 `emergMon.active`，走既有急停通路） |

命令行格式：`<CMD> [args] #<seq> *<CRC16 HEX4>\r\n`

**已废弃的设计**：`TEXT ON|OFF`。`printf` 走 `fputc` 直写 USART1，不经本模块的环形缓冲，因此**软件无法屏蔽文本输出**。改为主机侧过滤（文本调试台有一个"显示设备 printf 文本"开关）。

**参数值编码：Q16.16 定点（s32）**

`atof` 在 F1 上是软件浮点（毫秒级），**禁止进 ISR**。因此参数一律以 Q16.16 定点传输，MCU 只在收到命令时转一次 `float` / `double`（不在每毫秒路径上）。

| 参数 | 真实值 | Q16.16 |
|---|---|---|
| `TRACKL` | 53.2015 | 3486614 |
| `SPEEDL` | 0.532015 | 34866 |

（`53.2015 × 65536 = 3486613.5`，四舍五入得 3486614；精度 1/65536 ≈ 1.5e-5，相对误差 3e-7，远超需要。）

为保留"可手敲"的能力，MCU 同时接受**十进制小数字符串**，用**纯整数运算**解析，不引入任何浮点：

```
Q16.16 = 整数部分 × 65536 + (小数数字串整数值 × 65536) / 10^(小数位数)
```

例：`53.2015` → `53 × 65536 + (2015 × 65536) / 10000` = `3473408 + 13205` = `3486613`（与精确值 3486565 相差 1.4e-5，可忽略）。

### 5.7 可靠性与幂等

下行可靠性做四层：

| 层 | 机制 |
|---|---|
| L1 | 命令行带 `CRC16`；校验失败 → 丢弃并回 `ERR CRC` |
| L2 | 执行后回 `ACK <seq> OK` 或 `ACK <seq> <ERR名>` |
| L3 | 主机超时 200 ms 未收 ACK → 重发，最多 5 次（20/50/100/200/400 ms 指数退避） |
| L4 | 写参数后主机发 `GET <name>` 回读比对 |

**幂等保护（关键）**：MCU 记录 `linkLastSeq`。若收到的 `seq == linkLastSeq`，**不重复执行**，直接重放上次的 ACK。否则"重发导致参数写两次"或"重发导致标定动作重复触发"会酿成事故。

### 5.8 链路自检与自适应降级

由于蓝牙模块的确切型号与 UART 侧波特率尚未确认（见 §11），协议内置自检：

1. 上位机连上后先发 `PING` → 期待 `PONG`
2. 发 `RATE 250` 并**实测**：统计 2 秒内收到的快帧数与时间戳间隔，算出实际吞吐
3. 若实测吞吐 < 需求的 1.5 倍 → 自动降级：`RATE` 依次降到 200 / 100，并禁用 dump 的自动触发
4. 界面顶部常驻显示"实测吞吐 / 理论吞吐"，一旦掉到 50% 以下立刻告警

这样即使实际是 9600 的模块，系统也能自动退到一个可用的配置，而不是直接崩掉。

### 6.3 角度基准的循环依赖问题（重要）

标定 `gyroRatio` 和 `encAngleRatio` 时不能互相参照——**用陀螺标编码器、或用编码器标陀螺都是循环依赖**，误差会互相吸收，最后两个都偏。

必须引入**外部物理基准**。推荐方案：

**利用"前向红外正对墙"作为物理角度基准。** 当车头正对一面墙时，`irDist.f1 + irDist.f2` 取极小值（两前向传感器的和最小 = 中心正对墙面）。因此：

1. 把鼠放在迷宫**角格**（相邻两面墙，例如左墙 + 前墙）
2. `MOVE SERVO` 启动原地慢速旋转，固件在 `LINK_Tick()` 里做极值扫描状态机，找出 `f1+f2` 的两个相邻极小方向——这两个方向的夹角**几何精确等于 90°**
3. 在 0° ↔ 90° 之间**往复 10 次**（累计 900°），依次累加 `angleAcc` 变化量与编码器轮差变化量
4. `gyroRatio_new = ΔangleAcc / 900`，`encAngleRatio_new = Δ(encL−encR) / 900`

往复 10 次的意义：红外极值定位精度约 ±2°，单次 90° 的误差是 2.2%；累计到 900° 后误差被均摊到 **0.2%**，足够。而且这一步**全自动，不需要人介入**。

**备选（精度最高，需人工）**：在鼠下垫一张打印的量角器刻度盘，人工标注起止角度，按物理刻度算。

**不可用**：拿陀螺当基准标编码器，或反之。

### 6.4 Flash 布局与持久化

**参数页：page 99 = `0x08018C00`（1 KB）**

```
偏移      内容
0x000     magic   u32 = 0x4D435331 ('MCS1')
0x004     version u16 = 1
0x006     count   u16
0x008     crc16   u16   （覆盖 0x00A 起全部 payload）
0x00A     rsvd    u16
0x010..   payload：{ nameId u16, valueQ16.16 s32 } × N
```

| nameId | 名称 |
|---|---|
| 1 | `TRACKL` |
| 2 | `TRACKR` |
| 3 | `SPEEDL` |
| 4 | `SPEEDR` |
| 5 | `GYRORATIO` |
| 6 | `ENCANGLE` |
| 7 | `WALLDIST` |

`gyroStr.bias` 与 `irCalib` 8 值**继续沿用原有 page127 / page123 与数据格式**，不迁移。

**载入时机：`LINK_Init()`**（在 `HARDWARE_Init()` 之后调用）。此刻 `ISR_Init()` 已经给 `sysCfg.*` 赋过值，直接覆盖即可 → **`ISR_Init` 零改动**。

**降级行为**：magic 不匹配、version 不符、CRC 失败、或无参数页（全 `0xFFFF`）→ **静默保留源码默认值**。这天然安全：参数页损坏等于没标定，而不是加载一个错的值。

**安全模型**

| 动作 | 行为 |
|---|---|
| `SET` | 只写 RAM，立即生效，**不写 Flash** |
| `SAVE` | 显式写入 page 99（带 magic + version + CRC） |
| 写前 | **上位机自动把旧值导出到会话目录作备份**，并在界面提示备份路径 |
| `RESET` | 擦除 page 99，回源码默认（需重启生效） |

不自动写 Flash 的理由：调参时会反复试值，每页约 1 万次擦写寿命，逐次写盘既浪费寿命又无法撤销。

### 7.4 迷宫可视化

**注意实际规模**：`STRATEGY/maze.h` 里 `#define MAZETYPE 7`，所以当前构建是 **7×7 迷宫**（`mapWall[7][7]` = 49 字节，终点在 (6,6)），README 里"16×16 全迷宫"是宣传口径。上位机**不写死**尺寸，而是从 `PONG`/`VER` 上报的 `mazetype` 自适应——将来把 `MAZETYPE` 改成 16，墙图帧自动变成 516 字节，上位机不用改。

坐标约定（已核对 `MAZE_CoorUpdate`）：`UP`→cY+1、`RIGHT`→cX+1、`DOWN`→cY-1、`LEFT`→cX-1。所以 cX 向右增长、cY 向上增长，绘制时 y 轴需翻转。

墙位编码（低四位，**置位=无墙**）：bit0=上、bit1=右、bit2=下、bit3=左。只画"本格"的上/右/下/左四条，靠邻居格避免重复绘制。

- **实时坐标**：慢帧带 2 B 坐标，5 Hz 刷新，开销可忽略
- **墙图**：49 B 墙位 + 49 B 访问标记 + 4 B 头部 = 102 B 单帧，`MAP DUMP` 按需拉取（约 9 ms）
- **绘制**：网格 + 墙线 + 当前位置朝向三角 + 探索轨迹折线；未访问格以更暗底色区分
- 暂不叠加洪水填充距离图与路径数组

## 8. 资源预算

### 8.1 带宽（11520 B/s 上限）

帧开销修正为 8 字节后（见 §5.2），预算如下：

| 流 | 帧长 | 速率 | 占用 |
|---|---|---|---|
| 快帧 | 24 B | 250 Hz | 6000 B/s（52%） |
| 中帧 | 20 B | 50 Hz | 1000 B/s（9%） |
| 慢帧 | 24 B | 5 Hz | 120 B/s（1%） |
| 小计 | | | **7120 B/s（62%）** |
| 文本调试 + 命令余量 | | | **4400 B/s（38%）** |
| dump 突发 | 490 B | 按需 | 20 块 = 9828 B = **0.85 s**（期间暂停三类遥测帧） |

**实测（模拟器，250 Hz）**：6710 B/s，即需求值的 94%。这个值**不可能达到 100%**——需求值本身就是该配置下的理论上限，测量窗口还包含分批发送与突发帧的影响。因此链路自检的判据是"低于理论值 85% 才算撑不住"，而不是反过来要求高于理论值（最初写成 `got < need × 1.15` 是错的，会稳定误报降级）。

吞吐进一步降低时的降级建议由实测反推，而不是拍脑袋：

```
R_max = (实测 B/s − 1120) / 24        # 1120 = 中帧 + 慢帧的固定开销
从 {500, 250, 200, 100} 里取不超过 R_max 的最大值
```

### 8.5 存储余量实测（试链接）

加入 `link.c` 后固件一度**链接失败**：`L6220E: Load region LR_IROM1 size (91556 bytes) exceeds limit (90112 bytes)`。上限 90112 = 88 KB，因为 `0x08016000` 之后整段被划为固件自存数据区。

不依赖 Keil、直接在命令行测量（脚本：`code_stm32f1_mouse/trylink.sh`，用 armcc/armasm/armlink + 复刻工程布局的 scatter 做试链接；已验证"无 split"这一组能逐字节复现 Keil 的报错，说明配置等价）：

| 配置 | ROM 占用 | 相对 90112 | RAM 占用 | 相对 20480 |
|---|---|---|---|---|
| **A. Optim=Level0, OneElfS=0（原配置）** | 91588 | ✗ 超 1476 | — | — |
| **B. Optim=Level0, OneElfS=1（现行）** | **88132** | ✅ 余 **1980** | 17168 | ✅ 余 3312 |
| C. Optim=Level1, OneElfS=1 | 76356 | ✅ 余 13756 | 17176 | ✅ 余 3304 |

**采取的修正：只把 `uvprojx` 的 `<OneElfS>` 由 0 改为 1**（即 IDE 里的 "One ELF Section per Function" 勾选项）。它只做**死代码消除**——让链接器丢弃"没有任何地方引用"的函数（例如 `main.c` 里被注释掉的 7 个 `LESSON_*`），对所有被保留的函数不产生任何代码变化；优化级别仍为 `-O0`，**不影响已整定的运动控制行为**。这是零语义风险的省空间手段。

**没有采用把优化级别提到 -O1/-O2**（虽然能省 12 KB 以上）：那会改变所有函数的生成代码，而本项目大量依赖 ISR 与主循环共享的 `volatile` 变量，`-O0` 提升到优化级别后，历史上"靠未优化侥幸正确"的地方可能暴露成真 bug。对一个已整定、即将上赛场的机器人，这个风险不值得为 12 KB 余量去冒。若将来确实需要更多空间，建议按"先 `--split_sections` → 再裁剪字符串字面量 → 最后才考虑提优化级别并在赛场上重新验证"的顺序推进。

**余量 1980 字节（2.2%）偏薄**，后续新增代码前建议先跑一次 `bash trylink.sh` 确认，比开 Keil 快得多。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 蓝牙模块实际吞吐远低于 115200 | 250 Hz 快帧不成立 | §5.8 自适应降级；250 Hz 的选择本身留了 48% 余量 |
| 模块是 BLE（非 SPP COM 口） | `pyserial` 不可用，通信层要重写 | **§11 待确认**；若为 BLE 则改用 `bleak` + GATT，帧协议不变 |
| 蓝牙 SPP 偶发断连 | 数据出现空洞 | 会话目录保留 `raw.bin`；帧带 `SEQ`，主机能识别空洞；断连自动重连并重新握手 |
| `printf` 文本与二进制帧误同步 | 主机解析出错 | 帧头 `0xAA` 在 ASCII 可打印区间外，符号上不可能冲突；再加 CRC 兜底 |
| 抬高 RX 优先级影响运动实时性 | 控制周期抖动 | RX ISR 约 2.5 µs；实测 `cpuMon.ticks` 确认无明显上升 |
| 标定把参数写坏 | 比赛现场无法复现成绩 | `SET` 不写 Flash；`SAVE` 前自动导出旧值；`RESET` 一键回默认；参数页带 magic+version+CRC 三重校验 |
| 环缓冲与 `FLASHSAVE` 争用 `run_data[]` | 数据错乱 | 主流程 `flashSt.flashenable` 本来就为 0；LINK 激活时显式独占该数组，并拒绝 `flashwrite` |
| dump 与 1 kHz 写环并发 | DMA 读到正在写的内存 | `SCOPE DUMP` 隐含 `SCOPE STOP`，dump 期间环冻结 |

## 附录 A：为什么不复用按键菜单

`MENU_Run()` 的标定档（case 2–7）全部是 `while(1)` 流水灯死循环，靠断电复位退出（`APP/menu.c:118-171`）。若把远程标定挂在其上，会引入两类问题：一是远程流程与 LED 提示流程互相耦合，二是任何对菜单的改动都会直接影响比赛现场已经验证过的按键操作路径。

因此远程标定走独立路径，通过共享底层动作函数（`CALIB_Service()`）避免逻辑重复，而**不改变菜单的任何外部行为**。

## 附录 B：为什么不改 `ISR_Init` 载入参数

`ISR_Init()` 里 `sysCfg.*` 的 8 个赋值是源码默认值，也是红线 #13 相关的初始化路径。把参数载入放在 `LINK_Init()`（它在 `HARDWARE_Init()` 之后调用，此时 `ISR_Init()` 已完成）可以做到：

- 参数正常 → 覆盖为标定值
- 参数缺失/损坏 → 静默保留源码默认值，**天然安全降级**

`ISR_Init` 因此保持一字不改，红线零触碰。

## 附录 F：真机闭环 —— 蓝牙透传链路的"吞吐悬崖"（真根因）

这是本方案**最关键的实机发现**，它推翻了前一轮"接线/固件问题"的全部推论。

### F.1 现象与误导性

调试器逐项检查 **STM32 发送端一切正常**：PA9 有正确数据波形、静默时稳定为高（正确空闲态）、
USART1 寄存器（UE/TE/BRR/DMAT）全对、GPIO 配置对、未重映射、DMA 计数在递减、
甚至**绕过 DMA 直接写 `DR` 后 `TC` 也置位**。但 PC 侧始终 **0 字节**。

而烧回**原始例程**后 PC 立刻能正常收到（150 B/s 纯文本）—— 说明物理链路是好的。

### F.2 用最小固件做判别实验

把固件临时改成"最小测试版"（`fputc` 还原直写 `DR`、不启用 LINK、main 里只 `printf` 一行，
**延时做成全局可写变量**供调试器实时改），扫出两个层次：

| 测试方式 | 结果 |
|---|---|
| 3 秒窗口扫速 | 能过到约 **1508 B/s** |
| **持续发送 90 秒** | **511 B/s 在第 80–90 秒归零**（80s 段 155 B/s → 90s 段 **0**） |

**两者的差别正是问题的核心**：短时窗口里数据是在被"批量推送"，给出的是假象；
真正的**可持续吞吐**低得多。原始例程的 150 B/s 才是安全点。

### F.3 机制

一对透传模块之间，模块内部缓冲**一旦被灌满就停止向无线侧转发，且不会自行恢复**
（UART 侧没有流控，发送方会继续往里写）。所以表现是**一个字节都收不到**，
而不是"丢一部分"—— 这一点极具误导性。

**判据（很重要）：0 字节 ≠ 乱码。**
- 波特率不匹配 → 收到**乱码字节**（数据在流，只是切错）
- **0 字节** → 链路没建立，或**已经饱和**

### F.4 最终配置（已烧录验证）

| 帧 | 帧长 | 速率 | 占用 |
|---|---|---|---|
| 快帧 | 24 B | 5 Hz | 120 B/s |
| 中帧 | 20 B | 1 Hz | 20 B/s |
| 慢帧 | 24 B | 0.5 Hz | 12 B/s |
| **合计** | | | **≈152 B/s** |

**150 秒长测**：各段 149.6–159.7 B/s（±3%），**全程未归零，坏CRC 0，失步 0**。

### F.5 两个关键设计改动

1. **遥测总开关 `STREAM ON/OFF`，上电默认静默。**
   这是**必需项**：STM32 上电后在蓝牙射频链路建好之前就开始发送，会在无人读取时
   把模块缓冲灌死，导致此后上位机**无论何时打开都收不到**。改为由主机连上后主动开流。
2. **`linkFastDiv` 由 `u8` 改 `u16`**（以支持 0.5 Hz 这类 >255 的分频值）。

### F.6 真机端到端验证

`host/hardware_e2e_test.py` —— **15/15 通过**：端口默认选中 COM7、连接成功、
波特率下拉正确禁用/恢复、自动发 `STREAM ON`、三路帧都收到、零坏CRC、零失步、
链路自检判定 `ok`。

同时修正：`Link.self_check()` 的 `need_bps` 仍是 250 Hz 时代的 7120（恒误报 degraded）
→ 改为 152 B/s；界面速率按钮默认 250Hz → 5Hz，档位改为 5/10/20/2。

### F.7 本链路的能力边界（必须正视）

**约 152 B/s 的可持续吞吐意味着快帧只有 5 Hz** —— 对 PID 波形分析而言分辨率偏低
（一次 200 ms 转弯只有 1 个点）。因此：

- **实时波形只适合看趋势**，不适合看超调/振铃细节
- 高频细节必须走 **SCOPE**（本地 1 kHz 缓冲 + 事后整块回传）；
  9.8 KB 的 dump 真机实测约 **7 秒**（≈1.38 KB/s，见 §5.5 实测修订）——比早先按 152 B/s 估的 63 秒快得多
- **若想彻底解决，应把 CH340 直接接到电脑鼠的 PA9/PA10（跳过蓝牙）**：
  这样带宽回到 115200 的层级（约 11.5 KB/s），遥测可以跑满设计速率

> **待验证（2026-09-27）**：上面"152 B/s 上限 ⇒ 快帧只能 5 Hz"的推导，其 152 B/s 是**常驻预算**
> 而非实测上限 —— 真机突发已达 **~1.38 KB/s**（见 §5.5 实测修订）。若持续压测证明能稳定维持远高于
> 152 B/s，则遥测速率与快帧频率都有大幅上调空间；在有界压测完成前，仍按 152 B/s 设计。

### E.4 决定性实验：CH340 是单向通

1. **绕过固件直接写 `USART1->DR`**（`host/jl_tx_loopback_test.py`）→ 串口 **0 字节**
2. **反向：从 PC 发 `PING\r\n`，再读 `USART_RX_BUF`**（`host/jl_wire_test.py`）→ 缓冲里出现 **`b'PING'`**

→ **电脑→STM32 通，STM32→电脑不通。**
故 COM7 收不到遥测是 **CH340 的 RXD 没有接到 PA9**（接线/跳线问题），**与固件无关**。

（注：`linkLastStatus` 为空是预期行为 —— `link_Ack` 只在 `seq >= 0` 时记录，而无 CRC 的命令走 `link_Ack(-1,"ERR_NOCRC")`。）

### E.5 修掉的一个真实固件缺陷：`fputc` 与 DMA 抢 `DR`

原 `fputc` 是 `while ((USART1->SR & 0x40) == 0); USART1->DR = ch;`（**等 TC**）。
DMA 接管 TX 后有两个后果：

1. CPU 与 DMA **同时写 `USART1->DR`** → 调试文本被插进遥测帧中间（主机侧该帧 CRC 必失败）
2. **写 DR 会清 TC**，而 DMA 连续供数时 TC 几乎不置位 → `fputc` 的等待循环会把调用者（含 ISR 内的 printf）**长时间卡住**

修法（3 处）：`link.c` 新增 `LINK_PutChar()`（唯一 printf 出口，入 TX 环缓冲，PRIMASK 保护，环满丢字节不阻塞）；
`link_TxPut` 同样加保护；`link_SendFrame` 空间判据加 **+32B 余量**（防并发下 head 越过 `tail+256` 使无符号减法下溢）；
`usart.c` 的 `fputc` 改为一行 `LINK_PutChar((u8)ch);`。

**顺带核实**：`led.c` 的 19 处 printf 全在 `LED_ShowBlock()` 里，而**全工程无人调用** → 实际 printf 流量很小，原阻塞风险是"潜在"而非"当前在发生"。

### E.6 默认速率 250Hz → 100Hz

针对"蓝牙连接一段时间后会断开"，先**用 J-Link 运行时改 `linkFastDiv` 4→40** 做零成本验证：
帧率 306 → 80 帧/s。随后固件把默认值定为 `LINK_FAST_DIV_100HZ`：**字节率 6005 → 3005 B/s（砍一半）**，
而一次 200ms 转弯仍有 20 个点；需要高分辨率时用 `RATE 250/500` 临时升档或 `SCOPE` 取 1kHz。

### E.7 上位机修掉的 4 个真实缺陷

| # | 缺陷 | 修法 |
|---|---|---|
| 1 | **连接失败不写日志**（只改顶栏一行小字，用户完全看不到原因） | 新增主线程状态队列 `_state_queue` + `_drain_link_state()`，ERROR 时写日志并给提示 |
| 2 | **失败后仍装成"已连接"**（按钮变"断开"、禁用下拉、照样建会话目录） | `Link.open()` 由 `None` 改 **返回 bool**；调用方据此决定 UI 与是否建会话 |
| 3 | **端口方向不识别**（蓝牙被排到前面） | `ports.py` 新增方向识别/`usable`，传入端口标注"**收不到数据**"；排序改为 **可用 > 有线 > 蓝牙传出 > 蓝牙传入**（COM7 现在排第一并默认选中） |
| 4 | **回调跨线程操作 Qt 控件**（读取线程里 `setText`） | 回调只入队，主线程定时器里 drain |

另加 `explain_open_error()`：把"拒绝访问 / 信号灯超时 / 不存在"翻译成三句可照做的中文诊断。
