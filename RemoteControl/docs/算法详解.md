> 适用范围：**RemoteControl / 电脑鼠蓝牙上位机**项目（API 2.6.0）。
> 本文汇总本项目**自己引入的全部算法思路**，分「固件侧新增」与「上位机侧」两部分。
> 上游**迷宫搜索/冲刺算法**（`code_stm32f1_mouse` 团队原有代码）不在本文范围，
> 见 [`../code_stm32f1_mouse/docs/algorithm.md`](../code_stm32f1_mouse/docs/algorithm.md)。

## 0. 总览

比赛固件（STM32F103RB）原本只支持**按键 + 物理启动**，赛道调试靠串口 printf 肉眼观察。
本项目在**不改变比赛行为**的前提下，叠加了一条**双向二进制链路**与一整套**PC 侧工具链**，
把"调参、标定、监视、复现"全部搬到电脑上。核心约束只有一条：

> **两档共用同一份固件源码，比赛档产物必须逐字节不变。**
> 判据永远是 **hex 哈希比对**（基线 `f0a5f8637d96b61def2d…`），而不是看代码。

由此衍生的设计原则贯穿全文：

- **只加可见性，不改决策**：新增量一律做成"只读镜像"或"编译期常量的运行时化"，默认值
  = 原常量 ⇒ 不写参数时行为逐位不变。
- **门控宏**：共享的协议常量按 `#ifdef MOUSE_REMOTE` 分流，比赛档取旧值。
- **默认等值**：任何时候都能"关掉新机制、退回原行为"（安全网）。

| 层 | 固件侧新增 | 上位机侧 |
|---|---|---|
| 链路 | `HARDWARE/link.c/.h`（帧、命令、参数、事件） | `protocol/codec.py`、`protocol/commands.py`、`transport/link.py` |
| 数据 | 统一帧 49 B、时间锚 `upMs` | `model/ring.py`、`api/stream.py`、`api/timesync.py` |
| 测量 | 红外卡尔曼 + 阈值分档、电源 IIR | `api/analyze.py`、`api/calc.py` |
| 安全 | 双护栏运动、急停锁存 | `registry._precheck_maze_run`、`api/move.py` |
| 分析 | — | `analysis/metrics.py`、`api/analyze.py`、`api/calc.py` |

# 第一部分　固件侧新增算法

## 1. 链路层

### 1.1 文本 / 二进制共存的自恢复解析

固件与上位机之间的同一根串口上既有 **printf 文本**（调试输出），又有 **二进制帧**。
让两者共存的关键观察：

> **printf 只产出 `0x09-0x7E` + CR/LF，永远不可能产出 `0xAA`。**

于是解析算法为：**见到 `0xAA` 才尝试按帧解析；长度不足则等更多数据；CRC 校验失败则把该
`0xAA` 当普通文本字节吐出并前移一位。** 这样即使偶发错帧也不会卡死解析器（自恢复）。
实现见上位机 `codec.FrameStreamParser.feed()`。

### 1.2 CRC16/MODBUS

多项式 `0xA001`、初值 `0xFFFF`，查表推进（上位机 256 项表；固件 `linkCrcTab` 为 16 项半字节表，
两者已在 Python 上穷举 262144 组验证零差异）。校验向量 `crc16(b"123456789") == 0x4B37`。

**两处 CRC，两种覆盖范围**（易错点）：

- **命令行 CRC**：覆盖 `*` 之前的**全部 ASCII 字节**（`CMD [args] [#seq]`）；
- **帧 CRC**：覆盖 **TYPE/SEQ/PAYLOAD**（不含同步头与 LEN）。

### 1.3 幂等重放（命令可靠性 L3 的基石）

上位机重发时**字节完全不变**（同 seq、同 CRC）。固件记下"上一条命令"的 `(seq, crc)`，
若下一条与它**完全相同**则不执行、直接重放上次状态 —— 于是重复写参数、重复触发标定动作
都不会发生。这是"L3 超时重发"能安全使用的充分条件。

**`TELEM` 必须绕开这套簿记**：它是持续拉取命令，若写 `linkLastSeq/linkLastCrc`，
就会把"上一条待重放的真实命令"（如 `MOVE`/`CAL`）冲掉 —— 那条命令一旦 ACK 丢失，
上位机按同 seq 重发时**不会重放而是重新执行**（MOVE 重新起步、CAL 重新采集）。
这在真机上是真事故。所以 `TELEM` 在 `link_HandleLine` 里**提前拦截**，既不查也不写重放状态。

### 1.4 每 1 ms 只消费一行（物理约束）

固件收行逻辑：

```c
if (USART_RX_STA & 0x80) { len = USART_RX_STA & 0x3F; link_HandleLine(...); USART_RX_STA = 0; }
```

bit7 未清（上一行还没被取走）时，`usart.c` 会把后续到达的字节**直接丢弃**。
⇒ **同一时刻只能有 1 条命令在飞**。这条约束决定了上位机的全部时序设计（见 §2.3）。

### 1.5 序号：帧与事件共用

固件用一个 1 字节 `linkSeq` 给**帧和事件行统一编号**。接收端判 `step=(n-prev)&0xFF`，
`step>=2` 即"中间少了消息"。好处是"只加序号、不做重发"也能给出**最强保证：丢失可检测**。

## 2. 遥测采集：从"固件推"到"主机拉"

### 2.1 教训：为什么必须改成拉取

v2.0 曾让固件**自时钟持续发送**全量帧（≈4.3 KB/s）。但这条链路经过一对蓝牙透传模块，
其内部缓冲**一旦被灌满就停止转发且不会自行恢复**（必须给模块重新上电）。实测结果：
收到 `STREAM ON` 后模块缓冲瞬间灌死，连 `PING` 都收不到。

改成**请求-响应**后：PC 不请求 ⇒ 固件不发送 ⇒ 缓冲自然排空，**无需断电即可自愈**。
这就是"把发送节奏交给上位机"最实际的收益。

### 2.2 时间锚随每次拉取刷新

每条 `TELEM` 的应答都是 `ACK <seq> OK <upMs>`，带**完整 u32 时基**。
上位机把这个 `(本机单调秒, 设备 ms)` 记入 `store.set_anchor()`。因为每次都刷新，
所以锚不会陈旧、失锁能立刻自愈。

### 2.3 统一拉取器（`TelemetryPuller`，v2.10）

v2.10 起停等式与批式拉取合并为**一个**类：一条拉取命令的语义是"取回 n 帧"——
`n=1` 退化为停等（`TELEM` 回复门控），`n≥2` 为批式（`RATE PULL n t` 网格调度）。
设计要点见 [`已落地方案与决策记录.md`](已落地方案与决策记录.md) §4，本节只保留算法层结论。

由 §1.4 的物理约束推出：**任何时刻最多一条命令在等它的首帧**（停等是 n=1 的字面特例）。
`_refill()` 只在 `self._out` 为空时才发下一条。

真机证据（COM7）：

| 背靠背 N 条 | 回收率 |
|---|---|
| 1 | **100%** |
| 2 | 50% |
| 3 | 33% |
| 4 | 25% |
| 8 | 12% |
| 间隔 300 ms 逐条发 | **100%** |

固定窗口扫描（每档 6 s）：窗口 1 → **6.50 Hz**（RTT 153 ms）、2 → 6.49、4 → 7.15、6 → 7.15。

> **窗口 1 已经拿到 `1/RTT` 的满速**；加大窗口只多约 10%，却开始成串丢失。
> ⇒ 停等**不是软件限速，而是协议层的物理约束**，且比堆在途更快（零浪费、零丢失）。
> 早期版本用 AIMD 自适应窗口（1→16）是基于错误假设，真机实测后删除。

停等可达帧率 = `1/RTT`，实测 **4.41~6.5 Hz**；**没有软件 Hz 上限** —— 上限是链路往返涌现出来的。
突破该上限只能走批式（`n≥2`，把多条帧复用进一条命令的回复窗口），代价是自节流与锚刷新
（设计文档 §5/§7）；批中点注入 `TELEM` 刷锚是因为 `RATE PULL` 的 ACK 只有裸 `OK`、
不带时基（§2.2）。

### 2.4 让路（`suspend/resume`）

**问题**：急停/停止"按了不立即生效"。根因是拉取器**持续**发 `TELEM`，同一条 `STOP`/`ESTOP`
只要与某条 `TELEM` 落进同一个 1 ms 窗口就被丢弃；上位机要等 `TIMEOUT_S`(2.5 s) 才重发。
最坏情况是命令一直没生效，**车是被 MOVE 的时间护栏停下的**。

**对策**：`urgent` 命令发送前后调 `stream.suspend()/resume()` —— 暂停拉取、等在途请求收尾
（`QUIESCE_MAX_S=0.30 s`），使命令独占链路。实测：

| 场景 | 结果 |
|---|---|
| 拉取器开（修复前） | 1/5 需重发，转速归 0 中位 **3220 ms**（= 没生效） |
| 拉取器开 + 先让路 | **0/5 重发**，转速归 0 中位 **751 ms** |

**`stop()` 为什么要先等在途 `TELEM` 收尾**：`TELEM` 一旦写出就已在线，固件要等下一个 1 ms
tick 才消费它。若 `off()` 后紧接着发命令（"先停流、再发车"的最自然写法），会撞上那个窗口
（实测 3/4 首发被丢）。改为"等在途那条 `TELEM` 拿到应答再返回"（应答到达 ⇒ 固件必然已消费
完那一行）后，同一时序实测 **0/8** 丢首发。等待期间**不发任何字节**，不加重缓冲积压。

保留的两处**故意不改**：`QUIESCE_MAX_S=0.30` 的残留 1/12 延迟（避免拉长急停最坏延迟）、
`stop()` 的 `STOP_QUIESCE_MAX_S=0.60` 上限（兜住"应答真丢了"，不让 `off()` 挂死）。

### 2.5 保序解析（顺序即协议）

`FrameStreamParser.feed()` 返回 `Frame | str` **混排的有序列表**，读取线程必须**按顺序**处理。
把帧与事件拆成两个列表再分别跑，会让"帧, 事件, 帧"变成"帧, 帧, 事件"，共用序号看起来就跳了
（实测：一次 `STOPPED` 误报 3 个缺口、256 条丢失）。

## 3. 时间同步：把设备毫秒时基映射到本机单调时钟

对应需求："电脑鼠从发车命令开始其 LED 以 1 Hz 闪烁，同时需要记录其发车时间和时间间隔
来计算每一次接收到数据的准确时间。"

### 3.1 为什么必须做

蓝牙透传**有缓冲、有抖动**，一帧从固件发出到主机收到的延迟**不是常数**。用"主机收到时刻"
当数据的时间会污染时间轴 —— 而"检测运动特性"恰恰要看毫秒级的时间关系。
靠主机自己**无法**恢复真实发送时刻，所以必须让设备把它的时间告诉我们。

### 3.2 同余还原 `resolve_ms8`（本算法核心）

统一帧每帧只带 `ms8`（**低 8 位**，省带宽）。主机用"锚 + 本机流逝"预测一个粗值 `predicted`，
再在 `predicted + k·256` 的同余类里挑**与 `ms8` 同余且最接近预测值**的那个：

```
cand = floor(predicted/256)*256 + k*256 + ms8,  k ∈ {-1,0,1,2}
取 |cand - predicted| 最小者
```

只要预测误差 < **128 ms**（半个模周期，可容 55 帧）就必然选对。

**失锁判定**：还原值偏离预测 > 128 ms ⇒ 同余解不唯一 ⇒ 记一次丢失并**重新索要锚**，
**绝不静默给一个错的时间**。（锚最长有效期 `ANCHOR_MAX_AGE_S=120 s`。）

### 3.3 单程延迟：取最小值而不是平均

到达时刻 = 发送时刻 + 链路延迟，延迟未知且**恒为正**。经典做法（NTP 的 min-filter 思想）：

```
offset = min( t_recv_i - dev_ms_i / 1000 )
```

最小值才逼近"真偏移 + 最小延迟"。这样算出的时间**绝对值仍差一个未知常数**（最小延迟），
但**任意两帧之间的时间差是准确的** —— 这正是运动特性分析需要的。

### 3.4 频差拟合 `fit_clock` / `drift_ppm`

最小二乘拟合 `dev_ms/1000 = a + b·t_recv`，斜率 `b` 即"设备秒 / PC 秒"，`(b-1)·1e6` 是相对
频差（ppm）。样本少于 3 个或时间跨度太短则返回 None（拟合无意义）。

### 3.5 物理基准灯：独立校核

`ARM` 后固件让 LED 以 1 Hz（50% 占空）闪烁，供摄像头/人眼给出一条**独立**的单程延迟估计
（"灯亮"与"收到 armed"之差）；两边一比就知道 min-delay 估计是否可信。这正是把物理灯一起做的意义。

### 3.6 两种时间映射

- `frame_time(rec)` → 本机单调秒（`offset + up_ms/1000`，帧间隔准确）；
- `dev_ms(rec)` → "发车以来毫秒数"（`up_ms - armMs`），运动特性分析的主时间轴。

## 4. 参数持久化

### 4.1 Q16.16 定点

全部参数以**有符号 32 位 Q16.16** 承载：`真值 = q/65536`。选它是因为 STM32F103 无 FPU，
定点保证"下发的值 = 设备算的值"，避免浮点格式差异。上位机 `float_to_q1616` 的取整方向与
固件 `link_F2Q/link_D2Q` 一致（四舍五入到最近可表示值）。

### 4.2 F1 Flash 只能 1→0 —— 程序页 CRC 的坑（真机暴露的缺陷）

**现象**：`SAVE` 跨重启是空操作，参数没保存。
**根因**：`link_CalibSave()` 先写 CRC **占位值 0**，再回填真实 CRC。但 **F1 Flash 的位只能
从 1 写成 0**（写 1 必须靠擦除），于是"回填"这个动作根本写不进去 ⇒ 存值恒为 `0x0000` ⇒
上电校验必败 ⇒ `cnt != LINK_P_NUM` ⇒ 页被判无效、回落默认值。
**修复**：把校验值**一次性算出并真实写入**（`#ifdef MOUSE_REMOTE` 门控，比赛档不变）。
真机复验通过，判别脚本 `host/params_persist_probe.py`。

> ⚠️ 副作用：`link_CalibLoad` 校验 `cnt != LINK_P_NUM`。因此**扩容参数表会自动作废旧 page115**
> （回落默认值，重 `SAVE` 即可）—— 这是有意的安全行为，不是 bug。

### 4.3 门控宏：编译期常量 → 运行时变量

每个新参数在固件里的形态是"**宿主变量**（静态初值 == 编译期常量）+ **消费侧门控宏**"：

- 宿主变量定义在 `link.c`（如 `linkDisF60`），静态初值即原常量（如 `60`）；
- 消费点用宏门控（如 `isr.c` 里 `>LINK_DISF60`，`motion.c` 里
  `wallSns.wallThresh = LINK_WALLTHR_DEFAULT()`）；
- 比赛档里这些 id 存在于表里，但**运动代码不读它们**（保持编译期常量）。

⇒ **未 `SETQ` 时行为逐位不变**；**只有远程档**才吃这套运行时参数（赛前调参闭环仅对远程档成立）。

### 4.4 覆写警示（调参必须先知道）

部分参数被特定路径**运行时覆写且不恢复**：

- `IRTHRWALL`：恢复点（`motion.c` ×2，原写死 160）已改为读参数表（`LINK_WALLTHR_DEFAULT()`）；
- `TURNP/TURND/TURNDELAY/SPDTURN`：被**冲刺路径**覆写且不恢复 —— 但**远程档不进冲刺**，故不触发；
- `SPDSEARCH`：只参数化初值，转弯后回落固定 70。

详见 [`参数名称-功能-调整表.md`](参数名称-功能-调整表.md) §六。

## 5. 红外测量

### 5.1 ADC → 距离标定表

固件用 **250 点查表**把原始 ADC 映射成 mm。查表在两端被夹紧：贴太近返回 **0 mm**、
超出量程返回 **249 mm**。⇒ **单看距离会把"近得查不出"误当成"贴住了"**，
据此调参必然跑偏。上位机 `analyze.ir_saturation_stats()` 因此专门统计**饱和占比**。

### 5.2 卡尔曼滤波（可开关）

对红外测距做一维卡尔曼滤波，参数：

| 参数 id | 名称 | 含义 | 默认 |
|---|---|---|---|
| 29 | `IRKALQ` | 过程噪声 Q ×10000（越小越信任预测） | 100 = 0.0100 |
| 30 | `IRKALP` | 测量噪声 P ×10000（越大越平滑但迟钝） | 2000 = 0.2000 |
| 31 | `IRKALSW` | 开关 0/1 | 1 |

### 5.3 前向综合三模式

`IRFRONTMODE` 决定前向综合距离的算法：

| 值 | 算法 | 特点 |
|---|---|---|
| 0 | 均值（现状） | 默认 |
| 1 | 取小 | 更保守 |
| 2 | 加权 | — |

### 5.4 前墙双档拆分（零行为变化的证明点）

前墙几路红外**本来就分两档**（`isr.c` 里 4 个条件取或：① ② 是"双传感器互证"用 230/240/245，
③ ④ 是"单路近距"用 80），只是被或成了一个 `wallSns.front`。项目**不改那个或式**，
而是在**组帧时**用同一组阈值把它**拆开**：

```c
frontNear = wallSns.front && min(f1,f2) <  irCfg.thrFrontNear   /* 贴脸: 必须处理 */
frontFar  = wallSns.front && min(f1,f2) >= irCfg.thrFrontNear   /* 提前量: 可用于提前决策 */
```

**恒等式** `frontNear | frontFar == wallSns.front` 且两者互斥 ⇒ 原来 5 个读
`wallSns.front` 的决策点**一行都没改**。这就是"拆档本身零行为变化"的证明点。

## 6. 电源监控

### 6.1 电压换算与 IIR 滤波

```
mV = adcBatt × BATTKV / 1000          # BATTKV 默认 2417 (= 3.3V×3÷4096×1000) µV/LSB
filt = filt + (mV - filt) × BATTALPHA/1000   # BATTALPHA: 0=不滤波, 1000=完全跟随, 默认 100
```

### 6.2 档位映射

```
step = (BATTHIGHMV - BATTLOWMV) / BATTMAXPCT      # 默认 (7960-7000)/8 = 120 mV
档位 = clamp((filt - BATTLOWMV)/step, BATTMINPCT, BATTMAXPCT)
threshold = BATTLOWMV + 档位 × step
```

低于 `BATTLOWMV`（默认 7000 mV）时报低电。

> ⚠️ **固件对低电没有任何保护动作**（`safety.c` 只算出 `battMon.low` 供显示，不会停车）。
> 这是上位机发车硬闸存在的根本原因（见 §8.3）。

## 7. 运动护栏与急停锁存

### 7.1 双护栏（`MOVE RUN`）

远程运动受**时间 + 红外**双护栏约束，**停止条件全在固件 1 ms 中断里** ⇒ 上位机被 kill
也不会失控：

- 时间护栏：最长运行 `ms`（默认 2000）；
- 红外护栏：任意一路红外距离 < `ir_mm`（默认 10 mm）即停；`ir_mm < 0` ⇒ 关闭（只验证时间护栏）。

停止后上行 `STOPPED <REASON> #n`（`TIME`/`IR`/`ESTOP`/`USER`/`END`）。

### 7.2 急停锁存状态机

```
        ESTOP ──▶ [ESTOP_LOCK 置位] ──▶ 新 MOVE/CAL 一律 ERR_ESTOP
                                            │
                            STOP / MAZE STOP ┴─▶ [解锁] ──▶ 可再次 MOVE
```

`STOP` 是**重新获得控制权的唯一入口**（既停车又解锁）。`estop.clear` 只是它的同义入口。
锁存状态在统一帧 flags 的 `ESTOP_LOCK` 位**一眼可见**。

### 7.3 发车安全

**上位机独立硬闸**：`maze.run` 在**登记表层**带前置校验 `_precheck_maze_run` ——
`battMv < LAUNCH_MIN_MV`（默认 7000 mV，与固件 `BATTLOWMV` 默认一致，但改设备参数**不会**
放宽它）时拒绝发车并回 `ERR_LOWBATT`。放在登记表层是为了**任何** `send_cmd` 路径
（脚本/CLI/datalog）都绕不开；逃生舱是 `send_raw("MAZE RUN")`（把车架离地面）。

> **依据是真机事故**：当时 `battMv` 一路 7681 → 6747 → **3962 mV**，现场表现为"电机一直转、
> 且对红外障碍物不再敏感"（低电时红外发射管变暗 ⇒ 回波微弱 ⇒ 墙检测失效）。

**收车要靠 `MCU RESET`**：`MAZE STOP` 只置一个"请退出"标志，而该标志的检查在
`LESSON_Blind8()` 的 `while(1)` **顶部**；主循环有 30 余处**非协作式阻塞等待**
（`motion.c` 的 `while (cellOdom < dis)` 等），车在运动时程序正卡在那些循环**内部**，
标志根本轮不到。可靠路径是整机软复位（BSS 清零把发车状态一起清掉），成功判据是
复位后 `PING` 报 `rst=SW`。

## 8. 迷宫与状态复刻

### 8.1 路口分类（主机侧复刻）

v2.0 起固件**不再上报**路口分类（`MAZE EV` 已删除）。主机侧用统一帧里的**三位墙原语**
（`wallLeft/wallFront/wallRight`，`1=有墙`）复刻固件的分类（`codec.classify_road`，
与 `link.c` 的 `link_RoadKind` 逐分支一致）：

下表按"**该方向是否开口**"列出（与前/左/右三路互斥地划分）：

| 开口方向 | 类型 | kind |
|---|---|---|
| 前 + 左 + 右 全开口 | 7 | `CROSS` 十字 |
| 前 + 左 | 4 | `TEE_FL` 缺右 |
| 前 + 右 | 5 | `TEE_FR` 缺左 |
| 左 + 右（前方封死） | 6 | `TEE_LR` 前方封死 |
| 仅前 | 1 | `THRU` 直道 |
| 仅左 / 仅右 | 2 / 3 | `CORNER_L` / `CORNER_R` |
| 全封死 | 8 | `DEAD` 死路 |

> 函数内部把 `wall_*`（1=有墙）先取反成 `f/l/r`（1=开口）再分类。
> 固件端 20 ms 去抖的规则由调用方决定是否复刻；纯函数只做分类，不做时序。

### 8.2 冲刺态只读镜像

冲刺的 4 个量（`spurtmode` / `taskSt.*` / `mazeState.*`）是比赛固件的内部状态的**只读镜像**，
上位机**不能设置**它们（冲刺入口是比赛流程里"人工贴墙选档"那一段，刻意不动）。
唯一为此改动的地方是把 `APP/state.c` 的 `spurtmode` 由 `static` 改为全局 —— **只加可见性**。

# 第二部分　上位机侧算法

## 9. 数据模型与丢帧检测

`TelemetryStore` 维护**单流**环形缓冲（通道表同源于 `codec.UNIFIED_CHANNELS`）、最新值快照、
墙图、时间锚，以及**上行消息序号连续性**：

```
step = (seq - prev) & 0xFF
step >= 2  ⇒  up_gaps += 1; up_lost += step-1   (+ 若是事件行则 ev_* 同增)
```

因为帧与事件**共用**序号，只有同时看见两者的 store 才能正确判定 —— 这也是丢帧统计的
唯一真源在 store、`Link.counts` 只做"抄数"的原因。

## 10. 控制特性分析

### 10.1 阶跃响应指标（`calc.step_metrics`）

从一段阶跃曲线算 **σ% / ts / tp / rise**：

```
σ% = (peak - steady)/steady × 100%          # 超调量
tp = 首次达到峰值的时间
ts = 最后一次离开 ±band 之后的时刻(此后不再超出)
rise = 10% → 90% 上升时间
```

**关键点**：稳态值必须取**末段**（默认后 30%）。若整段平均，加速段会把"稳态"拉低，
超调量随之虚高。

### 10.2 跟踪误差（`analysis.metrics.tracking_error`）

对 `y` vs `ref` 给 `rms / maxabs / tail_mean / tail_rms`，尾部窗口默认后 20%。

### 10.3 按运动任务分段（`segment_by_task`）

按统一帧的 `motionTask` 变化切段，一次动作即一段；对每段算左右轮速度的阶跃指标
（target 取该段**最后 5% 的均值** —— 比取理论目标值更稳，因为帧里没有下发的目标转速，
而段尾通常已进入稳态）。

### 10.4 直行质量（`calc.straightness_metrics`）

```
drift_deg   = gyroAngle[-1] - gyroAngle[0]        # 航向漂移
drift_rate  = drift / seconds
speed_bias  = mean(speedL) - mean(speedR)         # 左右轮平均速度差
bias_pct    = bias / ((|mL|+|mR|)/2) × 100%       # 不对称度
```

"两轮速度一致性"是判断能不能走直线的最直接依据 —— 不一致说明两电机特性/编码器系数/PID
参数不对称，车会向低速一侧偏。

## 11. 标定算参（`api/calc.py`，纯函数）

### 11.1 理论系数

```
里程系数 = 编码器线数×4×(轮齿/编码齿) / 轮周长
         = 256×4×(42/10) / (π×22) ≈ 62.24      # 默认机械参数

陀螺角速率系数 = (灵敏度 mV/(度/s) / ADC最小刻度) × 1000
              = (0.67 / (3300/2^11)) × 1000 ≈ 415.8   # 默认 0.67mV、11位、3300mV
```

### 11.2 线性标定（里程与角度共用一条公式）

```
新系数 = 旧系数 × (固件读数 / 真实值)
```

统一规则：**读得偏大就把系数调小，读得偏小就把系数调大**，一步到位。两个方向看起来相反
其实是同一条（里程按固件自算的里程停车，角度命令固定圈数）。

### 11.3 验收线与误差

```
error_ratio = (读数 - 真值)/真值 × 100%     # "测距/测角误差 ≤ 3%"这条验收线
```

### 11.4 红外标定误差

`ir_error_stats` 给对一组"测量 vs 真值"的 `max/mean/RMS` 与最差点；
`pick_best_position` 在若干标定位置里选综合误差最小的（不同红外的最优方案可能不同，
应按通道分别比）。

## 12. 红外曲线重建（`analyze.ir_range_curve`）

统一帧的 `irAdc*` 与 `irF*` **逐帧同步**，所以把鼠标推着走一遍就能得到整条"ADC-距离"曲线，
用**幂律 `ADC = a·d^b`**（对数域最小二乘）拟合，返回 `a / b / r²`。作用是**校验或重建**
`irs.c` 里那张 250 点标定表，而不是靠手工摆两次（近点/远点）。`r² < 0.9` 就别用。

## 13. 电源分析（`analyze`）

- `batt_low_events`：从 mV 序列里找**低电区间**（判别"跑到一半掉电"）；
- `batt_discharge`：起止电压、总跌落、**最大瞬时跌落速率**（内阻的间接指标 —— 电机启动
  电流陡增时若内阻偏大，mV 会在一两个采样点内掉一大截，那种掉法会把 MCU 拉到复位）。
  统一帧约 4.6 ms/点，比旧 0.5 Hz 遥测帧强得多。

## 14. 设备模拟器（`sim/mouse_sim.py`）

协议与固件**逐字节一致**（共用 `pack_frame` / `pack_unified`），自带仿真物理与 7×7 迷宫探索。
意义：没有硬件时也能把上位机全链路跑到 `selftest --e2e` / `uismoke`，
且 `contract_test` 用它**逐条执行每个登记项**，把"登记表 ↔ 真实行为"钉死。
