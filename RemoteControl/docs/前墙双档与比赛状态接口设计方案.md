## 0.1 实施定案（与下方设计稿的差异，2026-10-07 用户拍板）

用户要求：**"比赛/例程8 代码都已监视为主，除发车、停止等关键命令外的额外命令都不必要，
尽量不要动比赛代码"**。据此对 §6 的六个待定项定案如下：

| 待定项 | 定案 | 与设计稿的差异 |
|---|---|---|
| ① 前墙上行承载 | **方案 B**（扩帧 +4 B，`PROTO_VER` 3→4） | 与推荐一致 |
| ② 前墙语义 | **β 互斥分档** | 与推荐一致 |
| ③ §1.2 的 5 个消费点 | **全部保持只读 `wallSns.front`，一行不改** | 与推荐一致；因此**零行为变化**成立 |
| ④ `IRFRONTMODE` 接线 / 新增 `IRFRONTCMB` | **不做** | 那要改 `isr.c` 的判定结构（比赛代码），且属"决策口径"而非"监视" |
| ⑤ 命令进入冲刺态（§3.3） | **不做** | 用户明确"额外命令不必要"；且 §3.3 本身就是红线声明 |
| ⑥ `fastwayCount90` / `spurtSpd.*` | `fastwayCount90` **进帧**；`spurtSpd.*` **都不做** | 前者是监视量；后者要走参数表（改面更大） |

**两处与设计稿的实现差异（都是"更省、更安全"的）：

1. **前墙双档不在 `isr.c` 算，而在 `link.c` 组帧时派生。**
   设计稿 §2.2 让 `WallSensor` 加两个字段并由 `isr.c` 赋值 —— 那要动比赛代码（`isr.c` 与
   `core.h` 结构体布局）。改在**链路层组帧时**用同一组阈值派生，`isr.c`/`core.h`/`maze.c`/
   `motion.c` **一个字节都不用改**，行为变化严格为零。恒等式与真值表完全不变（见 §2.1）。
2. **帧布局比设计稿更"诚实"**：设计稿把 `goaheadnum` 压到 3 bit；实现里给它**独立一整字节**
   （不静默截断），标志位另占一字节。载荷仍是 49 B。

**唯一改动到比赛代码的地方**：`APP/state.c` 的 `spurtmode` 由 `static` 改为**全局**
（并在 `state.h` 加 `extern` 声明）—— **只加可见性，逻辑一字未改**。理由是它是文件静态量，
否则链路层读不到"比赛选了哪一档冲刺"。

## 0. 摘要

要解决两件事，它们是**同一类问题**：固件内部"能区分"的东西，接口上"看不到 / 改不了 / 进不去"。

| # | 问题 | 现状 | 本方案 |
|---|---|---|---|
| 1 | 前墙只有一个 bool | `isr.c:685` 里其实有 4 个条件、**天然分两档**，被 `\|\|` 或成了一个 `wallSns.front` | 拆成 `frontNear` / `frontFar`，**保留 `front = near \|\| far`** 使 5 个现存消费点逐字不变 |
| 2 | 状态机接口不支持比赛代码的状态 | ① 上位机 `MOTION_TASK_NAMES` 与 `core.h` 枚举**错位 9 项**；② 比赛冲刺的选档量**全不出帧**；③ 没有任何命令能让固件**进入** SPURT 态 | 修表 + 补回传 + 加"进入"命令（三段，可分别取舍） |

**设计原则（沿用本项目既有纪律）**：
- 识别层拆开、决策层默认不动 ⇒ "拆档"本身**零行为变化**，可单独验收；
- 新增量一律**只读复制已公开全局量**（`wallSns` / `spurtmode` / `taskSt`），不在 maze/state/lesson/motion 里埋钩子；
- 上位机与固件的**枚举表必须由契约测试自动对齐**，不能靠人工维护两份。

## 1. 现状核对（设计的事实基础）

### 1.1 前墙：一个 bool，源自 4 个条件的或

`isr.c:685`：

```c
if ((irDist.f1 < irCfg.thrFrontLo   && irDist.f2 < irCfg.thrFrontHi)
 || (irDist.f2 < irCfg.thrFrontMid  && irDist.f1 < irCfg.thrFrontHi)
 || (irDist.f1 < irCfg.thrFrontNear)
 || (irDist.f2 < irCfg.thrFrontNear))
        wallSns.front = 1;
else    wallSns.front = 0;
```

- 条件 1/2 = **双传感器互证**，阈值 `thrFrontLo/Mid/Hi` = 230/240/245（参数 id 25/26/27）
- 条件 3/4 = **单传感器近距**，阈值 `thrFrontNear` = 80（参数 id 28）
- 两侧（`wallThresh` 160 / `thr45` 150 / `thrCritical` 60）都是**单阈值**，只有前墙是双档结构 —— 只是被或掉了。

### 1.2 `wallSns.front` 的全部消费点：**5 处 + 1 处组帧**

| # | 位置 | 语义 | 拆档后建议口径 |
|---|---|---|---|
| 1 | `MAZE_WallCheck()` `maze.c:158` | 把"前方有无墙"写进地图（地图只有有/无） | `front`（任一档） |
| 2 | `MAZE_BreakOrNot()` `maze.c:224` | "该停下重决策"的路口定义 | `front`（现行为），**后续可改为 `frontNear` 以提前决策** |
| 3 | `isr.c:214` 前墙对正 | `pidErr = f2 - f1` 做角度误差 | **`frontNear` 更合适**（只有贴脸才该用它对正） |
| 4 | `lesson.c:633` `roadStat` 数开口 | 路口形状统计 | `front` |
| 5 | `motion.c:950 / 962` `MOTION_Before180Turn()` | `front==0` → 刹车收尾；`front==1` → 转 `BEFORE180TURN` 用前墙定位 | **只看 `frontNear`**（远墙不该触发"用前墙定位"） |
| 6 | `link.c:1184` 组帧 | 上行状态 A bit6 | 改为两档（见 §2.3） |

> 第 5 点是个现成的例子：`MOTION_Before180Turn()` 在 `cellOdom` 只走到 40 时就判前墙。此时"两百多毫米外的远墙"与"贴脸墙"在当前实现里**完全不可区分**，都会走 `BEFORE180TURN` 分支。拆档后这里可以直接改判据 —— 这是"拆档能改进决策"的第一个落点。

### 1.3 上位机 / 模拟器的状态机表示现状

> 以下结论由脚本解析 `core.h` / `maze.h` / `codec.py` 得出（2026-10-07 实跑）：固件 `MotionTask_t` **38 个码**，上位机表 **37 项**。

| 项 | 现状 | 问题 |
|---|---|---|
| `codec.MAZE_TASK_NAMES` | 0 WAIT / 1 START / 2 SEARCH / 3 SPURT / 4 SPURT45 / 5 SPURT90 | ✅ **数值映射与 `maze.h:104-109` 完全一致**；仅命名风格不同（固件 `MAZESEARCH`/`SPURT_45`/`SPURT_90` ↔ 上位机 `SEARCH`/`SPURT45`/`SPURT90`） |
| `codec.MOTION_TASK_NAMES` | 见 §3.1 | ❌ **与 `core.h` 的 `MotionTask_t` 错位**：缺 9 个码、多 8 个幽灵码 |
| `sim/mouse_sim.py` | 只产生 `motion_task ∈ {0, 2, 32}` | ❌ 测试覆盖不到冲刺与快速转弯 ⇒ 错位**不会被测试发现** |
| 比赛冲刺量 | `spurtmode` / `taskSt.goaheadnum` / `taskSt.spurtFlag` / `taskSt.goOrBack` / `mazeState.spurtTestFlag` / `mazeState.objectGoToFlag` / `mazeState.fastwayCount90` / `spurtSpd.*` | ❌ **全部不出帧**，上位机看不到比赛选了哪种冲刺 |
| 命令侧 | `MAZE RUN`（只能从 WAIT 起跑）、`MAZE STOP`（只置 abort） | ❌ 没有任何命令能进入 `SPURT_45` / `SPURT_90` |

> 补充发现（低优先级）：`maze.c:50-58` 的 `MAZE_Stop()` 把 `mouseTask` 置 **99**，而帧里只有 3 bit ⇒ 会被截断成 `3 = SPURT`，上报成"正在冲刺"。该函数注释写明"当前未使用"，但属潜在误读点。

## 2. 第 1 部分：前墙拆成"远端 / 近端"

### 2.1 语义定义（**推荐：互斥分档**）

```c
/* isr.c doWallDetect()：原式拆成三段，逐位等价 */
u16 dMin = (irDist.f1 < irDist.f2) ? (u16)irDist.f1 : (u16)irDist.f2;

wallSns.front = ((irDist.f1 < irCfg.thrFrontLo  && irDist.f2 < irCfg.thrFrontHi)
              || (irDist.f2 < irCfg.thrFrontMid && irDist.f1 < irCfg.thrFrontHi)
              || (irDist.f1 < irCfg.thrFrontNear)
              || (irDist.f2 < irCfg.thrFrontNear)) ? 1 : 0;   /* 与原式逐字相同 */

wallSns.frontNear = (wallSns.front && dMin <  irCfg.thrFrontNear) ? 1 : 0;  /* 贴脸 */
wallSns.frontFar  = (wallSns.front && dMin >= irCfg.thrFrontNear) ? 1 : 0;  /* 提前 */
```

**恒等式**：`frontNear | frontFar == front`，且两者**互斥** ⇒ "墙落在哪一档"可直接判。

物理含义（一格 180 mm，红外查表量程 0–249 mm）：

- `frontFar` = 远端墙：两路都看到墙、但还没贴脸。**是"提前量"** —— 主要发生在距墙 80~245 mm，即约"前方一格以内的墙，在进入该格之前就被看到"。
- `frontNear` = 近端墙：墙已进车头 80 mm 内。**是"必须处理"** —— 停车 / 定位 / 转向。

真值表（含边界用例）：

| `f1` | `f2` | `front` | `frontNear` | `frontFar` | 场景 |
|---|---|---|---|---|---|
| 249 | 249 | 0 | 0 | 0 | 前方空旷（远端超量程） |
| 100 | 100 | 1 | 0 | **1** | 前方约半格处有墙，两路都看到 |
| 200 | 240 | 1 | 0 | **1** | 前方一格处有墙（240 恰在 `Hi` 内） |
| 40 | 240 | 1 | **1** | 0 | 斜着贴近墙：一路贴脸、一路 240 |
| 40 | 249 | 1 | **1** | 0 | **只有一路看到且贴脸** ⇒ 双路互证不成立，靠近端档兜底 |

**替代方案 α（字面拆或）**：`frontNear` = 原条件 3/4，`frontFar` = 原条件 1/2，两者**可同时为 1**。
不推荐：从分档结果无法直接读出"墙在哪一段"，决策还得再比较一次距离。若你更希望"近处有墙时远端也置位"，选 α。

### 2.2 固件改动（识别层，零行为变化）

| 文件 | 改动 |
|---|---|
| `HARDWARE/core.h` | `WallSensor` 增 `u8 frontNear; u8 frontFar;`（+2 B RAM） |
| `HARDWARE/isr.c` | `doWallDetect()` 按 §2.1 计算三值（原式一字不改，只多两个派生赋值） |
| `HARDWARE/core.c` | `CORE_Init()` 里 `wallSns.frontNear = 0; wallSns.frontFar = 0;` |

**§1.2 的 5 个消费点一行不改** —— 这就是"拆档不改变任何决策"的证明点，也是本轮可以先做、单独验收的部分。

### 2.3 上行承载：两个方案

帧载荷现有 45 B **偏移 0–44 全部占满**（`link.h:103-125`），没有连续空位。两个出路：

#### 方案 A（零增量，复用 `flags` 的两个死位）

`link_Flags()`（`link.c:1107-1130`）末尾明确写着：

```c
/* FLAG_SCOPING/FLAG_DUMPING 在 v2.0 恒为 0 —— SCOPE 与 dump 机制已删除。 */
```

即 `flags` 的 **bit3 (0x08)** 与 **bit4 (0x10)** 自 v2.0 起永久为 0 —— 正好两个空位：

```c
#define LINK_FLAG_FRONT_NEAR 0x08  /* 原 FLAG_SCOPING(恒 0) 复用 */
#define LINK_FLAG_FRONT_FAR  0x10  /* 原 FLAG_DUMPING(恒 0) 复用 */
```

- `LINK_UNIFIED_LEN` 仍 **45**、`LINK_PROTO_VER` 仍 **3**、帧长仍 **53 B**
- 上位机：`codec.FLAG_NAMES` 改两行、派生 `frontNear/frontFar`
- 代价：语义上把"感知量"塞进了"系统标志"；若将来真要恢复 SCOPE/dump 得另找位
- 破坏性：老主机若按 SCOPING/DUMPING 解释会误读（本项目不做向后兼容，可接受）

#### 方案 B（扩帧 +3 B，`LINK_PROTO_VER` 3 → 4）

| 偏移 | 内容 |
|---|---|
| 45 | `frontBits`：bit0 `frontNear`、bit1 `frontFar`、bit2 `frontBoth`（原双路互证式，调试用）、bit3–7 预留（留给后续转向位置开关） |
| 46 | 比赛冲刺选档打包（见 §3.2） |
| 47 | 比赛冲刺状态位（见 §3.2） |

- 载荷 45 → **48**，帧 53 → **56 B**；`LINK_PROTO_VER` → **4**
- 代价：`LINK_UNIFIED_LEN` / `codec.UNIFIED_CHANNELS`（39 → 42 项）/ `contract_test` 的 `assert len(...) == 39` / `mouse_sim._unified_frame()` / 文档 全部要同步
- 收益：位语义干净、一次把所有"比赛状态量"补齐、给后续扩展留 5 bit

**推荐：方案 B。** 理由：
1. §3.2 的比赛状态量**本来就得加**，与其做两次破坏性变更，不如一次做完；
2. `flags` 是"系统状态"，把感知量塞进去会污染语义，且**没有第二次扩展余量**；
3. 带宽代价可忽略：RTT 由蓝牙转发延迟主导（143–527 ms 实测），56−53=3 B 的空中时间只多约 **0.26 ms**（115200 下），相对现有 ≈100–200 B/s 的吞吐不是瓶颈。

> 若本轮只想动前墙、不碰比赛状态量，则**方案 A** 更划算（o 版本号、o 测试改动）。请拍板。

### 2.4 可选：把两个"假/缺"配置一并修掉（建议纳入，但不强制）

1. **`IRFRONTMODE`（id 32）是假配置**：`isr.c:668` 仍写死 `irDist.f = (irDist.f1 + irDist.f2) / 2`，`irCfg.frontMode` 只在 `core.c:107` 赋初值、在 `link.c` 收发参数，**全仓零消费点**。要么接线，要么删掉该 id（删除更诚实）。
2. **新增前墙合成口径参数** `IRFRONTCMB`（建议 id 39）：`0` = 或（现状）/ `1` = 仅近端 / `2` = 仅远端 / `3` = 要求双路都近端。挂在 `isr.c` 的 `wallSns.front` 计算处 ⇒ 上位机能远程决定"多保守才算有墙"。
3. **近端判据强度**：现在"任一路 < 80 mm"即判。可扩成两个阈值（`near` 单路 / `nearBoth` 双路），对应"贴墙过弯"与"正对墙"两种工况。

## 3. 第 2 部分：状态机接口对齐比赛代码

分三段，**互相独立、可分别取舍**。

### 3.1 必修 A：上位机动作名表与固件枚举错位（这是"接口不支持比赛状态"的直接原因）

`codec.MOTION_TASK_NAMES` 与 `core.h` 的 `MotionTask_t` 逐项对照：

| 码 | 固件 `core.h` | 上位机现状 | 判定 |
|---|---|---|---|
| 0 / 1 / 2 / 4 / 5 | NULL / GOSTRAIGHT / TURN / TURNAROUND / STOP | 同 | ✅ |
| **12** | SUPERSTRAIGHT | *（缺）* | ❌ 缺失 |
| **13** | INFRSTRAIGHT | *（缺）* | ❌ 缺失 |
| **14** | TURNLEFTFAST | *（缺）* | ❌ 缺失 |
| **15** | TURNRIGHTFAST | *（缺）* | ❌ 缺失 |
| **16** | EMERGENCY | *（缺）* | ❌ 缺失 |
| 17 | STRAIGHT45 | STRAIGHT45 | ✅ |
| **18** | FASTSTRAIGHT | *（缺）* | ❌ 缺失 |
| 27 / 28 | BEFORE90TURN / BEFORE180TURN | 同 | ✅ |
| **29** | AFTER180TURN | *（缺）* | ❌ 缺失 |
| 30 | SMARTSTRAIGHT | 同 | ✅ |
| **31** | CHANGESPEED | *（缺）* | ❌ 缺失 |
| 32 / 33 / 34 / 35 / 36 / 37 / 38 / 39 | SMARTSTRAIGHTFAST / STRAIGHTEYECLOSECOORADJ / STRAIGHTPOLE / ACC / SLOWDOWN / SPEEDUP / KEEPWALLDISTANCE / POINTTURN90 | 同 | ✅ |
| **40** | EDGESTRAIGHT | *（缺）* | ❌ 缺失 |
| 41 | FORWARDIRTEST | 同 | ✅ |
| 42–45 | SPURT90BLIND / SPURT90IR / SMARTSTRAIGHTSPURT / SMARTSTRAIGHTSPURTL | 同 | ✅ |
| **46–53** | *（固件无此码）* | TURNLEFTFAST / TURNRIGHTFAST / EMERGENCY / SUPERSTRAIGHT / INFRSTRAIGHT / FASTSTRAIGHT / EDGESTRAIGHT / CHANGESPEED | ❌ **幽灵码 8 项，且正好是 12–16/18/31/40 的错位影子** |
| 101–107 | LT90SEARCH…RT90SPURT | 同 | ✅ |

**影响**：真机跑到 `TURNLEFTFAST(14)`、`EMERGENCY(16)`、`EDGESTRAIGHT(40)` 等时，上位机会显示 `?` 或错名 ⇒ 现场无法判读比赛动作。**这正是"状态机接口不支持比赛代码状态"的核心**。

**另外两处纯命名差异**（不影响数值，但会让"逐字符比对"的契约测试误报，须一并归一）：
- 码 0：固件 `MOTION_TASK_NULL` ↔ 上位机 `NULL`
- 码 105：固件 `STRAIGHT_spurt_90` ↔ 上位机 `STRAIGHT_SPURT_90`

**根治（关键）**：不要手工维护两份枚举。`contract_test` 新增契约测试：
```
从 code_stm32f1_mouse/HARDWARE/core.h 解析 `MotionTask_t` 枚举体 → {码: 名}
从 code_stm32f1_mouse/STRATEGY/maze.h   解析 `mouseTask` 六个宏     → {码: 名}
断言与 codec.MOTION_TASK_NAMES / codec.MAZE_TASK_NAMES 逐项相等（含"无多余键"）
比对前把名字**归一化**（大写化 + 去下划线，如 STRAIGHT_spurt_90 → STRAIGHTSPURT90），
只为消除命名风格差异，数值映射仍须严格相等。
```
这样两份表**不可能再漂移**；`mouse_sim` 也同步补齐这些码的数值（至少让契约测试与模拟器都能覆盖）。

### 3.2 必修 B：比赛状态量回传

| 量 | 固件位置 | 取值 | 建议位宽 |
|---|---|---|---|
| `spurtMode` | `spurtmode`（`state.c:177/217` 赋值） | 未选 / 60 `SPURT_SPEED_90_LOW` / 61 `SPURT_SPEED_45_LOW` / 62 `MEDIUM` / 63 `HIGH` | 3 bit |
| `goaheadnum` | `taskSt.goaheadnum`（`main.h:203`） | 冲刺前行格数 | 4 bit |
| `spurtFlag` | `taskSt.spurtFlag` | 冲刺标志 | 1 bit |
| `goOrBack` | `taskSt.goOrBack` | 去 / 回 | 1 bit |
| `spurtTestFlag` | `mazeState.spurtTestFlag` | 冲刺测试使能 | 1 bit |
| `objectGoToFlag` | `mazeState.objectGoToFlag` | 回坐标中 | 1 bit |
| `fastwayCount90` | `mazeState.fastwayCount90` | 90° 路径动作计数 | 8 bit（可选） |
| `spurtSpd.{lTopSpeed,l45TopSpeed,l90TopSpeed,backTopSpeed}` | `spurtSpd` | 顶速 | **走参数表**，不进帧（可选，4 项） |

建议打包（方案 B 的偏移 46 / 47）：

```
偏移46: bit0-2 spurtMode(0=未选,1=90LOW,2=45LOW,3=MED,4=HIGH)
        bit3-5 goaheadnum(0..7)   bit6 spurtFlag   bit7 goOrBack
偏移47: bit0 spurtTestFlag  bit1 objectGoToFlag  bit2-7 预留
```
（`fastwayCount90` 若要全量则再加 1 B，载荷 49；`spurtSpd` 四项建议作为新参数 id 走 `SET/GET`，与已有的 `TRACKL/R`、`SPEEDL/R` 同类。）

> 若最终选方案 A（不扩帧），则本节的量**只能退化为一条只读命令** `SPURT STATUS`（类似旧的 `SNAP MAZE`）。但在 v2.1 拉取式链路下，多一条命令等于挤占帧率（严格停等、RTT 143–527 ms），**不推荐**。

### 3.3 必修 C：让上位机能"进入"比赛状态（命令侧）

**问题**：比赛固件的冲刺入口是 `state.c:172-253` 两个嵌套 `while(1)` 等 `irDist.f1/f2 < 20`（LED 提示人工选档）；`[4]` 档把这段整段 `return` 跳过（`state.c:152-171`）。于是：

- 远程**无法**触发出 `SPURT_45 / SPURT_90`（`[4]` 里 `mouseTask` 只会是 START/WAIT/SEARCH）；
- 也**无法**复现"选档"这一步（低/高速由贴哪面墙决定）。

**建议命令**（仅测试档 `[3]/[4]` 编译，比赛固件 `[5]` 不含 —— 用 `#ifdef MOUSE_ESTOP_RECOVERABLE` 同款门控）：

| 命令 | 作用 | 幂等 |
|---|---|---|
| `SPURT SELECT <45\|90> <LOW\|MED\|HIGH>` | 直接置 `mazeState.mouseTask = SPURT_45/90` + `spurtmode` + `spurtSpd` 顶速，**替代那段物理选档** | 走既有重放簿记 |
| `SPURT SPEED <item> <value>` | 设 `lTopSpeed / l45TopSpeed / l90TopSpeed / backTopSpeed` | 同上 |
| `GOAHEAD <n>` | 置 `taskSt.goaheadnum` | 同上 |
| `SPURT TEST <ON\|OFF>` | 置 `mazeState.spurtTestFlag`（配合 `STATE_SpurtTest()` 跑 `spurtTestAction`） | 同上 |
| `MAZE RUN` | 现有，仍走 WAIT → START → SEARCH | 不变 |

⚠️ **红线声明**：本节的命令**不替代比赛固件 [5] 的真实入口**。`[5]` 里那段物理选档是刻意设计（人工贴墙决定档位），属红线不动。本节只解决"测试档能复现并观测冲刺状态"。
