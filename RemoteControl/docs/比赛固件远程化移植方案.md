# 比赛固件远程化移植方案（code_competition 基线）

> 状态：**方案待评审**（2026-10-16）　|　上游基线：`code_competition/`（未入 git）
> 上位机基线：`host/` v2.10.1（PROTO 8 / fw 222）　|　被替代基线：`code_stm32f1_mouse/`（课程固件，MAZETYPE 7）

---

## 0. 摘要

`code_competition/` 是一套**与现有工程架构完全不同的比赛代码**：无 `link.c`、无 `isr.c`、
无 `APP/MOTION/STRATEGY` 分层，`main()` 是一个 1250 行的单体状态机，运动原语是
`taskgostraight/taskturn` 系列**忙等函数**，参数是 `user.c` 里的 `const` 常量。

**结论：可以移植，且上位机可以几乎不动。** 原因是现有远程层的设计恰好是"协议与平台解耦"的：

| 现有远程层的可分维度 | 是否可整体移植 |
|---|---|
| 通信协议（PROTO 8、49B/57B 帧、CRC16、幂等重放、停等/批式拉取） | ✅ 原样 |
| 命令集（24 条：PING/TELEM/RATE/MAZE/MOVE/CAL/RESET/ESTOP…） | ✅ 原样 |
| 参数表（41 项 Q16.16 + page115 持久化） | ✅ 原样（名字不变，宿主变量换绑） |
| 遥测帧字段 | ✅ 原样（新固件有对应裸全局量，见 §1.3） |
| `link.c` 协议引擎（3521 行） | ✅ 原样 90%+ |
| 上位机 `host/`（10 套件 702 测试 + 收车安全 13 项） | ✅ 绝大多数原样 |
| 平台相关（电机停止、发车握手、flash、LED、USART、1ms 节拍） | 🔧 需新写适配层 |

**核心工作量 = 一个新文件 `link_port.c`（平台适配层）+ 新固件里约 10 处 1~3 行的门控插入。**

**最高风险 = 协作式中止**（新固件全是忙等循环，`MAZE STOP` 这类软停止会永远卡住）——
§4.2 给出了解法，是本方案唯一需要仔细设计的地方。

## 2. 移植策略：三层架构

```
┌─────────────────────────────────────────────────────────────┐
│  L1  协议层  link.c / link.h        ← 从 code_stm32f1_mouse  │
│      命令解析 / 帧编解码 / CRC16 / 幂等重放 / RATE·TELEM      │
│      DMA TX 环 / CAL 家族 / MOVE 家族 / 参数表 41 项          │
│      对平台的访问全部收敛到 LP_* 钩子 ⇒ 可原样搬 90%+         │
├─────────────────────────────────────────────────────────────┤
│  L2  平台适配层  link_port.c / .h   ← 本次主要新写           │
│      ① 旧结构体名（speedSt/odomStr/gyroStr/irDist/wallSns/   │
│         mazeState/motionCtrl/battMon/sysCfg/irCfg/powerCfg/  │
│         pidGain/speedCfg/emergMon/taskSt/kalmanSt）做成镜像，  │
│         每 tick 从新固件裸全局量刷新（只读字段）               │
│      ② 动作钩子：LP_StopMotion / LP_Launch / LP_SoftReset /  │
│         LP_LedMark / LP_Flash* / LP_ParamGet·Set              │
│      ③ 41 项参数名 → 新固件变量绑定表                        │
├─────────────────────────────────────────────────────────────┤
│  L3  门控插入点（新固件内，~10 处 × 1-3 行，全部 #ifdef）      │
│      timer.c / usart.c / test.c / user.c                     │
└─────────────────────────────────────────────────────────────┘
```

**为什么用"结构体镜像"而不是改 link.c 的数据访问**：link.c 里有 ~40 处
`speedSt.speedL`、`odomStr.trackL` 这类访问，散落在 3521 行里。做成镜像后 link.c
几乎不用改，diff 可 review、可回归、可回退；代价是每 ms 拷贝 ~30 个标量（可忽略）。

> ⚠️ 镜像只承载**遥测（只读）**方向。**控制（写）方向必须走显式钩子**
> （`LP_StopMotion()` 等），否则写进镜像的值不会生效。这是本方案最容易出错的点，
> 已在 §5 风险 R2 列出。

- **未改动的比赛文件保持原样**（GBK 的继续 GBK，混合行尾不动）⇒ 比赛档 hex 零风险。

## 4. 关键设计决策

### 4.1 USART：TX 走 DMA，printf 让路

新固件 `fputc()` 是**轮询 `USART1->DR`**；链路的 `link_TxDrain/link_DmaStart` 用
**DMA1_Channel4**。两者同时写 DR 会乱码。

**做法（与旧工程完全相同）**：把 `usart.c` 的 `fputc` 改为调用 `LINK_PutChar()` 入 TX 环
（旧工程 `usart.c:36-40` 就是这么做的）。环满丢弃 + `linkDrop++`，不阻塞。

- TX：原样移植 `link_DmaInit`（`RCC->AHBENR|=1`、`USART1->CR3|=1<<7` DMAT、`CPAR=USART1->DR`）。
- RX：新固件的 `USART1_IRQHandler` + 64B 行缓冲已写好但被 `#ifdef EN_USART1_RX` 关掉。
  做法：在 Remote target 的 Define 里加 `EN_USART1_RX`，并在 `LINK_Init` 里配
  NVIC（USART1 RX 抢占 0 / SysTick 抢占 1），与旧工程 `link.c:3294-3295` 一致。

### 4.2 协作式中止（**最高风险，必须专门设计**）

**问题**：新固件所有运动原语都是忙等（`while(track<180) task=SMARTSTRAIGHT;`）。
置一个"请退出"标志**永远不会被检查到**；而 `freemode=1` 虽能立刻停电机（`timer.c:1157`），
却会让 `while(track<180)` 因 `track` 不再增长而**永久挂死**。

**推荐解法：全局 abort 标志 + SysTick 顶部"强制满足退出条件"**

```c
/* link_port.c */
u8 linkRunAbort = 0;          /* #ifdef MOUSE_REMOTE */

/* timer.c  SysTick_Handler 最顶部（门控插入点之一） */
#ifdef MOUSE_REMOTE
if (linkRunAbort) {
    task = NULL; step = 0;
    track = 0x7FFFFFFF; tick = 60000;     /* 让所有 while(track<X)/while(tick<X) 立即退出 */
    setvl = setvr = 0;
    speed = speedl = speedr = 0;
}
#endif
```

配合 `LP_StopMotion()` 里的 `freemode=1`（电机总开关，PWM 恒 0），
**1ms 内**：电机停 + 所有底层忙等返回。

**还需在顶层 `while(1)` 加 break 检查**（这些循环不 poll `track`/`tick`，或内含
`while(1)` 死等，约 6-8 处）：

| 位置 | 现况 | 处理 |
|---|---|---|
| `utility.c:748` `mazeSearch()` 的 `while(1)` | 靠 `breakornot()` 退出 | 加 `if(linkRunAbort) break;` |
| `utility.c:1103` `mouseGoahead()` 的 `while(1)` | 靠 `n==cNBlock` 退出 | 同上 |
| `utility.c:777 / 798 / 1024 / 1052` | `disf<10` / 转向失败的 **LED 闪灯死循环** | 改为 `while(!linkRunAbort){...}`，退出后回上层 |
| `utility.c:824` | `mazesearchnowall` 的 `while(1)` | 加 break 检查 |
| `test.c` 主 `while(1)`（`case MAZESEARCH`/`SPURT` 内） | 无退出条件 | 加 abort → `GucMouseTask=END` |
| `stratagy.c` `objectGoTo()` 等 | 靠步数递减退出 | 视实测补 |

**备选（不推荐单独使用）**：只靠 `MCU RESET` 收车。旧工程实践已证明 `MAZE STOP` 在阻塞
等待里不可靠、复位是唯一可靠手段；但"停止"必须能回到 WAIT 态以便再次发车，
不能每次都复位。**结论：abort 为主、复位为兜底**（`force_idle()` 分级收车逻辑照搬）。

**验收**：真机上"车在跑 → `MAZE STOP`/`ESTOP` → 1ms 内电机停 → 200ms 内 `GucMouseTask`
回到 WAIT → 可再次发车"。

### 4.3 参数可变性：`const` 的门控解除

`user.c` 的 7 个标量是 `const`（`angleratio/gangleratio/TrackRatioL/R/SpeedRatioL/R/dis2wall`），
放在 `.rodata`。直接改成非 const 会把它们移进 `.data` ⇒ **比赛档 hex 变**（触碰红线）。

**做法：成对门控**，比赛档逐字节不变：

```c
#ifdef MOUSE_REMOTE
u16  angleratio = 81*0.91;        /* 远程档可调（参数表 id 6） */
#else
const u16 angleratio = 81*0.91;   /* 比赛档原样 */
#endif
```

12 张转弯曲线表（`vouter_search[195]` 等）**保持 const**（参数表不调它们）。

其余参数本就是可变全局量，直接绑：`sidewall_threshold`↔IRTHRWALL、`kalmanswitch/Qf*/Pf*`
↔IRKAL*、`speed_ss/speed_turn`↔SPDSEARCH/SPDTURN、`turn_delay`↔TURNDELAY、
`GOSTRAIGHT_kp/turn_kp/turn_kd`↔GSKP/TURNP/TURND、`kpl/kil/kdl/kpr/kir/kdr`↔MKPL…MKDR。
**协议侧参数名一个都不改** ⇒ 上位机 `registry` 原样可用。

### 4.4 `MAZETYPE` 7 → 16 的协议影响（比预想的小得多）

勘察发现 host 侧**早已为可变迷宫尺寸做好设计**，因此这项几乎零成本：

- 遥测帧：`posX/posY` 是 4bit nibble，16×16 的 0-15 **刚好放得下**，帧布局不变。
- MAP 帧：102B → **516B**（`4+256×2`）。但
  - 固件侧 `LINK_MAP_LEN = 4 + MAZETYPE*MAZETYPE*2` 是**宏，随 `stratagy.h` 的
    `MAZETYPE` 自动展开**，`link.h:135-140` 注释已明确预期 16 的情形；
  - host 侧 `registry._decode_map_auto()`（`registry.py:424-431`）**从载荷长度反推 n**，
    `api/maze.py:8` 亦注明"迷宫尺寸取自设备上报的 mazetype，上位机不写死"。
  ⇒ **MAP 帧长度变化对 host 零改动**。
  TX 环 1024B 仍够（`link_TxPut` 环满丢弃有保护，`linkDrop` 可观测）。
- 需要动的只有：`sim/mouse_sim.py: MAZETYPE = 7 → 16`（`build_maze()` 随之）、
  `ui/maze_view.py`（已声称自适应，预计小改）、文档里"当前 7×7"的措辞。

### 4.5 版本号与兼容矩阵

`motionTask` 码值集合整体更换（旧 `MotionTask_t` ↔ 新 `timer.h` 的 `task` 枚举），
MAP 帧长度随 mazetype 变。二者都是**协议可见**的变化。

**推荐：PROTO 保持 8，fw 升到新号段 300，host 按 fw 选名称表。**

理由：帧结构、命令集、参数表、CRC、幂等、遥测偏移全部未变；变的是"码值的解释表"。
让 host 在 `PING` 后按 fw 号选择 `MOTION_TASK_NAMES` 表，比升 PROTO 的连锁改动小得多
（升 PROTO 会牵动 sim、全部 702 测试、§9 兼容矩阵、下游 Control）。

代价与对策：**旧 host（fw≤222）接新固件会把 motionTask 显示成错名**（功能不坏，
只是名字对不上）。对策：在 §9 兼容矩阵里明确写"PROTO 8 自 fw 300 起 motionTask 换表"，
并在 `PONG` 握手后由 host 打印一次告警。

> 备选：PROTO 8 → 9。更"干净"但要同步改 sim + 全部测试 + 文档 + 下游，工作量大一个量级。
> **倾向推荐方案 A（PROTO 8 + fw 300 + 自适应名表）**，请评审确认。

### 4.6 发车 / 收车 / 跑完 的状态流转

新固件**没有** `LINK_MazeRequested/Started/Finished` 的对应物，需要新建：

```
远程 MAZE RUN ──► linkMazeReq=1
                    │
   test.c 主循环 case WAIT 里（门控插入点）：
     if (linkMazeReq) { 跳过"等 disf2<20"按键闸门; GucMouseTask = START; }
                    │
   case START → mazeSearch() → MAZESEARCH → SPURT → fastway()+spurt(LOW)
                    │
   ★ 必须新增：跑完置 GucMouseTask = END
     （现状：test.c:1134 break 后又回到 case SPURT 重跑，唯一置 END 的 1102 行
       在注释块里 —— 这是新比赛代码自身的一个 bug，必须补）
                    │
   case END → LP_StopMotion() + LINK_MazeFinished() → 回 WAIT（可再次发车）
```

`linkMazeAbort` 语义照搬（`MAZE STOP`/`ESTOP` 置 1、`MCU RESET` 后自然清零），
但检查点从 `lesson.c:535` 改为 §4.2 的 SysTick 强制退出 + 顶层 break。
