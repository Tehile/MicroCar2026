## 0. 修正记录

本接口文档相对设计方案初版有三处修正，均为**查证源码后**得出：

| # | 项 | 初版 | 修正后 | 依据 |

## 1. 最终帧规格

```
AA 55 | LEN(2,LE) | TYPE(1) | SEQ(1) | PAYLOAD(49) | CRC16-MODBUS(2)
总长 57 B  →  11520 / 57 = 202 Hz (4.95 ms/点)   ← 115200 的**理论上限**；
                                                    v2.1 端到端实测 ≈100~200 B/s（见设计方案 §6.1）
```

> **【v2.1】帧格式不变**，只是发送节奏改由上位机的 `TELEM` 请求驱动（详见设计方案 §6.1）。
> **【v2.3】载荷 45 → 49 B**（帧 53 → 57 B、`LINK_PROTO_VER` 3 → 4）：新增 4 个
> **纯只读监视**字节（前墙双档 / 冲刺档位与标志 / 冲刺前行格数 / 90°路径计数）。
> **命令集与命令文本一字未动**，也没有任何决策逻辑被改（见 §1.3）。
> **【v2.4】帧格式不变**（仍 49 B / 57 B）。变的是**命令集与参数表**：
> 删课程层三条 `lesson.*`（命令 24 → 21 条）、参数表 38 → 24 项（只剩生产命名空间，
> `PARAM_IDS` 项数 == 固件 `LINK_P_NUM`）、`MAZE RUN` 增加**可选**目标词
> `BLIND|RACE`（默认 BLIND 时省略，老上位机的 `MAZE RUN` 行为完全不变）。
> 带宽代价可忽略：+4 B 在 115200 下只多约 0.35 ms 空中时间，而 RTT 由蓝牙转发延迟主导
> （实测 143–527 ms）。

### 1.2 位打包明细（偏移 35–37、39–40、45–46）

```
偏移35 (状态A):  bit0-1 dir(0=UP 1=RIGHT 2=DOWN 3=LEFT)
                 bit2-4 mazeTask(0=WAIT 1=START 2=MAZESEARCH 3=SPURT 4=SPURT_45 5=SPURT_90)
                 bit5   wallLeft      bit6 wallFront      bit7 wallRight
偏移36 (状态B):  bit0-6 motionTask(0..107, 见 core.h 的枚举)
                 bit7   irSwitch
偏移37 (状态C):  bit0-3 motionStep
                 bit4   critL          bit5 critR
                 bit6   left45         bit7 right45
偏移39:          bit0-3 posX(0-6)       bit4-7 posY(0-6)
偏移40:          bit0-3 goalX           bit4-7 goalY
偏移45 (前墙):   bit0 frontNear  bit1 frontFar  bit2 frontBoth  bit3-7 预留
偏移46 (冲刺):   bit0-2 spurtMode(0=未选 1=90LOW 2=45LOW 3=MED 4=HIGH)
                 bit3 spurtFlag  bit4 goOrBack  bit5 spurtTestFlag
                 bit6 objectGoToFlag            bit7 预留
```

> `goalX/goalY` 在源码里是 `char`（初值 7），4 bit 足够覆盖 0–15。

### 1.3 v2.3 新增量的语义与"零行为变化"证明

前墙这几路红外**本来就分两档**（`isr.c` 里 4 个条件取或：① ② 是"双传感器互证"用
230/240/245，③ ④ 是"单路近距"用 80），只是被或成了一个 `wallSns.front`。v2.3 不改
那个或式，而是在**组帧时**用同一组阈值把它**拆开**：

```c
frontNear = wallSns.front && min(f1,f2) <  irCfg.thrFrontNear   /* 贴脸: 必须处理 */
frontFar  = wallSns.front && min(f1,f2) >= irCfg.thrFrontNear   /* 提前量: 可用于提前决策 */
```

**恒等式** `frontNear | frontFar == wallSns.front` 且两者互斥 ⇒ 原来 5 个读
`wallSns.front` 的决策点（`maze.c:158/224`、`isr.c:214`、`lesson.c:633`、
`motion.c:950/962`）**一行都没改** —— 这就是"拆档本身零行为变化"的证明点。

冲刺那 4 个量是比赛固件的内部状态（`spurtmode` / `taskSt.*` / `mazeState.*`）的
**只读镜像**。上位机**不能设置**它们 —— 冲刺入口是比赛流程里"人工贴墙选档"那一段
（红线，刻意不动）；测试档(`[4]`)不跑冲刺，故这些位恒为 0。唯一为此改动比赛代码的
地方是把 `APP/state.c` 的 `spurtmode` 由 `static` 改为全局（**只加可见性，逻辑一字未改**）。

### 3.5.1 `api/stream.py` —— 停等拉取器（**v2.1 新增；真机实测后由"滑动窗口 + AIMD"改为严格停等**）

`TELEM` 是请求-响应式的，所以"发多少帧"完全由上位机决定。这一决策集中在 `PullRequester`：

| 项 | 值 / 行为 |
|---|---|
| 在途上限 | **恒为 1**（任何时刻只发一条 `TELEM`；`_refill()` 只在 `self._out` 为空时才发下一条） |
| 调度方式 | **严格停等**：收到应答（或超时）→ 才补发下一条；`tick()` 50 Hz 收割 → 补发 |
| 单请求超时 | `REQUEST_TIMEOUT_S = 3.0`（真机单帧往返 157~234 ms，取足量余量） |
| 时间锚 | 每条 `TELEM` 的应答都是 `ACK <seq> OK <upMs>`，`callbacks` 挂 `_absorb_anchor` → **每次拉取都刷新锚** |
| 停止 | `stop()` **立即丢弃在途请求**（不再等应答）—— 这是让蓝牙模块缓冲排空的唯一手段 |

**已删除（不再有自适应窗口）**：`MIN_WINDOW` / `MAX_WINDOW` / `FAST_START_WINDOW` / `ADAPT_INTERVAL_S`
四个常量与 `_adapt()` 方法；`start()` / `stop()` 的返回 data 由 `{"window": N}` 变为 `{"inflight": N}`；
`snapshot()` 的键**去掉 `window`、新增 `mode: "stop-and-wait"`**，其余 `running`/`inflight`/`sent`/`done`/`lost`/`hz`/`best_hz` 保留；
`StreamAPI.tune()` 的 `max_window` 参数**已删除**，只剩 `tune(request_timeout=...)`。

**为什么必须是停等：固件每 1 ms tick 只消费一行命令。** `HARDWARE/link.c` 的收行逻辑是：

```c
if (USART_RX_STA & 0x80) { len = USART_RX_STA & 0x3F; link_HandleLine(...); USART_RX_STA = 0; }
```

bit7 未清（上一行还没被取走）时，`usart.c` 会把后续到达的字节**直接丢弃** —— 所以**同一时刻只能有 1 条命令在飞**。
真机实测"背靠背发 N 条 `TELEM`"的回收率（COM7）：

| 背靠背 N 条 | 回收率 |
|---|---|
| 1 | **100%** |
| 2 | 50% |
| 3 | 33% |
| 4 | 25% |
| 8 | 12% |
| **间隔 300 ms 逐条发** | **100%** |

**固定窗口扫描**（每档 6 秒，COM7）进一步证明加大窗口不划算：

| 窗口深度 | 实测帧率 |
|---|---|
| 1 | **6.50 Hz**（RTT 153 ms） |
| 2 | 6.49 Hz |
| 4 | 7.15 Hz |
| 6 | 7.15 Hz |

→ **窗口 1 已经拿到 1/RTT 的满速**；加大窗口只多约 10%，却开始成串丢失（回收率随 N 掉），得不偿失。

```python
class PullRequester:
    def start(self) -> Result              # 非阻塞; 首发一条请求
    def stop(self)  -> Result              # 立刻停发 + 放弃在途
    def tick(self)  -> None                # 调度线程 50 Hz: 收割 -> 补发(仅在途为 0 时)
    def snapshot(self) -> dict             # {"running","mode":"stop-and-wait","inflight","sent","done","lost","hz","best_hz"}

class StreamAPI:                            # 门面 mc.stream
    def on(self, timeout: float = 3.0)  -> Result    # = PullRequester.start()
    def off(self, timeout: float = 3.0) -> Result    # = PullRequester.stop()
    def toggle(self, on: bool, ...)     -> Result
    @property
    def is_on(self) -> bool                # 拉取器是否在跑（明确状态, 不再靠"最近有没有帧"猜）
    def stats(self) -> dict                # 上面的 snapshot()
    def tune(self, request_timeout=None) -> dict    # 仅实验用；已无窗口参数
    def anchor(self)                       # 当前锚 (本机单调秒, 设备 ms); 未建立 = None
```

> **为什么用停等而不是"堆在途请求"**：真机已经证明固件每 1 ms tick 只消费一行命令，成串发必丢（见上表）。
> 停等**不是软件限速**，而是协议层的物理约束 —— 可达帧率 = **1/RTT**，且**比堆在途更快**（每一条请求都真的换回一帧，零浪费、零丢失）。
> 真机停等复测：12 秒收到 **53 帧 = 4.41 Hz**（≈234 B/s 载荷），**在途恒为 1、丢 0、bad_crc 0**；单帧往返 157~234 ms。
> **"没有软件 Hz 上限"依然成立** —— 上限是链路往返（1/RTT）**涌现**出来的，不是硬编码。根因与数据见设计方案 §6.1.5。
