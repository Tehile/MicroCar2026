# 链路 MTBF 压测方法（固定 FPS 连续通信）

> 工具：`host/link_mtbf_test.py` ＋ 固件 `RATE FIX <hz>`（远程档 `MOUSE_REMOTE` 的常态命令，v2.6 起）
> 目的：在**恒定负载**下长时间连续通信，记录**首次断连时刻**，用于**换环境重复测试**、
> 定位随机掉链的物理原因（供电 / USB 口 / 2.4G 干扰 / 距离）。

---

## 0. 为什么需要"固定 FPS"

真机已证实：断连是**链路/模块侧的随机故障**，与发送速率 F 高低、是否升档、是否停发**均无关**
（实测死亡时刻散布在 60 / 127 / 170 / 234 / >240 s，F 从 8.25 到 16 Hz 都死过）。

要在不同环境间比较"谁更稳"，**负载必须恒定**：
- AIMD 自适应（`RATE UP/KEEP/DOWN` + 2 s 看门狗停发）会让 F 随时震荡、断连后还停发，
  存活时长**不可比** —— 那套已在 v2.6 删除（容量上限早已知清 24~30 Hz，已无使用场景）；
- 事件触发式拉取（`RATE PULL`）的周期 ≡ RTT，负载随链路状态浮动，同样不适合做基准。

`RATE FIX <hz>` 正是为此而留：**恒定 F 持续发帧，不停发、不降速** —— 一个纯粹的
"基准负载发生器"。本工具就是它的配套上位机。

## 1. 前置条件

|---|---|
| 固件 | 已烧录含 `RATE FIX` 的远程档（旧固件会回 `ACK <seq> ERR_CMD`） |

## 5. 结果解读

| `result` | 含义 | 退出码 |
|---|---|---|
| `SURVIVED` | 跑满 `--duration` 未断 | 0 |
| `BROKE` | 连续 `--gap-timeout` 无帧，判**断连**；`t_fail_s` = 断连时刻 | 1 |
| `ABORTED` | 人工 Ctrl+C（数据仍已落盘） | 1 |

**核心指标是 `t_fail_s` / `alive_s`。** 同一环境下多跑几轮，看它是否**稳定复现**；
换环境后再跑，比较分布是否整体变长。

- `mean_fps_obs` ≈ `fps_hz` ⇒ 零丢帧、链路健康；
- `mean_fps_obs` 明显偏低 / `max_gap_ms` 很大 ⇒ 存在卡顿（可能是积压或干扰），
  但**注意**：帧到达本来就有抖动（实测 1 s 窗口内 10~13 帧、最大间隔 150~300 ms 属正常）。

## 6. 重复测试流程（排查物理原因）

**每轮建议同一 `--fps`、同一 `--duration`，只改一个环境变量。** 断连后**先尝试物理断电**
（拔插 USB / 断模块电源 3~5 s）再跑下一轮 —— 软件重连与固件停发实测都救不回来。

> ❌ **2026-10-12 假说已证伪（2026-10-15 复验）**：曾观察一次断连后 PC 侧 ~7 min 无响应、
> 约 9 min 未断电却恢复（`PING` OK），一度以为是"自愈、只是恢复慢"。
> **2026-10-15 复验：断连后不会自愈，必须物理断电复位。** 当日 B 组（26.3 Hz PULL）
> t=95.2 s 断连后用户持续等待，链路始终无响应；手动断电重连后 `rst=POR`、`PING` 立即 OK。
> 当日另有一次"断连后探测到 PING OK"的假象，实为用户在两次探测之间已手动复位过
> （`rst=POR` 可证）—— **`rst` 字段是判断"是否真复位过"的可靠依据**：
> 断连后若 `rst=POR`，说明期间断过电；若 `rst` 仍是 `SW`/`WD` 等而 `PING` 通，才是真恢复。

| tag 示例 | 变动的变量 |
|---|---|
| `baseline` | 现状 |
| `usb2-rear` | 换到 USB **2.0** 后置口（避开 USB 3.0 对 2.4G 的辐射干扰） |
| `cap-added` | 模块 VCC 并 **100 µF + 100 nF** 去耦电容 |
| `nopowersave` | 关闭 Windows USB 选择性暂停（设备管理器里 CH340 及其 Root Hub） |
| `short-dist` | 缩短距离 / 移除中间遮挡 |
| `fresh-bat` | 换新电池（排除鼠标侧供电） |

跑完几组后直接看 `mtbf_matrix.csv`，比较各组 `t_fail_s` 的分布。

## 8. 丢帧归属：丢在单片机（MCU）还是链路中段

统一帧 offset 44 是固件上报的 **MCU 侧丢帧累计**（`LINK_U_DROP`，见通信协议规格 §1.6）。
判定要同时看两件事：`mcu_drop` 涨不涨 + PC 实收帧数。

> 历史：一次性探针 `probe_link_drop.py`（运行时包装 registry 解码器把该字节单独取出）
> 已随 **v2.6.1 清理移除**。现在直接跑 `link_pull_evt.py`（结束打印 **MCU 丢帧字节
> 末值 / 增量累计**）或任一在 `RATE FIX`/`PULL` 下运行的工具即可读到它。

判据（`RATE FIX <fps>` 恒定发送期间）：

| `mcu_drop` | PC 实收 vs 目标 | 结论 |
|---|---|---|
| 不涨 | < 目标 | 帧已交给模块，**丢失在链路中段**（模块/蓝牙/CH340 缓冲） |
| 涨速 ≈ 缺口 | < 目标 | 丢在**单片机 TX 环**（模块 UART 顶住，喂不进） |
| 不涨 | = 目标 | 本档位健康 |

**已测得（真机 COM7，mcudrop 全部为 0）**：

| 目标 | 交付率 | MCU 丢帧 | 说明 |
|---|---|---|---|
| 12 Hz | 100.0 % | 0 | 远低于容量 |
| 24 Hz | 99.0 % | 0 | 贴近容量 |
| 30 Hz | 91.9 % | 0 | 超容量，稳态丢帧 |

⇒ **瓶颈不在单片机侧**（UART 115200 8N1，51 B/帧仅占 ~13 % 带宽，TX 环永不满）；
超出容量的帧在**链路中段**被丢弃，且是**稳态丢**（第 1 秒起就丢），不是渐进积压。

## 9. `RATE PULL` 语义与早期的「批量节拍拉取」（历史）

固件 `RATE PULL <n> <t_ms>`：单片机按 `t_ms` 间隔连发 `n` 帧后静默，等新 PULL；
**新 PULL 立即打断重排**。于是"一次发几帧、帧间留多久"完全由 PC 掌握。
参数语义（现行协议，见通信协议规格 §1.5）：`n` 钳 1..16、`t` 钳 1..5000 ms。

> ⚠️ 早期工具 `link_pull_batch.py`（PC 主导的批量节拍拉取，含 `--batch` / `--period-ms` /
> `--start-period-ms` / `--adapt-every` / `--up-factor`… 的自适应闭环）已随 **v2.6.1 清理移除**。
> 它的"**等本批收齐才发下一条 PULL**"做法把速率压到 5.5 Hz（原因见 §10.1），已被下面两个工具取代：
>   - `link_pull_pace.py`（间隔闭环匀速拉取，见 §10）；
>   - `link_pull_evt.py`（事件触发式、周期 ≡ RTT，见 §14）。
> 遗留产物 `pull_pull-fix83.csv` 等只作历史数据引用。

> ⚠️ 需**先烧录含 `RATE PULL` 的固件**（`code_stm32f1_mouse/USER/Object/Mouse.hex`）；
> 旧固件会回 `ERR_NAME`（表现为 `CommandError`）。

## 10. 间隔闭环匀速拉取 `link_pull_pace.py`（取代 `--period-ms` 定值做法）

### 10.1 为什么早期「批次级停等」的速率只有 5.5 Hz（历史）
`pull_pull-fix83.csv`（由已移除的 `link_pull_batch.py` 以 `--batch 2 --period-ms 83` 跑 300 s）：

| 指标 | 值 | 含义 |
|---|---|---|
| 授权节拍 n/t | **24.10 Hz** | ⚠️ **不是有效速率**，见下方说明 |
| 帧内节拍 1000/t | **12.05 Hz** | 固件帧尾广播的 F（单片机自己的节拍）；**这才是真实速率上限** |
| **实测列 `rate_hz`** | **5.52 Hz** | **PC 实际收到**的帧率（`收帧数/墙钟秒`） |

`实测列 = 接收帧率`，与真实速率上限 `1000/t = 12.05 Hz` 差 **2.18 倍**。原因：老工具
**等本批收齐才发下一条 PULL**（批次级停等）⇒ 每批多出一个"命令往返"的空档：
828 批 / 300.3 s = **362 ms 一批**（2 帧 / 362 ms = 5.52 Hz），而批内只占 83 ms，
余下 ~280 ms 是纯静默 —— 这正是"2 帧一顿 + 一大段静默"的来源。

> ⚠️ **`n/t` 不是速率，别再拿它做分母。** 固件是"每 t ms 发 1 帧、共 n 帧"，
> n 帧共占 **n·t** ms ⇒ 持续上限 = `n/(n·t)` = **1000/t**。`n·1000/t` 相当于把 n 帧
> 挤进一个 t 里，**比真实上限大 n 倍**。此前本表曾写"差 4.37 倍"，那是拿 5.52 去比
> `n·1000/t`（n=2）得到的，多出来的因子 2 就是 n —— **正确值是 2.18 倍**。
> 该列在工具输出里叫 **`授权(n/t)`**，请一律忽略。

> ⚠️ **该 CSV 的 `mcu_drop` 列是错的**：`_, ndrop, _ = fl.snapshot()` 写成了
> `ndrop, _, _ = ...`，取到的是**帧数**而非丢帧字节（所以出现 580 这种 >255 的值，
> "MCU 丢帧增量 1566" 实为帧数增量）。正确真值见 §8：**丢帧字节恒 0**。

### 10.2 速率列的口径（三列分别是什么）

`link_pull_pace.py` 启动时打印目标行、结束时打印"实收 vs 授权 vs 帧内"三列，
**只有前两个有意义**：

| 列名 | 公式 | 是否有效 | 说明 |
|---|---|---|---|
| `--fps` / 目标 / `帧内(1000/t)` | `1000/t` | ✅ **有效，且是设计目标** | `t = round(1000/fps)` 是固件的批内间隔；批周期 = `n/fps` = n·t ⇒ 持续速率 = `n/(n·t)` = `1/t` = **fps 本身**。 |
| `PC 实收` | 收帧数 / 存活秒数 | ✅ **有效** | 主机真正解析到的统一帧速率（含链路中段丢失）。**判据：实收 ≈ `--fps`。** |
| `授权(n/t)` | `n·1000/t` | ❌ **无效** | 把 n 帧挤进一个 t 里算，**比真实上限大 n 倍**。看到 12/60 这类数请直接忽略。 |

所以 `--fps 4 --batch 3` 的预期结果是**实收 ≈ 4 Hz**，不是 12 Hz：
`授权(n/t) = 12` 只是那个错误公式（3×1000/250）。实测 4.01 Hz / 交付 99.7% 属正常。

> 另注：`交付率 = 实收帧 / 授权帧`，其中"授权帧"= 批次数 × n，与速率列是两回事。
> 交付率接近 100% 而实收 ≈ fps，就是"链路健康 + 节拍跟上"。

### 10.3 正确做法：批还没发完就把下一条 PULL 发出去
固件 `PULL n t` 语义 = **收到即发第 1 帧，之后每 t ms 一帧，共 n 帧，发完静默**。
只要"下一条命令到达单片机"的时刻落在上一批末帧之后，两批就无缝拼成一条均匀流：

```
目标网格:  批 k 首帧应到 due_k,  下一批 due_{k+1} = due_k + n*T   (T = 1/fps)
发送时刻:  send_k = due_k - RTT      ← 整趟往返! 帧要"命令下行+帧上行"走完整趟
约束:      命令**到达**单片机 >= 上一批末帧发完 (= due_k - t) + safety
```

* `send = due - RTT/2` 是**错的**（早期版本踩过）：每批都晚 RTT/2 到，网格再被实测首帧
  牵着走 ⇒ 误差逐批累积，实测只有 10.4 Hz。
* **不在单片机上做任何计算**：`n` 与 `t` 由 PC 决定，单片机只做倒计时；
  PC 则按**实测**帧间隔/往返时延闭环决定"这一刻该不该再发一条 PULL"。

```bash
python link_pull_pace.py COM7 --fps 12 --batch 2 --duration 300 --tag pace12n2
python link_pull_pace.py COM7 --fps 12 --batch 4 --duration 300 --tag pace12n4
```

产物：`pace_<tag>_frames.csv`（逐帧 `gap_host_ms / gap_mcu_ms / ms8 / drop`）、
`pace_<tag>.csv`（逐秒 `recv_hz/cmd_hz/frame_hz/mcu_gap_ms/rtt_ms/drop_u8`）、
`pace_<tag>_summary.txt`、`--append-matrix` 跨环境总表。

### 10.4 度量方法学（重要，之前的结论有一半是被测错的）

| 观测量 | 可用性 | 依据 |
|---|---|---|
| 帧内 `ms8`（载荷 0，单片机毫秒时基低 8 位） | **可信，判定均匀性的唯一真值** | 标定：每 1000 ms 发一条 PULL，Δms8 = 975/1050 ⇔ 墙钟 967/1057；`RATE FIX 12` 跑 20 s 时钟比值 **1.0002** |
| 主机侧到达时刻（`_rx_mono`） | **不能用于抖动判定**，只能算速率 | CH340/USB 攒批：`RATE FIX 12`（源侧 Δms8 = 83/84、σ=0.5）下主机侧间隔 **σ = 76 ms**，两帧被打成 0.08 ms 间隔（57 B 在 115200 上就要 4.9 ms，物理不可能） |
| `LINK_U_DROP`(载荷 44) | 可信，**PULL/FIX 两种模式下恒 0** | 真机实测，见 §8 |

固件 PULL 定时精度实测（单条命令、读 Δms8）：
`t=83→83, 100→100, 200→200, 400→400`；`n=4,t=100 → [100,100,100]`；`n=4,t=250 → [250,250,250]`
—— **批内间隔精确等于 t，硬件定时，无需 PC 纠偏**。

### 10.5 12 Hz / n=2 闭环实测（60 s 量级）

| 指标 | 结果 |
|---|---|
| PC 实收 | **11.9 ~ 12.1 Hz**（目标 12.05，误差 <1%） |
| 交付率 | 96 ~ 100%（缺口来自链路中段整帧丢失，不是 PC 侧） |
| MCU 丢帧字节 | **0**（固件从未因发送环满丢帧） |
| 批起点间隔(ms8) | 均值 167.5 ms（目标 166.7） |
| 帧间隔(ms8) | **批内恒 83 ms**；跨批 **67 ms（约 3/4）或 142 ms（约 1/4）** |

跨批 67/142 的成因：**PC→单片机 的命令通路存在 ~75 ms 量级的量化**
（67 = 83.4−16，142 = 67+75，另见 217 = 67+150）。已尝试两种"纠偏"，都无效或有害：

* 主机侧**自旋**定时（排除 Windows 15.6 ms sleep 粒度）→ 67/142 照旧；

  新 PULL 落到上一批末帧之前 ⇒ 固件按"打断重排"丢弃本批剩余帧 ⇒ 交付率掉到 91%。
  ⇒ 默认**关闭**（`--phase-gain 0`），仅作实验。

## 11. 抖动的根因：下行命令通路 75 ms 量化（已定量验证）

§10.4 只说到"跨批 67/142、疑似 ~75 ms 量化"。本节把它做成了**可预测、可复现**的模型。

### 11.1 固化事实：固件的批内节拍是**精确**的

`--batch 4 --fps 12`（t=83）一轮里，按值分类后：

```
批内间隔: n=535 均值=83.0 σ=0.0 min=83 max=83      ← 535 个全部精确 83 ms
跨批间隔: n=182 众数 51(48.9%) / 126(16.6%)        ← 两簇相差 75
```

**σ=0** ⇒ 单片机自己倒计时发帧没有任何抖动。所以"数据不均匀"100% 来自
"下一条 PULL 什么时候到达单片机"，与固件无关，与上位机怎么算周期也无关。

### 11.2 模型：批起点被吸附到 75 ms 栅格

设批周期 `T = n·t`（ms），`Δ = T mod 75`。跨批间隔恒为**双峰**，两峰间距
**恒等于 75 ms**，且落在"早簇"的比例 = `(75 − Δ)/75`。三点独立验证：

| n | t | T | Δ = T mod 75 | 实测跨批双峰 | 间距 | 实测早簇占比 | 预测 (75−Δ)/75 |
|---|---|---|---|---|---|---|
| 1 | 83 | 83 | 8.3 | **75 / 150** | 75 | 603/695 = **86.8%** | **88.9%** |
| 2 | 83 | 167 | 16.7 | **67 / 142** | 75 | 555/716 = **77.5%** | **77.8%** |
| 4 | 83 | 333 | 33.3 | **51 / 126** | 75 | 98/176 = **55.7%** | **55.6%** |

六个独立数字（3 个间距 + 3 个占比）全部对上 ⇒ 模型成立。物理含义：
**PC 写下的命令并不是立刻被单片机执行的，而是被吸附到 75 ms 的栅格上**；
批周期于是要么"早一档"要么"晚一档"，但相位均匀推进 ⇒ 均值自动回正
（各轮实测批起点均值都精确等于 T）。

> 机制层面尚未定位到底是模块的收包刷新周期、还是 CH340/驱动的上行节奏，
> 但**它与上位机侧的定时精度无关**：主机自旋定时、ms8 相位闭环都改不动它（§10.4）。

### 11.3 直接推论：`n·t ≡ 0 (mod 75)` 时抖动塌缩 —— 已实测命中

Δ=0 时相位每批前进 0，永远落在同一栅格 ⇒ 双峰并成单峰。对 `n=2, t=75`
（T=150=2×75，即 **13.333 Hz**）的预测是"几乎全部间隔都精确等于 75 ms"：

```
--fps 13.3333 --batch 2 --duration 60
  结果 SURVIVED 60.1s  交付率 99.1%  PC 实收 13.23 Hz
  MCU 间隔直方图: [(75, 772), (74, 9), (76, 6), (151, 3), (150, 3), (331, 1)]
  σ = 11.2 ms   偏离目标>25%+5ms: 7/794
```

对照 12.05 Hz（t=83）：σ=24.0 ms、偏离 163/1437。**偏离率降到 1/12，σ 减半，
而且速率更高。** 772/794 = 97.2% 落在恰好 75 ms。

实测对比：

| 配置 | 目标 | PC 实收 | 交付率 | MCU σ | 偏离目标占比 |
|---|---|---|---|---|---|
| t=83, n=2 | 12.05 Hz | 11.98 Hz | 99.7% | 24.0 ms | 163/1437 = 11.3% |
| t=75, n=2 | 13.33 Hz | 13.23 Hz | 99.1% | **11.2 ms** | **7/794 = 0.9%** |
| t=83, n=1 | 12.05 Hz | 11.72 Hz | 97.6% | 30.5 ms | 97/703 = 13.8% |
| t=83, n=4 | 12.05 Hz | 11.96 Hz | 99.2% | 25.2 ms | 180/717 = 25.1% |

**结论（可操作）**：要"均匀到达"，先把批周期凑成 75 ms 的整数倍。
可行的 Δ=0 档位（t 必须为整数 ms）：

| T = n·t | 可达速率 | 说明 |
|---|---|---|
| 150 | 13.33 Hz | n=1/t=150、n=2/t=75、n=3/t=50（→**20 Hz**）… 同一 T 下 n 越大速率越高 |
| 225 | **22.2 Hz** | n=5/t=45、n=9/t=25（→40 Hz） |
| 300 | 20 Hz | n=6/t=50、n=8/t=37.5(非整数, 不可) |

即 **速率 = 1000·n /(75k)**：`n=5,t=45,T=225` 给 22.2 Hz，`n=3,t=25,T=75` 给 40 Hz。
**待验证**（链路一旦恢复）——但须先确认链路容量能否撑到 20 Hz 以上。

### 11.4 度量方法学补充（接 §10.3）

* **批内/跨批必须按"值"分类，不能按 CSV 的 `batch` 列**：`batch` 由读线程在读
  到帧时才读 `cur_batch`，主循环可能已推进到下一批 ⇒ 迟到的帧被贴上下一批的号
  （实测 n=1 时出现重复批号）。按值分类无竞态：批内 ≡ t，凡 `|gap−t|>3ms` 必是跨批。
* `link_pull_pace.py` 摘要里的 **`批起点间隔`** 原先用主机时间戳解缠 ms8，会选错分支
  （n=2/t=75 时真值 150 ms 被判成 181 ms）。**已修**：改用名义批周期 `T=n·t_cmd_ms`
  作解缠参考（单片机 ms8 与墙上时钟比率 1.0002，真值必在 T 附近）。

## 13. 速率控制原理：为什么"不知道基础频率"也能命中目标（附"倍数"的两条路线）

用户设想：**在稳定的单次拉取（基础频率）之上叠加"新发送"来达到倍数发送**，
以增强快速频率下的稳定性。这一节把原理讲透，并给出这个设想的两条实现路线与各自上限。

### 13.1 旧工具里"基础频率"是**涌现**出来的，不是被设定的

已移除的 `link_pull_batch.py` 的主循环（"**等本批收齐**"的批次级停等）：

```
while True:
    send PULL n t
    wait until got >= n          # deadline = n*t + 0.4s
```

速率 = `n / 批周期`，而批周期 = `(n-1)*t`（批内发帧）+ **L**（等收齐 + 轮询 + 0.4 s 余量）。
由 n=2 / t=83 实测 362 ms/批反解 ⇒ **L ≈ 279 ms**，比批内时间（83 ms）大 3 倍多。
所以"基础频率 5.52 Hz"是**等出来的结果**，代码里没有任何一处可以设置它。

| n（t=83 固定） | 批周期 | 速率 | 效率（相对 1000/t） |
|---|---|---|---|
| 1 | 279 ms | 3.58 Hz | 29.7% |
| **2** | **362 ms** | **5.52 Hz** | **45.9%** |
| 4 | 528 ms | 7.58 Hz | 62.9% |
| 8 | 860 ms | 9.30 Hz | 77.2% |
| 16 | 1524 ms | 10.50 Hz | 87.1% |
| ∞ | — | **12.05 Hz** | 100% |

### 13.2 新工具里"基础频率"根本不参与运算

`link_pull_pace.py` 把"该多快"从**观测**改成了**声明**：

```
t_cmd_ms = round(1000 / fps)        # 写进固件
due_k    = t0 + k * (n / fps)       # 第 k 批首帧**应到达**的时刻
due     += n / fps                  # 每批固定推进, 永不锁到实测（第 394 行）
```

- **定频是开环的**：`due_{k+1} − due_k ≡ n/fps` 是常数 ⇒ 持续速率 = `1000/t` = `fps`，
  结构上与链路好坏无关。哪怕某批整批丢了，网格也不漂、不累积误差。
- **实测只做一件事：算提前量** `rtt_est`（EWMA），决定"提前多久按下发送键"。
  它只**平移相位**，不改速率。所以"不知道基础频率"不是缺陷 —— 基础频率这个概念
  在新设计里**从未被引用**。

**提前量必须是整趟 RTT**：固件收到命令**立即发第 1 帧**，
`首帧到达 = send + RTT_下 + RTT_上 = send + RTT` ⇒ 想落在 `due` 就取 `send = due − RTT`。
早期误写 `due − RTT/2`，每批晚 RTT/2，实测被压到 10.4 Hz。

### 13.3 "倍数"的三条路线（只有两条是对的）

**路线 A：加大 n —— 用户的直觉，数学上成立**
不动调度、不动固件，只让每次拉取带更多帧 ⇒ 固定开销 L 被摊薄，效率单调上升
（见 13.1 表：n 从 2 到 16 把效率从 45.9% 推到 87.1%）。
附带好处很对症：**命令数下降 n 倍**（12/s → 0.75/s），而命令通道正是抖动来源（§11 的 75 ms 量化）。
代价：**天花板不变，仍是 `1000/t`**；且 n 大 ⇒ 单批突发变长，撞 TX 环/蓝牙缓冲的风险上升。

**路线 B：重叠节拍 —— 本工具**
不改 n，直接在时间轴上删掉"等"，效率立即 ~100%，**且与 n 无关**（n=1 也能跑满）。
代价：引入旧工具**永远不会有的**新失效模式 —— **命令早到会抢占丢帧**
（固件收到新 PULL 丢弃本批剩余帧）。实测把发送时刻往早推（`--phase-gain > 0`），
交付率从 ~100% 掉到 **91%**，故相位微调默认关；靠 `earliest` 夹紧 + `--safety-ms`（默认 12 ms）保护。

**❌ 路线 C：多线程 / 多定时器并行发 PULL —— 错的，别做**
PULL 是**抢占式**语义，两条流会互相打断：先到的命令作废另一条正在发的批次。
"叠加新发送"若实现成"再起一个发送者"，结果是**丢帧**而不是提速。
要"叠加"，必须把新发送**重排进同一条时间表**，而不是并排发。

**A、B 都不改变上限 `1000/t`**：两者乘的都是"效率"，乘不动"链路容量"。
所以"倍数增强"的可行区间是 **5.5 → 12 Hz**；要更高只能减小 t（= 改基础节拍）。

### 13.4 关于"倍数能增强稳定性"这个前提，需要泼一点冷水

前提是"单次拉取稳定可靠，所以用倍数方式能在快速频率下保持稳定"。但现有 MTBF 数据
**不支持"速率越高越不稳"**：断连时刻横跨 26.9 / 47.7 / 60 / 127 / 170 / 234 s，
同时也有多轮 120~300 s 存活，与 F 高低、升档、停发**都无关**（见 §7 与 `MEMORY.md`）。
看起来是**模块侧随时间累积的随机故障**，与配置无关。

⇒ 要回答"倍数是否增强稳定性"，唯一有说服力的做法是**对比 MTBF 分布**（不是看单轮）：

| 对照组 | 命令 | 观测量 |
|---|---|---|
| 旧停等（已移除的 `link_pull_batch.py`） | `--batch 2 --period-ms 83` | 5.52 Hz 的 MTBF |
| 路线 A | `link_pull_pace.py --fps 12 --batch 8` | 12 Hz、命令稀疏的 MTBF |
| 路线 B | `link_pull_pace.py --fps 12 --batch 2` | 12 Hz、命令密集的 MTBF |

每组重复 ≥5 次（300 s 或跑到断连），比较存活时间的**分布**。
关键点：路线 A 与 B 的**到达速率相同、命令频率差 4 倍**，正好把"帧率"与"命令负载"
两个变量分开 —— 这是这套对比设计的价值所在。

### 13.5 一个反直觉的结论：路线 A 可能比路线 B 更适合"稳定"

- 命令越少 ⇒ 越少机会撞上 75 ms 量化（§11）
- 单批越长 ⇒ 帧间由**固件倒计时**保证（实测 535 帧全部精确 83 ms，σ = 0.0）
- 即 **"基础频率 + 倍数"（路线 A）在稳定性上可能优于"重叠节拍"（路线 B）**，
  代价是速率上限被 t 锁死。

若走路线 A，批周期应取 75 ms 的整数倍（§11.3），即 `T = n·t = 75k` ⇒ 速率 = `13.33·n/k` Hz：
n=2/k=2 → **13.33 Hz**｜n=3/k=2 → **20 Hz**｜n=5/k=3 → **22.2 Hz**｜n=4/k=2 → 26.7 Hz。

## 14. 事件触发式拉取 `link_pull_evt.py`（周期 ≡ RTT，自锁；无目标频率）

### 14.1 方案（用户口径，2026-10-13 确认）

1. **基频仍是同一套"PC 拉取、MCU 发送"** —— 架构不变，单片机仍是被动的，只按
   `PULL <n> <t_ms>` 倒计时发帧；
2. **一个拉取周期内发多帧**（n > 1），"倍数"就是从这里来的；
3. **下一次拉取的触发 = 收到本周期第 1 帧**（事件驱动，不是定时发）；
4. **单片机侧不等上一批发完** —— 新 PULL 一到即丢弃本批剩余、从第 1 帧重发（抢占语义）；
5. n = 1 时与"已验证可靠"的老拉取模式（n=1 停等）**逐位同构**（那时"等整批收齐"就是"等唯一那帧"）。

固件侧已逐行核实：`link_PullSet()`（`link.c:1352`）每次调用都把 `linkPullTimer = 0`
（注释明写"立即发第一帧"），再调一次即覆盖 `linkPullCount/Period`，旧批剩余帧作废；
**这种抢占不产生任何丢帧计数**（帧是"从未发出"而非"发了丢了"），`LINK_U_DROP` 不动；
PULL 分支**跳过看门狗/停发**，所以连续拉取不会触发固件自己刹车。钳位 `n ∈ [1,16]`、`t ∈ [1,5000] ms`。

### 14.2 自锁性质：周期 ≡ RTT（这是本方案最漂亮的地方）

```
首帧到达 = send + d_down + d_up = send + RTT
```
而"收到本周期第 1 帧"又**立刻**触发下一条命令 ⇒
```
S_{k+1} − S_k = RTT   ← 周期恒等于链路往返时间
```
**PC 完全不需要测 RTT，也不需要设目标频率。** 由此推出的速度律：

| 量 | 表达式 | 说明 |
|---|---|---|
| 每周期实发帧数 | `N = min(n, ⌈RTT/t⌉)` | 超出部分被新命令抢占，**从未发出**（不占链路、不算丢帧） |
| 到达速率 | `≈ N/RTT ≈ 1/t + 1/RTT` | 上限仍由 `t` 决定 |
| 命令频率 | `≡ 1/RTT` | 与 n、t 都无关（这是本方案唯一"费"的地方） |
| 帧间隔序列 | `t, t, …, t, (RTT mod t)` | **均匀性只取决于 RTT mod t**；t 越小越均匀、越快 |

**`n` 不是速率旋钮，`t` 才是。** `n·t ≥ RTT` 之后抢占成常态，速率自己跑满；反之
`n·t < RTT` 会让单片机发完一批后**空转**等命令 ⇒ 白丢时间。所以 n 只需"够大"（设大无代价，
设小才是损失）。这一点与 §13.3 的"路线 A"是同一件事，只是这里不再需要人算，链路自己给。

### 14.3 与 §10 排程式（`link_pull_pace.py`）的控制哲学对比

| | 排程式 `link_pull_pace.py` | **事件触发式 `link_pull_evt.py`** |
|---|---|---|
| 何时发下一条 | PC 按 `due += n/fps` 算好的日历 | **收到本周期第 1 帧就立刻发** |
| 需要测什么 | 需要 `rtt_est`（整趟 RTT）当提前量 | **什么都不用测** |
| 速率 | 可指定（误差 <1%） | 自锁于链路（= `⌈RTT/t⌉ / RTT`） |
| 相位 | PC 决定，可整体平移 | 由链路决定 |
| 失效模式 | 相位推早会抢占丢帧（实测交付掉到 91%） | 判据或 ACK 丢失 ⇒ 漏一个周期后**如实报断**（**绝不补发**，见 §14.12） |

两者**速率上限相同**（都是 `1000/t` 的量级），复杂度上事件触发式更低，代价是速率不可指定。
用户明确选择事件触发式（"速率是自锁的，不需要设置目标频率"），故 `link_pull_evt.py` 只需要
`--batch n` 与 `--t-ms t` 两个参数。

### 14.4 触发判据：`frame` / `ack` / `auto`，以及 `RTT ≡ 0 (mod t)` 死角

**frame（用户口径）**：批内间隔恒 = t（实测 535/535 精确，σ = 0.0），所以"**与前一帧间隔 ≠ t**
的那一帧"就是本周期第 1 帧。用 **ms8**（帧内单片机毫秒时基，真值）判定，**不用主机时间戳**
（被 CH340/USB 攒包污染 σ≈75 ms，见 §10.4）。判别时用一条关键不对称：
**短间隔（< t）= 批起点；长间隔（> t）= 丢帧**（`k·t` 的整数倍），后者绝不能当批起点。
⚠️ 需 `t < 128`（ms8 只有 8 位）。

⚠️ **死角（重要）**：批起点间隔 = `RTT mod t`。当 **RTT 恰是 t 的整数倍**时，本批最后一帧
落在 `A+k·t`、而新命令也在 `A+k·t` 到达 ⇒ 那帧被抢占，真正的前一帧是 `A+(k−1)·t` ⇒
**批起点间隔恰好等于 t，与批内完全一样**，帧判据永远看不到边界 ⇒ **停摆**。
实测 RTT 是 **300 ms**，取 `t = 75`（300 = 4×75）正好踩中；`t = 100`、`150` 同理。
离线自测已对 16 组退化参数逐一复现（见 §14.6）。
⇒ **这正是"固定 t 靠不住"的第一个信号**：死角参数不只取决于 t，还取决于当时的 RTT，
而 RTT 不是你能预知的。§14.8 的 `--frames N` 就是从根上绕开这件事。

**ack**：`RATE PULL` 会回 `ACK <seq> OK`；固件里顺序是 `link_PullSet()`（把帧留到**下一个 1ms
tick** 才进 TX 环）**先**、`link_Ack()`（字节立刻进环）**后** ⇒ 线上顺序是 ACK 先于本批第 1 帧。
无歧义、与 t 无关、"批内丢帧"不会误触发；代价是依赖 ACK 本身不丢。

**auto（默认）= frame 为主 + ack 兜底**：先扫帧，扫不到再看 ACK。这样既保留了用户口径，
又填掉了上述死角。

⚠️ **度量学补充（新踩的坑）**：**主机侧观察到的 ACK/帧先后 ≠ 线上顺序。** ACK（14 B）与本批
第 1 帧（59 B）常被 USB 缓冲**攒进同一个突发**一起释放，于是主机侧看两者几乎同时（实测
"F1 到达 − ACK 到达"均值 0.2 ms，而线上顺序应差约 5 ms）。所以：
* `link_pull_evt.py` 汇总里的 **"ACK 提前量"不能用来验证固件顺序**，只说明"两者被打包在一起"；
* 首轮真机里 `auto` 的触发统计是 **frame 105 : ack 12** —— 不是"ACK 丢了 90%"，而是
  **判据竞速的结果受分块影响**，这在修复"结算"缺陷后（见 14.5）已不再重要。

### 14.8 动态 `t`：`--frames N`（把旋钮从 `t` 换成「倍数」，2026-10-13 当日追加）

**起因**：用户问"`-t-ms 83` 这个参数有必要吗？它应该结合上一次拉取的时间动态计算"。答案分两半——
**速率上没必要，均匀性上很必要**，而且是"不改就是隐患"的那种必要。

#### （1）为什么固定 `t` 是个"抽奖"

§14.2 的帧间隔序列 `t, t, …, t, (RTT mod t)`，最后一项就是隐患：**均匀性完全由 `RTT mod t` 决定**。
以实测 RTT = 300 ms 为例：

| t | 每周期帧数 | 间隔序列 | 极差 | 判定 |
|---|---|---|---|---|
| **83** | 4 | 83, 83, 83, **51** | **32 ms** | 本轮实跑的档位 |
| 76 | 4 | 76, 76, 76, 72 | **4 ms** | 最优 |
| **75** | **5** | 75, 75, 75, 75, **0** | **75 ms** | 灾难：75 整除 300，边界间隔塌成 0 |
| 100 | 4 | 100, 100, 100, **0** | **100 ms** | 灾难 |
| 101 | 3 | 101, 101, **98** | 3 ms | 最优 |
| 150 | 3 | 150, 150, **0** | **150 ms** | 灾难 |

同一 RTT 下最好与最坏**差 50 倍**，且相邻 1 ms 的 `t` 就能从最优掉到灾难（76 → 75）。
**所以固定 `t` 的问题不是"不好"，而是无法预知好不好**——而 `t` 一旦选错，代价是每个周期都有一次
几十毫秒的间隔畸变（对"尽量均匀"的初衷是直接违背的）。

#### （2）正确的动态公式：`t = ⌊RTT/N⌋ + 1`（不是 `round`）

把旋钮从 `t` 换成 **N = 每周期目标帧数**——这正好就是用户说的"**基础拉取频率的倍数**"：
基频 = 每周期 1 帧 = `1/RTT` = 单帧拉取（已验证可靠的那个模式），N 帧/周期 = N 倍基频。

要每周期**恰好** N 帧，需同时满足 `(N−1)·t < RTT` 与 `N·t > RTT` ⇒

```
t = ⌊RTT / N⌋ + 1          ⇒   N_eff ≡ N，间隔极差 = N − (RTT mod N) ∈ [1, N] ms
```

⚠️ **不能写成 `round(RTT/N)`**：只要 `N | RTT` 它就退化成 `t = RTT/N`，于是 `N·t = RTT`、
下一帧正好落在周期末尾 ⇒ `N_eff = N+1` 且边界间隔塌成 0。离线自测里 6/6 个 `N | RTT` 用例
全部翻车（RTT=300/N=4 ⇒ 间隔 `75,75,75,75,0`）。

#### （3）RTT 从哪来：**必须用 ms8，不能用主机时间戳**（差 20 倍）

批起点帧的 ms8 做差 = 一个周期 = RTT，且是 **MCU 时基**。实测同一轮：

| 口径 | 均值 | σ | 极差 |
|---|---|---|---|
| 主机时间戳周期 | 301.1 ms | **13.8 ms** | 166.2 |
| **ms8 周期（MCU）** | **300.6 ms** | **0.7 ms** | 2（剔 2/132 野值后） |

主机侧的 13.8 ms 全是 CH340/USB 攒包与线程调度抖动，**不是 RTT 的真实抖动**。拿它去推 `t`
（`t = ⌊RTT_host/4⌋+1`）会在 74/75/76 之间跳——而 **75 恰好是灾难值**，所以那样做**比固定 `t` 更糟**。
实现里还加了 `--rtt-window`（默认 8）取**滑窗中位数**抗离群：原始 ms8 周期里有 2/132 个
225 / 457 ms 的野值（单样本口径 `t` 取值 `{76:126, 75:3, 57:1, 115:1, 74:1}`；K=8 中位数后 `{76:130}`）。

⚠️ **解缠参照必须用"主机周期"，不能用"ms8 自己的中位数"**。ms8 只有 8 位，`R(x)` 有 256 ms 的
分支歧义；若拿 ms8 估计值当中位数参照，一旦某次解缠错了就会**自锁在错值上永不恢复**
（构造实例：RTT 从 300 突降到 120 ⇒ 解成 376 ⇒ 参照跟着走 ⇒ 越错越信）。
改用 `median(host_hist)`（主机周期是**无歧义直接测量**，误差只有 ±14 ms）当参照，就天然自恢复：
RTT 真变化时主机周期几轮内跟上、把参照拉回正轨。再加一道 **±80 ms 一致性闸**，
256 ms 的错分支必被拒、主机自身的野值（实测有过 451 ms）也一并滤掉——一箭双雕。

#### （4）关于「硬约束 1」的**取消**：`N` 现在没有下限（2026-10-13 起）

> 旧版有 `t ≤ 127 ms`（ms8 只有 8 位）⇒ `N > RTT/127` 的下限，RTT=300 时 N ≥ 3（≈10 Hz）；
> 实现里检测到 `N` 太小还会**自动抬到下限**并打印一次警告（`n` 同步抬高）。**这条已作废。**

* **它到底在防什么**：只有 **ms8 帧间隙判据**需要 `t ≤ 127` —— `t > 127` 时"丢一帧"的间隔
  `2t` 会与 256 ms 折回混淆、被判成"批起点" ⇒ 提前触发 ⇒ 多发命令 ⇒ 顶爆链路。
* **为什么能取消**：默认判据改读固件打的 `FLAG_PULLF1` 标记帧（v2.6.1 / fw 219，见 §14.15）后，
  "哪一帧是批起点"是**读事实**、与 `t` 无关 ⇒ 下限随之取消。于是 `--frames 1`
  即**纯单帧拉取**（≈`1/RTT`，与先前长期验证稳定的老模式逐字节相同）、`--frames 2` 也都直接可用，
  不必再借 `--batch` 去绕那个自动抬升。
* ⚠️ **仅 `--trigger frame` 仍受 `t ≤ 127` 限制** —— 那条通路在主循环里**单独告警**（不再误报其它档）。

**剩下唯一与判据有关的硬约束**：帧判据的 `tol` 必须 **< 1 ms**。批起点间隔最多只比 `t` 短
`t − bd = N − (RTT mod N)`，最坏**恰好 1 ms**；`tol ≥ 1` 会把边界判成批内 ⇒ **漏触发、环路停摆**。
默认 `0.75` 安全。

> 离线自测已同步：反演覆盖 (RTT, N=**1**..8) 共 88 组、断言 `N_eff ≡ N`；`effective_N()` 变成
> **恒等函数**（把"无下限"这个决定写进 docstring）；CLI 推导新增 `N=1/2` 两组用例。

#### （5）实现要点：动态 `t` 下判据必须**按"上一帧所属批"取 `t`**

批内间隔精确等于**该批发射时**的 `t`，而 `t` 会逐周期变 1 ms。若一律拿当前 `t` 去比，
旧批的批内间隔（例如 76）对上新的 `t`（75）会 `|76−75| > tol` ⇒ **整批被误判成丢帧**；
而放宽 `tol` 去兼容，边界又会漏检（见硬约束 2）——两头堵。
解法是 `link_pull_evt.py` 里的 `t_of_batch`：发送前把 `t` 记到批号上，扫描时用**上一帧所属批**的 `t`。
（这条是写测试时才想清楚的，**不做就会在第一次 `t` 变化时静默崩掉触发环路**。）

⚠️ 但更要命的是**"帧属于哪一批"本身怎么定**：**必须在收到该批 ACK 时打标**，不能用发送时刻。
用发送时刻打标时，在途的上一批尾帧会被贴上**新批号**，`t_of_batch` 一查就是**新 `t`**，
于是旧批的批内间隔被误判成批起点 ⇒ 多发命令 ⇒ 触发周期中位数塌 ⇒ 解缠参照塌 ⇒ **自锁发散**。
完整链条、两处修复与 2×2 离线对照见 **§14.9**。

#### （7）结论：`-t-ms` 该不该留？

* **作为"速率旋钮"：不需要**。速率 = `N/RTT`，周期被自锁钉死在 RTT 上，`t` 只决定帧落在周期内的哪里。
  换句话说，**你原方案里"周期动态计算"的那一环，在自锁结构里已经自动完成了**——周期不是自由变量。
  真正该被"动态计算"的是 `t`，而它需要一个 RTT 估计，用的是 ms8 而不是主机时间戳。
* **作为"均匀性旋钮"：必须动态**，且公式是 `⌊RTT/N⌋+1`，`N` 才是人该给的那个数（= 倍数）。
* **`--t-ms` 保留的价值**：① 动态模式下的**起步种子**（第一个周期还没有 RTT 估计）；
  ② 跑固定 t 对照实验；③ 显式钉死一个 `t`（极低频档 `N=1` 现已直接支持，无须再借它）。

### 14.9 起步单帧轮(`--bootstrap K`)与 `--frames` 发散的根因（2026-10-13 定位）

**起因**：用户跑 `--frames 4`，**3.9 s 就断**（上一轮 `t=45` 档是 3.4 s，构成第二个"短命"样本）。
逐周期表（`evt_dyn_n4_periods.csv`）暴露了真正的问题——`t` 在跑：

```
周期  1    2    3    4    5    6    7    …   14   15
t_ms  83   83   83   76   76   62   68   …   38   38
周期   —   348  197  308  316  134  150  …  142  308   (ms)
```

`t` 一路往下掉，周期跟着腰斩。用户当时的假说是"**第一轮没有正确处理发送数据周期**，所以第一轮
应当一次只拉一帧"。这个假说**方向对**（起步阶段确实最薄弱），但真机数据说明它只是**表象**。

#### （1）`--bootstrap K`：采纳用户假说（起步退回单帧拉取）

起步 K 个周期改发 `RATE PULL 1 t` —— 与先前真机验证稳定的原模式**逐字节相同**：

* 起步时动态 `t` 还没有 RTT，只能拿种子 `--t-ms` 猜（实测前 **3** 个周期都在用种子 83）；
* `n=1` 时**不需要 `t` 正确**（单帧发完即静默，下一条命令由帧到达驱动）；
* `n=1` 时相邻帧间隔 = 周期 = RTT ⇒ **这几轮顺带把 RTT 测准**，切到 N 帧时 `t` 已经是对的。
  → 离线断言：落在种子 `t` 上的周期数 **3 → 0**。

⚠️ 最少 2 轮（ms8 的 RTT 样本要两个批起点帧做差）。⚠️ 起步轮**帧判据失效**（长间隔 = RTT，
会被判成"丢帧"）⇒ 这一段强制走 ACK 通路。

#### （2）但根因是**一个反馈级联**，不是"第一轮"

把逐周期表按值分类就看到了：第 6 期的 `boundary_gaps_ms` 记的是 **`57;57`**，而那一期的 `t` = 62。
**57 正是第 5 期（`t=57`）的批内间隔** —— 它被判成了"批起点"。链条是：

```
fl.cur_batch 在【发送时刻】改
   ⇒ 此刻还在途的上一批尾帧被贴上【新批号】
   ⇒ 扫描时取 t_of_batch[新批号] = 【新 t】，拿旧批的批内间隔(57)去比新 t(62)
   ⇒ |57−62| > tol ⇒ 判成批起点 ⇒ 【多发一条命令】
   ⇒ 周期腰斩 ⇒ 主机触发周期中位数塌一半 ⇒ ℹ 解缠参照(rtt_ref)塌
   ⇒ ±80ms 一致性闸的锚点失效、腰斩样本反被放行 ⇒ t 继续掉 ⇒ 自锁发散
```

⚠️ 关键在最后一环：**解缠参照当时取自 `median(host_hist)`（触发周期）**。触发周期是**环路健康的
产物**——环路一被带偏它就塌，锚点塌了闸门就失效，于是越错越信。**这才是自毁的引擎。**

#### （3）两处修复（都必要，2×2 对照已证）

| 修复 | 内容 |
|---|---|
| ① **RTT 来源**（根治） | 样本改取 **ACK 标记的批首帧**（收 ACK 时记下帧下标 `ack_idx`），**刻意绕开间隙分类**；解缠参照改用 **逐条命令的 `send → ACK` 往返**（`rtt_send`）——它无 256 ms 分支歧义，且**不随环路健康度变化**（环路被带偏时周期腰斩，但每条命令自己的往返还是 RTT）。腰斩样本在 ±80 ms 闸前被拒 ⇒ 发散环断在这里。 |
| ② **打标时机**（防复发） | `fl.cur_batch` 改到**收到该批 ACK 时**才更新（`make_ack_cb` 里 `fl.cur_batch = rec["batch"]`）。MCU 收到第 k 条命令的那一刻才（重新）开始第 k 批的发射，"这条 ACK 之后的帧"才属于第 k 批。发送时刻只**编号**，不改打标。 |

⚠️ 实现细节（不写就会静默失效）：**`ack_idx` 只消费已经落盘的帧下标**。收 ACK 那一刻该批的 F1
**还没到**（线上 ACK 在前），`ms8_of(ii)` 返回 `None`；若照样推进游标，这个样本就**永久丢掉**
（因为每次触发都发生在 ACK 之后、F1 之前）⇒ RTT 估计永远空转、`t` 一直是种子值。所以游标只推进
到**第一个未落盘**的下标为止。

新增诊断：`early_trig` 计数"触发到触发**明显早于 RTT/2**"的次数，并打印警告 —— 它是判据退化的
信号灯，出现就说明该换 `--trigger ack` 了。

#### （4）离线对照：`test_tagging_race()`（事件级仿真，2×2）

仿真忠实建模：命令走 `D` 才到单片机（所以上一批尾帧**晚于**发送时刻到达）、F1 在 `S+RTT` 到达、
ACK 在线上排在本批 F1 之前、新 PULL 抢占、**攒包**（ACK 与 F1 常进同一批 USB 突发一起释放 ——
这正是"触发后结算"能吃掉重复触发的原因）、ms8 在**整数 tick** 上取（浮点取整会造 ±1 ms 伪抖动，
而 `tol=0.75` 会被这点伪抖动全部判成批起点，踩过）。

RTT = 225 ms、N = 4、种子 `t` = 83、真值 `t` = 57、26 个周期：

| 变体（打标时机 / RTT 来源） | 稳态 `t` | 早触发 | 判读 |
|---|---|---|---|
| 发送时刻 / 间隙分类（**旧实现**） | `{4,5,7,12}` | **22/26** | ✗ 发散（`t` 从 83 塌到 4） |
| 发送时刻 / ACK 标记 | `{57}` | 23/26 | △ `t` 对了，但环路**仍在误发命令** |
| 收到 ACK / 间隙分类 | `{50,53,57}` | 0/26 | △ 环路稳了，但 `t` 有偏（参照口径不对） |
| 收到 ACK / ACK 标记（**现实现**） | `{57}` | **0/26** | ✓ 干净（周期 224~228 ms，±2 是 tick 量化） |

⇒ **两处都得改**：只换 RTT 来源能阻止雪崩，但打标竞态仍会误发命令；只改打标则 `t` 仍会被带偏。
（`t` 会因 RTT 真的漂移而变 —— 实测 RTT 有 **150 / 225 / 300** 三值，彼此差正好 75 ms ——
那时发送时刻打标就在过渡期误判，所以打标必须等 ACK。）

回归：contract 253/253、facade 46/46；新工具命令白名单仍只有 `PING` / `RATE PULL` / `RATE OFF`。

⚠️ 上面那条"两处都得改"在**真机上跑满 120 s 后才暴露还有第三处**：解缠的**判据口径**。
见下一节 §14.10 —— 它同一晚被真机打出来（RTT 换档 300→150），修复后 `fix4_n4` 满时长存活。


### 14.10 RTT 换档：75 ms **物理格点**解缠 + 合理性闸（2026-10-13 真机暴露 → 修复 → 复验）

#### (1) 真机暴露：RTT 由 300 换到 150，环路是对的、`t` 冻住了

`fix3_n4`（`--frames 4 --bootstrap 2 --duration 120`）前 100 个周期教科书级干净（周期 300/375、
`t`=76、`n`=4、批起点间隔恒 72、13.3 Hz、`early_trig`=0）。**第 101 周期链路停顿 547 ms 之后**，
周期永久落到 **150 ms**：`n`=2、`t`∈{76,102}、批起点间隔 74/48。全部自洽：

```
150 = 76 + 74 = 102 + 48     N_eff = floor(150/76)+1 = 2
```

⇒ **这不是发散，是 RTT 真的换了档**（150 与 300 同在一个 75 ms 等差数列上），环路自锁依然正确。
但三个坏消息：

* **`t` 没跟手**（应变成 `floor(150/4)+1 = 38`），冻在 76/102；
* **`early_trig` 报 146 次**（阈值取 `median(send→ACK)`=300 的一半），绝大多数是**误报**；
* **204 个 RTT 样本被闸丢弃**，而 `T=150` 时 `n` 掉到 2 ⇒ **命令频率从 3.3 翻到 4.65 Hz**。
  速率没掉（速率 ≈ `N/周期` ≈ `1/t`，与 RTT 无关），但**下行负载翻倍**，离"灌爆蓝牙透传模块"
  那道不可自愈的红线更近了。

#### (2) 根因：**"离参照最近"的解缠 + 静态 ±80 闸**，在换档时两个分支全被拒

ms8 只有 8 位，周期/RTT 必过 256 折回。旧法：

```python
obs = min((raw, raw-256, raw+256), key=lambda v: abs(v - ref))   # ref = median(send→ACK) = 300
```

真值 **150** 时 `raw = 150`，候选 `{150, −106, 406}`：`|150−300| = 150` vs `|406−300| = 106`
⇒ **选中 406**。再被 `|406−300| = 106 > 80` 的一致性闸拒掉。于是**正确分支(150)与错误分支(406)
双双出局** ⇒ `rtt_hist` 永不更新 ⇒ `t` 冻在旧档。8 个漏网样本使 `median(rtt_hist)` 一度到 406，
`t` 于是出现 `floor(406/4)+1 = 102`。

#### (3) 修复：`unwrap_rtt` —— 按 **75 ms 格点**判，不按"离参照最近"

关键观察：**真机 RTT 只取 150/225/300/375（= 75×2/3/4/5），全是 75 的整数倍**；而 ±256 的错分支
恰好偏离格点

```
256 mod 75 = 31 ms
```

⇒ **"哪个候选落在 75 的格点上"就是无歧义的定值判据**，不依赖任何参照：

| 真值 | `raw = v & 0xFF` | 候选 | 新法(格点) | 旧法(离 300 最近) |
|---|---|---|---|---|
| 150 | 150 | {150, −106, 406} | **150** ✓ 放行 | 406 ✗ 被闸拒 |
| 225 | 225 | {225, −31, 481} | **225** ✓ | 225 ✓ |
| 300 | 44 | {44, −212, 300} | **300** ✓ | 300 ✓ |
| 375 | 119 | {119, −137, 375} | **375** ✓ | 375 ✓ |
| 450 | 194 | {194, −62, 450} | **450** ✓ 放行 | 194 ✗ 被闸拒 |

闸也随之放宽为**合理性**：`60..900 ms` 且（在格点上 **或** 离参照 ≤80）。
`unwrap_gap`(帧间隙) 保持"离 `t` 最近" —— 在 **① 帧判据 ② `t ≤ 127`** 两个前提下，帧间差**恒 < 256**
（批内 = `t`，批起点 = `RTT mod t` < `t`），压根不需要解缠；这条也顺手修掉了逐帧 CSV 的 `gap_mcu_ms`：
旧代码拿**主机间隔**当参照去挑 ±256 分支，攒包时主机间隔虚高到 ~200–300 ⇒ 把 76 ms 的批内间隔写成
**332 ms 的假"长间隔"**（实测 17 个）。现在直取 `raw & 0xFF`。
> ⚠️ 前提 ② 只在 `--trigger frame` 下才被保证：默认走标记帧判据时不看间隙，`N=1/2` 允许 `t > 127`
> （见 （4）节）。若在帧判据下跑 `t > 127`，"丢一帧"的 `2t` 折回会被读成批起点 —— 主循环会告警。

**防护职责的转移**（这点要说明白）：环路崩塌的防护**不再靠这道闸**，而是靠 §14.9 的**打标时机**
（收到该批 ACK 才打标）。RTT 样本来源是 ACK 标记帧，与间隙分类解耦 ⇒ 闸可以放心放宽。
新增 `off_lattice` 计数（落在格点外的样本）= "75 ms 量化模型还成不成立"的体检指标。

#### (4) 复验 `fix4_n4`（同一命令，SURVIVED **120.2 s** —— 本轮硬件测试首次满时长存活）

| 指标 | `fix3_n4`（85.6 s 断连） | `fix4_n4`（120.2 s 存活） |

### 14.12 删除「超时补发」：事件驱动必须纯净（2026-10-13，用户指出）

**用户指正**：「兜底补发」不属于本方案。方案本身就是要让通信与传输状况**动态调整** ——

### 14.13 离线复现平台：模拟器 `mouse_sim` 的 `RATE` 族

真机链路是**稀缺资源** —— 模块会随机停转发（须物理断电），一轮压测动辄几分钟。所以"事件触发式拉取"的每一次判据改动，都必须先在**离线**上验证。为此模拟器 `host/host/sim/mouse_sim.py` 与固件**同构**地实现了整个 `RATE` 族：

### 14.14 判据的病灶：为什么"推算"批起点不够

批起点（本周期第 1 帧）是事件驱动式拉取的**唯一**触发信号。但它原先只能**推算**：`classify_gap` 拿"与前一帧的 ms8 间隔"去猜 —— 批内间隔恒 = `t`（固件倒计时，实测 **535/535 σ=0**），跨批间隔 `bd = RTT mod t = t − (N − RTT mod N)`，**恒比 t 短 1..N ms**。

**四种误判来路**：

| # | 来路 | 后果 |
|---|---|---|
| ① | **t 归档错**：动态 t 逐周期变，一批的批内间隔必须与**该批发射时**的 `t` 比 | 用当前 t 比旧批 ⇒ `\|76−75\|>tol` 整批误判 |
| ② | **ms8 ±256 折回**：ms8 只有 8 位，间隔 > 256 ms 会折回 | 长周期被看成短间隔 |
| ③ | **RTT 换档**：换档瞬间 t 与新周期不匹配 | 过渡期误判 |
| ④ | **1 ms 刀锋**：边界间隔只比 `t` 短 1 ms | 实例 `RTT=375/N=4 ⇒ t=94、bd=93` |

外加一个**对偶死角**：`RTT ≡ 0 (mod t)` ⇒ `bd` 恰好 = `t` ⇒ 判据**看不到边界** ⇒ 漏触发 / 停摆（`t=75`、`RTT=300` 即踩中：`bd=t=75`）。

**后果链**：任何一次误判成"批起点" ⇒ **提前触发** ⇒ 多发命令 ⇒ 抢占在途批 ⇒ 周期被压短 ⇒ 实际速率 `= N/周期 > N/RTT` ⇒ **顶过链路容量** ⇒ 模块缓冲灌满即停转发（且**不自愈**）。这正是早期几轮"莫名其妙早死"的形态。

⚠️ 现状里 `early_trig` 只是**事后计数**（`hp < 0.5·RTT_est`），**不阻止发送**；真正拦住的只有 `--min-period-ms`（默认 30 ms）这道硬闸。⇒ 需要一个**事实型**信号。


### 14.15 `LINK_FLAG_PULLF1`：把批起点判据从「推算」改成「读事实」

**载体为什么是复用而非新开位**：统一帧 flags 字节 8 位**已满**（FREEMODE/SLEEP/EMERG/**0x08**/DUMPING/MOTOR_OFF/ESTOP_LOCK/EVQ）。`0x08` 原是 `SCOPING`，而那套示波器机制 v2.0 已删除 ⇒ 该位**自 v2.0 起恒 0、全树无置位点、无消费者**。故**改名复用**：`LINK_FLAG_PULLF1`。

**固件三处改点**（全在 PULL 分支内；FIX 档与比赛档恒 0）：

1. `link.h`：定义 `LINK_FLAG_PULLF1 0x08`、重写 flags 位说明块、`LINK_FW_VER` 218→**219**、加 v2.6.1 历史条目；
2. `link.c`：新增 `static u8 linkPullF1`；`link_SendUnified()` 在 `pl[LINK_U_FLAGS] = link_Flags();` **之后** OR 置位并**立刻清零**；`link_RateService()` 的 PULL 分支取 `firstFrame`；`link_RateStop()` 清零。

```c
/* link_SendUnified(): 两档共用 ⇒ OR 必须门控, 否则比赛档 hex 会变 */
pl[LINK_U_FLAGS] = link_Flags();
#ifdef MOUSE_REMOTE
    if (linkPullF1) { pl[LINK_U_FLAGS] |= LINK_FLAG_PULLF1; linkPullF1 = 0u; }
#endif

/* link_RateService() PULL 分支: 必须在倒计时之前取 firstFrame */
firstFrame = (linkPullTimer == 0u) ? 1u : 0u;
if (linkPullTimer > 0u) { linkPullTimer--; if (linkPullTimer > 0u) return; }
linkPullF1 = firstFrame;
link_SendUnified();
linkPullF1 = 0u;
```

判据原理：`link_PullSet()` 把 `linkPullTimer` 置 0（下一 tick 就发），而**每发一帧**又把它重置为 `linkPullPeriod(≥1)` ⇒ "带 `timer==0` 进入 PULL 分支"**当且仅当本批第一帧**（新 PULL 抢占时 timer 同样置 0 —— 那正是**新批首帧**，也正是要标的）。

**两条铁律（不是可选优化）**：

- **必须 `#ifdef MOUSE_REMOTE` 包住 OR**：`link_SendUnified` 两档共用，裸 OR 会改比赛档产物 ⇒ hex 基线变；
- **不放进 `link_Flags()`**：那个函数两档共用且是**只读**状态镜像，放进去会引入副作用（每帧都被消费），破坏"只标一帧"的语义。

⚠️ 必须在**倒计时之前**取 `firstFrame`：批内末帧的 `timer` 恰好减到 0，事后再看会把**末帧**误标成首帧 ⇒ 上位机提前触发 —— 正是要消灭的缺陷。

**上位机改动**：
- `codec.py`：`FLAG_SCOPING`→`FLAG_PULLF1`，解码字段 `scoping`→`pullf1`（`FLAG_NAMES`、`telemetry._FLAG_KEYS` 同步）；
- `mouse_sim.py`：`pull_f1` 状态 + `_flags` 里 OR，与固件同序；
- `link_pull_pace.py`：`FrameLog` 采集 `flags`（供探针）；逐帧 `_frames.csv` 增 `flags` 列；
- `link_pull_evt.py`：**标记帧为主 + ACK 兜底 + 间隙仅诊断**；`--trigger mark/ack/frame` 分别强制单一通路。

**`--trigger auto` 的三信号优先级**：

| 信号 | 触发条件 | 性质 |
|---|---|---|
| ★ **标记帧** | `flags & 0x08` | **读事实**（固件亲口），与 `t`/RTT/ms8 全都无关 |
| **ACK 兜底** | 标记帧在 `--mark-grace-ms`（默认 20 ms）内不到 | 比 F1 早 ~5–6 ms，无歧义；代价 = 依赖 ACK 不丢 |
| **间隙**（frame） | 仅 `--trigger frame` | 旧推算判据，保留为**对照/探针** |

- **限时吸收窗**：用非标记通路触发后开一个 `clamp(3×grace, 70 ms, 120 ms)` 的窗，窗内到达的标记帧**只记账不触发**。⚠️ 上限**必须 < 最小观测 RTT(150 ms)** —— 否则会吃掉**下一批**的正常标记（限时，而非布尔标志）。
- **自动降级**：PONG 的 `fw < 219` ⇒ 退回 ACK 通路，行为与 v2.6 **逐字相同**（**换固件不需要换命令**）；若板上自称 fw≥219 却连续 ≥5 个周期不见标记帧，也自动撤回（避免每周期白等 grace）。

**版本与兼容**：

## 16. 容量定位：~150 ms 转发量子与 10 Hz 档（2026-10-15 复验，fw 221）

本节推翻 §11-15 的两个乐观旧结论，给出 v2.9 批式拉取(`mc.stream.pace()`)的依据。

### 16.1 转发量子的发现（结构性问题，不是抖动）

`pace_v28paceD_frames.csv`（`RATE PULL 3 75`，MCU 侧 ms8 严格 75 ms 一拍）原始列对比：

| 侧 | 观测 |
|---|---|
| MCU（帧内 ms8 差分） | {75:1851, 74:196, 76:225} —— 固件节拍完美 |
| PC（`t_s` 差分） | **{0:267}** —— 267 对帧在 <1 ms 内**成对到达**，批与批才隔 ~155 ms |

唯一自洽解释：**蓝牙模块把 75 ms 节奏的帧两两攒批，按 ~150 ms 量子转发**给 USB。
由此：

- **链路真实容量 = 2 帧/150 ms ≈ 13.3 Hz**。旧结论"容量 24~30 Hz"偏乐观 ——
  它测的是平滑均值，没识破这个量子；
- paceB 的"293 ms"、paceD 的"331 ms"边界间隔，全部是 ~150 ms 的整数倍附近
  （不是命令抢占，也不是随机抖动）；
- ⚠️ **分析陷阱**：ms8 是 8 位，自己拿它做差分会把 >255 ms 的间隔**折叠**
  （293 ms 折成 37 ms）⇒ 必须用工具已算好的 `gap_mcu_ms` 列。

### 16.2 存活矩阵（2026-10-14 夜 ~15 同一模块，断连判定 = 连续 3 s 无帧）

| 组 | 命令 Hz | 帧 Hz | 存活 | 交付率 |
|---|---|---|---|---|
| `RATE FIX 12` ×2 | 0 | 12 | **300 s ✓** / 143 s ✗ | — |
| evt（动态 t） | 3.7 | 24.6 | 15.5 s ✗ | — |
| `PULL 4 37`（paceB） | 6.7 | 26.3 | 95.2 s ✗ | 93.9% |
| `RATE FIX 26` | 0 | 26 | 113.3 s ✗ | — |
| `PULL 3 75`（paceD） | 4.4 | 13.3 | 176.3 s ✗ | 97.3% |
| **`PULL 3 100`（paceE）** | **3.3** | **10** | **300 s ✓** / 240.9 s ✗ | **99.9% / 98.6%** |

按容量分档聚合：≤13.3 Hz 四样本均值 **245.9 s**、2/4 活满；>20 Hz 三样本均值
**74.7 s**、0/3 活满 ⇒ 低帧率显著更优（均值差 3.3 倍），统计上成立。

### 16.3 但"稳定"买不到：断连随机 + 两个先行指标

- **任何档位都有约一半概率在 300 s 内随机死亡**（模块侧故障）。§13.5"路线 A 更稳"
  的前提（RTT 稳定在 300 ms）不成立；paceB 证伪"均匀就稳"；fix26 证伪"命令通路是
  主因"——**负载本身才是分档因素，但同档内是随机的**。
- **断连无前兆**：paceD 的 293 ms 边界从 t=1.9 s 就存在、全程均匀分布、断连前
  不密集化；主机侧 >150 ms 间隔同样无趋势 ⇒ 突发死亡，不可预测、不可预警。
- **RTT 是先行指标**：paceE 活满时 RTT 收敛 57 ms；paceE2（模块已连续工作
  ~10 min）RTT 137 ms、240.9 s 死。疑似模块热衰疡，待验证。
- **自愈假说已证伪**（见 §6）：必须物理断电；`rst=POR` 是判断"是否真复位过"的依据。

### 16.4 v2.9 决策 / v2.10 整合

`PULL 3 100`（基频 3.33 Hz + 每批 3 帧 = **10 Hz**，容量 75%）定为默认工作档：
传输量 2.5 倍（停等式 ~4 Hz 的 2.5 倍）、交付率 98.6~99.9%、存活 240~300 s。
已整合为 `mc.stream.pace()`（v2.10 起统一拉取器 `TelemetryPuller`，
`host/host/api/stream.py`；v2.9 时为独立的 `PacePull` 类），并带
**断连自动检测**（连续 3 s 无帧 ⇒ `Event.ERROR(kind="link_lost")` 提示物理断电
复位）—— 因为"保证不断"做不到，能买的只有"断连后多快恢复"。

**下一步待办**：① 模块热衰疡假说（长时工作 RTT 漂移）；② 换 USB 2.0 后置口
排除环境衰疡；③ 13.3 Hz 顶格档补样本（若接受偶发崩+快恢复，可再多 33% 传输量）。
