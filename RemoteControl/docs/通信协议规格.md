> 适用版本：**API 2.14.0**　|　固件：新基线 `code_competition` 远程档 `PROTO 10 / FW 314`（迷宫 16）、

> 面向"怎么用上位机"请看 [`api_reference.md`](api_reference.md)，面向"怎么把 CLI 跑起来"请看 [`../host/README.md`](../host/README.md)。

## 0. 物理层与双档

| 项 | 值 |
|---|---|
| 物理层 | UART **115200-8-N-1**，经蓝牙 SPP 透传（或直连 / TCP 接模拟器） |
| 编码 | 下行命令与上行文本行均为 **ASCII**；上行二进制帧为原始字节 |
| 共存 | printf 文本只产出 `0x09-0x7E` + CR/LF，**永不产出 `0xAA`** ⇒ 见到 `0xAA` 即尝试按帧解析，CRC 失败则回退当文本（自恢复） |

每个固件工程都是**单工程双 Target**，由宏 `MOUSE_REMOTE` 区分（新基线里它来自 Keil
Target 的 Define；课程固件写在 `USER/main.h`）：

| 固件工程 | 档 | 开关 | 协议指纹 | 说明 |
|---|---|---|---|---|
| **`code_competition`（新基线）** | 远程档 | Target_Remote 的 `MOUSE_REMOTE,EN_USART1_RX` | `PROTO 10 · FW 314 · 迷宫 16` | 参数表 41、TX 环 1024 B、远程发车/收车/中止、`RATE` 族、`PULLF1`、4 个 LED 状态、**建图增量通道** |
| 同上 | 比赛档 | Target 1（**无** `MOUSE_REMOTE`） | —（不跑链路层） | 源码零改动，红线 hex `68ad6be2…` |
| **`code_stm32f1_mouse`（课程固件）** | 远程档 | `#define MOUSE_REMOTE 1` | `PROTO 8 · FW 222 · 迷宫 7` | 历史参考；参数表 41、TX 环 1024 B |
| 同上 | 按键比赛档 | 什么都不定义 | `PROTO 5 · FW 216` | 参数表 24、TX 环 256 B |

> **课程固件**两档共用同一份 `link.c`，因此 `LINK_PROTO_VER` / `LINK_FW_VER` / `LINK_P_NUM`
> 三个宏必须用 `#ifdef MOUSE_REMOTE` 门控，否则比赛档 hex 会变。**新基线**（`code_competition`）
> 的 `REMOTE/*.c/*.h` 则是**整文件** `#ifdef MOUSE_REMOTE` 门控 —— 比赛档把这些文件编译成
> **空翻译单元**，`#else` 分支里的旧值（`PROTO 5 · FW 216 · 24`）在固件中**永不可达**，
> 仅作为上位机 `contract_test.py` 文本解析的"比赛档契约"锚点（host 侧仍然有效）。
> 判"没动比赛代码"永远用 **hex 哈希比对**（课程固件 `f0a5f863…`；新基线 `68ad6be2…`），
> 不要用 `.axf`（含 DWARF 调试段）。
> ⚠️ Keil 的 `-b -t "<target>"` 会把工程文件列表里的**所有 .c 都编一遍**，所以新基线
> `REMOTE/*.c` 必须**整文件**门控（移植背景见 [`已落地方案与决策记录.md`](已落地方案与决策记录.md) §1）。

连接后的**第一条命令应当是 `PING`**，核对 `PONG` 指纹再往下走。

## 1. 下行命令（PC → 设备，文本行）

### 1.1 行格式

```
<CMD> [args] [#<seq>] *<CRC16 HEX4>\r\n
```

| 字段 | 说明 |
|---|---|
| `<CMD> [args]` | 命令关键字与参数，空格分隔，全大写 |
| `#<seq>` | **可选**序号（0..65535 十进制）。用于**幂等重放**：固件记下 (seq, crc)，若下一条完全相同则**不执行**、直接重放上次状态 |
| `*<CRC16>` | 星号后 **4 位十六进制大写**（可为小写，固件都认）。**CRC 覆盖 `*` 之前的全部字节**（`CMD [args] [#seq]`，不含 `*` 与 CRLF） |
| 行尾 | `\r\n`（`\n` 亦可） |

CRC 算法：**CRC16/MODBUS**，多项式 `0xA001`，初值 `0xFFFF`。
校验向量：`crc16(b"123456789") == 0x4B37`（固件 `link_Crc16` 与上位机 `codec.crc16_modbus` 逐位一致）。

示例：

```
PING #12*A1B2\r\n
SETQ TRACKL 3486515 #13*0F3C\r\n
```

### 1.2 可靠性四层

| 层 | 机制 | 失败表现 |
|---|---|---|
| **L1** | 命令行带 CRC16，固件校验失败回 `ACK -1 ERR_CRC` | `ERR_NOCRC`（无星号）/ `ERR_CRC` |
| **L2** | 固件执行后回 `ACK <seq> <OK\|ERR_xxx>` | 状态串非 OK |
| **L3** | 上位机超时未收 ACK 则**字节不变**重发（最多 5 次，`TIMEOUT_S=2.5`） | `TIMEOUT` |
| **L4** | 写参数后由上层 `GET` 回读校验 | `READBACK_MISMATCH` |

### 1.3 两条不能违反的纪律

1. **严格停等**：固件**每 1 ms tick 只消费一行命令**（`link.c`：`if (USART_RX_STA & 0x80)`；
   bit7 未清时 `usart.c` 把后续字节**直接丢弃**）。⇒ 同一时刻只允许 1 条命令在飞。
   实测背靠背 `TELEM` 回收率：N=1→100%、2→50%、3→33%、4→25%、8→12%；间隔 300 ms 逐条发→100%。
2. **`TELEM` 绕开幂等簿记**：`TELEM` 在 `link_HandleLine` 里**提前拦截**，既不查也不写
   `linkLastSeq/linkLastCrc`。否则持续拉取会把"待重放的真实命令"冲掉（MOVE 会重起步、CAL 会重采）。

### 1.5 速率族：`RATE`（v2.6 起为远程档常态）

编译门控：`MOUSE_REMOTE`（`link.h`）。按键比赛档不含本段 ⇒ 比赛产物逐字节不变。
**统一帧长度未变**（49 B 载荷 / 57 B 帧）：v2.6-exp 曾在帧尾追加 2 B 目标帧率供 AIMD 反馈
读取，AIMD 被"事件触发式拉取"取代后该字段零消费者，已连同 AIMD 命令一并删除。

| 命令 | 参数 | 语义 |
|---|---|---|
| `RATE OFF` | — | 关闭自时钟（回到"仅 `TELEM` 拉取"） |
| `RATE FIX <hz>` | 1..30 | **固定节拍压测**：恒定 F 持续发帧，不看门狗、不降速、不停发 |
| `RATE PULL <n> <t_ms>` | n=1..16, t=1..5000 | **批量节拍（PC 主导）**：按 `t_ms` 连发 `n` 帧后静默，等新 PULL；新 PULL 立即打断重排 |

- 固件侧实现：`link_RateService` —— 每 1 ms 累加 `F(Q8.8)`，满 `LINK_RATE_FRAME_UNIT = 256000`
  就发一帧（1000 ms 恰好 F 帧）。`RATE OFF` 调 `link_RateStop()` 复位全部节拍状态。
- `RATE PULL` 置位后**立即发第一帧**（`linkPullTimer = 0`），之后每 `t_ms` 一帧，共 `n` 帧；
  期间收到**新的 PULL** 立即打断重排，旧批次剩余帧作废 —— 这是**抢占，不是丢帧**，
  **不计入** `LINK_U_DROP`。事件触发式拉取（周期 ≡ RTT）就架在这条语义上。
- `RATE` 与 `TELEM` 一样在 `link_HandleLine` 里**提前拦截**，不查不写幂等重放簿记
  （否则周期性下发会冲掉待重放的真实命令，见 §1.3）。
- **没有看门狗/静默停发**：那属于已删除的 AIMD 自适应。现在两种模式都不会无界发包 ——
  `PULL` 发完 `n` 帧就静默等下一条命令，`FIX` 只在压测时用且由操作者显式 `RATE OFF` 收尾。
- 模式互斥：`RATE FIX` 清 PULL 批次；`RATE PULL` 退出固定节拍。
- 上位机侧登记为 `rate.off` / `rate.fix` / `rate.pull`（均 `no_retry`）；工具
  `host/link_mtbf_test.py`（`RATE FIX` 压测）、`host/link_pull_pace.py`、
  `host/link_pull_evt.py`（后两者基于 `RATE PULL`）。

### 1.6 统一帧内的诊断字段：`LINK_U_DROP`（offset 44）

固件每帧上报 `(u8)linkDrop` —— **自上次上电/软复位以来，因 TX 环空间不足而整帧丢弃**
的累计计数低 8 位。上位机默认不解码它；`host/link_pull_evt.py` 在结束时打印
**MCU 丢帧字节 末值/增量**，用来判定[丢帧发生在单片机侧还是链路中段](#)。

- `mcu_drop` 不涨、而实收 < 目标 ⇒ 帧已成功交给模块，**丢失在链路中段**（模块 / 蓝牙 / CH340 缓冲）。
- `mcu_drop` 涨速 ≈ (目标 − 实收) ⇒ 丢在单片机 TX 环（模块把 UART 顶住，喂不进）。

### 1.7 发车标记灯（v2.8，仅远程档）

**这不是协议内容，而是 `MAZE RUN` 的副作用**——它不改任何字节、不新增字段、不新增命令，
但录像/外部设备能看见它，故在此登记。

| 项 | 值 |
|---|---|
| 触发 | 远程档 `MAZE RUN [BLIND\|RACE]` **被接受**的那一刻（回 `ERR_BUSY` / `ERR_ESTOP` 时不触发） |
| 动作 | 直接写引脚点亮 **LED1–LED4**（低电平点亮 ⇒ 4 个灯全亮） |
| 时长 | `LINK_LAUNCH_MARK_MS` = **300 ms**（`link.h`），窗口内 `LINK_Tick` 每 1 ms 重写引脚保持 |
| 释放后 | 引脚交还常规逻辑 —— 基准灯（LED4）与迷宫/状态灯行为**一字未改** |

- **动机**：录像时需要一个无歧义的发车时刻标定（对轴）。LED 由暗变全亮的那一帧即发车帧。
- **为什么不走 `LED_On(0)`**：先 `ARM` 再发车时 `ledBeaconLock` 已置位，`LED_On` 会直接返回；
  标记改为直接写引脚，任何情况下都亮。
- ⚠️ 窗口内 4 灯被强制点亮 ⇒ 若同时 `ARM`，外部看到的 1 Hz 方波会出现 **300 ms 的缺口**；
  窗口一过自动恢复（`linkTimeLed` 被置 `0xFF`，令基准灯下一拍重写）。
- 按键比赛档**不含**本段（`#ifdef MOUSE_REMOTE`）⇒ 比赛产物逐字节不变。

## 2. 上行应答与事件（设备 → PC，文本行）

### 2.1 ACK

```
ACK <seq> <OK|ERR_xxx> [附加字段…]
```

- 成功判定用**前缀** `OK`（状态串可带附加字段，如 `OK <upMs>` / `OK <a> <b> <c>`），不是全等。
- `seq` 与下行命令的 `#seq` 对应；**CRC 失败时为 `ACK -1 ERR_CRC`**。

### 2.2 参数回读行

```
P <id> <q16.16>
```

每个参数一行。`GET ALL` 会在远程档回 41 行。

### 2.3 上行事件行（仅两条）

```
STOPPED <REASON> #<n>
ESTOP TRIP #<n>
```

| REASON | 含义 |
|---|---|
| `TIME` | 时间护栏到 |
| `IR` | 近墙保护（红外护栏） |
| `ESTOP` | 急停 |
| `USER` | `STOP` 命令 |
| `END` | 任务正常跑完（固定脉冲直线 / 定长转） |

### 2.4 序号 `#n` 的语义（**关键**）

**帧与事件行共用同一个 1 字节计数器**（固件 `linkSeq`）。因此：

- 上位机看到的是一串"帧 / 事件交织"的统一编号；
- 相邻两条上行消息的 `step = (n - prev) & 0xFF`：`step >= 2` ⇒ 中间少了 `step-1` 条
  ⇒ 置"事件流不完整"标记（`up_gaps / up_lost`）；
- **"帧号跳 1"是正常的，不是丢帧** —— 这正是早期"逐帧比较"写法会误判的原因。
- 顺序即协议：解析器必须**按到达顺序**处理（见 §4.3）。

## 3. 二进制帧（设备 → PC）

### 3.1 帧结构

```
AA 55 | LEN(2, LE) | TYPE(1) | SEQ(1) | PAYLOAD(LEN) | CRC16-MODBUS(2, LE)
```

| 字段 | 字节 | 说明 |
|---|---|---|
| 同步头 | 2 | `0xAA 0x55` |
| LEN | 2 | **载荷**长度（小端），不含头尾 |
| TYPE | 1 | 帧类型 |
| SEQ | 1 | 与事件行共用的 1 字节序号 |
| PAYLOAD | LEN | 见下 |
| CRC16 | 2 | MODBUS，覆盖 **TYPE/SEQ/PAYLOAD**（小端） |

帧开销固定 **8 B**（同步 2 + LEN 2 + TYPE 1 + SEQ 1 + CRC 2）。

| TYPE | 名称 | 载荷长 | 帧长 | 用途 |
|---|---|---|---|---|
| `0x0A` | `UNIFIED` | **30 B** | **38 B** | 唯一周期遥测帧（v9 起；v10 只改字段偏移，长度不变） |
| `0x07` | `MAP` | 4+2n² B | 变长 | 墙图整块（静态数据，按需拉取；n=7 时 98 B） |

理论上限：`11520 B/s ÷ 38 B ≈ 303 Hz`（v9 帧重排前为 `÷ 57 B ≈ 202 Hz`）。**实际**受蓝牙转发延迟主导（RTT 150~530 ms），
可达帧率 = `1/RTT ≈ 4.4~6.5 Hz`，提波特率无效。

### 3.2 PONG（`PING` 的应答）

```
PONG <proto> <fw> <mazetype> <txbuf> <rst>
```

**两代固件并存**（2026-10-16 起）：`code_competition/`（**新基线**，比赛固件）与
`code_stm32f1_mouse/`（课程固件，历史参考）。两者**协议完全相同**，靠 `fw` 号区分；
上位机的"本次在验哪代"由 `host/host/fwprofile.py` 统一解析（环境变量 `RC_FW_PROFILE`，
默认 `competition`）。

| 字段 | 新基线 `code_competition` | 课程固件 `code_stm32f1_mouse` | 说明 |
|---|---|---|---|
| `proto` | **9** | 8 | `LINK_PROTO_VER`（v9 帧重排起新基线为 9，课程固件仍 8） |
| `fw` | **311** | 222 | `LINK_FW_VER` —— **上位机据此判档** |
| `mazetype` | **16** | 7 | 迷宫尺寸 n（MAP 帧随之 520 B / 104 B） |
| `txbuf` | 1024 | 1024 | TX 环大小（字节） |
| `rst` | `POR`/`SW`/`IWDG`/`PIN` | 同 | **上次复位原因**（`SW` = 软复位成功判据） |

> 旧版本表里的"比赛档 `5/216/256`"指**课程固件**的非远程分支；新基线的比赛档不跑链路层
> （`link.c` 被 `#ifdef MOUSE_REMOTE` 整文件门控成空 TU），没有 `PONG`。

### 3.3 统一帧载荷字段表（30 B）

> **v9（2026-10-20）**：载荷 49 → **30 B**。原则是"帧里只留每帧会变的动态量"——
> 静态规划结果（`fastwayCount`/`fastwayCount90`）、本地健康计数（`dropCnt`）、
> 以及可由其他位推出的量（`frontNear`）全部出帧，改由事件行 / `PING` 文本低频上报。
> 逐条理由与旧→新偏移映射见 [`已落地方案与决策记录.md`](已落地方案与决策记录.md) §5。
>
> **v10（2026-10-23）**：长度仍是 **30 B**，但 **偏移 6..22 整体前移 5 B** ——
> `irMm[4]` 由 u16 压成 u8（省 4）、`battMv` 由 u16 压成 `round(mV/50)` 的 u8（省 1）、
> `encAngle` 整项删除（省 2），腾出的 **7 B 全部给建图增量通道**（偏移 23 头 + 24..29 三条 2 B 条目）。
> 帧长刻意不变：本链路实测 RTT 恒 300–310 ms 且**全部发生在 PC 侧 CH340**，与帧长无关，
> 缩短帧换不到任何速率，却要拆掉全部 `len == 30` 断言。

| 偏移 | 字段 | 类型 | 字节 | 说明 |
|---|---|---|---|---|

### 3.4 位打包明细

```
偏移16 (状态A):  bit0-1 dir(0=UP 1=RIGHT 2=DOWN 3=LEFT)
                 bit2-4 mazeTask(0=WAIT 1=START 2=SEARCH 3=SPURT 4=SPURT45 5=SPURT90 6=END)
                 bit5   objectGoToFlag(1=正在按坐标回调)     bit6-7 预留
偏移17 (状态B0): bit0-6 motionTask(0..107, 见 core.h)      bit7 预留
偏移18 (状态B1): bit0 spurtFlag  bit1 goOrBack
                 bit2-5 led1..led4(1=亮, v9.1)            bit6-7 预留
偏移19 (状态C):  bit0 wallLeft  bit1 wallFront  bit2 wallRight
                 bit3 frontFar(1=远墙档 / 0=近墙档)  bit4 frontBoth  bit5-7 预留
偏移21:          bit0-3 posX(0-15)                         bit4-7 posY(0-15)
偏移22 (冲刺):   bit0-2 spurtMode(0=未选 1=LOW_90 2=LOW 3=MED 4=HIGH)
                 bit3 spurtTestFlag   bit4-7 goaheadnum(0..15)
```

恒等式：`frontNear == wallFront && !frontFar` —— 前墙远近是在**组帧时**用同一组阈值
把原本或成一个的 `wallSns.front` 二分出来的，`wallSns.front` 的既有消费点一行未改。
`frontFar=1` 蕴含 `wallFront=1`；上位机要"贴脸该处理"就按上式现算。

`状态B` 为什么是两字节：`motionTask` 占 7 bit，加上 `spurtFlag`/`goOrBack` 共 9 bit，
一字节装不下（去掉 `irSwitch` 只腾出 1 位）。v9 之前这两个布尔在"冲刺态"字节里，
现在按语义归位到执行层。

### 3.4b 建图增量通道（偏移 23–29，v10）

> 目的：让上位机**实时**复现固件内部墙图，不必等跑完再 `MAP DUMP`（那条走 Flash 存档快照，
> `LP_SyncMap()` 全仓无调用点，上电未 `CAL BLOCK` 时回的是全 0 图）。方案与取舍见
> [`已落地方案与决策记录.md`](已落地方案与决策记录.md) §6。

**数据来源**：固件 `LINK_Tick`（1 kHz）比对 `GmcMouse` 坐标变化 —— 变了就是"走了一格"，
把该格的 `GucMapBlock[x][y] & 0x0F` 压进一个 **32 条**的环（RAM 64 B），每帧最多带 3 条。
采样点选在 `LINK_Tick` 而不是 `__wallCheck()`：`utility.c`/`test.c` 一字不动 ⇒ 比赛档 hex 天然不变。

**`mapHdr`（偏移 23）**

| bit | 名称 | 含义 |
|---|---|---|
| 0–1 | `count` | 本帧携带的条目数 **0..3** |
| 2 | `lossy` | 自上一帧以来环溢出过（丢过最旧）⇒ `anchor` 之前有洞 |
| 3 | `resync` | 本批是新序列起点（发车/坐标跳变/上电）⇒ host 应清图重来 |
| 4–7 | 预留 | 必须为 0 |

**`mapEntry[k]`（偏移 24..29，每条 2 B）**

| 字节 | bit | 名称 | 含义 |
|---|---|---|---|
| byte0 | 0–3 | `open4` | 该格四向**可通位**，`GucMapBlock[x][y] & 0x0F` **原值**（bit0=+Y bit1=+X bit2=-Y bit3=-X，**1=通**） |
| byte0 | 4–7 | 预留 | 必须为 0 |
| byte1 | 0–3 | `posX` | 格坐标 x（0–15） |
| byte1 | 4–7 | `posY` | 格坐标 y（0–15） |

**每条都带绝对坐标**（不用"锚点 + 方向链"压缩成 1 B/条）：链式能省一半字节，
但每帧 3 条相对"冲刺极限 2 条/拉取周期"已有 **7.5 倍余量**，而链式一旦某条方向出错会
**静默污染整批**（表现为整张图偏移一格、看不出来）。绝对坐标让单条错误最多错一格，
下一条自动纠正，host 侧也免掉 `mod 16` 走格与链传播校验。

> `open4` **刻意保持"可通位"语义，不转成"有墙位"**：与固件 `GucMapBlock` 一一对应，
> 上位机显示墙时才取反。注意它按**绝对方向**编号，而 `状态C` 的 `wallLeft/Front/Right`
> 是**相对朝向** —— 两个字节不能用同一套宏。

**上位机重建规则**（`host/host/api/mapd.py: MapReplayer`，须照抄固件 `__wallCheck()`）：

```python
wall[x][y] = open4 | (open4 << 4)          # 低=可通位, 高=未探明位
for d in 0..3:
    if not (open4 >> d) & 1:               # 这一面有墙
        wall[邻居(x,y,d)] &= ~(0x10 << d)  # 清邻居"未探明"位: 0x10=+Y 0x20=+X 0x40=-Y 0x80=-X
```

**必须带门控**：只有本格低半字节仍为 `0x00` 才写（固件 `if ((GucMapBlock[x][y]&0x0f)==0x00)`）。
漏了这条会把邻居后来清掉的"未探明"位重置回去，重建图就不能与固件逐字节相同了。
反过来，正因为有这个门控，**重复收到同一格是无害的**（幂等）—— 整帧被 TX 环丢弃后
下一帧原样重发是安全的。

**环语义**

- "进入发送缓冲区后清空" = **推进 tail**（FIFO 消费），绝不整块清。
- **只有本帧真的写进 TX 环才推进 tail**（判据：`linkDrop` 快照前后相等）。整帧被丢时
  tail 原地不动，下一帧原样再带 —— 因为每条自带绝对坐标，重发幂等。
- 环满时丢**最旧**并置 `lossy`：保证"最新一格永远在环里"，洞只会出现在前面。
- 深度 32 条覆盖 **14.4 s（搜索 450 ms/格）/ 4.1 s（冲刺 129 ms/格）** 的完全静默；
  满 32 条时 5 条/帧 × 17 Hz ⇒ 0.4 s 排空，不会永久落后。

**带宽**

| 量 | 值 |
|---|---|
| 每格耗时 | 搜索 **450 ms** / 冲刺 **129 ms**（格距 180 mm） |
| 拉取批次周期 | 5 帧（59 ms）+ 命令往返（≈300 ms）≈ **360 ms** |
| 每周期产出 | 搜索 0.8 条 / 冲刺 **≈2 条** |
| 每周期供给（3 条/帧 × 5 帧） | **15 条** ⇒ 余量 **7.5 倍** |
| ⚠ 纯 `TELEM`（N=1） | 3.3 Hz × 3 = 10 条/s，而冲刺 7.75 格/s ⇒ 余量仅 **1.3 倍** |

⇒ **建图期间保持 `RATE PULL` 的 N ≥ 2**（`codec.MAPD_MIN_PULL_N`）。按正常拉取用法碰不到。

**起点格不会出现在增量流里**（已知且合理）：固件上电后第一个采样 tick 只建立坐标基线
（`linkMapDPrevOk`），而起点格的 `GucMapBlock` 低半字节仍是初值 `0x00`
（`__wallCheck()` 只在"走进某格"时跑），所以它永远不会入环。这与固件实际的
`GucMapBlock` 状态一致 —— host 重建出的图也缺它，不是丢数据。

**交叉校验**：`pos`（偏移 21）仍是实时坐标，`count < 3` 时最后一格应等于它；
不等只记 `pos_mismatch_n` 告警，**不丢批**（真相以每条自带的坐标为准）。

### 3.5 flags 位（`LINK_FLAG_*`）

| 位 | 名称 | 含义 |
|---|---|---|
| 0x01 | `FREEMODE` | `freemode==1`：电机输出被**强制为 0**（注意不是"解锁"） |
| 0x02 | `SLEEP` | 休眠 |
| 0x04 | `EMERG` | 急停生效（本次上电以来触发过） |
| 0x08 | `PULLF1` | **本帧 = 收到 `RATE PULL` 后发出的第一帧**（批首帧）。远程档专属，**每批恰好 1 帧**带此位；比赛档无 `PULL` ⇒ 恒 0 |
| 0x10 | `IR_SWITCH` | **红外采样轮在跑**（`irswitch==1`）。v9 起复用恒 0 的 `DUMPING` 位 —— 它描述「传感器在不在采样」，与运动任务无关，不该占状态B1 |
| 0x20 | `MOTOR_OFF` | [保留] 恒 0（v2.4 取消安全档后无发送方） |
| 0x40 | `ESTOP_LOCK` | 急停**锁存**中：新的 MOVE/CAL 被拒（`ERR_ESTOP`），须 `STOP` 解锁 |
| 0x80 | `EVQ` | 有事件行因 TX 空间不足被丢弃 ⇒ 事件流不完整 |

> **0x08 的历史**：v2.0 起它是恒 0 的 `SCOPING`（示波器机制已删，全树无置位点、无消费者）。
> v2.6.1 把它**改名复用**为 `PULLF1`（flags 字节 8 位已满，这是唯一无主的位）。
> 固件在 `link_RateService` 的 PULL 分支组帧前置位、`link_SendUnified` 里 OR 进载荷并立刻清零
> （`#ifdef MOUSE_REMOTE` 门控 ⇒ 比赛档产物逐字节不变）。
> 用途：让上位机的"批起点"判据从**按 ms8 帧间隙推算**变成**读事实** —— 推算有四类误判
> （t 归档错 / ms8 ±256 折回 / RTT 换档 / 比 t 只短 1 ms 的刀锋）与一个对偶死角
> （`RTT ≡ 0 (mod t)` 时批起点间隔恰好 = t ⇒ 旧判据永远看不到边界、环路停摆）。
> 详见 [`链路MTBF压测方法.md`](链路MTBF压测方法.md) §14.15。

### 3.6 墙图帧（`MAP`，TYPE 0x07）

```
cX(int8) cY(int8) dir(u8) task(u8) | mapWall[n²] | mapVisited[n²]
```

行主序，x 外层。`n`（=mazetype）由**载荷长度反推**（固件不重复发）。墙位低四位编码：
`bit0=上 bit1=右 bit2=下 bit3=左`，**置位表示"无墙/可通行"**。

## 4. 上位机侧解析约定

### 4.1 统一帧扁平化

位打包字段在解码时**直接展开**成独立键（`dir / mazeTask / wallLeft / …`），上层
（`ring / monitor / analyze`）看到的是平铺字段，不需要知道打包细节。
`UNIFIED_CHANNELS` 有 **49** 项（与 49 字节恰好相等的巧合，不是约束）。

### 4.2 帧分派表驱动

帧分派走 `registry.FRAMES`（`{TYPE: FrameSpec}`），**不得**出现 `type == TYPE_*`
比较或 `decode_*` 直调（由 `contract_test` 的 `check_frame_dispatch_is_table_driven` 静态断言）。
未登记的帧类型**静默忽略并计数**（前向兼容）。

### 4.3 保序解析（硬要求）

`FrameStreamParser.feed()` 返回 `Frame | str` **混排的有序列表**，调用方必须**按顺序**处理。
把帧与事件拆成两个列表再分别跑，会让"帧, 事件, 帧"变成"帧, 帧, 事件"，序号看起来就跳了
（实测一次 `STOPPED` 会误报 3 个缺口、256 条丢失）。

## 5. 远程运动双护栏（`MOVE RUN`）

```
MOVE RUN <sp_l> <sp_r> [ms] [ir_mm]
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `sp_l / sp_r` | — | 左右轮速度 cm/s（绝对值上限 `LINK_RUN_SPEED_MAX=300`，超限回 `ERR_VALUE`） |

> urgent 命令走 `suspend()/resume()` 让路（`QUIESCE_MAX_S=0.30`，残留 1/12 延迟是**故意不改**，
> 避免拉长急停最坏延迟）。

## 6. 标定（`CAL`，请求-响应）

```
CAL <item> <act>
```

- `item ∈ {GYRO, WALLDIST, IRDATA, GYRORATIO, ENCANGLE}`
- `act ∈ {START, ABORT}`，或 IRDATA 的相位号 `0..3`
- **采完才回 ACK**（ACK 即"这一步完成，请摆下一个位置"），最坏可能数秒
  ⇒ 超时 `10 s` 且 **不重发**（`no_retry`，重发会往正在进行的采集里插命令）
- 结果值用 `GET` 回读；`GYRORATIO` / `ENCANGLE` 这套用 `ACK … OK <a> <b> <c>` 带回三个值

### 6.1 菜单功能远程化（v2.7，仅远程档）

> ⚠️ **基线差异（2026-10-16 核定）**：本段"等车循环轮询 `BUTTON1`、短按进 `MENU_Run()`"
> 是**课程固件**（v2.7）的行为。**新基线远程档的等车循环不轮询按键**（纯等 `MAZE RUN`
> 请求），`MENU_Run()` 全树无调用点 —— 该特性属于"2.x 旧固件专属、新基线不再支持"，
> 按用户决策（2026-10-16）**废弃**，不补代码；菜单维护功能已由下表 `CAL` 家族 6 项
> 全覆盖，无功能损失。

同时，菜单里这些维护功能也可以在链路上直接调用 —— 命令文本沿用 `CAL <item>`，**省略 act 词**：

| 菜单 | 命令 | ACK 附加字段 | 说明 |
|---|---|---|---|
| 2 擦红外标定 | `CAL ERASEIR` | — | 擦 IRDATA 页（page123）并复位分步序列。⚠️ 只擦 Flash：内存 `irCalib` 与查表要等下次上电 `CALIB_InitIr` 才重载 |
| 4 红外自检 | `CAL IRSELF` | `OK <l> <r> <ref>` | **仅传感器段**（左右红外各判一次）。原菜单后半段"前向开电机扫 FORWARDIRTEST"**不远程化**（远程已有 `MOVE RUN` 双护栏） |
| 5 显示传感器 | `CAL SENSOR` | — | 固件 printf 固定 4 行（里程/红外 4 路/陀螺）。⚠️ 值**不在 ACK 里**，结构化取值请用统一遥测帧 |
| 6 红外 8 值 | `CAL IRCAP <1..4>` | `OK <a> <b> <step>` | 分步替代原来的"按按键确认"。第 4 步擦页并按读序写 8 个半字，序列复位 |
| 7 块数据 | `CAL BLOCK` | `OK <path45> <path90> <ir_valid>` | 先把 Flash 墙图**重载进 `mazeState`**（随后 `MAP DUMP` 拿到的才是 Flash 里的图），再回概览；墙图本身仍走 `maze.dump` |
| 8 擦运行数据 | `CAL ERASEALL` | — | 擦 BLOCK/BLOCK_POINT/GOPATH/BACKPATH/GOPATH_90/BACKPATH_90 **6 页** |

与旧五项的三点差别：

1. **立即 ACK**（不等采集）—— 两条不同的流，`calib.cal` 的 `timeout=10s` 对它们是富余的。
2. **全部仅远程档**；比赛固件回 `ERR_VALUE`（`link_CalItemToId` 不认这些词）。
3. 运动中/标定中一律 `ERR_BUSY`（`link_MotionBusy` 闸）—— 运动途中擦 Flash 会打掉正在用的墙图/路径。

`CAL IRCAP` 的两条固件规矩（否则分别回 `ERR_VALUE` / `ERR_BUSY`）：

- **必须从 1 开始顺序调**（1 左近墙 / 2 左远墙 / 3 前近墙 / 4 前远墙；每步摆位不同，
  跳步会把数记到错位置）。第 1 步随时可重发 = 中止重标。
- 第 1 步前 IRDATA 页必须为全 `0xFFFF` —— 这是**远程版新增**的安全闸（原菜单 6
  没有这条：它采样完才擦页），防止"顺手把 4 步再跑一遍"把好标定悄无声息地换掉；
  重标请先显式 `CAL ERASEIR`。

与菜单 8 的两点**有意差异**：远程版擦完**返回值守、不休眠**（菜单 8 之后进流水灯
死循环，远程设备睡下去就失联）；且**不擦** page101–114 录制区（历史采集数据）。

⚠️ `ERASEIR` / `ERASEALL` 不可逆，而固件侧**没有**二次确认 —— 确认由上位机把着：
`registry` 的 `precheck` 要求显式 `confirm=True`，否则就地返回 `NEED_CONFIRM`
（不碰链路）；CLI 侧对应 `--confirm`。

### 7.1 参数编码

## 8. 错误码

| 码 | 触发 |
|---|---|
| `ACK -1 ERR_NOCRC` | 行内没有 `*` 或 CRC 位数不足 |
| `ACK -1 ERR_CRC` | CRC 校验失败 |
| `ERR_CMD` | 不认识的命令关键字 |
| `ERR_NAME` | 不认识的参数名 |
| `ERR_VALUE` | 参数值非法（越界 / 档位不匹配） |
| `ERR_BUSY` | 设备忙（如 `MAZE RUN` 已在跑） |
| `ERR_ESTOP` | 急停锁存中，新的 MOVE/CAL 被拒 |
| `ERR_TIMEOUT` | 设备侧等待超时 |

> `NEED_CONFIRM` **不是设备错误码**：它是上位机 `registry` precheck 的本地状态
> （`CAL ERASEIR` / `CAL ERASEALL` 未显式 `confirm=True` 时就地返回，命令根本没上链路）。
