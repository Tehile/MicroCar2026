## 4. ★ `ERR_ESTOP` 死锁 —— 确认为真实固件缺陷

### 4.1 现象

`MAZE RUN RACE` / `MAZE RUN BLIND` **恒回 `ERR_ESTOP`**，且**无法用 `STOP` / `MAZE STOP` / `TARE` 解锁**，**`MCU RESET` 之后仍然被拒**。

### 4.2 实测证据（车全程静止，`MAZE RUN` 必被拒故无风险）

```
① 当前状态                      OK          lock=True  emerg=False free=True sleep=False
② STOP（固件应清锁）            OK          lock=True  emerg=False free=True sleep=False   ← 回 OK 但锁未清
③ MAZE RUN RACE                ERR_ESTOP    lock=True  ...
④ MAZE STOP                    OK          lock=True  ...
⑤ MCU RESET → 等 6.5s           OK          lock=True  ... rst=SW（复位确实生效）
⑥ MAZE RUN RACE                ERR_ESTOP    ← 复位后依然被拒
```

- 12 秒慢速观察（每 0.4 s 采样）：`lock/emerg/freemode/sleep/task` **状态变化次数 = 0**（无自愈）。
- 5 秒事件行监听：**无 `ESTOP TRIP` 事件**（说明 `LINK_EStopTrip()` 不是本次的置位者）。

### 4.3 根因分析（代码 + 实测闭环）

**关键矛盾**：`estop_lock = True` 但 `emerg = False`。查固件 `link.c:1143` 的注释，答案是**设计如此**：

```c
/* 急停锁存是独立于 emergMon 的**链路层**事实: 表示"必须显式 STOP 才能再动"。 */
if (linkEStop)  f |= LINK_FLAG_ESTOP_LOCK;
```

**但实现与该设计不自洽**，构成死锁：

| 环节 | 代码位置 | 行为 |
|---|---|---|
| 置位 `linkEStop = 1` | `link.c:2715`（`ESTOP` 命令） | 置位 |
| 清零 `linkEStop = 0` | `link.c:2696`（`STOP` 命令）、`link.c:2822`（某 RUN 分支） | 清零 |
| 再次置位 | `link.c:3481` `LINK_EStopTrip()`，由 `timer.c:1152` **每毫秒调用** | 见下 |

```
timer.c:1152  LINK_EStopTrip();          ← 每 tick 调用
  └─ link.c:3478  if (linkEStop) return; ← 已锁存就直接返回(防 1ms 刷行)
     link.c:3481  linkEStop = 1;
```

而 `LINK_EStopTrip()` 的注释说它"由 `isr.c` 在 `emergMon.active==1` 时调用"。实际调用点在 `timer.c:1152`，**没有 `emergMon.active==1` 的前置判断**（对比 `timer.c:1136` 的 `if(isemergency==1)` 块内并没有调用它）。

⇒ **每次 `STOP` 把 `linkEStop` 清 0，下一个 tick 的 `LINK_EStopTrip()` 立刻又置回 1。** 实测完全吻合（② STOP 回 `OK` 但 `lock` 仍 `True`）。

### 4.4 另一个独立缺陷：`isemergency` 无清零点

```
timer.c:1275   if (emergency_count>200 || setvl>2000 || …) isemergency=1;
utility.c:1397 if(disf<20) isemergency=1;
全树: 只有 timer.c:109 的初始化 =0, **无任何 isemergency=0 的赋值点**
```

⇒ 一旦被置 1 就**永久为 1**。`STOP` 清的是 `emergMon.active`（链路层），而 `link_port.c:180` `LP_SyncIn` 每 tick 执行 `emergMon.active = isemergency;` 会**把 1 写回**，于是 `STOP` 的清零被立即撤销。

这也解释了为什么 `MCU RESET` 之后仍是 `ERR_ESTOP`：**如果 `isemergency` 曾被置 1，复位是唯一的清除手段**（复位后从 `main()` 重跑，全局量重新初始化）。实测复位后仍被拒，说明要么 `isemergency` 在复位后仍为 1（`hardware_init()` 阶段又触发了 `utility.c:1397`），要么 `linkEStop` 的每 tick 置位路径才是主因。

> ⚠️ 这两条是**推断**，本轮无 J-Link 无法直接读 `isemergency` / `linkEStop` 的 RAM 值确认。
> 下一步（需 J-Link 或加诊断字段）：读 `isemergency`(`0x2000xxxx`) 与 `linkEStop`(`0x200000FC`) 的实际值。

### 4.5 影响与临时绕行

| 影响 | 说明 |
|---|---|
| 发车完全阻塞 | `MAZE RUN` 是发车唯一入口，恒 `ERR_ESTOP` ⇒ **P3 发车/收车/容量测试全部无法进行** |
| 只读测试不受影响 | `PING`/`TELEM`/`GET`/`SETQ` 全部正常（本轮 23/23 已证） |
| 现场风险 | 比赛档按键流程不受影响（`link.c` 整文件 `#ifdef MOUSE_REMOTE`） |

**临时绕行（不改固件）**：给 `timer.c:1152` 加 `if (linkEStop) { } else` 之类的门控，或在 `LINK_EStopTrip()` 里加"本 tick 刚被 STOP 清零则不重锁"的抑制窗口。**本轮按约定不改代码。**

## 6. 遥测实测特征

| 指标 | 实测 |
|---|---|
| 帧率 | 8 s → 27 帧；10 s → 34 帧（**丢帧 0**） |
| RTT | 平均 299–301 ms，中位 299 ms，最大 357 ms |
| `ms8` | 27–34 个样本**全不同**，范围 `[6, 254]`，逐帧差 `{−212, 44, 45}` |
| `trackL` | 恒 `−15`（首采）/ `0`（复采），**漂移 `+0`** |

**`ms8` 不是单调时钟**：逐帧差出现负值与多个离散值 ⇒ 它是**下采样批内的时基标记**（批长度不同 ⇒ 差值不同）。host 侧**不可**用它算时间戳；绝对时刻须用 `TELEM` 的 ACK 第三字段（时基锚）。
