### 0.1 用户明确的原则

1. **不改原有比赛代码**：1 kHz 红外采样、`run_data[]` 黑匣子、比赛算法一行不动。
2. **软件不设速率上限**：只受物理链路约束。波特率维持 115200（后续可试提高）。（v2.1：改为 PC 拉取后**"不设 Hz 上限"的原则不变** —— 不设的是软件硬编码上限，速率由链路往返（1/RTT）决定（停等，见 §6.1.5）。⚠️ 但**提高串口波特率不会改善帧率**：真机实测 RTT≈224 ms，而一帧 53 B @115200 只占 4.6 ms，其余全是蓝牙模块的转发延迟，与波特率无关。）
3. **上位机算得出的不上报**：统计量（峰值速度、位移、耗时）由上位机从流数据计算。
4. **上行只留"持续流 + 异常"**。
5. **波特率上限是物理事实**，不是策略。

## 1. 背景与动机

### 1.1 现状：三条上行通道并存

| 通道 | 形态 | 带宽 |
|---|---|---|
| ① 周期遥测 | 4 种帧：`FAST` 24B@5Hz / `MID` 20B@1Hz / `SLOW` 24B@0.5Hz / `TIME` 20B@1Hz | ≈172 B/s |
| ② 阻塞问答 | `SNAP [域]` 一问一答，6 个域 | 零常驻 |
| ③ 本地录制 + 事后整块回传 | `SCOPE START` 本地 1 kHz 写环 → `SCOPE DUMP` 整块回传 | 突发 1.38 KB/s × 7.1 s |

### 1.2 为什么必须改

> ⚠️ **v2.1 真机实测推翻了本节下面第（1）条的核心论据 —— 请先读这段。**
> §1.2 当时依据"一次 `SCOPE DUMP` 实测 1.38 KB/s 持续 7.1 s 未堵死"，判定"152 B/s 的上限不可靠、
> 不应作为设计前提"。**真机（2026-10-05，COM7/CH340 + 蓝牙透传）复测结论相反**：这条链路
> **实测只能承载约 100~200 B/s**，单条命令应答往返 **≈1.21 s**。那次 `SCOPE DUMP` 是**短时突发**，
> 而 v2.0 压上去的是**持续流**（53 B × ≈217 Hz ≈ **4.3 KB/s**，≈链路能力的 **20 倍**），
> 才会把蓝牙模块的内部缓冲灌满并**永久停止转发**。**v1.5.5 `link.c` 里那条
> "缓冲灌满即停止转发、需重新上电"的注释是对的**，v2.0 把它当"待复验的旧结论"删掉，就是本轮事故的根因。
> **因此本节下面"三通道并存带来协议分叉 / 时序脆弱"（第 2、（3）条）仍然成立**（协议精简的依据不变），
> **只有"带宽不是瓶颈"这一条作废**。完整证据链与整改见 §6.1。
>
> 下面表格中"USART1 物理天花板 11 520 B/s"指的是 **MCU ↔ 蓝牙模块的串口线**；
> **端到端（PC ↔ 蓝牙透传 ↔ MCU）的有效吞吐**要以真机实测的 **≈100~200 B/s** 为准 —— 二者差了两个数量级。

**（1）"双流"的唯一理由是物理速率不足，而这个前提不成立。**

通道 ③ 的存在理由是"实时传不了高分辨率，所以先存后传"。但实测数据是：

| 项 | 数值 |
|---|---|
| USART1 物理天花板（115200-8-N-1，**只到蓝牙模块为止**） | **11 520 B/s** |
| ~~实测突发（`SCOPE DUMP`）~~ **短时突发** | ~~1 380 B/s 持续 7.1 s，未堵死~~（**短突发成立；不能外推为"可持续"**） |
| **端到端吞吐（v2.1 真机实测）** | 持续灌流 **≈100~200 B/s**（把模块缓冲灌死前的量级）；**停等拉取载荷吞吐 ≈234 B/s @ 4.41 Hz** —— 两者是同一量级的两种测法；命令往返 **≈1.21 s**（停等单帧往返实测 157~234 ms，见 §6） |
| 代码注释声称的安全线（`link.c`） | "数百 B/s，超限就完全堵死且需模块重新上电" —— **v2.1 复现，注释是对的** |

~~**实测值比注释高 9 倍，而天花板是注释值的 67 倍。**~~ 该上限数字**来源不可靠，不应作为设计前提** ——
**这一段结论作废**：`SCOPE DUMP` 的高速率是**短突发**（缓冲还能吃下），不代表可**持续**推送；
**"超限即静默、需重新上电"已被真机复现**（见 §6.1）。**"不可靠"这个判断本身就是错的**。

**（2）三通道并存带来协议与实现的双重分叉。**

`SNAP` 与周期帧的字段**大量重复**（MOTION/ODOM/SENSE 三域与快/中/慢帧覆盖同一批量），上位机要为同一物理量维护两条解析路径（`decode_*` 与 `parse_snap_line`）。

**（3）阻塞轮询与实时流混用导致时序脆弱。**

`SNAP` 在流开启时会与遥测争抢 TX 环（这正是"快照要加 `LINK_SNAP_NEED_SPACE` 空间门"与"TX 环 256→512 B"的原因），且 dump 期间 ACK 被挤后约 1 s（详见 `CHANGELOG [1.5.1]`）。

### 1.3 不变的硬约束

| 约束 | 依据 |
|---|---|
| **1 kHz 红外采样**：`doWallDetect()` 在 `SysTick_Handler()` 每 1 ms 跑，位于 `#ifdef MOUSE_TEST_MODE` **之前** | `isr.c:770` 附近；比赛算法依赖 |
| **`run_data[]` 9600 B 黑匣子**：由比赛状态机驱动 | `flash.c:37`、`APP/state.c:290`、`flashSt.flashenable` 由 `state.c:224` 置 1 |
| **比赛算法一行不动** | 用户要求 |
| **波特率 115200** | 用户决定维持，后续再试 |

> 注：`run_data[]` 在 SCOPE 砍掉后**不再被链路模块借用**，回到纯比赛黑匣子状态 —— RAM 归位，且不影响比赛固件。

## 2. 设计原则

> **① 上行只有两类：持续数据流 + 异常事件。**
> **② 下行一律请求-响应（上位机发起，设备应答）。**
> **③ 上位机能算的，设备不传。**

对第 ③ 条要划清边界 —— 去重的对象是**纯函数映射的重复量**，不是"原始 vs 计算"：

| 量 | 能否去重 | 原因 |
|---|---|---|
| 红外 mm | ✅ 去重（但与 ADC 双传，见 §4.2） | 查表映射，无状态 |
| 电池 mV | ✅ 去重，只传 mV | 乘系数，无状态 |
| 墙位 bits | ✅ 去重 | 可由 ADC + 阈值参数算出 |
| **陀螺角度** | ❌ **必须由 MCU 算** | 1 kHz 积分结果；回传帧率实测只有**个位数 Hz**（v2.1 停等拉取：4.4~6.5 Hz，= 1/RTT），上位机积分会丢掉大量分量 |
| **里程 `trackL/R`** | ❌ **必须传累加值** | 累加量，传瞬时值无法还原 |
| **坐标 / 任务 / flags** | ❌ **必须原样传** | 状态机输出，上位机无法复刻 |

## 3. 上行模型

```
① 统一数据流      53 B / 帧        由上位机 `TELEM` 拉取，含**完整迷宫状态机**与决策结果
② STOPPED <reason> #n             任务结束 / 近墙保护 / 用户停车
③ ESTOP TRIP       #n             急停（立即，不等任务收尾）
④ 复位原因                        随 PING 应答返回（见 §10）
```

> 事件行统一带序号 `#n`（1 字节循环，与帧的 `SEQ` 同一计数器空间，见 §8.3）。
> **`MAZE EV` 已从上行清单删除** —— 理由见 §8.4。
> **【v2.1】① 由"固件自时钟持续流"改为"上位机拉取"** —— 帧率（原写 217 Hz）不再是固件承诺值，
> 而是停等拉取按链路往返（1/RTT）逼近；见 §6.1。

**已删除的上行**：

| 删除项 | 去向 |
|---|---|
| `FAST` / `MID` / `SLOW` / `TIME` 四种帧 | → 统一帧 |
| `SNAP MOTION/ODOM/SENSE/POWER/TIME/MAZE` | → 统一帧（可测量量）／参数命令（配置） |
| `SCOPE DUMP` 的 `DUMP_HDR/BLK/END` | → 删除（本地录制机制整体取消） |
| `MAZE` 1 Hz 状态帧 | → 统一帧已含 `task`/`posX`/`posY`/`flags` |
| **`MAZE EV <EVENT> …`（8 子类）** | → **删除**（2026-10-05 决策）：状态量已全部在统一帧（`mazeTask`/`posX,posY`/`wallL,F,R`/`goalX,goalY`/`stackIdx`/`motionTask`），边沿由上位机差分取得 |
| `ARMED <ms>` | → `ARM` 命令应答 |
| `CALSTEP` / `CALDONE`×4 / `CALERR`×2 | → 命令应答（见 §9） |
| `MOVEDONE RUN/FWD/ROT` 全部统计量 | → 上位机从流计算 |

## 4. 统一帧规格

### 4.1 帧结构

```
AA 55 | LEN(2,LE) | TYPE(1) | SEQ(1) | PAYLOAD(45) | CRC16-MODBUS(2)
└──── 开销 8 B ────┘                  └─ 载荷 45 B ─┘
总长 53 B  →  11520 / 53 = 217 Hz (4.60 ms/点)   ← 这是 115200-8-N-1 的**理论上限**
                                                     （v2.1 端到端实测 ≈100~200 B/s，见 §6.1）
```

> **【v2.1】帧本身未变**（仍是 53 B / `TYPE=0x0A`），只把"谁来控制发送节奏"从固件改为上位机。
> 217 Hz 的算式仍成立，但它是**串口线**的上限；端到端（含蓝牙透传）实测远低于此，故拉取模式下
> 帧率由**链路往返（1/RTT）**决定（停等拉取），**不能按 217 Hz 预估** —— 真机实测仅 **4.4~6.5 Hz**，见 §6.1.5。

- `TYPE`：新取 `LINK_TYPE_UNIFIED = 0x0A`，便于上位机明确区分协议版本（`0x01` 是旧 FAST）。
- `SEQ`：1 字节循环。上位机用差检测丢帧。
- `CRC16-MODBUS`：与现有一致。

### 4.2 载荷字段表（45 B）

**单位纠正（重要）**：`odom.c:96-101` 显示 `trackAbsL = (…) / sysCfg.trackRatioL` —— 除法**已经做了**，
所以 `trackL/trackR/trackAbs/cellOdom` 的单位是 **mm（物理距离）**，不是 pulse。
s16 覆盖 **±32767 mm = ±32.7 m**，7×7 迷宫（单格 180 mm、全程几米）绰绰有余。
> 早前版本误按 pulse 计算，得出"s16 在 616 mm 饱和、必须改 s32"的结论 —— **该结论作废**，
> `trackL/trackR` 保持 **s16**，省下 4 B。

| 偏移 | 字段 | 类型 | 字节 | 来源 / 说明 |
|---|---|---|---|---|
| 0 | `ms8` | u8 | 1 | `linkTimeMs & 0xFF`，时间锚（见 §5） |
| 1–8 | `irAdc[4]` | u16×4 | 8 | 原始 ADC：F1/F2/L/R。**标定核查与饱和判定用** |
| 9–16 | `irMm[4]` | u16×4 | 8 | 4 路距离 mm。与 ADC **双传**（非线性映射，上位机不便复算） |

| 23–24 | `gyroAngle` | s16 | 2 | 陀螺积分角度（1 kHz 积分，上位机丢样算不出） |

### 4.4 为什么 `wallThresh` 必须传（不可推导）

`wallSns.wallThresh` 在运行时会被**两处改写**：

| 位置 | 值 | 场合 |
|---|---|---|
| `core.c:92` | `WALL_SIDE_THRESHOLD`（参数默认 160） | 初始化 |
| `state.c:225` | **140** | 比赛流程 |
| **`motion.c:418`** | **110** | **运动控制中** |

而 `isr.c:676/680` 判定侧墙用的正是它。**上位机从参数 `IRTHRWALL` 读到 160，与运行时的 110/140 不是一回事** ——
不传它，就无法解释"为什么这次没判出侧墙"。故必须进帧（1 B）。

### 4.5 决策数据：只传结果，不传输入

`EXPLORE_CrosswayChoice()` 首行是 `FLOODFILL_Open(goalX, goalY)` —— **全图重算**，且会改写 `mapStepOpen`。
因此决策**输入**（`sF/sL/sR` 全开图步数、选中的贴墙法则）：

- 不能每帧算（毁 1 kHz 控制环）
- 不能只读调用（`FLOODFILL_Open` 有副作用）
- 要拿到就必须改 `explore.c` —— **那是原有比赛代码，不可动**

所以只传**决策结果**，而它全部来自既有状态变量，**已在帧内**：

| 决策结果 | 字段 |
|---|---|
| 目标格变化 | `goalX` / `goalY` |
| 状态机迁移 | `mazeTask` |
| 岔路栈深度 | `stackIdx` |

| **实际执行的动作** | `motionTask` + `motionStep` |

## 5. 时间锚与同步

### 5.1 机制

**【v2.1 修正：锚的获取从"开流时给一次"改为"每次拉取都刷新"】**

1. **锚**：**每条 `TELEM` 的应答都带完整 u32 时基** → `ACK <seq> OK <upMs>`
   （v2.0 曾是 `STREAM ON` 应答带一次；`STREAM ON` 已删除，见 §7.1）
   ⚠️ **故 `TELEM` 不参与幂等重放**（实施决策）：固件的"相同 seq + 相同 CRC → 重放上次应答"
   机制会缓存应答字符串；若命中，重发**只能拿到旧锚**、而且**拿不到新的一帧**。因此 `TELEM`
   在应答后清 `linkLastSeq`，使下一条同 seq 命令走真实执行路径。这是"锚必须每次新鲜"的直接后果。
   **收益**：失锁后不必专门"重新索要锚" —— 下一次正常拉取就自动带入新鲜锚（自愈）。
2. **每帧**：带 `ms8 = linkTimeMs & 0xFF`
3. **还原**：以锚 + 单调时钟粗估 `predicted_up_ms`，在"低 8 位 = `ms8`"的候选中选最接近的那一个

### 5.2 为什么足够

模周期 256 ms。v2.0 按 217 Hz 估一周期可容纳 **55 帧**；v2.1 拉取模式下帧率更低
（真机端到端 ≈100~200 B/s，见 §6.1），一周期内**还能容纳更多帧**，余量**更宽松**。
只要粗估误差 < 128 ms 就能唯一还原。设备晶振 vs PC 时钟漂移约 100 ppm = **3.6 ms/小时**，远小于余量，**连续数小时不会失锁**。

### 5.3 失锁检测

还原后若 `|还原值 − 预测值| > 128 ms`，上位机判定失锁并**重新索要锚**。v2.1 下锚**每次 `TELEM` 应答都会刷新**，因此无需额外命令 —— 上位机只需丢弃失锁后的第一批帧、等下一次拉取的应答把锚带回即可。绝不静默错标。

### 5.4 为什么保留时间戳（而非用接收时刻）

| 做法 | 得到的采样时刻 | 误差 |
|---|---|---|
| 用 PC 接收时刻 | `upMs + 链路延迟` | **真机实测命令往返 ≈1.21 s**（原记录 230 ms 偏低），抖动 ms 级 |
| 用 `ms8` 同余还原 | 设备 1 ms 定时器 | **0 ms** |

链路往返已达**秒级**（且随应答长度增长）—— 用接收时刻会把秒级、且逐条不同的延迟直接写进时间轴，
故"事后分析"必须用设备时钟。

**成本**：帧长 +1 B。**收益**：事后分析的时间轴不受蓝牙抖动污染，且**事后无法补救**。

## 6. 背压与丢样语义

### 6.1 拉取模式 = 把发送节奏交给上位机（v2.1 真机实测后的修正）

#### 6.1.1 事故：自时钟把蓝牙模块的缓冲灌死

**这是本项目最重要的一条实测教训，写在最前面。**

v2.0 的规则是"设备自时钟、无 Hz 上限"：固件每 1 ms 检查 TX 环与 DMA 是否空闲，够就组一帧发出去。
它假设"背压会让帧率自动收敛到链路真能力"。**真机（2026-10-05，COM7/CH340 + 蓝牙透传）证明这个假设是错的**：

| 项 | 实测值 |
|---|---|
| 这条链路的**端到端吞吐** | 持续灌流 **≈100~200 B/s**；停等拉取载荷 **≈234 B/s**（@4.41 Hz） |
| 单条命令应答往返（`MAP DUMP` 120 B） | **≈1.21 s**（不是早期记录的 230 ms） |
| v2.0 自时钟压上去的速率 | 53 B × ≈217 Hz ≈ **4.3 KB/s** |
| 超出链路能力 | **约 20 倍** |

**后果**：蓝牙透传模块的**内部缓冲被灌满后停止转发，且不会自行恢复** —— 必须给模块**重新上电**。
现场表现极有辨识度：

- `PING` / `ARM` / `GET ALL` / `MAP DUMP` 这些**小的、一次性的突发全部正常**；
- 而一旦收到 `STREAM ON`（开始持续流），**立刻 0 字节**；
- 之后**连 `PING` 都不再应答**，**只有断电重上才恢复**。

**根因不在固件，而在"谁能控制发送节奏"**：固件把 TX 环看作背压信号，但**第一个缓冲（蓝牙模块内部）对 MCU 完全不可见**，
MCU 的 TX 环空不空与蓝牙模块灌没灌满毫无关系。**在 MCU 这一侧"背压会收敛"的假设，跨过蓝牙透传就不成立了。**

**关键证据（历史）**：**v1.5.5 的 `link.c` 里本来就写着这条约束** ——
"其内部缓冲一旦被灌满就会停止转发，且不会自行恢复（需要模块重新上电）"，
并因此用一个分频把常驻速率**刻意压到 152 B/s**。v2.0 重写链路时，**把这条注释连同分频一起删掉了**（见 §1.2 的勘误）。

#### 6.1.2 排查中已排除的原因（都不要再去查）

| 被怀疑项 | 为什么排除 |
|---|---|
| `link_AckU` 坏 | `ARM` 走**同一个** `link_AckU`，应答正常 → 函数没问题 |
| TX 环 / DMA 坏 | `MAP DUMP` 的 **120 B 突发**正常发出 → 环与 DMA 都能通 |
| MCU 卡死 | IWDG 已启用，若真卡死 2 s 内必复位、`PING` 应恢复；但现场 **20 s 不恢复**，与"卡死"不符 |
| 端口掉线 | `list_ports()` 每 **0.25 s** 采样、持续 **15 s**，COM7 **始终在**（串口没掉） |

排除完这四条，"对端缓冲满了、且不会自愈"是唯一能解释全部现象的假设 —— 并且它**与 v1.5.5 的注释完全吻合**。

#### 6.1.3 修正：PC 拉取（请求-响应）

**【v2.1 现行机制】**

```
PC  -> TELEM
设备 <-  一帧统一帧(53 B) + `ACK <seq> OK <upMs>`(带时间锚)
```

- 固件**删除** `STREAM ON` / `STREAM OFF` 与"开流"状态；**新增 `TELEM` 命令**。
- 固件**不再自时钟发帧** —— 收到一条 `TELEM` 才组一帧（`link.c` 的 `link_SendUnified()`）。
- **发送节奏完全由上位机决定**：PC 不发请求，固件就一个字节都不发。
- **自愈性质**：PC 停止请求 → 固件不再发送 → 蓝牙模块缓冲**自然排空** → **无需断电即可恢复**。
  （真机已验证：停发 10 s 后帧计数不再增长，再发 `PING` **立刻应答**，无需断电 —— 见 §6.1.5。）

上位机侧是**严格停等拉取器** `host/host/api/stream.py` 的 `PullRequester`：

- **在途请求恒为 1**：任何时刻只发一条 `TELEM`，`_refill()` 只在 `self._out` 为空时才补发下一条；
- 收到应答（或超时）才发下一条 —— "请求-响应-请求"的严格停等，**绝不 burst**；
- 单条请求等待上限 **3 s**（覆盖真机 RTT 157~234 ms 的波动，取足量余量）；
- 仍**没有任何软件 Hz 上限** —— 可达帧率 = **1/RTT**，由链路往返时间决定
  （真机 RTT 在 150~230 ms 波动，对应 **4.4~6.5 Hz**）。
  这与用户"不要软件限速、尽量吃满物理带宽"的要求一致（见 §0.1 第 2 条）。

> 换句话说：**不设上限**这件事没有变，变的只是"谁在数这个上限" —— v2.0 让固件盲目地全速灌，
> v2.1 让上位机**按应答是否到达**逐条收敛，**收敛点自然落在链路真能力上**。
> **【真机实测后修正】最初的 v2.1 实现是"滑动窗口 + AIMD"（窗口 1..16 自适应），
> 真机证明这是错的，已改为严格停等 —— 根因与数据见 §6.1.5。**

#### 6.1.4 与 v2.0 自时钟实现的对照（已被取代，保留备查）

> ⚠️ 以下为 v2.0 的实现记录，**已被 v2.1 取代**，仅作历史留存。
>
> 初版判据写"每 1 ms 查 TX 环空间 ≥ 48+余量"，但环是 512 B、链路每 ms 只送出 11.52 B ——
> 照此判据头几毫秒每次都"够"，环会被连续灌满。后改为"链路完全空闲"（DMA 空闲 **且** TX 环已排空）才组帧：
>
> ```
> 每 1 ms 检查: (DMA 空闲) 且 (TX 环 head == tail) ?
>     是 → 组"当前最新值"为一帧, 入环
>     否 → 跳过(下 1 ms 再试)
> ```
>
> 在**纯串口线**上，这让一帧 53 B 用 4.60 ms 送出、帧率 ≈217 Hz。**但在蓝牙透传链路里，
> 这个 217 Hz 恰恰是灌死模块的元凶** —— 因为蓝牙模块的缓冲不在 MCU 的背压回路里（见 §6.1.1）。

#### 6.1.5 为什么是停等而不是流水线（真机实测根因）

> **【v2.1 真机修正】** 最初的 v2.1 把上位机拉取器做成"**滑动窗口 + AIMD**"（窗口 1..16 自适应）。
> **真机（COM7）实测证明这个设计是错的**，它已被改为**严格停等**（在途恒 1）。本节给出根因与数据。

**根因：固件每 1 ms tick 只消费一行命令。** `HARDWARE/link.c` 的收行逻辑是：

```c
if (USART_RX_STA & 0x80) { len = USART_RX_STA & 0x3F; link_HandleLine(...); USART_RX_STA = 0; }
```

bit7 未清（上一行还没被取走）时，`usart.c` 会把后续到达的字节**直接丢弃** ——
**同一时刻只能有 1 条命令在飞**。真机实测"背靠背发 N 条 `TELEM`"的回收率：

| 背靠背 N 条 | 回收率 |
|---|---|
| 1 | **100%** |
| 2 | 50% |
| 3 | 33% |
| 4 | 25% |
| 8 | 12% |
| **间隔 300 ms 逐条发** | **100%** |

**固定窗口扫描**（每档 6 秒，COM7）—— 窗口 1 已经是满速，加大窗口没有收益：

| 窗口深度 | 实测帧率 |
|---|---|
| 1 | **6.50 Hz**（RTT 153 ms） |
| 2 | 6.49 Hz |
| 4 | 7.15 Hz |
| 6 | 7.15 Hz |

→ **窗口 1 就拿到 1/RTT 的满速**；加大窗口只多约 10%，却开始成串丢失（上表回收率随 N 掉），得不偿失。

**停等不是"软件限速"，而是协议层的物理约束。** 可选帧率被 RTT 钉死为 1/RTT：

- **延迟分解**（各 12 次取中位）：裸串口 write→收到 ACK **224.1 ms**（范围 143~527 ms）；
  经 `CommandClient.send`→`Pending.done` 221.8 ms；经 `MouseClient.send_cmd` 220.4 ms；
  停等 + 接收即补发 224.3 ms。→ **T2 − T1 = −2.3 ms，命令层零开销**。
- **停等版真机复测**：12 秒收到 **53 帧 = 4.41 Hz**（≈234 B/s 载荷），**在途恒为 1、丢 0、`bad_crc` 0**；
  随后复拉 5 秒得 4.40 Hz、丢 0。单帧 `TELEM` 往返 **157~234 ms**。
- **自愈验证成功**：停止拉取后静默 10 秒（帧计数不再增长），再发 `PING` **立刻应答 —— 不需要断电**。
  这是"蓝牙模块缓冲只是被灌满、并非永久损坏"的直接证据，也说明"不再请求 → 设备不再发 → 缓冲自然排空"这条恢复路径成立。

**结论**：可达帧率 = 1/RTT ≈ **4.4~6.5 Hz**（RTT 在 150~230 ms 间波动）。
**停等比堆在途请求更快** —— 每一条请求都真的换回一帧（零浪费、零丢失），而流水线只会把命令挤丢。
早先某次扫描到的 153 ms 只是**链路延迟波动**，不是稳定基线，不能据此以为可以流水线提速。

#### 6.1.6 发车状态必须能被显式复位（v2.1.1 修复）

**真机缺陷（2026-10-05）**：`[4]` 数据收集档**发过一次车之后**，`MAZE RUN` 每次都回
`ERR_BUSY`，**连 `STOP` 也救不回来** —— 现场只能断电重启。用户报告的现象是
"测试中发车和急停可能会出现繁忙而无法下达指令"。

**根因是两个条件叠加：**

1. `MAZE RUN` 的忙判据是 `linkMazeReq || linkMazeRun`，而 `linkMazeReq` 置位后
   **只有上电（`LINK_Init`）才清零** —— `LINK_MazeStarted()` 当时只置 `linkMazeRun`，
   没有消费这个请求位。"请求"在语义上应当是**边沿信号**（main 消费即清零）；
   把它做成电平信号，就把"有一个待处理的发车请求"和"正在跑迷宫"两件事
   混进了同一个变量。
2. `LESSON_Blind8()` 是 `while(1)` **永不返回**，所以发车之后**没有任何路径**能复位
   发车状态。急停只能停电机（ISR 每 1 ms 强制清速度目标），**停不掉那个循环** ——
   于是变成"车停了，但程序还在迷宫里"。

**修复（三处）：**

| 改动 | 说明 |
|---|---|
| `linkMazeReq` 改在 `LINK_MazeStarted()` 里清零 | 请求位变成边沿信号（main 消费即清） |
| **新增 `MAZE STOP`** | 带出迷宫 + 复位发车状态 + **解锁急停**；`STOP` / `ESTOP` 同样带出迷宫 |
| `LESSON_Blind8()` 加退出检查、`main()` 等待循环改为可重复 | 让"发车 → 收车 → 再发车"成立，不必断电 |

**为什么不是"清一下标志"就够**：症结不在于标志没清，而在于**主循环出不来**。
只要 `LESSON_Blind8()` 不返回，任何"清标志"都只会让主机的视图与固件实际状态不一致
（主机以为空闲了，固件其实还在迷宫循环里空转）。所以修复的落点是给迷宫循环一个
**受链路层控制的出口**（`linkMazeAbort`），再由 `main()` 复位发车状态 ——
状态复位是"循环真的退出了"的结果，而不是一个孤立的赋值。

退出前会把停车动作做干净（速度目标归零、回到自由模式、清运动任务、
`mazeState.mouseTask` 复位到 `WAIT`），不让半途的动作残留到下一轮。
`MAZE RUN` 的失败语义也一并明确化：已在跑回 `ERR_BUSY`；**急停锁存中回 `ERR_ESTOP`**
（原先会默默接受、再被 ISR 每帧清零速度，现场表现为"发了车却不动"）。

**对比赛固件零影响**：上述新增代码全部门控在 `#ifdef MOUSE_DATA_LOG` 之下。
`[5]` 档 ROM **90872 B，与改动前逐字节同尺寸**，且 `fromelf` 符号表里
`LINK_MazeFinished` / `LINK_MazeAbortRequested` / `linkMazeAbort` **一个都不存在**。

### 6.2 `dropCnt` 的用途（降为诊断量）

正常情况下**恒为 0**。非 0 说明有别的路径在抢环（如调试 `printf`），是有效的告警。

配合 `SEQ` 可区分故障类型：

| 现象 | 原因 | 该做什么 |
|---|---|---|
| `SEQ` 跳变 + `dropCnt` **增加** | 设备主动丢（本地拥塞） | 改代码/查 printf |
| `SEQ` 跳变 + `dropCnt` **不变** | 链路丢（蓝牙模块缓冲溢出） | 停等拉取器不 burst、也没有自适应窗口（§6.1.5），这类丢失在拉取模式下应极少出现；若持续如此，说明链路确实极窄或模块异常 |

> **【v2.1 真机修正】** 早先的窗口 + AIMD 版本曾把这条诊断量当作"窗口自适应"的输入
> （丢一帧就减半）。**AIMD 已删除，改为停等**：不 burst 就没有这层反馈环，`dropCnt`/`bad_crc`
> 回归纯诊断量（告警用），见 §6.1.5。

### 6.3 "最新数据"的确切语义

**采样与回传解耦**：

- MCU 内部照旧 **1 kHz 采样**供比赛算法用（不动）
- 回传每帧取**当前最新值**（是**降采样**，不是平均，不是缓存回放）

即：**发送时刻**的瞬时状态（拉取模式下即"收到 `TELEM` 那一刻"的状态）。
这正对应"确认发送成功后直接传输最新数据"。

## 8. 事件集（上行异常）

| 事件 | 触发 | 内容 |
|---|---|---|
| `STOPPED <reason> #n` | 任务结束 | `reason ∈ {TIME, IR, ESTOP, USER, END}` |
| `ESTOP TRIP #n` | 急停瞬间 | 无参数（要求**最低延迟**，不等任务收尾） |

> `MAZE EV` **不在其中** —— 已于 2026-10-05 删除，理由见 §8.4。

### 8.1 `STOPPED` 的原因码

| reason | 含义 |
|---|---|
| `TIME` | 时间护栏到 |
| `IR` | **近墙保护**：红外护栏触发 |
| `ESTOP` | 急停 |
| `USER` | `STOP` 命令 |
| `END` | 任务正常跑完 |

### 8.2 为什么保留事件（而非全并入帧）

**帧是采样（可丢），事件是通知（不可丢）**。判断规则：能"从帧的变化"推出来的才可精简。

| 事件 | 能否从帧推 | 判定 |
|---|---|---|
| `STOPPED` 的 reason | ❌ "时间到"与"红外触发"帧里区分不出 | **必留** |
| `ESTOP TRIP` | ⚠️ `flags` 有 `ESTOP_LOCK`，但延迟 4.17 ms（丢帧则 8.3 ms） | **必留**（安全） |

### 8.3 事件行序号与发送保护

**序号**：每条事件行带 `#n`（1 字节循环）。主机按 `step = (n - prev) & 0xFF` 判定：`step >= 2` 说明中间丢了 `step-1` 条 → 置"事件流不完整"标记。与帧的 `SEQ` **共用同一计数器**，故帧与事件的相对顺序也可判。

**为什么只加序号、不做 ACK / 不重发**：

| 方案 | 吞吐 | 结论 |
|---|---|---|
| 停等重发（发一条等 ACK） | 1 / 1.21 s（真机实测往返）≈ **0.83 条/s** | ❌ 实测事件率 5~6 条/s（≈167 ms/条）→ **远远跟不上**，队列必然积压 |
| 滑动窗口 | 可跟上 | ❌ 需序号 + 窗口 + 乱序重组，与"尽可能精简"冲突 |
| **只加序号** | 无额外时延 | ✅ 设备端零队列、主机零应答；丢失**可检测**（虽不可恢复，但可标记） |

> **【v2.1】** 上表"1.21 s"是**真机实测**的端到端往返（v2.0 写的是 0.230 s，偏低约 5 倍）。
> 结论不变：事件行**只加序号、不做 ACK/重发**。（v1.5.5 曾按 230 ms 算成 4.3 条/s；即便按那个偏乐观的数字，
> 结论也已是"跟不上"。）

> 序号是"可检测"，目标是**不假装完整**。真要求"不可丢"的场合（如 `ESTOP TRIP`），靠的是它**立即发 + 事件行短**，而非重发。

**发送保护**（沿用现有机制）：发送前检查 TX 空闲 ≥ `LINK_EV_NEED_SPACE`（约 64 B），不足则**丢弃并计数**（`evDrop`）→ 状态帧 `flags` 的 `EVQ` 位置 1。宁可少发，也不让长文本在拥塞时回绕覆盖。

### 8.4 为什么删除 `MAZE EV`

`MAZE EV` 是 v1.5.5 为**实验 8 走迷宫**加的事件流（8 子类：BEGIN/EXIT/TASK/ROAD/JUNC/TURN/GOAL/CELL）。当时它独有信息是因为**旧帧里没有任何迷宫状态字段**。统一帧改版后这个前提消失了：

| 原 `MAZE EV` 子类 | 统一帧里的对应字段 | 结论 |
|---|---|---|
| `TASK` 迁移 | `mazeTask`（3 bit，0–5） | ✅ 可差分 |
| `CELL` 进入新格 | `posX`+`posY`（各 4 bit） | ✅ 可差分 |
| `GOAL` 到达终点 | `posX,posY` + `goalX,goalY` | ✅ 可差分 |
| `JUNC` 岔路栈变化 | `stackIdx` | ✅ 可差分 |
| `TURN` 进入转弯 | `motionTask`（7 bit，0–107） | ✅ 可差分 |
| `BEGIN`/`EXIT` 进出迷宫 | `mazeTask` 的 WAIT↔非 WAIT 边沿 | ✅ 可差分 |
| **`ROAD` 路口分类（8 类）** | 帧内**只有** `wallLeft/Front/Right` 三位**原语** | ⚠️ **不再直接上报** |

**唯一代价**：`ROAD` 的 8 类路口判定（THRU/CORNER_L/CORNER_R/TEE_FL/TEE_FR/TEE_LR/CROSS/DEAD）是固件 20 ms 去抖后算出的**分类结果**，帧里没有。两条出路：

1. **上位机复刻判据** —— 分类逻辑简单（对三位开口做组合查表），在 PC 端按同样的去抖规则复刻，历史数据可事后重算；
2. **不分析该量** —— 若走迷宫调参只关心"状态机走到哪、动作是什么"，原语三位已够。

> 决策依据（用户 2026-10-05）：**走迷宫调参关心的是状态机与动作，不是路口分类**；且分类可由原语复刻，不值得为它单开一条不可靠的上行通道。

**丢帧时的边沿**：差分取边沿的前提是相邻帧连续。若 `SEQ` 跳变，该段差分不可信 → 上位机按"该区间边沿未知"处理，**不伪造**。

## 9. 标定流程重设计

### 9.1 现状：人机协作 + 异步提示

`CAL IRDATA` 分 **3 个相位**（`link.c:1860-1920`）：

```
phase 1: 左轮远距    → irCalib.rawlavrgfar
phase 2: 前向近距    → rawf1avrgnear / rawf2avrgnear
phase 3: 前向远距    → rawf1avrgfar / rawf2avrgfar
```

每相位采够样本后发 `CALSTEP IRDATA <phase>`，这是**"请摆下一个位置"的节拍提示**。

### 9.2 改为请求-响应

| 现在 | 改成 |
|---|---|
| 发 `CAL IRDATA 1` → 设备采集 → 主动发 `CALSTEP IRDATA 1` | 发 `CAL IRDATA 1` → **设备采够样本才回 ACK**（ACK 即"该步完成，请摆下一位置"） |
| `CALDONE IRDATA` 事件 | 最后一步的 ACK 即完成；结果值用 `GET` 读参数 |
| `CALERR <item> TIMEOUT` 事件 | ACK 的错误码 `ERR_TIMEOUT` |

**收益**：
- 5 类标定事件（`CALSTEP`×1 / `CALDONE`×4 / `CALERR`×2）全部消失
- **可靠性更高**：事件行会被 TX 空间门丢弃，而 ACK 有重发机制
- 标定节奏由上位机控制（提示摆放 → 发下一条），时序更清晰

### 9.3 长耗时命令的超时

`CAL <item> START` 要等采集完成（可能数秒）。上位机须用**更长的超时**（建议 10 s），且该命令**归入 `no_retry`**（重发无意义，副作用已产生）。

沿用既有教训（`CHANGELOG [1.5.1]`）：`no_retry` 命令的超时归属**调用者**，由 `_wait_pending()` 超时时调 `abandon()` 摘除挂起项，否则 `Pending` 永久残留。

## 10. 看门狗与异常处理

### 10.1 设备侧：IWDG 看门狗

- 启用 `IWDG`（独立看门狗，LSI 时钟，不复位时不受主时钟影响）
- 在主循环与 `SysTick` 的**健康路径**喂狗
- **风险**：喂狗点若落在长阻塞路径之后会误复位。需逐一核查现有长阻塞点（Flash 擦写、`while(1)` 迷宫循环）

### 10.2 复位原因上报

`PING` 应答带 `rst=<cause>`：

| 值 | 来源 |
|---|---|
| `POR` | 上电复位 |
| `SW` | 软件复位 |
| `IWDG` | **看门狗复位**（即"程序卡死过"） |
| `PIN` | 复位引脚 |

读取 `RCC->CSR` 的 `PINRSTF/PORRSTF/SFTRSTF/IWDGRSTF`，**读后写 `RMVF` 清标志**。

**上报时机**：`PING` 是连接后第一条命令，因此上位机一连上就能知道"设备刚复位过"。

### 10.3 上位机侧：超时判定

- 超过 N ms（建议 **500 ms**，约 120 帧）未收到任何数据帧 → 状态置"链路异常"
- 区分两种情况：**蓝牙掉线**（串口读错误/超时）与**设备卡死**（串口正常但无数据）
- 若随后 `PING` 回报 `rst=IWDG`，可确认"曾发生卡死且已自恢复"

## 13. 风险与未决

### 13.1 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **蓝牙模块缓冲溢出（MCU 不可见）** | ~~无 RTS/CTS 硬件流控，模块缓冲溢出会**帧内丢字节**→CRC 失败，而 MCU 完全不知道~~ **【v2.1 真机已复现：不只是丢字节，而是灌满后停止转发、需重新上电】** | `dropCnt` 与 `bad_crc` 联合诊断；**拉取模式把发送节奏交给上位机**（§6.1.3）—— 这是根治，因为"灌满"的前提（固件盲目全速发）已消失 |
| ~~**1 ms tick 粒度导致帧间隔抖动**~~ | ~~帧率 217 Hz 但间隔是 4 或 5 ms~~ **【v2.1：拉取模式下帧间隔由链路往返（1/RTT）决定，不再是 4/5 ms 的 tick 颗粒度】** | 可接受（`ms8` 精度即 1 ms） |
| **IWDG 误复位** | 长阻塞路径（Flash 擦写、迷宫 `while(1)`）若未被喂狗覆盖 | 逐一核查喂狗点；先只读验证不带 IWDG |
| **事件仅可检测、不可恢复** | 序号只让主机知道"丢了"，无法补回；`STOPPED` 丢失则任务结束原因不明 | 事件行短 + 立即发；主机置"事件流不完整"标记而非静默；必要时用 `PING`/帧 `flags` 交叉判断 |
| **一次性大改、无法回退** | 协议不兼容，旧上位机连不上新固件 | 归档当前版本（`v1.5.5`）作为回退基线 |
| **AIMD 已删除，改为停等** | 最初的 v2.1 实现用"滑动窗口 + AIMD"（窗口 1..16），真机实测证明**成串发必丢**（回收率随 N 掉：2 条 50%、4 条 25%、8 条 12%），已改为**严格停等**（在途恒 1）。停等复测 4.41 Hz / 丢 0；停发自愈成功（见 §6.1.5） | 已落地；`pull_smoke.py` 断言"模式为 stop-and-wait"且"在途恒不超过 1 条" |
| **链路 RTT 波动** | 真机实测 RTT 在 **143~527 ms** 间波动（停等复测的单帧往返 157~234 ms），可达帧率随之在 **4.4~6.5 Hz** 波动 | 属物理链路特性，**无法消除**；停等已做到零浪费、零丢失，波动只能接受（见 §6.1.5） |
| ~~`s32` 里程改动~~ | **已作废**：纠正后 `trackL/trackR` 单位是 mm，s16 覆盖 ±32.7 m 足够，**不改类型** | — |

### 13.2 未决问题

> 2026-10-05 已闭环三项（原 1/2/4）：`MAZE EV` **删除**、事件行**加序号**、`MAZE EV <mask>` 随事件行一并删除。

1. **`PING` 的 `txbuf` 字段**：SCOPE 取消后 `scopedepth` 已无意义，`txbuf` 是否仍要上报（用于版本指纹）？
2. ~~**波特率提升的时间点**：提高波特率会自动反映为更高帧率~~ —— **已证伪（2026-10-05 真机实测）**：
   RTT≈224 ms 中串口只占 4.6 ms，**瓶颈是蓝牙模块的转发延迟**，提波特率几乎不改变 RTT，
   因此也不会提高帧率。原判断"帧率 = 1/RTT，波特率提高会直接缩短 RTT"是错的。
   若将来真要提速，方向是**换掉蓝牙透传**（或改用有线），而不是提波特率。仍未实测模块是否支持 460800，
   且要**以真机实测吞吐为准**（不要重蹈"按 11520 B/s 推算 217 Hz"的覆辙，见 §6.1.1）。
3. **`fastwayCount` vs `fastwayCount90`**：目前只取前者，`fastwayCount90`（90° 路径动作计数）是否也要？
   ⚠️ 注意：`MAZE EV` 删除后，这类"统计量"已无上报通道 → 若需要，只能进帧（帧还剩 0 B 余量，需换字段）。
4. **`motionTask` 需 7 bit（0–107）**：若将来枚举继续扩张会溢出。当前预留 1 bit 余量，需设静态断言。
5. **`ROAD` 路口分类的去向**（由 §8.4 派生）：上位机复刻固件分类判据（§8.4 出路 1），还是干脆不分析（出路 2）？
6. **拉取器的窗口参数已取消**（v2.1 真机修正）：**AIMD 已删除，改为严格停等**（在途恒 1），
   不再有 `MIN_WINDOW` / `MAX_WINDOW` / 自适应周期；唯一可调的是单请求超时（默认 3 s）。见 §6.1.5。
7. ⚠️ **【待决策】课程实验的波形采样密度不足**（2026-10-05 真机实测发现，用户决定"暂不处理，先记着"）：
   停等拉取在真机上只有 **≈4.4 Hz**（1/RTT），而实验三（100 mm @ 50 cm/s）只跑约 200 ms
   ⇒ **只采到约 1 个点**（600 mm ≈ 5 点、1000 mm ≈ 9 点）。
   v2.0 设想的"统一帧 217 Hz ⇒ 0.2 s 内 43 点、够算 σ%/ts/tp"**不成立**，
   于是 `LessonAPI._compute` 算出的阶跃指标在真机上**不可信**。
   **v1.5.5 的 `SCOPE`（1 kHz 本地录制 + 停车后整块 `DUMP` 回传）正是为解决它而存在**；
   v2.0 删除它时依据的正是上面那个错误的 Hz 前提。
   可选出路：① 恢复最小化的"按需本地录制 + 停车后回传"（要改固件、要重烧）；
   ② 拉长实验距离换点数（治标：暂态占比变小，指标仍不可信）；③ 接受现状，只用于看趋势。
   **当前取 ③**：`lesson_smoke` 的断言已压到"攒到 ≥3 帧（只验通路，不验密度）"并打印实测密度。
