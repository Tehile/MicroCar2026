## 1. 一句话结论

**时间同步靠"三条腿"，缺一不可：**

| 腿 | 载体 | 解决什么 |
|---|---|---|
| **毫秒时基** | 固件 `linkTimeMs`（SysTick 1ms 自增，u32） | 设备侧单调时间，与链路无关 |
| **软件戳** | `TIME` 帧 @1Hz（完整 u32）+ 快帧保留字节（低 8 位） | 每秒一个绝对锚点；**每个快帧**都能落位 |
| **物理灯** | `ARM` 后 LED 以 1Hz（50% 占空）闪烁 | 供摄像头/光电/人眼**独立校核**，也能标定单程延迟 |

三者**同源同拍**：TIME 帧在 `linkTimeMs % 1000 == 0` 时发出，基准灯也在同一刻翻转。
所以"软件说到第 N 秒"与"灯正好翻转"可以互相印证。

**数据完整性靠一条结构性事实**：命令解析与遥测组帧**都在 SysTick 的 1ms 中断里**（`LINK_Tick`），
与主循环无关。因此即使主循环卡在 `LESSON_Blind8()` 的 `while(1)` 里跑迷宫，
遥测照样上行、命令照样执行 —— 数据收集可以**直接搭在阻塞式自走上，不必改造迷宫**。

## 2. 固件侧

### 2.1 第五档模式 `MOUSE_DATA_LOG`

`code_stm32f1_mouse/USER/main.h` 顶部现在是**五档（五选一）**：

```c
/* #define MOUSE_TEST_NO_MOTOR 1 */   /* [1] 安全测试模式(电机禁用) */
/* #define MOUSE_TEST_MOTOR_LAB 1 */  /* [2] 电机远程控制实验(电机可控 + 双护栏) */
/* #define MOUSE_LESSON_LAB 1 */     /* [3] 课程调参实验(剖面引擎) */
#define MOUSE_DATA_LOG 1              /* [4] 数据收集档(无记忆迷宫 + 运动控制 + 远程发车) */
/* 全部注释掉 */                      /* [5] 原比赛固件(自走 / 按键菜单 / 课程实验) */
```

四者**互斥**，同时定义两个以上会 `#error`。

| 模式 | 电机 | 自走策略 | `MOUSE_TEST_MODE` | 用途 |
|---|---|---|---|---|
| [1] `NO_MOTOR` | 禁用 | 无 | 定义 | 静态标定 / 回传 |
| [2] `MOTOR_LAB` | 可控 | 无 | 定义 | 电机远程控制（双护栏） |
| [3] `LESSON_LAB` | 可控 | 无 | 定义 | 课程调参（剖面引擎） |
| **[4] `DATA_LOG`** | **可控** | **有** | **不定义** | **数据收集（远程发车 + 采集）** |
| [5] 比赛固件 | 可控 | 有 | 不定义 | 比赛 |

> **关键**：[4] 与 [1][2][3] 的本质差别是**它不定义 `MOUSE_TEST_MODE`** ——
> 数据收集档**要跑自走策略**（运动状态机 `doTask*`、`LESSON_ISR` 都要编译进去）。
> 前三个测试档的共同点是"把可能自己跑起来的口子关掉"，而 [4] 恰恰要打开它。

`main.c` 的 [4] 分支：

```c
#elif defined(MOUSE_DATA_LOG)
    ... 传感器/电池/急停监控就绪 ...
    STATE_LoadMapAndSelectSpeed();
    STATE_DetermineGoaheadNum();
    MOTION_SetAngle(0);
    taskSt.backSearch = 1;

    /* 等上位机 MAZE RUN。注意: 采集与命令全由 SysTick 的 LINK_Tick() 完成,

    while (!LINK_MazeRequested())
        DELAY_Ms(1);

    LINK_MazeStarted();
    LESSON_Blind8();   /* 无记忆走迷宫(不返回) */
```

### 2.2 时间同步（**不依赖任何档**）

这一组在 `link.c` 里**无条件编译**，生产固件同样可用 —— 这才是"相对独立"的落点。
它只在收到 `ARM` 时才起作用，所以对既有固件的 LED 行为**零影响**。

```c
static u32 linkTimeMs;   /* 上电以来的毫秒时基；SysTick 里 linkTimeMs++，u32 可走 49 天 */
static u32 linkArmMs;    /* 发车时刻在该时基上的读数；0 = 未武装 */
static u8  linkArmed;
static u8  linkTimeLed;  /* 基准灯电平 */
```

1Hz 基准灯（在 `LINK_Tick` 最开头，与 TIME 帧同拍）：

```c
if (linkArmed) {
    u8 lv = (u8)(((linkTimeMs - linkArmMs) % 1000u) < 500u);   /* 50% 占空 */
    if (lv != linkTimeLed) {
        linkTimeLed = lv;
        LED4 = lv ? 0 : 1;   /* 低电平点亮；直接写引脚, 不走 LED_On/Off */
    }
}
```

**为什么直接写引脚？** 因为发车后 `ledBeaconLock = 1`，`LED_On/LED_Off` 全部直接返回：

```c
/* led.h */
extern u8 ledBeaconLock;   /* 由 link.c 维护: 发车后置 1 */

/* led.c */
void LED_On(u8 n)  { if (ledBeaconLock) return; ... }
void LED_Off(u8 n) { if (ledBeaconLock) return; ... }
```

这样 LED 就**完全归基准灯独占**。否则迷宫/菜单的状态灯会把这个供外部做时间对齐用的方波
搅浑 —— 而方波一旦不干净，**时间同步就废了**（光电/摄像头读到的是噪声）。
未发车时 `ledBeaconLock = 0`，LED 行为一字不变。

> **取值**：基准灯 = **LED4（PC7）**。在数据收集档里这个引脚原本是迷宫"右侧有墙"指示灯；
> 发车后它被基准灯接管（这是有意的取舍：时间基准比单灯状态重要，且状态在遥测里都有）。
> 其余模式（含比赛固件）永不进入锁定状态。

### 2.3 命令组：`ARM` / `MAZE RUN`

```text
ARM        →  ACK <seq> OK   +  异步行 `ARMED <armMs>`
MAZE RUN   →  ACK <seq> OK | ERR_BUSY | ERR_VALUE
MAZE EV …  →  ACK <seq> OK   +  异步行 `MAZE EVMASK <n>`(查询时)
MAZE RST   →  ACK <seq> OK
```

- **`ARM`** —— 发车：`linkArmed=1; linkArmMs=linkTimeMs;` 点亮基准灯并锁定 LED；
  回一行 `ARMED <ms>`（异步，与 1Hz 的 TIME 帧重复一次是有意的 —— 单条文本丢了也能自愈）。
- **`MAZE RUN`** —— 远程发车跑无记忆迷宫。固件**只置请求位**，真正的 `while(1)` 由主循环执行；
  命令处理在中断里，绝不能在 ISR 里跑迷宫。已发车过则回 `ERR_BUSY`。
- **`MAZE RUN` 只在 [4] 档有实现**：其余固件回 `ERR_VALUE` 而不是假装 OK ——
  否则主机会以为发车了，实际什么都不会跑。
- **`MAZE EV` / `MAZE RST`** —— 迷宫**状态机回传**的事件掩码与统计清零。
  发车之后"识别到弯道/岔路口/死路/终点"等状态会以 `MAZE EV …` 事件行上行，
  另有 1 Hz 的 `TYPE_MAZE(0x09)` 状态帧与 `SNAP MAZE` 点查。
  **详见 `docs/迷宫状态机回传.md`**（实验 8 无记忆走迷宫）。

> **为什么 `ARM` 与 `MAZE RUN` 分开？** `ARM` 之后**任何动作**（跑迷宫、`MOVE RUN`、
> 课程实验）都被同一个时间基准覆盖，不限于跑迷宫。这也让"先武装、确认同步收敛、再发车"
> 成为可能。

### 2.4 回传：`TIME` 帧 @1Hz + 快帧低 8 位

新帧 `LINK_TYPE_TIME = 0x08`，payload **12 字节**：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0–3 | `upMs` (u32 LE) | 上电以来的毫秒时基 |
| 4–7 | `armMs` (u32 LE) | 发车时刻；0 = 未武装 |
| 8 | `led` | 当前基准灯电平（0/1） |
| 9 | `flags` | bit0=已武装 bit1=迷宫在跑 bit2=基准灯亮 |
| 10–11 | 保留 | |

同时把**快帧的保留字节**（原来恒 0）改成时基低 8 位：

```c
f[15] = (u8)(linkTimeMs & 0xFFu);
```

单看这 1 字节只能定位到 256ms 窗口，但与 1Hz 的完整 u32 锚点配合，
就能把**每一个快帧**都钉到准确时刻 —— 而**帧长一个字节都没变**，零带宽代价。

### 2.5 1kHz dump 也带上绝对起点

`DUMP_HDR` 的 payload 由 8 字节扩到 **12 字节**，末尾追加 `startMs`(u32)：

| 偏移 | 字段 |
|---|---|
| 0–1 | `totalPts` |
| 2 | `ptsPerBlk` |
| 3 | `channels` |
| 4–5 | `filled`（实际采集点数） |
| 6–7 | `start`（写指针，回绕时用来旋转到时间正序） |
| **8–11** | **`startMs`** = 回传数组中**最早一点**的绝对设备毫秒时基 |

固件在 `link_ScopeSample()` 里记下"环里第 0 点"的时刻，发送头时换算成最早一点：

```c
link_Put32(&hdr[8], (s32)(linkScope.startMs +
                          (linkScope.cnt >= LINK_SCOPE_LEN ? (u32)linkScope.idx : 0u)));
```

上位机侧 `dump_arrays()` 于是把时间轴从"从 0 起的相对下标"换成**绝对设备时刻**：

```python
t = np.arange(len(arr), dtype=np.float64) + float(start_ms)   # t = startMs + i
```

> ⚠️ **这是一处行为变更**：`dump` 的 `t_ms` 现在是绝对设备毫秒，不再从 0 开始。
> 好处是 1kHz 数据可以直接与发车时刻、基准灯对齐；`analyze` 等按"差值"用它的地方不受影响。

## 3. 上位机侧

### 3.1 单调时钟（`host/host/clock.py`）

原工程**所有**时间戳都取自 `time.time()`（墙钟）。对"显示时间轴"无所谓，
但对时间同步是致命的 —— 一次 NTP 回拨就会让映射倒挂。因此新增：

```python
now_monotonic()   # 任何"差值/时长/映射"计算
now_wall_ms()     # 只有"给人看的时间戳"才用
```

帧的"到达时刻"由读取线程在解析完那一瞬打上（`_rx_mono`），并**跟着记录走**，
所以落盘/UI 拿到的是同一个时刻，不会被线程间延迟污染。

### 3.2 门面 `mc.timesync`（`TimeSyncAPI`）

| 方法 | 作用 |
|---|---|
| `arm()` | **发车**：记下"发出命令的单调时刻"，发 `ARM`，等 `ARMED` 回执 |
| `maze_run()` | 远程发车跑无记忆迷宫 |
| `wait_sync(samples, timeout)` | 等若干 TIME 帧到达（映射收敛） |
| `offset_s()` / `drift_ppm()` | 当前偏移估计 / 设备时钟相对频差 |
| `frame_time_up(rec)` | 把一帧换算成**设备毫秒时基**上的发送时刻 |
| `frame_time(rec)` | 换算成**本机单调秒** |
| `dev_ms(rec)` | 换算成"**发车以来毫秒**" |
| `frame_age_ms(rec)` | 这一帧从设备发出到本机收到经历了多久（**单程延迟实测**，仅 TIME 帧可用） |
| `snapshot()` / `explain()` | 状态快照 / 人可读结论 |

### 3.3 算时间的三条纯函数（可脱离硬件单测）

```python
min_delay_offset(samples)   # offset = min(t_recv - dev_ms/1000)
fit_clock(samples)          # 最小二乘 dev_s = a + b*t_recv
drift_ppm(samples)          # (b - 1) * 1e6
resolve_ms8(ms8, predicted) # 8 位 -> 完整时基(在 256 窗口里挑最接近预测的那个)
```

**为什么偏移取最小值而不是平均？** 单程延迟恒为正，平均值等于"真偏移 + 平均延迟"；
**最小值**才逼近"真偏移 + 最小延迟"。这是 NTP 里就在用的 min-filter 思想。

**为什么要估漂移？** 晶振有频差。对 `(t_recv, dev_ms)` 做最小二乘，`b-1` 就是相对频差（ppm）。
长采集不修正的话，几秒钟后毫秒级误差会累积到几十毫秒。

**8 位怎么还原成完整时基？** 以"预测值"为基准，在 `predicted + k*256`（k = -1,0,1,2）里挑与
`ms8` 同余且最接近预测的那个。只要预测误差 < 128ms 就必然选对 ——
而"最近一次 TIME 帧 + 单调时钟 + 漂移修正"的预测误差远小于此。

### 3.4 丢帧检测

原协议里帧头有 1 字节 SEQ，但**解析后被直接丢弃**，于是根本算不出丢了多少帧。
现在在帧分派处启用它（`link._dispatch_frame`）：

```python
step = (f.seq - prev) & 0xFF
if step >= 2:                      # 256 回绕天然连续, 不该误报
    counts["seq_gap"] += 1         # 间隙次数
    counts["seq_lost"] += step - 1 # 丢失帧数
```

SEQ 在固件里每发一帧 +1（全帧型共用计数器），所以"相邻两帧序号差 != 1"就是丢帧的**硬证据**。
`mc.stats()` 里因此多了 `seq_gap` / `seq_lost` 两个量。

## 4. 三个时间概念，别混淆

| 概念 | 含义 | 用途 |
|---|---|---|
| `upMs` | 固件**上电以来**毫秒 | 设备侧绝对时基 |
| `armMs` | **发车时刻**在 `upMs` 上的读数 | 把数据换算成"发车以来" |
| `dev_ms` | `upMs - armMs`，即**发车以来**毫秒 | 分析运动特性时该用的时间轴 |
| `t_host_ms` | 主机**墙钟**毫秒 | 只用于与外部记录粗对齐 |
| `offset` | `min(t_recv - upMs/1000)` | 把设备时基映射到本机单调时钟 |

**单程延迟只能估，但估得准。** 到达时刻 = 发送时刻 + 延迟，延迟未知且恒为正，
所以取最小值。因此：

- **任意两帧之间的时间差是准确的**（这正是运动特性分析需要的）；
- 绝对时刻仍差一个常数（未知的最小延迟）；
- **基准灯给出独立的延迟估计**（人/摄像头量"灯亮"与"收到 ARMED"的差），两边一比就知道估得准不准
  —— 这就是把物理灯一起做的意义。

## 6. 边界与注意

- **`MAZE RUN` 只在 [4] 档有实现**。在 [1][2][3][5] 上回 `ERR_VALUE`（不假装成功）。
- **基准灯独占 LED4**：发车后迷宫/菜单的状态灯被 `ledBeaconLock` 挡掉。这是刻意的取舍 ——
  方波干净是时间同步的前提。
- **中/慢帧没有自己的时间戳**，`dev_ms` 是用"到达时刻投影到设备时基"估的，
  会**偏大约一个单程延迟**。要精确的逐帧时刻请用快帧（带 8 位）或时间帧（带 u32）。
- **dump 的 `t_ms` 语义已变**：现在是绝对设备毫秒，不再从 0 起。
- **8 位还原要求预测误差 < 128ms**：长时间收不到 TIME 帧（>128ms 漂移）会选错窗口。
  1Hz 的帧率下正常情况远小于此；若链路长时间中断，重新同步会自动恢复。
- **时间同步不依赖测试档**，生产固件也编译进去了；但只要不发 `ARM`，它对既有行为零影响。
