## 1. 现状诊断

### 1.1 机制层已经 headless，可直接复用

实测确认以下模块**均不 import Qt**，可以在纯 Python 环境跑：

| 模块 | 职责 | 规模 |
|---|---|---|
| `protocol/codec.py` | 帧编解码、CRC16、Q16.16、流式分流解析 | 351 行 |
| `protocol/commands.py` | 命令构造、ACK 状态机、超时重发、幂等、回读校验 | 324 行 |
| `transport/ports.py` | 端口枚举、排序、方向识别 | 126 行 |
| `transport/link.py` | 双模后端、后台读取、帧分派、吞吐实测、自检 | 404 行 |
| `model/ring.py` | 三路环形缓冲、最新快照、dump 累积 | 254 行 |
| `model/session.py` | 会话目录、CSV、raw.bin、meta、报告 | 155 行 |
| `analysis/metrics.py` | 阶跃指标、跟踪误差、按任务分段 | 137 行 |

**这一层不用动。** 问题全在它上面。

### 1.2 编排逻辑被锁死在 `MainWindow` 里 ← 这是核心缺口

`MainWindow._refresh()`（`ui/main_window.py:382-409`）一个人干了六件事：

```python
def _refresh(self) -> None:
    self._drain_link_state()          # ① 链路状态队列 → 顶栏 + 日志
    self.status.refresh(); self.scope.refresh(); self.fetch.refresh()   # ② 绘图(唯一真正属于 UI 的)
    for line in self.client.drain_events():    # ③ 异步消息 → 标定向导 + 会话文本
        self.wizard.handle_async(line)
    if s: self.maze.set_position(...)          # ④ 慢帧 → 迷宫坐标
    if self.session is not None:               # ⑤ 三路遥测落盘
        self.session.write_fast(_f); ...
    self._refresh_labels()                     # ⑥ 顶栏读数 + 降级建议
```

其中 **①③④⑤⑥ 五项与界面无关**，是纯粹的业务编排。`_toggle_connect()`（235-269 行）里还埋着三条业务规则：

- 连接成功 → **自动发 `STREAM ON`**（因为固件上电默认静默）
- 断开之前 → **先发 `STREAM OFF`**（否则下次连接时模块缓冲里压着旧数据）
- 连接失败 → **不建会话目录、不改按钮状态**

`_refresh_labels()`（417-461 行）里还有"链路降级建议 + `_warned_rate` 去重状态"。

**后果**：现在要写个脚本用完整功能，必须把上面这些**重抄一遍**。`hardware_e2e_test.py` 就是被迫这么做的——这正是接口要被抽出来的直接证据。

### 1.3 三条隐式运行时契约（没人写在文档里，但漏了就坏）

| # | 契约 | 漏掉的后果 |
|---|---|---|
| C1 | 必须有人**每 20ms 调 `client.poll()`** | 超时/重发机制完全不工作，每条命令都等到 `TIMEOUT` |
| C2 | 必须有人**周期调 `client.drain_events()`** | 事件列表涨到 250 条才截断，标定向导收不到设备回话 |
| C3 | 必须有人**周期把遥测落盘**（现在靠 40Hz 定时器） | 中帧 1Hz / 慢帧 0.5Hz 时侥幸不漏，一旦升速就**成片漏数据** |

现在这三条只存在于 `MainWindow` 的实现里。C3 还有个隐藏缺陷：**按轮询快照落盘，天然会漏**——高采样率下每秒 5 个点只有最后 1 个被写进 CSV。

### 1.4 结论

接口化的实质不是"再包一层"，而是：

1. 把 `_refresh()` 里那五项编排**搬进门面**（顺带修掉 C3 的漏帧）；
2. 把 C1/C2/C3 三条契约**变成门面内部的自动行为**；
3. 把"新增功能"从"改若干处 if-else"变成"**改一张表**"，并加机制保证不漏。

## 2. 目标与非目标

### 非功能硬指标（每条都可测）

| # | 指标 | 验收方式 |
|---|---|---|
| N1 | **headless**：`host/api.py` 及其以下不 import Qt | 静态断言：`import host.api` 后 `sys.modules` 里无 `PySide6` |
| N2 | **线程安全**：任意调用者线程可调 API | 压力测试：3 线程并发 500 次 set/get |
| N3 | **push/pull 双模式**：脚本用回调、GUI 用拉取 | 两种模式各一条 e2e |
| N4 | **可阻塞**：脚本能写同步代码 | `mc.wait(pred, timeout)` 覆盖所有异步动作 |
| N5 | **无硬件可用**：除物理动作外全功能可演练 | 全部 e2e 针对 `mouse_sim` 与 `raw.bin` 回放各跑一遍 |
| N6 | **可扩展**：新增命令/帧只改一张表 | 契约测试 + lint 断言 |

### 非目标（明确排除）

- 不做跨语言绑定（C/Python 之外）
- 不做 Web UI（服务模式只提供 JSON-RPC，界面仍用现有 Qt）
- 不改协议帧格式、不改固件既有行为（唯一新增：`CAPS` 命令）
- 不做多设备并发（串口天然独占；多实例连接同一口时明确报错而不是静默竞争）

## 4. 目标架构

### 4.1 分层

```
调用者         Python 脚本 │ CLI │ JSON-RPC 服务 │ Qt GUI
                    ↓ 调用          ↑ 事件
门面层         host/api.py ── MouseClient
               · 连接生命周期（含自动 STREAM 开关）
               · 事件总线（push/pull 双模式）
               · 20ms 调度线程（poll / 事件分发 / 订阅式落盘）
               · 会话编排（目录 / CSV / raw.bin / 报告）
               · 七个子 API 分区
                    ↓
注册表层       host/registry.py ── COMMANDS 表 · FRAMES 表 · CAPS 能力协商
               · 由表生成命令方法与帧分派；新增功能只改表
                    ↓
机制层         transport · protocol · model · analysis        【零改动】
                    ↑ 可替换后端
仿真/回放      sim/mouse_sim(TCP) · replay(raw.bin)
```

### 4.2 `MouseClient` 的职责与生命周期

```python
mc = MouseClient(
    session_dir="sessions",      # 会话根目录
    auto_session=True,           # 连接后自动开会话
    auto_stream=True,            # 连接后自动 STREAM ON / 断开前 STREAM OFF
    scheduler_hz=50,             # 调度线程频率(默认 50Hz=20ms, 与固件重发超时匹配)
    telemetry_window_s=30.0,
)
```

构造时启动**调度线程**，它每 20ms 做四件事（即把 C1/C2/C3 契约内置）：

1. `client.poll()` —— 超时与重发
2. 把 `client` 的异步消息与 `Link` 的状态变更投进**事件总线**
3. **订阅式落盘**：每收到一帧就写一行 CSV（不再靠轮询，修掉 C3 漏帧）
4. 周期性任务：dump 进度事件、链路自检与降级建议（带去重）

`connect()` 内部顺序（把 `_toggle_connect()` 的业务规则固化）：

```
open backend → 成功? ──否──→ 发 STATE=ERROR 事件，不开会话，返回 False
                 │
                 是
                 ↓
          开会话目录 → 自动 STREAM ON → 后台发 PING/VER/CAPS 做能力协商
```

`disconnect()`：先 `STREAM OFF` → 关 session（写 `meta.json`）→ 关后端。

### 4.3 子 API 分区（签名级）

```python
# ── 连接 ───────────────────────────────────────────────
mc.connect("COM7")                       # 简写
mc.connect(Target.serial("COM7", 115200))
mc.connect(Target.tcp(5555))             # 模拟器
mc.disconnect()
mc.is_connected -> bool
mc.device -> {"proto":2, "fw":3, "mazetype":7, "commands": {...}}
mc.caps("CAL") -> bool                   # 固件是否支持某命令(能力协商结果)

# ── 事件 ───────────────────────────────────────────────
mc.on(Event.TELEMETRY, cb)      # cb(stream, rec)
mc.on(Event.TEXT, cb)           # cb(line)
mc.on(Event.STATE, cb)          # cb(state, detail)
mc.on(Event.ERROR, cb)
mc.on(Event.DUMP_PROGRESS, cb)  # cb(frac, got_blk, total_blk, eta_s)
mc.on(Event.DUMP_DONE, cb)
mc.on(Event.MAP, cb)
mc.on(Event.ADVICE, cb)         # 链路降级建议(去重后)
mc.drain_events() -> list[Event]   # pull 模式, GUI 用
mc.wait(pred, timeout=10)          # 通用阻塞; pred() 为真即返回

# ── 遥测 ───────────────────────────────────────────────
mc.telemetry.latest()                  # (fast, mid, slow) 三个 dict
mc.telemetry.history("fast", seconds=10)   # -> (t: ndarray, data: ndarray, channels)
mc.telemetry.stats()                   # 帧计数/吞吐/CRC/失步
mc.telemetry.self_check()              # {need_bps, got_bps, level, suggest_rate}

# ── 参数 ───────────────────────────────────────────────
mc.params.get_all() -> dict[str, float]
mc.params.get("TRACKL") -> float
mc.params.set("TRACKL", 53.2015) -> Result    # 含 ACK + 回读校验
mc.params.set_many({"TRACKL": ..., "TRACKR": ...}, derive_speed=True)
mc.params.readback("TRACKL") -> int | None    # Q16.16 原始值
mc.params.backup() -> path                    # 导出 csv
mc.params.save() -> Result                    # 写 Flash(前自动备份)
mc.params.reset() -> Result

# ── 标定 ───────────────────────────────────────────────
mc.calib.items() -> list[str]                 # 按固件 CAPS 裁剪
mc.calib.run("GYRO") -> CalibResult           # 各分项: gyro/walldist/irdata/gyroratio/encangle
mc.calib.step("IRDATA", "SAMPLE") -> Result   # 手工单步
mc.calib.report(path=None) -> path            # 写 calib/report.md

# ── 开环移动（标定辅助）────────────────────────────────
mc.move.forward(pulses=10000, speed=0) -> Result
mc.move.rotate(pwm=3000, ms=1500) -> Result
mc.move.servo("SWEEP") -> Result

# ── 示波器 / dump ──────────────────────────────────────
mc.scope.start(); mc.scope.stop()
arr = mc.scope.fetch(timeout=180, on_progress=cb)   # 阻塞直到完整回传
mc.scope.last() -> DumpArrays | None
mc.scope.progress() -> (frac, eta_s)

# ── 迷宫 ───────────────────────────────────────────────
mc.maze.fetch(timeout=10) -> dict     # MAP DUMP + 阻塞等待
mc.maze.grid() -> list[list[int]]
mc.maze.position() -> (x, y, direction, mouseTask)

# ── 分析（纯离线，不需要连接）──────────────────────────
mc.analyze.step(t, y, target=...) -> dict
mc.analyze.segments(t_ms, task) -> list[dict]
mc.analyze.summary(arr) -> list[dict]      # 每段指标汇总

# ── 会话 ───────────────────────────────────────────────
mc.session.open(name=None); mc.session.close(); mc.session.path
mc.session.note("换电池后重测")

# ── 逃生舱（保证不被接口束缚）──────────────────────────
mc.send_raw("GET ALL", wait=True) -> Result
```

**设计原则**：所有会等设备应答的方法默认 `wait=True` 并带超时；需要异步时传 `wait=False` 拿 `Pending`。这样脚本能写直线代码，GUI 能保持非阻塞。

### 4.4 线程模型

```
读取线程 (Link)       read → raw.bin → parser → store / client        [原有]
调度线程 (MouseClient) poll / 事件投递 / 订阅式落盘 / 周期任务          [新增]
调用者线程           调 API；wait=True 时用 Condition 阻塞等待         [调用者]
```

- 调度线程是**唯一**的事件生产者，所以订阅回调不跑在读取线程里 —— 调用者无需担心"回调里读 store 是否死锁"。
- `wait()` 用 `threading.Condition` 实现，`Pending` 完成时通知；无忙等。
- 回调仍在调度线程执行，因此**回调里不得调用 `wait=True` 的方法**（会自锁）—— 文档明确写出并加运行时检测（在调度线程上调用阻塞方法时抛 `ReentrancyError`）。

### 4.5 事件模型

统一事件类型（`Event` 枚举），push 与 pull 共用同一份队列：

| 事件 | 载荷 | 用途 |
|---|---|---|
| `TELEMETRY` | `(stream, rec)` | `fast` / `mid` / `slow` 帧 |
| `TEXT` | `line` | 设备 `printf` 与 `ACK` 之外的文本 |
| `STATE` | `(state, detail)` | 链路状态变更 |
| `ERROR` | `(kind, msg)` | 打开失败 / 读错误 / 解码错误 |
| `DUMP_PROGRESS` | `(frac, got, total, eta)` | 1kHz 回传进度（约 60 s，必须有反馈） |
| `DUMP_DONE` | `arrays` | 回传完成 |
| `MAP` | `dict` | 墙图 |
| `ADVICE` | `(level, suggest_rate)` | 链路降级建议（去重） |

**GUI 用 pull**（`drain_events()` 在 Qt 主线程），**脚本用 push**（`on()`），二者可同时用。

## 5. 扩展性保证（五条硬机制）

这是"未来新功能也要保证这一点"的落点。前四条是**机器强制**，第五条是流程。

### E1 单一登记点：新增功能只改一张表

```python
# host/registry.py
@dataclass(frozen=True)
class CommandSpec:
    name: str            # API 名:      "params.set"
    wire: str            # 线上模板:    "SETQ {name} {q}"
    args: tuple[str, ...]
    ack: bool = True
    since: str = "1.0"   # 引入版本
    needs: tuple[str, ...] = ()   # 依赖的固件能力 tag

COMMANDS: dict[str, CommandSpec] = {
    "ping":        CommandSpec("ping", "PING"),
    "params.set":  CommandSpec("params.set", "SETQ {name} {q}", ("name", "q")),
    "scope.fetch": CommandSpec("scope.fetch", "SCOPE DUMP"),
    ...
}

@dataclass(frozen=True)
class FrameSpec:
    type: int
    name: str
    decoder: Callable[[bytes], dict]
    stream: str          # fast/mid/slow/dump/map/evt
    since: str = "1.0"

FRAMES: dict[int, FrameSpec] = {
    TYPE_FAST: FrameSpec(TYPE_FAST, "FAST", decode_fast, "fast"),
    ...
}
```

配套两条断言（进 CI）：

- **`link.py` / `api.py` 里不得出现 `TYPE_` 字面量**（帧分派必须走 `FRAMES`）；不得出现裸命令字符串（必须走 `COMMANDS`）。
- 新增 `since` 版本时，`docs/api_reference.md` 自动重新生成 —— 文档漂移在结构上不可能。

帧分派改造（`link.py:_dispatch_frame`，唯一需要动的机制层代码）：

```python
spec = FRAMES.get(f.type)
if spec is None:
    self.counts["unknown_frame"] += 1     # 前向兼容: 固件加新帧, 旧主机不报错
    return
self.store.push(spec.stream, spec.decoder(f.payload))
```

这一处改动同时带来**前后兼容**：固件升级加了新帧类型，未升级的主机静默忽略而不是抛异常。

### E2 固件侧清单自动比对 ← 跨语言项目最关键的一条

固件是 C、主机是 Python，两侧的常量/命令名**没有编译期约束**。加一个脚本：

`host/tools/sync_check.py` 解析：

- `HARDWARE/link.h` 的 `#define LINK_P_*`、`LINK_TYPE_*`、`LINK_SCOPE_*`
- `HARDWARE/link.c` 里的命令字符串表
- `HARDWARE/line.h` 的 `LINK_FAST_LEN` 等载荷长度

与 `host/registry.py` 的 `COMMANDS` / `FRAMES` / `params.PARAM_IDS` 逐项 diff。不一致 → 测试失败并打印差异表。

**效果**：固件加了命令但主机没登记 / 主机登记了固件里没实现 / 参数 id 错位 —— 全部在**提交时**发现，而不是在实机上浪费一小时。

### E3 契约测试

`host/contract_test.py` 遍历注册表：

- 每条 `CommandSpec` → 在模拟器上发一次 → 断言收到 `ACK ... OK`
- 每个 `FrameSpec` → 断言"编码→解析"往返一致，且模拟器能产出该帧
- 每个 `PARAM_IDS` → 断言模拟器可读写且回读一致

**覆盖率断言**：注册表条目数 ≥ 固件清单条目数。新功能若没进表，这条就红。

### E4 能力协商（`CAPS`）

固件新增一条命令（约 20 行）：

```
> CAPS #7*CRC
< CAPS 18 PING VER GET SETQ SAVE RESET TARE CAL SCOPE RATE TEXT MAP MOVE STREAM STOP ESTOP
```

主机连上后自动拉取，`mc.caps("CAL")` 据此回答。行为差异：

| 场景 | 现在 | 接口化后 |
|---|---|---|
| 主机构建了按钮，固件不支持该命令 | 发出 → 等 5×200ms → `TIMEOUT`，日志难读 | `mc.caps()` 提前为假，**UI 直接置灰**，API 返回 `Unavailable` |

这解决一个真实痛点：**固件与主机版本不同步时**，现在是"点了没反应，1 秒后报超时"，以后是"按钮灰着，鼠标悬停告诉你固件不支持"。

### E5 API 版本契约与文档自动生成

- `host/__init__.py` 导出 `API_VERSION`（语义化版本），与固件 `proto` 分开
- 每个 API 方法带 `since`；破坏性变更只允许新增 `_v2` 名称 + 弃用期
- `docs/api_reference.md` 由 `registry.py` + docstring 生成，**手写文档不再是真相来源**
- `host/CHANGELOG.md` 记录每次 API 变更

## 6. 四种调用形态

### 6.1 Python SDK（主形态）

```python
from host.api import MouseClient, Event

with MouseClient.connect_to("COM7") as mc:      # 上下文管理器, 退出自动断开+收会话
    mc.wait(lambda: mc.telemetry.latest()[0], timeout=5)   # 等首帧

    print(mc.device)                            # 能力协商结果
    print(mc.params.get_all())

    # 参数: 一个物理量一个来源, speedRatio 自动派生
    mc.params.set("TRACKL", 53.2015)
    mc.params.save()

    # 标定
    r = mc.calib.run("GYRO")                    # 鼠保持静止, 内部采 1.5s
    print(r.value, r.ok, r.note)

    # 跑一次动作, 停车后拉完整波形
    mc.scope.start()
    mc.move.forward(pulses=10000, speed=40)
    mc.wait(lambda: mc.telemetry.latest()[0].get("speedL") == 0, timeout=10)
    mc.scope.stop()
    arr = mc.scope.fetch(on_progress=lambda f, eta: print(f"{f:.0%} ~{eta:.0f}s"))

    for seg in mc.analyze.summary(arr):
        print(seg["task_name"], seg["metrics"])
```

**这一段的含义**：上面 20 行覆盖了 A–J 全部功能组，且没有任何"记得每 20ms 调一次"的隐藏要求。

### 6.2 CLI（脚本化与随手验证）

```
python -m host.cli ports --json                      # 端口清单(含方向判断)
python -m host.cli connect COM7 --stream --record     # 连接+开流+录会话
python -m host.cli get TRACKL --json
python -m host.cli set TRACKL 53.2015 --save
python -m host.cli calib gyro
python -m host.cli scope fetch --out dump.csv
python -m host.cli maze --out map.json
python -m host.cli diagnose COM7                      # 现 diag_port.py 的能力
python -m host.cli scan-baud COM7                      # 现 scan_baud.py
python -m host.cli replay sessions/2026-09-27_0132 --analyze
```

**约定**：每个子命令 = 一次 API 调用；`--json` 输出结构化结果。这让 **CLI 本身成为机器可调用的接口**，不需要 Python 环境也能用（例如 shell 脚本、或其他语言的 subprocess）。

### 6.3 服务模式（JSON-RPC 2.0 over WebSocket）

```
python -m host.cli serve --port 8765 --connect COM7
```

```
→ {"jsonrpc":"2.0","id":1,"method":"params.set","params":{"name":"TRACKL","value":53.2015}}
← {"jsonrpc":"2.0","id":1,"result":{"ok":true,"applied":53.2015,"readback":3486614}}
推送 ← {"jsonrpc":"2.0","method":"event","params":{"kind":"telemetry.fast","data":{...}}}
```

**关键设计**：方法名 = API 路径，**由注册表自动导出**。所以 E1 保证的事情在这里自动成立 —— 新增一个 `CommandSpec`，服务接口立刻多一个方法，一行代码不用写。

用途：远程操作（笔记本连鼠、台式机分析）、跨语言调用、以及将来接自动化流程/Agent。

**约束（要写进文档）**：串口独占。服务模式与 GUI **不能同时连同一个口**；同进程内应共享同一个 `MouseClient` 实例。

### 6.4 离线回放 —— 让"支持全部功能"在无硬件时可验证

`raw.bin` 里已经是完整的原始字节流（这正是当初刻意保留它的原因）。回放器只需实现与 `_SerialBackend`/`_TcpBackend` **相同的三个方法**（`read/write/close`），`Link` 一行都不用改：

```python
class _ReplayBackend:
    def read(self, n: int) -> bytes: ...   # 按原始时间戳释放字节, 可加速/减速
    def write(self, data: bytes) -> None: ...   # 丢弃(或记录为"当时发出的命令")
    def close(self) -> None: ...
```

于是 `Target(kind="replay", path="sessions/xxx/raw.bin")` 就能：

- **无硬件跑通 A–J**（含标定流程的逻辑路径、dump 分析、指标计算）
- **历史数据复算**：协议改了也能用新解析器重跑旧数据
- **回归测试的黄金数据**：把一次真实跑车录下来，当成固定测试用例

这是"接口支持全部功能"这句话唯一能在今天（硬件不稳定、链路只有 152 B/s）被**实际验证**的途径。

## 7. 迁移路径

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1 门面骨架** | `api.py`：调度线程、事件总线、会话编排、A–J 全部子 API 收口 | N1–N4 通过；`mc` 端到端脚本在模拟器上跑通 A–J |
| **P2 注册表与契约** | `registry.py`、`link.py` 改查表、`contract_test.py`、`sync_check.py`、固件加 `CAPS` | E1–E4 全绿；改一张表新增一条命令，两侧自动同步 |
| **P3 CLI** | `cli.py` 覆盖常用子命令 + `--json` | 每条子命令各一条冒烟；输出可被 `jq` 解析 |
| **P4 回放** | `replay.py` + `Target(kind="replay")` | 用现存会话目录回放，指标与当初一致 |
| **P5 服务模式** | `service/` JSON-RPC + 方法自动导出 | 远程调用全部 API；新增命令后服务方法自动出现 |
| **P6 UI 改造** | `MainWindow` 改为门面的消费者 | `uismoke.py` + `hardware_e2e_test.py` 全绿，行为无变化 |

**P6 放最后，理由**：它是唯一有回归风险的一步，而且**前面几步做完后 UI 不改也能正常工作**（门面与 UI 并存，UI 暂时继续走老路径）。但长期必须做 —— 否则编排逻辑有两份，必然漂移。

**P6 的护栏**：现在的 `uismoke.py`（离屏截图）与 `hardware_e2e_test.py`（15 项断言）是现成的回归网。改造前先把它们扩到"覆盖每个面板"，改完必须全绿。

| # | 风险 | 对策 |
|---|---|---|
| R1 | P6 改 UI 引入回归 | 先扩充冒烟测试到每面板；P1–P5 期间新旧并存，随时可回退 |

| R7 | 蓝牙链路 152 B/s 的物理限制仍在 | 接口层不解决，但把"实时看状态 / 停车拉数据"的分工固化进 `mc.scope.fetch()` 的语义与进度事件，让调用者不会误以为可以实时拉 dump |
