# 电机远程控制实验与双流数据传输

> 适用阶段：**电脑鼠轮子悬空**（不会真正跑动），需要远程让电机转一下、验证"命令 → 动作"闭环，
> 并且**在一条几百 B/s 量级的窄链路上同时看到两件事**：
> ① 运动进行中的**实时流**（证明"真的在动"）；② 运动结束后的**高分辨率日志流**（看"动得怎么样"）。
>
> 相关代码：固件 `USER/main.h`（模式开关）、`HARDWARE/link.c|h`、`HARDWARE/isr.c`、`HARDWARE/motor.c`；
> 上位机 `host/host/api/lab.py`、`host/host/api/move.py`、`host/host/motor_test.py`。
> 设计出处：`docs/蓝牙上位机设计方案.md` **§5.5（1 kHz 环形缓冲协议）**、附录 F（吞吐悬崖与能力边界）。
>
> ⚠️ **v2.0 传输模式重构（2026-10-05 决策）废止了本文的核心机制「双流」，本文作为 v1.x 历史记录保留，不再更新**：

## 1. 一句话结论

电机能不能动、什么时候必须停，**全部由固件的 1 ms 中断说了算**，上位机只是"发命令 + 看数据"。

- 上位机进程被 kill、Ctrl+C、蓝牙掉线 —— 电机**照样**按护栏停；
- 急停是一条**随时可用、无需任何前置条件**的命令，且**锁存**：不显式复位，谁也再动不了它。

这就是本阶段"确保可靠"的全部含义。

## 2. 三个护栏（都在固件里）

| # | 护栏 | 触发条件 | 默认 | 关闭方式 | 判定位置 |
|---|---|---|---|---|---|
| 1 | **时间** | 运行时长 ≥ 设定值 | **2000 ms（2 s）** | 不可关闭（上限 60000 ms） | `link_MoveService()`，1 ms 周期 |
| 2 | **红外** | 四路红外**任一路** < 阈值 | **10 mm（1 cm）** | `ir_mm` 传**负值** | 同上 |
| 3 | **急停** | 收到 `ESTOP`（或按键急停） | 常备 | 只能靠 `STOP` 解锁 | `isr.c` 急停分支 + 命令处理 |

三条护栏互不依赖、逐条独立判定，**任一条成立即停车**；判定结果写进 `MOVEDONE RUN` 明细（见 §3.3）。

**为什么红外取"四路最小值"而不是只看前方两路？** 轮子悬空时车体姿态任意，侧向贴障碍同样危险；
本实验要证明的正是"**任何一路贴脸都能停**"。见 `link_MinIr()`。

## 3. 固件侧

### 3.1 模式开关（五选一）

`code_stm32f1_mouse/USER/main.h` 顶部现在是**五档**（本文写时是三档，后来为课程调参、数据收集各加了一档）：

```c
/* #define MOUSE_TEST_NO_MOTOR 1 */  /* [1] 安全测试模式(电机物理禁用) —— 标定/回传阶段 */
#define MOUSE_TEST_MOTOR_LAB 1      /* [2] 电机远程控制实验(电机可控 + 双护栏) —— 本阶段 ← 当前 */
/* #define MOUSE_LESSON_LAB 1 */   /* [3] 课程调参实验(电机可控 + 课件剖面引擎) */
/* #define MOUSE_DATA_LOG 1 */     /* [4] 数据收集档(含自走策略 + 远程发车) */
/* 全部注释掉 */                   /* [5] 原比赛固件(自走、按键菜单、课程实验) */
```

- 三个宏**互斥**，同时定义两个以上会 `#error`；
- 任一被定义即派生 `MOUSE_TEST_MODE`，用来统一包住"无自走菜单"的测试分支
  （`isr.c` 的 `switch(motionCtrl.task)` 与 `LESSON_ISR()` 被它跳过）；
- **[2] 与 [1] 的关键区别**：`MOTOR_PwmInit` / `MOTOR_LoopControl` 的 `#ifdef` 只看
  `MOUSE_TEST_NO_MOTOR` —— 所以 [2] 下**电机走正常 PWM 闭环路径**，是可动的；
- **[3] 与 [2] 一样电机可控**，差别是 [3] 多一层剖面引擎、电机六增益变成运行时变量
  （文档见 `docs/课程调参实验与参数设定.md`）。[2] 与 [4] 用的是 `motor.h` 的编译期红线常量。

### 3.2 命令：`MOVE RUN`

```text
MOVE RUN <spL> <spR> [<ms>] [<ir_mm>] [#seq] *CRC16
```

| 参数 | 含义 | 缺省 | 边界 |
|---|---|---|---|
| `spL` `spR` | 左右轮目标速度 cm/s（可正可负可 0，**不能同时为 0**） | 必填 | ±300，超限 → `ERR_VALUE` |
| `ms` | 最长运行时间（护栏 1） | 2000 | 1…60000，超上限截断 |
| `ir_mm` | 红外停车阈值 mm（护栏 2） | 10 | **负值 = 关闭红外护栏**；≤0 且非负者按默认 10 处理 |

**拒绝规则（`ERR_*`，不执行）**：

- `ERR_ESTOP` —— 急停锁存中，任何 `MOVE`/`CAL` 一律拒；
- `ERR_BUSY` —— 正在跑别的运动 / 标定；
- `ERR_VALUE` —— 速度超限或左右同时为 0。

命令处理做的事（`link.c` MOVE RUN 分支）：

1. `speedSt.freemode = 0`、把 `speedTargetL/R` 设为目标 —— 电机进入闭环；
2. 记下左右轮里程起点 `runStartL/R`、时长上限、红外阈值；
3. **顺手开启本地 1 kHz 记录**：`flashSt.flashenable = 0`（独占 `run_data[]`，挡住既有黑匣子写）
   + `linkScope.state = LINK_SCOPE_RUN` —— 这就是"双流"里的**日志那一路**，全程**零带宽占用**；
4. `linkLogReady = 0`（清掉上一轮的"日志就绪"提示）。

### 3.3 明细回传：`MOVEDONE RUN`

停车时（无论哪条护栏触发）固件上行**一行文本**：

```text
MOVEDONE RUN <REASON> <ms> <ir_min> <chan> <dL> <dR> <vpkL> <vpkR>
```

| 字段 | 含义 |
|---|---|
| `REASON` | `TIME` / `IR` / `ESTOP` / `STOP` / `USER` |
| `ms` | 实际运行时长 |
| `ir_min` / `chan` | 全程四路红外最小值，及来自哪一路（`F1/F2/L/R`） |
| `dL` `dR` | 左右轮本次里程（编码器脉冲） |
| `vpkL` `vpkR` | 左右轮**实测速度峰值** cm/s |

用文本行而不是新帧型：一次运动只有一行，低频；零帧开销，且能复用既有的异步文本解析通路。
`vpkL/vpkR` 是**"电机确实响应了"的客观证据** —— 比"命令发出去了"强得多，
轮子悬空时尤其重要。上位机 `parse_movedone_run()` 对短行**容错**（缺字段给 `None`，不抛异常）。

### 3.4 急停：`ESTOP` / 解锁：`STOP`

**`ESTOP`（随时可用）** 在 `link.c` 的处理：

1. 若正在 `MOVE RUN`，先按 RUN 格式补一行 `MOVEDONE RUN ESTOP …`（让上位机拿到统一明细）；
2. 停车：`speedTargetL/R = 0`、`freemode = 1`、清任务与标定子状态；
3. **置锁存** `linkEStop = 1`，并保留日志（`linkLogReady = 1`）—— 刚急停正是最想看现场波形的时刻；
4. 主动上行一行 `ESTOP TRIP`，让上位机**不必等到下一帧快帧**就知道出事了。

**锁存的威力**：`linkEStop == 1` 时，`MOVE RUN` / `MOVE FWD` / `MOVE ROT` / `CAL GYRORATIO` /
`CAL ENCANGLE` **全部**返回 `ERR_ESTOP`，直到显式 `STOP`。这是"确保随时在于掌控之中"的硬保证。

**`STOP` = 唯一的解锁入口**，同时兼任"正常停车"：清 `linkEStop`、`emergMon.active/delay`、
`sleepmode`（测试模式下）。

**硬件级冗余**：主机没来得及发 `ESTOP` 时，`isr.c` 里原有的急停按键分支也会调
`LINK_EStopTrip()`（**幂等**，重复调用无副作用）。所以"停车"这件事有两条独立路径：
命令路径与按键路径，都对链路层生效。

### 3.5 两个新的快帧状态位

快帧 flags 字节（`link_Flags()`）新增两位，让上位机**一眼可见**而无须额外查询：

| 位 | 宏 | 含义 |
|---|---|---|
| bit6 | `LINK_FLAG_ESTOP_LOCK` (0x40) | 急停**锁存**中（区别于 bit2 的"本次上电触发过一次") |
| bit7 | `LINK_FLAG_RUNLOG` (0x80) | 运动日志**已就绪**：1 kHz 环已冻结，可直接 `SCOPE DUMP` |

上位机 `mc.estop_locked` / `mc.log_ready` 两个属性直接读它们。

## 4. 双流：为什么必须分时

### 4.1 带宽账（硬约束）

**先看上限**：USART1 固定在 115200-8-N-1（`BRR=0x271`），MCU↔模块一侧理论上限 = **11520 B/s**。

**再看真机实测**（CH340 + 蓝牙透传，2026-09-27）：

| 场景 | 实测速率 | 说明 |
|---|---|---|
| 常驻遥测（快 5 Hz + 中 1 Hz + 慢 0.5 Hz） | **≈152 B/s** | 这是**刻意压低的预算**，留了约 9× 余量 |
| 1 kHz 日志回传（`SCOPE DUMP` 短促突发） | **≈1.38 KB/s** | 9.8 KB 在 **7.1 s** 内传完，两次重复完全一致 |

即链路**突发**能到 ~1.38 KB/s（约为 UART 上限的 12%，典型的廉价 BLE 透传水平），
而 152 B/s 是**长时间常驻**才用的保守预算。二者不矛盾：前者是短促突发，后者是持续占用。

> ⚠️ 早期笔记里"超过 152 B/s 会把模块缓冲灌满、彻底静默"的结论**需要重新验证**：
> 改用独立读线程持续抽干串口后，真机上连续回传未出现静默。更可能的原因是
> **上位机抽干不够快**（轮询式读取），而非链路硬顶。在做真正的持续压测
> （风险：若真灌满需给模块重新上电）之前，常驻预算仍按 152 B/s。

**但这不影响"分时"的结论** —— 一次 dump 是 **~9.8 KB**（20 块 × 490 B，固定），
即便按 1.38 KB/s 也要 **7.1 s** 才传完，而一次动作本身通常只有 2 s。
**运动时若同时拉日志，实时性直接没了。**
结论：**实时流与详细日志只能分时**。

### 4.2 时间线

```text
        ┌──────────── 运动进行中（≤ ms，默认 2 s）────────────┐   ┌── 停止后 ──┐
链路    │ 只跑实时流：快/中/慢帧 ≈152 B/s，看"有没有在动"    │   │ 回传日志流 │
固件    │ MOVE RUN 一开始就在本地 1 kHz 写 run_data[]        │   │ 环已冻结   │
        │ （零带宽！这是关键：高分辨率记录不占链路）          │   │ SCOPE DUMP │
        └────────────────────────────────────────────────────┘   └────────────┘
                                                          ~9.8 KB (20 块 × 490 B, 固定)
停止那一刻：目标速度归零 + freemode=1（电机停）
            + SCOPE 由 RUN→FROZEN（冻结环，DMA 才能安全读）
            + linkLogReady=1（flags bit7，告诉上位机"可以拉日志了"）
            + 上行 MOVEDONE RUN …（明细）
```

**分工口诀**：实时流看"有没有在动"，日志流看"动得怎么样"；两者分辨率差两个数量级
（实测一次 0.6 s 动作：实时流 6 点 ≈ 9.7 Hz，日志流 599 点 = 1000 Hz，**约 100 倍**）。

### 4.3 谁负责哪一半

| 环节 | 责任方 |
|---|---|
| 运动期间的高分辨率记录 | **固件**（`run_data[]`，1 kHz，零带宽） |
| 运动期间的实时预览 | 固件三路遥测帧 + 上位机采样 |
| 停止判定（时间/红外/急停） | **固件 1 ms ISR** —— 不依赖上位机 |
| 冻结日志、置就绪位 | **固件**（`link_MoveFinishRun`） |
| 停止后拉取 + 存盘 + 分析 | 上位机（`scope.fetch()` → CSV → `analyze.explain()`） |

原则：**能放固件的判定/记录，就不放上位机**。上位机越"薄"，实验越可靠。

## 5. 上位机用法

### 5.1 门面 API（`mc.lab`）

```python
from host.api import MouseClient

with MouseClient.connect_to("COM7") as mc:      # 退出自动断开
    st = mc.lab.status()                        # 只看状态, 不动
    print(st["motor_disabled"], st["estop_locked"], st["ir_min"])

    r = mc.lab.run(                             # 一次完整双流实验(阻塞)
        sp_l=40, sp_r=40,                       # 左右轮 cm/s(反向=原地转)
        ms=2000,                                # 时间护栏
        ir_mm=10,                               # 红外护栏; 负值=关闭
        fetch_log=True,                         # 停止后自动回传 1kHz 日志
        realtime_hz=5.0,                        # 运动期间实时采样频率
        on_sample=lambda rec: print(rec["t"], rec["speedL"]),
        on_progress=lambda f, eta, bps: None,   # 日志回传进度(调度线程)
    )
    print(r.ok, r.reason, r.elapsed_ms, r.ir_min, r.ir_chan)
    print(r.realtime["approx_bps"], r.log_points, r.log_seconds, r.warning)

    mc.lab.estop()                              # 随时急停(锁存)
    mc.lab.resume()                             # STOP: 正常停车 + 解锁
```

`RunResult` 里既有**动作结果**（`reason/elapsed_ms/ir_min/dR/peak_l…`），
也有**两条流各自的观测量**（`realtime` 统计 + `samples` 列表、`log_points` / `log_arrays` / `log_seconds`）。
门面在实验前还会**主动拦截**两种"看起来像没反应"的坑：

- `MOTOR_DISABLED` —— 设备刷的是安全固件（[1]），电机恒 0；直接返回，不空等；
- `ESTOP_LOCKED` —— 设备处于急停锁存；提示先 `resume()`。

以及一个 `warning`：**开跑前就已有红外读数 < 阈值**（动作会在第一个周期被护栏停掉，省掉一次现场排查）。

## 6. 现场操作流程（轮子悬空）

1. `USER/main.h` 里确认 **`MOUSE_TEST_MOTOR_LAB` 打开、且 `MOUSE_TEST_NO_MOTOR` 注释掉**；Keil 编译下载。
2. 先**只看不动**，确认设备侧一切正常：

   ```bash
   python -m host.motor_test COM7 --status
   ```

   期望看到 `电机 可控`、`急停锁存 否`、四路红外有读数。

3. 正式实验（**一只手放在 `--estop` 上**）：

   ```bash
   python -m host.motor_test COM7 --sp 40 --time 2 --ir 10 --out run.csv --out-realtime rt.csv
   ```

   - 观察实时流是否出现"目标 → 实测速度"跟随（证明电机真的响应了）；
   - 期望结束时停止原因 = `TIME`（若红外先触发则是 `IR`，说明传感器前方有障碍）；
   - 结束后自动回传 1 kHz 日志并打印两条流的**分辨率对比**。

4. 需要中途停：**Ctrl+C** —— 程序会立即发 `ESTOP`（固件侧另有护栏，不会失控）。
5. **急停之后必须显式复位**才能再动：

   ```bash
   python -m host.motor_test COM7 --resume      # = STOP, 正常停车 + 解锁
   ```

> 无 GUI 的终端同样能跑：`motor_test` 只依赖 `host` 包，不需要 PySide6。
> 若想同时用图形/仪表盘盯数据，另开 `python -m host.monitor COM7`。

| 项目 | 实测值 |
|---|---|
| 停止原因 | **TIME @ 2000 ms**（时间护栏精确到时） |
| 实测峰值 | L **46** / R **50** cm/s（命令 40 —— 电机确实响应了） |
| 实时流 | ≈152 B/s 量级，坏 CRC 0 |
| **日志回传** | **1200 点 / 9.8 KB，用时 7.1 s**（两次重复一致）→ **≈1.38 KB/s** |

**两个只有真机才暴露的事实**：

1. **dump 时长基本固定**：`link_DumpService()` 无条件把 20 块（`blk` 0→19）全发完再发 `END`，
   与"实际采到多少点"无关；上位机再按 `filled` 截断。所以 0.6 s 与 2 s 的动作，回传耗时都是 **~7.1 s**。
2. **短动作期间红外会抖**：一次运行中 R 路瞬时读到 **8 mm** 并触发红外护栏（124 ms 就停）。
   数秒后复测四路均回到 249 mm —— 说明这是**电机转动时的瞬时读数**，并非真障碍。
   悬空实验若要跑满时间，可把 `ir_mm` 设为**负值**临时关掉红外护栏。

## 8. 边界与注意

- **日志长度随动作时长自适应**：1 kHz 环深 1200 点 = 1.2 s。动作短于 1.2 s 时，
  回传点数 ≈ 时长×1000（如 0.6 s → 599 点），**不是固定 1200**。这是正确行为（`dump_arrays()` 按 `filled` 截断）。
  但**线上传输量是固定的**（20 块 × 490 B ≈ 9.8 KB），因此回传耗时恒为 **~7.1 s**，与动作长短无关。
- **红外只走 0.5 Hz 慢帧**：短于 ~2 s 的动作，实时流里可能整轮都没刷新到红外 →
  终端显示 `—`。**动作内**的全程最小红外由固件在 1 kHz 上统计，随 `MOVEDONE RUN` 一并给出，不丢。
- **`ir_mm` 用负值关闭护栏**：因为协议里"缺省"和"写 0"都解析为 0，无法用 0 表达"关闭"。
- **MOVE RUN 全程 `flashenable = 0`**：它独占 `run_data[]`；若业务侧本有黑匣子写入，运动期间被让位。
- **急停锁存必须显式 `STOP` 复位**：这是刻意的 —— "确保随时在于掌控之中"。
- **上电不锁存**：`LINK_Init()` 里 `linkEStop = 0`，只有真正急停过才锁。
