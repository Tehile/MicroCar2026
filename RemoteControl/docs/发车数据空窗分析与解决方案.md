# 发车数据空窗：分析与解决方案

> 日期：2026-10-22　范围：远程档（`MOUSE_REMOTE`）　状态：**方案待拍板，未动代码**

## 一、症状

上位机在发车（`MAZE RUN`）时必须先停拉流、让命令走完、再恢复拉流。实测表现为：

- 发车命令发出后，**有一段时间（数百毫秒到 2 秒）收不到任何数据帧**；
- `led_bit_verify.py` L3 实测：发车命令在 `t=0.94 s`，第一个"发车标记"帧在 `t=1.25 s`，中间 310 ms 无数据；
- 帧率在发车瞬间掉到 0，恢复后回到 13 Hz。

## 二、根因：四层叠加

### L1 传输层 —— 蓝牙透传模块是半双工的（不可改）

模块在同一时刻只能承载一个方向的无线传输。实测证据：拉流期间下发命令，固件多次回
`ACK -1 ERR_CRC` / `ERR_NOCRC`，即**上行命令字节被模块截断**。所以命令只能在
"固件静默期"下发。

> 注意区分：`ERR_CRC` 说明命令**收到了但被打坏** ⇒ 执行未发生 ⇒ 主机必须重发。
> 这不是固件 bug，是链路物理特性。

### L2 协议层 —— `RATE PULL` 是"一次性批量"，发完就静默

`link.c:1378-1403`：

```c
if (linkPullCount == 0u)
    return;               /* 批次跑完 → 静默，等下一条 PULL 命令 */
```

`LINK_PULL_N_MAX = 16`（`link.h:433`）。因此**主机要持续拉流，就必须每批都下一次
`PULL` 命令**，而每次下单都要等一个完整 RTT。严格停等模型下，每个命令切换点都是一段空窗。

### L3 调度层 —— 主机侧"等 ACK 才继续"（真正的痛点）

`led_bit_verify.py:221-236` 的 `batch()`：

```python
self.send_checked("RATE PULL %d %d" % (n, t_ms))   # 发命令，等 ACK OK
while 收到的帧 < want: self.pump()                  # 才开始收数据
```

发车流程因此变成：

```
收满上一批 → 发 MAZE RUN → 等 ACK(1 RTT) → 发 RATE PULL → 等 ACK(1 RTT) → 开始收帧
                                  └────────── 2 个 RTT 的静默 ──────────┘
```

RTT 约 150 ms ⇒ **约 300 ms 空窗**；若 ACK 被 L1 打坏而触发重试（`send_checked` 最多
5 次，每次 80 ms 间隔），空窗可达 **1~2 s**。这就是"发车后长时间收不到数据"的直接原因。

### L4 硬件层 —— 发车启动要连续擦 7 页 Flash（物理下界）

`test.c:671-685`（比赛档共用代码）：

```c
erase_run_data();                                   /* 远程档 save_num=1 → 1 页 */
STMFLASH_ErasePage(FLASH_ADDR_BLOCK);               /* +1 */
STMFLASH_ErasePage(FLASH_ADDR_BLOCK_POINT);         /* +1 */
STMFLASH_ErasePage(FLASH_ADDR_GOPATH);              /* +1 */
STMFLASH_ErasePage(FLASH_ADDR_BACKPATH);            /* +1 */
STMFLASH_ErasePage(FLASH_ADDR_GOPATH_90);           /* +1 */
STMFLASH_ErasePage(FLASH_ADDR_BACKPATH_90);         /* +1 */
```

单 bank 的 F103 在擦除期间**从 Flash 取指被硬件 stall** ⇒ SysTick 中断延迟 ⇒
`link_RateService()` 停摆 ⇒ 固件自己发不出帧。每页 20~40 ms ⇒ **140~280 ms 连续无响应**。

注意 SysTick 优先级最低（`SCB->SHP[11] = 0x40`），USART1 优先级 0 ⇒ 这段时间**命令
仍能应答**，只是拉流停摆。

## 三、空窗预算

| 分段 | 现状 | 方案 E | E + C |
|---|---|---|---|
| 发车命令往返 + 等 ACK | 150~2000 ms | 5 ms（随命令上行） | 5 ms |
| 等首批帧的批内间隔 | — | t ms（20~60） | 20~60 ms |
| 擦 7 页 Flash stall | 140~280 ms | 140~280 ms | **7 段 30~40 ms** |
| 恢复下拉命令往返 | 150 ms | 0（已并入复合命令） | 0 |

## 四、方案

### 方案 E —— 复合命令：`MAZE RUN` 携带拉流参数（**推荐主方案，2026-10-22 用户提案**）

> 提案原文："在发送发车命令的同时附带拉流指令，在发车确认后同时开始数据流发送。"

> **约束（用户明确，2026-10-22 补充）**：拉流模型**保持"等本批 N 帧回来，再拉下一批"不变**。
> 因此**不引入固件自动续订 / `hold` 窗口**；批次停等与"在途 ≤1"铁律原样保留。

**评估结论：可行，采纳为主方案。**

命令形态（**无 `hold` 参数**，一条命令 = 发车 + 启动**恰好一批** N 帧）：

```
MAZE RUN [BLIND|RACE] [PULL <n> <t_ms>]
```

`n/t` 可选，不带即保持现有行为 ⇒ 向后兼容，既有验收脚本不受影响。

固件落点：`link.c:2770-2812` 的 `MAZE RUN` 分支，回 `link_Ack(seq, "OK")` 之后解析可选
PULL 参数。**ACK 天然排在数据帧前面**（TX 是 FIFO，ACK 先入队，首帧要等下一个 SysTick）。

---

#### E.1 主机侧拉流状态机（本方案的核心）

主机必须**明确知道"此刻能不能发命令"**，因此引入显式三态：

| 状态 | 含义 | 进入条件 | 允许的动作 |
|---|---|---|---|
| `IDLE` | **已确认固件静默** | ① 收满本批 N 帧<br>② `RATE OFF` 收到 ACK<br>③ 连接后 `RATE OFF` + 静候 250 ms 无残流 | 可下发**任意**命令（含复合命令） |
| `PENDING` | 批次在途，固件正在发 | 刚下发一条 `RATE PULL` 或复合命令，目标 N 帧 | **只收帧/收 ACK，禁止发任何命令** |
| `RESETTING` | 疑似失同步，重建静默 | `PENDING` 超时仍未收满 N 帧 | 只发 `RATE OFF`，回到 `IDLE` |

铁律：**非 `IDLE` 不发命令**。这条直接消灭 L1 半双工截断的诱因，
不再依赖"卡在批次边界"这种人工纪律，而由状态机强制保证。

#### E.2 三种拉流发起场景（含"先前没有传输、此次是启动"）

| 场景 | 之前状态 | 主机动作 | 固件侧路径 | 空窗 |
|---|---|---|---|---|
| **① 续订** | `IDLE`，上一批 N 帧已收满 | 发复合命令 `MAZE RUN … PULL n t` | `link_RateStop()` → 置 `linkMazeReq` → ACK → `link_PullSet(n,t)` | ≈ t+5 ms |
| **② 启动（此前从未拉流）** | `IDLE`（上电后或 `RATE OFF` 之后，固件 `linkRateOn=0`） | **同上，同一条命令** | **完全相同的路径** | ≈ t+5 ms |
| **③ 危险（批次未收满就发）** | `PENDING` 未收满 | **禁止下发**；超时则进 `RESETTING` | — | — |

关键点：**固件侧不区分 ① 和 ②**，是同一条幂等路径；区分只发生在**主机侧的状态判定**。
所以"此前没有传输、此次是启动"**不需要新协议**，只需要主机在启动前把自己置于 `IDLE`。

连接后的**静默握手（必须做，不可省略）**：主机打开串口 → 发 `RATE OFF` → 等 ACK →
再静候 250 ms 确认无残流 → 置 `IDLE`。否则固件可能还在跑上一轮遗留的批次，
此时任何命令都会被截断。`led_bit_verify.py` 的 `Sess.off()` 已有此逻辑，可直接复用。

#### E.3 "不等 ACK"的正确实现：并行而非阻塞

发车时**不阻塞等 ACK**，而是"一边收 ACK 一边收帧"：

1. 主机下发复合命令，立刻切到 `PENDING`（目标 N 帧）；
2. 循环 pump：ACK 行先到（TX FIFO 保证），随后是 N 个数据帧；
3. **ACK 为 `OK`** → 继续等满 N 帧 → 满则进 `IDLE`；
4. **ACK 为 `ERR_BUSY` / `ERR_ESTOP` 等错误** → 立即中止等待、清空帧缓冲、回 `IDLE`，
   改用裸 `RATE PULL n t` 单独拉流观察状态（此时发车未受理，无数据浪费）；
5. **ACK 超时/损坏** → 同 seq 幂等重发（见 E.4）；重发后仍无帧 ⇒ 判链路异常。

`FrameStreamParser` 本就同时处理帧与文本行，`pump()` 已分开归类 ⇒ **主机侧零改造**。

#### E.4 固件必须补的一处：幂等重放要能重放拉流（否则死锁）

现状 `link.c:3198-3207`：同 seq 同 CRC ⇒ **只回放上次 ACK，不重放任何副作用**。
复合命令若 ACK 在途中丢失，主机按 E.3 第 5 条同 seq 重发 → 固件只回 ACK、**不启动拉流**
⇒ 主机永远等不到帧 ⇒ **死锁**。

修法（拉流是"状态"而非"动作"，重启它天然幂等）：

```c
/* 影子变量: 上次受理成功且携带 PULL 参数时的拉流请求 */
static u8  linkLastPullN;   /* 0 = 无挂起拉流 */
static u16 linkLastPullT;
```

- 在 `linkLastSeq/linkLastCrc` 赋值之后（即**任何**新命令都会覆盖影子）统一
  `linkLastPullN = 0;`；
- `MAZE RUN` 受理成功并启动 PULL 后，写入 `linkLastPullN/T`；
- 幂等重放分支回放 ACK 之后补一句：

```c
if (linkLastPullN)
{
    linkRateOn = 1;
    link_PullSet(linkLastPullN, linkLastPullT);
}
```

先例：`RATE PULL` 之所以天然幂等，是因为它被放在幂等分支**之前**直接执行
（`link.c:3165-3195`）。`MAZE RUN` 的发车副作用不能重复执行，故只能走"重放 ACK + 重放拉流"。

#### E.5 其余实现约束

- **发车被拒时不启动拉流**：`ERR_BUSY` / `ERR_ESTOP` 分支必须直接 `return`，
  不能先 `link_PullSet`（否则白拉一批无意义帧，且主机已按 E.3 第 4 条回退）；
- **统一先 `link_RateStop()` 再 `link_PullSet()`**：防止主机误判"无在途批次"时，
  固件仍在跑残余批次导致两个批次叠加；
- 解析用现成的 `link_TokIs(&p, "PULL")` + `link_TokNum(&rp)`（无 token 时返回 0），
  `n/t` 仍由 `link_PullSet` 做上下钳位；
- `RATE FIX` 与 PULL 互斥语义不变；
- 改动全部落在 `#ifdef MOUSE_REMOTE` 内，比赛档 hex 不变。

#### E.6 收益与剩余盲区

- 覆盖 L2 + L3：空窗从 **440~2430 ms → 约 25~65 ms**（`t=20` 时约 25 ms，`t=60` 时约 65 ms）；
  **批次停等模型与"在途 ≤1"完全保留**；
- **不覆盖 L4**：发车连擦 7 页 Flash 的 **140~280 ms 硬件 stall 依旧**，只能靠方案 C 缓解。

### 方案 A —— host 侧乐观续订（零固件改动，可独立先行）

1. `PULL` 改成**不等 ACK 的乐观续订**：同 seq 重发，固件幂等重放只补 ACK、不重启批次，
   主机直接把 ACK 当异步事件处理，边收帧边续订。
2. 发车改成**乐观发 + 后台确认**：发出 `MAZE RUN` 后不阻塞等待，继续灌 `PULL`；收到
   `ACK OK` 即确认，收到 `ERR_BUSY/ERR_ESTOP/无应答` 再重试（同 seq 幂等，安全）。

收益：消除 L2/L3 的两个 RTT 空窗。风险：低，只动 host 脚本。
局限：**只对"续订"有效**——"此前没有传输、此次是启动"的场景需要固件配合复合命令；
且若沿用"同 seq 重发"，固件只补 ACK 不重启批次 ⇒ 批次可能永远等不满，必须配 E.4 的影子变量。

### 方案 B —— 固件侧"拉流自续订 + 命令插入自动让路"（**已降级为备选**）

> **不推荐先做**：用户已明确"等本批 N 帧回来再拉下一批"的模型不变，本方案第 1 条
> （`hold` 自续订窗口）与之直接冲突。保留记录，仅在日后需要"发车期间长期持续拉流"时再启用。

改动全部在 `REMOTE/link.c` 的 `#ifdef MOUSE_REMOTE` 内，比赛档 hex 不变。

1. **自续订窗口**：`link_PullSet()` 里新增 `linkPullHold`（u8，按帧计）。
   批次跑完后不立即静默，而是每 `t_ms` 继续发 1 帧并递减 `linkPullHold`，减到 0 才静默。
   窗口取 8 帧（`RATE PULL 4 60` ⇒ 480 ms 兜底）。
2. **命令插入让路**：`link_ExecCmd()` 入口，若当前在拉流，置 `linkPullPause = 1`
   （保存 `n/t/hold` 到影子变量）⇒ 立即停止发帧 ⇒ 正常执行命令并回 ACK。
3. **自动恢复**：置 `linkPullResume = 1`；`LINK_Tick()` 里当 `link_DmaIdle()` 为真且
   ACK 已经入队 ≥ `LINK_PULL_RESUME_MS`（如 25 ms）时，恢复影子参数并清 pause。
   ⇒ **主机发完命令不必再下 `RATE PULL`，固件自己回到拉流态。**

收益：主机只需发一次 `PULL` 之后一直收；任何命令可任意时刻插入，只损失 ACK 传输的
20~40 ms。风险：中低，需回归 `RATE OFF/FIX/PULL` 全部路径 + 灌模块压力测试。

### 方案 C —— Flash 页间放行（突破物理下界）

在 `test.c:677-682` 每两页之间插一个**门控调用**：

```c
STMFLASH_Unlock(); STMFLASH_ErasePage(FLASH_ADDR_BLOCK);
#ifdef MOUSE_REMOTE
	linkFlashGap();          /* 页间放行: 补发一帧 + 重置 PULL 定时器 */
#endif
	STMFLASH_Unlock(); STMFLASH_ErasePage(FLASH_ADDR_BLOCK_POINT);
```

`linkFlashGap()` 实现在 `link.c`（远程层），在页间插空里主动调一次
`link_SendUnified()` 并重置 `linkPullTimer`，把 200 ms 连续 stall 切成 7 段 30 ms。

- 比赛档编译时该调用被预处理剔除 ⇒ **红线 hex 必须逐字节相同**（用
  `python build_competition_modes.py --incremental` 校验）；
- 风险：往比赛文件插 `#ifdef` 属于红线边缘动作，须专门验证；
- 收益：把唯一的硬件死区压到一帧以内。

### 方案 D —— 事件推送（架构级，可延后）

让固件在状态变化时**主动**推帧（`RATE EVT`），发车期间主机完全不需要下令拉流。
这与 v9.1 的 LED 位上报同源。频率极低不会灌死模块，但改动面最大，暂不推荐先做。

1. **方案 E**（主方案，一步到位）：
   - 固件：`MAZE RUN … PULL <n> <t_ms>` + `linkLastPullN/T` 影子变量（E.4）；

   - 预期空窗 **440~2430 ms → 约 25~65 ms**（L4 的 Flash stall 暂计在内）；

## 六、验证判据（实机）

- 空窗定义：`MAZE RUN` 下发到"下一帧到达"的时间差，判据 **< 100 ms**（方案 E 目标）；
- **状态机约束（硬判据）**：`PENDING` 期间不得发出任何字节；用带时间戳的收发日志核对；
- **启动场景专项**：连接后不做任何拉流，直接发 `MAZE RUN … PULL 4 20`，
  必须收满 4 帧 + 1 个 OK ACK（覆盖"此前没有传输、此次是启动"）；
- **续订场景专项**：收满一批后立刻发复合命令，同样必须收满 4 帧；
- **失同步场景**：人为少收 1 帧（如中途 `RATE OFF` 打乱），
  主机须超时进 `RESETTING` 并自动恢复，不得死等；
- **幂等专项**：复合命令发出后人为丢弃 ACK 再重发，固件须**回 ACK 且重新启动拉流**
  （验证 E.4 的影子变量，否则会死锁）；
- ACK 混排：主机须能在同一条流里正确分离 ACK 行与统一帧，不得误判为 CRC 错；
- 被拒场景：连发两次 `MAZE RUN`（第二次应 `ERR_BUSY`），确认**第二条不产生任何数据帧**；
- 帧率：发车瞬间掉帧数 **≤ 2**，之后 500 ms 内回到目标频率；
- 灌模块压力：连续发车 5 次，每次 `MAZE RUN` 后 30 s，COM7 静读 0 字节 ⇒ 判模块被灌死（不合格）；
- 红线：`python build_competition_modes.py --incremental` 后比赛档 hex 仍为 `68ad6be2…8141`；
- 离线套件：`contract_test` 263/0、`v9_pull_verify --selftest` 19/0 必须保持全绿。
## 七、收车安全网（2026-10-23 事故后补）

**事故**：一次发车验证之后，车持续跑动未停。

**复盘**：不是单点失误，而是四条相互独立的缺口叠加，任一条补上都不会跑飞：

| # | 缺口 | 后果 |
|---|---|---|
| ① | `main()` 的 `finally` 只发 `RATE OFF`，**从不发 `MAZE STOP`** | 任何异常/中断都不停车 |
| ② | 停车命令走 `send_checked()`，而它断言 `state == IDLE` | 发车后多为 `PENDING/RESETTING`，STOP 被**本地断言**拦死，一个字节都没发出去 |
| ③ | `_launch_once` 的收车顺序执行、不在 `try/finally` 里 | 中间抛异常（如 `ACK -1 ERR_CRC` → `_await` 超时）直接跳过收车 |
| ④ | `launch_blackout.py` 无 `finally` | 该脚本被 Ctrl-C 中断即**永不发停车** |

**修法与铁律**：

1. **安全命令永不受状态机约束**：新增 `Sess.raw_cmd()`，直接写串口、不查状态。
   车在跑的时候，"状态机是否自洽"必须让位于"先把车停下"。
2. **`Sess.halt()` 分级停车 + 必须验证**：
   `MAZE STOP`（唯一同时做「停 PWM + 退出迷宫循环 + 解急停」的命令）
   → 拉 2 帧验 `mazeTask/motionTask` 归零 → 不成立才升 `ESTOP` → 再不成立才 `MCU RESET`。
   **只看 `ACK OK` 不算停住**；拿不到验证帧也判失败（安全出口宁可报失败）。
3. **退出路径无条件经过 halt()**：正常结束、异常、`KeyboardInterrupt`、`atexit` 四条都走。
   `halt()` 内部**屏蔽 SIGINT** —— 连按两次 Ctrl-C 会打断 `finally`，车就真的跑掉了。
4. **停车必须用新 seq**：复用 seq 会命中固件幂等重放分支（只补 ACK、不重做副作用），
   命令实际没执行却看着"成功"。
5. 每个发车脚本自己负责收车，不依赖调用方。

**离线回归判据**（`led_bit_verify.py --selftest` 新增 11 条）：
- `PENDING` 状态下停车命令照样发出；
- STOP 回 OK 且验证停稳 ⇒ **不得**下发 ESTOP/RESET；
- STOP 无应答 ⇒ 重试 `SAFETY_HALT_TRIES` 次后升级 `ESTOP` + `MCU RESET`；
- STOP 回 OK 但仍在动 ⇒ 判失败并升级急停；
- 发车过程中抛异常 ⇒ 仍执行 halt（用桩对象验证调用序列）。

**真机已验证**：`halt()` 在待命状态走通 `MAZE STOP → ACK OK → 拉帧 → mazeTask=0 motionTask=0`；
`launch_blackout.py` 用假串口注入 `KeyboardInterrupt` 验证「发车 → 中断 → MAZE STOP → 关串口」整条路径。

### 8.2 基准灯（L2）间歇失败：不是固件逻辑坏了，是被状态灯覆盖

**现象**：同一固件连跑 6 次，L2「ARM 后 led4 应 1 Hz 翻转」5 次通过（6~12 次翻转，
中位 979~1049 ms），**1 次翻转 0 次**（run6）。帧照常收、`ARM` 照常回 `ACK OK`。

**根因（已在源码级证实，不是推测）**：

1. `link.c` 的基准灯段**只在电平变化沿**写 LED4：
   `if (lv != linkTimeLed) { ... LED4 = ... }` —— 1 Hz 方波 ⇒ 每 500 ms 才写一次，
   写完到下一次被覆盖的窗口只有**不到 1 ms**。
2. 该段注释假设"`ledBeaconLock` 已把所有状态灯的写入挡掉了"。**这个假设在本平台不成立**：
   - `link_port.c:59-61` 明写它只是个**影子**，"新固件无人读"；
   - `led.c` 的 `ledon()/ledoff()` 是**无门控**的裸引脚写。
3. 因此固件的状态灯/电池灯（`timer.c:1280-1291`，`showbattery==1 && SHOWVOLTAGE` 时
   **每个 SysTick** 都 `ledoff(0); ledon(battarypercent)`）会立刻把 LED4 写回去。
4. 组帧间隔 40 ms，而基准灯的"亮"只存在不到 1 ms ⇒ **采样几乎永远落在状态灯残值上**，
   于是翻转数归零。是否归零取决于当时状态灯有没有在动（`sleepmode`、电池显示），
   所以表现为**间歇性**，与 ARM 时刻无关。

**修法（FW 313，一行语义改动）**：在 `#ifdef MOUSE_REMOTE` 内新增 `0a3` 段，
**每 tick 无条件重钉一次** `LED4`：

```c
if (linkArmed)
{
    linkTimeLed = (u8)(((linkTimeMs - linkArmMs) % (u32)LINK_TIME_DIV)
                       < (u32)(LINK_TIME_DIV / 2));
    LED4 = linkTimeLed ? 0 : 1;   /* 低电平点亮 */
}
```

三条要点：
- 该段放在 `0b` 发车标记灯**之前**，标记窗口仍然压过它，L3 语义不变；
- 组帧在 Tick 第 5 段、**同一 tick 稍后**读 ODR ⇒ 帧里必然读到基准灯真值，与时序无关；
- 全部包在 `#ifdef MOUSE_REMOTE` 内 ⇒ 比赛档产物不变（红线 hex 逐字节相同，已校验）。

这与 v2.8 发车标记灯的做法一致（它的注释已经写明"每 1 ms 重写一次才守得住"）——
本质是**同一个结论**：在这块板子上，想让某个灯表达"我的语义"，就必须每 tick 重钉，
不能靠"写一次然后指望没人动它"。

**副产品**：状态指示在 `linkArmed` 后对 LED4 完全失效（基准灯独占）—— 这正是
`ledBeaconLock` 原本的设计意图，只是此前从未真正生效。

### 8.5 发车批次 N 参数化 + 一次链路掉线（2026-10-23 16:45~16:52）

#### 事故：N=8 连测时蓝牙链路掉线

第一次跑完整 L3（`MAZE RUN PULL 8 40`）时，**批次只收到 1/8 帧**，随后：

```
MAZE STOP 无 OK 应答 -> 升级急停 ESTOP -> 升级软复位 MCU RESET 无 ACK
复位后能 PING 通   FAIL(None)
```

**这不是固件问题，是链路静默**：断电重启后再探测，

```
[监听1.2s] 字节 0                        ← COM7 能打开、零字节
PING -> PONG 9 313 16 1024 POR + ACK OK   ← 立刻恢复，且 rst=POR
```

判据与既有结论一致（`docs/链路MTBF压测方法.md`）：**COM7 能开、0 字节、断电即自愈**
= 透传模块被灌死/掉线，属物理层，与固件逻辑无关。发车批次是全程最密的一段
（8 帧 / 40 ms = 200 帧/s 瞬时），是唯一值得收窄的地方。

> 处置顺序也复盘了一遍：脚本 `halt()` 的分级升级（STOP → ESTOP → RESET）在链路
> 已死时**一条都进不去**，最后仍要靠人手动停车 + 断电。也就是说链路断开的场景下
> **软件收车网是无效的**——这条要写在安全须知里，不能指望脚本兜住。

#### 处置：把发车批次做成参数，判据随 N 缩放

`led_bit_verify.py` 新增 `--mark-n / --mark-t`（默认 8 / 40，仅影响发车那一条复合
命令的 `PULL <n> <t_ms>`）。N 变小后三条判据必须同步缩放，否则测的是"我把 N 改小了"：

| 判据 | 原值（按 N=8 定） | 缩放后 |
|---|---|---|
| 收到统一帧 | ≥ 25 | ≥ 17 + N |
| 窗口至少 N 帧 | ≥ 2 | `N×t < 300` 时放宽到 1（标注"采样下限"） |
| 窗口跨度 | 100~600 ms | `N×t < 300` 时下限 `max(20, N×t/2)` |

### 8.6 方案 C（Flash 页间放行）完整论述

#### 8.6.1 物理机制：为什么擦 Flash 会让整条链路停摆

STM32F103RB 是**单 bank** Flash。擦除一页时 FPEC 拉高 BSY，Flash 阵列不可读；而
Cortex-M3 的取指、中断向量取址、常量池读取**全部要经过 Flash**。于是：

```
擦除命令写入 -> BSY=1 -> 任何取指都 stall -> SysTick 进不来 -> linkTimeMs 停走
                                                   -> 拉流状态机停 -> 不组帧
```

注意 `STMFLASH_ErasePage()` 内部的 `STMFLASH_WaitDone(0x5FFF)` 是"轮询 + `delay_us(1)`"，
**看起来**只占 us 级；实际第一次轮询的取指就被 stall 到擦除完成 —— 这两种写法在
F1 上等价，都是硬停 20 ms。

**实测反推的模型（与两轮数据都吻合）**：

| 量 | 值 | 依据 |
|---|---|---|
| 实测空窗 | 157.9 ms（N=8）/ 142~232 ms（N=2） | run6 / §8.5 |
| 擦除黑窗总量 | ≈ 118 ms | 空窗 − t_ms |
| 单页擦除 | **≈ 19.7 ms** | 118 / 6（见 8.6.2 的页数修正） |

⇒ `158 ≈ 118（黑窗）+ 40（t_ms 计时从零重来）`，**两项都占**。这一点很关键：
不是"擦完就能发帧"，而是擦完之后 `linkTimeMs` 才重新开始计时，还要再等一个 `t_ms`。

#### 8.6.2 一处旧记录修正：远程档实际只擦 6 页，不是 7 页

`test.c:673-675` 的 `erase_run_data()` 包在 `#ifdef FLASHSAVE` 里，而 `FLASHSAVE`
只在 **`#ifndef MOUSE_REMOTE`** 时才 `#define`（`test.c:18-20`，同样写法见
`timer.c:34`、`stmflash.c:10`）。远程档定义了 `MOUSE_REMOTE` ⇒ **这一段根本不编译**。

所以远程档每次发车擦的是 `test.c:677-682` 的**6 页**，全是 1 KB 页、地址 1 KB 对齐：

```
0x0801E000 BLOCK        0x0801DC00 BLOCK_POINT   0x0801F000 GOPATH
0x0801F800 BACKPATH     0x0801E400 GOPATH_90     0x0801E800 BACKPATH_90
```

6 × 19.7 ms = 118 ms ✓ 与实测完全对上（若按 7 页算，单页只有 17 ms，与 F1 手册的
20~40 ms 页擦除时间不符）。**结论：C 要放行的是 6 个间隙，不是 7 个。**

#### 8.6.3 实现形态：不要试图"把代码搬 RAM"，而是主动泵一帧

第一直觉是"把擦除等待段放进 RAM 执行，让中断能跑"。**这条路在 F1 上不成立**：
中断向量表和 ISR 代码本身在 Flash，向量取址一样被 stall。除非把向量表 + ISR + 拉流
状态机整体搬进 SRAM，代价远超收益，还要改链接脚本（触碰红线）。

可行且最小的形态是**在页与页之间主动放行一次链路**：

```c
/* link.c（整文件已在远程档门控内） */
void LINK_PageGapPump(void)   /* 不看时间, 待发批次还在就直接出一帧 */
{
    if (linkPullLeft == 0) return;
    link_EmitOneFrame();      /* 组一帧塞进 TX 环 */
    linkPullLeft--;
    linkPullLast = linkTimeMs;
}
```

```c
/* test.c 的 6 次擦除之间, 逐点门控 */
STMFLASH_Unlock(); STMFLASH_ErasePage(FLASH_ADDR_BLOCK);
#ifdef MOUSE_REMOTE
LINK_PageGapPump();
delay_us(1200);               /* 让 USART TX 把 30 B 发完(460800 下约 0.65 ms) */
#endif
STMFLASH_Unlock(); STMFLASH_ErasePage(FLASH_ADDR_BLOCK_POINT);
...
```

三个要点：

1. **必须"不看时间"**。8.6.1 的模型说明 `linkTimeMs` 已被擦除吞掉 118 ms，
   若仍按 `now - last >= t` 判断，切了窗也不会出一帧。故 Pump 直接放行。
2. **必须补一小段 delay**。组帧只是塞进 TX 环，真正上线上要 0.65 ms；黑窗里
   USART 中断也进不来，所以泵完要留出这一小段。
3. **必须逐点门控**。`test.c:671-685` 整段在 `#if 1` 里、**不在** `MOUSE_REMOTE` 内，
   属比赛档共用代码。6 个钩子各包一个 `#ifdef MOUSE_REMOTE`，改完重编比赛档、
   校验 hex 与红线 `68ad6be2…8141` 逐字节相同。

#### 8.6.4 收益模型（四种配置对比）

关键点在这：**光把黑窗切成洞不够**。切了洞，SysTick 每个间隙只补进 1~2 tick，
`linkTimeMs` 一共才走回 6×2 = 12 ms，仍差 28 ms 才到 40 —— 空窗几乎不变。
真正起作用的是"间隙里**主动**出一帧，不看时间"。

| 配置 | 首帧时刻 | 机理 |
|---|---|---|
| 现状 | **≈158 ms** | 118 黑窗 + 40 计时从零重来 |
| 只把 t_ms 调到 20（不动固件） | ≈138 ms | 黑窗不变，只省 20 ms 计时 |
| C 只插放行窗口、不泵帧 | ≈158 ms | `linkTimeMs` 只补回 12 ms，**几乎没有改善** |
| **C + 间隙主动泵帧** | **≈20~45 ms** | 第一个间隙（0~20 ms）一结束就出一帧，与 `t_ms` 无关 |

⇒ 结论要改口径：**C 的有效形式是"主动泵帧"，不是"插入延时"**。上一轮记录里
"C 必须配 t=20"的说法是按"帧按到期发"推的，那个模型下 C 确实白改 —— 但改成
主动泵之后，`t_ms` 不再决定首帧时刻，只决定**剩余帧的节奏**。

发车批仍建议用 `--mark-n 16 --mark-t 20`（host 侧改，零固件风险）：6 个间隙泵掉 6 帧，
剩 10 帧按 20 ms 续，总覆盖 320 ms，正好完整覆盖 300 ms 标记窗口；若仍用 n=2/t=40，
两帧在间隙里就泵完了，之后只能靠常规批次接力。

#### 8.6.5 风险清单（按严重度排序）

1. **红线**：改动落在比赛档共用段，必须 6 处独立门控 + hex 逐字节比对。任一处理解
   错都会让比赛档行为变化。
2. **擦除期中断危险性**：擦除/编程序列期间若 ISR 里发生**任意 Flash 写**，FPEC 状态
   会被破坏（可能整页写坏）。远程档飞行记录已关（`FLASHSAVE` 不定义），SysTick 里
   没有 Flash 写 —— 但这是**前提条件，必须在实现时复核并注释**，不能默认。
3. **时序副作用**：6 × 1.2 ms ≈ 7 ms 额外发车时间，对迷宫无影响；但若有人把 delay
   调大（比如 5 ms），发车总时长会显著增长。
4. **TX 环竞争**：泵帧时环里可能还有统一帧，`link_SendFrame` 空间不足会**整帧丢弃**
   且只 `linkDrop++`，不报错。需要判 `link_TxSpace()` 再泵。
5. **验证成本**：需车轮悬空真机跑，且要证"比赛档没动"（hex）+ "远程档没退化"
   （全套 10 个 host 套件）。

#### 8.6.6 决策建议：冻结 C

- 判据已经满足：空窗 142~232 ms 全在硬上限 250 ms 内，且**方案 E 已吃掉协议层的
  全部收益**（剩的是物理下限）。
- C 的收益是"发车瞬间的可视性"（158 → 25~45 ms），不是功能缺失 —— 车本来就看不见
  那 118 ms 里发生了什么。
- 代价是**动比赛档共用段**（红线风险最高的那类改动）+ 真机验证成本。
- 建议：**保持冻结**，把 `t_ms=20` 这条（host 侧单独可做、零固件风险）留作需要时
  的备选 —— 它单独只能到 ~118+20=138 ms，收益更小，所以也一并冻结。

若将来一定要做，验收顺序固定为：先只加钩子（行为等价，跑离线全绿 + hex PASS）→
再加泵帧（真机 N=16/t=20）→ 最后才调 t。
