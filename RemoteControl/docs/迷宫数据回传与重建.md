### 读表要点（三条）

1. **墙图只有一个权威：F1。** M1/M2 只是它的"回传镜像"，而这条同步线（`LP_SyncMap`）**没有接线**。
2. **两个"全 0"含义完全不同，别混。** F1 低 4 位为 0 = "这格没探过"（正常数据，新图就是这样）；M2 全 0 = "从来没被填过"（接线缺失）。
3. **帧头和帧体新鲜度不一样。** 图帧头的坐标/朝向走 M3/M4（**每 tick 刷新**），墙图和访问图走 M1/M2（**从不刷新**）。所以 `MAP DUMP` 的表现是：**位置是对的、还在动，图是死的** —— 这正是链路断点的典型症状，而不是解码或渲染出错。

## 二、生命周期：什么时候变（按时间顺序）

| 时刻 | 发生了什么 | 动到的变量 |
|---|---|---|
| 上电 | `mouseInit()` 把墙图铺成"全部未探索" | F1 ← `0xf0`（`test.c:142`） |
| 发车 `MAZE RUN` | 先擦 6 页 Flash，若 BLOCK 首半字 `!= 0xFFFF` 就把上一轮的图读回来 | F1 ← S1（`test.c:688-698`） |
| 跑图每一格 | 进入新格 → 标访问 → 若该格没测过就测墙并回写四邻 | F2 ← 1（`utility.c:421`）；F1 ← 新墙位（`utility.c:446-474`） |
| 到终点掉头 | 若 `block_write_flag==1`，把整张图存进 Flash | S1 ← F1（`utility.c:1088` → `stmflash.c:241`） |
| 收车 | 墙图留在 RAM，**没人往 M1 搬** | —（这就是断点） |
| `CAL BLOCK` | 从 Flash 读回镜像 + 位置/目标，随后 `MAP DUMP` 才拿得到图 | M1 ← S1（`link.c:2401`）；M2 不变 |
| `MAP DUMP` | 组 516 B 载荷发出，先发图、后回 ACK | L1 ← M1+M2+M3+M4（`link.c:1935-1951`） |
| 主机收帧 | 按长度反推 n、还原二维、存进 ring、刷新 UI | H1 ← L1；H2 ← H1 |

## 三、唯一的断点与后果

```
LP_SyncMap()  link_port.c:293-304      做的正是"F1/F2 -> M1/M2"这次拷贝
              ├─ 定义    link_port.c:293
              ├─ 声明    link_port.h:417
              ├─ 注释提到 link_port.c:69 / link_port.h:413
              └─ 调用点  ✗ 一个都没有（link_SendMap 里也没有）
```

后果（可推演，待真机确认）：

| 场景 | `MAP DUMP` 返回的墙图 |
|---|---|
| 上电后、未 `CAL BLOCK` | 全 0 图（四面皆墙、全未访问、位置 0,0） |
| 先 `CAL BLOCK` | Flash 里**上一轮存档**的图 |
| 刚跑完一轮、未掉头存档 | **还是上次镜像的值**，本轮探索结果进不去 |
| 跑完且已掉头存档 + `CAL BLOCK` | 才是本轮结果 |

⇒ `MAP DUMP` 现在的准确语义是"**Flash 存档快照通道**"，不是"实时墙图通道"。
`通信协议规格.md:440` 写"先 `CAL BLOCK` 再 `MAP DUMP` 才拿到 Flash 的图"，正好反证了这一点。

## 四、修法

**推荐：新增 `MAP LIVE`，不动 `MAP DUMP`**

```c
/* link.c, MAP 分支内 */
if (link_TokIs(&p, "LIVE"))
{
    LP_SyncMap();          /* link.h -> link_port.h 已能看到声明, 不用加 include */
    link_SendMap();
    link_Ack(seq, "OK");
    return;
}
```

- `MAP DUMP` 行为逐字节不变 ⇒ 现有 host 与文档零回归；
- `MAP LIVE` 给实时图；host 侧加一条 `maze.live`，复用现成 `decode_map`；
- 代价：`LP_SyncMap()` 一次 512 B 拷贝 ≈28 µs（`link_port.c:288` 的估算），低频命令可忽略。

**备选 A（一行，但有回归面）**：`link_SendMap()` 开头直接调 `LP_SyncMap()`。
`MAP DUMP` 语义就从"存档图"变成"实时图"，与 `通信协议规格.md:440`、`api_reference.md:44` 冲突，且 `CAL BLOCK` 之后拿到的不再是"刚校验的那份"。

**备选 C（不改固件）**：host 拉图前先发 `CAL BLOCK`。只是把"旧图"变成"确定的 Flash 图"，仍拿不到实时结果，不解决根本问题。

### 不改代码的三步确认

1. `PING` 记下 `mazetype`；直接 `MAP DUMP` —— 预期 `mapWall` 全 0。
2. 发一次 `MAZE RUN`，跑几秒 `MAZE STOP`，再 `MAP DUMP` —— 若与第 1 步**完全相同**，即证实实时图未回传。
3. `CAL BLOCK` 后再 `MAP DUMP` —— 若这时变成非零、有墙有路，则三份图的关系与第一节一致。

## 五、墙位编码与 UI 重建

```
每个字节:  低 4 位 = 本格    bit0 上  bit1 右  bit2 下  bit3 左   置 1 = 无墙 / 可通行
           高 4 位 = 镜像    同样四向、方向相反, 供隔壁格查自己的边界
```

固件印证：`stratagy.c:120-135` 是 `if ((GucMapBlock[cX][cY] & 0x01) && 邻居可走)` —— 置位才允许往上走。

UI 三条规则（`ui/maze_view.py:78-145`）：

1. `cY` 向上增长而屏幕 y 向下 ⇒ `oy + (n-1-cy)*cell`。
2. 每格只画"右边 + 上边"，靠共享边避免重复画线。
3. `not (b & WALL_UP_OPEN)` 才画墙 —— 与"置位 = 可通行"一致。

两个显示层边界：

- 外框永远画（`maze_view.py:108`），即使数据里外圈位是可通行。
- F1 的 `0xf0` / `0xD0`（`test.c:779-790` 环形搬运用）低 4 位为 0 ⇒ 渲染成"四面皆墙的孤格"。属算法内部约定，主机不做特判，但看图时会出现个别全墙格。
- 顺带：`link.c:2391` 注释里"既有 98B 帧"是**过时注释**（现在 516 B 载荷），不影响行为。

## 六、时间与容量

| 项 | 值 | 说明 |
|---|---|---|
| 图帧载荷 | 516 B | `4 + 16×16×2` |
| 图帧线上 | 524 B | 头 8 B（sync2 + len2 + type1 + seq1）+ CRC2 |
| TX 环 | 1024 B | 放一帧图后只剩 500 B，**容不下第二帧** |
| 实测往返 | ≈1.21 s | 524 B 上行 + 命令下行，含透传模块延迟 |
| 命令重试 | 禁止 | `no_retry=True`，超时 5 s |

⇒ 发图期间任何下行命令都可能把 ACK 打坏，而 ACK 是判断成没成的唯一依据。
所以 `MAP DUMP` 只能在链路空闲（`IDLE`）时发，不能与拉流批次并行 —— 与本项目三态状态机一致。

另外：`link_SendFrame` 空间不足时是**整帧丢弃**（`linkDrop++` 后 return），而调用方不检查返回值、`ACK` 照回 `OK`。所以主机可能"收到 OK 却没收到图"，`MazeAPI.fetch()` 里必须有 `store.get_map()` 兜底。
