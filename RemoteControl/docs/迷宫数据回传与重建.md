# 迷宫数据的回传与主机侧重建（现状勘察）

> 2026-10-23 源码级勘察。回答两个问题：**固件里的迷宫图是怎么变成主机上那张图的**，
> 以及这条链路上**哪个环节现在是断的**。
> 相关文件：`code_competition/REMOTE/link.c`、`REMOTE/link_port.c`、`USER/test.c`、
> `STRATAGY/stratag.c`、`host/host/protocol/codec.py`、`host/host/api/maze.py`、
> `host/host/ui/maze_view.py`。

## 一、结论先行

链路本身是通的，编码与重建也自洽，但**有一处接线缺失**：

```
MAP DUMP  ->  link_SendMap()  ->  发的是 mazeState.mapWall(镜像)
                                        ^
                                        |  只被两处写:
                                        |    ① CAL BLOCK: 从 Flash 读
                                        |    ② LP_SyncMap(): 从 GucMapBlock 拷  <-- 从未被调用
                                        |
                          本轮发车跑出来的实时墙图在 GucMapBlock 里, 进不了镜像
```

⇒ **`MAP DUMP` 当前等价于"Flash 存档快照"，拿不到本轮实时探索结果。**
上电后若没先 `CAL BLOCK`，拿到的是全 0 图（全墙 + 全部未访问 + 位置 0,0）。

## 二、固件侧：三份"地图"

| 名称 | 位置 | 类型 | 谁写 | 谁读 |
|---|---|---|---|---|
| `GucMapBlock[16][16]` | `stratagy.c:51` | `uchar` | 算法（`mazeSearch` / `mapStepEdit` 等） | 算法自身、`SaveBlockData()` |
| `GucMapGet[16][16]` | `stratagy.c:55` | `uchar` | `utility.c:421` 置 1（访问过） | 算法判"未访问 == 0" |
| `mazeState.mapWall[16][16]` / `mapVisited` | `link_port.c:36` 的 `MazeState mazeState` | `u8` | `link.c:2401`（CAL BLOCK 从 Flash 读）、`link_port.c:300`（`LP_SyncMap`，**未被调用**） | `link.c:1946/1949`（组图帧） |
| Flash BLOCK 区 | `0x0801E000`（`FLASH_ADDR_BLOCK`） | 每格占 2 B（写入 `int`） | 跑完一轮由 `SaveBlockData()` 写 | 发车流程 `test.c:688-698` 读回 `GucMapBlock`；`CAL BLOCK` 读进镜像 |

要点：

1. **`GucMapBlock` 是 `uchar`，低四位本格墙、高四位镜像格墙**（`link_port.c:290`
   注释）。`mazeState.mapWall` 同为 `u8`，`LP_SyncMap` 的赋值是**同宽度直接赋值**，
   无截断问题。Flash 读回时 `STMFLASH_ReadHalfWord()` 返回 `int` 再赋给 `uchar`，
   取的是低字节 —— 与写入侧一致。
2. **`GucMapGet` 的语义是 `1=已访问 / 0=未访问`**（`utility.c:421` 置 1、
   `stratagy.c:780` 判 `== 0`）。`link_port.c:291` 的注释写"0xFF=未访问"是**过时注释**，
   实现与主机侧（非 0 即已访问）一致，**不是 bug**。
3. 发车时 `test.c:688-698` 会把 Flash BLOCK 读回 `GucMapBlock` —— 这就是"上一轮的图"
   在本轮开局重新进入算法的路径（`flashaddrmax != 65535` 才读）。

## 三、回传路径（`MAP DUMP`）

```
host: MouseClient.send_cmd("maze.dump")        # commands.py:447, no_retry=True, timeout=5s
  |  "MAP DUMP #<seq>*<crc>\r\n"
  v
固件: link_HandleLine -> MAP/DUMP -> link_SendMap()      # link.c:2737-2746
  |  pl[0..3] = cX, cY, mouseDirection, mouseTask
  |  pl[4 .. 4+256]      = mazeState.mapWall[x][y]   (x 外层, 行主序)
  |  pl[260 .. 516]      = mazeState.mapVisited[x][y]
  v
link_SendFrame(LINK_TYPE_MAP, pl, 516)                  # link.c:1936-1950
  |  线上 = 2(sync) + 2(len) + 1(type) + 1(seq) + 516 + 2(crc) = 524 B
  v
link_Ack(seq, "OK")        # 注意: 先发图, 后回 ACK —— ACK 在图之后到达
```

三个实现细节值得记住：

- **`LINK_MAP_LEN = 4 + MAZETYPE*MAZETYPE*2 = 516`**（`link.h:164`）。固件**不重复发
  mazetype**，主机靠载荷长度反推：`n = round(sqrt((len-4)/2))`（`registry.py:427`）。
- **整帧丢弃而非部分写入**：`link_SendFrame` 空间不足时 `linkDrop++` 后 `return`
  （`link.c` 组帧段），但**调用方不检查返回值，ACK 照回 OK** ⇒ 主机可能收到
  `ACK OK` 却没有图帧。这就是 `MazeAPI.fetch()` 里 `if not r.ok and not hits:`
  还要兜底 `store.get_map()` 的原因。
- **`no_retry=True`**：整块回传占链路（实测 ≈1.21 s），重发会造成两份图交错，
  所以命令层显式禁止重试。

## 四、主机侧解码与重建

```
codec.decode_map(payload, mazetype)                     # codec.py:491-507
  cx, cy, direction, task = struct.unpack("<bbBB", p[:4])
  wall    = p[4 : 4+n*n]
  visited = p[4+n*n : 4+2*n*n]
  grid[x][y] = wall[x*n + y]        # 行主序还原成二维
  vis[x][y]  = visited[x*n + y]
       |
       v
registry.FRAMES[TYPE_MAP] -> store.push_map(rec)        # ring.py:190
       |  mazetype / mapWall / mapVisited 存入 ring
       |  触发 on_map 回调 + 事件 "map"
       v
MazeAPI:  grid() / visited() / cell() / to_text()       # api/maze.py:292-357
MazeWidget.paintEvent                                   # ui/maze_view.py:78-145
```

### 墙位编码（唯一权威）

```
mapWall[x][y] 低四位:  bit0 上  bit1 右  bit2 下  bit3 左
                       置位 = 该方向【无墙/可通行】
```

固件侧的印证：`stratagy.c:120-135` 是 `if ((GucMapBlock[cX][cY] & 0x01) && 邻居可走)`
—— 置位才允许往"上"走，说明置位 = 可通行。与 `api/maze.py:5` 的注释一致。

### UI 重建的三条规则

1. **坐标翻转**：`cY` 向上增长，屏幕 y 向下 ⇒ `cxy()` 里 `oy + (n-1-cy)*cell`。
2. **每格只画两条边**：按"本格低四位"画 `(x+1,y)` 的右边和 `(x,y+1)` 的上边，
   靠共享边避免重复画线（`maze_view.py:126-137`）。
3. **`not (b & WALL_UP_OPEN)` 才画墙**：与"置位=可通行"对齐。

### 两个显示层面的已知边界

- 外框永远画（`maze_view.py:108`），即使数据里外圈位为"可通行"。
- `test.c:779-780` 里有 `GucMapBlock[...] = 0xf0` 的镜像格填充写法（16×16 环形坐标
  搬运）。`0xf0` 低四位 = 0 ⇒ 显示成"四面皆墙"的孤立格。这属算法内部约定，
  主机侧不需要特判，但看图时会出现个别全墙孤格。

## 五、断点：`LP_SyncMap()` 从未被调用

`LP_SyncMap()`（`link_port.c:293-304`）的职责写得很清楚：

```c
/* 把墙图/访问图拷进镜像(MAP DUMP 前调用) */
mazeState.mapWall[x][y]    = GucMapBlock[x][y];
mazeState.mapVisited[x][y] = GucMapGet[x][y];
```

但全仓检索的结果是：**只有定义（`link_port.c:293`）、声明（`link_port.h:417`）、
以及两处注释提到它（`link_port.c:69`、`link_port.h:413`），没有任何调用点。**
`link_SendMap()` 里也没有。

### 后果（可推演，待真机确认）

| 场景 | `MAP DUMP` 返回 |
|---|---|
| 上电后、未 `CAL BLOCK` | 全 0 图：四面皆墙、全部未访问、位置 (0,0) |
| 先 `CAL BLOCK` | Flash 里的**上一轮存档图**（这正是 `link.c:2390-2393` 注释描述的用法） |
| 发车跑完一轮 | **仍是上次镜像的值** —— 本轮实时探索结果在 `GucMapBlock` 里，没同步 |
| 跑完后再 `CAL BLOCK` | 才更新（前提是本轮结果已由 `SaveBlockData()`（`stmflash.c:233`）写进 Flash） |

⇒ 现状下 `MAP DUMP` 的准确语义是"**Flash 存档快照通道**"，而不是"实时墙图通道"。
文档里"先 CAL BLOCK 再 MAP DUMP 才拿到 Flash 的图"这句（`通信协议规格.md:440`）
正好反证了这一点：它把 `CAL BLOCK` 当成了前置条件。

### 建议修法（零回归优先）

**方案 B（推荐）：新增 `MAP LIVE`，不动 `MAP DUMP` 的语义**

```c
/* link.c, MAP 分支内 */
if (link_TokIs(&p, "LIVE"))
{
    LP_SyncMap();          /* link.c 已通过 link.h -> link_port.h 看到该声明 */
    link_SendMap();
    link_Ack(seq, "OK");
    return;
}
```

- `MAP DUMP` 行为**逐字节不变** ⇒ 现有 host 与文档零回归；
- `MAP LIVE` 给实时图；host 侧加一条 `maze.live` 命令 + 复用现成 `decode_map`；
- 成本：`LP_SyncMap()` 一次 512 B 拷贝 ≈28 us（`link_port.c:288` 的估算），
  属低频命令，可接受。

**方案 A（更省事，但有回归面）**：直接在 `link_SendMap()` 开头加 `LP_SyncMap()`。
一行搞定，但 `MAP DUMP` 的语义从"存档图"变成"实时图"，与
`通信协议规格.md:440`、`api_reference.md:44` 的描述冲突，且 `CAL BLOCK` 之后
`MAP DUMP` 不再是"读回刚校验的那份图"。

**方案 C（不改固件）**：host 每次拉图前先发 `CAL BLOCK`。只是把"旧图"变成
"确定是 Flash 里那张图"，仍然拿不到实时结果。**不解决根本问题。**

### 真机确认方法（三步，不需要改代码）

1. `PING` 记录 `mazetype`；直接 `MAP DUMP`，看 `mapWall` 是否全 0（预期是）。
2. 发一次 `MAZE RUN`（车轮悬空或跑道），跑几秒后 `MAZE STOP`，
   再 `MAP DUMP` —— 若地图与第 1 步完全相同，即证实"实时图未回传"。
3. `CAL BLOCK` 后再 `MAP DUMP` —— 若此时地图变成上一轮存档（非零、有墙有路），
   则三份地图的关系与本文第二节一致。

## 六、附：这条链路的时间与容量

| 项 | 值 | 说明 |
|---|---|---|
| 图帧载荷 | 516 B | `4 + 16×16×2` |
| 图帧线上 | 524 B | 头 8 B（sync2 + len2 + type1 + seq1）+ CRC2 |
| TX 环 | 1024 B | 放一帧图后仅剩 500 B，**容不下第二帧图** |
| 实测往返 | ≈1.21 s | 524 B 上行 + 命令下行，含透传模块延迟 |
| 命令重试 | 禁止 | `no_retry=True`，超时 5 s |

⇒ 命令层"在途 ≤1"在这里是硬性要求：**发图期间任何下行命令都可能把 ACK 打坏**，
而 ACK 又是判断成没成的唯一依据。所以 `MAP DUMP` 只能在链路空闲（IDLE）时发，
不能与拉流批次并行 —— 与本项目既有的三态状态机一致。
