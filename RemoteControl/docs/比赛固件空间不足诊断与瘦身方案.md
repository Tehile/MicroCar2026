## 0.0 已实施（2026-10-04）：方案 D —— 运行数据区上移

**约束**：原有比赛程序（运动/迷宫/状态机/查表）**一行不动**；只从存储布局入手。

**做法**：`FLASH_EraseRunData()` 按 `saveNum/100+1 = 13` 页擦除，而运行数据区**预留了 29 页**——
16 页是虚设的。把这 16 页还给程序区，并把链路模块的标定页从"落在擦除范围内"的位置挪出来。

| 页 | 原布局 | **新布局** | 改在哪 |
|---|---|---|---|
| 0..87 | 程序区（88 KB） | **0..100 程序区（101 KB）** | `Mouse.uvprojx` IROM1 `0x16000` → `0x19400` |
| 88 | `FLASH_ADDR_DATA_NUM` | — | — |
| 89..117 | `FLASH_ADDR_DATA`（预留 29 页；实擦 13 页） | — | — |
| **101** | — | `FLASH_ADDR_DATA_NUM` `0x08019400` | `flash.h` |
| **102..114** | — | `FLASH_ADDR_DATA` `0x08019800`（擦除范围 13 页） | `flash.h` |
| **115** | — | `FLASH_ADDR_SYSCALIB` `0x0801CC00`（原 page 99） | `link.h` |
| **116** | — | `FLASH_ADDR_LESSONPARAM` `0x0801D000`（原 page 100） | `link.h` |
| 117 | — | 备用 | — |
| 118..127 | 迷宫/路径/红外/陀螺 | **原样不动** | — |

**改动清单（共 5 处，全是地址常量 + 1 个项目设置，无一行程序逻辑）**

| 文件 | 改动 |
|---|---|
| `HARDWARE/flash.h` | `FLASH_ADDR_DATA_NUM` 0x08016000→**0x08019400**；`FLASH_ADDR_DATA` 0x08016400→**0x08019800** |
| `HARDWARE/link.h` | `FLASH_ADDR_SYSCALIB` 0x08018C00→**0x0801CC00**；`FLASH_ADDR_LESSONPARAM` 0x08019000→**0x0801D000** |
| `USER/Mouse.uvprojx` | IROM1 `<Size>` 0x16000 → **0x19400** |

**结果（实测，五档一次跑完）**

| 档位 | Code | RO-data | RW | **ROM** | RAM | 余量 |
|---|---|---|---|---|---|---|
| [1] 安全测试 | 28384 | 456 | 2136 | 30976 | 16744 | 72448 |
| [2] 电机远程 | 28936 | 456 | 2136 | 31528 | 16744 | 71896 |

**顺带修掉一个真实缺陷**：`FLASH_EraseRunData()` 被 `calibrate.c:71` / `menu.c:136` / `state.c:274`
三处调用，擦除 **page 89..101**；而链路模块的标定页/课程参数页原先取 **page 99 / 100**，
**正落在该范围内** —— 触发一次擦除就会把生产标定与课程参数一起抹掉。上移后录制区为 102..114，不再相交。

**不受影响**：迷宫墙/起终点/90°路径/红外标定/常规路径/陀螺零偏（page 118..127）地址未变 →
**不需要重新标定**；录制容量未削减（仍 1200 组 / 13 页擦除）。
**唯一须知**：链路模块自己的标定页搬了家，板上旧标定读不到 → 会回落源码默认值，重做 `SAVE` 即恢复
（与本项目既定的 D1 决策一致）。

**已加的回归**：`contract_test [S5]` 新增 4 条断言 —— 程序区上界必须等于 `FLASH_ADDR_DATA_NUM`；
运行数据擦除范围必须为 13 页；`FLASH_ADDR_SYSCALIB` / `FLASH_ADDR_LESSONPARAM` 必须
**位于数据区、1 KB 对齐、不越过迷宫页、且不在擦除范围内**。日后任何人改动 `saveNum` 或这些页地址，
断言会立刻报红。

> 下面第 0~8 节保留完整诊断与**备选方案（A/C/E）**，供后续需要更大余量时取用。

## 0. 结论速览

**问：是不是"缓存区"导致的空间不够？**

**是，但要分清两种"缓存"：**

| | 结论 |
|---|---|
| **RAM 侧的缓冲区**（`run_data[1200]`=9600 B、TX 环 512 B、RX 64 B…） | **不是瓶颈**。[5] RAM 用 17617 / 20480 B，**还余 2863 B**。对照实验：把 `saveNum` 从 1200 降到 900（省 2400 B RAM）后 [5] **仍然链接失败** → 可排除 RAM。 |
| **ROM 侧的常量查表** | **就是主因**。`MOTION/speedtable.c` 一个文件装了 **43 张 `const short` 查表 = 20266 B（19.8 KB）**，该文件的**代码只有 14 B**。它占 88 KB 程序区的 **22.5%**，是全工程**最大的单一 ROM 消耗**。 |

**关键结论：缺口只有 ~3.9 KB，而"只做查表的元素类型收窄"一项就能省 8488 B（2.2 倍缺口），且不需要改动任何算法逻辑。** 单项即可解决。

**另一个重要的量级判断**：过去容易怀疑的 C 库 printf/浮点（`printfa.o`/`dflti.o`/`ffixui.o`/`qnan.o`…）经实测**总共只有 ≈1.9 KB**，不是杠杆所在。

## 1. 诊断结论

### 1.1 程序区上限（原 88 KB）是**设计约束**，不是配置疏漏

| 项 | 值 |
|---|---|
| 芯片 | STM32F103RB：Flash 128 KB / RAM 20 KB（0x5000） |
| uvprojx IROM1（**原**） | `StartAddress=0x08000000` `Size=0x16000` = **90112 B（88 KB）** |
| uvprojx IROM1（**现**） | `Size=0x19400` = **103424 B（101 KB）**（见 §0.0） |
| 上限的来由 | `HARDWARE/flash.h` `FLASH_ADDR_DATA_NUM` 指向数据区起始页—— **该页以下才是程序区，程序区不得越界** |

数据区（40 页 = 40 KB，页号 88..127）的划分 —— 下表的**"页"列是原布局**，现布局见 §0.0：

| 页 | 常量 | 用途 |
|---|---|---|
| 88 | `FLASH_ADDR_DATA_NUM` | 运行数据条数 |
| **89–117** | `FLASH_ADDR_DATA` | **运行数据录制区，29 页 = 29 KB（最大的一块）** |
| 118 | `FLASH_ADDR_BLOCK_STACK` | 搜索交叉点栈 |
| 119 | `FLASH_ADDR_BLOCK_POINT` | 起点/终点 |
| 120 | `FLASH_ADDR_BLOCK` | 迷宫墙信息 |
| 121 / 122 | `GOPATH_90` / `BACKPATH_90` | 90° 冲刺路径 |
| 123 | `FLASH_ADDR_IRDATA` | 红外标定表 |
| 124–125 / 126 | `GOPATH` / `BACKPATH` | 常规路径 |
| 127 | `FLASH_ADDR_GYRO0` | 陀螺零点 |

| 档位 | Code | RO-data | RW-data | ZI-data | ROM 合计 (Code+RO+RW) | 结果 |

### 1.3 排除 RAM（对照实验）

## 2. 主因详解：`MOTION/speedtable.c` 的 43 张查表

### 2.1 全部 43 张表（10 个"族"）

| 族 | 表 | 点数 | 字节 |
|---|---|---|---|
| Spurt（冲刺 90°） | `vouterSpurt` `vinnerSpurt` `gyroLSpurt` `gyroRSpurt` | 182 ×4 | 1456 |
| Search（搜索 90°） | `vouterSearch` `vinnerSearch` `gyroLSearch` `gyroRSearch` | 227 ×4 | 1816 |
| Around（掉头） | `vlAround` `vrAround` `gyroAround` | 267 ×3 | 1602 |
| Point（点转） | `vouterPoint` `vinnerPoint` `gyroLPoint` `gyroRPoint` | 232 ×4 | 1856 |
| T90Low / V90Low | `vouterT90Low` `vinnerT90Low` `gyroLt90Low` `gyroRt90Low` / `vouterV90Low` `vinnerV90Low` `gyroLv90Low` `gyroRv90Low` | 195×4 / 187×4 | 1560 / 1496 |
| T45Low / V45Low | 同上四位一组 ×2 | 152×4 / 171×4 | 1216 / 1368 |
| T135Low / V135Low | 同上四位一组 ×2 | 302×4 / 294×4 | 2416 / 2352 |
| 180Low | `vouter180Low` `vinner180Low` `gyroL180Low` `gyroR180Low` | 391 ×4 | 3128 |
| | | **10133 点** | **20266 B** |

> **没有死表可删。** `LOW_ENABLE` 在 `MOTION/motion.h:14` **已定义**，19 张 `*Low` 表全部参与 `turnParamTable`。且 `speedtable.o` 的 RO = 20266 B **恰好等于 43 张表之和** → 链接后一张都没被丢弃。

### 2.2 值域：**38 张能压进 1 字节**

| 可放类型 | 张数 | 说明 |
|---|---|---|
| `int8`（−128..127） | **32** | 例：`vouterSpurt` 75..119、`gyroLSpurt` −3..90 |
| `uint8`（0..255） | **6** | `vouterT135Low` `vouterV135Low` `vouterV45Low` `vouterV90Low`（最大 145）、`gyroLt135Low` `gyroLv135Low`（0..135） |
| 需 16 位 | **5** | 值域跨 ±180：`gyroAround`(−180..0)、`gyroL180Low`(−6..180)、`gyroR180Low`(−180..6)、`gyroRt135Low`(−135..0)、`gyroRv135Low`(−135..0) |

### 2.3 仿射冗余：16 张可以"不存"

逐值验证（`a[i] == k*b[i] + c`，k ∈ {+1,−1}，**全表逐点成立，不是近似**）：

| # | 关系（精确） | 可省 |
|---|---|---|
| 1 | `gyroRSpurt = −gyroLSpurt` | 364 |
| 2 | `vinnerSpurt = −vouterSpurt + 150` | 364 |
| 3 | `gyroRSearch = −gyroLSearch` | 454 |
| 4 | `vinnerSearch = −vouterSearch + 120` | 454 |
| 5 | `gyroRPoint = −gyroLPoint` | 464 |
| 6 | `vinnerPoint = −vouterPoint` | 464 |
| 7 | `vrAround = −vlAround` | 534 |
| 8 | `gyroRt90Low = −gyroLt90Low` | 390 |
| 9 | `gyroRv90Low = −gyroLv90Low` | 374 |
| 10 | `vinnerT90Low = −vouterT90Low + 140` | 390 |
| 11 | `gyroRt45Low = −gyroLt45Low` | 304 |
| 12 | `gyroRv45Low = −gyroLv45Low` | 342 |
| 13 | `gyroRt135Low = −gyroLt135Low` | 604 |
| 14 | `gyroRv135Low = −gyroLv135Low` | 588 |
| 15 | `gyroR180Low = −gyroL180Low` | 782 |
| 16 | `vinner180Low = −vouter180Low + 140` | 782 |
| | **合计（16 张）** | **7654 B** |

其中 **12 张是纯取反（c=0）**：1 3 5 6 7 8 9 11 12 13 14 15；**4 张是"取反 + 常数"**：2(150) 4(120) 10(140) 16(140)。
规律的物理含义很清楚：**右转的表 = 左转表的镜像**，而左/右转在 `motion.c:726-746` 的 `turnParamTable` 里本来就是**成对、且 vouter/vinner 互换**的条目。

> **引用面极小**：这 16 张表**只出现在 2 个文件**——`MOTION/speedtable.h`（extern 声明）与 `MOTION/motion.c`（`turnParamTable` 初始化 + 3 处赋值），合计约 20 处。这是"去冗余"可行性的关键。

## 3. 方案

### 方案 A —— 查表元素类型收窄到 1 字节　【首选】

| 项 | 内容 |
|---|---|
| **做法** | 按 §2.2 的分类，把 43 张表的声明由 `const short` 改为 `const signed char` / `const unsigned char`（38 张 1 字节）；其余 5 张保持 16 位 |
| **收益** | 10133 点中 8488 点变 1 字节 → **省 8488 B（8.3 KB）**，即缺口的 **2.1 倍** |
| **改动面** | 3 个文件：`MOTION/speedtable.c`（43 个定义）、`MOTION/speedtable.h`（43 条 extern）、`MOTION/motion.c` 的 `TurnParam_t` 指针类型 + **`sizeof` 陷阱**（见 §4.1）；另 `HARDWARE/core.h` 的 `TurnTable` 三个指针类型 |
| **是否动算法** | **不动**。读取点（`isr.c` 的 9 处 `*(turnTbl.xx + tick)`）表达式不变，C 会自动提升为 `int` 参与运算；唯一必须改的是"把字节数当元素数"的那处（属修正隐含假设，不是改算法） |
| **风险** | **低**。可用脚本逐值比对（§6.1）把"表内容不变"变成硬保证 |
| **建议** | **先做这个，单项达标** |

### 方案 B —— 仿射去冗余（16 张改为派生）　【叠加 A 更佳】

| 项 | 内容 |
|---|---|
| **做法** | 删掉 16 张表；因左/右转在 `turnParamTable` 中成对出现，给 `TurnParam_t` 增加 `s8 negate; s16 offset;` 两个字段（12 处 negate=−1，4 处再带 offset），`isr.c` 的 9 处解引用改为 `(*(tbl+tick)) * negate + offset` |
| **收益** | **省 7654 B（7.5 KB）** |
| **与 A 叠加** | 先 B 后 A：43 张 → 27 张 → 其中仅 `gyroL180Low`/`gyroAround` 留 16 位 → 最终 **≈6964 B**，**合计省 13302 B（13.0 KB）** |
| **改动面** | `speedtable.c/h`（删定义）、`motion.c`（`turnParamTable` + `TurnParam_t`）、**`isr.c`（9 处实时路径解引用）** |
| **风险** | **中**。`isr.c` 是 1 kHz 实时路径，多一次乘法/加法（可接受），但一旦 negate/offset 配错就是"转弯方向反了"这类现场事故 |
| **建议** | A 之后再评估；若 A 已够用（余量 ~4.5 KB），B 可不做 |

### 方案 C —— `link.c` 按档裁剪

| 项 | 内容 |
|---|---|
| **背景** | `link.o` = 14298 B，其中 `link_ExecCmd`（命令分派）单函数 **2704 B**。按名归类"实验档专属"函数 ≈ **4638 B**（`link_SnapLine` 1080、`link_CalibService` 1232、`link_ScopeSample` 340、`link_MoveService` 412、`link_MoveFinishRun` 256、`link_DumpService` 212…），但 `link_ExecCmd` 里还内联着这些命令的处理分支，实际可裁量更大 |
| **做法** | 新增档位宏（如 `MOUSE_TOOL_LAB`），把 `SNAP`/`SCOPE`/`DUMP`/`MOVE`/`LESSON`/`ARM`（实验档专属命令）整体包进 `#ifdef` |
| **收益** | 估 **4.6~9 KB** |
| **代价** | **[5] 会失去**远程 `MOVE RUN`、`SNAP` 快照、`SCOPE` 1 kHz 录制；**但保留**参数读写/`SAVE`、标定、遥测流 —— 比赛现场标定与监视仍可用 |
| **风险** | 中（功能回归，需明确 [5] 是否需要这些命令）；改动集中在 `link.c`，不动运动算法 |
| **建议** | 若希望"比赛固件也不牺牲功能"，优先 A/B/D |

### 方案 D —— 让出 Flash 数据区若干页　【✅ 已实施，见 §0.0】

| 项 | 内容 |

## 4. 必须避开的陷阱

### 4.1 ⚠️ `sizeof` 陷阱（本轮诊断中最重要的一条）

`MOTION/motion.c:722` 附近：

```c
typedef struct {
    int angle;          /* MOTION_SetAngle 参数 */
    const short *gyro;  /* 前馈陀螺角度表 */
    const short *vl;    /* 左轮速度表 */
    const short *vr;    /* 右轮速度表 */
    u16 length;         /* = sizeof(gyro表), 用于 while(motionCtrl.tick < length/2-2) */
} TurnParam_t;

static const TurnParam_t turnParamTable[] = {
    {LT90SPURT, -90, gyroLSpurt, vinnerSpurt, vouterSpurt, sizeof(gyroLSpurt)},
    ...
```

**`length` 存的是"字节数"，使用处用 `length/2 - 2` 得到"点数"** —— 这里**把元素宽度 = 2 字节这个隐含假设写死在除法的分母上**。

一旦按方案 A 把元素收窄到 1 字节，`sizeof` 减半 → `length/2` 变成"点数的一半" → **转弯会只走一半的表、动作被截断**（而且是"看起来能动、只是不对"的可怕故障）。

**修法**：把 `length` 改成"点数"语义 —— 初始化写 `sizeof(tbl)/sizeof(tbl[0])`，使用处改 `tick < length - 2`。涉及 `motion.c` 两处。

### 4.2 类型可见性（漏改不一定报错）

表的类型声明分布在 **3 处**，必须同步：

| 位置 | 内容 |
|---|---|
| `MOTION/speedtable.h` | 43 条 `extern const short xxx[N];` |
| `MOTION/motion.c` | `TurnParam_t` 的 `const short *gyro/vl/vr` |
| `HARDWARE/core.h` | `TurnTable`（`turnTbl`）的三个指针，被 `isr.c` 解引用 |

第 3 处漏改 → 跨编译单元类型不一致，属**未定义行为**，且编译器未必报错（可能只有 `#47-D` 一类告警，正是本工程"114 warnings"里容易被忽略的那种）。

### 4.3 `isr.c` 的实时解引用（表达式不变，但要确认接收类型）

`HARDWARE/isr.c` 有 9 处形如：

```c
gyroStr.target   = *(turnTbl.gyro + motionCtrl.tick);
speedSt.speedTargetL = *(turnTbl.vl + motionCtrl.tick) - motionCtrl.pidErr * pidGain.turnP - ...;
```

表元素变 `signed char` 后会自动提升为 `int` 参与运算，**表达式无需改动**；但要确认左侧目标类型足够宽（`gyroStr.target` 为 `double`、`speedSt.speedTargetL` 为 `int` → OK）。

### 4.4 `LOW_ENABLE` 已定义

`MOTION/motion.h:14` `#define LOW_ENABLE` —— 19 张 `*Low` 表**全部在用**，不能当死代码删除。`speedtable.c:161` 也有 `#ifdef LOW_ENABLE`。

### 4.5 逐值等价比对是"不改算法"的唯一硬保证

编译通过、能跑，都**不能**证明表内容没变。必须用脚本比对（§6.1）。

**为什么选 D 而不是 A：**

3. D 的收益（13312 B）比 A（8488 B）更大，且**余量更充足**。
