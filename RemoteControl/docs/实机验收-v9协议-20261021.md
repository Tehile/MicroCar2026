## 三、两个现场现象与判定（都不是固件缺陷）

### 1. 首包截断：「有 ACK 无 PONG」

首轮第二次启动时 S1 收到 `ACK 1 OK` 而没有 `PONG`。判定为**主机侧 USB 首包截断**，依据：

- `PONG` 与 `ACK` 走**同一个 TX 环、同一次 DMA**（`link_ExecCmd` 里先 `link_TxStr("PONG ")...` 再 `link_Ack()`）；
- 环满时 `link_TxPut()` 是**逐字节丢尾部**，只会丢后面的 ACK，不可能只丢前面的 PONG；
- 因此「只丢前 30 B、留下尾部 ACK」只能发生在主机侧接收路径；
- 紧接着连测 60 次 PING：**60/60 PONG 与 ACK 全到，0 复现**。

已给 S1 加最多 3 次自动重试（间隔 0.35 s），并把判据写进脚本注释：*只丢前段 = 主机侧截断；只丢尾部 = 固件环满*。

### 2. N=6 灌死透传模块

N=6 跑到 t=17.0 s 判 BROKE（`--gap-timeout` 连续 3 s 无帧），此时：

- 交付率仍是 1.000，说明断之前一帧没丢；
- 断后 `COM7` **能打开但读不到任何字节**，连 ACK 都没有；
- 物理断电重启后 `PONG ... POR` 立刻恢复 ⇒ 模块侧死锁，与固件无关（固件若能收命令就一定会 ACK）。

这与 v8 时代「排程式拉取 `link_pull_pace.py` 6.9 s 灌死模块」是同一类问题：**透传模块在持续高频下行时会被灌死，只能断电恢复**。因此：

- `v9_pull_verify.py` 的 `--ladder` 默认值由 `4,6,8` 改为 **`4,5`**，N≥6 必须显式指定；
- 阶梯逻辑保持「某档 BROKE 立即停」。
