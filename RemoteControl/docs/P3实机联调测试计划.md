## 0. 三条铁律（每一步都适用）

| # | 铁律 | 原因 |
|---|---|---|
| 1 | **上电前车必须绝对静止** | `hardware_init()` 的陀螺零偏标定是阻塞死循环（`gyro0==-1` 等 `angle_counter>1000`，而它一见 `gangle` 变化就清零）。车一动 ⇒ 永久自旋 ⇒ 标定完成前串口全程 0 字节。**症状与 NVIC 故障完全相同，极易误判。** |
| 2 | **判状态必须用新鲜帧** | `telemetry.latest()` 是缓存，链路一停就永远停在旧值。必须记帧计数 → 发 `TELEM` → 等计数真变了。**空帧 ≠ 待命**（空帧意味着链路不通，必须按"可能在跑"处理）。 |
| 3 | **安全出口宁可报失败，绝不谎报成功** | 收车判据 `rst=SW`；刚发过车的一律 `assume_busy=True`。`force_idle()` 停不住时必须报"未确认待命，请人工断电"。 |

**辅助判档**：`PING` → `PONG 8 300 16 1024 <rst>`。
`fw=300` = 远程档。若 `PING` 永远无 `PONG`，先怀疑**烧错档**（比赛档无 `LINK_Init`），
用 J-Link 读 Flash 首字确认：远程档 `0x200034F8` / 比赛档 `0x20005000`。

### 8.2 本轮新发现（阻塞项）

**排程式拉取 `link_pull_pace.py` 会把链路打死（远程档 fw=300）。**

```
link_pull_pace.py COM7 --fps 12 --batch 2 --duration 90
  t=6.89s 之后零帧 → t=10.0s 判 BROKE
  交付率 67.2%(82/122)   发送过期让位 1 次   批次无首帧 0    MCU 丢帧字节恒 0
  RTT 估计收敛到 62.9ms(远小于实际)，`send_at < earliest` 闸按 RTT/2 算 ⇒ 提前发
```

- 现象与"透传模块缓冲灌满"完全一致：**CH340 仍在（COM7 可开）、模块不再转发**；
  静候 25s + 8 次 `PING` 全静默 ⇒ **不自愈，须物理断电**。
- 根因方向：排程式按时间表无条件发 `RATE PULL`，落后时的"让位立即发"绕开了
  "在途 ≤1"这条不变量 ⇒ 抢占在途批、命令频率瞬顶 ⇒ 模块灌死。
  实测帧表里 `g_host=0.00` 成对出现（USB 攒包）与单片机侧 83/67ms 交替（批尾被抢占）互相印证。
- 对照：同一链路 **事件触发式 120s 零丢帧**（周期≡RTT 自锁，天然在途 ≤1）⇒
  真机长跑只认 `link_pull_evt.py`。已在 `link_pull_pace.py` 启动处加显著告警，
  并在 `docs/链路MTBF压测方法.md` §14.3 的"控制哲学对比"结论上加注实测证据。
