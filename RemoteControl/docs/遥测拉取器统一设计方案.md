# 遥测拉取器统一设计方案（v2.10.0，已实施，待真机验收）

> 2026-10-15。目标：把 `host/host/api/stream.py` 里的**停等式拉取器**（`PullRequester`，
> 单条 `TELEM` 阻塞至回复）与**批式拉取器**（`PacePull`，一条 `RATE PULL n t` 取回多帧）
> 合并成一个拉取器。用户判断："后者是前者的拓展，一次请求发 1 帧时后者退化为前者"——
> 本设计把这句判断变成代码结构：**统一轴就是 n（每条命令取回几帧），n=1 即停等**。
> 固件 / 协议零改动（PROTO 8 / fw 221 不变），本轮只动上位机与文档。
>
> **实施结果**（2026-10-15 当晚）：① 旧类名**不留别名**（用户决定，下游自行适配）；
> ② 自节流的"上一条已启动"信号由帧基改为 **ACK 基**（§12.1，实测教训）；
> ③ 新增 `stream_unified_smoke.py` 78 项，旧 624 项一项不掉；④ **真机验收 41/41 通过**
> （§9.3，脚本 `host/v210_accept.py`）。

---

## 0. 结论先行

1. **一个类、一个状态机**：`TelemetryPuller`（stream.py），剖面参数只有 `(n, t_ms)`。
   `n=1` → 命令词 `TELEM`、回复门控（= 今天的停等式）；`n≥2` → 命令词 `RATE PULL n t`、
   网格调度（= 今天的批式）。退化发生在**调度器层面**，不只是参数层面。
2. **四件共同持有**：在途不变量、让路（suspend/resume）契约、断连判定、时间锚维护。
   今天它们在两套类里各写一遍（或只写了一半），合并后各只有一处。
3. **门面 `mc.stream` 对外符号一个不删**：`on/off/toggle/pace/pace_off/mode/is_on/
   anchor/suspend/resume/tick/stats/tune` 全部保留原语义 ⇒ 下游 `Control` 与全部
   9 个测试套件（624 项）**零改动**。
4. **顺带补两个现有缺口**（都是统一后"只有一处"才暴露出来的）：
   - 批式模式**从不刷新时间锚**（`RATE PULL` 的 ACK 不带时基）⇒ 设备一旦复位，
     ms8 同余还原永久失锁且无恢复路径；
   - 停等式**没有断连判定**（只能数 lost 请求，永不自停、无 link_lost 事件）。

## 1. 为什么要统一

### 1.1 两套状态机在重复同一组不变量

| 不变量 / 机制 | 停等式 `PullRequester` | 批式 `PacePull` | 重复的代价 |
|---|---|---|---|
| 在途 ≤1 条命令 | `_out` 长度恒 ≤1（`_refill` 只在空时发） | `_pending` 一批一发（网格天然错开） | 同一纪律两处实现，改一处忘一处 |
| 让路 suspend/resume | 等在途回复 ≤0.3s（丢回复补 0.12s 静默） | `RATE OFF` + 等尾帧 ≤0.3s | 两套 + 门面 `_suspended_kind` 路由；**2026-10-15 实测**按 running 路由会清掉外层暂停记忆（pull_smoke 3 项失败），已改成按记忆路由——但这类 bug 的根因是"有两个对象要路由" |
| 断连判定 | **无**（请求超时只计 lost，链路死了也静静重试） | 3s 无帧 ⇒ `Event.ERROR(kind="link_lost")` + `dead` | 停等用户在真机上得不到"该断电了"的提示 |
| 时间锚 | 每条 `TELEM` 回复带 `ACK OK <upMs>`，逐条刷新 ⇒ 失锁立刻自愈 | **从不刷新**（`RATE PULL` 回的是裸 `ACK OK`，`link.c:3145-3170`） | 见 §5：批式下锚只建一次，设备复位后同余还原永久失锁，`timesync.needs_anchor()` 根本没有消费者 |
| 统计 | sent/done/lost/hz/best_hz/inflight | batches/frames/lost_batches/rtt_ms/fps_* | 两套字段，工具要写两套读法 |
| 启停 | start/stop（等在途收尾 ≤0.6s） | start/stop（`RATE OFF`） | stop 的两条时序纪律（S8f）只在一边有契约测试钉着 |

### 1.2 统一轴确实存在

两条链路的**命令语义**可以写成同一句话：

> 一条拉取命令的语义 = "取回 n 帧"。

- `n=1`：命令 `TELEM`，取回 1 帧；下一条必须等这条的**回复**（停等）。
- `n≥2`：命令 `RATE PULL n t`，取回 n 帧（批内间隔 t）；下一条按网格 `T=n·t` 发。

固件侧语义（`link.c` 实测）：`RATE PULL` 置位后立即发首帧、每 t 一帧共 n 帧、发完静默；
新 PULL 抢占（旧批剩余帧作废，**不计** `LINK_U_DROP`）。所以 `n=1` 的 PULL 与 TELEM
在"取一帧"上同构——差别只在**回复里带不带时基**（§2.4）。

## 2. 统一模型

### 2.1 剖面与命令词

| 剖面 | 命令词 | 调度 | 帧率 | 现状对应 |
|---|---|---|---|---|
| `n=1` | `TELEM` | 回复门控（在途清空才发下一条） | 1/RTT（真机 4.4~6.5Hz） | `PullRequester` |
| `n≥2` | `RATE PULL n t` | 网格：每 `T=n·t` 一条，提前 RTT 估计发 | n/T（默认 3/100ms=10Hz） | `PacePull` |

- 参数约束不变：`n∈[1,16]`（固件上限），`t_ms≥1`；`T=n·t` 建议 75ms 整数倍
  （下行命令通路按 75ms 量化，见《链路MTBF压测方法》§16）。
- **`n=1` 时 `t_ms` 被忽略**（停等的周期就是 RTT，不是 t）。下游 Control 的切换端点
  允许 `n=1`，文档/注释必须写明这一点，否则现场会以为 `n=1,t=100` 是 10Hz。

### 2.2 统一不变量（停等是它的 n=1 特例）

> **任何时刻，最多一条命令在"等它的首帧"。**

- 停等式：等的是那条命令的回复（回复 ≡ 它唯一的帧）。
- 批式：等的是该批首帧到达（或 `T+1s` 判整批丢失）。
- 这条不变量正是固件"每 1ms tick 只消费一行命令"（背靠背 N 条回收率 N=2→50%）
  在上位机侧的对策：命令永远不成串。

### 2.3 自节流（self-throttle）——把不变量 2.2 做实

下一条命令的发车时刻：

```
next_send = max(网格点 − RTT估计, 上一条命令 ACK 到达时刻)
```

> ⚠️ 实施期修正：设计稿原文写的是"上一条**首帧**到达时刻"。真机化模拟测试（U4）证明
> 帧基信号在退化域会被污染——ACK 按 seq 唯一归属、帧无归属，详见 §12.1。

- **正常域（RTT < T，即已验证的 10Hz 档：T=300ms vs RTT 57~137ms）**：网格主导，
  与现行为**逐拍一致**——提前 RTT 发、网格恒进、不锁实测首帧（锁实测会把 RTT 抖动
  写进网格累积成速率误差，`link_pull_pace.py` 实测被压到 10.4Hz/目标 12.05）。
- **退化域（RTT > T，模块热衰 / 链路变慢）**：今天会按网格继续发，新 PULL **抢占**
  旧批剩余帧 ⇒ 成批丢帧；自节流后自动降到 `1/max(T, RTT)` 的命令节奏，用帧率换完整批。
- `n=1` 时命令间距 ≡ RTT——**字面意义上的停等**。用户"后者退化为前者"的判断在调度器
  里精确成立。

⚠️ 自节流是唯一改动批式正常域之外行为的点，**必须真机复核**（§10.3）；正常域预期
与现行为无差异。

### 2.4 为什么 n=1 保留 `TELEM` 而不用 `RATE PULL 1 t`

| 候选 | 回复内容 | 锚 | 结论 |
|---|---|---|---|
| `TELEM` | 一帧 + `ACK <seq> OK <upMs>`（完整 u32 时基） | 逐条刷新，失锁立刻自愈 | **采用** |
| `RATE PULL 1 t` | 裸 `ACK <seq> OK`（`link.c:3170` `link_Ack`） | 无 | 不采用 |

停等式"每条回复刷锚"是 timesync 自愈的根基（`api/timesync.py`：锚随每次拉取刷新，
比"开流时给一次"更稳）。改用 PULL 1 会把这颗螺丝拧松。固件将来若给 RATE 的 ACK 加
`upMs`，可再评估合并命令词（§11 已评估不做）。

## 4. 状态机：一拍 `tick()`（调度线程 50Hz，非阻塞）

```
tick():
  0) not running → return
  1) 断连判定（共享检测器，阈值分模式，§6）
  2) 收割在途：
       telem: p.done → done++/lost++；超 REQUEST_TIMEOUT_S → abandon, lost++
       pull : 首帧到（samples 增长）→ RTT IIR(0.25)，pending 清；
              超 T+1s 无首帧 → lost_batches++，pending 清
  3) 调度下一条（§2.3 自节流 + 网格恒进）
  4) 时间锚维护（§5）
  5) 统计：hz 按 2s 窗口帧到达实算；RTT 估计两种模式同口径 IIR
```

- **RTT 口径统一**：telem 用"回复时刻−发送时刻"，pull 用"首帧时刻−命令发送时刻"，
  都是 IIR(0.25)，都进 stats 的 `rtt_ms`。停等式因此第一次有了 RTT 可读
  （`fps_target` 在 telem 模式报 `1/RTT`——正是 docstring 里"窗口 1 已拿到 1/RTT 满速"
  的那个量）。
- **命令发送全部 `wait=False, no_retry=True`**（与现状一致）：tick 里绝不阻塞；
  `TELEM`/`RATE` 都绕开幂等簿记（协议规格 §1.3）。

## 5. 时间锚：补齐批式缺口（统一后新增）

**现状问题**（合并时才看得见）：`RATE PULL` 的 ACK 是裸 `OK`，而 `PacePull` 不挂
`_absorb_anchor` ⇒ 进入批式后锚停在"最后一次 `TELEM`"上永不刷新。`ANCHOR_MAX_AGE_S=120s`
和 `needs_anchor()` 写了却没有消费者 ⇒ 设备复位（`linkTimeMs` 归零）后，所有帧的
ms8 同余还原预测全错、`locked=False/lost++`，**且没有任何路径恢复**。停等式靠
"下一条 TELEM 的回复"天然自愈，批式没有。

**方案**（pull 模式专用，telem 模式不需要——它每条回复都刷）：

- 每 `ANCHOR_REFRESH_S`（默认 30s，取 `ANCHOR_MAX_AGE_S=120s` 的 1/4），在**批中点**
  （`due + T/2`，距上一条 PULL 150ms、距下一条 150ms，绝不撞 1ms 收行窗口）注入一条
  `TELEM`：不等回复，回调挂 `_absorb_anchor`。
- `timesync.needs_anchor()` 为真（未建锚 / 失锁 / 超 120s）时，下一拍立即注入。
- 代价：3.3Hz 命令预算里多 0.033Hz；固件对 `TELEM` 立即回一帧（**不影响** PULL 批
  计时，`linkPullTimer` 独立走时）；预期零丢帧，真机复核（§10.3）。
- 注入期间用 `_anchor_outstanding` 防叠加（回调清除，超时兜底）。
- stats 增 `anchor_refreshes` 计数；`mc.reanchor()` 改为调 `refresh_anchor()`
  （现实现是 `stream.on()`——已在跑时是空操作，是个假动作）。

## 6. 断连判定统一

同一检测器（"连续无帧超过阈值"），阈值分模式，各自用实测依据：

| 模式 | 阈值 | 推导 |
|---|---|---|
| pull（批式） | `GAP_TIMEOUT_S = 3.0s` | 实测正常最大帧间隔 236ms（paceE），12× 余量；真机 8 组样本全是这个死法且必须物理断电 |
| telem（停等） | `2×REQUEST_TIMEOUT_S + 1.0 = 7.0s` | 必须同时容得下两种正常长空档：① 单条请求被提前放弃的最坏帧间隙 ≈ 超时(3s)+RTT；② **`MCU RESET` 后首帧遥测 ~3.2s**（收车/救援路径，Control 在用）——3.2s×2.2 的余量 |

触发后与批式现行为一致：`dead=True`、`running=False`、只发一次
`Event.ERROR(kind="link_lost")`（提示物理断电 3~5s 再重连）、之后 `start()` 清 dead
可恢复。telem 模式因此**新增**该能力（原来只能数 lost）；Control 的 `stalled` 判据
（6s 窗口）不变，两者互补。

## 7. 让路与停止契约（合并后）

- `suspend()`：嵌套计数；最外层按 kind 分派——
  - telem：停补发 + 等在途回复（≤0.30s）；回复没等到补 `QUIESCE_TAIL_S=0.12s` 全静默
    （收到回复 ⇒ 固件已消费完那行 ⇒ 接收端必然空闲）。
  - pull：发 `RATE OFF`（等 ACK）+ 等尾帧落地（≤0.30s 兜底）。
- `resume()`：仅当原本在跑；telem → `_refill`；pull → 重发 `RATE PULL`（3 次重试）。
- `stop()`/`off()`：同 §3.1 模式感知拆teardown；S8f 源码契约保留。
- `MouseClient.send_cmd()`（urgent）/ `send_raw()` 的让路调用点**零改动**——
  门面签名没变，只是内部不再有路由。

### 8.2 stats() 字段口径（并集，两套旧读法都不破）

| 字段 | telem（n=1） | pull（n≥2） | 口径 |
|---|---|---|---|
| `mode` | `"stop-and-wait"` | `"pace"` | 拉取器自报（pull_smoke/pace_smoke 断言的旧契约） |
| `stream_mode` | `off/stopwait/pace` | 同左 | 门面三态 |
| `sent`/`done`/`lost` | TELEM 请求数 / 成功 / 超时 | RATE PULL 命令数 / 完成批 / 丢批 | **命令口径**（launch_link_live 差分读它） |
| `frames` | = done（1 命令 1 帧） | 到达帧数 | **帧口径** |
| `batches`/`lost_batches` | = sent / = lost（每条 TELEM 就是一批 1 帧） | 原义 | 退化字面成立 |
| `inflight` | `_out` 长度（恒 ≤1） | 1 = 有命令在等首帧 | 统一不变量 2.2 的可观测面 |
| `hz`/`best_hz` | 2s 窗口帧率（原算法） | 同左 | 一致 |

## 12. 实施记录（2026-10-15，与设计的差异只此一节）

### 12.1 自节流的"上一条已启动"信号：帧基 → ACK 基（本轮最重要发现）

设计稿 §2.3 用"上一条**首帧**到达时刻"做自节流的下界。U4（`--rtt-ms 500` +
`pace(2,150)`）实测**节流从未生效**：RTT 被估成 53ms、命令按网格率 3.5Hz 发。

**根因**：帧没有归属。批式下"首帧"这个信号不干净——上一条批的剩余帧会在**下一条
命令发出之后**才到达（500ms 注入延迟使 ACK 与首批帧同 burst 在 `pace()` 返回瞬间
到达，与首个网格命令发送竞速），把新 pending 当成自己的首帧清掉，RTT 因此被低估
（真实 458ms 被估成 53ms）。ACK 则按 seq 唯一归属，且与批首帧同 burst 到达 ——
取 ACK 更干净。

**修法**：`_pending` 改存 `(Pending, send_wall)`；`_reap_pull` 只在 `p.done`
（ACK 到达）时清算并 IIR 刷 RTT；`_schedule_pull` 门控 `self._pending is not None`
（上一条 ACK 未回 ⇒ 让路）；删掉帧基 fallback。修复后 U4：
`batches=8 frames=18 lost=0 rtt=458ms cmd_hz=2.00 fps=4.50` —— 命令间距 = 1/RTT、
整批完整、帧率 = n/RTT，与设计预期逐条吻合。该证据已写入 `stream.py` 类 docstring。

### 12.2 不留旧类名别名（用户拍板）

设计稿 §3/R4 原计划保留 `PullRequester = TelemetryPuller` 兼容视图。用户明确
**不需要保留别名**，下游自行适配。实施：`__all__ = ["TelemetryPuller", "StreamAPI"]`；

`ui/main_window.py` 注释；624 项旧断言**零文本改动**（只改导入名）即全绿。
