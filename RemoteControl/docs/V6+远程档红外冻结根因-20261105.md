# V6+ 远程档「红外读数冻结」根因与修复（2026-11-05）

## 一、现象

上位机看到四路红外（`irF1/irF2/irL/irR`）**不随环境变化**：把车换位置、用手挡传感器，数值一位不变。
没有报错、没有掉线、帧率正常，所以看起来像"上位机解析错了"或"传感器坏了"。

## 二、真机取证：不是"值不对"，是"值不动"

用 `CAL SENSOR` 读固件内部的**原始 ADC**（不是换算后的距离），每 0.8 s 一次，连采 75 s：

```
# t(s)  adcf1  adcf2  adcl  adcr
   0.7       0    293     1   231
  30.0       0    293     1   231
  75.6       0    293     1   231      ← 期间用户在左右传感器前各挡过 3 秒
```

**逐位相同**。`rawf1/rawf2/rawl/rawr` 完全没在更新 ⇒ 冻结发生在 ADC 采样之后、写入 `raw*` 之前（或更早）。

## 三、根因：卡尔曼增益算出 0/0 = NaN

`REMOTE/link_port.c` 的 `LP_SyncOut()` 每个 1 ms tick 都执行：

```c
Qf1 = Qf2 = Ql = Qr = (double)irCfg.kalQ / 10000.0;
Pf1 = Pf2 = Pl = Pr = (double)irCfg.kalP / 10000.0;
```

而 `irCfg` 是**本工程没有 `CORE_Init()` 的遗留空洞**（那条架构里 `CORE_Init` 负责从固件常量填这些镜像结构，
V6+ 是老式固件，没有它）⇒ `irCfg` 恒为 BSS 零 ⇒ `Q = P = 0`。

`adc.c:getdistance()` 里 `kalmanswitch` 默认是 **1**（走卡尔曼分支）：

```c
covf1tmp = covf1 + Qf1;          /* 第一拍 cov=1.0 -> 1.0；之后 cov 已被写成 0 */
kf1 = covf1tmp/(covf1tmp+Pf1);   /* 第二拍起 = 0/(0+0) = NaN */
f1  = f1tmp + kf1*((double)TempL - f1tmp);   /* NaN 传染，永久 NaN */
covf1 = (1-kf1)*covf1tmp;
```

`f1/f2/f/l/r` 全部变 NaN 后，`rawf1 = f1` → `(int)NaN` → 一个固定残值，`disf1 = FindDis(...)` 也跟着定死。
**四路红外从此是"定格的常数"，而且看起来还挺像真的**（本次残值 0 / 293 / 1 / 231）。

### 决定性对照实验（零改动验证）

| 动作 | `adcf1/adcf2/adcl/adcr` | 结论 |
|---|---|---|
| 基线（卡尔曼开，Q=P=0） | `0 / 293 / 1 / 231`，75 s 一位不变 | 冻结 |
| `SETQ IRKALSW 0`（关卡尔曼，`f=TempL` 直通） | `5,7,5 / 37,36,38 / 6,4,3 / 12,11,13` | **立刻活了** |
| `SETQ IRKALSW 1` + `IRKALQ 100` + `IRKALP 2000` | `3,3,2,4 / 38,38,38,37 / 5,4,4,5 / 13,14,13,13` | **也活了** |

两行合起来就把根因钉死了：**问题在 Q/P=0，不在传感器、不在 ADC、不在上位机**。

## 四、为什么上一轮"参数接线"没解决、反而更隐蔽

上一轮把红外阈值（23–28）、`TRACKCOORD`（39）、原点转 PID（47–49）从"死参数"接成了活的，
唯独漏了卡尔曼（29/30）。于是 `Q/P` 继续被 0 推回固件——而且因为阈值现在真的生效了，
**表面上"参数都对了"**，读数却还是死的，更难往这个方向想。

## 五、修法（4 处，全部在 `REMOTE/` 内 ⇒ 比赛档不编译，红线天然不变）

1. **`link_port.c` `LP_SyncIn()`** —— 像阈值那样把卡尔曼回填进镜像（固件是真源）：
   ```c
   irCfg.kalQ = (u16)(Qf1 * 10000.0 + 0.5);
   irCfg.kalP = (u16)(Pf1 * 10000.0 + 0.5);
   irCfg.kalOn = kalmanswitch ? 1u : 0u;
   ```
2. **`link_port.c` `LP_SyncOut()`** —— 加 0 值护栏（挡住上电首拍 / 存储页遗留的 0）：
   ```c
   if (irCfg.kalP != 0 && irCfg.kalQ != 0) { ...推 Qf/Pf... }
   ```
3. **`link.c` `link_ParamApplyOne()`** —— `IRKALQ/IRKALP` 收到 0 视为"未设置"，`break` 保持当前生效值
   （存储页里这两项确实是 0，来自更早的 BSS 时代）。
4. **`link.c` `LINK_Init()`** —— `(void)link_CalibLoad();` 之后**无条件**再跑一次 `link_ParamFromSys()`，
   让 `GET` 显示**实际生效值**。否则存储页的 0 会显示出来，看上去像"参数又坏了"。

### 时序为什么是安全的

`LINK_Init`：`LP_SyncIn`（回填）→ `link_ParamFromSys`（建表）→ `link_CalibLoad`（存储页覆盖）
→ `link_ParamFromSys`（按生效值重建表）→ `LP_SyncOut`（下发）。

每 tick：`LP_SyncIn`（固件→镜像）→ 命令处理（`SETQ` 改镜像）→ `LP_SyncOut`（镜像→固件）。
同一次 tick 内没有第二次 `SyncIn`，所以 `SETQ` 改的值能落地并被下一拍读回，**是恒等回声、不会打架**。

## 七、烧录后怎么验

```bash
cd host
python ir_live_verify.py COM7 --seconds 12     # 采样期间请移动车体 / 挡传感器
```

- **P1 参数**：`IRKALQ` / `IRKALP` 必须非 0（100 / 2000）；阈值 23–28 = 150/60/230/245/240/65
- **P2 抖动**：冻结的特征是**峰峰恒为 0**（逐位相同）。只要有一路有自然抖动，就说明链路是活的
- **P3 响应**：采样期间有动作时，任一路变化 > 20

判定 = `参数正常 且 (有抖动 或 有响应)`。只按"有没有动作"判会把"车静止 + 传感器正常"误判成 FAIL。

> ⚠️ 判传感器真假的正确姿势：**看峰峰，不看绝对值**。冻结是"数字化常数"；
> 而 293 / 231 这种看着很合理的值，恰恰可能是 NaN 留下的残值。
