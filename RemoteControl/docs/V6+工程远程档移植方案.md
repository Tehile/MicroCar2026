# 为 V6+ 比赛工程加装远程档 —— 考察结论与设计方案

> 基线：`code_competition - V6+`（2026-10-29，V6 连续转弯九成速，四档 0/2/4/6mm）
> 参照：`code_competition`（远程档现役，PROTO 10 / FW 314 / host API 2.14.0）
> 本轮只做考察与设计，未改任何源码、未编译、未烧录。

---

## 0. 结论先行

**V6+ 不是"没有远程代码"，而是"有骨架、缺三层皮"。**

分叉时作者完整保留了 `MOUSE_REMOTE` 门控：`#ifndef MOUSE_REMOTE` 共 **42 处**，覆盖 test.c / timer.c /
utility.c / stratagy.c / adc.c / stmflash.c / utility.h；`REMOTE/link.c`、`link.h`、`link_port.c`、
`link_port.h` 四个文件都在位，`USER/Remote/` 里还留着 **2026-10-22 16:59 的远程档完整构建产物**
（`link.o` 355 KB、`TEST_Target_Remote.dep`、`RTE/_Target_Remote/`、`DebugConfig/Target_Remote_*.dbgconf`）。
当时的远程档是能编出来的，ROM 95248 / RAM 13560。

真正缺的是三件事：

| 缺失项 | 现状 | 影响 |
|---|---|---|
| ① `REMOTE/link.c` + `link.h` 版本 | **v9.1（FW 311 / PROTO 9）**，10-21 快照 | 与现役 host（按 PROTO 10 解帧）不兼容，建图增量通道缺失 |
| ② `USER/TEST.uvprojx` 的 `Target_Remote` | **已被删除**，只剩 V6_0mm/2mm/4mm/6mm 四个比赛 Target | 无法选档、无法编译、无法烧录远程档 |
| ③ 构建脚本 / 文档 | `build_competition_modes.py` 硬编码 `code_competition` | 无红线校验，改完无法自证比赛档没动 |

外加一个**必须先处理的编码陷阱**：`UTILITY/utility.c` 是 **UTF-8 + CRLF**，而 `test.c`/`timer.c`/
`stratagy.c`/`utility.h`/`stmflash.c` 等是 **GBK + CRLF**。同一工程混编码，用错工具回写会让中文注释
整段变 `锟斤拷`（V6+ 里已有的乱码注释就是这么来的），且 GBK 写盘若先截断再编码失败会留下 0 字节文件。

## 3. 需要拍板的两个设计决策

### D1（核心）：远程档跑哪一套算法？

这是本次移植唯一有实质分歧的地方。

**现状事实**：V6+ 把 V5/V6 的能力全部在远程档关闭了 ——
V5 停车前置复核、V6 连续弯九成速、Grid90 冲刺、V5 掉头限幅，远程档一律不编译。
也就是说，**当前结构的远程档跑的是 V3/V4 时代的运动逻辑**，你用它观察不到 V6 的真实行为。

根因不只是"作者想隔离"，还有一条**连带依赖**：`v5_diag` 定义在 `stmflash.c` 的 `#ifdef FLASHSAVE` 里，
而 `FLASHSAVE` 只在 `#ifndef MOUSE_REMOTE` 时定义（为了关飞行记录省 9.5 KB RAM），
于是"关飞行记录"顺带把 V5 诊断和 V6 连续弯状态字节一起关掉了。

| | 方案 A：1:1 恢复现状 | 方案 B：保真远程档 |
|---|---|---|
| 做法 | 只补 G1–G8，门控一处不改 | 新增 `REMOTE_FULL`，把 42 处 `#ifndef MOUSE_REMOTE` 改为 `#if !defined(MOUSE_REMOTE) \|\| defined(REMOTE_FULL)`；把 `v5_diag` 定义从 `FLASHSAVE` 块解耦 |
| 远程档行为 | = V3/V4 算法，与比赛档**不一致** | = V6 比赛算法，仅关飞行记录 |
| 工作量 | 小（换 2 个文件 + 工程配置） | 中大（42 处门控 + 新路径补钩子 + 时序重验） |
| 风险 | 极低，比赛档 hex 天然不变 | 需要重跑 V6 的真机验收 |
| 调试价值 | 只能看链路/流程/建图 | 能看真实 V6 行为、真实圈速 |
| RAM | 13560 | 13630 + `v5_diag`(≤256) + V6 表项 ≈ 14.0 KB，仍有余量 |

**建议：分两步，A 先落地，B 作为目标形态。**

理由：A 的价值是先把"能编、能烧、能通链路"这条底线恢复（1 次编译 + 1 次 PING 就能验收），
不引入任何对比赛档的风险；B 的价值才是长期价值，但它会改动 42 处门控，必须独立一轮、独立验收。
如果直接上 B，一旦某处门控改错，比赛档 hex 变了也难定位是哪一处。

**若选 B，必须额外处理三件事**（现状里没有）：
1. `v5_diag` 定义从 `#ifdef FLASHSAVE` 移到独立门控（+256 B RAM，`search_guard_v5.h:41`
   有 `sizeof<=256` 的静态断言兜底）。
2. **V6 新高保真路径缺中止钩子**：`gridPath90()`、`spurt_grid90()`、`gridFastStraight90()`、
   `gridSearchWait90()` 的循环里都没有 `LP_AbortRequested()` 判断（作者假设远程档不跑它们）。
   不补的话，高保真远程档下 `MAZE STOP` 无法中止冲刺 —— 这是踩过的坑，必须补。
3. `test.c` 的 Grid90 冲刺分支会擦 6 页 Flash（≈118 ms 黑窗），远程档发车空窗判据需重新标定。

### D2：Remote Target 做 1 个还是 4 个？

V6 的 4 个 Target 只差 `GOAL_DEPARTURE_EXTRA_MM=0/2/4/6`（终点掉头后的起步附加毫米）。

- **1 个（`Remote_0mm`，推荐）**：远程档用于调试，0mm 基线就够；少 3 份构建、少 3 份维护。
- 4 个：若需要"用远程档复现某档比赛行为"（只有 D1 选 B 时才真正需要），则要做 4 个。

若 D1 选 A，这四个参数对远程档**毫无意义**（V3 算法里根本没有 `GOAL_DEPARTURE_EXTRA_MM` 的消费点，
`utility.c:31-36` 的兜底值为 0），做 1 个就够。

## 4. 实施设计（M1，A 路线）

### 4.1 协议层同步

```
code_competition/REMOTE/link.c   →  code_competition - V6+/REMOTE/link.c
code_competition/REMOTE/link.h   →  code_competition - V6+/REMOTE/link.h
```

- **字节级复制**（`copy /b` 或 python `read/write binary`），不能走会重编码的编辑器。
- 两个文件都是整文件 `#ifdef MOUSE_REMOTE` 门控 + GBK + CRLF，原样搬运即可。
- 搬完核对：`LINK_PROTO_VER=10`、`LINK_FW_VER=314`、文件大小 130014 / 39298。
- **不要动** `link_port.c/h`（两侧已逐字节相同，改了反而引入差异）。

v10 相对 v9.1 的实质变化（会影响验收口径）：
- 帧长仍 30 B，但**字段偏移整体前移 5 B**：`irMm[4]` u16→u8、`batt` mV→mV/50、`encAng` 删除。
- 腾出的 7 B 成为**建图增量通道**（偏移 23 头 + 24..29 三条 2 B 条目），数据源是 `LINK_Tick`
  1 kHz 采样 `GmcMouse` 变化，环深 32 条（RAM +64 B）。
- 采样逻辑纯在 `link.c` 内，不碰 `utility.c` ⇒ 比赛档天然安全。

### 4.2 uvprojx 追加 Target_Remote

在 `<Targets>` 内**末尾追加**第 5 个 `<Target>`，从 `V6_0mm` 块整体克隆后只改 6 个字段：

| 字段 | V6_0mm 现值 | Target_Remote 目标值 |
|---|---|---|
| `<TargetName>` | `V6_0mm` | `Target_Remote` |
| `<ToolsetNumber>` | 同 | 同 |
| `<Define>`（Cads 内） | `STM32F10X_MD,USE_STDPERIPH_DRIVE,GOAL_DEPARTURE_EXTRA_MM=0` | `STM32F10X_MD,USE_STDPERIPH_DRIVE,MOUSE_REMOTE,EN_USART1_RX` |
| `<IncludePath>` | `...;..\SYSTEM;.\RTE\_V6_0mm` | 同上但末段换 `.\RTE\_Target_Remote` |
| `<OutputDirectory>` | `.\Build\V6_0mm\` | `.\Remote\` |
| `<OutputName>` | `TEST_V6_0mm` | `TEST` |
| `<ListingPath>` | `.\Build\V6_0mm\` | `.\Remote\` |

其余（Device / Cpu / IRAM / IROM / Optim=1 / CreateHexFile / ScatterFile 空 / 文件组 G1–G7 全同）
保持与 V6_0mm 一致 —— 远程档与比赛档共用同一份文件列表，`REMOTE/*.c` 本就在 `USER` 组里。

**硬性约束**：
- 既有 4 个 `<Target>` 的**顺序和内容一个字节都不能动**（历史脚本的正则按顺序取档位）。
- 只追加，不重排；`<Targets>` 之外的 `<TargetOption>`/`<CommonProperty>` 不碰。
- 文件必须以 **CRLF + GBK** 写回（`TEST.uvprojx` 现状即如此）。

### 4.3 uvoptx 追加

`TEST.uvoptx` 里 `<Target>` 条目需要同步追加一个 `Target_Remote` 块，否则 Keil 打开后 Target 列表
与调试器配置对不上。可以从 `code_competition/USER/TEST.uvoptx` 的 `Target_Remote` 块克隆，

`RTE/_Target_Remote/RTE_Components.h` 与 `DebugConfig/Target_Remote_STM32F103RB_1.0.0.dbgconf`
**已存在**，无需新建。

### 4.4 构建脚本

`build_competition_modes.py` 里 `FW = .../"code_competition"` 与 `TARGETS` 列表是硬编码的。
建议新增 `--project` 参数并让 `TARGETS` 按工程读取，或直接复制出 `build_v6_modes.py`。
后者更快、对现役脚本零风险，缺点是两份要同步维护 —— 建议先用后者，稳定后再合并。

脚本要具备的能力（对齐现役）：
1. 逐 Target `UV4 -b -t "<name>"`，从日志抓 `Program Size` 行。
2. **UV4 exit code 不可靠**，一律以日志里的 `N Error(s)` 判定。
3. 全量重编前先删该 Target 输出目录的产物（`.o/.d/.crf/.lst/.lnp/.dep/.axf/.hex/.map/.htm`）。
4. 比赛档 hex 与基线 sha256 比对（红线），不一致即失败退出。
5. 远程档额外打印 ROM/RAM，并检查 `FW 314 / PROTO 10` 是否出现在 hex 的版本常量附近（可选）。

### 4.6 编码纪律（本次新增，与旧记忆不同）

| 文件 | 编码 | 换行 |
|---|---|---|
| `UTILITY/utility.c` | **UTF-8** | CRLF |
| `UTILITY/utility.h`、`search_guard_v5.h`、`search_turn_v6.h` | GBK / ASCII | CRLF |
| `USER/test.c`、`HARDWARE/TIMER/timer.c`、`STRATAGY/stratagy.c`、`HARDWARE/STMFLASH/stmflash.c` | GBK | CRLF |
| `HARDWARE/ADC/adc.c`、其余 SYSTEM/HARDWARE | ASCII | CRLF |
| `REMOTE/*` | GBK | CRLF |
| `TEST.uvprojx` / `TEST.uvoptx` | GBK | CRLF |

**规矩**：
- 改哪个文件就用哪个文件的编码往返：`open(p,'rb').read().decode(enc)` → 修改 → `open(p,'wb').write(s.encode(enc))`。
- 写盘必须**先 encode 再 open('wb')**，不能先 open 再 encode（编码失败会留 0 字节文件，踩过）。
- `utility.c` 的 UTF-8 尤其危险：用 GBK 工具回写会把全文中注释变成乱码（V6+ 里已有的乱码就是这么来的，
  不影响编译但会污染 diff）。
- 改完用 `git diff --stat` 确认没有整文件重写（行数变化应与改动量同量级）。

## 5. 实施设计（M2，B 路线，可选）

只列要点，规格待 M1 完成后再细化。

### 5.1 门控升级

新宏 `REMOTE_FULL`，由 Target_Remote 的 `<Define>` 追加传入。替换规则：

```c
#ifndef MOUSE_REMOTE
   ↓
#if !defined(MOUSE_REMOTE) || defined(REMOTE_FULL)
```

**例外（保持门控，不跟随 `REMOTE_FULL`）**：
- `stmflash.c:12-14`、`timer.c:36-38`、`test.c:18-20` 三处 `#define FLASHSAVE` —— 飞行记录必须继续关，
  否则 RAM 直接爆 9.5 KB。
- `test.c` 里 `#include "link.h"` 那类是 `#ifdef MOUSE_REMOTE`，方向相反，不动。

### 5.2 `v5_diag` 解耦

```c
#ifdef FLASHSAVE
const u16 save_num=1136;
volatile V5_STOP_DIAGNOSTICS v5_diag={0};   /* ← 从这里移出 */
const u8 per_timer=2;
#endif
```
改为：
```c
#ifdef FLASHSAVE
const u16 save_num=1136;
const u8 per_timer=2;
#endif
#if !defined(MOUSE_REMOTE) || defined(REMOTE_FULL)
volatile V5_STOP_DIAGNOSTICS v5_diag={0};   /* V5/V6 状态字节, 远程保真档也要 */
#endif
```
`search_guard_v5.h:41` 已有 `sizeof(V5_STOP_DIAGNOSTICS)<=256` 的静态断言，超了会直接编译失败。

### 5.3 新高保真路径补中止钩子

### 5.4 容量与验收

预估 RAM ≈ 14.0 KB / 20 KB，ROM ≈ 97–98 KB / 128 KB。M2 完成后必须**重跑 V6 的实车验收**
（连续弯九成速、终点 4mm 起步、冲刺曲线），因为门控打开后远程档与比赛档的行为应完全一致，
这是 M2 的核心验收标准：**同一条路线，两档的转弯计数、速度曲线、圈速应可逐帧对比**。

## 6. 验收计划

### 6.1 编译级（M1 必过）

1. 先用 `build_v6_modes.py` 重编 4 个比赛档，确认 hex 与 §4.5 基线**逐字节相同**（改工程前先跑一遍，
   确定基线本身是新鲜的）。
2. 追加 `Target_Remote` 后再编 4 个比赛档 —— 必须仍逐字节相同。**这一步是"没动比赛代码"的唯一证据。**
3. 编译 `Target_Remote`：0 error，记录 ROM/RAM。
4. 检查产物落在 `USER/Remote/TEST.hex`，且 `USER/TEST.hex`（比赛档）未被覆盖。

### 6.2 静态级

1. 用本轮的预处理模拟器复跑一遍，确认远程档编译区内无 V5/V6 符号泄漏（M1 应保持现状结果）。
2. 确认 `REMOTE/link.h` 的 `LINK_PROTO_VER==10`、`LINK_FW_VER==314`。
3. `git diff --stat` 确认只改了预期文件，且 `utility.c` 没有被整文件重写。

### 6.3 真机级（M1）

沿用现役脚本，**不得自行发明新流程**：

| 步骤 | 脚本 | 判据 |
|---|---|---|
| S0 链路 | `host/v9_pull_verify.py`（S0–S4） | PING/PONG、FW=314、PROTO=10 |
| S1 零运动 | 同上（零运动段） | 帧率 N=4/5、交付率 1.000 |
| S2 LED/基准灯 | `host/led_bit_verify.py --mark-n 2` | led4 中位 1049±，发车全 1 窗口 |
| S3 发车/中止 | `host/launch_blackout.py --mark-n 2` | 空窗 ≤250 ms、`halt_ok=true` |
| S4 收车 | `force_idle()` 定式 | STOP→ESTOP→RESET 三级都通 |

**安全红线（不变）**：`--mark-n 2`；不要用 `RATE FIX`；发车前确认低电闸；链路断死时软件收车网无效，
必须人工停车 + 断电。
