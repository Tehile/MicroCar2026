# 通信协议 v10 —— 字段瘦身 + 建图增量通道（已落地）

> 状态：**已落地**（2026-10-23）。基线 v9.2.1（`PROTO 9` / `FW 313` / 帧载荷 30 B），
> 目标产物 `PROTO 10` / `FW 314` / 帧载荷 **30 B**。
> 目标：把 IR / 电池 / 编码角三项瘦身腾出的 **7 B** 用于「电脑鼠内部建图的实时同步」。
>
> 结论：**可行，且比"每帧存 5~7 条"的原始设想更稳** —— 带宽 3 条/帧就够（7.5 倍余量），
> 真正该加的是**缓冲深度 32 条**（RAM 64 B），两者不是一回事。

---

## 0 结论速览

| 项 | 决策 | 依据 |
|---|---|---|
| `irMm[4]` u16→u8 | ✅ 已落地，省 **4 B** | 全部红外阈值 ≤ 245 mm < 255，饱和不改变任何判决 |
| `battMv` u16→u8 | ✅ 已落地，省 **1 B** | 取 `round(mV/50)`，低电闸 7000 mV ↔ 140 整数，零量化误差 |
| `encAng` 删除 | ✅ 已落地，省 **2 B** | 上位机唯一消费者是 monitor 一行显示，无算法依赖 |
| 腾出的 7 B | 全部给建图增量通道 | 变长尾部虽更省字节，但本链路速率由 RTT 决定，与帧长无关（见 §4.5） |
| 帧总长 | **仍 30 B 定长** | 帧长不变 ⇒ `len == 30` 断言、RingBuffer 宽度假设全部保持有效 |
| 每帧带宽 | **3 条**，每条 **2 B** | 实际需求 ≤2 条/拉取周期，供给 15 条 ⇒ 余量 7.5 倍 |
| 每条编码 | **自带绝对坐标**（用户拍板） | 链式 1 B/条 能省一半，但容量有 7.5× 余量；链式一旦某条方向错会**静默污染整批** |
| 缓冲深度 | **32 条**（固件 RAM 64 B） | 覆盖 14.4 s 搜索 / 4.1 s 冲刺的完全静默 |
| 锚点 | **每条都带**，不再单设 anchor 字节 | 帧自包含，单条错最多错一格 |
| 方向字段 | **不上帧**，由坐标差反推（固件只用来判"是否单步"） | 与坐标自洽，免疫掉头/坐标跳变/回绕 |
| 固件改动面 | **只在 `REMOTE/`**（link.h / link.c） | 采样在 `LINK_Tick`，不动 `utility.c`/`test.c` ⇒ 比赛档 hex 逐字节不变（已复核） |
| 版本 | `PROTO 9→10`、`FW 313→314`、host API `2.13.0→2.14.0` | 帧长不变但字段偏移变，仍属不兼容 |

## 1 三项裁剪的评估

### 1.1 `irMm[4]`：u16 × 4 → u8 × 4（省 4 B）

**可行性判据不是"距离多大"，而是"判决点会不会被饱和切掉"**。
固件里所有红外判决都是"小于阈值"形式，阈值来自参数表（`irCfg`）：

| 阈值 | 默认值 | 用途 |
|---|---|---|
| `thrCritical` | 60 | 侧墙临界 |
| `thrFrontNear` | 65 | 前墙"贴脸" |
| `thr45` | 150 | 45° 斜看 |
| `thrFrontLo` | 230 | 前墙远距-低 |
| `thrFrontMid` | 240 | 前墙远距-中 |
| `thrFrontHi` | 245 | 前墙远距-高 |

上界 245 < 255 ⇒ **饱和到 255 不改变任何一条 `<thr` 的判决**。

**硬约束**：参数表里任何红外阈值必须 **≤ 254**。当前默认最大 245，安全；
但 `SET` 命令能写任意 u16，故 host 侧需钳位（`SET` 路径拒绝 >254 的红外阈值）。
**这是本项唯一的真风险。**

**代价**：>255 mm 的真实距离不可见（饱和）；远墙标定本来就以 245 为上限，实际无损失。
`analyze.ir_range_curve` 的曲线会在 255 处截平，文档已写明。

### 1.2 `batt`：u16 mV → u8（省 1 B）

**编码**：`batt = (mv + 25) / 50`，即 **50 mV/LSB**，0..255 ⇒ 0..12750 mV。

- 低电闸 `LAUNCH_MIN_MV = 7000` ↔ **140 整**，零量化误差（`7000/50 = 140`）。
- 量化误差 ±25 mV，远小于电池 IIR 本身的噪声。
- 3S（12.6 V）也能表示（252），2S 满电 8.4 V → 168，留足余量。

**为什么不用百分比**：锂电电压-容量曲线非线性，百分比要查表，且**恰好在闸门附近丢精度**
—— 而闸门是这个字段唯一有硬性用途的地方。上位机拿到 `batt × 50` 的 mV 再决定要不要换算。

### 1.3 `encAng` 删除（省 2 B）

全仓盘查过，上位机唯一消费者是 `monitor.py` 的一行显示，无算法/标定/控制依赖
（`calib.py` 里的 `encAngleRatio` 是**参数**，走 `GET/SET`，与帧无关）。

**但"可由 trackL/trackR 换算"要打个折**：固件的 `angle` 经过 `angleratio` 缩放，
且转弯时会被 `setangle()` 重置基准，host 用 `trackL/trackR` 复算只能得到**相对角**，
绝对值无法逐位复现。当前没人在乎（唯一消费者是显示），但**如果将来要做"角度-里程一致性对拍"，这 2 B 得还回来**。

## 2 建图增量通道：数据从哪来（代码证据）

### 2.1 唯一的"走一格"路径

```c
// utility.c:355
void __mouseCoorUpdate(void) {
    switch (GucMouseDir) {
    case 0: GmcMouse.cY++; break;   // 0 = +Y
    case 1: GmcMouse.cX++; break;   // 1 = +X
    case 2: GmcMouse.cY--; break;   // 2 = -Y
    case 3: GmcMouse.cX--; break;   // 3 = -X
    }
    __wallCheck();                  // ← 同一函数里紧接着写墙图
}
```

调用点共 4 处：`utility.c:765 / 1096 / 1130`、`test.c:1248`。
**全部是"坐标 ±1 然后立刻写墙"**，没有例外。

`__mouseCoorUpdate_Fast(num)`（utility.c:385）能一次跳 `num` 格，但**全仓零调用点，是死代码**
—— 本方案必须把它钉死为"禁止启用"。

### 2.2 `GucMapBlock` 的真实语义（容易搞反，务必钉死）

```c
GucMapGet[x][y] = 1;                 // 访问标记
ucMap  = MOUSEWAY_B;                 // 来路恒通
if (lefthaswall)   ucMap &= ~MOUSEWAY_L;  else ucMap |= MOUSEWAY_L;
if (forwardhaswall)ucMap &= ~MOUSEWAY_F;  else ucMap |= MOUSEWAY_F;
if (righthaswall)  ucMap &= ~MOUSEWAY_R;  else ucMap |= MOUSEWAY_R;
ucMap &= 0x0F;                                  // 低半字节 = 四向可通位
GucMapBlock[x][y] = ucMap | (ucMap << 4);       // 复制到高半字节(未探明位)
// 再按"我这面有墙"清邻居的高半字节对应位(0xdf/0x7f/0xef/0xbf)
```

- **低半字节 = 四向可通位**：`bit0 = +Y`、`bit1 = +X`、`bit2 = -Y`、`bit3 = -X`。**1 = 通，0 = 有墙**。
- **高半字节 = 同向"未探明"位**：初值 `0xf0`。本格判定出"这面有墙"时，去清**邻居**的对应位
  （`0x10 << d`：0x10=+Y、0x20=+X、0x40=-Y、0x80=-X）。
- 写入**带门控**：只有本格低半字节原为 `0x00` 才写。所以重复访问不会覆盖（也因此**幂等**）。
- 洪水填充 `mapStepEdit()` 用 `& 0x01/0x02/0x04/0x08` 判"能不能走" ⇒ **1 = 可走**，与上面一致。

> ⚠ 项目里已经踩过"注释把 0xFF 写成未访问"的坑（`link_port.c:291` 的过时注释）。
> 本方案所有材料统一口径：**低半字节 1 = 可通**，host 侧显示墙时才取反。

### 2.3 采样点选在 `LINK_Tick`，而不是 `__wallCheck`

| 方式 | 侵入面 | 红线风险 | 精度 |
|---|---|---|---|
| A. 在 `__wallCheck()` 里加 `#ifdef MOUSE_REMOTE LINK_MapDeltaPush(...)` | `utility.c`（比赛档也编） | ⚠ 高：`#ifdef` 写漏就改比赛档产物 | 指令级 |
| **B. 在 `LINK_Tick`（1 kHz）里采样 `GmcMouse` 变化** ✅ | **只在 `REMOTE/link.c`** | ✅ 零（`utility.c`/`test.c` 一字不动） | ≤1 ms |

选 **B**，三条理由：

1. `GmcMouse` / `GucMouseDir` / `GucMapBlock` 的 `extern` **已在 `link_port.h:129-133`** ⇒ 零新增依赖。
2. 一格最短 129 ms（冲刺极限），1 kHz 采样不可能漏格。
3. 比赛档根本不编 `REMOTE/*.c` ⇒ 红线天然安全（仍按铁律复核 hex）。

**采样保护（关键）**：ISR 可能正好抢占在 `GmcMouse.cY++` 与 `__wallCheck()` 之间。
此时该格低半字节还是初值 `0x00` ⇒ 会把"四向全封死"写进增量链，**污染整张图**。

对策：**低半字节为 `0x00` 就本 tick 不记，下 tick 再采**。因为 `__wallCheck` 无条件置"来路可通"位，
写完后低半字节**必非 0** ⇒ 下一 tick 必然采到正确值。自愈，无需重试逻辑。

### 2.4 非单步 = 坐标跳变

推送时用 **s16 差值**判定单步（`|dx| + |dy| == 1`），不是 `mod 16` 回绕：

- 迷宫 16×16 坐标恒在 0..15，本就不需要回绕；
- 而 `mod 16` 会把"越界后 &0x0F"误判成单步（`16 & 0x0F == 0`，从 15 看就是 +1），**静默错一格**。

真正的跳变来自 `test.c:772-790` 起步时把 `cX` 由 0 搬到 15 并整列搬图，以及 `CAL ERASE` 后地图被清。
跳变时**清环 + 置 `resync`**，以当前格重开序列。跳变每轮最多发生一次（且发生在起步前，环本来就是空的）。

## 3 帧格式（v10，30 B 定长）

```
偏移  长度  字段          说明
----  ----  ------------  --------------------------------------------------------
 0     1    ms8           设备毫秒时基低 8 位
 1     4    irMm[4]       u8 ×4：F1 F2 L R（mm，饱和 255）
 5     1    batt          u8：round(mV/50)，140 = 7000 mV
 6     2    speedL        s16 cm/s
 8     2    speedR        s16 cm/s
10     2    gyro          s16 陀螺积分角
12     2    trackL        s16 左轮相对里程 mm
14     2    trackR        s16 右轮相对里程 mm
16     1    stateA        位打包（不变）
17     1    stateB0       位打包（不变）
18     1    stateB1       位打包（不变）
19     1    stateC        位打包（不变）
20     1    flags         LINK_FLAG_*（不变）
21     1    pos           posX(4) | posY(4)（不变）
22     1    spurt         冲刺上下文（不变）
23     1    mapHdr        count(0..3, bit0-1) | lossy(bit2) | resync(bit3) | 预留
24     2    mapEntry[0]   byte0 = open4(bit0-3) | 预留；byte1 = x(bit0-3) | y(bit4-7)
26     2    mapEntry[1]   同上
28     2    mapEntry[2]   同上
----  ----  ------------  --------------------------------------------------------
             合计 30 B（与 v9 相同；线上帧仍 38 B，帧开销 8 B 不变）
```

与 v9 相比：**偏移 6..22 整体前移 5 B**（`encAng` 删 2、`irMm` 缩 4、`batt` 缩 1，共 −7；尾部加 7），
**帧长不变**。`stateA/B0/B1/C/flags/pos/spurt` 的位定义一字不改。

### 3.1 为什么每条都带绝对坐标（用户拍板）

原方案是"1 B 锚点 + 每条 1 B（方向 2 bit + 可通位 4 bit）"，5 条/帧。

改成每条 2 B 后：

| | 链式（原方案） | 绝对坐标（现行） |
|---|---|---|
| 每条 | 1 B | **2 B** |
| 每帧容量 | 5 条 | **3 条** |
| anchor 字节 | 需要 1 B | **取消**（每条自含位置） |
| 供给/周期（5 帧一批） | 25 条 | **15 条** |
| 需求/周期 | 2 条 | 2 条 |
| **余量** | 12× | **7.5×** |

链式编码**唯一的收益是容量**，而容量有 7.5 倍余量。用"整批数据相互依赖"换一个用不上的指标，
换来三个实际风险/成本：

1. **错误会扩散**：某条方向错（或固件哪天启用了 `__mouseCoorUpdate_Fast`），后面所有条目的格子
   都会被平移到错误位置，而且**看不出来**。现在一条错最多错一格，下一条自动纠正。
2. **host 侧代码复杂**：`mod 16` 走格、链传播校验、anchor 维护、"走完应等于 pos"那套交叉验证，
   全部消失，只剩"读 pos → 写 map"。
3. **单帧不能独立解读**：抓包看到一帧要先找序列起点。

### 3.2 `mapHdr`（偏移 23）

| bit | 名称 | 含义 |
|---|---|---|
| 0-1 | `count` | 本帧携带的条目数 **0..3** |
| 2 | `lossy` | 自上一帧以来发生过环形缓冲溢出（丢过最旧）⇒ 前面有洞 |
| 3 | `resync` | 本批是新序列起点（发车/新图/坐标跳变/上电）⇒ host 应把它当新锚 |
| 4-7 | 预留 | 必须填 0 |

### 3.3 `mapEntry[k]`（偏移 24..29）

| 字节 | bit | 名称 | 含义 |
|---|---|---|---|
| byte0 | 0-3 | `open4` | 该格四向可通位，**`GucMapBlock[x][y] & 0x0F` 原值**（1=通） |
| byte0 | 4-7 | 预留 | 必须填 0 |
| byte1 | 0-3 | `posX` | 格坐标 x（0..15） |
| byte1 | 4-7 | `posY` | 格坐标 y（0..15） |

> `open4` **刻意保持"可通位"语义，不转成"有墙位"**：与固件一一对应，host 显示时取反即可。
> 中间转一道手最容易出反相 bug（本项目已有先例），能省一次就省一次。
>
> 注意 `open4` 是**绝对方向**，而 `stateC` 的 `wallLeft/Front/Right` 是**相对朝向** ——
> 两个字节不能用同一套宏。

`dir` 字段**不上帧** —— host 需要时用 `pos[k] - pos[k-1]` 自己算。

### 3.4 与 `pos` 字段的关系

`pos`（偏移 21）仍是**实时当前位置**，与增量链互为交叉校验，但**不作为锚点**。
稳态下 `pos` 等于最后一条 entry 的格子；host 只在 `count < 3` 时拿它对照（`pos_mismatch_n` 告警，**不丢批**）。

## 4 固件侧实现（已落地）

### 4.1 环形缓冲

```c
/* 仅 #ifdef MOUSE_REMOTE（link.c 整文件门控） */
typedef struct { u8 pos; u8 open4; } LinkMapD;   /* pos = x | y<<4 */
static LinkMapD linkMapD[LINK_MAPD_DEPTH];       /* 32 条 = 64 B RAM */
static u8 linkMapDHead;   /* 写指针: 采样推进 */
static u8 linkMapDTail;   /* 读指针: 组帧消费 */
static u8 linkMapDLossy;  /* sticky */
static u8 linkMapDResync; /* sticky */
static u8 linkMapDPrevOk;
static s16 linkMapDPrevX, linkMapDPrevY;
```

**只存 2 B/条**：`pos`（绝对坐标）+ `open4`。时间戳不进环 —— 逐格耗时可用"帧到达时刻 ± 一帧（59 ms）"近似，够用。

### 4.2 采样与入环（`LINK_Tick` 内，1 kHz）

```
若 (!prevOk) { prev = GmcMouse; prevOk = 1; return; }        /* 首次：只建立基线 */
若 (坐标与 prev 相同) return;
若 (坐标越界 0..15) { prev = cur; return; }                  /* 不入环, 防越界索引 */
o4 = GucMapBlock[x][y] & 0x0F;
若 (o4 == 0x00) return;                                      /* §2.3：__wallCheck 还没跑完 */
若 (非单步) link_MapReset();                                 /* 清环 + resync */
link_MapPush(pos = x | y<<4, o4);
prev = cur;
```

调用点在 `LINK_Tick` 的最前面（`LP_SyncIn()` 之后），越早采到，本 tick 组帧就越新鲜。

### 4.3 为什么不需要临界区

采样（push）与组帧（pop）**都在同一个 SysTick ISR 里** ⇒ `head`/`tail` 同上下文，
SPSC 退化成一个上下文，`__disable_irq()` 可以省。这是"采样法"相对"挂钩 `__wallCheck`"的第二个好处
（第一个是零侵入）。

> **如果将来把 push 挪回任务上下文**，就必须补回临界区：
> ```c
> u32 pm = __get_PRIMASK(); __disable_irq();
> /* 写 2 字节 + 推进 head */
> __set_PRIMASK(pm);   /* 必须保存/恢复, 不能盲目 __enable_irq() */
> ```

### 4.4 组帧与 tail 推进

```c
mn = (head - tail) & (DEPTH-1);  if (mn > 3) mn = 3;
hdr = mn | (lossy ? LOSSY : 0) | (resync ? RESYNC : 0);
pl[U_MAPHDR] = hdr;
for (k = 0; k < 3; k++) {
    if (k < mn) { b0 = linkMapD[(tail+k)&(DEPTH-1)].open4; b1 = ...pos; }
    else        { b0 = 0; b1 = 0; }          /* count=0 时绝不填上次残值 */
    pl[U_MAPENT + 2*k] = b0;  pl[U_MAPENT + 2*k + 1] = b1;
}
d0 = linkDrop;
link_SendFrame(LINK_TYPE_UNIFIED, pl, LINK_UNIFIED_LEN);
if (linkDrop == d0) {                        /* 只有真的写进 TX 环才推进 */
    tail = (tail + mn) & (DEPTH-1);
    lossy = 0;  resync = 0;
}
```

**判据为什么用 `linkDrop` 快照**而不是给 `link_SendFrame` 加返回值：那个函数是两档共用的老函数，
改签名属于动红线面上的东西；用快照零侵入，且 `link_SendFrame` 本来就是"整帧丢弃或全成功"二选一，
快照比对完全够用。

> **铁律**：整帧被丢（`linkDrop++`）时 tail **原地不动**，下一帧原样再带一遍。
> 因为每条自带绝对坐标，重发是幂等的。

### 4.5 为什么不做变长尾部

帧头已有 `LEN`，把载荷做成 `23 + 1 + 3×2` 完全合法，空帧能省 7 B。**但不做**：

> `RTT 恒 300–310 ms`，全部发生在 PC 侧 CH340，**与帧长无关**；帧率 = N / RTT。

即当前链路是**"往返受限"而不是"字节受限"** —— 把帧缩短 7 B 一点速率都换不来，
反而要改掉所有 `assert len == 30` 的断言、CSV 宽度假设、`link_TxPut` 的空间估算。

### 4.6 实际资源

| 项 | v9.2.1 | v10 |
|---|---|---|
| 远程档 ROM | 96808 B | **97352 B**（+544） |
| 远程档 RAM | 13568 B | **13640 B**（+72 = 环 64 + 5 个静态字节 + 对齐） |
| 比赛档 hex | `68ad6be2…8141` | **逐字节相同（PASS）** |

## 5 上位机侧（已落地）

### 5.1 通道与偏移

- `UNIFIED_CHANNELS`：删 `encAngle` ⇒ **32 项**（v9.1 是 33）。
- `irMm` 四项保留，值域由 0..65535 变 0..255。
- `battMv` 通道名**保留**（CSV 表头不变），解码时 `batt × 50` 还原成 mV，低电闸逻辑零改动。
- `decode_unified()` 额外返回 `d["mapd"] = {"count","lossy","resync","entries"}`；
  `pack_unified()` 做成对偶（sim 要能造帧）。
- 帧长断言 `len == 30` **全部保持有效**（这正是选定长的好处）。

### 5.2 `MapReplayer`（`host/host/api/mapd.py`）

```python
rp = MapReplayer(16)
for frame in frames:            # frame 是 decode_unified() 的结果
    rp.apply(frame)
rp.wall[x][y]                   # 与固件 GucMapBlock 逐字节相同（1 = 可通）
rp.walls(x, y)                  # {'N': True, ...} True = **有墙**（已取反）
rp.stats()                      # frames/entries/applied/cells/holes/resync/lossy/pos_mismatch
```

`_write()` **逐行照抄固件 `__wallCheck()`**：

```python
if (wall[x][y] & 0x0F) != 0: return   # 固件的写入门控 —— 漏了就不能逐字节相同
wall[x][y] = open4 | (open4 << 4)
for d in 0..3:
    if not (open4 >> d) & 1:
        wall[邻居(x,y,d)] &= ~(0x10 << d)
```

> 那条**门控**是关键：不加它，重复应用同一批会把邻居后来清掉的"未探明"位重置回去，
> 重建图就与固件不一致了。加上它，重复应用天然幂等。

`visited[x][y]` = 该格是否出现在任何一条 entry 里。**顺带解决了老问题**：
`CAL BLOCK` 从来不填 `mapVisited`（`link.c:2397-2411` 只写 `mapWall`），访问图恒全 0；
现在 host 自己就能给出真实访问图。

### 5.3 已知边界：起点格不在增量流里

固件上电后第一个采样 tick 只建立坐标基线，而起点格的 `GucMapBlock` 低半字节仍是初值 `0x00`
（`__wallCheck()` 只在"走进某格"时跑），所以起点格**永远不会入环**。

这与固件实际的 `GucMapBlock` 状态一致（固件那边它也是 0）⇒ host 重建图缺它**不是丢数据**。
起点信息本来就要靠 `CAL BLOCK` / `pos` 补。

### 5.4 输出

- 固定 32 列 CSV 照旧；增量条目**不进 CSV**（它是变长列表），由 `MapReplayer` 内部维护。
- `monitor.py`：`encAngle` 那行删掉，改为「地图 +n / re / LY」。
- `ui/status_panel.py`：新增「建图」字段（已重建格数 / 累计条目 / 洞数），用 `_seq` 去重，
  `resync` 时清图重来。

## 6 时序分析

### T1 节拍测算

| 量 | 值 | 来源 |
|---|---|---|
| 迷宫格距 | **180 mm** | `utility.c:760/799/832` 的 `while(track<180)` |
| 搜索速度 | 400 mm/s（`speed_ss=40` cm/s） | `timer.c:54` |
| ⇒ 搜索每格耗时 | **≈450 ms** | 计算 |
| 冲刺上限 | `LTopSpeed=140` cm/s ⇒ 180 mm ≈ **129 ms/格** | `utility.c:1261` 等 |
| 单帧间隔（N=5） | **≈59 ms**（17.0 Hz，RTT≈300 ms） | `docs/链路MTBF压测方法.md` |
| 批次模型周期 | 一批 5 帧（59 ms）+ 命令往返（≈300 ms）≈ **360 ms** | v9.2 复合命令 |
| 每周期产出条目 | 搜索 **0.8 条** / 冲刺 **≈2 条** | 计算 |
| 每周期供给能力 | **5 帧 × 3 条 = 15 条** | 设计 |
| ⇒ 余量 | **7.5 倍** | — |
| ⚠ 纯 `TELEM`（N=1） | 3.3 Hz × 3 = 10 条/s vs 冲刺 7.75 格/s ⇒ 余量 **1.3×** | ⇒ 建图期间保持 **N ≥ 2** |

### T2 生产 / 消费同在一个 ISR

- **生产**：`LINK_Tick` 里采样 `GmcMouse`。
- **消费**：同一 ISR 的后半段 `link_SendUnified()`。

于是环的 `head`/`tail` 都在 ISR 内推进，**没有跨上下文竞争**（§4.3）。
唯一需要留意的是 `GmcMouse` 由任务上下文改、被 ISR 读 —— 这正是 §2.3 那条采样保护要解决的。

### T3 "清空"的确切语义

用户原话是"进入发送缓冲区后清空存储的内容"。**不能整块清**：

- 环里有 20 条、一帧只带走 3 条时，整块清会**丢掉 17 条**。
- 正确定义：**推进 tail（FIFO 消费）**，且**只有本帧真的写进 TX 环才推进**。

若帧已入队但模块把数据吞了（链路灌死）—— 无法感知，属于不可恢复区，host 侧表现为 SEQ 跳号 ⇒ 记洞。

### T4 为什么不让每条省掉坐标

见 §3.1。核心是"错就错成洞，不会静默错位"。

### T5 溢出与背压

- 深度 32 条：搜索 32×450 ms = **14.4 s**、冲刺 32×129 ms = **4.1 s** 的完全静默才会溢出。
- 溢出策略：丢**最旧** + `lossy` sticky（下一帧报出后清）。
- 排空速度：环满 32 条时，3 条/帧 × 17 Hz ⇒ **0.6 s 排空**，远快于重新攒满的速度。

### T6 发车黑窗（已被现有测量覆盖）

- v9.2.1 实测：`MAZE RUN` → 下一帧空窗 **157.9 ms**（= 118 ms 擦 6 页 Flash + 40 ms 重计时），
  之后 2.9 s 才见首个运动任务。
- 关键点：**这 3 s 里车一格都没走** ⇒ 环里根本不会积压，**发车窗口对建图通道零影响**。
- 反倒是这段时间的 `count` 恒为 0，正好让"空帧格式"在真机第一帧就被验证一遍。

### T7 收车 / 中止时的尾巴

- `MAZE STOP` / `ESTOP` 后不再有新的格，但环里可能有未发出的 1~3 条。
- 处理：**不发**额外安全命令（安全网已够复杂，不要为地图数据增加出口）；
  停车后若链路仍在，host 再拉 1~2 帧即可自然带走。
- **安全须知照旧**：链路断死时脚本收车完全无效（`halt()` 三级全进不去），地图数据同样拿不回来。
  这条不能因为新增了建图通道就写成"数据不会丢"。

### T8 `resync` 与 host 清图时机

- **host 主动清图**：`MAZE RUN` 回 ACK OK 的那一刻（host 自己知道要重新跑了）。这是最可靠的时机。
- **固件 `resync` 位**：兜底。覆盖"host 重启 / 掉线重连 / 固件自己清环"这几种 host 不知情的情况。
  一次性，**报完即清**（但只在帧真的写进 TX 环时才清）。
- 若带 `resync` 的那一帧丢了：下一条 entry 仍是绝对坐标 ⇒ 不会把图写错，只是"该清没清"。
  用 `lossy`/`holes` 计数提示即可。

### T9 长跑与回绕

- `ms8` 8 位每 256 ms 绕一圈 —— host 已用"ACK 锚 + 同余还原"，与本通道无关。
- `count`/`head`/`tail` 都是 u8，深度 32 是 2 的幂 ⇒ 用 `& 0x1F` 取模，无除法。

## 9 未采用的方案与理由

| 备选 | 否决理由 |
|---|---|
| 链式编码（1 B 锚点 + 每条 1 B 方向/可通） | 容量 12× 余量用不上，而单条方向错会**静默污染整批**；host 侧还要维护走格与链校验（§3.1） |
| 变长尾部（`23+1+n`） | 速率由 RTT 决定、与帧长无关；省下的字节换不到任何东西，却要拆掉全部 `len==30` 断言 |
| 独立 `TYPE 0x0B` 地图帧 | 停等在途 ≤1 ⇒ 地图帧会**抢占**遥测帧，帧率直接减半 |
| ASCII 事件行 `MAPD x y w #n` | 一条 ≈15 B 且要过 TX 环/`linkEvDrop`，比 2 B 二进制贵一个数量级 |
| 在环里存 `ms8` 时间戳（+32 B RAM） | 逐格耗时用帧到达时间近似（误差 ≤59 ms）已够；需要时再加 |
| 在 `__wallCheck` 里挂钩（精确到指令） | 要改 `utility.c`，红线风险；采样法 ≤1 ms 精度已远超需求 |
| 用 `GucMouseDir` 当方向 | 掉头/坐标平移/越界时会与坐标脱节 |

**附带建议（不在本方案范围，但顺手能解决三个老问题）**：
新增 `MAP LIVE` 命令按块回传固件**当前**墙图（16×16 = 256 B，分 2~3 帧）。
`MAP DUMP` 走的是 Flash 存档快照（`LP_SyncMap()` 全仓无调用点），上电未 `CAL BLOCK` 时回全 0 图、
跑完一轮也拿不到本轮结果；`CAL BLOCK` 又不填 `mapVisited`。有了 `MAP LIVE`，
"重连后一次拿全图"和 §8.2 的对拍都不必依赖 Flash。
